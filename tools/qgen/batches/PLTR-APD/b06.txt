# PLTR-APD batch 06: Domain 5 round 1 (OSDK, APIs, and External Applications), 8 questions

@ PLTR-APD D5 T5.1 applied use-case
S: A team is building an internal React application that lets signed-in employees view and update Work Orders through the OSDK. Which setup fits?
A: A service-based application with a client secret embedded in the React bundle so that every employee shares one identity
B: An application registered for user-based OAuth, scoped to Work Order and its Actions, with the OSDK generated for that scope
C: Direct database access from the browser to the backing datasets, bypassing the Ontology to keep the application simple
D: An application scoped to every object type in the Ontology so that future features never need a new scope
K: B
G: ## User-based apps with scoped OSDK
The exam guide covers registering applications, configuring OAuth, scoping Ontology resources and generating the OSDK, and choosing user-based authentication when users sign in.
## Setup
- Register the application; user-based OAuth flow.
- Scope: Work Order object type and the Actions the app uses.
- Generate the OSDK for that scope; regenerate when scope changes.
Example: each employee signs in and sees only the work orders their permissions allow; updates go through the Actions.
W: User-based OAuth with a scoped OSDK: each employee acts as themselves within the application's narrow scope, and secrets never reach the browser.
X: A=Shared secret in the bundle: anyone can extract it, and every action is attributed to one service identity instead of the employee.
C=Direct dataset access: bypasses Actions, validation and object permissions that the Ontology provides.
D=Every object type: over-scoping means a compromised app can reach far more than it needs.
T: Use user-based OAuth and a narrowly scoped OSDK for applications used by signed-in employees.
V: OSDK, Developer Console

@ PLTR-APD D5 T5.4 applied troubleshooting
S: An OSDK application can read Customer objects but receives an error when calling the Update Customer Action. The signed-in user can run that Action in Workshop. What is the most likely cause?
A: The OSDK does not support invoking Actions at all, so the application must call Workshop instead to perform any update
B: The app's scope lacks that Action; access is the intersection of the app's scope and the user's permissions
C: The user's password expired between reading the object and submitting the Action in the application
D: Customer objects cannot be updated from any external application under any configuration
K: B
G: ## Scope intersection
The exam guide lists diagnosing scope intersections among OSDK skills. What an OSDK app can do is limited by both the user's permissions and the application's configured scope.
## Fix
- Add the Action to the application's scope.
- Regenerate the OSDK if bindings change.
- Retest as the same user.
Example: the scope listed only the Customer object type; adding Update Customer resolves the error.
W: The app's scope excludes the Action: the user's own permission is not enough when the application itself is not scoped to it.
X: A=OSDK cannot invoke Actions: the OSDK supports applying Actions; the error comes from configuration.
C=Expired password: authentication worked moments earlier for the read, and expiry would fail every call, not just the Action.
D=Cannot update externally: external apps update objects through scoped Actions routinely.
T: OSDK access is the intersection of app scope and user permissions; add missing resources to the scope.
V: OSDK, Developer Console

@ PLTR-APD D5 T5.3 applied use-case
S: An external dashboard built with the OSDK needs the total contract value per region across 2 million Contract objects. How should it be retrieved?
A: Fetch all 2 million objects page by page into the dashboard and sum the contract values in the user's browser
B: Use an OSDK aggregation (group by region, sum of value) so the platform returns only the totals
C: Export the contracts to a CSV every night and have the dashboard parse the file
D: Call the REST API once per contract to read its value and region
K: B
G: ## Aggregate on the platform
The exam guide lists fetching, paginating and aggregating among OSDK skills. Totals over millions of objects should be computed where the data lives.
## Approach
- Aggregation request: group by region, sum value.
- Results: one row per region.
- Pagination only when individual objects are needed.
Example: the dashboard receives twelve region totals in one call.
W: Platform-side aggregation through the OSDK: the dashboard gets the answer, not two million objects.
X: A=Fetch everything: millions of objects transferred and summed in a browser; slow and fragile.
C=Nightly CSV: stale, ungoverned and outside the OSDK's permission model.
D=One call per contract: two million calls hit rate limits and take hours.
T: Use OSDK aggregations for totals rather than fetching and summing objects client-side.
V: OSDK

@ PLTR-APD D5 T5.4 applied troubleshooting
S: After a property was renamed in the Ontology, an external OSDK application started failing at runtime with field errors, although the build passed weeks ago. What should be done?
A: Rename the property back in the Ontology so that the external application continues to work unchanged forever
B: Regenerate the OSDK, update code using the old name, and coordinate future renames through lineage
C: Catch and ignore the field errors in the application so that users stop seeing them
D: Rebuild the application with the old OSDK package, which is guaranteed to match the current Ontology
K: B
G: ## Stale SDK packages
The exam guide lists stale SDK packages among OSDK failure modes. Generated bindings reflect the Ontology at generation time.
## Fix
- Regenerate the OSDK; compile errors now show every affected use.
- Update the code; test; deploy.
- Process: Ontology changes check external consumers and plan compatible transitions.
Example: `customerName` became `displayName`; regeneration surfaces four call sites to update.
W: Regenerate and update, then coordinate future changes: the application matches the current Ontology and the next rename is planned.
X: A=Rename back: freezes the Ontology for one consumer instead of updating that consumer.
C=Ignore errors: users silently get missing fields, and nobody fixes the mismatch that caused them.
D=Old package: the old package is exactly what no longer matches.
T: Regenerate the OSDK after Ontology changes and coordinate breaking changes with external consumers.
V: OSDK, Workflow Lineage

@ PLTR-APD D5 T5.2 applied comparison
S: Which application most clearly calls for service-based rather than user-based authentication?
A: An internal application where analysts sign in each morning and edit the objects they own through governed Actions
B: A nightly integration with no user present that syncs approved orders to an ERP
C: A Workshop module embedded in an internal portal for managers
D: A mobile application used by field staff who sign in each morning
K: B
G: ## When there is no user
The exam guide asks you to choose user-based or service-based authentication. Service-based fits headless processes; user-based fits applications where people act as themselves.
- Nightly integration: no user; a service client with minimal scope.
- Analyst app, embedded module, field app: users present; user-based.
Example: the ERP sync runs at 02:00 with client credentials limited to reading approved orders.
W: A headless nightly integration: no user is present, so a narrowly scoped service client is the appropriate identity.
X: A=Analysts editing objects: users are present and should act as themselves for permissions and audit.
C=Embedded module for managers: managers sign in; their own permissions should apply.
D=Field mobile app: staff sign in; user-based authentication keeps actions attributable.
T: Use service-based authentication for headless integrations and user-based for applications people sign in to.
V: OSDK

@ PLTR-APD D5 T5.4 applied troubleshooting
S: An external application calling Foundry APIs works in testing but receives rate-limit errors in production at peak hours. What should the developer change?
A: Retry every failed request immediately in a tight loop until it succeeds, so that no request from any user is ever lost
B: Reduce call volume (batch, aggregate, cache stable data) and add exponential backoff with jitter
C: Create many separate applications with different credentials so that each stays under the limit
D: Ask users to avoid using the application during peak hours
K: B
G: ## Living within rate limits
The exam guide lists rate limits among OSDK diagnostics. The remedies are fewer calls and polite retries.
## Changes
- Batch and aggregate; avoid one call per object.
- Cache data that changes rarely.
- Backoff with jitter; surface persistent failures.
Example: replacing per-row reads with one aggregation and caching reference data cuts calls by 90%; errors disappear.
W: Fewer, larger calls with caching and backoff: the application stays within limits and recovers gracefully when it touches them.
X: A=Tight retry loop: multiplies the load that triggered the limit and makes the errors worse.
C=Many applications: evades limits by multiplying identities, which complicates governance and audit.
D=Avoid peak hours: shifts the problem onto users and fixes nothing.
T: Handle rate limits by reducing call volume and using backoff with jitter.
V: OSDK, REST API

@ PLTR-APD D5 T5.1 applied tradeoff
S: A requirement asks for an internal approval workflow with forms, tables and charts for 200 employees. A developer proposes building a custom React application with the OSDK. What should be considered first?
A: Always build custom applications, since they are more flexible than any native tool
B: Whether Workshop meets the need with less code; use the OSDK when custom UX or external users require it
C: Building both a Workshop module and a custom React application and letting each employee decide which one to use
D: Avoiding both and using emailed spreadsheets for approvals
K: B
G: ## Workshop, OSDK or hybrid
The exam guide's self-check: given an internal, external or embedded requirement, choose Workshop, OSDK or a hybrid and justify it.
## Reasoning
- Internal forms, tables and charts: Workshop's native strengths.
- OSDK when needed: custom UX, external audiences, embedding in other products.
- Maintenance: native modules avoid custom build and hosting.
Example: the approval workflow ships in Workshop in a week; a later partner portal uses the OSDK.
W: Prefer the native tool when it meets the need, and reach for the OSDK for requirements Workshop does not serve.
X: A=Always custom: more code, hosting and maintenance without a requirement that justifies it.
C=Both: duplicated effort and two sources of truth for one workflow.
D=Emailed spreadsheets: approvals happen outside the platform with no validation, permissions or audit trail.
T: Choose Workshop when it meets the need; use the OSDK for custom, external or embedded requirements.
V: Workshop, OSDK

@ PLTR-APD D5 T5.2 advanced use-case
S: A public-facing portal must show customers the status of their own orders. Customers do not have Foundry accounts. How should access be designed?
A: Create a Foundry account for every customer and give each one Viewer on the orders project
B: A backend with a service client scoped to order status that authenticates customers and returns only their orders
C: Embed a service secret in the portal's JavaScript so that the browser can call Foundry directly for each customer
D: Publish all orders on a public page and let customers search for their own order number
K: B
G: ## External users without platform accounts
The exam guide asks you to choose authentication without exposing secrets and to scope resources narrowly.
## Design
- Backend holds the service credentials; scope limited to the order status data needed.
- The portal authenticates customers in its own system and the backend filters by customer.
- Audit and rate limiting at the backend.
Example: a customer signs in to the portal and sees three orders; the backend queried only those.
W: A server-side service client with minimal scope and per-customer filtering: customers see their own orders and no secret reaches the browser.
X: A=Accounts for every customer: inappropriate for a public audience and over-permissions them on a project.
C=Secret in JavaScript: anyone can extract it and read every order.
D=Public page: every customer's orders become visible to anyone on the internet who can guess or search a number.
T: Serve external users through a backend with scoped service credentials and per-user filtering.
V: OSDK, Developer Console
