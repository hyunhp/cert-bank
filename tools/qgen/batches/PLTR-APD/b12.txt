@ PLTR-APD D3 T3.2 applied use-case
S: A function must return each warehouse's count of overdue shipments for a dashboard of 300 warehouses, computed from millions of Shipment objects. Which implementation is appropriate?
A: Iterate over all Shipment objects in the function, checking each one's due date and counting overdue shipments per warehouse in a dictionary
B: Filter shipments to overdue status server-side and aggregate counts grouped by warehouse, returning one row per warehouse
C: Return every Shipment object to the dashboard and let a chart widget count overdue items per warehouse in the browser
D: Ask each warehouse manager to count their overdue shipments manually and type the number into a form every morning
K: B
G: ## Server-side aggregation
The exam guide lists filtering and aggregating among function skills. Counting across millions of objects is an aggregation the platform performs efficiently.
## Implementation
- Filter: status overdue (or due date < today and not delivered).
- Aggregate: count grouped by warehouse.
- Return: 300 rows.
Example: the dashboard loads in a second with current counts.
W: Server-side filter and group-by count: the dashboard gets 300 numbers instead of millions of objects.
X: A=Iterate all objects: millions of loads in a function exceed time and memory limits.
C=Return everything to the browser: transfers millions of objects that the browser cannot handle.
D=Manual counts: slow, error-prone and stale by the time anyone reads them.
T: Aggregate large object sets server-side in functions.

@ PLTR-APD D3 T3.4 applied use-case
S: A team wants confidence that a pricing function behaves correctly before publishing a new version. What testing approach fits?
A: Publish the new version and watch production for complaints during the first week
B: Unit tests on representative and edge inputs plus a branch run against real objects before publishing
C: Test only the happy path with one typical example, since edge cases such as missing tariffs rarely occur in practice
D: Ask the AI assistant whether the function is correct and publish if it agrees
K: B
G: ## Testing before publishing
The exam guide asks you to explain how a function will be tested and published, and to test and diagnose failures.
## Approach
- Unit tests: normal, edge and error cases.
- Branch run with real objects; compare with expected results.
- Publish a new version; monitor.
Example: a test with a missing tariff reveals a null-pointer path that is fixed before release.
W: Unit tests on edge cases plus a branch run on real data: defects are found before any consumer sees the new version.
X: A=Publish and watch: customers and consumers become the test suite.
C=Happy path only: edge cases are exactly where pricing errors cost money.
D=Ask the assistant: a model's opinion about correctness is not a test and catches none of the edge cases that matter.
T: Test functions with edge-case unit tests and branch runs before publishing versions.
V: Functions, branches

@ PLTR-APD D3 T3.1 applied tradeoff
S: A function needs to call an external currency API and parse its response, and it is maintained by engineers fluent in TypeScript. Another candidate implementation uses AIP Logic to "interpret" the API response. Which is better?
A: AIP Logic, since language models are good at reading API responses and adapting to format changes automatically
B: A TypeScript v2 function with explicit parsing and error handling for the structured response
C: A Workshop formula that calls the API directly from the browser on each page load
D: Manual entry of exchange rates by finance staff each morning
K: B
G: ## Structured data is code's job
The exam guide asks you to choose a paradigm by determinism, runtime capabilities and maintainer audience. A structured API response has one correct parse.
## Implementation
- Typed parsing; errors handled explicitly.
- Retries and timeouts as needed.
- Tests with sample responses, including malformed ones.
Example: a malformed response raises a clear error rather than a guessed rate.
W: Deterministic TypeScript parsing with error handling: exact results, testable behaviour and the team's own language.
X: A=AIP Logic: adds cost and nondeterminism and may silently produce a wrong rate.
C=Browser formula: exposes the API from the client and duplicates calls on every load.
D=Manual entry: error-prone and unnecessary when an API exists.
T: Parse structured responses deterministically in code, not with a language model.
V: Functions

@ PLTR-APD D3 T3.3 applied use-case
S: A function computes a credit limit used by an Action. Auditors want to know, for any approved limit, which version of the logic produced it. What should be in place?
A: Nothing, since auditors can always read the current function code to infer how past values were computed
B: Published function versions, with the Action recording the version used alongside the result
C: A comment in the code noting the date of each change
D: A spreadsheet where developers note which version they think was live each month
K: B
G: ## Provenance and versioning
The exam guide lists provenance and versioning among function concepts. Results that matter later must point to the logic that produced them.
## Design
- Publish versions; the Action calls a specific version.
- Record version id with the result.
- Old versions retained for reproduction.
Example: limit L-882 shows "computed by creditLimit v7"; auditors rerun v7 on the stored inputs.
W: Versioned functions with the version recorded on each result: any past value is traceable to the exact logic.
X: A=Read current code: the current code may differ from the version that computed past values.
C=Comments: a dated comment in the code is not linked to any stored result and goes out of date as the code changes.
D=Spreadsheet guesses: developers' recollections of which version was live are unreliable and give auditors nothing to verify.
T: Record the function version used with consequential results.

@ PLTR-APD D3 T3.2 applied troubleshooting
S: A function that traverses Customer → Orders → Items → Supplier for a single customer works in development but times out for some customers in production. What is the most likely cause?
A: The development environment has faster networking, which explains why the function only times out in production
B: An unbounded multi-hop traversal loading huge object counts for large customers; bound it
C: The production function is out of date and needs to be republished with the same code to start working
D: The customers with timeouts have corrupted data that must be deleted
K: B
G: ## Unbounded traversal
The exam guide warns about unsafe or unbounded link traversal among function failures. Multi-hop traversal multiplies object counts for large customers.
## Fix
- Filter at each hop (recent orders, open items).
- Aggregate where only counts or sums are needed.
- Limits and pagination where lists are needed.
Example: a customer with 20,000 orders and 300,000 items now returns in 400 ms using filtered hops and an aggregation.
W: Bound the traversal: development data was small, production customers multiply the objects loaded at each hop.
X: A=Faster networking: the difference is data volume per customer, not the environment.
C=Republish: republishing identical code changes nothing; the same traversal times out for the same customers.
D=Corrupted data: large customers are valid; the function does not scale to them.
T: Bound multi-hop link traversals with filters, limits and aggregations.

@ PLTR-APD D3 T3.3 applied comparison
S: A developer is explaining to a new team member how function-backed Actions apply their changes and how they are governed. Which statement about function-backed Actions is correct?
A: A function-backed Action applies edits as the function executes, one by one, so partial results are visible if it fails midway
B: The function returns edits that the Action applies after validation, so the result is governed by the Action's permissions and criteria
C: A function-backed Action bypasses the Action's submission criteria because the function is trusted
D: Function-backed Actions cannot edit more than one object
K: B
G: ## How function-backed Actions work
The exam guide lists function-backed Actions among function concepts. The function computes edits; the Action governs and applies them.
- Edits returned and applied by the Action.
- Permissions and submission criteria still apply.
- Multiple objects can be edited in one submission.
Example: approving a claim edits the claim, a payment and a policy in one Action.
W: The function returns edits and the Action applies them under its governance: computation and control are cleanly separated.
X: A=Edits applied one by one: edits are returned and applied by the Action, not streamed during execution.
C=Bypasses criteria: the Action's criteria and permissions still govern execution.
D=One object only: function-backed Actions commonly edit several objects.
T: Function-backed Actions return edits that the Action validates and applies.

@ PLTR-APD D3 T3.4 applied troubleshooting
S: A function called from Workshop returns correct results when the developer runs it but an error for analysts: "object type not found". What is the likely cause?
A: The analysts are using a different browser that does not support the function's return type when it is displayed in Workshop
B: The function queries an object type analysts cannot see; under user-scoped execution it looks missing
C: The function is too slow for analysts, so the platform cancels it with a misleading message
D: The analysts' module is in a different time zone
K: B
G: ## Visibility looks like absence
The exam guide asks you to diagnose function failures and to understand user-scoped execution. Without access, a resource can appear not to exist.
## Checks
- Analysts' access to the object type and its data.
- Decide: grant access, or change the function to return only data they may see.
Example: the function reads an internal Cost object type restricted to finance; the analyst version omits it.
W: User-scoped access hides the object type from analysts: the error reflects permissions, not a missing resource.
X: A=Different browser: functions run on the server; browsers do not affect object type resolution.
C=Slowness: a timeout reports differently; this is about visibility.
D=Time zone: the module's time zone affects how dates display, not whether an object type can be found.
T: When functions fail only for some users, check whether those users can see the resources the function reads.
V: Functions, permissions

@ PLTR-APD D3 T3.1 advanced use-case
S: A team must implement routing logic that assigns incoming cases to queues using fifteen explicit business rules, plus a free-text field that occasionally needs interpretation when no rule applies. Who will maintain it: business analysts who change rules monthly. What design fits?
A: An AIP Logic function that applies all fifteen rules from a long prompt and interprets the free text in the same call
B: Rules in deterministic code driven by a governed rules dataset analysts can update, with an AI step only for unmatched cases
C: A TypeScript function with all fifteen rules hard-coded, released by engineers every time analysts want a change
D: Manual routing by a supervisor reading every case
K: B
G: ## Rules as data, AI for the residual
The exam guide asks you to choose by determinism, maintainability and maintainer audience, and to use AI only where it adds value.
## Design
- Rules dataset maintained by analysts through a governed process.
- Deterministic function applies the rules.
- AI step for cases no rule matches, with typed output and review.
Example: 92% of cases route by rule; 8% go through AI classification and a review queue.
W: Deterministic, data-driven rules analysts can maintain, with AI reserved for cases rules cannot handle: correct, maintainable and economical.
X: A=Rules in a prompt: nondeterministic application of explicit rules.
C=Hard-coded rules: every monthly rule change needs an engineering release, and analysts cannot maintain their own rules.
D=Manual routing: a supervisor reading every case does not scale and delays every assignment.
T: Keep explicit rules deterministic and maintainable as data; use AI only for the residual.
V: Functions, AIP Logic
