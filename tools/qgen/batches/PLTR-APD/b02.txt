# PLTR-APD batch 02: Domain 1 round 1 (Ontology Schema Design and Workflow Assembly), 8 questions

@ PLTR-APD D1 T1.1 applied use-case
S: Three object types (Vehicle, Drone and Vessel) each have a location, a status and an operator, and a dispatch application must list all of them together and run the same Assign Operator Action on any of them. Which Ontology construct supports this cleanly?
A: Merge the three object types into one generic Asset type with dozens of mostly empty properties covering every kind of equipment
B: An interface declaring the shared properties, implemented by all three types, so the app and Action work against the interface
C: Three separate applications, one per object type, each with its own copy of the Assign Operator Action and list view
D: A dataset that unions the three backing datasets into one table, displayed in the application without any object types at all
K: B
G: ## Interfaces for shared shape
The exam guide lists interfaces and shared properties among Ontology constructs. When several object types share a shape that applications act on, an interface describes that shape once.
## Design
- Interface `Dispatchable`: location, status, operator.
- Vehicle, Drone and Vessel implement it, keeping their own specific properties.
- The dispatch list and the Assign Operator Action target the interface.
Example: one list shows 300 vehicles, 40 drones and 12 vessels; one Action assigns operators to any of them.
W: An interface implemented by the three types: applications and Actions work across them through the shared shape, while each type keeps its own identity and specific properties.
X: A=One generic type: collapses distinct entities into a wide, sparse type that is hard to validate and evolve.
C=Three apps and three Actions: duplicates logic and screens, and they drift apart over time.
D=Union dataset without objects: loses Actions, links and object-level permissions that the application needs.
T: Use interfaces to let applications and Actions work across object types that share a shape.
V: Ontology Manager

@ PLTR-APD D1 T1.2 applied troubleshooting
S: A link between Customer and Account was configured as one-to-one, but some customers have several accounts, and the application shows only one account for them seemingly at random. What should the developer conclude and do?
A: The application widget is buggy and should be replaced with a different widget that displays every linked account correctly
B: The cardinality does not match the data; make it one-to-many, verify with counts, and update consumers
C: Delete the extra accounts so that each customer has exactly one account and the one-to-one link becomes correct again
D: Keep the link and add a note in the application telling users that only one account is shown for each customer
K: B
G: ## Cardinality must match the data
The exam guide asks you to select appropriate cardinality and to check whether the data supports the relationship. A one-to-one link over one-to-many data silently hides rows.
## Fix
- Count accounts per customer in the backing data.
- Change the link to one-to-many; review keys.
- Update applications and Functions that assumed a single account; roll out on a branch.
Example: 8% of customers have two to five accounts; after the change the customer page lists all of them.
W: Correct the cardinality to match the data and migrate consumers: users see every account and logic stops relying on a false assumption.
X: A=Widget bug: the widget shows what the link returns; the link definition is wrong.
C=Delete accounts: destroys real business data to fit a modelling mistake.
D=Warning note: users keep seeing an incomplete account list, and Functions relying on the link stay wrong.
T: Verify link cardinality against the data before modelling, and fix the model when the data disagrees.
V: Ontology Manager

@ PLTR-APD D1 T1.3 applied use-case
S: A claims team needs a workflow: an adjuster reviews a claim in an application, records a decision with validation, and a follow-up task is created for payments when a claim is approved. Which assembly of components fits?
A: A single AIP Logic function that reads the claim, decides on the adjuster's behalf and writes the payment task without any user interaction
B: A Workshop module for review, an Action Type for the validated decision, and an Automate step that creates the payment task on approval
C: A spreadsheet export of claims that adjusters edit and email back to the payments team for manual processing
D: A pipeline transform that recomputes all claim decisions nightly from the adjusters' comments in a free-text field
K: B
G: ## Assembling an operational workflow
The exam guide asks you to assemble workflows across Ontology entities, Workshop, Functions, Actions and Automate, using each for its role.
## Assembly
- Workshop: review the claim and its context.
- Action Type: record the decision with validation and an audit trail.
- Automate: on approval, create the payment task (background, retry-safe).
Example: an approval at 10:02 creates a payment task at 10:03 assigned to the payments queue.
W: Workshop for interaction, an Action for the governed state change and Automate for the follow-up: each component does the part it is designed for.
X: A=Logic decides alone: removes the adjuster's decision from a consequential process.
C=Spreadsheet by email: decisions leave the platform with no validation, no audit trail and days of delay.
D=Nightly recompute from free text: decisions should be recorded explicitly, not inferred from comments.
T: Assemble workflows from Workshop for interaction, Actions for governed changes and Automate for follow-ups.
V: Workshop, Action types, Automate

@ PLTR-APD D1 T1.4 applied use-case
S: A developer must rename a property on an object type that several applications use. Before changing anything, they want to know which Workshop modules, Functions and Actions depend on it. Which capability helps most?
A: Searching through all project folders by hand and opening every module one at a time to look for the property name
B: Workflow Lineage, to see the applications, Functions, Actions and automations that use the object type and property
C: Asking in the team chat whether anyone remembers using that property in their applications
D: Renaming the property and waiting to see which applications report errors afterwards
K: B
G: ## Impact analysis before change
The exam guide asks you to use Workflow Lineage to understand impact, troubleshoot access and plan changes without breaking live consumers.
## Use
- Open the object type in Workflow Lineage; trace dependent modules, Functions, Actions and automations.
- List owners; plan a compatible transition (new property, migration, removal).
Example: lineage shows two modules and one Function using the property; they are updated on a branch before the rename merges.
W: Workflow Lineage reveals dependents before the change: the rename can be planned so no live consumer breaks.
X: A=Manual search: slow, incomplete and misses Functions and automations.
C=Ask in chat: people forget, leave or never knew; recollections miss Functions and automations that use the property.
D=Rename and wait: every dependent module and Function breaks in production before anyone has a plan to fix it.
T: Use Workflow Lineage to find dependents before changing Ontology resources.
V: Workflow Lineage

@ PLTR-APD D1 T1.1 applied comparison
S: A property "priority" appears on Ticket, Task and Incident object types and must mean the same thing with the same allowed values everywhere. Which construct ensures consistency?
A: Three independent string properties defined separately on each object type, documented in a wiki page that lists the allowed values
B: A shared property (with a value type constraining allowed values) used by all three object types
C: A numeric property on each type where every team chooses its own scale of priority values
D: A free-text property on each type, since teams can agree informally on the wording they use
K: B
G: ## Shared properties and value types
The exam guide lists shared properties and value types among modelling constructs. A shared property defines meaning once; a value type constrains values.
## Design
- Shared property `priority` with value type allowing low, medium, high, critical.
- Used by Ticket, Task and Incident.
- Filters and Actions behave consistently across types.
Example: a cross-type "critical" filter returns tickets, tasks and incidents alike.
W: One shared property constrained by a value type: the same meaning and the same allowed values on every object type that uses it.
X: A=Independent properties with a wiki: drift is guaranteed and nothing enforces the values.
C=Team-chosen numeric scales: identical numbers mean different things across types.
D=Free text: "High", "high" and "HIGH" become different values, so filters and Actions behave inconsistently.
T: Use shared properties with value types for attributes that must mean the same thing across object types.
V: Ontology Manager

@ PLTR-APD D1 T1.2 applied troubleshooting
S: Users report that edits they made to Supplier objects in an application disappeared after the backing data was refreshed. The data team says supplier codes were reformatted in the source. What is the most likely cause?
A: The application failed to save the edits, and users should have clicked the save button a second time
B: The reformatted codes changed the primary key, so new objects appeared and the edits stayed on old keys
C: The edits were rejected by validation, which silently discards changes that do not match the new data format
D: Ontology edits always expire after a data refresh, so users must re-enter them every time the source updates
K: B
G: ## Stable identity preserves edits
The exam guide asks you to select stable identity. User edits are attached to primary keys; if the key value changes, the object is effectively new.
## Response
- Confirm: compare old and new key values.
- Repair: map old keys to new and migrate edits.
- Prevent: key on a stable identifier, not a formatted code; coordinate source changes.
Example: "SUP-0042" became "SUP42"; mapping restores 900 edits.
W: A key change re-identified the objects: edits remain on the old identities, which is why they seem to vanish.
X: A=Save twice: the edits were saved; they are attached to keys that no longer exist.
C=Silent validation: validation rejects at submission; it does not delete saved edits later.
D=Edits expire: user edits persist across refreshes as long as the primary key stays the same; they do not expire.
T: Key objects on stable identifiers so source formatting changes do not detach user edits.
V: Ontology Manager

@ PLTR-APD D1 T1.3 applied tradeoff
S: A team proposes building a new application by copying an existing module and its Actions, then changing them, instead of reusing them. The two applications serve similar workflows for different regions. What is the better approach?
A: Copy everything, since independent copies avoid coordination between the two teams that own the regional applications
B: Reuse shared Actions, Functions and object types, and parameterize or embed the module for regional differences
C: Build the second application entirely in an external tool so the two cannot interfere with each other
D: Ask the original team to add the second region's screens into their module as extra tabs
K: B
G: ## Reuse over duplication
The exam guide asks you to assemble workflows from reusable parts and preserve module interfaces. Copying Actions and logic doubles maintenance and lets rules diverge.
## Approach
- Shared Action Types and Functions for the common logic.
- A module parameterized by region (variables) or embedded with region-specific inputs.
- Region-specific differences isolated in configuration.
Example: a validation fix applies to both regions at once because both use the same Action Type.
W: Shared components with parameterized differences: one place to fix logic, consistent rules, and regional variation where it belongs.
X: A=Copy everything: fixes must be made twice and behaviour diverges.
C=External tool: rebuilds what the platform already provides and loses Ontology integration, Actions and governance.
D=Extra tabs in one module: couples two teams' screens without solving reuse cleanly.
T: Reuse Actions and Functions and parameterize modules instead of copying them.
V: Workshop, Action types

@ PLTR-APD D1 T1.4 advanced troubleshooting
S: After an object type's permissions were changed, a Workshop module shows empty tables for some users while others see data. The developer needs to find which resource in the workflow causes this. What is the most efficient approach?
A: Rebuild the module from scratch on the assumption that the empty tables are caused by a corrupted layout
B: Trace module, object type and backing data with Workflow Lineage and access checks to find the denying layer
C: Grant the affected users Owner on every project in the workflow so that permission problems cannot occur
D: Tell affected users to log out and back in repeatedly until the tables start showing data
K: B
G: ## Tracing access through the workflow
The exam guide lists Workflow Lineage for troubleshooting access and warns against solving access problems by over-permissioning.
## Approach
- Lineage: module → object types → backing datasets or views.
- Check access for an affected user at each layer: object type, restricted view, marking.
- Change the exact control that should change.
Example: the object type is now backed by a restricted view whose policy excludes the users' region; the policy is corrected.
W: Lineage plus per-layer access checks: the exact denying control is found and fixed without broad grants.
X: A=Rebuild the module: the module is fine; data access differs by user.
C=Owner everywhere: over-permissioning that ignores the real cause.
D=Log out repeatedly: permissions are evaluated on each request; signing in again does not change what the user may read.
T: Trace access failures through Workflow Lineage and fix the exact layer that denies access.
V: Workflow Lineage, permissions
