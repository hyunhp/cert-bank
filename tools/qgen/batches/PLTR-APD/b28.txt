# PLTR-APD batch 28: Domain 3 round 4 (Ontology Functions), 8 questions

@ PLTR-APD D3 T3.2 applied use-case
S: A function must find all Equipment objects at a site that have no inspection in the last 90 days. Sites have up to 3,000 pieces of equipment, each with many inspections. Which approach is efficient?
A: Load every piece of equipment and every inspection into memory, then compare dates for each piece in nested loops inside the function
B: Query equipment at the site and use a server-side filter or aggregation on linked inspections in the last 90 days to find those with none
C: Ask inspectors to keep a spreadsheet of equipment they have not inspected recently and upload it each week
D: Return all equipment to Workshop and let users scroll through each item's inspection history manually
K: B
G: ## Server-side filtering over links
The exam guide lists querying, filtering, aggregating and traversing links among function skills, and warns about unbounded traversal.
## Approach
- Object set: equipment at the site.
- Filter or aggregate linked inspections with date ≥ today − 90.
- Return equipment with a count of zero.
Example: the function returns 42 overdue items in under a second for a 3,000-item site.
W: Server-side filtering and aggregation over the link: the query finds overdue equipment without loading thousands of inspections into memory.
X: A=Nested loops in memory: loads every inspection for the site and becomes slow and fragile as history grows.
C=Inspector spreadsheet: manual, weekly and outside the platform, so overdue items are found late or not at all.
D=Manual scrolling: pushes thousands of checks onto users who will inevitably miss some.
T: Find objects by conditions on linked objects with server-side filters or aggregations.

@ PLTR-APD D3 T3.4 applied troubleshooting
S: A function-backed Action fails for some objects with an error that a linked object could not be found. The function traverses Order → Customer and reads the customer's tier. What should be checked?
A: Whether the Action's form is too wide for the screen, which can hide linked objects from the function at execution
B: Whether some orders lack a resolvable or visible customer, and handle that case explicitly
C: Whether all customers should be deleted and recreated so that the links are rebuilt from scratch
D: Whether the function should catch all errors and continue silently with a default tier
K: B
G: ## Missing or invisible links
The exam guide lists diagnosing function failures and safe traversal among skills.
## Checks
- Orders without a customer id, or with an id that does not resolve.
- Customers the invoking user cannot see.
- Code: handle a missing link with a clear validation message.
Example: 0.5% of orders came from a guest checkout without a customer; the Action now reports "Order has no customer" instead of crashing.
W: Data or permission gaps in the link explain failures on specific objects; handling them explicitly turns crashes into clear messages.
X: A=Form width: the function's execution does not depend on the layout of the form.
C=Recreate customers: the gap is in orders' links or visibility, not in customer identity.
D=Silent default tier: hides the data problem and may quietly apply the wrong tier and pricing to real orders.
T: Handle missing or invisible linked objects explicitly in functions.
V: Functions

@ PLTR-APD D3 T3.1 applied use-case
S: A function must generate a polite rejection email for job applicants based on structured reasons, and the HR team wants the tone adjustable without code changes. Which paradigm and setup fit?
A: A TypeScript function with hard-coded email templates, updated by developers whenever HR asks for different wording
B: AIP Logic with the reasons as typed input, HR-maintained tone guidance, and review before sending
C: A Python function that sends the same fixed sentence to every applicant regardless of the reason
D: Have HR write each rejection email manually without any assistance
K: B
G: ## Language generation with controllable guidance
The exam guide asks you to choose paradigms by LLM needs and maintainer audience.
## Setup
- Inputs: reasons as typed values.
- Guidance: tone instructions HR can maintain.
- Output reviewed by HR before sending (Action).
Example: HR adjusts tone guidance to be warmer; emails change without a code release.
W: AIP Logic with typed inputs and HR-maintained guidance: natural wording that HR controls, with review before anything is sent.
X: A=Hard-coded templates: every wording change needs a developer release.
C=One fixed sentence: ignores the reasons and reads impersonally.
D=Manual writing: HR writes every email by hand, which is slow and inconsistent at high application volumes.
T: Use AIP Logic for language generation with guidance owners can adjust, and review outputs before sending.

@ PLTR-APD D3 T3.3 applied comparison
S: Which practice best supports reliable use of a function by an external application through the OSDK?
A: Changing the function's return type whenever convenient, since external apps can adapt automatically at runtime
B: Publishing versions, documenting the return type, and regenerating the OSDK when the function changes
C: Hiding the function from the OSDK and asking external developers to call internal endpoints directly
D: Returning untyped text so that external apps can parse whatever they need
K: B
G: ## Stable contracts for external consumers
The exam guide lists return types, versioning and generated SDK bindings among function concepts.
- Versions protect consumers from unexpected changes.
- Typed returns generate typed bindings.
- Regeneration updates the external app deliberately.
Example: v3 adds a field; the external app upgrades its SDK and starts using it when ready.
W: Versioned, typed functions with regenerated bindings: external apps get a stable, type-checked contract that changes only when they choose.
X: A=Change whenever convenient: external apps break unexpectedly; there is no runtime adaptation.
C=Internal endpoints: bypasses the supported, scoped interface.
D=Untyped text: external apps lose type safety and must parse free text, which breaks whenever the wording changes.
T: Give external consumers versioned, typed functions and regenerated OSDK bindings.
V: Functions, OSDK

@ PLTR-APD D3 T3.2 applied troubleshooting
S: A function that sums revenue per region returns correct results for small regions but times out for the largest region. Profiling shows it loads all Sale objects for the region and sums in code. What is the fix?
A: Raise the function's timeout limit so that the largest region's sum has enough time to finish loading
B: Use a server-side aggregation (sum grouped by region) instead of loading individual Sale objects
C: Split the largest region into smaller fake regions so each one fits within the time limit
D: Ask users from the largest region to avoid using the function at busy times
K: B
G: ## Aggregate, do not load
The exam guide lists aggregating among function skills. Summing by loading every object scales with data size; aggregation does not.
## Fix
- Aggregation: sum of amount grouped by region.
- Optional filters (period) applied server-side.
Example: the largest region's total returns in 300 ms instead of timing out.
W: Server-side aggregation: totals are computed where the data lives, so the largest region is as fast as the smallest.
X: A=Longer timeout: the load still grows with data and eventually fails again.
C=Fake regions: distorts the data model to hide an inefficient implementation.
D=Avoid busy times: asks the largest region's users to work around an implementation problem that aggregation removes.
T: Use server-side aggregations for sums rather than loading objects into functions.

@ PLTR-APD D3 T3.4 applied use-case
S: A team wants to prevent regressions in a function used by a high-traffic Action. Changes are made weekly. What should be in place?
A: Manual spot checks by the developer who made the change, done on a couple of objects before publishing
B: Unit tests run on every change, a branch run on real objects, and versioned publishing
C: No tests, but a quick rollback if users complain after the weekly change
D: Tests written once at the start of the project and never updated
K: B
G: ## Regression protection for functions
The exam guide asks you to test and diagnose functions and explain how they are tested and published.
## Practice
- Unit tests for rules and edge cases; updated with each change.
- Branch run against real objects.
- Versioned publishing with rollback.
Example: a weekly change breaks rounding for one currency; the unit test fails before release.
W: Maintained tests, branch runs and versioned releases: weekly changes are checked before they reach the Action's users.
X: A=Manual spot checks: miss edge cases and depend on one person.
C=Rollback after complaints: users absorb every regression first.
D=Stale tests: tests written once stop covering the rules as the code changes week after week.
T: Protect frequently changed functions with maintained tests, branch runs and versioned releases.
V: Functions, branches

@ PLTR-APD D3 T3.3 applied use-case
S: An Action uses a function to compute insurance premiums. Regulators require that any premium can be reproduced later. What should the Action record?
A: Only the final premium amount, since the function can always recompute it later from current data
B: The premium, the function version and the input values used
C: A link to the function's source code repository and nothing else
D: The name of the developer who last edited the function
K: B
G: ## Reproducibility needs version and inputs
The exam guide lists provenance and versioning among function concepts.
## Record
- Result, function version, inputs (or a snapshot reference).
- Old versions retained.
Example: the regulator asks about policy P-201; rerunning premiumCalc v8 with the stored inputs gives the same 1,240.
W: Result plus version plus inputs: any premium can be recomputed exactly as it was, even after data and logic change.
X: A=Final amount only: current data and logic may differ, so recomputation would not reproduce the original.
C=Repository link: does not identify which version or inputs were used.
D=Developer name: identifies a person, not the logic version or inputs, so the premium cannot be reproduced.
T: Record function version and inputs with results that must be reproducible.

@ PLTR-APD D3 T3.1 advanced tradeoff
S: A team is choosing how to implement a function that classifies documents by type. A rule-based TypeScript version reaches 85% accuracy; an AIP Logic version reaches 96% on the evaluation set but costs more per call. Volume is 2,000 documents a day, and misclassification causes manual rework. What should guide the decision?
A: Always choose the TypeScript version, since deterministic code is better than AI in every case regardless of accuracy
B: Weigh rework from the accuracy gap against AI cost at this volume, considering rules first and AI for the rest
C: Always choose the AIP Logic version, since higher accuracy always wins regardless of cost
D: Choose whichever version the most senior developer prefers
K: B
G: ## Decide with evidence
The exam guide asks when AI adds value over deterministic logic and to choose based on requirements and maintainability.
## Analysis
- 11 points of accuracy at 2,000/day = about 220 fewer misclassifications daily.
- Rework cost per misclassification versus model cost per call.
- Hybrid: rules for clear cases, AI for the rest.
Example: rules handle 60% with near-perfect accuracy; AI handles the remaining 40%; total cost falls and accuracy stays at 96%.
W: Weigh the accuracy gain against cost at real volume, considering a hybrid: the decision rests on measured value, not on a blanket preference.
X: A=Always code: ignores a large, measured accuracy gain and its rework savings.
C=Always AI: ignores cost and the chance that rules handle many cases perfectly.
D=Seniority: a preference is not evidence; accuracy, cost and rework at real volume should decide.
T: Choose between rules and AI by measured accuracy, cost and rework at real volume.
V: AIP Logic, Functions
