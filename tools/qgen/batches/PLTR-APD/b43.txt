# PLTR-APD batch 43: Domain 2 round 6 (Action Types and Write-Back Patterns), 8 questions

@ PLTR-APD D2 T2.2 applied use-case
S: A Book Room Action lets employees reserve meeting rooms. Double bookings happen when two people book the same room for overlapping times. How should the Action prevent this?
A: Show a reminder on the booking form asking people to check the room calendar carefully before submitting a booking
B: Criteria checking for overlapping bookings at execution, naming any conflicting booking
C: Let double bookings happen and ask the office manager to resolve conflicts by email every morning
D: Allow each employee to book only one room per month so that overlaps are rare
K: B
G: ## Execution-time conflict checks
The exam guide asks you to validate at execution and reason about concurrency.
## Configuration
- Criteria: no existing booking for the room overlaps the requested interval.
- Message: "Room booked 10:00–11:00 by J. Park".
- Concurrency: the check runs at execution, so two simultaneous requests cannot both pass.
Example: the second of two overlapping requests is rejected with the conflicting booking named.
W: Overlap criteria evaluated at execution: double bookings are prevented for every submission path, with a helpful message.
X: A=Reminder on the form: people still miss conflicts, especially when two of them book at the same moment.
C=Morning email resolution: double-booked meetings collide before anyone fixes them.
D=One booking per month: an arbitrary restriction that destroys the usefulness of booking.
T: Prevent conflicting bookings with execution-time submission criteria.

@ PLTR-APD D2 T2.1 applied comparison
S: Which change is a good reason to convert a declarative Action to a function-backed Action?
A: The team wants to rename the Action's button label in the Workshop module to match new wording used by the business
B: The Action must now compute a value from several linked objects and edit multiple objects together
C: The Action needs one more simple parameter copied into a property
D: The Action's description text needs to be updated
K: B
G: ## When functions are needed
The exam guide recommends function-backed Actions for computation, branching or cascading changes.
- Computing from linked objects and multi-object edits: function-backed.
- Labels, simple parameters and descriptions: declarative configuration.
Example: a Close Project Action now computes final cost from linked invoices and closes child tasks.
W: Computation across linked objects with multi-object edits is the case declarative rules cannot express, so the conversion is justified.
X: A=Button label: a presentation setting in the module, unrelated to the Action's implementation.
C=One simple parameter: declarative rules handle copying a parameter into a property.
D=Description text: changing documentation has no bearing on how the Action computes or edits anything.
T: Convert to function-backed Actions when logic requires computation or cascading edits.
V: Action types

@ PLTR-APD D2 T2.3 applied troubleshooting
S: An Action works for users in the London office but fails with a permission error for the Paris office, although both offices belong to the same team group. What should be checked?
A: Whether Paris users are using a different keyboard layout that changes the submitted values
B: Whether the target objects for Paris carry a regional marking or policy that Paris users lack
C: Whether the Action only works in English
D: Whether Paris users should be given administrator rights
K: B
G: ## Object-level differences
The exam guide asks you to identify the exact permission control involved in Action failures.
## Checks
- Compare markings and policies on London versus Paris objects.
- Compare user attributes used by policies.
- Fix the specific control with the data owner.
Example: Paris objects carry an "EU-Restricted" marking; Paris users were never added to it.
W: An object-level control differs by region: the failure follows the objects and users' attributes, not the team group.
X: A=Keyboard layout: typing differences can change inputs but never produce a permission error.
C=English only: Actions are not restricted by language, and the error is about permissions, not input.
D=Administrator rights: grants sweeping access without understanding which control is blocking Paris users.
T: When Action failures follow regions or groups of objects, compare their markings and policies.
V: Action types, markings

@ PLTR-APD D2 T2.4 applied use-case
S: Users ask why their Action submissions are rejected, and the error messages say only "Validation failed". What should the developer improve?
A: Nothing; users should contact the developer by email to ask what went wrong with each submission
B: Give each submission criterion a specific message naming the failed rule and how to fix it
C: Remove the validation rules so that submissions are no longer rejected
D: Log the failures silently without telling users anything
K: B
G: ## Actionable validation messages
The exam guide's safe-UX guidance: distinguish invalid input from denied access and transient failure, and tell users what happened.
## Improvement
- Message per criterion: "Amount exceeds your limit of 500."
- Guidance on what to change.
Example: rejections drop as users correct inputs themselves.
W: Specific messages per rule: users understand and fix their submissions without contacting anyone.
X: A=Email the developer: slow for users and creates support load for questions a good message would answer.
C=Remove validation: lets invalid submissions in to avoid explaining why they were rejected.
D=Silent logging: users stay confused and keep resubmitting the same invalid input.
T: Give each Action validation rule a specific, actionable message.
V: Action types

@ PLTR-APD D2 T2.2 applied troubleshooting
S: An Action's webhook to an ERP occasionally creates duplicate entries when users click Submit twice quickly. What should be fixed?
A: Ask users to click the Submit button only once and wait patiently for the confirmation message to appear
B: Use an idempotency key per submission for the webhook and disable the button while submitting
C: Remove the webhook and enter ERP data by hand
D: Add a long delay before every webhook call
K: B
G: ## Duplicate submissions
The exam guide asks for idempotency and safe UX for Actions with side effects. A double click sends two submissions in quick succession, and a webhook without idempotency turns each into a separate ERP entry.
## Fix
- Idempotency key per logical submission.
- UI: disable while submitting; show status.
Example: a double click produces one ERP entry.
W: Idempotency plus UI protection: duplicate clicks no longer create duplicate external records.
X: A=Ask users: double clicks and impatient resubmissions will still happen; a request is not a technical control.
C=Manual entry: abandons a working integration and reintroduces typing errors and delays.
D=Long delay: slows every submission and still sends two calls when the user clicks twice.
T: Make Action side effects idempotent and guard against double submission in the UI.
V: Action types, webhooks

@ PLTR-APD D2 T2.3 applied use-case
S: An Action lets agents change a customer's credit limit. Increases above 10,000 must be approved by a risk officer. How should this be implemented?
A: Let agents set any limit and have risk officers review changes once a quarter
B: Criteria allowing agents up to 10,000, with larger increases routed to a risk officer's approval
C: Give agents the risk officer role so that they can approve their own increases
D: Remove the ability to change credit limits entirely
K: B
G: ## Thresholds and approvals
The exam guide asks you to reason about validation, permissions and approvals for consequential changes.
## Design
- Agent Action: criteria limit ≤ 10,000.
- Above: create an approval request object.
- Risk officer Action approves and applies.
Example: an agent requests 25,000; the risk officer approves the next morning and the limit updates.
W: Thresholded criteria with an approval path: routine changes are fast and large ones get the required review.
X: A=Quarterly review: large increases are used before anyone checks.
C=Self-approval: agents approving their own large increases defeats the purpose of a risk officer's review.
D=Remove the ability: blocks legitimate limit changes the business needs every day.
T: Route changes above thresholds to approval Actions.
V: Action types, permissions

@ PLTR-APD D2 T2.4 applied troubleshooting
S: After a release, an Action intermittently fails with errors that the target object was modified by another user. Users retry and it usually works. What does this indicate?
A: The platform is unstable and the Action should be rebuilt from scratch
B: Concurrent edits; show a clear conflict message and refreshed data
C: Users are clicking too fast after the release and should be told to wait ten seconds between consecutive actions
D: The Action should ignore conflicts and always overwrite
K: B
G: ## Concurrency conflicts
The exam guide lists concurrency among Action concerns.
## Handling
- Explain: "This record was updated by someone else; review and resubmit."
- Refresh the object.
- Consider narrower edits to reduce conflicts.
Example: a dispatcher sees the updated assignment and resubmits with current data.
W: Conflict detection is working as intended: users need a clear message and fresh data, not a rebuild.
X: A=Rebuild: the Action is correctly detecting that someone else changed the object; rebuilding would not change that.
C=Wait ten seconds: arbitrary and does not address simultaneous edits by different users.
D=Always overwrite: silently discards whatever the other user just changed, which is worse than a conflict message.
T: Handle concurrent-edit conflicts with clear messages and refreshed data.
V: Action types

@ PLTR-APD D2 T2.1 advanced tradeoff
S: An Action creates an order, reserves inventory across three warehouses, and charges a payment provider. The payment step sometimes fails after inventory is reserved. What design balances consistency and reliability?
A: Do all steps synchronously in one Action and leave reservations in place if payment fails, cleaning them up manually
B: Reserve atomically with the order, charge asynchronously, and release reservations if payment fails
C: Charge the payment first, then create the order whenever inventory happens to be available
D: Skip inventory reservations and hope stock is available at shipping time
K: B
G: ## Internal atomicity and compensations
The exam guide asks about atomicity and partial failure in Actions and integrations.
## Design
- Function-backed Action: order + reservations together.
- Payment via async, idempotent call with status.
- On failure: compensating release of reservations; user notified.
Example: a declined card releases the three reservations within a minute and marks the order "payment failed".
W: Atomic internal edits with an asynchronous payment and compensations: consistent state and clean recovery when an external step fails.
X: A=Manual cleanup: reservations from failed payments block stock for other customers until someone notices.
C=Charge first: customers may be charged for items that turn out to be unavailable.
D=No reservations: two customers can buy the last unit, leading to overselling and cancellations.
T: Combine atomic internal edits with idempotent external steps and compensations.
V: Action types, Automate
