# PLTR-APD batch 19: Domain 2 round 3 (Action Types and Write-Back Patterns), 8 questions

@ PLTR-APD D2 T2.2 applied use-case
S: A Reassign Ticket Action lets team leads move a ticket to another agent. The business requires that the new agent belongs to the same team and is not on leave. How should this be enforced?
A: Show a warning text in the form reminding team leads to check the new agent's team and leave status before submitting
B: Submission criteria on the Action checking the target agent's team and leave status at execution, with a clear message
C: A weekly report listing reassignments to agents on leave, so that managers can correct them afterwards
D: Remove the reassign capability and let tickets stay with their original agent indefinitely
K: B
G: ## Rules evaluated at execution
The exam guide lists submission criteria and validation among Action configuration and asks you to validate again at execution.
## Configuration
- Criteria: target agent's team = ticket's team; target agent not on leave.
- Message explaining which condition failed.
- Form can pre-filter the agent list, but criteria enforce the rule.
Example: choosing an agent on leave shows "Selected agent is on leave until 20 Oct".
W: Criteria on the Action enforce both rules for every submission path, and users see why a choice was refused.
X: A=Warning text: informs team leads but lets invalid reassignments through whenever someone skips the check.
C=Weekly report: tickets sit with absent agents for days before anyone corrects them.
D=Remove reassignment: blocks a legitimate operational need instead of governing it.
T: Enforce business rules for Actions with submission criteria evaluated at execution.

@ PLTR-APD D2 T2.4 applied troubleshooting
S: An Action's execution history shows frequent failures with a validation message that the "end date must be after start date", but users insist they entered valid dates. What should the developer investigate?
A: Whether users are lying about their inputs, and add a stronger warning to the form telling them to be careful
B: Whether dates are converted unexpectedly (time zones, date-only vs timestamp, format) between form and validation
C: Whether the validation should be deleted, since users keep hitting it
D: Whether the Action should be rebuilt as a function-backed Action, which never has validation problems
K: B
G: ## Reproduce with the same inputs
The exam guide's playbook: reproduce with the same identity and inputs, inspect validation evidence, and repair without removing controls.
## Investigation
- Compare submitted values in execution history with what users saw.
- Time zones: a date shown as 15 Oct may be stored as 14 Oct 23:00 UTC.
- Date-only versus timestamp comparisons.
Example: start dates defaulted to midnight in UTC while end dates were local; same-day ranges failed. Normalizing fixes it.
W: Inspect conversions between form and validation: users entered valid dates that became invalid in transit, which the evidence will show.
X: A=Users lying: the evidence points to a systematic conversion problem, not user error.
C=Delete validation: removes a correct rule because of a bug elsewhere.
D=Function-backed rebuild: the time-zone conversion problem would follow the data into any implementation, function-backed or not.
T: When valid-looking inputs fail validation, check value conversions such as time zones and formats.
V: Action types

@ PLTR-APD D2 T2.1 applied use-case
S: A Mark Delivered Action needs to set the status, record the delivery time, and increment the customer's delivered-orders count on a linked Customer object. Which implementation fits?
A: Three separate declarative Actions that users must run one after another for each delivered order
B: A function-backed Action that edits the order and recomputes the linked customer's count, applied together
C: A declarative Action for the order and a nightly batch that recounts every customer's delivered orders from scratch
D: Ask users to update the customer's count by hand after marking each order as delivered
K: B
G: ## Cascading edits
The exam guide recommends function-backed Actions for computation, branching or cascading changes.
## Implementation
- Function: set status and time on the order; recompute the customer's count from linked delivered orders (idempotent).
- Edits applied together by the Action.
Example: marking order O-15 delivered updates the customer's count from 41 to 42 in one submission.
W: One function-backed Action applying both edits: the order and the customer stay consistent, and recomputing the count avoids drift on retries.
X: A=Three Actions: users can stop halfway, leaving the order and the customer inconsistent.
C=Nightly recount: the count is wrong for up to a day after each delivery.
D=Manual count updates: users forget or miscount, so the customer's delivered-orders figure drifts away from reality.
T: Use function-backed Actions for edits that cascade to linked objects.
V: Action types, Functions

@ PLTR-APD D2 T2.3 applied comparison
S: Which statement about the security layers involved when a user runs an Action is correct?
A: If a user can see the Action's button in a module, every security check for running it has already passed
B: Running an Action involves independent checks (run permission, object edit rights, markings)
C: Action permissions are the same as project roles, so any Editor can run any Action in the project
D: Markings do not apply to objects edited through Actions
K: B
G: ## Independent layers
The exam guide asks you to understand the independent security layers for action execution.
- Visibility of a button is not authorization.
- Action permission, object edit permissions and markings are evaluated separately.
- Failures name the layer; fix that layer.
Example: a user may run the Action but lack the marking on one object; that submission fails.
W: Independent checks at execution: each must pass, which is why seeing or running one part does not guarantee the rest.
X: A=Button means authorized: visibility in the UI is not an authorization decision.
C=Same as roles: Action permissions are configured separately and can be narrower.
D=Markings do not apply: markings protect data regardless of the path used to change it.
T: Treat Action execution as several independent security checks.
V: Action types, permissions

@ PLTR-APD D2 T2.2 applied use-case
S: An Action creates a maintenance work order. After it succeeds, the external CMMS system must receive the work order. Sometimes the CMMS is down. What design handles this well?
A: Make the Action fail entirely whenever the CMMS is unreachable, so that no work order exists without a CMMS copy
B: Create the work order, then deliver it to the CMMS asynchronously with retries and visible status
C: Ask technicians to retype every work order into the CMMS manually at the end of each day
D: Call the CMMS synchronously and, if it times out, call it again immediately until it responds
K: B
G: ## Decouple internal change from external delivery
The exam guide asks for failure visibility, idempotency and recovery for integrations, and to move failure-prone work to trackable background flows.
## Design
- Action creates the work order (source of truth).
- Background delivery with retries and backoff; idempotency key.
- Status on the object: pending, synced, failed.
Example: during a CMMS outage, 30 work orders show "pending sync" and deliver automatically when it recovers.
W: Asynchronous, idempotent delivery with visible status: users are not blocked by an outside outage, and nothing is lost or duplicated.
X: A=Fail on CMMS outage: blocks technicians from recording work whenever a dependency is down.
C=Manual retyping: duplicate effort and inconsistency between systems.
D=Immediate repeated calls: hammers a struggling system and may create duplicates.
T: Deliver Action results to external systems asynchronously with retries, idempotency and status.
V: Action types, Automate, webhooks

@ PLTR-APD D2 T2.4 applied use-case
S: A developer wants to verify that a revised Approve Action rejects invalid cases and accepts valid ones before release, including permission differences. Which test plan fits?
A: Test once as the developer, who has every permission, with one valid object
B: Branch tests with valid, invalid and edge cases, as users with and without permission
C: Release the change to production and watch how many approvals fail or succeed during the first week of use
D: Ask one team lead to try the Action on a real object and report back
K: B
G: ## Testing Actions as the guide describes
The exam guide asks you to test happy paths, invalid inputs, concurrency, partial failure, retries and permission differences, using branches.
## Plan
- Branch with test objects.
- Cases: valid; each failing criterion; edge values.
- Identities: permitted and not permitted.
Example: a user without approval rights is refused with the expected message; a valid approval succeeds.
W: Branch tests covering valid, invalid and permission cases: the Action's behaviour is verified for every kind of user before release.
X: A=Developer only: a fully permitted tester never sees permission failures.
C=Production watching: real users absorb every mistake while the team counts failures after the fact.
D=One real object: a single test covers almost nothing and puts a real record at risk if the change is wrong.
T: Test Actions on branches across valid, invalid and permission cases.

@ PLTR-APD D2 T2.1 applied tradeoff
S: An Action currently uses declarative rules. A new requirement adds a calculation of a late fee based on days overdue and the customer's tier. What is the right change?
A: Keep it declarative and ask users to calculate the late fee themselves and type it into a form field
B: Move to a function-backed Action computing the fee from days overdue and tier, with tests for the rules
C: Add a nightly job that calculates late fees for every record and overwrites whatever was submitted
D: Remove the late fee requirement because declarative Actions cannot handle it
K: B
G: ## When requirements outgrow declarative rules
The exam guide recommends function-backed Actions when computation is needed.
## Change
- Function computes the fee deterministically; Action applies it.
- Tests for tiers and boundary days.
Example: 12 days overdue at tier B yields the documented fee every time.
W: A function-backed Action for the new calculation: the fee is computed consistently and tested, not entered by hand.
X: A=Users calculate: each user applies the rules slightly differently, so fees are inconsistent and often wrong.
C=Nightly overwrite: users see wrong values until night and their submissions are silently replaced.
D=Drop the requirement: the business needs the fee, and function-backed Actions handle such calculations directly.
T: Convert to function-backed Actions when calculations become part of the change.
V: Action types, Functions

@ PLTR-APD D2 T2.3 advanced troubleshooting
S: A user can submit an Action that edits Project objects, but for one project the submission fails with a permission error while others succeed. The Action and the user's groups are unchanged. What is the most likely explanation and next step?
A: The platform randomly rejects some submissions, so the user should retry until it works
B: That project carries a control the user lacks (a marking or policy); check access on it
C: The user's Action permission was revoked for that project only, which is impossible, so the error must be ignored
D: The Action should be granted to everyone in the organization to avoid future failures
K: B
G: ## Object-specific denials
The exam guide asks you to identify whether a rejection is caused by permissions, validation, submission criteria or execution logic, and to change the exact control.
## Steps
- Compare the failing object's markings and policies with the others.
- Check access for the user on that object.
- Decide with the data owner whether access is appropriate.
Example: the failing project carries a "Restricted R&D" marking; the user is not a member, which is correct.
W: An object-specific control explains one failing object among many: the access check identifies it and the owner decides.
X: A=Random rejection: permission errors are deterministic; retrying produces the same denial for that object.
C=Ignore the error: the denial may be protecting sensitive data on that project, which must be understood, not ignored.
D=Grant to everyone: over-permissioning that ignores the real control.
T: When one object fails an Action others pass, look for object-specific markings or policies.
V: Action types, markings
