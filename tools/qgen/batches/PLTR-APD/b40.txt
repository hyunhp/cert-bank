# PLTR-APD batch 40: Domain 7 round 5 (AIP Logic and AI-Powered Applications), 8 questions

@ PLTR-APD D7 T7.1 applied use-case
S: An application uses AIP Logic to extract the counterparty, amount and effective date from uploaded contracts so that a reviewer can confirm them. Some contracts state amounts in words ("two hundred thousand"). How should the output be designed?
A: Return a single sentence describing the contract terms, which the reviewer reads and retypes into the confirmation form field by field
B: Return a typed struct with a numeric amount, currency, date and counterparty, plus quoted evidence, validated before pre-filling the form
C: Return the amount exactly as written in the contract text, words included, and let downstream systems try to parse it later
D: Skip the amount field entirely because amounts written in words are too difficult for any model to handle reliably
K: B
G: ## Typed extraction with evidence
The exam guide asks you to configure typed outputs and AI-backed Actions.
## Design
- Output: amount (number), currency, effective date, counterparty, evidence span.
- Validation: positive amount, valid date and currency.
- Reviewer confirms in a pre-filled Action form.
Example: "two hundred thousand euros" becomes 200000 EUR with the quoted phrase shown as evidence.
W: Typed values with evidence and validation: the reviewer confirms structured data quickly and can check each value against its source text.
X: A=Descriptive sentence: the reviewer retypes everything, defeating the purpose and introducing transcription errors.
C=Raw text amounts: pushes parsing into every downstream system and leaves values inconsistent.
D=Skip the amount: drops the most important field instead of extracting and validating it.
T: Extract structured, validated values with evidence for human confirmation.
V: AIP Logic, Action types

@ PLTR-APD D7 T7.2 applied use-case
S: An AI assistant helps warehouse staff answer questions about stock levels. It has a tool that can adjust inventory counts. Staff only need answers, not adjustments. What should the developer do?
A: Keep the adjustment tool but instruct the assistant never to use it unless a user insists strongly
B: Remove the write tool, leaving read-only tools scoped to stock queries, since the task needs no writes
C: Give the assistant administrator rights so it can always answer any question
D: Let staff choose whether to enable the adjustment tool in each conversation
K: B
G: ## Minimum capability
The exam guide asks you to select the minimum data and capabilities an AI workflow needs.
## Change
- Remove the inventory adjustment tool.
- Keep read-only stock lookups scoped to the user's warehouse.
Example: "how many pallets of item 44 are in aisle 3?" works; nothing can be adjusted through the assistant.
W: Remove capabilities the task does not need: the assistant cannot be talked into changing inventory, and answers are unaffected.
X: A=Instruction not to use it: the capability remains and can be triggered by persuasive or injected text.
C=Administrator rights: expands what the assistant can reach far beyond its purpose.
D=Per-conversation toggle: leaves the risk in place and depends on user judgement every time.
T: Remove AI tools that the task does not require, especially write tools.
V: AIP Agent Studio

@ PLTR-APD D7 T7.3 applied troubleshooting
S: An AI summary feature produces good results in the evaluation suite but users report poor summaries for very long cases. The suite contains mostly short cases. What should the team do?
A: Conclude that users are wrong since the suite passes, and keep the feature unchanged
B: Add long cases to the suite, inspect their traces, and adjust context handling
C: Remove long cases from the application so that the feature only summarizes short ones
D: Switch to a random different model and hope long cases improve
K: B
G: ## Representative evaluation
The exam guide asks you to use evaluation, traces and execution history to diagnose quality.
## Steps
- Add long-case evaluation examples.
- Traces: truncation or missing sections in context.
- Fix: chunked summarization or prioritized context; re-run the suite.
Example: long cases were truncated at the context limit; summarizing sections first fixes them.
W: Make the suite representative of real inputs and use traces to fix the cause: the gap between evaluation and user experience closes.
X: A=Suite passes: the suite does not represent long cases, so passing it says nothing about them.
C=Remove long cases: users need summaries most for long cases.
D=Random model switch: untested and may not address truncation.
T: Keep AI evaluation suites representative of real inputs, including long and unusual cases.
V: AIP Evals, AIP Observability

@ PLTR-APD D7 T7.4 applied use-case
S: AI FDE generated a function that queries the Ontology using string-built filters such as concatenating user-supplied text into a query expression. What should the reviewer require?
A: Accept it, since the function compiled and returned correct results for the reviewer's own test input
B: Use typed query APIs with parameters instead of string-built filters, and test odd input
C: Escape all quotes in the user text by hand and keep the string-building approach
D: Restrict the function to administrators so that unusual input cannot cause problems
K: B
G: ## Platform idioms over string building
The exam guide asks you to validate platform idioms in AI FDE-generated code.
## Requirement
- Typed filters via the Ontology query APIs.
- User input passed as values, not concatenated into expressions.
- Tests with quotes, special characters and empty strings.
Example: a customer name with an apostrophe no longer breaks the query.
W: Typed query APIs with parameters: correct behaviour for any input and no fragile, injectable string building.
X: A=Accept after one test: unusual input such as quotes can break or subvert string-built queries.
C=Manual escaping: hand-written escaping is fragile and misses cases, so the underlying string-building risk remains.
D=Administrators only: limits who can use it without fixing the code.
T: Require typed query APIs instead of string-built filters in generated functions.
V: Functions, AI FDE

@ PLTR-APD D7 T7.1 applied comparison
S: Which design best uses AI to help agents handle customer emails?
A: AI reads each email and sends a reply directly to the customer with no human review
B: AI classifies and drafts a reply, and the agent reviews and sends it via an Action
C: AI decides whether each customer deserves a refund and issues it immediately
D: AI deletes emails it considers spam without any record of what it deleted
K: B
G: ## Assist, then act through Actions
The exam guide asks you to configure AI-backed Actions and prevent unsafe actions.
- Classification and drafting: AI assistance.
- Sending and refunds: Actions controlled by the agent.
Example: the agent reviews a drafted reply referencing the customer's order and sends it in one click.
W: AI classification and drafting with agent review and Action-based sending: faster handling with human control over what customers receive.
X: A=Direct sending: unreviewed AI replies reach customers, including any mistakes or invented details.
C=Automatic refunds: consequential decisions made by the model alone.
D=Silent deletion: misclassified legitimate emails are lost without any record or way to recover them.
T: Use AI to classify and draft, and keep sending and consequential actions behind human-controlled Actions.
V: AIP Logic, Action types

@ PLTR-APD D7 T7.2 applied troubleshooting
S: An AI feature that answers questions about projects sometimes reveals project names from other departments to users who should not see them. The feature retrieves context using a service identity with broad access. What should change?
A: Add a prompt instruction telling the model not to mention other departments' projects
B: Run retrieval as the user so context includes only projects they may see
C: Remove all project names from the Ontology
D: Ask users not to ask about other departments
K: B
G: ## Retrieval under user permissions
The exam guide asks you to select minimum data and to separate user permissions from execution identity.
## Change
- Retrieval executes as the user.
- Tests with users from different departments.
Example: a marketing user asking about all projects sees only marketing projects in the answer.
W: User-scoped retrieval: the model never receives projects the user cannot see, so it cannot reveal them.
X: A=Prompt instruction: the restricted names are still in the context and can leak.
C=Remove names: destroys project data everyone legitimately needs in order to hide it from a few.
D=Ask users: requests not to ask enforce nothing; the restricted names still reach the model.
T: Retrieve AI context with the user's permissions, not a broad service identity.
V: AIP Logic, permissions

@ PLTR-APD D7 T7.3 applied use-case
S: A team wants to know whether a new prompt for an AI-backed Action is better than the old one before releasing it. What approach is sound?
A: Release the new prompt to all users and see whether they complain more or less than they did about the old one
B: Run both prompts on the same suite with repeats, compare per category, then release
C: Ask the model which prompt it prefers
D: Choose the longer prompt since longer prompts are always better
K: B
G: ## Comparing prompts with evidence
The exam guide asks you to use evaluation to diagnose and improve AI features.
## Approach
- Same cases, both prompts, repeated runs.
- Per-category comparison.
- Release with monitoring and rollback.
Example: the new prompt improves extraction of dates by 6 points and is equal elsewhere; it is released.
W: Side-by-side evaluation with repeats and monitored release: the decision rests on measured differences.
X: A=Complaints as measurement: slow, biased and exposes users to a possibly worse prompt.
C=Ask the model: a model's preference between prompts is not a measurement of output quality.
D=Longer is better: prompt length is not quality; longer prompts can perform worse and cost more.
T: Compare prompt versions on the same evaluation suite before releasing.
V: AIP Evals

@ PLTR-APD D7 T7.4 advanced troubleshooting
S: An AI FDE-generated Function that updates many objects passed review and tests but caused a production incident: it edited objects outside the intended project because the query had no project filter. What should change in the team's process?
A: Stop using AI FDE entirely and write all Functions by hand from now on
B: Add edit-scope checks to review and tests asserting which objects are edited
C: Run generated Functions only at night so that incidents affect fewer users
D: Give the Function's execution identity administrator rights so that it never fails again
K: B
G: ## Learning from a side-effect incident
The exam guide asks you to validate side-effect safety and platform idioms in generated code.
## Process change
- Review checklist: explicit scope filters and limits on every bulk edit.
- Tests: assert the set of edited objects matches expectations.
- Least-privilege execution identity limits blast radius.
Example: the next generated Function without a project filter is caught by the checklist.
W: Strengthen review and tests around edit scope: the specific failure is caught in future, while generated code remains usable.
X: A=Ban AI FDE: overcorrects; the gap was in review, not in using generation.
C=Run at night: the same out-of-scope edits still happen, just at a different hour.
D=Administrator rights: widens what a faulty Function can damage instead of narrowing it.
T: Add edit-scope checks and tests to the review process for generated Functions.
V: Functions, AI FDE
