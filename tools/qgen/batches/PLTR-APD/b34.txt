# PLTR-APD batch 34: Domain 1 round 5 (Ontology Schema Design and Workflow Assembly), 8 questions

@ PLTR-APD D1 T1.2 applied use-case
S: A school-district application tracks Students and Courses. Students enroll in many courses each term, courses have many students, and each enrollment has a grade and a term. How should enrollment be modelled?
A: A many-to-many link between Student and Course, with grades stored as a list property on the Student object in course order
B: An Enrollment object type with term and grade, linked many-to-one to Student and to Course
C: A list of course names stored on each Student object, with a parallel list of grades kept in the same order
D: A single Course object per student, duplicating the course for every student who enrolls in it
K: B
G: ## Relationships with attributes
The exam guide asks for meaningful relationships and appropriate cardinality. A grade belongs to a specific student in a specific course in a specific term.
## Model
- Enrollment: key, term, grade, status.
- Links: Enrollment → Student, Enrollment → Course.
- Queries: a student's transcript; a course roster per term.
Example: student S-77 has 14 enrollments over three terms, each with its own grade.
W: An Enrollment object with term and grade linked to both sides: transcripts and rosters are natural traversals and each grade has its own home.
X: A=Grades as a list on Student: grades cannot be tied reliably to courses or terms, and the list cannot be validated or queried.
C=Parallel lists on Student: fragile ordering, no links to Course objects and no way to represent the term of each grade.
D=Course per student: duplicates the course's identity hundreds of times and makes rosters and course-level reports impossible.
T: Model many-to-many relationships that carry data as their own object type linked to both participants.
V: Ontology Manager

@ PLTR-APD D1 T1.1 applied comparison
S: Which situation is the clearest reason to introduce an interface in the Ontology?
A: A single object type needs one extra property that only one application uses, and nothing else changes
B: Several object types share a common set of properties that applications and Actions want to treat uniformly
C: An object type has too many properties, so it should be split into an interface and nothing else
D: A team wants to rename an object type without changing anything about how it is used
K: B
G: ## When interfaces help
The exam guide lists interfaces among Ontology constructs. An interface describes a shared shape implemented by several object types.
- Multiple types, shared properties, uniform treatment in apps and Actions: an interface.
- One extra property, splitting a wide type, renaming: other tools.
Example: Vehicle, Vessel and Aircraft implement `Trackable`, and one map module shows all of them.
W: Several object types with a shared shape used uniformly: exactly the situation interfaces are designed for.
X: A=One extra property: a property or a linked detail type handles it; no shared shape exists across types.
C=Too many properties: splitting a wide type is a modelling decision about entities, not what interfaces solve.
D=Renaming: a rename is a change to one type and has nothing to do with shared shapes.
T: Introduce interfaces when multiple object types share a shape that consumers treat uniformly.
V: Ontology Manager

@ PLTR-APD D1 T1.3 applied use-case
S: A quality team wants inspectors to record defects on a tablet, have defects above a severity automatically create a corrective-action task, and let managers review open tasks on a desktop dashboard. Which assembly fits?
A: A single desktop module for everyone, where inspectors walk to a workstation and managers create tasks by hand when they notice defects
B: A tablet module with a Record Defect Action, an automation creating tasks for high severity, and a manager dashboard module
C: A shared spreadsheet where inspectors log defects and managers check for severe ones every afternoon
D: An AI agent that decides on its own which defects matter and creates tasks without any recorded rule
K: B
G: ## Workflow assembly by role and step
The exam guide asks you to assemble workflows across Workshop, Actions and Automate and choose channels for users.
## Assembly
- Tablet module: Record Defect Action (validated).
- Automation: severity ≥ threshold → create corrective task.
- Desktop dashboard: open tasks with Actions for managers.
Example: a severity-4 defect recorded at 10:00 creates a task at 10:01 visible on the manager dashboard.
W: Role-specific modules, a validated Action and a rule-based automation: each user works on the right device and follow-ups are reliable.
X: A=Desktop for everyone with manual task creation: inspectors lose time and severe defects depend on managers noticing them.
C=Shared spreadsheet: no validation or audit, and severe defects wait until someone checks in the afternoon.
D=AI deciding without a rule: severity thresholds are explicit; an AI adds unpredictability where a rule is clear.
T: Assemble workflows with device-appropriate modules, validated Actions and rule-based automations.
V: Workshop, Action types, Automate

@ PLTR-APD D1 T1.4 applied troubleshooting
S: A developer cannot work out why a user lacks access to a module's data. The module reads two object types and one Function. What tool gives the quickest view of which resources are involved?
A: Reading every module's configuration page one by one until the resources are found and listed by hand
B: Workflow Lineage for the module, then checking access along that path
C: Asking the user to describe what they think the module reads, then checking those resources
D: Granting the user Owner on every project the developer can think of and seeing whether the data appears
K: B
G: ## Lineage for access troubleshooting
The exam guide lists Workflow Lineage for troubleshooting access.
## Steps
- Open the module in Workflow Lineage.
- List object types, Functions, backing datasets and views.
- Check the user's access at each one.
Example: the Function reads a third object type not visible in the module itself; the user lacks access to it.
W: Workflow Lineage shows the full dependency path, including resources hidden behind the Function, so access can be checked exactly where it matters.
X: A=Manual configuration reading: slow, and resources read inside Functions are easy to miss entirely.
C=User's description: users rarely know which resources a module depends on behind the screen.
D=Owner on many projects: over-permissioning by trial and error that may expose unrelated data.
T: Use Workflow Lineage to see a module's full dependency path before checking access.
V: Workflow Lineage

@ PLTR-APD D1 T1.1 applied tradeoff
S: Two teams want different display names for the same "status" values (one wants "In Progress", the other "Working"). Both use the same Task object type. What is the best approach?
A: Create two different status properties on Task, one per team, and keep them both updated by hand
B: Keep one status property with a stable value set, and let each team's module display its own labels
C: Create a separate Task object type for each team with its own status values
D: Let each team overwrite the shared status values with their preferred labels whenever they edit a task
K: B
G: ## Stable values, presentation per audience
The exam guide asks for meaningful properties and value types, and for designing interfaces per user workflow.
## Approach
- One status property with a stable value set (value type).
- Each module maps values to its preferred display labels.
Example: the stored value `in_progress` shows as "In Progress" in one module and "Working" in another.
W: One stable value set with display labels in each module: data stays consistent while each team sees familiar wording.
X: A=Two status properties: two sources of truth that drift apart whenever someone updates only one of them.
C=Separate object types: duplicates the Task entity to accommodate a naming preference.
D=Overwrite shared values: the stored values flip between wordings and filters break for everyone.
T: Keep stored values stable and adapt labels in the presentation layer.
V: Ontology Manager, Workshop

@ PLTR-APD D1 T1.2 applied troubleshooting
S: An application lists Orders with their Customer, but for 15% of orders the customer column is blank. The orders have a customer id. The customers exist and the developer can see them. What should be checked next?
A: Whether the developer's own permissions are too broad, which hides problems with links for every user
B: Whether the affected users can see those customers, and whether the id formats match the Customer key
C: Whether blank customer columns are normal for 15% of orders in any Ontology
D: Whether the customer column should be removed from the application
K: B
G: ## Data and visibility both matter
The exam guide asks you to check whether the data supports relationships and to troubleshoot access.
## Checks
- Format: "c-001" versus "C-001", padding, whitespace.
- Visibility: customers restricted by region or marking for some users.
- Compare as an affected user and as the developer.
Example: the affected orders belong to a region whose customers are hidden from these users by policy.
W: Check both key formats and the users' visibility of the linked customers: either explains a link that resolves for the developer but not for others.
X: A=Developer's permissions: broader permissions explain why the developer sees more, but the question is what the users can see.
C=Normal blanks: a 15% gap is a data or permission problem, not a normal property of links.
D=Remove the column: hides the symptom and loses information users need.
T: When links appear blank for some users, check key formats and those users' visibility of the target objects.
V: Ontology Manager, permissions

@ PLTR-APD D1 T1.3 applied comparison
S: Which step in a customer-onboarding workflow is best implemented as an automation rather than an Action?
A: A salesperson submitting a new customer's details through a validated form
B: Sending a welcome email and creating tasks after a customer is approved
C: A manager approving or rejecting the new customer after reviewing the details
D: A user correcting a typo in the customer's address
K: B
G: ## Actions for decisions, automations for follow-ups
The exam guide's decision table: Actions for governed user-initiated changes; Automate for triggers and orchestration.
- Submit, approve, correct: user-initiated Actions.
- Welcome email and tasks after approval: automation.
Example: approval at 15:00 sends the welcome email and creates three tasks at 15:01.
W: Follow-ups triggered by an approval are orchestration, which automations handle reliably without user effort.
X: A=Submitting details: a user-initiated change that needs a validated Action.
C=Approving or rejecting: a human decision recorded through an Action.
D=Correcting a typo: a user edit through an Action with validation.
T: Use Actions for user decisions and automations for follow-ups they trigger.
V: Action types, Automate

@ PLTR-APD D1 T1.4 advanced use-case
S: An object type will be retired and replaced by a new one. Several modules, Functions and two automations depend on the old type. What is a safe retirement plan?
A: Delete the old object type immediately and fix whatever breaks as users report problems
B: List dependents via lineage, migrate them on a branch, then retire the old type
C: Rename the new type to the old name so that consumers pick it up without any changes
D: Keep both types forever so that nothing ever needs to be migrated
K: B
G: ## Retiring Ontology resources
The exam guide asks you to plan changes without breaking live consumers using Workflow Lineage.
## Plan
- Lineage: all dependents of the old type.
- Migrate each dependent to the new type; test on a branch.
- Transition period; monitor; retire the old type.
Example: three modules, two Functions and two automations move in two weeks; the old type is then removed.
W: Lineage-driven migration with a transition period: consumers move deliberately and nothing breaks when the old type is retired.
X: A=Delete immediately: every dependent breaks at once in production.
C=Rename tricks: properties and links differ, so consumers break in subtler ways.
D=Keep both forever: duplicated entities and confusion about which type is authoritative.
T: Retire object types through lineage-driven migration and a transition period.
V: Workflow Lineage
