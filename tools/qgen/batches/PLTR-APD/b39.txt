@ PLTR-APD D6 T6.1 applied tradeoff
S: An automation currently runs every five minutes to check all 200,000 orders for status changes and then sends notifications. It is expensive and notifications arrive up to five minutes late. What is a better design?
A: Run the same full check every minute instead of every five minutes so that notifications arrive sooner
B: Replace polling with an event trigger on the status change and idempotent notifications
C: Run the full check once a day to reduce cost, accepting notifications up to a day late
D: Ask customers to check order status on the website instead of sending notifications at all
K: B
G: ## Events instead of polling
The exam guide asks you to select triggers and evaluation modes that fit the requirement.
## Design
- Trigger on status property change.
- Condition on relevant transitions.
- Idempotent notification effect.
Example: a status change at 10:02 produces a notification at 10:02; no full scans run.
W: Event-driven triggers on the actual change: notifications are faster and the cost of scanning every order disappears.
X: A=Polling every minute: five times the scanning cost for a smaller but still present delay.
C=Daily check: cheaper but notifications arrive up to a day late, which defeats their purpose.
D=No notifications: removes a feature customers rely on instead of fixing its design.
T: Prefer event triggers on specific changes over frequent polling schedules.
V: Automate

@ PLTR-APD D6 T6.2 applied use-case
S: An automation's effect occasionally fails because an external system returns "busy" for a few minutes during its own batch jobs. The team wants these runs to succeed without manual intervention. What should be configured?
A: Remove the automation's failure notifications so that the team is not disturbed by these errors
B: Backoff retries covering the busy window, idempotent effects, and alerts on exhaustion
C: Have someone manually rerun failed runs every morning
D: Change the automation to run only once a week when the external system is quiet
K: B
G: ## Absorbing transient failures
The exam guide lists retries, backoff and notifications among automation configuration.
## Configuration
- Backoff sized to cover a few minutes.
- Idempotent effects so retries are safe.
- Alerts after retries are exhausted.
Example: a busy response at 02:10 succeeds on the third attempt at 02:16; no alert fires.
W: Backoff sized to the busy window with idempotent effects: transient failures heal themselves and real outages still alert someone.
X: A=Remove notifications: hides real failures along with transient ones.
C=Manual reruns: someone repeats failed runs every morning, toil that properly configured retries would remove.
D=Weekly runs: every effect waits up to a week, which is far worse than an occasional few-minute retry.
T: Configure backoff to absorb known transient failures and alert only when retries are exhausted.
V: Automate

@ PLTR-APD D6 T6.3 applied troubleshooting
S: Two automations both trigger when a Case closes: one archives attachments, the other sends a survey that links to the attachments. Sometimes the survey links are broken. What is happening and how is it fixed?
A: The survey system is unreliable at generating links and should be replaced with a different provider as soon as possible
B: A race with archiving; run the survey after archiving with the new links
C: Attachments are deleted randomly by the platform
D: Customers are clicking the links too late
K: B
G: ## Ordering dependent automations
The exam guide asks you to account for race conditions in automations.
## Fix
- One workflow: archive, then send the survey with archived links.
- Or trigger the survey on the archive completion.
Example: surveys always link to the archived location.
W: Express the dependency so the survey follows archiving: the race disappears and links are always valid.
X: A=Replace the survey provider: the links are broken by ordering, not by the provider.
C=Random deletion: the attachments were moved, deterministically, by the other automation.
D=Late clicks: some links are already broken the moment the survey arrives, so click timing is not the cause.
T: Order dependent automation steps explicitly instead of letting them race.
V: Automate

@ PLTR-APD D6 T6.4 applied use-case
S: An automation should run on new Supplier objects but a developer wants to check what it would do before turning it on. Which approach fits?
A: Turn it on and watch production to see what it does to new suppliers over the next week
B: Run it manually on test suppliers and review the effects before enabling
C: Read the configuration carefully and assume it will behave as intended
D: Ask suppliers to report any unexpected emails they receive
K: B
G: ## Testing before enabling
The exam guide asks you to test automations safely before enabling production triggers.
## Steps
- Representative test objects (normal, edge).
- Manual runs; review effects.
- Enable live trigger; monitor.
Example: a test reveals the onboarding email is sent twice for suppliers with two contacts; fixed before go-live.
W: Manual runs on test objects before enabling: problems are found without affecting real suppliers.
X: A=Watch production: every real supplier created this week receives whatever the automation does wrong.
C=Assume correctness: reading a configuration does not reveal cases such as suppliers with two contacts.
D=Supplier reports: relying on external partners to notice mistakes is slow and damages the relationship.
T: Test automations manually on representative objects before enabling live triggers.
V: Automate

@ PLTR-APD D6 T6.1 applied comparison
S: Which situation is best handled by an automation condition rather than by the effect's code?
A: Deciding whether the automation acts at all, such as only for large orders
B: Formatting the text of the notification email that is sent to the customer once the automation runs
C: Calculating the discount amount to apply
D: Choosing the font of the generated PDF
K: A
G: ## Conditions decide whether to act
The exam guide lists conditions and effects separately in automation configuration.
- Conditions: whether the automation runs (value, region, status).
- Effects: what it does (formatting, calculations, documents).
Example: a condition on value > 10,000 limits the review automation to large orders.
W: Conditions filter which events lead to effects, keeping effects focused and reducing unnecessary runs.
X: B=Formatting text: shaping the notification's wording is part of what the effect produces once it runs.
C=Calculating a discount: logic within the effect or a function.
D=Choosing a font: a presentation detail of the effect's document output, unrelated to whether to act.
T: Put "whether to act" in automation conditions and "what to do" in effects.
V: Automate

@ PLTR-APD D6 T6.2 applied troubleshooting
S: An automation owned by a former employee is still running, but nobody knows what it does, and its failures go nowhere. What should the team do?
A: Delete the automation immediately since nobody knows what it does
B: Use lineage and run history to understand it, assign a team owner, then keep or retire it
C: Leave it untouched forever, since changing an automation that nobody understands might break something important
D: Duplicate it under a current employee's name and keep both running
K: B
G: ## Orphaned automations
The exam guide lists service ownership and notifications among automation configuration.
## Steps
- Lineage and history: triggers, effects, affected objects.
- Assign team ownership; route alerts.
- Decide: keep (documented) or retire (with notice).
Example: the automation turns out to escalate overdue invoices; it is kept, documented and owned by finance ops.
W: Investigate, assign ownership and decide deliberately: the automation either becomes properly owned or is retired safely.
X: A=Delete immediately: may break an important process nobody remembers.
C=Leave untouched: its failures stay invisible and nobody can fix or explain it when it misbehaves.
D=Duplicate: two automations then react to the same events and produce duplicate effects.
T: Investigate and adopt or retire orphaned automations rather than ignoring them.
V: Automate, Workflow Lineage

@ PLTR-APD D6 T6.3 applied use-case
S: An automation sends shipping notifications when an Order's status becomes "Shipped". Sometimes a user marks an order Shipped by mistake and changes it back within a minute. Customers still receive the notification. What design improvement helps?
A: Prevent users from ever changing an order's status back once it has been set to Shipped
B: Re-check the status before sending, and send a correction if one already went out
C: Send notifications only at the end of each day to avoid mistakes
D: Ask users to be more careful when changing statuses
K: B
G: ## Live state before external effects
The exam guide asks you to account for live changes and in-flight work in automations.
## Design
- Short confirmation window or re-check current status before sending.
- If already sent, a correction notification.
Example: an order switched back within 30 seconds sends nothing.
W: Re-check live state before sending and handle the already-sent case: mistakes no longer reach customers in most cases.
X: A=Forbid corrections: users could no longer fix genuine mistakes, leaving wrong statuses in place.
C=End of day: every customer's notification is delayed by hours to avoid a rare mistake.
D=Be more careful: mistakes will still happen; the automation design should tolerate them.
T: Re-validate live state before external effects in automations.
V: Automate

@ PLTR-APD D6 T6.4 advanced troubleshooting
S: An automation silently stopped producing effects a week ago. Its evaluation history shows triggers firing, conditions matching, and effects marked as skipped. What should the developer investigate?
A: Whether the automation's trigger needs to be recreated, since automation triggers expire automatically every week
B: Why effects are skipped: mute state, identity permissions or effect conditions
C: Whether the objects that trigger it were deleted
D: Whether the platform silently ignores automations older than a month
K: B
G: ## Diagnosing skipped effects
The exam guide lists diagnosing mute, evaluation and effect failures among automation skills.
## Investigation
- Effect mute state.
- Execution identity permissions.
- Effect-level conditions or misconfiguration.
- Then: alert on skipped effects.
Example: the execution identity lost write access in a permissions review; restoring the specific permission resumes effects.
W: Triggers and conditions work, so the cause is at the effect level: mute state, permissions or effect conditions, followed by alerting to catch it next time.
X: A=Trigger expiry: the evaluation history shows triggers firing normally, so the trigger is not the problem.
C=Deleted objects: conditions are matching existing objects, so the triggering objects clearly still exist.
D=Age limit: the platform has no such behaviour, and the history shows the automation still evaluating.
T: When effects are skipped, check mute state, execution identity permissions and effect conditions.
V: Automate
