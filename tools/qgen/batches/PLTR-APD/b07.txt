# PLTR-APD batch 07: Domain 6 round 1 (Automate and Operational Workflows), 8 questions

@ PLTR-APD D6 T6.1 applied use-case
S: When a Maintenance Request is created with priority "Critical", the on-call technician must be notified within minutes; other priorities should be handled in a daily digest. How should the automation be configured?
A: A daily schedule that sends one digest containing all requests including the critical ones, delivered every morning at eight
B: A creation trigger conditioned on priority = Critical that notifies at once, plus a daily digest for the rest
C: A trigger on any property change of any Maintenance Request that sends a notification to every technician each time
D: Ask technicians to refresh the request list every few minutes and look for critical items themselves
K: B
G: ## Triggers, conditions and schedules
The exam guide asks you to select triggers, conditions and effects. Two different latency needs call for two automations.
## Configuration
- Event: object created, condition priority = Critical, effect: notify on-call.
- Schedule: daily digest of non-critical requests.
- Ownership and notification routing documented.
Example: a critical request at 14:02 notifies the on-call technician at 14:03; the rest appear in tomorrow's 08:00 digest.
W: A conditioned creation trigger for urgent cases and a schedule for the rest: each class of request gets the latency it needs without flooding technicians.
X: A=Daily digest for all: critical requests wait up to a day, which defeats the purpose of the priority.
C=Any change to everyone: floods every technician with irrelevant notifications until they ignore them.
D=Manual refreshing: depends on attention and adds delay; automation exists to remove exactly this.
T: Combine conditioned event triggers for urgent work with scheduled automations for routine work.
V: Automate

@ PLTR-APD D6 T6.2 applied use-case
S: An automation calls an external ticketing API that sometimes returns transient errors. The business wants failures retried sensibly and someone informed if retries are exhausted. What should be configured?
A: No retries, so that every transient error is visible immediately as a failure that someone must fix by hand
B: Bounded retries with backoff, a failure notification to the owning team on exhaustion, and recorded status
C: Unlimited immediate retries, so that the call eventually succeeds no matter how long the external system is down
D: A daily manual check of the external system for missing tickets by whoever has time
K: B
G: ## Retries, backoff and ownership
The exam guide lists retries, backoff, fallbacks, notifications and service ownership among automation configuration.
## Configuration
- Retry policy: limited attempts with exponential backoff.
- On exhaustion: notify the owning team; status recorded on the object.
- Idempotent call so retries do not duplicate tickets.
Example: a 30-second outage is absorbed by retries; a two-hour outage notifies the integration team after the last attempt.
W: Bounded retries with backoff, idempotency and owner notification on exhaustion: transient errors heal themselves and real outages reach someone who can act.
X: A=No retries: every brief glitch in the external API becomes a manual task for someone, even when a retry would succeed.
C=Unlimited immediate retries: hammers a struggling system and never escalates.
D=Daily manual check: missing tickets are discovered up to a day late, depending on whoever happens to have time.
T: Configure bounded retries with backoff, idempotency and owner notification for external effects.
V: Automate

@ PLTR-APD D6 T6.3 applied troubleshooting
S: Two automations react to the same Order update: one sets a discount, the other recalculates the total. Occasionally the total is computed before the discount is applied, producing wrong totals. What is the cause and fix?
A: The platform randomly reorders edits, and nothing can be done except running the recalculation again manually every evening
B: A race between independent automations; chain them or combine both steps into one ordered workflow
C: The Order object type is corrupted and should be recreated with new primary keys for every order
D: Users are editing orders too quickly; ask them to wait a minute between edits
K: B
G: ## Race conditions between automations
The exam guide asks you to account for race conditions and dependencies in Automate.
## Fix
- Express the dependency: recalculate when the discount changes, not on the same original event.
- Or one automation performing both steps in order.
- Test with concurrent updates before enabling.
Example: after chaining, every total reflects the discount, including bursts of simultaneous updates.
W: Make the dependency explicit by chaining or combining: the total is always computed after the discount, removing the race.
X: A=Random reordering and manual reruns: the cause is two unordered automations, which can be fixed in configuration.
C=Recreate the object type: identity and data are fine; the ordering of effects is the problem.
D=Slower users: the race happens within a single update; user pace is irrelevant.
T: Resolve races between automations by chaining dependent steps or combining them into one ordered workflow.
V: Automate

@ PLTR-APD D6 T6.4 applied use-case
S: A new automation will send emails to customers when their orders ship. The developer wants to verify it before it touches real customers. What is the right approach?
A: Enable the automation on all orders and watch the first few hundred emails go out to real customers
B: Test with representative objects and a test recipient before enabling live triggers, then monitor
C: Skip testing, since email automations are simple and rarely fail in any way that matters
D: Ask a customer to confirm they received a test email in production
K: B
G: ## Testing before enabling
The exam guide asks you to test automations safely before enabling production triggers.
## Approach
- Test objects covering normal and edge cases.
- Effects directed at a test recipient; content reviewed.
- Enable; monitor the first runs; rollback plan.
Example: the test reveals a missing tracking number for split shipments; it is fixed before any customer receives an email.
W: Representative tests with safe recipients before enabling, then monitoring: problems are found before customers see them.
X: A=Enable on all: every content or condition mistake reaches real customers before anyone has reviewed a single email.
C=Skip testing: wrong conditions, missing fields and broken templates are common in new email automations.
D=Ask a customer: turns real customers into testers and still exposes them to whatever is wrong.
T: Test automations with representative objects and safe effects before enabling live triggers.
V: Automate

@ PLTR-APD D6 T6.3 applied use-case
S: A live automation must be changed to add a new condition. Hundreds of runs are in progress or queued. How should the change be made safely?
A: Edit the automation in place immediately; in-flight runs will simply pick up the new condition halfway through
B: Plan it: understand in-flight and queued runs, test the change, apply at a quiet time, and monitor
C: Delete the automation and recreate it with the new condition, accepting the loss of queued runs
D: Create a second automation with the new condition while leaving the old one running unchanged
K: B
G: ## Changing live workflows
The exam guide asks you to account for live workflow changes and in-flight work.
## Plan
- Understand how existing and queued runs behave across a change.
- Test the new condition.
- Apply when load is low; monitor; rollback ready.
Example: the change is applied at 22:00; monitoring shows queued runs completing under the old definition and new events using the new one.
W: A planned change with testing, timing and monitoring: in-flight work completes predictably and new behaviour is verified.
X: A=Edit in place blindly: unpredictable behaviour for runs already in flight.
C=Delete and recreate: hundreds of queued runs are lost along with the automation's history and configuration.
D=Two automations: both react to the same events, so every matching order now produces duplicate effects.
T: Change live automations deliberately, accounting for in-flight runs, with testing and monitoring.
V: Automate

@ PLTR-APD D6 T6.1 applied comparison
S: Which situation is best handled by a scheduled automation rather than an event-triggered one?
A: Notifying an approver the moment a high-value request is submitted
B: Sending a weekly summary of overdue tasks to each team lead every Monday morning
C: Creating a follow-up task as soon as an incident is marked resolved
D: Alerting security when a sensitive object's status changes to "Compromised"
K: B
G: ## Event versus schedule
The exam guide asks you to select triggers and evaluation modes. Time-based summaries are schedules; reactions to changes are events.
- Weekly overdue summary: schedule.
- Immediate notifications and follow-ups on state changes: events.
Example: every Monday at 08:00, each team lead receives one summary of their overdue tasks.
W: A weekly summary is time-driven: a schedule produces one digest at the right time regardless of when tasks became overdue.
X: A=Immediate approver notification: needs an event trigger on submission.
C=Follow-up on resolution: must happen as soon as the incident's status changes, which is an event trigger, not a schedule.
D=Security alert on status change: an event that must fire immediately.
T: Use schedules for time-based summaries and events for reactions to changes.
V: Automate

@ PLTR-APD D6 T6.2 applied troubleshooting
S: An automation has been failing silently for two weeks because its notifications were sent to an engineer who moved to another team. What should be fixed?
A: Re-route notifications to the engineer who discovered the issue, since they now know about the automation
B: Assign ownership to a team, route failures to its channel or rotation, and review ownership periodically
C: Disable the automation since nobody noticed it was failing
D: Add every engineer in the company to the notification list so that someone always sees failures
K: B
G: ## Ownership and routing
The exam guide lists service ownership and notifications among automation configuration. Individual owners leave; teams persist.
## Fix
- Owner: a team.
- Notifications: team channel or on-call rotation.
- Periodic review of owners and routes.
Example: the next failure reaches the integrations rotation within minutes.
W: Team ownership with team-level routing and reviews: failures reach someone regardless of individual moves.
X: A=Another individual: repeats the same single point of failure.
C=Disable it: the automation exists for a business purpose; two weeks of silent failure call for ownership, not removal.
D=Everyone: a notification sent to the whole company is noise that everyone assumes someone else will handle.
T: Give automations team ownership and route failures to teams, not individuals.
V: Automate

@ PLTR-APD D6 T6.3 advanced use-case
S: An automation creates an invoice in an external billing system when a contract is signed. Because Automate executes at least once, the team worries about duplicate invoices and partial failures (invoice created but status not recorded). What design handles both?
A: Trust that the automation will only ever run once per signed contract and add no further safeguards in the billing integration
B: An idempotency key per contract, status recorded after success, and a status or billing lookup before creating on retry
C: Run the automation only once per day to reduce the chance of duplicates
D: Create invoices manually instead of automating them
K: B
G: ## At-least-once with partial failures
The exam guide asks you to design automations that stay safe when an event is repeated, an external system times out, or an effect partially fails.
## Design
- Idempotency key derived from the contract.
- Status recorded after success; retries check it.
- If status is missing but the external call may have succeeded, query by key before creating.
Example: a retry after a timeout finds the invoice already exists under the key and simply records its id.
W: Idempotency keys, status recording and reconciliation on retry: neither repeats nor partial failures produce duplicate invoices.
X: A=Trust single execution: at-least-once means duplicates will happen.
C=Once per day: a daily schedule still executes at least once, so duplicates remain possible, and invoices are delayed.
D=Manual: gives up the automation instead of designing it to be safe, and manual invoicing has its own errors.
T: Design external effects for at-least-once execution with idempotency keys, status and reconciliation.
V: Automate
