# PLTR-APD batch 15: Domain 6 round 2 (Automate and Operational Workflows), 8 questions

@ PLTR-APD D6 T6.1 applied use-case
S: An automation should run when an Asset's temperature property exceeds 90 degrees, but only once per crossing, not every time the value changes while it stays above 90. How should the trigger be configured?
A: Trigger on every change to the temperature property and let the effect decide whether to do anything each time
B: A condition on the transition from at or below 90 to above 90, so the effect fires once per crossing
C: A schedule every minute that checks all assets and creates an alert for any asset currently above 90 degrees
D: Ask operators to watch a dashboard and trigger the effect manually when they notice a high reading
K: B
G: ## Transition conditions
The exam guide lists conditions and evaluation modes among automation configuration. A threshold crossing is a transition, not a state.
## Configuration
- Property-change trigger on temperature.
- Condition: previous ≤ 90 and new > 90.
- Effect: create an alert or notify; idempotent per crossing.
Example: readings 88, 92, 95, 93 produce one alert at 92; a later 85 then 91 produces a second.
W: A transition condition fires once per crossing: alerts reflect real events instead of repeating for every reading above the threshold.
X: A=Every change: the effect runs for every reading above 90, flooding operators with duplicate alerts.
C=Minute schedule on state: repeats alerts every minute while the asset stays hot, and adds up to a minute of delay.
D=Manual watching: depends on attention and is slower than an automated trigger.
T: Use transition conditions for threshold crossings so effects fire once per event.

@ PLTR-APD D6 T6.2 applied tradeoff
S: An automation's effect calls a partner API that is down for several hours. The business wants work to continue while the partner is unavailable and to catch up later. What design fits?
A: Fail every run immediately and discard the work, since the partner will eventually come back online
B: Retries with backoff, then a fallback that marks work pending for later replay, with an owner alert
C: Retry every few seconds indefinitely until the partner responds, regardless of how long the outage lasts
D: Stop the whole automation and all other workflows until the partner confirms recovery
K: B
G: ## Fallbacks for long outages
The exam guide lists retries, backoff and fallbacks among automation configuration, and asks for workflows that stay safe when external systems fail.
## Design
- Short outages: retries with backoff.
- Long outages: fallback marks objects pending and queues them; owners alerted.
- Recovery: a process or schedule replays the queue idempotently.
Example: 400 objects queue during a four-hour outage and are processed within 20 minutes of recovery.
W: Retries plus a pending-status fallback and replay: work is preserved through the outage and completed safely afterwards.
X: A=Discard: work is lost and nobody knows which objects were affected.
C=Retry every few seconds forever: hammers the partner and never escalates or preserves state clearly.
D=Stop everything: unrelated workflows halt for one partner's outage.
T: Combine retries with a pending-status fallback and idempotent replay for long external outages.
V: Automate

@ PLTR-APD D6 T6.3 applied troubleshooting
S: An automation that creates a follow-up task when a case closes sometimes creates two tasks for the same case. Logs show the trigger fired twice for one closure. What should the developer do?
A: Report the duplicate firing as a platform bug and wait for it to be fixed before using the automation again
B: Make the effect idempotent: check for an existing follow-up task (or use a deterministic key) first
C: Add a sleep of one minute at the start of the effect so that duplicate triggers overlap less often
D: Delete duplicate tasks manually each morning
K: B
G: ## Expect duplicates
The exam guide states that automations must account for at-least-once execution and duplicate effects.
## Fix
- Before creating: look up an existing follow-up for the case.
- Or create with a deterministic key so a second create is rejected.
- Test by firing the trigger twice.
Example: the second run finds the existing task and exits.
W: Idempotent effects make duplicate triggers harmless, which is the design the guide expects under at-least-once execution.
X: A=Platform bug: at-least-once execution is expected behaviour; the effect must tolerate it.
C=Sleep: duplicates still run, only later; the race is not removed.
D=Manual cleanup: somebody deletes duplicates every morning while the automation keeps creating new ones.
T: Make automation effects idempotent so repeated triggers do not create duplicates.
V: Automate

@ PLTR-APD D6 T6.4 applied troubleshooting
S: An automation stopped producing effects, but its configuration is unchanged and no errors appear. The developer suspects it is muted or its condition never evaluates to true. How should they investigate?
A: Delete and recreate the automation, since unexplained silence always means corrupted configuration
B: Check whether it is muted, inspect evaluation history for matched conditions, and test with an object
C: Increase the number of retries so that the automation tries harder to produce effects
D: Ask users whether they have noticed anything unusual
K: B
G: ## Diagnosing silent automations
The exam guide lists diagnosing mute, evaluation and effect failures among automation skills.
## Steps
- Status: muted, paused, ownership issues.
- Evaluation history: did triggers occur, did conditions match?
- Effect history: attempted and failed?
- Test with a known object.
Example: the automation was muted during a maintenance window and never unmuted.
W: Check mute state, evaluation and effect history, then test: the silent failure is located in the stage where it occurs.
X: A=Delete and recreate: loses history and may recreate the same condition problem.
C=More retries: retries apply to failed effects; nothing is being attempted.
D=Ask users: indirect and slow compared with the automation's own history.
T: Investigate silent automations through mute state, evaluation history and effect history.
V: Automate

@ PLTR-APD D6 T6.1 applied comparison
S: Which automation design best handles "every night, close all draft orders older than 30 days"?
A: An event trigger on each draft order creation that waits 30 days inside the effect before closing it
B: A scheduled automation that queries drafts older than 30 days and runs a Close Action on each, idempotently
C: A user-triggered button that closes drafts when someone remembers to click it
D: A trigger on any order property change that closes the order if it happens to be old
K: B
G: ## Scheduled bulk maintenance
The exam guide lists schedules and effects among automation choices. A nightly sweep over a condition is a scheduled query plus an Action.
## Design
- Schedule: nightly.
- Query: drafts with created date < today − 30 days.
- Effect: Close Action per order; idempotent; summary notification.
Example: 140 drafts are closed at 01:00; the owner receives a summary.
W: A nightly schedule querying the condition and running a governed Action: simple, predictable bulk maintenance.
X: A=Wait 30 days in the effect: long-running waits are fragile and invisible.
C=Manual button: closing drafts depends on someone remembering to click, so old drafts accumulate whenever they forget.
D=Any change trigger: old drafts that never change are never closed.
T: Use scheduled automations with queries and Actions for periodic bulk maintenance.
V: Automate, Action types

@ PLTR-APD D6 T6.2 applied use-case
S: An automation in a shared project is owned by an individual, and its failures go to their personal inbox. The team wants operations to be resilient to people changing roles. What should be configured?
A: Keep the individual owner and ask them to forward any failure emails to the rest of the team whenever they remember to
B: Team ownership with notifications to a team channel or rotation, and the project scope reviewed
C: No notifications, since failures are rare and someone will eventually notice
D: Duplicate the automation under each team member's name so that someone always owns a copy
K: B
G: ## Ownership as configuration
The exam guide lists service ownership, notifications and project scope among automation configuration.
## Configuration
- Owner: the team (or a service identity owned by the team).
- Notifications: team channel or on-call rotation.
- Scope: the project the automation should act within.
Example: when the creator moves teams, failures still reach the operations rotation.
W: Team ownership with team-routed notifications: the automation keeps an accountable owner regardless of individual moves.
X: A=Forwarding when remembered: unreliable and still tied to one person.
C=No notifications: failures go unnoticed until users complain.
D=Duplicate per member: multiple automations firing on the same events, creating duplicate effects.
T: Assign automations to team ownership with team-routed notifications.
V: Automate

@ PLTR-APD D6 T6.3 applied use-case
S: An automation runs when an Invoice is approved and posts it to an accounting system. Users sometimes approve and then immediately reject an invoice. What must the design handle?
A: Nothing, since a rejection always happens before the automation runs and cancels it automatically
B: Races with in-flight work: re-check the current status before posting and handle reversal if posted
C: Prevent users from rejecting invoices once they are approved, under any circumstances
D: Post to accounting only once a week to reduce the chance of reversals
K: B
G: ## Live state and in-flight work
The exam guide asks you to account for race conditions and live changes in automations.
## Design
- Before the effect: re-read the invoice; proceed only if still approved.
- If already posted when rejected: a reversal workflow.
- Log both paths.
Example: an approval followed by rejection within seconds skips posting because the status check fails.
W: Re-check current state before acting and handle reversals: the automation stays correct when users change their minds quickly.
X: A=Automatic cancel: automations do not cancel themselves because a later change happened.
C=Forbid rejection: legitimate corrections must remain possible.
D=Weekly posting: delays accounting without removing the race.
T: Re-validate live state before automation effects and design reversal paths.
V: Automate

@ PLTR-APD D6 T6.4 advanced use-case
S: A team must change an automation's condition and effect for a critical billing workflow. They need confidence before it affects real customers. What sequence is appropriate?
A: Make the change in production and compare the next invoices with last month's by hand
B: Test with representative objects outside production, enable gradually, and monitor with rollback
C: Disable billing for a week while the change is developed and then enable it all at once
D: Apply the change and rely on customers to report incorrect invoices
K: B
G: ## Safe changes to critical automations
The exam guide asks you to test automations safely before enabling production triggers and to change live workflows carefully.
## Sequence
- Manual tests on representative objects.
- Non-production run; compare effects.
- Gradual enablement (subset); monitor; rollback ready.
Example: the new rule is enabled for one region first; after two clean cycles it goes live everywhere.
W: Test, stage and monitor with rollback: the critical workflow changes without exposing all customers to an unverified rule.
X: A=Production change with manual comparison: customers receive any mistake first.
C=Disable billing: a week without invoices disrupts revenue for a change that can be tested without stopping anything.
D=Customers as testers: wrong invoices damage trust and create correction work; billing changes must be verified first.
T: Change critical automations through testing, staged enablement and monitoring with rollback.
V: Automate
