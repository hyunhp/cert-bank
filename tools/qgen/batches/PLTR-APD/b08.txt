# PLTR-APD batch 08: Domain 7 round 1 (AIP Logic and AI-Powered Applications), 8 questions

@ PLTR-APD D7 T7.1 applied use-case
S: An application lets service agents draft a reply to a customer complaint using AI. The draft must reference the customer's open orders and must never be sent without the agent's review. How should the AI feature be built?
A: An AIP Logic function that writes the reply and sends it to the customer automatically as soon as the complaint is opened
B: A Logic function drafting from the complaint and linked orders, shown for the agent to edit and send via an Action
C: A free-text box where agents paste the complaint into an external chatbot and copy the answer back into the application
D: A nightly pipeline that drafts replies for all complaints, which are sent automatically the next morning
K: B
G: ## Draft, review, then act
The exam guide asks you to configure prompts, typed inputs and outputs and AI-backed Actions, and to prevent unsafe actions.
## Design
- Logic function: inputs complaint and linked orders; output draft text.
- Workshop: agent reviews and edits.
- Action: sends the reply with audit; the AI never sends on its own.
Example: the draft cites order O-221's delay; the agent softens a sentence and sends.
W: AI drafts from typed Ontology context and a human-sent Action: useful assistance with the agent accountable for what reaches the customer.
X: A=Automatic send: removes the required review and lets an unchecked draft reach customers.
C=External chatbot: customer data leaves governance and the draft lacks order context.
D=Nightly auto-send: stale drafts sent without review the next day.
T: Use AI to draft from typed Ontology context and keep sending behind a human-reviewed Action.
V: AIP Logic, Workshop, Action types

@ PLTR-APD D7 T7.2 applied tradeoff
S: An AI feature summarizes a support case. The developer gave the Logic function access to all object types and every Action in the Ontology "for flexibility". What is the problem and the fix?
A: There is no problem, since a model with broad access produces better summaries than one with narrow access
B: It breaks minimum capability; give only the case and linked objects as inputs and no write Actions
C: Give the function administrator rights as well, so that it never fails on permissions
D: Remove the AI feature, since any AI with data access is too risky
K: B
G: ## Minimum data and capabilities
The exam guide asks you to select the minimum Ontology data and capabilities an AI workflow needs. A summary requires reading one case's context.
## Fix
- Inputs: the case and linked messages.
- Tools: none that write.
- Execution: as the user, so permissions apply.
Example: the narrowed function produces the same summaries and cannot touch any other object type.
W: Narrow inputs and no write tools: the feature does its job and cannot be steered into reading or changing unrelated data.
X: A=Broad access is better: more context adds noise and expands what a manipulated prompt could reach.
C=Administrator rights: maximizes the blast radius of any mistake.
D=Remove the feature: discards a useful tool that can be scoped safely.
T: Give AI features only the data and tools their task requires; summaries need read access only.
V: AIP Logic

@ PLTR-APD D7 T7.3 applied troubleshooting
S: An AI feature that suggests next steps for cases has become slow and costly. The trace shows a 40,000-token prompt because every linked document is injected in full. What should the developer do?
A: Switch to the largest available model so that it can process the long prompt faster
B: Trim context to relevant documents and summaries of long ones, then compare quality, latency and cost
C: Remove all linked documents from the prompt so that the model relies only on its general knowledge to suggest next steps
D: Cache the 40,000-token prompt so that it does not need to be built again for any case
K: B
G: ## Diagnose with traces, then trim context
The exam guide asks you to use evaluation and traces to diagnose latency and cost, and warns against simply choosing a larger model.
## Approach
- Trace: which inputs dominate tokens.
- Select relevant documents; summarize long ones.
- Measure quality, latency and cost before and after.
Example: prompts shrink to 6,000 tokens; latency halves; evaluation scores are unchanged.
W: Trace-guided context reduction measured by evaluation: cost and latency fall where they originate, with quality checked.
X: A=Largest model: more expensive per token and still processes the same oversized prompt.
C=No documents: answers lose the case-specific grounding they need.
D=Cache the prompt: each case has different documents, so the cache rarely hits and cost stays.
T: Use traces to find oversized context and trim it to what the task needs, verified by evaluation.
V: AIP Logic, AIP Observability

@ PLTR-APD D7 T7.4 applied use-case
S: AI FDE generated a function that recommends and immediately applies a discount to an order. Before publishing, what should the reviewer check specifically about side effects?
A: Only that the code compiles and follows the team's naming conventions
B: That recommending is separated from applying via a governed Action, edits are bounded, and retries are safe
C: That the function produces discounts as large as possible for every order, since customers always prefer larger discounts
D: That the generated code is as short as possible
K: B
G: ## Side-effect safety in generated code
The exam guide asks you to validate schema, platform idioms, provenance and side-effect safety before publishing AI FDE-generated code.
## Review
- Separation: recommend versus apply; writes through an Action with validation and permissions.
- Scope of edits: only the target order.
- Idempotency: a retry does not stack discounts.
Example: the reviewer splits the function into `recommendDiscount` and an Action `applyDiscount` with a cap and an approval rule.
W: Separate recommendation from governed application, bound the edits and make them retry-safe: the generated function cannot change orders unsafely.
X: A=Compiles and naming: says nothing about what the function changes or whether it can do so twice.
C=Maximize discounts: a business rule invented by the reviewer, not a safety check.
D=Shortest code: brevity says nothing about which objects the function changes or whether a retry stacks discounts.
T: Review generated functions for side effects: separate recommend from apply and bound and protect edits.
V: Functions, AI FDE, Action types

@ PLTR-APD D7 T7.1 applied comparison
S: Which requirement is a good fit for adding AI to an application rather than deterministic logic?
A: Calculating sales tax from a jurisdiction table and an order amount
B: Classifying free-text customer feedback into product themes for a review screen
C: Checking that a date field is not in the future before an Action is submitted
D: Sorting a table of invoices by due date
K: B
G: ## When AI adds value
The exam guide's self-check asks when AI adds value over deterministic logic. Interpretation of unstructured text is the clear case; tables, validations and sorting are rules.
- Tax from a table, date validation, sorting: deterministic.
- Theme classification of free text: AI with typed output.
Example: feedback "battery dies by lunch" is classified as "Battery life" and shown on the review screen.
W: Classifying free text needs interpretation: the case where AI adds value over rules.
X: A=Sales tax: an explicit calculation from a table, best done deterministically.
C=Date validation: a fixed rule that belongs in the Action's submission criteria, where it is enforced deterministically.
D=Sorting: ordering invoices by due date is a table setting; no interpretation is involved and AI adds nothing.
T: Use AI for interpreting unstructured content; keep rules, validations and calculations deterministic.
V: AIP Logic

@ PLTR-APD D7 T7.3 applied use-case
S: Users say an AI-generated "risk explanation" in an application is sometimes wrong. The developer wants evidence to decide what to fix. What should be set up?
A: Ask the users to describe the bad explanations from memory in a monthly meeting
B: An evaluation suite of representative cases, traces of production runs, and captured user corrections
C: Switch to a different model immediately without measuring whether the new one actually produces better risk explanations
D: Hide the explanation until complaints stop
K: B
G: ## Evidence for AI quality
The exam guide asks you to use evaluation, traces and execution history to diagnose poor grounding and quality.
## Setup
- Evaluation suite: cases with expected content.
- Traces: inputs and outputs of failing runs.
- Feedback: user corrections captured and turned into new cases.
Example: traces show explanations fail when the risk score lacks a linked contract; the prompt and inputs are fixed and the suite confirms it.
W: Evaluation, traces and captured feedback: the team can see why explanations fail and verify that fixes work.
X: A=Monthly recollections: vague, late and unreproducible; nobody can trace which inputs produced the bad explanation.
C=Switch models blindly: may not fix the cause and introduces new behaviour.
D=Hide it: removes the feature's value for all users and produces no evidence about what went wrong.
T: Diagnose AI quality with evaluation suites, production traces and captured user feedback.
V: AIP Evals, AIP Observability

@ PLTR-APD D7 T7.2 applied troubleshooting
S: An agent embedded in a module can call a "Cancel Order" Action. A user tricked it into cancelling orders belonging to other customers by pasting instructions into a comment. What is the right remediation?
A: Add a sentence to the agent's system instructions telling it never to cancel orders that belong to other customers
B: Scope the tool to the order in context, apply the user's permissions and validation, and confirm cancellations
C: Remove all tools from every agent in the organization
D: Block users from writing comments on orders
K: B
G: ## Constrain tools, not just prompts
The exam guide asks you to prevent an AI workflow from taking unsafe or unsupported actions. Prompt instructions are bypassable; tool scope and Action validation are not.
## Remediation
- Tool scope: only the order in the current context.
- Action: user's permissions, submission criteria, confirmation.
- Adversarial test with injected instructions.
Example: a pasted instruction to cancel order 991 fails because the tool only accepts the order in context.
W: Scope the tool, enforce permissions and validation, and confirm destructive actions: the injected instruction cannot reach other orders.
X: A=Instruction sentence: content can override it; the capability remains.
C=Remove all tools: disables every agent's legitimate capabilities across the organization to fix one agent's tool scope.
D=Block comments: removes a legitimate feature without fixing the tool.
T: Defend AI-triggered Actions with scoped tools, user permissions, validation and confirmation.
V: AIP Agent Studio, Action types

@ PLTR-APD D7 T7.4 advanced use-case
S: A team uses AI FDE to generate several Functions per week. Which review standard should apply before any generated Function is published?
A: Publish automatically once the generated code compiles, since generation is reliable enough for routine Functions
B: Full code review plus schema, platform idioms, provenance and side-effect checks, with tests and a branch run
C: Review only Functions longer than 200 lines, since short Functions cannot contain serious errors
D: Ask AI FDE to review its own output and publish if it reports no problems
K: B
G: ## A standard for generated code
The exam guide asks you to review AI FDE-generated Function code and validate schema, platform idioms, provenance and side-effect safety before publishing.
## Standard
- Types match the Ontology schema.
- Idioms: server-side queries, bounded traversal, proper edits.
- Provenance recorded; tests and branch execution.
- Human reviewer accountable for the merge.
Example: a 30-line generated Function passes compile but fails review for editing objects outside its input set; it is corrected before publishing.
W: Full review plus the guide's specific checks: generated code earns publication the same way any code does.
X: A=Compile is enough: compiling code can still violate schema, scale or side-effect rules.
C=Length threshold: short Functions can still write the wrong objects.
D=Self-review: the tool that produced the code shares its own blind spots; an independent human reviewer is required.
T: Hold generated Functions to full review with schema, idiom, provenance and side-effect checks.
V: Functions, AI FDE
