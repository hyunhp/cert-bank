# PLTR-APD batch 25: Domain 8 round 3 (Application Security, Governance, and Operations), 8 questions

@ PLTR-APD D8 T8.1 applied use-case
S: A claims application must let adjusters in each region see only their region's claims, while supervisors see all regions. Claims are Ontology objects. Which control should be used?
A: A Workshop filter defaulted to the adjuster's region, which adjusters are trusted not to change when they open the module
B: An object security policy (or a restricted view backing the type) granting rows by region attribute, with supervisors seeing all
C: Separate object types per region, each duplicated from the same source, with project roles per region
D: A marking per region applied to the whole claims dataset so each adjuster holds only their region's marking
K: B
G: ## Row-level access on objects
The exam guide lists restricted views and governance controls among application security tools and asks you to separate application access from data access.
## Configuration
- Policy: adjuster's region attribute = claim region; supervisors' group sees all.
- Applies in every module, Function and API.
- Tested with an adjuster and a supervisor.
Example: a North adjuster sees 2,400 claims; a supervisor sees 18,000.
W: A row-level policy on the claims data: each adjuster sees only their region everywhere, while supervisors keep full visibility.
X: A=Workshop filter: a UI default users can change; other tools ignore it entirely.
C=Duplicated per-region types: multiplies object types and pipelines for what one policy expresses.
D=Marking per region on the whole dataset: markings are all-or-nothing per dataset, not row selection.
T: Enforce row-level visibility on objects with data-level policies.
V: restricted views, permissions

@ PLTR-APD D8 T8.2 applied use-case
S: An executive wants a new dashboard module shared with 200 managers. The module reads several object types, some of which contain data that certain managers should not see. How should sharing be designed?
A: Give all 200 managers Owner on every project the module reads from, so that the module works for everyone without errors
B: Share the module (resource access) with the managers, and let each user's data permissions decide what they see within it
C: Copy all data the module needs into a single new unrestricted dataset so that sharing is simple
D: Send each manager a weekly PDF export instead of sharing the module at all
K: B
G: ## Separate application access from data access
The exam guide asks you to separate application/resource access from data access and avoid over-permissioning.
## Design
- Module shared with the managers' group.
- Data permissions (roles, markings, policies) unchanged; each manager sees what they may.
- Empty states explain when data is not visible.
Example: two managers see fewer rows in one chart because of a regional policy, as intended.
W: Share the module and keep data permissions in charge: everyone can open the dashboard and sees only what they are entitled to.
X: A=Owner everywhere: grants far more than needed, including edit and delete rights.
C=Unrestricted copy: strips data protections to simplify sharing.
D=PDF export: weekly static files lose interactivity, go stale immediately and leave the platform's access control.
T: Share applications broadly while letting data permissions govern what each user sees.
V: permissions, Workshop

@ PLTR-APD D8 T8.3 applied troubleshooting
S: A Function runs project-scoped under a service identity and writes summaries to Report objects. Users report that some Reports created by it are visible to people who should not see them. What should be reviewed?
A: Whether users are sharing their screens with colleagues who then see the Reports by accident
B: Where the Function writes and the permissions on the created objects
C: Whether the service identity should be deleted entirely, since project-scoped execution is never acceptable for any Function
D: Whether users should be told to close Reports they should not see
K: B
G: ## Writes under elevated identities
The exam guide asks you to distinguish execution identity from user visibility and review the resulting access model.
## Review
- Where the Function writes: which project, which object type.
- Permissions on that location: who can read created Reports.
- Correct the location or apply markings/policies.
Example: Reports were written to a broadly shared project; moving them to a restricted one fixes visibility.
W: Review the write location and its permissions: the service identity created objects in a place too many users can read.
X: A=Screen sharing: the visibility exists in the platform's permissions, not in what users show each other.
C=Delete the identity: project-scoped execution is legitimate; its outputs need correct permissions.
D=Ask users to close Reports: not a control; the data is still readable.
T: When elevated execution creates objects, verify the permissions of the place they are written.
V: permissions, Functions

@ PLTR-APD D8 T8.4 applied troubleshooting
S: Users report an application's Actions intermittently fail with timeouts at the end of each month. Monitoring shows Action latency spikes when a monthly batch automation runs. What should the developer do?
A: Ask users to avoid working in the application at the end of each month while the monthly batch automation is running
B: Confirm contention in monitoring, then reschedule or throttle the batch
C: Disable all monitoring during month-end so that alerts do not fire
D: Increase the timeout on every Action to ten minutes
K: B
G: ## Correlating with operational signals
The exam guide asks you to monitor application and automation health and use evidence to investigate failures.
## Steps
- Correlate Action latency with the batch run.
- Reschedule the batch off-hours, throttle it, or reduce its impact.
- Monitor after the change.
Example: moving the batch to 02:00 and throttling it removes the month-end timeouts.
W: Use monitoring to confirm contention and change the batch's timing or load: users stop paying for a background job.
X: A=Avoid month-end: pushes the problem onto users and fixes nothing.
C=Disable monitoring: removes the evidence that pointed to the batch job while the timeouts carry on.
D=Ten-minute timeouts: users wait longer for the same contention.
T: Correlate failures with operational signals and reschedule or throttle competing workloads.
V: monitoring, Automate

@ PLTR-APD D8 T8.1 applied comparison
S: Which control is most appropriate to ensure only reviewed changes reach a production application's Functions and Actions?
A: A shared password for the production environment that only the senior developers on the team are told about
B: Branch protection requiring approval before changes merge to production
C: A weekly meeting where developers describe their changes verbally
D: Disabling all changes to production permanently
K: B
G: ## Branch protection
The exam guide lists branch protection among application security controls.
- Protected production branch; approvals required.
- Changes developed and validated on branches.
Example: a Function change needs one approval and a passing branch build before merge.
W: Branch protection with required approvals: review is enforced by the platform for every change.
X: A=Shared password: unattributable changes, no audit trail, and nothing that requires anyone to review a change.
C=Verbal descriptions: no enforcement and no record of what actually merged.
D=No changes ever: stops every fix and improvement, which is a failure of a different kind.
T: Enforce review of production application changes with branch protection.
V: branches

@ PLTR-APD D8 T8.2 applied troubleshooting
S: A user can open an application and see objects, but a specific property column is blank for them while colleagues see values. What is the most likely cause?
A: The user's display settings hide that column's text colour against the background
B: Property-level security restricts that property; check access to it separately from the object
C: The property is too long to display for this user's screen size
D: The Ontology loses property values for new users until they have used the application for a week
K: B
G: ## Property-level visibility
The exam guide asks you to identify the exact permission control involved and separate access layers.
## Check
- Property security policy on the column.
- The user's group membership or attributes against that policy.
- Decide with the owner whether access is appropriate.
Example: the salary property is visible only to HR; the user is in Finance, so the column is blank by design.
W: A property-level control explains blank values for one user while the object itself is visible: check that specific layer.
X: A=Text colour: other columns display; colleagues on similar settings see values.
C=Screen size: long values are truncated on small screens, not blanked, and colleagues on the same devices see them.
D=New-user delay: values do not depend on how long a user has used the application; the platform has no such behaviour.
T: When a single property is blank for some users, check property-level security.
V: permissions

@ PLTR-APD D8 T8.3 applied use-case
S: An automation must create follow-up tasks in a project that the triggering users cannot access, by design. An auditor asks how this is controlled. What should the developer document?
A: That the automation runs as the triggering user, which explains everything the auditor needs to know
B: The execution identity, its minimal permissions, what it writes where, who sees the output, and its owner
C: That automations are trusted by default and need no documentation
D: That the developer personally checks the automation's output every week
K: B
G: ## Documenting execution identity
The exam guide asks you to separate user permissions from execution identity and review the resulting access model.
## Documentation
- Identity and its permissions (least privilege).
- Inputs read, outputs written and their location.
- Visibility of outputs; owner and alerting.
Example: the auditor sees that the automation runs as `svc-followups` with write access to Tasks only.
W: A clear record of identity, permissions, data flow and ownership: the access model is explicit and reviewable.
X: A=Runs as the user: contradicts the design, since users cannot access the target project.
C=Trusted by default: an auditor needs a description of identity and permissions; trust without evidence is no basis for audit.
D=Weekly personal checks: not a control and depends on one person.
T: Document automations' execution identity, permissions, outputs and owner for audit.
V: Automate, permissions

@ PLTR-APD D8 T8.4 advanced use-case
S: An application team wants a single view of their application's operational health: Action failures, Function latency, automation runs, Ontology indexing status and AI usage. What should they build and how should it be used?
A: A view showing only daily active users, reviewed once a quarter by the product owner
B: A monitoring view of those signals with thresholds routed to the owning team, runbooks and reviews
C: A spreadsheet that developers update manually when they notice problems
D: Nothing extra, since each component already shows its own errors to users in the application whenever something fails
K: B
G: ## Operational health in one place
The exam guide asks you to monitor application, Ontology, automation, indexing and AIP health and use evidence to investigate.
## Build
- Aggregated metrics per component.
- Alert thresholds and routing to owners.
- Runbooks; regular review of trends.
Example: rising indexing lag is spotted on Tuesday, before users see stale data on Wednesday.
W: Aggregated signals with thresholds, routing, runbooks and reviews: problems are detected and handled before they reach users.
X: A=Active users quarterly: says nothing about failures and is far too infrequent.
C=Manual spreadsheet: depends on someone noticing and remembering.
D=Rely on user-facing errors: users discover every failure first, and silent problems such as indexing lag show no error at all.
T: Monitor all application components with routed alerts and runbooks.
V: monitoring
