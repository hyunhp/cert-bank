# PLTR-APD batch 03: Domain 2 round 1 (Action Types and Write-Back Patterns), 8 questions

@ PLTR-APD D2 T2.1 applied comparison
S: An Action must change a Ticket's status to "Closed" and set a closed date. Another Action must close a Ticket, recalculate an SLA breach flag from several linked objects, and close all linked subtasks. Which implementation fits each?
A: Function-backed for both, since any Action that edits objects should always run custom code for consistency
B: Declarative edit rules for the simple close; a function-backed Action for the second, which needs computation and cascading edits
C: Declarative rules for both, since cascading edits across linked objects can always be expressed as simple property updates
D: A Workshop variable for the first and an automation for the second, avoiding Actions entirely
K: B
G: ## Declarative or function-backed
The exam guide's decision table: declarative rules for direct, governed edits; function-backed Actions for computation, branching or cascading changes.
## Mapping
- Simple close: set two properties; declarative rules are clear and governed.
- Complex close: compute SLA from links and edit many objects; a function-backed Action.
Example: the complex Action closes a ticket and its seven subtasks in one atomic submission with a recomputed flag.
W: Match the implementation to the logic: declarative for simple edits, function-backed where computation and cascading edits are required.
X: A=Function-backed for everything: adds code and maintenance where declarative rules are simpler and safer.
C=Declarative for both: computing a flag from linked objects and editing many subtasks needs logic.
D=Variables and automations instead of Actions: loses validation, permissions and audit for user-initiated changes.
T: Use declarative Action rules for direct edits and function-backed Actions for computed or cascading changes.

@ PLTR-APD D2 T2.2 applied use-case
S: An Approve Expense Action must only be submittable when the expense is in "Submitted" status, the amount is within the approver's limit, and the approver is not the person who submitted it. How should this be configured?
A: Instructions in the Workshop module's help text telling approvers which expenses they are allowed to approve
B: Submission criteria checking status, the user's limit and approver ≠ submitter, with clear messages
C: A nightly job that reverses any approval that violated the rules during the day
D: Hide the Approve button for every user except one administrator who checks the rules manually
K: B
G: ## Submission criteria encode the rule
The exam guide lists parameters, validation and submission criteria among Action configuration. Rules that decide whether a state change is allowed belong in the Action, evaluated at execution.
## Configuration
- Criteria: object status = Submitted; amount ≤ approver's limit (user attribute or linked object); current user ≠ submitter.
- Messages explain which condition failed.
Example: an approver opening their own expense sees "You cannot approve an expense you submitted."
W: Submission criteria evaluated at execution with clear messages: the rules are enforced for every path that runs the Action.
X: A=Help text: tells approvers the rules but enforces nothing; an approver can still approve their own expense.
C=Nightly reversal: invalid approvals take effect first and may already have triggered payments.
D=Single administrator: one person becomes a bottleneck for every approval, replacing enforceable rules with manual effort.
T: Enforce Action preconditions with submission criteria evaluated at execution.

@ PLTR-APD D2 T2.3 applied troubleshooting
S: A user with Editor on the project can see the Action button in a module but receives a permission error when submitting it on a marked object. What explains this?
A: Editor on the project always grants permission to run every Action on every object in that project, so the platform is wrong
B: Action execution has independent layers (Action permission, object edit permission, markings); one is missing
C: The Action button is cached from an earlier session, and the permission error will disappear once the browser is restarted
D: Actions can only be submitted by project Owners, so the user must be promoted to Owner on the project
K: B
G: ## Independent layers
The exam guide asks you to understand the independent security layers for Action execution. Seeing a button does not mean every layer allows the edit.
## Checks
- Action-level permission: is the user allowed to run this Action?
- Object-level: can the user edit this object, including marking requirements on its data?
- Fix the specific missing layer; do not over-grant.
Example: the user lacks the "Finance" marking on the object's backing data; the right owner decides whether to grant it.
W: Independent layers: the user passes one check but fails another, which is why the button appears yet submission fails.
X: A=Editor grants everything: roles do not override markings or Action permissions.
C=Cached button: the error comes from the server-side check at submission.
D=Owners only: Action permissions are configured per Action, not limited to Owners.
T: Diagnose Action denials layer by layer: Action permission, object permission and markings.

@ PLTR-APD D2 T2.4 applied troubleshooting
S: An Action succeeds for one Order but fails for another with the same form in the same module. What does the exam guide recommend investigating?
A: The module's layout, since a UI defect is the most likely reason that identical forms behave differently
B: The two objects' state, links, preconditions and permissions, which explain different outcomes
C: The browser version on the user's laptop, since Action forms are known to behave differently in older browsers
D: The time of day each submission was made, since Actions are generally less reliable during busy working hours
K: B
G: ## Same UI, different data
The guide's practice scenario: when an Action succeeds for one object and fails for another with the same UI, compare object state, links, preconditions and permissions rather than assuming a UI defect.
## Compare
- Status and property values against submission criteria.
- Required links present?
- Markings or policies on the failing object.
- Execution logs for the failure message.
Example: the failing order has no linked customer, which the Action's criteria require.
W: Compare data, links, preconditions and permissions between the two objects: that is where the difference lives.
X: A=Layout defect: the same form succeeded for another object a moment earlier, so the interface itself is working.
C=Browser version: the same user in the same browser gets different outcomes, so the browser is not the variable.
D=Time of day: the outcome follows each object's state and access, which is why one succeeds and the other fails.
T: When an Action fails for one object but not another, compare the objects' state, links, preconditions and permissions.

@ PLTR-APD D2 T2.2 applied use-case
S: When a Purchase Order is approved through an Action, an external ERP must be notified. The team wants the notification tied to the Action's success. Which configuration fits?
A: Ask approvers to send an email to the ERP team after each approval so they can update the ERP manually
B: A webhook or side effect on the Action calling the ERP after success, retry-safe and with visible failures
C: A nightly batch that compares approved orders with the ERP and sends any missing notifications the next day
D: An instruction in the Action's description reminding developers to integrate with the ERP later
K: B
G: ## Side effects on Actions
The exam guide lists side effects and webhooks among Action configuration. Notifications tied to a governed change belong with the Action.
## Configuration
- Webhook or side effect on successful submission.
- Idempotency key so retries do not double-notify.
- Visible failure state and a recovery path.
Example: approval of PO-4471 posts to the ERP; a timeout is retried once with the same key and succeeds.
W: A webhook or side effect on the Action with retry-safe handling: the external update follows the governed change reliably.
X: A=Manual emails: depend on every approver remembering, arrive late and leave the ERP out of step with the platform.
C=Nightly reconciliation: every approval reaches the ERP up to a day late, which delays purchasing.
D=Description reminder: a note for developers integrates nothing; approvals still never reach the ERP.
T: Attach external notifications to Actions as webhooks or side effects with idempotency and failure visibility.

@ PLTR-APD D2 T2.4 applied use-case
S: A developer changed an Action Type's validation and wants to test it without affecting production objects or users. What approach fits?
A: Edit the Action in production and ask a few users to try it carefully on real objects during the day
B: Test the change on a branch with representative and invalid inputs, then review and merge
C: Disable the Action for everyone until the change has been tested in production by the developer
D: Skip testing since validation changes cannot affect users
K: B
G: ## Testing Actions safely
The exam guide lists branches, validation and live execution evidence for testing Actions.
## Approach
- Branch: Action change plus test objects.
- Cases: valid, invalid, edge, permission differences.
- Review; merge; monitor execution evidence after release.
Example: an invalid amount is rejected with the new message on the branch; the change merges.
W: Branch testing with representative and invalid cases before merge: users are not exposed to an unverified change.
X: A=Test in production: real objects and real users absorb the risk of a validation mistake during working hours.
C=Disable for everyone: blocks every user's work for a change that can be tested safely on a branch.
D=Skip testing: validation decides what users can submit; an untested rule can block valid work or admit invalid data.
T: Test Action changes on branches with valid, invalid and permission cases before merging.

@ PLTR-APD D2 T2.3 applied tradeoff
S: An operations manager asks the developer to remove all validation from an Action because users are complaining that it rejects their submissions. What is the right response?
A: Remove the validation immediately, since users know their process better than the rules do
B: Find which rules reject submissions and why, fix wrong ones or improve messages, and keep protective validation
C: Give every complaining user administrator rights on the project so that the validation no longer applies to their submissions
D: Tell users to submit the same form repeatedly until the validation accepts it
K: B
G: ## Diagnose before removing controls
The exam guide warns never to fix an Action failure by granting broad permissions or removing validation before understanding the cause.
## Approach
- Find the rules causing rejections (execution evidence).
- Classify: wrong rule (fix), correct rule with poor message (improve), correct rule (keep and explain).
Example: a date rule used the wrong time zone; fixing it removes 80% of complaints.
W: Diagnose and fix the specific rules while keeping protective validation: users are unblocked without losing correctness.
X: A=Remove all validation: invalid approvals and malformed data enter production, along with whatever the rules were protecting.
C=Administrator rights: over-permissioning that bypasses the problem.
D=Resubmit until accepted: rules are deterministic; it will not pass.
T: Diagnose rejected submissions rule by rule rather than removing validation.

@ PLTR-APD D2 T2.2 advanced use-case
S: An Action creates a shipment and calls an external carrier API. Occasionally the carrier times out after creating the shipment on its side, the Action reports failure, and users retry, creating duplicate shipments. What should change?
A: Add more automatic retries to the Action so that timeouts are retried immediately without involving the user
B: Use an idempotency key on the carrier call and record a visible operation status on the object
C: Increase the timeout to ten minutes so that the carrier always responds before the Action gives up
D: Tell users never to retry a failed submission under any circumstances
K: B
G: ## Idempotency before retries
The exam guide's practice scenario: when a button triggers the same external update twice after a timeout, design idempotency and reliable operation status before adding more retries.
## Design
- Idempotency key per shipment request.
- Status on the object: pending, created, failed.
- UI shows pending; retries reuse the key.
Example: a retried submission returns the carrier's existing shipment instead of creating a second one.
W: Idempotency keys and operation status: retries become safe and users can see what actually happened.
X: A=More retries: each retry of a call that already succeeded on the carrier side creates another duplicate shipment.
C=Longer timeout: users wait longer and timeouts still happen occasionally.
D=Never retry: genuine failures then stay unrecovered, and users have no way to know which case they are in.
T: Make external calls idempotent and expose operation status before relying on retries.
