# PLTR-APD batch 23: Domain 6 round 3 (Automate and Operational Workflows), 8 questions

@ PLTR-APD D6 T6.1 applied comparison
S: Which trigger choice best fits "when a Shipment's status changes to Delayed, notify the customer once"?
A: A daily schedule that emails every customer with any delayed shipment, every day, for as long as the shipment stays delayed
B: A property-change trigger on status with a condition that the new value is Delayed, and an idempotent notification
C: A trigger on object creation, since every shipment is created before it can become delayed
D: A trigger on any change to any property of any shipment that emails the customer whenever something changes
K: B
G: ## Event on the transition
The exam guide asks you to select triggers, conditions and effects. "Changes to Delayed" is a property transition.
## Configuration
- Property-change trigger on status.
- Condition: new value = Delayed.
- Effect: notify with an idempotency key per shipment and delay event.
Example: a shipment delayed at 14:00 produces one customer email at 14:01.
W: A conditioned property-change trigger with idempotent notification: exactly one message at the moment the delay occurs.
X: A=Daily repeated emails: customers receive the same notice every day, which is not what "once" means.
C=Creation trigger: shipments are created long before any delay, so the condition is evaluated at the wrong time.
D=Any change: notifies customers about irrelevant edits and floods them with messages.
T: Trigger on the specific property transition and keep the effect idempotent.
V: Automate

@ PLTR-APD D6 T6.2 applied use-case
S: An automation in a project with sensitive data sends summaries to a Slack channel. The security team asks how to make sure it cannot read beyond its own project. What should be configured?
A: Run the automation as an administrator so that it never fails, and trust the summary content to be safe
B: Set the automation's project scope and execution identity to the minimum it needs
C: Move all sensitive data into a public project so that the automation's scope does not matter
D: Remove the automation and ask analysts to post summaries manually
K: B
G: ## Scope and identity for automations
The exam guide lists project scope and service ownership among automation configuration and least privilege among security principles.
## Configuration
- Execution identity with read access to the project's needed objects only.
- Project scope set; notification destinations reviewed.
- Content review of what the summary includes.
Example: the automation can read the case objects in its project but not HR data in another project.
W: Minimal project scope and execution identity: the automation reads only what its summaries need, and nothing more.
X: A=Administrator identity: grants the automation access to everything, the opposite of what security asked for.
C=Public project: exposes sensitive data to everyone to simplify one automation.
D=Manual posting: removes useful automation instead of scoping it.
T: Scope automations' project and execution identity to the minimum their effects need.

@ PLTR-APD D6 T6.3 applied troubleshooting
S: An automation that applies a discount when an order total exceeds 1,000 occasionally applies the discount twice. Logs show it ran twice when two line items were added to the order within the same second. What is happening and how is it fixed?
A: The platform has a bug that duplicates runs at random, and nothing at all can be done in the automation's own design
B: Two near-simultaneous updates each met the condition; make the discount idempotent with a flag
C: The order total is calculated incorrectly, so the threshold should be raised to 2,000
D: Users should be prevented from adding more than one line item per minute
K: B
G: ## Duplicate effects from near-simultaneous events
The exam guide asks you to account for duplicate effects and race conditions in automations.
## Fix
- Effect checks `discount_applied` before acting, and sets it atomically.
- Or trigger on the transition from ≤ 1,000 to > 1,000 only.
- Test with concurrent updates.
Example: two updates within a second now apply the discount once.
W: An idempotent effect guarded by an applied flag (or a transition condition): concurrent events can no longer double the discount.
X: A=Platform bug: two updates legitimately produced two evaluations; the design must tolerate it.
C=Raise the threshold: changes the business rule and leaves the duplication.
D=Limit user edits: restricts legitimate work to hide a design flaw.
T: Guard automation effects against concurrent events with idempotency checks or transition conditions.
V: Automate

@ PLTR-APD D6 T6.4 applied troubleshooting
S: An automation's evaluation history shows its condition is evaluated on every update, but the effect never runs. The condition compares a status to "approved". Objects do show status "Approved" in the application. What is the likely cause?
A: The automation's effect is disabled by the platform after 100 evaluations
B: The stored value differs in case or code from "approved"; compare it and fix the condition
C: The automation only runs its effects on weekdays, and all of the recent updates happened to occur at the weekend
D: The objects are too large for automations to evaluate
K: B
G: ## Evaluations that never match
The exam guide lists diagnosing evaluation failures among automation skills.
## Steps
- Inspect an evaluated object's stored value.
- Compare with the condition: case, enumeration code versus display label.
- Fix the condition; test with a known object.
Example: the stored value is "APPROVED"; the condition used "approved". After the fix, effects run.
W: The condition never matches the stored value: evaluation history shows activity, but a case or code mismatch keeps the effect from running.
X: A=Disabled after 100: no such limit; the effect never ran even once.
C=Weekdays only: no such schedule was configured; evaluations are happening.
D=Objects too large: evaluations are already completing; size is not the issue.
T: When conditions evaluate but never match, compare stored values with the condition's exact values.
V: Automate

@ PLTR-APD D6 T6.1 applied use-case
S: A team needs to remind account managers about contracts expiring in 30 days. Expiry dates are stored on Contract objects. Which automation design fits?
A: A trigger on contract creation that waits 30 days less than the contract term inside the effect before sending a reminder
B: A daily scheduled automation querying contracts expiring in exactly 30 days and notifying their managers idempotently
C: Ask managers to check the contract list every morning for upcoming expirations
D: A trigger on every change to any contract property that checks the expiry date each time
K: B
G: ## Time-based conditions with schedules
The exam guide lists schedules, conditions and effects among automation configuration.
## Design
- Daily schedule.
- Query: expiry date = today + 30 days.
- Effect: notify the manager; record that the reminder was sent.
Example: each morning, eight managers receive reminders for contracts expiring next month.
W: A daily query on expiry date with idempotent notifications: reminders arrive on time without long waits or noisy triggers.
X: A=Long wait in effect: a run that sleeps for months is fragile, invisible and lost if anything restarts.
C=Manual checks: depend on each manager's daily habit, so expirations are missed whenever someone is busy or away.
D=Every change: contracts that never change never trigger reminders.
T: Use daily schedules with date queries for time-based reminders.
V: Automate

@ PLTR-APD D6 T6.2 applied troubleshooting
S: An automation's notifications are going to a team channel, but the team says they are overwhelmed by hundreds of low-value alerts and ignore them. Real failures are missed. What should change?
A: Send the notifications to more channels as well, so that someone somewhere notices the important ones among the hundreds
B: Send only actionable failures to the team, put warnings in a digest, and tune conditions
C: Turn off all notifications, since the team ignores them anyway
D: Ask the team to read every notification carefully
K: B
G: ## Actionable notifications
The exam guide lists notifications and service ownership among automation configuration. Alerts must be actionable to be useful.
## Changes
- Failures after retries: immediate alert to the owner.
- Warnings and informational events: daily digest.
- Condition tuning to remove noise.
Example: daily alerts drop from 300 to 3, and the next real failure is handled within minutes.
W: Tiered, tuned notifications: real failures stand out and get handled, while lower-value information is still available.
X: A=More channels: spreads the same hundreds of low-value alerts to more people, who will ignore them too.
C=Turn off: real failures then go entirely unnoticed until users complain about the consequences.
D=Read everything: reading hundreds of alerts a day carefully is unrealistic, so important ones still slip through.
T: Make automation alerts actionable by tiering severity and tuning noise.
V: Automate

@ PLTR-APD D6 T6.3 applied use-case
S: An automation posts invoices to an ERP when they are approved. Occasionally the ERP accepts the invoice but the automation's response times out, and it retries. How should duplicates be prevented?
A: Disable retries so that a timeout never leads to a second attempt, even when the first attempt really failed
B: Send an idempotency key per invoice and store the ERP reference once confirmed
C: Ask the ERP team to delete duplicate invoices every morning
D: Wait 24 hours before retrying any failed attempt
K: B
G: ## Retry safety with external systems
The exam guide's practice scenario: a timeout after an external update requires idempotency and reliable status before more retries.
## Design
- Idempotency key derived from the invoice id.
- On retry, the ERP returns the existing invoice for that key.
- Store the ERP reference and status on the invoice object.
Example: a retried post receives the original ERP id; no duplicate is created.
W: Idempotency keys with stored references: retries are safe, so real failures are still recovered without duplicates.
X: A=Disable retries: invoices whose first attempt genuinely failed are never posted, creating a different gap.
C=Manual deletion: the ERP team cleans up every morning a problem the integration could prevent entirely.
D=24-hour delay: invoices are late and duplicates are still possible.
T: Make external effects idempotent before relying on retries.
V: Automate

@ PLTR-APD D6 T6.4 advanced use-case
S: Before enabling a new automation that will change thousands of objects nightly, the team wants confidence in its behaviour and a way to stop it quickly if something goes wrong. What should be in place?
A: Enable it on all objects immediately and review the results the next morning
B: Test on representative objects, start with a small subset, monitor, and keep a mute switch
C: Skip testing entirely because the automation only uses existing Actions that have already been tested on their own
D: Ask users to report any unexpected changes they notice
K: B
G: ## Safe enablement
The exam guide asks you to test automations safely before enabling production triggers and to handle partial failure.
## Plan
- Manual tests with representative objects.
- Start with a subset (one region or a sample).
- Monitor effects; mute switch; rollback steps documented.
Example: the first night runs on 200 objects; a wrong condition is caught and fixed before the full rollout.
W: Tests, staged enablement, monitoring and a quick stop: problems surface on a small scale and can be halted.
X: A=All at once: a mistake affects thousands of objects before anyone looks.
C=Skip testing: the automation's conditions and orchestration are new, even if the Actions are not.
D=User reports: changes to thousands of objects overnight are detected slowly and incompletely by whoever happens to notice.
T: Enable large automations in stages with monitoring and a quick way to stop them.
V: Automate
