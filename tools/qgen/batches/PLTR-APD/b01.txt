@ PLTR-APD D1 T1.2 applied use-case
S: A maintenance team needs an application where technicians record inspections of equipment. Each inspection belongs to one piece of equipment and is performed by one technician, and supervisors must see each machine's inspection history. How should the Ontology be modeled before any screen is designed?
A: A single Equipment object type with a list property holding inspection dates and a second list holding technician names in the same order
B: An Inspection object type with its own key, linked many-to-one to Equipment and to Technician, so history is a link traversal
C: An Inspection object type keyed on the equipment name, so that each machine has exactly one inspection object updated in place
D: Separate object types per equipment category, each with its own inspection properties, so screens can be tailored to each category
K: B
G: ## Model the workflow's entities first
The exam guide asks you to model entities, identity and cardinality before designing screens. An inspection is an event with its own attributes (date, result, notes) and two relationships.
## Model
- Inspection: stable key, date, result, notes.
- Links: Inspection → Equipment (many-to-one), Inspection → Technician (many-to-one).
- History: traverse Equipment → Inspections, sorted by date.
Example: pump P-12 shows 18 inspections by four technicians; a new inspection is one new object created by an Action.
W: An Inspection object with a stable key and two many-to-one links: each event has a home for its attributes, history is a natural traversal, and Actions can create inspections cleanly.
X: A=Parallel lists on Equipment: fragile ordering, no link to Technician objects, and no place for results or notes per inspection.
C=Keyed on equipment name: one object per machine overwrites history, and a name is not a stable identifier.
D=Types per category: duplicates the same concept across types, complicating every query, Action and screen.
T: Model events that relate entities as their own object type with a stable key and links to each participant.
V: Ontology Manager

@ PLTR-APD D2 T2.4 applied troubleshooting
S: A supervisor can open a purchase request in a Workshop module and see all its properties, but the Approve button is unavailable for them while a colleague with the same role can approve. What should the developer check first?
A: Whether the supervisor's browser is outdated, since unavailable buttons are usually a rendering problem in older browsers
B: The Action's permissions and submission criteria against this user and object, since viewing an object does not grant permission to act on it
C: Whether the object type's backing dataset is stale, since stale data always disables Actions for every user who opens the object
D: Whether the Workshop module needs to be republished, since buttons only appear for users who opened the module after its last publish
K: B
G: ## Read access is not write access
The exam guide's practice scenario is explicit: when a user can view an object but cannot approve it, inspect action-specific authorization and preconditions.
## Checks
- Action permissions: is this user (or a group they belong to) allowed to run the Action?
- Submission criteria: do the object's current state or the user's attributes fail a condition (for example, approver cannot be the requester, amount above the user's limit)?
- Compare with the colleague: same role, but different group membership or a criterion tied to the user.
Example: the criteria require approver ≠ requester; this supervisor created the request, so the button is disabled with an explanatory message.
W: Action permissions and submission criteria evaluated for this user and object: the only layers that make a visible object non-actionable for one user and actionable for another.
X: A=Outdated browser: the colleague sees the same module; a rendering issue would not track per-user authorization this precisely.
C=Stale data: staleness does not disable an Action for one user while another user can run it on the same object.
D=Republish the module: module publishing does not create per-user differences in Action availability.
T: When users can view but not act, check the Action's permissions and submission criteria for that user and object.
V: Action types, Workshop

@ PLTR-APD D3 T3.1 applied comparison
S: A team needs a function that computes a shipment's estimated cost from weight, distance and a tariff table, returns the same result for the same inputs, and will be maintained by engineers who already write TypeScript. Which paradigm fits?
A: AIP Logic, since any function that reads Ontology data should use a language model to interpret the inputs flexibly
B: A TypeScript v2 function, since the logic is deterministic, the team knows TypeScript, and no LLM capability is needed
C: A Workshop variable with a formula, since all calculations belong in the application layer rather than in Functions
D: A scheduled pipeline transform that precomputes every possible combination of weight, distance and tariff in a dataset
K: B
G: ## Choosing the function paradigm
The exam guide asks you to select TypeScript v2, Python v2 or AIP Logic based on determinism, runtime capabilities, LLM needs, maintainability and the maintainer audience.
## Reasoning
- Deterministic arithmetic over Ontology data: no LLM needed.
- Maintainers know TypeScript: maintainability favours TypeScript v2.
- Reusable: callable from Workshop, Actions and automations.
Example: `estimateCost(shipment)` reads the tariff object, computes the price and returns a typed result in milliseconds.
W: A TypeScript v2 function: deterministic, testable, reusable logic in the language its maintainers know, with no unnecessary model call.
X: A=AIP Logic: introduces nondeterminism and model cost for a calculation with one correct answer.
C=Workshop formula: logic locked into one module cannot be reused by Actions or automations and is harder to test.
D=Precompute every combination: the input space is effectively unbounded; a function computes on demand.
T: Choose the function paradigm by determinism, LLM need and maintainer skills; deterministic logic belongs in code.
V: Functions

@ PLTR-APD D4 T4.3 applied troubleshooting
S: A Workshop module loads slowly. The developer finds that a hidden tab contains several object tables and charts whose variables are computed on page load even though most users never open that tab. What change addresses this most directly?
A: Upgrade every user's laptop so that the browser can compute the hidden tab's variables faster on page load
B: Load the hidden tab's widgets and variables only when it is opened, and trim unneeded variable dependencies
C: Remove the hidden tab and its widgets entirely, since any content that most users do not open is unnecessary
D: Duplicate the module into two separate modules and ask users to choose which one to open each morning
K: B
G: ## Pay only for what users open
The exam guide lists variable dependencies, lazy loading and performance refactoring among Workshop skills. Work computed for content nobody sees is pure cost.
## Refactor
- Lazy load: the tab's widgets and their variables evaluate when the tab becomes visible.
- Dependency review: remove variables that recompute without being used.
- Measure load time before and after.
Example: initial load drops from 9 seconds to 2; the tab takes a second to appear for the few users who open it.
W: Lazy loading plus dependency cleanup: the expensive work moves to the moment it is needed, and the common path becomes fast.
X: A=Faster laptops: the queries and computations are not limited by the client alone, and the waste remains.
C=Remove the tab: some users need it; the problem is when it loads, not that it exists.
D=Two modules: duplicates maintenance and confuses users for a problem lazy loading solves.
T: Improve Workshop performance by deferring work for hidden content and trimming unnecessary variable dependencies.
V: Workshop

@ PLTR-APD D5 T5.2 applied use-case
S: A partner-facing web portal built with the OSDK runs on the partner's servers and must call Foundry to read a curated set of objects with no end user signed in to Foundry. How should authentication be set up?
A: Embed a Foundry user's personal token in the portal's front-end code, since the portal needs some credential to call the platform
B: Use a service-based (client credentials) application with scopes limited to the needed object types, with the secret held server-side
C: Ask each partner to sign in with a shared Foundry account whose password is published in the portal's help page
D: Grant the application access to every object type in the Ontology so that scope errors never occur in production
K: B
G: ## Service authentication with minimal scope
The exam guide asks you to choose user-based or service-based authentication without exposing secrets, and to scope Ontology resources.
## Setup
- Register the application for a service-based (client credentials) flow.
- Scopes: only the object types and Actions the portal needs.
- Secret stored on the portal's server, never in browser code; rotation planned.
Example: the portal's backend obtains a token with its client credentials and reads the partner catalog objects; nothing else is reachable.
W: Service-based authentication with least-privilege scopes and a server-side secret: the portal can run without a signed-in user and cannot reach more than it needs.
X: A=Personal token in front-end code: exposes a user's credential to anyone who opens the page and ties the portal to one person.
C=Shared published account: no identity, no audit and an exposed password.
D=Every object type: over-scoping turns any portal compromise into broad data exposure.
T: For headless external apps, use service-based OSDK authentication with minimal scopes and server-side secrets.
V: OSDK, Developer Console

@ PLTR-APD D6 T6.3 applied use-case
S: An automation sends a shipping notice to an external carrier API when an Order becomes "Ready". Because execution is at least once, the same order occasionally produces two notices. What design makes the effect safe?
A: Disable retries on the automation so that each Ready transition can only ever be processed one time
B: Make the effect idempotent with a per-order idempotency key and a notified status checked first
C: Add a five-minute delay before the effect so that duplicate triggers have time to cancel each other out
D: Ask the carrier to ignore duplicate notices manually when their staff notice two messages for the same order
K: B
G: ## Designing for at-least-once
The exam guide asks you to account for at-least-once execution and duplicate effects, and to design automations that stay safe when events repeat.
## Design
- Idempotency key derived from the order id with the external call, where the API supports it.
- Status on the order (`carrier_notified_at`), set atomically with the send; the effect checks it first.
- Retries remain enabled for transient failures.
Example: a retried run finds the order already notified and skips the call; the carrier receives exactly one notice.
W: Idempotency keys plus a notified status: repeats become harmless while retries still recover from transient failures.
X: A=Disable retries: transient failures then lose notices entirely; duplicates are traded for gaps.
C=Five-minute delay: duplicates do not cancel each other; both still run.
D=Carrier ignores duplicates: pushes the problem to a partner and relies on manual attention.
T: Make automation effects idempotent so at-least-once execution never produces duplicate external actions.
V: Automate

@ PLTR-APD D7 T7.4 applied troubleshooting
S: An engineer used AI FDE to generate a TypeScript function that updates order statuses. It compiles and passes a quick manual test, but the reviewer notices it loads every order in the Ontology and filters them in memory. What should happen before publishing?
A: Publish it, since compiled code that passes a manual test is ready for production regardless of how it was generated
B: Rework it to platform idioms (server-side filtering, pagination, bounded edits), add tests, check side effects
C: Ask AI FDE to regenerate the function repeatedly until a version appears that the reviewer does not object to
D: Replace the function with a Workshop button that asks users to update each order's status by hand instead
K: B
G: ## Reviewing generated function code
The exam guide asks developers to review AI FDE-generated Function code and validate schema, platform idioms, provenance and side-effect safety before publishing.
## Review
- Platform idioms: filter and paginate the object set server-side; avoid loading everything into memory.
- Bounded edits: only the intended objects; no unbounded traversal.
- Tests on representative and edge cases; side effects confirmed.
Example: the reworked function filters `status = "Packed"` server-side and updates 200 orders instead of loading 3 million.
W: Rework to platform idioms with bounded edits and tests: the generated draft becomes safe and scalable before anything is published.
X: A=Compiles and passes one test: an unbounded load works on a small test and fails or times out at production scale.
C=Regenerate until accepted: generation without understanding does not establish correctness.
D=Manual updates: abandons the automation instead of fixing the code.
T: Review generated Function code for platform idioms, bounded edits and side effects before publishing.
V: Functions, AI FDE

@ PLTR-APD D8 T8.3 applied troubleshooting
S: An automation creates follow-up tasks on objects that the user whose change triggered it cannot see. The user is confused, and an auditor asks how this is possible. What explains it, and what should be reviewed?
A: The platform has a bug that leaks hidden objects to automations, and the automation should be disabled until it is fixed
B: The automation runs under its own execution identity; review that identity's permissions and who can see the tasks
C: The triggering user must secretly have access to the objects, and their permissions should be removed immediately to be safe
D: Automations always run as administrators, so nothing can or should be reviewed about what they access
K: B
G: ## Execution identity versus user visibility
The exam guide's practice scenario: when an automation writes data the initiating user cannot see, distinguish the automation's execution identity from the user's visibility and review the resulting access model.
## Review
- Execution identity: which service identity or owner runs the automation, and what it can read and write.
- Least privilege: only the objects and Actions the workflow needs.
- Visibility of results: who should see the created tasks; adjust permissions on the outputs, not on the user.
Example: the automation runs as a project-scoped service identity; the tasks land in a project the requester cannot see, which is intended, and this is documented for the auditor.
W: Separate the automation's execution identity from the user's visibility and review both: the behaviour is explained and the access model is checked deliberately rather than by guesswork.
X: A=Platform bug: the behaviour follows from the automation's identity, which is how automations are designed to run.
C=User secretly has access: the user really cannot see the objects; the automation's identity can.
D=Always administrators: automations run under a configured identity whose permissions should be reviewed and minimized.
T: Distinguish execution identity from user visibility when automations act, and review both explicitly.
V: Automate, permissions
