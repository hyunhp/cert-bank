@ PLTR-APD D4 T4.1 applied use-case
S: A module needs a map of sites, a list of the selected site's assets, and a form to create a work order for the selected asset. How should the widgets be connected?
A: Three independent widgets where users must re-select the site and the asset separately in each one
B: Chain map selection → site variable → filtered asset list → asset variable → Action parameter
C: One giant table containing every site and asset together, with a free-text field for typing the asset id into the form
D: Three separate modules, one per widget, with users copying identifiers between them
K: B
G: ## Chained selection variables
The exam guide asks you to design the variable and event flow for a user workflow.
## Flow
- Map outputs selected site.
- Asset list filters by that site; outputs selected asset.
- Action form receives the asset as a default parameter.
Example: clicking a site shows its 40 assets; picking one opens a work order form for it.
W: A chain of selection variables: each widget narrows context for the next, and the Action receives the right asset automatically.
X: A=Independent widgets: users repeat selections and can mismatch site and asset.
C=Giant table with typed ids: slow, confusing and error-prone.
D=Separate modules: users copy site and asset identifiers between modules by hand, which is slow and error-prone.
T: Chain Workshop selections through variables into Action parameters.
V: Workshop, Action types

@ PLTR-APD D4 T4.3 applied troubleshooting
S: A dashboard module recomputes a heavy aggregation every time a user switches tabs, even though the data has not changed. Users find tab switching slow. What should be changed?
A: Remove the tabs and put all content on one long page so that nothing needs to recompute on navigation
B: Compute the aggregation outside the tabs' lifecycle so tab switches reuse it
C: Add a spinner on each tab so users understand the delay
D: Ask users to stay on one tab per session
K: B
G: ## Avoid unnecessary recomputation
The exam guide lists variable dependencies and performance refactoring among Workshop skills.
## Fix
- Compute the aggregation once in a variable whose inputs are the filters, not the active tab.
- Tabs read the result.
Example: tab switches become instant; the aggregation recomputes only when filters change.
W: Compute once and reuse across tabs: navigation stays fast while results update only when their real inputs change.
X: A=One long page: loses organization and still renders everything.
C=Spinners: make the delay visible but do not remove it; the aggregation still recomputes on every switch.
D=One tab per session: restricts users to work around a design flaw.
T: Make expensive Workshop variables depend on data inputs, not navigation state.
V: Workshop

@ PLTR-APD D4 T4.2 applied comparison
S: Which is the right way to show a list of a customer's open tickets in a Workshop module?
A: A text widget where a developer pastes ticket numbers by hand each morning
B: An object table bound to the selected customer's linked open-ticket object set
C: An image of the ticket system's screen refreshed weekly
D: A spreadsheet download link that users open in another program
K: B
G: ## Bind widgets to Ontology data
The exam guide asks you to connect Workshop to Ontology data.
- Object set: selected customer → tickets, filtered to open.
- Object table displays it; actions can be added per row.
Example: selecting a customer shows their five open tickets, always current.
W: An object table bound to the linked, filtered object set: always current, permission-aware and actionable.
X: A=Manual text: a developer pasting ticket numbers each morning is labour-intensive and stale within hours.
C=Weekly image: a static picture of another system cannot be filtered or acted on and is outdated within a day.
D=Spreadsheet download: leaves the application and its permissions.
T: Display Ontology data in Workshop through object tables bound to object sets.
V: Workshop

@ PLTR-APD D4 T4.4 applied use-case
S: A team builds the same "customer header" (name, tier, contact, risk badge) in five different modules, each slightly different. Maintenance is painful. What should they do?
A: Keep all five versions of the header and update each one by hand in its own module whenever the design changes
B: One reusable header module with a customer input, embedded in all five modules
C: Merge all five modules into one enormous module with every page
D: Remove the header from all modules to avoid maintenance
K: B
G: ## Reusable modules with stable interfaces
The exam guide lists modules among Workshop building blocks and asks you to preserve module interfaces.
## Approach
- One header module; input: customer object.
- Embedded in five modules.
- Interface changes made compatibly.
Example: adding a "VIP" badge to the header updates all five modules at once.
W: One embedded module with a stable input: changes are made once and appear everywhere consistently.
X: A=Five hand-maintained copies: each design change is made five times and the versions inevitably drift apart.
C=One enormous module: unmanageable and couples unrelated workflows.
D=Remove the header: users lose the customer context they rely on in every one of the five modules.
T: Factor repeated UI into reusable embedded modules with stable interfaces.
V: Workshop

@ PLTR-APD D4 T4.3 applied use-case
S: A module triggers an Action and then immediately reads a property the Action updates. Sometimes the read returns the old value. What should the developer do?
A: Add a fixed delay of several seconds after the Action before reading the property, and hope it is enough
B: Refresh the dependent widgets from the Action's completion event
C: Ask users to click a refresh button whenever values look wrong
D: Read the property twice and use the second value
K: B
G: ## Event ordering
The exam guide asks you to understand asynchronous event behaviour in Workshop.
## Fix
- On Action success: refresh the dependent object set or variable.
- Avoid reading before the write completes.
Example: the status badge updates as soon as the Action completes, every time.
W: Chain the refresh to the Action's completion: the read happens after the write, removing the race.
X: A=Fixed delay: sometimes still too short under load and usually longer than needed, so it fails and slows users at once.
C=Manual refresh: asks users to notice wrong values and fix the view themselves, which many will not do.
D=Read twice: the second read can still happen before the write completes, so the race remains.
T: Refresh dependent Workshop data from Action completion events, not fixed delays.
V: Workshop, Action types

@ PLTR-APD D4 T4.1 applied troubleshooting
S: A filter dropdown in a module shows only 50 values, but there are 300 regions. Users cannot find their region. What should the developer check?
A: Whether the users' screens are too small to display a dropdown list longer than fifty entries without scrolling
B: The dropdown's data source and limits; use a searchable filter that supports all values
C: Whether regions beyond the first 50 were deleted from the Ontology
D: Whether users should type the region into a free-text field instead
K: B
G: ## Filter configuration
The exam guide lists filters among Workshop design skills and asks you to diagnose why the interface does not show expected data.
## Fix
- Inspect how the dropdown's options are populated and any display limits.
- Use a searchable selector or property-value filter for large value sets.
Example: a searchable region filter lets users type "Nor" and find "Northern Highlands".
W: Configure the filter for the full value set with search: users find their region among 300 options.
X: A=Screen size: the fifty-value limit comes from how the dropdown is populated, not from the size of anyone's screen.
C=Deleted regions: other widgets in the same module still show those regions, so they exist in the Ontology.
D=Free-text field: invites typos and spelling variants that silently match nothing.
T: Use searchable filters for large value sets in Workshop.
V: Workshop

@ PLTR-APD D4 T4.2 applied tradeoff
S: A module needs a "risk score" per row in a table of 500 contracts. The score can come from a function computing it on the fly or from a property materialized nightly. Users sort by it and the score changes daily. Which is better?
A: A function-backed column computed live for all 500 rows every time the table loads or is sorted
B: A materialized property for display and sorting, with live detail for the selected contract
C: Ask users to compute risk scores in a spreadsheet and enter them manually
D: Hide the risk score since it cannot be both fast and current
K: B
G: ## Materialize for sorting
The exam guide covers performance refactoring and connecting Workshop to Ontology data.
## Reasoning
- Daily-changing value; sorting across 500 rows.
- Materialized property sorts instantly.
- Live function for the selected item if exact freshness matters.
Example: the table sorts instantly; the side panel shows a live recomputation for one contract.
W: A materialized property for list operations plus live detail where needed: fast sorting with sufficient freshness.
X: A=Live for all rows: slow loads and sorting for a daily-changing value.
C=Spreadsheet entry: scores typed in by hand are error-prone and out of date by the next day.
D=Hide the score: users lose information they need, when a materialized property makes it both fast and current enough.
T: Materialize values used for list sorting; compute live only for selected items.
V: Workshop, Ontology

@ PLTR-APD D4 T4.4 advanced tradeoff
S: A team wants to add a major new page to a module used daily by 300 people, but the page's queries are heavy and not yet tuned. How should they release it?
A: Add the page to the live module immediately and tune its performance later, based on whatever complaints users send
B: Develop and tune on a branch, pilot with a small group, then release with monitoring
C: Never add new pages to busy modules
D: Build the page as a separate module and stop maintaining the original
K: B
G: ## Safe release of heavy features
The exam guide asks you to preserve module behaviour when changing it and to choose deployment carefully.
## Approach
- Branch development and tuning.
- Pilot with a small group; measure load.
- Release with monitoring; ability to hide the page quickly.
Example: the pilot reveals a slow aggregation; it is materialized before 300 users see the page.
W: Branch, tune, pilot and monitor: the new page arrives without slowing the module for everyone.
X: A=Release then tune: all 300 daily users experience the untuned page's slowness before anyone fixes it.
C=Never add pages: blocks legitimate improvements users need in order to avoid a problem that piloting solves.
D=Abandon the original: splits users across two modules and leaves one of them unmaintained.
T: Release heavy Workshop features through branches, pilots and monitoring.
V: Workshop, branches
