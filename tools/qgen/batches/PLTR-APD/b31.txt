@ PLTR-APD D6 T6.1 applied use-case
S: An automation must generate a weekly compliance report every Monday at 07:00 from objects updated during the previous week, and notify the compliance lead. Which configuration fits?
A: A trigger on every object update during the week that regenerates the report each time any object changes
B: A Monday 07:00 schedule querying last week's updates, generating one report and notifying the lead
C: A manual button that the compliance lead clicks on Monday morning whenever they remember to
D: A daily schedule that sends seven partial reports per week to the compliance lead
K: B
G: ## Scheduled reports
The exam guide asks you to select triggers and effects that fit the requirement.
## Configuration
- Schedule: Monday 07:00.
- Query: updated between last Monday and Sunday.
- Effect: generate the report; notify the lead; record completion.
Example: every Monday at 07:00 the lead receives one report covering the prior week.
W: A weekly schedule with a bounded query and one notification: exactly the report requested, on time, once.
X: A=Every update: regenerates the report thousands of times a week for a single Monday deliverable.
C=Manual button: depends on the lead remembering and delays the report whenever they forget.
D=Seven partial reports: fragments the weekly view and floods the lead with messages.
T: Use schedules with bounded queries for periodic reports.
V: Automate

@ PLTR-APD D6 T6.2 applied troubleshooting
S: An automation retries a failing external call up to 20 times with no delay between attempts. When the external system is down, the automation hammers it and floods logs. What should change?
A: Increase retries to 100 so that the call eventually succeeds when the system comes back
B: Fewer retries with backoff and jitter, then a pending fallback and an owner alert
C: Remove retries entirely so that the automation fails on the first error every time
D: Run the automation every second to keep trying
K: B
G: ## Retries with backoff and fallbacks
The exam guide lists retries, backoff, fallbacks and notifications among automation configuration.
## Change
- Retries: few, with exponential backoff and jitter.
- Fallback: mark pending; queue for later.
- Notify the owning team on exhaustion.
Example: during a 2-hour outage, the automation makes a handful of attempts per item, then queues them; all are processed after recovery.
W: Backoff, bounded retries and a pending fallback: the external system is not hammered and work is preserved and visible.
X: A=More retries: a hundred immediate attempts per item multiply the hammering and the log noise during an outage.
C=No retries: every brief network blip becomes a failed run, even when a second attempt seconds later would succeed.
D=Every second: running the whole automation every second amplifies the hammering instead of backing off.
T: Configure bounded retries with backoff, then fall back and alert.
V: Automate

@ PLTR-APD D6 T6.3 applied use-case
S: An automation updates customer tiers nightly. A developer needs to change the tier rules while the automation is live and some runs are in progress. What should they do?
A: Edit the rules mid-run so that remaining customers get the new rules and earlier ones keep the old rules
B: Change between runs, test first, and record the rule version applied to each customer
C: Disable the automation permanently and update tiers manually from now on
D: Change the rules in a copy of the automation and let both run every night
K: B
G: ## Changing live automations
The exam guide asks you to account for live workflow changes and in-flight work.
## Approach
- Change between runs, not mid-run.
- Test with representative customers.
- Record rule version on each tier update.
Example: the new rules apply from Thursday night; every customer's tier shows "rules v4".
W: Change between runs with testing and version recording: every customer is processed consistently under a known rule version.
X: A=Mid-run edit: customers in the same run get different rules.
C=Manual updates forever: gives up a working automation and replaces it with slow, error-prone manual tier changes.
D=Two copies: both automations update the same customers each night, overwriting each other's tiers.
T: Change live automations between runs, tested and with rule versions recorded.
V: Automate

@ PLTR-APD D6 T6.4 applied troubleshooting
S: An automation's effect calls an Action, and the effect history shows failures with "submission criteria not met". The automation's condition matched. What is the likely explanation?
A: The automation is broken and must be recreated from scratch
B: The condition matched but the Action's criteria rejected it at execution; align them
C: Automations cannot call Actions, so the effect should be removed
D: The Action's submission criteria are always ignored for automations, so this error message must be impossible
K: B
G: ## Condition versus criteria
The exam guide lists diagnosing evaluation and effect failures among automation skills.
## Investigation
- Compare the automation's condition with the Action's submission criteria.
- Check object state at execution time (it may have changed).
- Align the condition or handle rejections explicitly.
Example: the automation triggered on "Approved", but the Action also requires a payment reference, missing on some objects.
W: The condition matched but the Action's criteria did not: aligning them or handling rejections removes the failures.
X: A=Recreate: the mismatch between the condition and the Action's criteria would be recreated exactly as before.
C=Cannot call Actions: automations commonly call Actions as effects; the failure comes from the criteria.
D=Criteria ignored: submission criteria apply to every invocation, including those from automations, which is why it failed.
T: Align automation conditions with the Action criteria their effects must pass.
V: Automate, Action types

@ PLTR-APD D6 T6.1 applied comparison
S: Which situation is the clearest case for an event-triggered automation rather than a schedule?
A: A monthly summary of all incidents sent to leadership on the first business day
B: Notifying an on-call engineer as soon as an incident's severity is raised to Critical
C: Archiving all closed tickets older than one year every night
D: Recalculating customer lifetime value once per week
K: B
G: ## Event-driven reactions
The exam guide asks you to select triggers and evaluation modes. Immediate reactions to changes are events.
- Severity raised to Critical: event, immediate.
- Monthly summaries, nightly archiving, weekly recalculations: schedules.
Example: the engineer is paged within a minute of the change.
W: An immediate reaction to a specific change is the defining case for an event trigger.
X: A=Monthly summary: produced on a calendar date regardless of any particular change, which is a schedule.
C=Nightly archiving: a periodic sweep over old tickets that is naturally a scheduled automation.
D=Weekly recalculation: a periodic batch computation that a weekly schedule handles, not a reaction to an event.
T: Use event triggers for immediate reactions and schedules for periodic work.
V: Automate

@ PLTR-APD D6 T6.2 applied use-case
S: A team moves an automation from a personal project into a team project. They want failures to reach the team and the automation to keep running if its creator leaves. What should be configured?
A: Keep the creator as owner and execution identity, and forward failure emails manually
B: Team ownership, a team execution identity, the right project scope and team-routed alerts
C: Give the automation administrator rights so that it never depends on anyone's permissions
D: Ask every team member to create their own copy of the automation
K: B
G: ## Durable ownership
The exam guide lists service ownership, project scope and notifications among automation configuration.
## Configuration
- Owner: team.
- Execution identity: team-managed, least privilege.
- Scope: the team project.
- Notifications: team channel or rotation.
Example: the creator leaves; the automation runs and alerts reach the team as before.
W: Team ownership, team identity, correct scope and team notifications: the automation survives staff changes and failures reach someone.
X: A=Creator-owned: when the creator leaves, the identity loses access, the automation stops and nobody is notified.
C=Administrator rights: gives the automation far more access than it needs, enlarging the impact of any mistake.
D=Personal copies: several automations react to the same events and produce duplicate effects.
T: Give automations team ownership, team identities and team-routed notifications.
V: Automate

@ PLTR-APD D6 T6.3 applied troubleshooting
S: An automation that creates invoices on order completion produced two invoices for some orders after a platform hiccup caused events to be redelivered. What design prevents this?
A: Ask the platform team to guarantee exactly-once delivery for all events in the future
B: Create invoices idempotently, checking for an existing one or using a deterministic key
C: Disable the automation during platform maintenance windows
D: Delete duplicate invoices manually after each incident
K: B
G: ## At-least-once delivery
The exam guide states that automations must account for at-least-once execution and duplicate effects.
## Design
- Deterministic invoice key from the order id.
- Effect checks existence before creating.
- Test by replaying events.
Example: a redelivered event finds invoice INV-O-881 already exists and exits.
W: Idempotent creation: redelivered events become harmless, which is the expected design under at-least-once execution.
X: A=Exactly-once guarantee: the design must assume repeats can happen.
C=Disable during maintenance: redelivery can happen at other times too.
D=Manual deletion: someone cleans up duplicate invoices after every incident, a problem idempotency would prevent entirely.
T: Design automation effects to be idempotent under redelivered events.
V: Automate

@ PLTR-APD D6 T6.4 advanced use-case
S: Before turning on a new automation that sends payment reminders to customers, the team wants to confirm it will contact the right customers with the right amounts. What should they do?
A: Turn it on for all overdue customers at once and check a small sample of the emails that were sent the next morning
B: Test with representative objects and test recipients, then enable for a small monitored segment
C: Trust the conditions because they were written carefully
D: Enable it and ask customers to report errors
K: B
G: ## Testing before live triggers
The exam guide asks you to test automations safely before enabling production triggers.
## Steps
- Manual runs on representative objects (overdue, just paid, disputed).
- Test recipients; review content and amounts.
- Enable for a small segment; monitor; expand.
Example: testing reveals disputed invoices would receive reminders; a condition excludes them before go-live.
W: Manual tests with safe recipients, then a small monitored rollout: mistakes are caught before customers receive them.
X: A=Enable for all: any wrong condition or amount reaches every overdue customer before the team checks a single email.
C=Trust: carefully written conditions still miss cases such as disputed invoices; only testing reveals them.
D=Customers report errors: unacceptable for payment communications.
T: Test customer-facing automations with test recipients and roll out gradually.
V: Automate
