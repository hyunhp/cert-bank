# PLTR-APD batch 10: Domain 1 round 2 (Ontology Schema Design and Workflow Assembly), 8 questions

@ PLTR-APD D1 T1.1 applied use-case
S: A permit-tracking application needs a "jurisdiction" attribute on Permit, Inspection and Violation objects, always one of 40 official jurisdiction codes. Different teams own the three object types. How should the attribute be defined?
A: Let each team define its own jurisdiction property in whatever format their source system uses, and reconcile the values later in each application
B: A shared property with a value type restricting it to the 40 codes, used by all three object types
C: A free-text property on each object type, with a wiki page listing the 40 official codes for teams to copy from
D: A separate Jurisdiction lookup application that users open to translate codes whenever they read a permit
K: B
G: ## One definition for a cross-cutting attribute
The exam guide lists shared properties and value types among Ontology constructs. A shared property gives one meaning across types; a value type constrains the allowed values.
## Design
- Value type: the 40 official codes.
- Shared property `jurisdiction` used by Permit, Inspection and Violation.
- Pipelines map source values to the codes; unknown values are flagged.
Example: a cross-type filter "jurisdiction = J-17" returns permits, inspections and violations consistently.
W: A shared property constrained by a value type: every team uses the same definition and invalid codes are rejected rather than reconciled later.
X: A=Team-specific formats: guarantees inconsistent values across the three types and pushes reconciliation into every application.
C=Free text plus a wiki: nothing enforces the codes, so typos and variants enter the Ontology unchecked.
D=Lookup application: adds a manual step to every read and still leaves the stored values inconsistent.
T: Define cross-cutting constrained attributes once as shared properties with value types.
V: Ontology Manager

@ PLTR-APD D1 T1.2 applied use-case
S: An application tracks Projects and Employees. An employee can work on many projects and a project has many employees, and the application must show each person's role and allocation percentage on each project. Which model is correct?
A: A many-to-many link between Project and Employee with no properties, and the role stored as a property on the Employee object
B: An Assignment object type holding role and allocation, linked many-to-one to both Project and Employee
C: A list of employee names on each Project, with a parallel list of roles and another of allocation percentages
D: A single Employee property listing every project name, separated by commas, with roles written in brackets
K: B
G: ## Relationships that carry data
The exam guide asks you to select appropriate cardinality and meaningful relationships. A role and allocation belong to the pair (employee, project), not to either side alone.
## Model
- Assignment: key, role, allocation, start date.
- Links: Assignment → Project, Assignment → Employee.
- Actions create and end assignments with validation (allocations ≤ 100%).
Example: Ana is Lead at 60% on Apollo and Reviewer at 20% on Zeus.
W: An Assignment object linked to both sides: the role and allocation have a home, and both directions remain queryable and editable through Actions.
X: A=Plain many-to-many with role on Employee: an employee has a different role on each project, so one property cannot represent it.
C=Parallel lists: fragile ordering, no links to Employee objects and no way to validate allocations.
D=Comma-separated text: unqueryable, unlinked and impossible to edit safely through Actions.
T: Model many-to-many relationships that carry attributes as their own object type.
V: Ontology Manager

@ PLTR-APD D1 T1.3 applied use-case
S: A field-service workflow must let a dispatcher assign a job, let a technician accept it on a tablet, and automatically notify the customer once accepted. Which assembly fits the guide's lifecycle?
A: One Workshop page where the dispatcher edits job properties directly in a table, and the customer is notified manually by phone after the technician calls in
B: A dispatcher module with an Assign Action, a technician module with an Accept Action, and an automation notifying the customer on acceptance
C: A spreadsheet shared by dispatchers and technicians, with customers emailed from personal inboxes when someone remembers
D: A single AIP agent that assigns, accepts and notifies on its own, without any user interaction or confirmation
K: B
G: ## Each step in its component
The exam guide's lifecycle: identify state changes, implement them as Actions, orchestrate follow-ups with automations, and design interfaces per user.
## Assembly
- Dispatcher module: Assign Action with validation (technician available, skill match).
- Technician module: Accept Action; status visible.
- Automation: on acceptance, notify the customer (idempotent).
Example: the job is assigned at 09:00, accepted at 09:05, and the customer receives a message at 09:06.
W: Role-specific modules with Actions for each state change and an automation for the notification: governed, auditable and tailored to each user.
X: A=Direct table edits and phone calls: no validation, no audit, and the notification depends on someone remembering.
C=Shared spreadsheet: ungoverned, conflicting edits and unreliable customer communication.
D=Autonomous agent: removes the dispatcher's and technician's decisions from a process that needs them.
T: Assemble workflows with role-specific modules, Actions for state changes and automations for follow-ups.
V: Workshop, Action types, Automate

@ PLTR-APD D1 T1.4 applied troubleshooting
S: After a link type between Supplier and Contract was deleted during a cleanup, two applications and a scheduled automation started failing. The developer did not know they depended on it. What practice would have prevented this?
A: Deleting link types only on Fridays, so that any failures happen over the weekend when fewer users are affected
B: Checking Workflow Lineage for consumers of the link type before the change, then migrating them or keeping the link
C: Never deleting anything from the Ontology, so that unused resources accumulate indefinitely
D: Asking users to report failures quickly so that the link can be recreated after the fact
K: B
G: ## Impact before removal
The exam guide asks you to use Workflow Lineage to understand impact and plan changes without breaking live consumers.
## Practice
- Lineage on the link type: modules, Functions, Actions, automations using it.
- Migrate or retire consumers first; then remove.
- Communicate with owners.
Example: lineage shows two modules and one automation; they are updated on a branch before the link is removed.
W: Lineage-based impact analysis before removal: dependents are found and migrated first, so cleanup breaks nothing.
X: A=Friday deletions: failures still happen; only the timing of the damage changes.
C=Never delete: the Ontology fills with unused resources that confuse developers and users.
D=Recreate after failures: users absorb the outage and the recreated link may not match the original.
T: Check Workflow Lineage before removing or changing Ontology resources.
V: Workflow Lineage

@ PLTR-APD D1 T1.1 applied comparison
S: Which statement about modelling before designing screens reflects the guide's recommended approach?
A: Design the screens first and create whatever object types the screens happen to need, one per screen
B: Model meaningful objects and links with stable identity first, then design the interface on top of that model
C: Store all data in one object type with generic columns so that any screen can display anything it needs
D: Skip the Ontology and bind screens directly to datasets, since modelling slows development down
K: B
G: ## Model first
The exam guide's decision table: model meaningful objects and links before designing the interface, checking identity, properties, editability and whether the data supports the relationships.
- Screen-shaped object types duplicate entities and break reuse.
- A generic single type loses meaning, validation and links.
Example: Case, Customer and Message are modelled first; three modules then reuse them.
W: Model the domain first and build screens on it: object types stay meaningful and reusable across applications.
X: A=One type per screen: duplicates entities and couples the Ontology to today's layout.
C=One generic type: loses meaning, validation and links between entities.
D=Bypass the Ontology: binding screens straight to datasets loses Actions, links and the object-level permissions applications rely on.
T: Model objects and links before designing screens.
V: Ontology Manager

@ PLTR-APD D1 T1.2 applied troubleshooting
S: A link between Order and Customer is backed by a customer id column, but many orders show no linked customer in the application although the customer exists. What should the developer check?
A: Whether the application's layout hides linked objects when the screen is narrower than a certain width
B: Whether the foreign key values match the customer primary keys exactly (format, case, padding) and whether the user can see those customers
C: Whether customers need to be re-created every time a new order is placed
D: Whether link types only display the first hundred links ever created in the Ontology
K: B
G: ## Links depend on matching keys
The exam guide asks you to check whether the data supports a relationship. A link resolves only when the foreign key equals the target key, and the reader can see the target.
## Checks
- Key formats: "C-0042" versus "C42", trailing spaces, case.
- Orphans: ids with no customer.
- Permissions: the user may not see some customers.
Example: the order source pads ids with zeros; normalizing them in the pipeline restores 30,000 links.
W: Matching key values and target visibility decide whether a link resolves: the check finds both data and permission causes.
X: A=Layout width: the link returns no object at all; it is not a display issue.
C=Re-create customers: customers persist; the join values do not match.
D=First hundred links: no such limit explains specific orders missing their customer.
T: When links appear missing, verify foreign key formats and target visibility.
V: Ontology Manager, permissions

@ PLTR-APD D1 T1.3 applied tradeoff
S: A team wants a workflow where AI suggests a resolution category for each incident and an analyst confirms it. They debate storing the AI suggestion and the confirmed category in the same property. What is the better design?
A: One property overwritten by the AI and then by the analyst, since only the final value matters to anyone
B: Separate properties for the AI suggestion and the confirmed category, with the confirmation written by an Action
C: Store only the AI suggestion and treat it as final, since analysts usually agree with it
D: Store neither and let analysts type the category into a comment field
K: B
G: ## Keep suggestion and decision apart
The exam guide asks for auditable state changes and separating AI recommendations from execution.
## Design
- `ai_suggested_category` written by the AI step (with version).
- `confirmed_category` written by the analyst's Action (with user and time).
- Metrics: agreement rate between the two.
Example: the analyst overrides 12% of suggestions; the team uses those cases to improve the prompt.
W: Separate suggestion and decision with an Action for confirmation: the decision is attributable, and disagreement becomes measurable feedback.
X: A=One overwritten property: loses which value came from the AI and which from the analyst.
C=AI as final: removes the confirmation the workflow requires.
D=Comment field: free text cannot be filtered, counted or compared with the AI suggestion, so neither reporting nor feedback works.
T: Store AI suggestions and human decisions separately, with the decision written by an Action.
V: Action types, AIP Logic

@ PLTR-APD D1 T1.4 advanced use-case
S: A user reports they cannot see a new module's data, while the developer can. The module reads two object types, one backed by a restricted view. What is the most efficient way to locate the cause?
A: Grant the user Owner on every project in the workflow, then remove permissions one at a time until the module breaks again
B: Follow the module's dependencies with Workflow Lineage and check the user's access at each layer, especially the restricted view's policy
C: Recreate the module under the user's account so that it uses their permissions from the start
D: Ask the user to clear their browser cache and try again every few hours
K: B
G: ## Lineage-guided access checks
The exam guide asks you to use Workflow Lineage to troubleshoot access and to avoid over-permissioning.
## Approach
- Lineage: module → object types → backing datasets and views.
- Check the user's access at each step; the restricted view's policy is a likely candidate.
- Change the exact control.
Example: the policy requires a department attribute the new user lacks; HR updates the profile.
W: Trace the dependencies and check access per layer: the restricted view's policy is identified without broad grants.
X: A=Grant everything then subtract: exposes data broadly and is slow.
C=Recreate under the user: modules evaluate the reader's permissions anyway; nothing changes.
D=Clear cache: access is evaluated on the server for each request, so clearing the browser cache changes nothing.
T: Use Workflow Lineage to find the layer that denies a user, then fix that control.
V: Workflow Lineage, restricted views
