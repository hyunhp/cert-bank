# PLTR-APD batch 13: Domain 4 round 2 (Workshop Application Development), 8 questions

@ PLTR-APD D4 T4.3 applied troubleshooting
S: In a Workshop module, a chart depends on a filter variable, and a table depends on the chart's selection. Users report the table sometimes shows data for the previous filter after they change it. What is likely happening?
A: The Ontology is returning stale data, which is unrelated to the module's variables and must be fixed by the data engineering team
B: An async ordering issue: the table reads the chart's old selection; reset or derive the selection from the filter
C: The users' monitors refresh too slowly to show the new table values in time
D: Workshop tables can only update once per minute, so users must wait before reading them
K: B
G: ## Variable dependencies and async events
The exam guide asks you to understand variable dependencies and asynchronous event behaviour and to diagnose stale interfaces.
## Fix
- Reset the chart selection when the filter changes.
- Or derive the table's input from both filter and selection so it cannot use a stale selection.
- Test rapid filter changes.
Example: after resetting selection on filter change, the table always reflects the current filter.
W: A stale intermediate selection in the dependency chain: resetting or deriving it removes the race between variable updates.
X: A=Stale Ontology data: the same data shows correctly after the selection refreshes; the module's wiring causes it.
C=Monitor refresh: the screen shows whatever the table holds; the wrong rows come from the module's variable wiring.
D=Once-per-minute updates: no such limit; tables update with their inputs.
T: Diagnose stale Workshop views through variable dependencies and asynchronous update order.
V: Workshop

@ PLTR-APD D4 T4.1 applied use-case
S: A module serves several user steps: search for a case, review details, and record a decision. Users get lost in one long scrolling page. What design improves usability?
A: Add more widgets to the same page and shrink them so that everything is visible at once without any scrolling at all
B: Pages or sections per step with clear navigation, carrying the selected case as a variable
C: Create a separate module for each step and ask users to copy the case id between modules
D: Remove the decision step and record decisions by email instead
K: B
G: ## Structure around the workflow
The exam guide asks you to design pages, sections and layouts around the user workflow.
## Design
- Page or section per step; navigation between them.
- Selected case passed as a variable.
- Decision step offers the Action with context.
Example: users move from Search to Review to Decide without losing the selected case.
W: Workflow-shaped pages with a shared selection variable: users follow the process without scrolling or retyping.
X: A=More widgets on one page: adds to the overload that is confusing users and makes each widget harder to read.
C=Separate modules with copied ids: friction and errors from manual context passing.
D=Email decisions: decisions leave the platform without validation, permissions or an audit trail.
T: Organize Workshop modules into pages or sections that follow the workflow, passing context through variables.
V: Workshop

@ PLTR-APD D4 T4.2 applied use-case
S: A module must show a list of a manager's direct reports and, for each, a computed "workload score" from a function. The list can have up to 50 people. How should it be built?
A: Call the workload function separately from 50 text widgets, each configured by hand for one employee
B: An object table of the manager's reports with a function-backed workload column
C: Ask managers to compute workload in a spreadsheet and upload it to the module
D: Hard-code each employee's workload into the module and update it monthly
K: B
G: ## Function-backed columns
The exam guide asks you to connect Workshop to Ontology data and Functions. A computed value per row belongs in a function-backed column.
## Design
- Object set: reports linked to the selected manager.
- Function-backed column: workload(employee).
- Sorting and filtering on the column as needed.
Example: the table lists 23 reports with current workload scores, sorted highest first.
W: A table over the manager's reports with a function-backed column: one configuration scales to any team size and stays current.
X: A=50 hand-configured widgets: brittle and breaks when the team changes.
C=Spreadsheet upload: managers do manual work each time and the uploaded scores are stale as soon as data changes.
D=Hard-coded values: the scores are wrong the day after they are typed and every team change needs a module edit.
T: Use function-backed columns for computed values per row in Workshop tables.
V: Workshop, Functions

@ PLTR-APD D4 T4.4 applied troubleshooting
S: After a developer renamed an output variable of an embedded module, two parent modules stopped receiving the selected object. What happened and how should this be avoided?
A: Embedded modules randomly lose connections over time, and parent modules must be rebuilt periodically
B: The rename broke the interface; restore compatibility or migrate parents together via lineage
C: The parent modules need more memory to receive outputs from embedded modules
D: Embedded modules can only output text, not objects, which is why the selection stopped working
K: B
G: ## Interfaces are contracts
The exam guide asks you to preserve module interfaces when making changes.
## Practice
- Treat inputs and outputs as a contract.
- Find embedding parents before changes.
- Keep the old name during transition or update parents in the same change.
Example: the variable is restored as `selectedOrder`; a new output is added alongside for future use.
W: The rename broke the interface; compatible changes coordinated with parents keep embeddings working.
X: A=Random disconnection: the break coincides exactly with the rename.
C=More memory: a broken binding is a configuration mismatch; resources have nothing to do with it.
D=Text only: modules pass objects; it worked before the rename.
T: Preserve embedded module interfaces or migrate parents together when changing them.
V: Workshop, Workflow Lineage

@ PLTR-APD D4 T4.3 applied tradeoff
S: A module recomputes an expensive function-backed variable every time any filter changes, even filters unrelated to it. Users find the module sluggish. What is the best refactor?
A: Remove all filters from the module so that the expensive variable is computed only once when the page loads
B: Make the variable depend only on the inputs it needs, so unrelated filters do not trigger recomputation
C: Add a loading spinner over the whole module while the variable recomputes
D: Ask users to change filters less often
K: B
G: ## Precise dependencies
The exam guide lists variable dependencies and performance refactoring among Workshop skills.
## Refactor
- Inspect which inputs the variable uses.
- Remove unrelated dependencies.
- Measure response time after.
Example: changing the date filter no longer recomputes the region score; response time falls from 4 to 0.5 seconds.
W: Narrow the dependencies: the expensive variable recomputes only when the inputs it actually uses change, so unrelated filters respond instantly.
X: A=Remove filters: users lose the filters they need to do their work; the slowness is fixed by removing features.
C=Spinner: hides the slowness instead of removing it, which the exam guide explicitly warns against.
D=Change filters less: asks users to work around a design problem the developer can fix in configuration.
T: Make Workshop variables depend only on the inputs they use.
V: Workshop

@ PLTR-APD D4 T4.2 applied comparison
S: Which is the most appropriate way for a Workshop module to let users change an object's status?
A: An editable table cell bound directly to the status property, with no Action, validation or audit trail behind it
B: An Action button or inline Action that runs the configured Action Type with validation and permissions
C: A text box where users type the new status and a developer applies it later
D: A link to the backing dataset where users edit the value directly
K: B
G: ## Writes go through Actions
The exam guide distinguishes reading data from changing state through an Action Type.
- Action: validation, permissions, audit, side effects.
- Direct edits bypass these controls.
Example: changing status to "Closed" runs the Close Ticket Action, which checks open subtasks first.
W: Use Actions for state changes in Workshop: every change is validated, permitted and audited.
X: A=Direct edit without an Action: any value can be written with no validation, permission check or audit trail.
C=Developer applies later: every status change waits for a developer and becomes manual work.
D=Edit the dataset: bypasses the Ontology, its Actions and its permissions entirely.
T: Change object state in Workshop through Actions.
V: Workshop, Action types

@ PLTR-APD D4 T4.1 applied use-case
S: A module should display a warning banner when the selected order's delivery date is in the past and its status is not "Delivered". How should this be built?
A: Ask users to compare the dates themselves and remember to check the status
B: A derived boolean variable controlling the banner's conditional visibility
C: A separate module showing all overdue orders that users must open alongside the main one
D: A daily email listing overdue orders to all users
K: B
G: ## Conditional visibility from derived state
The exam guide lists variables and conditional visibility among Workshop features.
## Design
- Variable: isOverdue = deliveryDate < today and status ≠ Delivered.
- Banner visible when isOverdue.
- Optionally offer an Action from the banner.
Example: selecting order O-55 shows "Delivery overdue by 3 days".
W: A derived condition variable driving visibility: the warning appears exactly when it applies, with no user effort.
X: A=Users compare: each user must notice dates and statuses themselves, so overdue orders are missed inconsistently.
C=Separate module: users must keep a second module open and match orders by hand while working.
D=Daily email: a list in an inbox is not tied to the order the user is looking at, and it is a day old.
T: Drive contextual warnings with derived variables and conditional visibility.
V: Workshop

@ PLTR-APD D4 T4.4 advanced use-case
S: A module used by 500 people must be substantially redesigned. The team wants to avoid disrupting users while the new version is built and tested. What approach fits?
A: Edit the live module directly during business hours and fix whatever problems users report as the redesign progresses
B: Build it on a branch or new version, pilot it, communicate, then switch with a rollback option
C: Delete the old module first so that users are forced to wait for the new one
D: Keep both modules forever and let users choose
K: B
G: ## Releasing module changes safely
The exam guide asks you to choose deployment channels and change applications without disruption.
## Approach
- Build on a branch or as a new module version.
- Pilot with a few users; collect feedback.
- Communicate; switch; keep rollback for a period; retire the old version.
Example: 20 pilot users find two confusing labels; they are fixed before 500 users switch.
W: Branch or versioned build, pilot, communicate and switch with rollback: the redesign arrives without disrupting daily work.
X: A=Edit live: 500 users experience every half-finished intermediate state and become the testers.
C=Delete first: users have no working tool at all until the new module is ready.
D=Both forever: two modules to maintain and users unsure which one is current.
T: Redesign live modules on branches or versions with pilots and rollback.
V: Workshop, branches
