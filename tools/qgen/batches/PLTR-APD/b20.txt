# PLTR-APD batch 20: Domain 3 round 3 (Ontology Functions), 8 questions

@ PLTR-APD D3 T3.2 applied use-case
S: A function must update the status of all open tasks linked to a project when the project is cancelled. Projects can have up to 5,000 tasks. How should the edits be implemented safely?
A: Loop over every task in the Ontology, checking each one's project link in memory, and edit the matching tasks one at a time
B: Query the project's linked tasks filtered to open status server-side and return bounded edits for them, tested on a large project
C: Ask users to open each task and change its status manually after cancelling the project
D: Edit only the first 100 tasks, since functions should never edit more than 100 objects in any situation
K: B
G: ## Targeted, bounded edits
The exam guide lists querying, filtering, traversing links and performing edits safely among function skills.
## Implementation
- Traverse project → tasks with a server-side filter on open status.
- Return edits for exactly those tasks.
- Test with the largest project; confirm limits and duration.
Example: cancelling a project with 4,200 open tasks updates them all in one Action.
W: Filtered link traversal with edits for exactly the affected tasks: correct, efficient and tested at the real scale.
X: A=Loop over every task in the Ontology: loads far more objects than needed and is slow and fragile at scale.
C=Manual updates: thousands of clicks and inevitable misses for large projects.
D=First 100 only: leaves most open tasks unchanged; the limit is arbitrary rather than derived from requirements.
T: Edit linked objects by filtering the traversal server-side and returning bounded, tested edits.

@ PLTR-APD D3 T3.4 applied troubleshooting
S: A function that calculates shipping costs returns different results for the same inputs on different runs. The code reads the current exchange rate inside the function. What explains this and what should change?
A: The function is nondeterministic because TypeScript has random behaviour in arithmetic, so it should be rewritten in Python
B: The exchange rate changes between runs; pass it in or record the rate and timestamp used, so results are reproducible
C: The platform caches functions randomly, so results vary; publish a new version to clear the cache
D: Rounding errors always cause different results, so round everything to whole numbers
K: B
G: ## Hidden inputs
The exam guide asks you to test and diagnose function behaviour and record provenance. A value read from a changing source is an input, even if it is not a parameter.
## Change
- Make the rate an explicit input (or snapshot it at the start).
- Return or store the rate and timestamp with the result.
- Tests use fixed rates.
Example: two quotes an hour apart differ because the rate moved; each quote now shows the rate it used.
W: Treat the live rate as an explicit, recorded input: results become reproducible and differences explainable.
X: A=Language randomness: arithmetic is deterministic in both languages; the input changed.
C=Random caching: no such behaviour explains varying arithmetic results.
D=Round to whole numbers: hides the cause and loses precision customers are billed on.
T: Make changing external values explicit inputs and record them with results.

@ PLTR-APD D3 T3.1 applied comparison
S: Which function requirement is the clearest case for AIP Logic rather than TypeScript or Python code?
A: Summing the line items of an invoice and returning the total amount including tax for display in the application
B: Writing a readable explanation of why a claim was flagged, from flag data and notes
C: Checking whether an order date falls on a weekend
D: Sorting a list of suppliers by on-time delivery rate
K: B
G: ## Where language models add value
The exam guide asks you to choose a paradigm by determinism, runtime capabilities and LLM needs.
- Sums, date checks and sorting: deterministic code.
- Readable explanation from structured data and free-text notes: language generation suits AIP Logic.
Example: "Flagged because the claim was filed 3 days after the policy started and the repair estimate exceeds the vehicle value."
W: Generating a readable explanation from mixed data needs language capability, the case where AIP Logic fits.
X: A=Summing line items: arithmetic with one correct answer belongs in code.
C=Weekend check: a deterministic date rule with no interpretation involved.
D=Sorting by rate: an ordering operation that code performs exactly and cheaply.
T: Use AIP Logic for language generation and interpretation; use code for deterministic computation.

@ PLTR-APD D3 T3.3 applied use-case
S: A function used by a Workshop module and an external OSDK app needs a new optional parameter. How should it be introduced without breaking either consumer?
A: Add the parameter as required in place, since both consumers will be updated eventually by their owners
B: Publish a new version with the parameter optional and defaulted, and regenerate the OSDK
C: Create a second function with a different name and maintain both independently forever
D: Change the parameter list in the existing published version without telling the consumers
K: B
G: ## Compatible function changes
The exam guide lists versioning and generated SDK bindings among function concepts.
## Approach
- New version; parameter optional with a default preserving old behaviour.
- Regenerate the OSDK for the external app.
- Consumers adopt the parameter on their schedule.
Example: the module passes the new parameter immediately; the external app keeps working with the default until its next release.
W: An optional, defaulted parameter in a new version: both consumers keep working and can adopt the change independently.
X: A=Required in place: both consumers break until they are updated.
C=Second function forever: two copies of the same logic that must both be fixed and slowly diverge over time.
D=Silent change: consumers break without warning or a version to fall back to.
T: Introduce function parameters as optional with defaults in a new version.

@ PLTR-APD D3 T3.2 applied troubleshooting
S: A function aggregates order totals by region, but the totals are slightly lower than finance's figures. Investigation shows the function counts only the first page of results from a query. What should be fixed?
A: Increase the page size to a very large number so that one page always contains all of the orders for every region
B: Aggregate server-side (or iterate every page) and add a test against a known total
C: Multiply the result by a correction factor that makes it match finance's figures
D: Ask finance to adjust their figures to match the function's output
K: B
G: ## Pagination bugs
The exam guide lists paginating and aggregating among function skills. Reading only the first page silently truncates results.
## Fix
- For totals: server-side aggregation (sum grouped by region).
- If iterating: follow all pages.
- Test: compare with an independent control total.
Example: switching to aggregation returns totals that match finance exactly.
W: Aggregate server-side (or page through everything) and test against a control total: the truncation disappears and is guarded.
X: A=Huge page size: hides the bug until data grows past the new size, and loads more than necessary.
C=Correction factor: a fudge that becomes wrong as data changes.
D=Change finance's figures: the function is wrong, not finance.
T: Never compute totals from a single page; aggregate server-side or iterate all pages.

@ PLTR-APD D3 T3.4 applied use-case
S: Before publishing a function that applies discounts, the team wants tests that will catch mistakes in edge cases. Which test set is most valuable?
A: One test with a typical order and a typical discount, since edge cases rarely happen in real usage
B: Cases for zero-value orders, maximum discounts, missing tiers, expired promotions and rounding
C: Tests that only check whether the function compiles successfully without errors
D: Tests generated by asking the function to test itself
K: B
G: ## Edge-case tests
The exam guide asks you to explain how a function will be tested and to diagnose common failures.
## Cases
- Boundaries: zero, maximum, rounding.
- Missing data: no tier, no promotion.
- Expired or invalid inputs.
Example: a test with a missing tier exposes an exception that would have blocked checkout.
W: Boundary and missing-data cases: the tests target exactly where discount logic tends to fail.
X: A=One typical case: misses the boundaries where pricing errors cost money.
C=Compiles only: a function can compile perfectly and still apply the wrong discount at every boundary.
D=Self-testing: a function cannot meaningfully validate its own logic.
T: Test functions at boundaries and with missing or invalid inputs.

@ PLTR-APD D3 T3.3 applied comparison
S: Which statement about provenance for function-backed Actions is most accurate?
A: Provenance is irrelevant because Actions already record who ran them, so the function's logic version never matters
B: Recording which function version and inputs produced an edit lets auditors reproduce and explain it later
C: Provenance means storing the function's source code inside every edited object as a text property
D: Provenance is only needed for AIP Logic functions, never for TypeScript or Python functions
K: B
G: ## Why provenance matters
The exam guide lists provenance among function concepts. Who ran an Action is not the same as which logic computed the change.
- Record function version and key inputs with consequential edits.
- Reproduce past results with the same version.
Example: an auditor asks why a fee was 45; the record shows feeCalc v12 with 15 days overdue and tier C.
W: Version and inputs recorded with edits: past changes can be explained and reproduced, which actor identity alone cannot do.
X: A=Irrelevant: the actor is known but the logic that computed the value is not.
C=Source code in every object: bloated, unmanageable and still not linked to the published version.
D=AI only: deterministic code changes between versions too, so its results need the same provenance.
T: Record function version and inputs with consequential edits for later explanation.

@ PLTR-APD D3 T3.1 advanced tradeoff
S: A function written in Python by a former data scientist is now maintained by application developers who work only in TypeScript, and it contains simple deterministic logic. It fails occasionally and nobody wants to touch it. What should be considered?
A: Leave it unchanged forever, since rewriting working code is always riskier than maintaining it
B: Rewrite it in TypeScript v2 with equivalence tests, then switch consumers to the new version
C: Convert it to AIP Logic so that the model can handle its occasional failures automatically
D: Delete it and ask consumers to implement the logic themselves
K: B
G: ## Maintainer audience
The exam guide includes maintainability and maintainer audience in paradigm choice. Code nobody can maintain is a risk.
## Approach
- Rewrite in TypeScript v2.
- Equivalence tests against recorded inputs and outputs.
- New version; migrate consumers; retire the old one.
Example: the rewrite reproduces 500 recorded cases exactly and fixes the null handling that caused failures.
W: A tested rewrite in the maintainers' language: the logic stays the same and the team can now own and fix it.
X: A=Leave forever: an unmaintained, failing function remains a growing risk.
C=AIP Logic: turns simple deterministic logic into a nondeterministic model call, adding cost and new failure modes.
D=Consumers reimplement: every consumer writes its own copy, so the same logic is duplicated and diverges.
T: Align function language with the maintainers, rewriting with equivalence tests when needed.
V: Functions
