# PLTR-APD batch 16: Domain 7 round 2 (AIP Logic and AI-Powered Applications), 8 questions

@ PLTR-APD D7 T7.1 applied use-case
S: An application needs AI to extract the due date, amount and vendor from uploaded invoices so a clerk can confirm them before an Action creates the payable. How should the AIP Logic function's output be defined?
A: A free-text paragraph describing the invoice, which the clerk reads and retypes into the Action's form field by field
B: A typed struct (vendor, amount, due date, plus a confidence or evidence field) that pre-fills the Action form for confirmation
C: A single string containing all three values separated by semicolons, which the form splits before display
D: No output at all; the function writes the payable directly to the Ontology without the clerk seeing anything
K: B
G: ## Typed outputs feeding Actions
The exam guide asks you to configure typed inputs and outputs and AI-backed Actions responsibly.
## Design
- Struct output with typed fields and evidence.
- Pre-filled Action form; clerk confirms or corrects.
- Validation in the Action (date format, positive amount).
Example: the clerk sees vendor, amount and date with the source line highlighted and submits in seconds.
W: Typed structured output pre-filling a confirmable Action: fast for the clerk, validated, and still under human control.
X: A=Free-text paragraph: the clerk retypes every field, which defeats the purpose and introduces typos.
C=Semicolon string: fragile parsing that breaks when a vendor name contains the delimiter.
D=Direct write: removes the confirmation step the workflow requires before creating payables.
T: Use typed AIP Logic outputs to pre-fill Actions that a person confirms.
V: AIP Logic, Action types

@ PLTR-APD D7 T7.2 applied use-case
S: An agent embedded in a sales application should answer questions about the selected account's opportunities. Which configuration follows the minimum-capability principle?
A: Give the agent read access to every object type in the Ontology and all Actions so it can answer any question a user might ask
B: Give it the selected account and its opportunities as context, read-only tools scoped to that account, and no write Actions
C: Give it administrator credentials so that permission checks never interrupt the conversation
D: Give it no context and let it answer from the model's general knowledge
K: B
G: ## Minimum data and capability
The exam guide asks you to select the minimum Ontology data and capabilities an AI workflow needs.
## Configuration
- Context: the selected account and its opportunities.
- Tools: read-only, scoped to that account.
- No write Actions; execution as the user.
Example: "which deals close this quarter" is answered from the account's opportunities; nothing else is reachable.
W: Scoped context and read-only tools: the agent can do its job and cannot reach or change anything beyond it.
X: A=Everything readable and writable: a manipulated prompt could read or change unrelated data.
C=Administrator credentials: removes the permission checks that protect data.
D=No context: answers ungrounded in the account's actual data.
T: Give AI features only the context and tools their task requires.
V: AIP Agent Studio

@ PLTR-APD D7 T7.3 applied troubleshooting
S: Users say an AI summary feature in a Workshop module sometimes states facts not present in the case. What should the developer do first?
A: Increase the temperature so that the model explores more phrasing options and finds the correct facts
B: Inspect traces to see whether the facts were in the context, then constrain the prompt and add grounding cases
C: Switch to a larger model immediately, since unsupported statements always come from model size
D: Remove the summaries and show the full case text instead
K: B
G: ## Diagnose grounding with traces
The exam guide asks you to use evaluation, traces and execution history to diagnose poor grounding.
## Steps
- Traces: was the fact in the input? If not, the model invented it.
- Fix: instruction to use only provided content; structured output with evidence.
- Evaluation: grounding cases.
Example: traces show missing linked notes in context; adding them and an evidence field removes the invented details.
W: Trace-based diagnosis followed by targeted fixes and grounding evaluation: the cause is found and the fix is verified.
X: A=Higher temperature: increases variation and makes unsupported statements more likely, not less.
C=Larger model without evidence: may not fix missing context and raises cost.
D=Remove summaries: discards the feature instead of fixing it.
T: Use traces to diagnose ungrounded AI output, then constrain and evaluate.
V: AIP Logic, AIP Observability

@ PLTR-APD D7 T7.4 applied troubleshooting
S: An AI FDE-generated Function passes its tests, but a reviewer notices it writes to an object type that does not exist in the current Ontology schema under that name. What should happen?
A: Publish it anyway, since the platform will create the missing object type automatically on first use
B: Correct the code against the actual schema and generated types, then rerun the tests
C: Rename the existing object type to match the generated code
D: Remove the write so that the Function compiles without it
K: B
G: ## Validate generated code against the schema
The exam guide asks you to review AI FDE-generated Function code and validate schema, platform idioms, provenance and side-effect safety.
## Steps
- Compare names and types with the current schema.
- Use generated bindings so mismatches fail at compile time.
- Rerun tests with real objects on a branch.
Example: the generator used `Customers`; the schema has `Customer`; switching to the binding fixes it.
W: Correct against the real schema and rely on generated types: the mismatch is fixed and similar errors are caught earlier next time.
X: A=Auto-create: object types are not created implicitly by Functions.
C=Rename the object type: changes the Ontology for every consumer to suit one generated file.
D=Remove the write: the code compiles but no longer performs the update it was generated for, so the feature is broken.
T: Check generated Functions against the actual Ontology schema and generated bindings.
V: Functions, AI FDE

@ PLTR-APD D7 T7.1 applied comparison
S: Which design best uses an agent in an application rather than a single AIP Logic function?
A: Extracting the same three fixed fields from each uploaded document in exactly the same way every time it runs
B: A conversational assistant answering varied follow-ups about a case using scoped lookup tools
C: Computing a deterministic risk score from five numeric properties
D: Translating a fixed product description into French for a catalogue field
K: B
G: ## Agents for open-ended interaction
The exam guide lists agents and AI-backed Actions among AI configuration. Agents suit multi-turn, variable requests with tool use; Logic functions suit fixed tasks.
- Fixed extraction, translation: Logic functions.
- Deterministic score: code.
- Varied follow-ups with lookups: an agent.
Example: "what else did this customer report last month?" leads the agent to query related cases.
W: An open-ended, multi-turn assistant with tool lookups: the case where an agent's flexibility is needed.
X: A=Fixed extraction: a single typed Logic function is simpler and more predictable.
C=Deterministic score: five numeric properties combined by a fixed formula belong in code, with no AI involved.
D=Fixed translation: one input and one output per item, which a single Logic call handles without an agent.
T: Use agents for open-ended, multi-turn tasks and Logic functions or code for fixed tasks.
V: AIP Agent Studio, AIP Logic

@ PLTR-APD D7 T7.2 applied troubleshooting
S: A cost report shows an AI feature calls the model on every page load for every user, even when the underlying case has not changed. What should the developer change?
A: Accept the cost, since AI features are inherently expensive and every page load should regenerate the content
B: Store or cache results keyed by case version and regenerate only when the case changes
C: Switch to the most expensive model so fewer calls are needed
D: Remove the feature for all users
K: B
G: ## Avoid redundant AI calls
The exam guide asks you to use traces and execution history to diagnose cost and to choose interactive versus background work sensibly.
## Change
- Cache or store results keyed by case version.
- Regenerate only on change or explicit request.
Example: model calls drop by 85% while users see the same summaries.
W: Cache by case version and regenerate on change: cost falls without changing what users see.
X: A=Accept: most calls produce results identical to the previous ones and waste money.
C=Expensive model: costs more per call and does not reduce the number of calls.
D=Remove for all: discards value instead of fixing the call pattern.
T: Cache AI results by input version and regenerate only when inputs change.
V: AIP Logic, Workshop

@ PLTR-APD D7 T7.3 applied use-case
S: Before releasing an AI-backed Action that proposes refund amounts for agents to confirm, the team wants evidence of quality. What should the evaluation include?
A: A demo with three hand-picked cases shown to stakeholders
B: Representative and edge cases with expected outputs, plus checks that proposals respect policy limits
C: Only the cases where the AI is known to perform well
D: A single overall score obtained by asking the model to rate the quality of its own refund proposals on a scale
K: B
G: ## Evaluating AI-backed Actions
The exam guide asks you to use evaluation to diagnose and verify AI features and to prevent unsafe actions.
## Suite
- Representative and edge cases with expected outputs.
- Assertions: proposals within policy limits.
- Run on each change; track over time.
Example: an edge case with a 90-day-old order reveals proposals ignoring the policy; the prompt and validation are fixed before release.
W: A representative suite with edge cases and limit checks: quality and safety are measured before agents rely on the proposals.
X: A=Hand-picked demo: three chosen cases show what works, not how often it fails or whether limits hold.
C=Known good cases only: excludes exactly the cases where proposals might exceed policy, hiding the risk.
D=Self-rating: the model grading its own proposals measures confidence, not correctness against policy.
T: Evaluate AI-backed Actions on representative and edge cases with policy checks.
V: AIP Evals, Action types

@ PLTR-APD D7 T7.4 advanced use-case
S: AI FDE produced a Function that updates customer tiers and also calls an external marketing API. The team must decide whether it is safe to publish. Which review points are most important for side-effect safety?
A: Whether the generated code follows the team's preferred formatting, naming style and comment conventions throughout
B: Bounded edits, an idempotent external call with safe credentials, and no partial state on failure
C: Whether the Function is shorter than the previous version
D: Whether the Function compiles on the reviewer's laptop
K: B
G: ## Side-effect review
The exam guide asks you to validate side-effect safety in AI FDE-generated code before publishing.
## Review
- Edits: only intended customers; validated.
- External call: idempotency key, timeouts, retries, no secrets in code.
- Failure handling: no partial updates; clear status.
Example: the reviewer moves the external call into an automation with retries and keeps the tier update in a governed Action.
W: Bounded edits, idempotent external calls, safe credentials and clean failure handling: the side effects are safe before anything is published.
X: A=Formatting: style matters little compared with uncontrolled side effects.
C=Shorter: fewer lines say nothing about whether the external call can duplicate or leak credentials.
D=Compiles locally: compilation checks syntax and types, not what the Function changes or calls in production.
T: Review generated Functions for bounded edits, idempotent external calls and failure handling.
V: Functions, AI FDE, Automate
