# PLTR-APD batch 21: Domain 4 round 3 (Workshop Application Development), 8 questions

@ PLTR-APD D4 T4.1 applied use-case
S: A module must let users filter a list of incidents by region, severity and date range, and a chart and a table must both reflect the same filters. How should the filters be wired?
A: Configure separate filters inside the chart and inside the table, and ask users to set them identically each time
B: Define shared filter variables applied to one object set variable that feeds both the chart and the table
C: Duplicate the module into one version per region, with severity and date filters fixed in each copy
D: Let users export the list to a spreadsheet and filter it there before looking at the chart
K: B
G: ## Shared state through variables
The exam guide lists variables and filters among Workshop design skills. One filtered object set feeding several widgets keeps them consistent.
## Design
- Filter widgets write to variables.
- One object set variable combines the filters.
- Chart and table both consume it.
Example: selecting region "North" and severity "High" updates both widgets at once.
W: Shared filter variables feeding one object set: every widget shows the same filtered data without users repeating themselves.
X: A=Separate widget filters: users must set them twice and the views drift apart whenever one is forgotten.
C=One module per region: multiplies maintenance and still cannot combine regions.
D=Export to a spreadsheet: leaves the application and loses the live chart entirely.
T: Drive multiple Workshop widgets from shared filter variables and one object set.
V: Workshop

@ PLTR-APD D4 T4.3 applied troubleshooting
S: A Workshop page with ten widgets loads in 15 seconds. Profiling shows each widget makes its own heavy query for the same base object set, and two function-backed variables run on load although they are only used in a collapsed section. What should be changed?
A: Add a progress bar so users understand why the page takes 15 seconds, without changing the queries
B: Share one base object set across widgets and lazy-load the collapsed section's variables
C: Split the page into ten pages, one per widget, so that each loads separately
D: Ask users to keep the module open all day so they only pay the load time once
K: B
G: ## Remove duplicate work and defer the rest
The exam guide lists variable dependencies, lazy loading and performance refactoring among Workshop skills.
## Refactor
- One base object set variable reused by all widgets.
- Lazy loading for collapsed sections and their functions.
- Measure load time before and after.
Example: load time falls from 15 seconds to 3; the collapsed section takes a second when opened.
W: Reuse the base query and defer hidden work: duplicated and unnecessary computation is removed from page load.
X: A=Progress bar: hides the slowness, which the guide warns against, and fixes nothing.
C=Ten pages: fragments the workflow without removing duplicated queries.
D=Keep it open: shifts the cost to users and fails after every refresh.
T: Share base object sets across widgets and lazy-load hidden sections.
V: Workshop

@ PLTR-APD D4 T4.2 applied use-case
S: A module needs a button that runs an AI summary for the selected case and stores it so colleagues can see it later. How should this be connected?
A: A button that calls the AI function and displays the summary in a text widget only for the current user's session
B: A function-backed Action calling the AI function and storing the summary with author and time
C: Ask users to copy the summary into an email to their colleagues
D: Generate the summary in the user's browser and save it to the user's local disk
K: B
G: ## AI results that others need
The exam guide asks you to connect Workshop to Actions, Functions and AIP capabilities.
## Design
- Function-backed Action: call the AI function, write summary, author, time, version.
- Module shows the stored summary.
- Permissions on the Action and the property.
Example: a colleague opening the case the next day sees the summary with who generated it.
W: A function-backed Action storing the AI output: the summary becomes shared, governed and auditable data.
X: A=Session-only display: the summary disappears when the user leaves, and colleagues never see it.
C=Email: copies scatter outside the platform with no link to the case.
D=Local disk: inaccessible to colleagues and outside governance.
T: Persist AI outputs others need through Actions with provenance.
V: Workshop, Action types, AIP Logic

@ PLTR-APD D4 T4.4 applied comparison
S: Which change to a widely embedded Workshop module is backward compatible?
A: Renaming an existing output variable that parent modules read
B: Adding a new optional input variable whose default preserves current behaviour
C: Removing an input variable that some of the parent modules currently set when they embed the module
D: Changing an output variable from an object to a list of objects
K: B
G: ## Compatibility of module interfaces
The exam guide asks you to preserve module interfaces when making changes.
- Additive optional inputs with defaults: compatible.
- Renames, removals and type changes: breaking for parents that use them.
Example: a new optional `showArchived` input defaults to false; existing parents behave as before.
W: An optional input with a behaviour-preserving default: existing parents are unaffected and can adopt it when they choose.
X: A=Rename an output: parents bound to the old name stop receiving values.
C=Remove an input: parents that set it break or lose behaviour.
D=Change the output type: parents expecting a single object receive a list and fail.
T: Make embedded module changes additive and optional to stay compatible.
V: Workshop

@ PLTR-APD D4 T4.3 applied use-case
S: Users of a module complain that after they submit an Action, the page freezes for 30 seconds while a follow-up calculation runs. What is the best design change?
A: Keep the calculation synchronous and add a message asking users to wait patiently
B: Move the calculation to a background automation and show its status in the module
C: Remove the calculation entirely, even though downstream users rely on its results
D: Ask users to submit the Action only at the end of the day
K: B
G: ## Interactive versus background work
The exam guide's decision table: keep short, predictable work interactive; move long or failure-prone work to a trackable background flow with status.
## Design
- Action completes quickly.
- Automation runs the calculation.
- Module shows "calculating…" then the result.
Example: users continue working immediately; the result appears 30 seconds later.
W: Background execution with visible status: users are not blocked and still see when the result arrives.
X: A=Wait patiently: keeps users frozen; the guide warns against hiding slow work.
C=Remove: downstream users who rely on the calculation's result lose it entirely, which is not a performance fix.
D=End of day: users batch their submissions and wait anyway, while the synchronous design stays unchanged.
T: Move long post-Action work to background flows with visible status.
V: Workshop, Automate

@ PLTR-APD D4 T4.1 applied troubleshooting
S: A section of a module is supposed to appear only when the selected order is "On Hold", but it never appears even for on-hold orders. Other widgets show the order correctly. What should be checked?
A: Whether the browser blocks conditional sections for security reasons on certain devices
B: The visibility condition's variable and its exact compared value (case, code versus label)
C: Whether conditional visibility only works for the first hundred orders in an object set
D: Whether the module must be republished for each order separately
K: B
G: ## Checking conditions
The exam guide asks you to diagnose why the interface is not rendering expected data, including variables and conditional visibility.
## Checks
- Is the condition reading the selected-order variable?
- Does the compared value match stored values ("ON_HOLD" versus "On Hold")?
- Preview with a known on-hold order.
Example: the property stores "ON_HOLD"; the condition compared with "On Hold"; correcting it shows the section.
W: Inspect the condition's variable and comparison value: a mismatch there explains a section that never appears.
X: A=Browser blocking: conditional visibility is evaluated by the module, not blocked by browsers.
C=First hundred orders: no such limit applies to a single selected order.
D=Republish per order: a module is published once and evaluates conditions for whichever order is selected.
T: When conditional content never appears, verify the condition's variable and exact comparison values.
V: Workshop

@ PLTR-APD D4 T4.2 applied tradeoff
S: A module could compute a "days until due" value either with a function-backed variable or by reading a property materialized nightly by a pipeline. The value is displayed and used to sort a list of 20,000 items. Which is better?
A: A function-backed variable recomputed for all 20,000 items on every page load, since it is always exact to the second
B: A nightly-materialized property for sorting, with exact values computed only for a selected item
C: Ask users to compute the value mentally from the due date column
D: Hard-code the value into the module once a month
K: B
G: ## Stored values for sorting at scale
The exam guide asks about performance refactoring and connecting Workshop to Ontology data. Sorting needs a stored, indexed value.
## Reasoning
- 20,000 items sorted by a computed value: materialize it.
- Day precision is enough; nightly refresh fits.
- A function can still show exact detail for one selected item.
Example: the list sorts instantly by the stored value; the detail panel shows exact hours remaining.
W: Materialize for sorting at scale and compute exact detail only where needed: fast lists with sufficient precision.
X: A=Recompute all on load: slow and unnecessary for a day-level value.
C=Mental arithmetic: users would have to compute and compare dates themselves, and the list still could not be sorted.
D=Hard-coded monthly: the value is wrong for most of the month and needs manual maintenance.
T: Materialize values used for sorting large lists; compute exact values per item only when needed.
V: Workshop, Ontology

@ PLTR-APD D4 T4.4 advanced use-case
S: A Workshop application will be used by internal staff and also embedded in a partner-facing portal where partners should see a reduced set of pages and no internal Actions. What deployment approach fits?
A: Embed the same internal module in the partner portal and hide internal pages with CSS so partners cannot see them
B: A partner module reusing shared components, exposing only partner pages and Actions, with data-level permissions
C: Give partners internal accounts so they can use the full internal module
D: Email partners screenshots of the relevant pages each week
K: B
G: ## Channels and audiences
The exam guide asks you to choose deployment channels and secure applications appropriately.
## Approach
- Partner module: only partner pages and Actions.
- Shared components keep logic single-sourced.
- Data-level permissions ensure partners read only partner data whatever the UI.
Example: partners see order status and a "request change" Action; internal approval Actions are absent.
W: An audience-specific module over shared components with data-level controls: partners get what they need, and internal capabilities are not exposed.
X: A=CSS hiding: the pages and Actions remain reachable; hiding is not access control.
C=Internal accounts: partners would see internal data and Actions, a serious over-permissioning of an external audience.
D=Screenshots: weekly static images are out of date immediately and are shared outside any access control.
T: Serve different audiences with dedicated modules over shared components and data-level permissions.
V: Workshop, permissions
