# PLTR-APD batch 37: Domain 4 round 5 (Workshop Application Development), 8 questions

@ PLTR-APD D4 T4.1 applied use-case
S: A module must let a dispatcher pick a date, see the drivers available that day, and assign one to a route. Which Workshop design fits?
A: A text box where dispatchers type a date and a driver name, then submit an email to the operations team for manual assignment
B: A date picker writing a date variable, a filtered driver list using it, and an Assign Action taking the selected driver and route
C: A static list of all drivers regardless of date, with dispatchers checking availability in a separate calendar application
D: Three separate modules for date selection, driver lists and assignments, with dispatchers copying values between them
K: B
G: ## Variable-driven workflow
The exam guide lists widgets, variables and events among Workshop building blocks.
## Design
- Date picker → date variable.
- Driver list filtered by availability on that date.
- Assign Action with driver and route parameters.
Example: choosing 20 Oct shows six available drivers; assigning one updates the route.
W: Widgets connected through variables into an Action: the dispatcher sees the right drivers and assigns in one place.
X: A=Typed values and email: no validation and a slow manual assignment step outside the platform.
C=Static list with a separate calendar: dispatchers must cross-check availability by hand and will make mistakes.
D=Three modules: dispatchers copy values between screens, which is slow and error-prone.
T: Build Workshop workflows by chaining widgets through variables into Actions.
V: Workshop, Action types

@ PLTR-APD D4 T4.3 applied troubleshooting
S: A module's chart flickers and recomputes several times when a user changes one filter, because three variables depending on that filter update one after another and each triggers the chart. What should be changed?
A: Ask users to change filters slowly so that the chart has time to settle between updates
B: Make the chart depend on one combined variable that updates once per filter change
C: Remove the chart from the module
D: Add a delay of five seconds before the chart loads
K: B
G: ## Consolidate dependencies
The exam guide asks you to understand variable dependencies and asynchronous event behaviour.
## Fix
- Combine intermediate variables into one object set or derived variable.
- The chart depends on that single variable.
Example: changing the filter now recomputes the chart once.
W: One combined dependency: a filter change triggers a single recomputation, removing flicker and wasted work.
X: A=Change filters slowly: asks users to work around a dependency design problem that the developer can fix.
C=Remove the chart: users lose information they need in order to hide a fixable recomputation problem.
D=Fixed delay: makes every interaction five seconds slower and may still flicker if updates take longer.
T: Consolidate Workshop variable dependencies so one change triggers one recomputation.
V: Workshop

@ PLTR-APD D4 T4.2 applied comparison
S: Which way of displaying an AI-generated answer in Workshop best supports users verifying it?
A: Show the answer as plain text with no indication of its sources or how it was produced
B: Show the answer with citations linking to the objects it used
C: Show only a confidence percentage and hide the answer itself
D: Show the answer in a pop-up that closes automatically after five seconds
K: B
G: ## Verifiable AI in applications
The exam guide asks you to connect Workshop to AIP capabilities and to diagnose poor grounding.
- Citations to objects or documents used.
- Links to open them.
Example: "Delivery delayed due to port closure (see Shipment S-4, Incident I-9)" with clickable links.
W: Answers with citations and links: users can verify claims against the source objects before acting on them.
X: A=Plain text: users cannot tell grounded claims from invented ones.
C=Confidence only: a percentage without the answer gives users nothing to act on or verify.
D=Disappearing pop-up: users cannot read or verify it properly.
T: Display AI outputs with citations to the objects they used.
V: Workshop, AIP Logic

@ PLTR-APD D4 T4.4 applied use-case
S: An embedded module currently takes a single "order" input. A new parent module needs to pass a list of orders instead. Three existing parents pass one order. What is the compatible change?
A: Change the existing input from a single order to a list of orders, so that all four parents must now pass lists
B: Add a new optional list input while keeping the single-order input, handling either in the module
C: Remove the input entirely and have the module query all orders itself
D: Create a copy of the module for the new parent and maintain both separately forever
K: B
G: ## Additive interface changes
The exam guide asks you to preserve module interfaces when making changes.
## Change
- New optional `orders` list input.
- Existing `order` input unchanged.
- Module handles whichever is provided.
Example: the three existing parents keep working; the new parent passes a list.
W: An additive optional input: existing parents are untouched and the new one gets what it needs.
X: A=Change the input type: the three existing parents pass a single order and break as soon as the module expects a list.
C=Remove the input: the module loses the context its parents provide, and the existing embeddings stop working.
D=Copy the module: every future fix must be made twice and the two copies drift apart.
T: Extend embedded module interfaces additively with optional inputs.
V: Workshop

@ PLTR-APD D4 T4.3 applied use-case
S: A module's main page shows an aggregate chart computed from 10 million objects on every load. The numbers only change nightly. How should it be optimized?
A: Recompute the aggregate live on every page load, since live computation is always the most accurate choice
B: Materialize the aggregate nightly (a property or small dataset) and have the chart read the stored result
C: Remove the chart and show a table of all 10 million objects instead
D: Ask users to open the page less often
K: B
G: ## Precompute what changes rarely
The exam guide covers performance refactoring and connecting Workshop to Ontology data. When the underlying numbers only change once a night, recomputing them from 10 million objects on every page load repeats identical work.
## Change
- Nightly materialized aggregate (a property or a small dataset).
- Chart reads the stored values.
- Freshness shown on the page.
Example: page load drops from 12 seconds to 1.
W: Precomputed nightly aggregates: the chart shows exactly the same numbers instantly.
X: A=Live every load: repeats the same expensive computation thousands of times a day.
C=Table of 10 million: slower than the chart and useless for spotting the trends the chart shows.
D=Open less often: shifts the cost onto users while the page stays just as slow when they do open it.
T: Materialize aggregates that change rarely instead of recomputing them on load.
V: Workshop, Ontology

@ PLTR-APD D4 T4.1 applied troubleshooting
S: A button in a module should open a form pre-filled with the selected object's values, but the form opens empty. Selection works elsewhere in the module. What should the developer check?
A: Whether the form is too large for the screen to show the values
B: Whether the Action's parameters use the selected-object variable as defaults
C: Whether users are clicking the button too quickly after selecting an object, before the selection has registered
D: Whether forms can ever be pre-filled in Workshop
K: B
G: ## Parameter defaults
The exam guide asks you to connect Workshop to Actions and diagnose rendering issues.
## Check
- Action button configuration: parameter defaults bound to the selected object variable.
- Correct property mapping.
Example: the "customer" parameter was mapped to nothing; binding it to the selection pre-fills the form.
W: Map the Action's parameters to the selection variable: the form opens pre-filled with the chosen object.
X: A=Screen size: the form is empty because no values were passed in, not because they are hidden by the layout.
C=Clicking quickly: selection is already set before the click.
D=Cannot pre-fill: forms routinely take defaults from variables.
T: Bind Action parameters to selection variables to pre-fill forms.
V: Workshop, Action types

@ PLTR-APD D4 T4.2 applied tradeoff
S: A team wants their Workshop module to call an external weather API directly from the page to show conditions at each site. What is the better design?
A: Call the API from the page for every site on every load, with the API key embedded in the module's configuration visible to users
B: Ingest or fetch weather data on the platform side (a sync or a function with stored credentials) and show it from the Ontology
C: Ask users to open a weather website in another tab
D: Hard-code typical weather values for each site
K: B
G: ## Platform-side integration
The exam guide asks you to connect Workshop to data and functions, and to avoid exposing secrets.
## Design
- Weather data fetched by a sync or function with server-side credentials.
- Stored or computed per site; displayed in the module.
Example: site cards show current conditions refreshed every 15 minutes.
W: Fetch on the platform side with protected credentials: the module shows weather without exposing keys or hammering the API.
X: A=Direct calls with an exposed key: leaks credentials and multiplies calls per user.
C=Another tab: users switch away from the module and must match sites to weather by hand.
D=Hard-coded values: typical weather is not current weather, so the information would be wrong most of the time.
T: Integrate external data on the platform side, not from the page with exposed credentials.
V: Workshop, Functions

@ PLTR-APD D4 T4.4 advanced tradeoff
S: A module is used by both a central team and regional teams. Regional teams want simplified pages, while the central team needs everything. The developer considers building one module with many conditional sections versus separate modules. What should guide the decision?
A: Always build one module with conditional sections for every possible audience, regardless of complexity
B: One module if differences are small; audience-specific modules over shared components if not
C: Build a separate module for every individual user
D: Give regional teams the central module and ask them to ignore what they do not need
K: B
G: ## Choosing structure by divergence
The exam guide asks you to design layouts for user workflows and choose deployment channels.
## Reasoning
- Small differences: conditional visibility in one module.
- Large differences: separate modules sharing Actions, Functions and embedded components.
Example: regional teams get a three-page module; the central team keeps a ten-page module; both use the same Actions.
W: Match structure to how much the audiences diverge: simplicity for regional users without duplicating the logic behind both modules.
X: A=One module always: becomes unmanageable when audiences diverge.
C=Module per user: hundreds of near-identical modules that nobody could keep consistent or fix.
D=Ignore what you do not need: regional users face cluttered pages and make mistakes using controls meant for others.
T: Choose between conditional sections and separate modules based on audience divergence.
V: Workshop
