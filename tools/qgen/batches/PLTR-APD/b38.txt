# PLTR-APD batch 38: Domain 5 round 5 (OSDK, APIs, and External Applications), 8 questions

@ PLTR-APD D5 T5.3 applied use-case
S: An external field app must let technicians close work orders while offline, syncing when connectivity returns. Closing a work order is an Action with validation. How should the sync be designed?
A: Write directly to the backing dataset when the device reconnects, bypassing the Action so that offline changes always apply without validation
B: Queue the intended Action calls locally and invoke them via the OSDK on reconnection, handling validation failures and conflicts per call
C: Ask technicians to note closures on paper and have an office clerk enter them into Workshop at the end of each day
D: Disable closing work orders entirely unless the technician has a connection at that exact moment
K: B
G: ## Offline queues that respect Actions
The exam guide lists invoking Actions via the OSDK and handling failures in external apps.
## Design
- Local queue of intended Action calls with parameters and timestamps.
- On reconnect: invoke each via the OSDK; idempotency keys for retries.
- Show validation failures and conflicts (for example, already closed by someone else) to the technician.
Example: three closures made offline sync at 16:05; one is rejected because the order was reassigned, and the technician sees why.
W: Queued Action calls replayed through the OSDK with conflict handling: offline work is preserved and still passes validation and permissions.
X: A=Write to the dataset: bypasses validation, permissions and audit, and can overwrite changes others made meanwhile.
C=Paper and a clerk: duplicate effort, delays and transcription errors.
D=Online-only closures: blocks field work in exactly the places where connectivity is poor.
T: Replay offline changes as Action calls through the OSDK, handling validation and conflicts.
V: OSDK, Action types

@ PLTR-APD D5 T5.1 applied troubleshooting
S: A developer registered an external app and generated the OSDK, but every call fails with a scope error, even for simple reads of an object type the developer can view in Foundry. What was likely missed?
A: The developer's own account must be granted administrator rights on the platform before any OSDK call can succeed
B: The object type was not added to the app's scopes before generating the OSDK; add it and regenerate
C: The OSDK only works after the app has been in use for a week, so the developer should wait
D: External apps can never read object types that are visible in Foundry
K: B
G: ## Scopes before generation
The exam guide covers scoping Ontology resources and generating the OSDK, and lists scope errors among diagnostics.
## Fix
- Add the needed object types and Actions to the app's scopes.
- Regenerate the OSDK.
- Test the call again.
Example: adding `Product` to the scopes and regenerating makes the read succeed.
W: Missing scope: the app can only reach resources it is scoped to, whatever the developer can see in Foundry.
X: A=Administrator rights: the issue is the app's scope, and administrator rights would be over-permissioning.
C=Wait a week: there is no waiting period for OSDK access; the app lacks the scope and will keep failing until it is added.
D=Never readable: external apps read scoped object types routinely.
T: Add needed resources to an app's scopes before generating the OSDK.
V: OSDK, Developer Console

@ PLTR-APD D5 T5.2 applied comparison
S: An internal scheduling tool runs a background job every 15 minutes to sync calendar data, and has a page where staff see their own schedules. Which authentication setup is correct?
A: User-based authentication for the background job, requiring one staff member to stay signed in permanently
B: Service-based auth with narrow scope for the background job, and user-based auth for the schedule page
C: A single service identity for both, so staff see every schedule in the organization
D: No authentication for the page, since it is internal
K: B
G: ## Different actors, different identities
The exam guide asks you to choose user-based or service-based authentication appropriately.
- Background job: no user present; service identity with minimal scope.
- Schedule page: each staff member sees only their own data.
Example: the job writes calendar entries; each employee sees only their schedule.
W: Service identity for headless sync and user identity for the page: each actor has appropriate access and audit.
X: A=User-based background job: fails whenever that person signs out or leaves.
C=One service identity: every staff member would see everyone's schedules through the service's broad access.
D=No authentication: being on an internal network is not authorization, and nothing would restrict whose schedule is shown.
T: Use service identities for background jobs and user identities for interactive pages.
V: OSDK

@ PLTR-APD D5 T5.4 applied troubleshooting
S: An external dashboard shows correct data in development but empty results in production for the same user. Development and production apps are registered separately. What should be compared first?
A: The color scheme of the two dashboards, since different themes can hide results
B: The two registrations' scopes, enabled resources and target environments
C: The size of the users' screens in each environment
D: Whether production databases are always empty for external apps
K: B
G: ## Environment configuration
The exam guide lists deployment issues and scope intersections among OSDK diagnostics.
## Compare
- Scopes and enabled object types per registration.
- Target environment and resource identifiers.
- The user's access in each environment.
Example: the production registration lacked the `Shipment` scope; adding it fixes the dashboard.
W: Compare registrations and targets between environments: separate registrations often differ in scope or configuration.
X: A=Color scheme: a visual theme cannot change which data the API returns; empty results come from configuration or access.
C=Screen size: display size does not remove rows from an API response; the same user sees data in development.
D=Production always empty: there is no rule that external apps receive no data in production; something differs in setup.
T: When behaviour differs across environments, compare app registrations, scopes and targets.
V: OSDK, Developer Console

@ PLTR-APD D5 T5.3 applied use-case
S: An external app must create a support ticket and attach the customer link in one operation, so that tickets are never created without a customer. How should it be implemented?
A: Create the ticket with one API call and set the customer link with a second call afterwards, accepting occasional orphan tickets
B: Invoke a single Action via the OSDK that creates the ticket with the customer link as a required parameter
C: Write the ticket directly to a dataset with a customer column, bypassing the Ontology
D: Create tickets without customers and ask agents to fix links manually
K: B
G: ## One governed operation
The exam guide lists invoking Actions via the OSDK and reasoning about atomicity.
- An Action with the customer as a required parameter creates the ticket and link together.
- Validation ensures the customer exists.
Example: a failed customer lookup rejects the request; no orphan ticket is created.
W: A single Action with a required customer parameter: the ticket and its link are created together or not at all.
X: A=Two calls: a failure or timeout between them leaves tickets without customers, which the requirement forbids.
C=Direct dataset write: bypasses validation, permissions and audit.
D=Manual fixes: agents repair links after the fact, creating extra work and leaving data inconsistent in the meantime.
T: Use a single OSDK Action call for operations that must succeed together.
V: OSDK, Action types

@ PLTR-APD D5 T5.4 applied use-case
S: A team wants early warning when their external app starts failing due to OSDK or API issues (expired credentials, scope errors, rate limits). What should they implement?
A: Wait for users to email the support team whenever something seems to go wrong when they are using the external app
B: Log errors by type, monitor error and token refresh rates, and alert the owners
C: Restart the app server every hour to prevent errors
D: Suppress all errors in the app so users never see them
K: B
G: ## Observability for external apps
The exam guide lists diagnosing scope, authentication, stale SDK, rate limits and deployment issues.
## Implementation
- Categorize errors: auth, scope, validation, rate limit, transient.
- Metrics and alerts per category.
- Runbooks for each.
Example: a spike in auth errors after a credential rotation pages the team within minutes.
W: Categorized error monitoring with alerts: problems are detected and classified before users report them.
X: A=Wait for emails: many users never report problems, and those who do report them late and without detail.
C=Hourly restarts: do not fix auth, scope or rate-limit problems.
D=Suppress errors: users cannot tell that requests failed and the team never learns that anything is wrong.
T: Monitor external apps' API errors by category and alert owners.
V: OSDK

@ PLTR-APD D5 T5.1 applied use-case
S: An external partner portal needs read access to Product and Order objects and the ability to create Return Requests. The team wants to follow least privilege. How should scopes be set?
A: Request every object type and Action in the Ontology so the portal never needs another registration change
B: Scope reads to Product and Order and the Create Return Request Action only
C: Give the portal administrator access because partners are trusted
D: Leave scopes empty and rely on partners' own permissions to restrict access
K: B
G: ## Least-privilege scopes
The exam guide covers scoping Ontology resources for applications.
## Scopes
- Read: Product, Order.
- Action: Create Return Request.
- Review on each feature change.
Example: a later feature to cancel returns adds exactly one Action to the scope after review.
W: Scopes limited to what the portal uses: a compromise or bug cannot reach other object types or Actions.
X: A=Everything: grants the portal access to every object type and Action for convenience, widening any compromise.
C=Administrator access: trusting partners is not a control, and administrator access is the opposite of least privilege.
D=Empty scopes: the app could not function, and scopes are a required layer.
T: Scope OSDK applications to exactly the object types and Actions they use.
V: OSDK, Developer Console

@ PLTR-APD D5 T5.2 advanced troubleshooting
S: Audit logs show that all changes made through an internal OSDK app appear under one service identity, so the team cannot tell which employee made which change. Compliance requires individual attribution. What should change?
A: Add a free-text "changed by" field to every Action that users fill in themselves
B: Switch to user-based OAuth so each employee's calls run under their own identity
C: Keep the service identity and ask employees to email the team after each change
D: Disable audit logs since they do not provide useful information
K: B
G: ## Attribution through identity
The exam guide asks you to choose user-based or service-based authentication and separate user permissions from service identities.
## Change
- User-based OAuth for the interactive app.
- Actions run as the signed-in employee.
- Service identity kept only for background tasks.
Example: the audit log now shows each change with the employee who made it.
W: User-based authentication attributes every change to the employee who made it, which is what compliance requires.
X: A=Self-reported field: users can leave it blank or type someone else's name, so it is not reliable attribution.
C=Emails: unreliable and stored apart from the changes, so they cannot prove who made a specific change.
D=Disable audit: removes the very records compliance depends on, making the problem worse rather than better.
T: Use user-based authentication when actions must be attributed to individuals.
V: OSDK, Action types
