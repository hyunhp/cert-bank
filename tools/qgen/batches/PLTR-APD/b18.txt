# PLTR-APD batch 18: Domain 1 round 3 (Ontology Schema Design and Workflow Assembly), 8 questions

@ PLTR-APD D1 T1.2 applied troubleshooting
S: A Facility object type is keyed on the facility's street address. When a facility's address was corrected in the source, its maintenance history and user comments disappeared from the application. What is the cause and the fix?
A: The application's cache kept the old address, so users should clear their browsers and the history will reappear for that facility
B: The key changed with the address, creating a new object; switch to a stable facility id and migrate edits and links
C: The maintenance history was deleted by the correction in the source, so it must be re-entered manually by the technicians
D: Address corrections are not supported by the Ontology, so the source team should stop correcting addresses
K: B
G: ## Stable identity
The exam guide asks you to select stable identity. An address is a mutable attribute; using it as a key ties identity to something that changes.
## Fix
- Key on the facility id from the system of record.
- Migrate existing edits and links from address-keyed objects.
- Keep the address as an ordinary, editable property.
Example: after the migration, correcting an address updates a property and the history stays attached.
W: A mutable attribute used as the key re-identified the facility: a stable id restores continuity and prevents the next correction from detaching history.
X: A=Browser cache: the object really has a new key on the server; clearing caches cannot reattach edits to a different identity.
C=History deleted at source: the history lives on the old object in the Ontology; it was detached, not deleted, and can be migrated.
D=Stop correcting addresses: the business must be able to fix data; the modelling choice is what needs to change.
T: Never key objects on mutable attributes such as addresses or names.
V: Ontology Manager

@ PLTR-APD D1 T1.1 applied use-case
S: An insurance application models Policies, and each policy can have many Coverages of different types with different properties (auto coverage has vehicle fields, home coverage has property fields). How should coverages be modelled?
A: One Coverage object type with every possible field for every coverage kind, most of them empty for any given coverage
B: Separate object types per coverage kind implementing a common Coverage interface, each linked to its Policy
C: Coverage details stored as one long JSON text property on the Policy object, parsed by each application
D: One object type per policy, with coverage fields added as new properties each time a policy adds a coverage
K: B
G: ## Interfaces for related but different types
The exam guide lists interfaces and object types among modelling constructs. Coverages share a shape (premium, limit, policy link) but differ in specifics.
## Model
- Interface `Coverage`: premium, limit, start, end.
- AutoCoverage and HomeCoverage implement it with their own properties.
- Links: each coverage → Policy.
Example: a policy page lists all coverages through the interface and shows type-specific details when one is opened.
W: Type-specific object types sharing an interface: each kind keeps its own properties, and applications can still treat all coverages uniformly.
X: A=One wide type: sparse, hard to validate and grows with every new coverage kind.
C=JSON on Policy: unqueryable, unvalidated and unlinkable from applications and Actions.
D=Properties per policy: changes the schema for every policy and makes the model unstable.
T: Use interfaces over type-specific object types when related entities share a shape but differ in detail.
V: Ontology Manager

@ PLTR-APD D1 T1.3 applied tradeoff
S: A team designs a returns workflow. One proposal puts all logic (eligibility, refund calculation, warehouse notification, customer email) into a single Workshop button script. Another separates them into components. Which design is better and why?
A: The single button script, since one place for all logic is easier to read than several components working together
B: Separate components: a Function for eligibility and refund, an Action for the return, and automations for notifications
C: Put everything into an AIP Logic prompt so that the model handles eligibility, calculation and notifications flexibly
D: Skip automation and ask the warehouse to check a list of returns every afternoon
K: B
G: ## Each component for its job
The exam guide's decision table: Functions for reusable logic, Actions for governed state changes, Automate for triggers and orchestration, integrations for external systems.
## Design
- Function: eligibility and refund amount, reusable and testable.
- Action: create the return with validation and audit.
- Automations: notify the warehouse and email the customer, retry-safe.
Example: the same eligibility Function is reused by the customer portal and the agent module.
W: Functions, Actions and automations each doing their part: logic is reusable and tested, changes are governed and follow-ups are reliable.
X: A=One button script: untestable, not reusable and bypasses Action validation and audit.
C=Everything in a prompt: nondeterministic calculations and notifications for rules that have exact answers.
D=Manual afternoon check: every return waits for the warehouse's daily look at a list, which depends on someone remembering to do it.
T: Separate reusable logic, governed changes and follow-up orchestration into Functions, Actions and automations.
V: Functions, Action types, Automate

@ PLTR-APD D1 T1.4 applied use-case
S: An auditor asks which applications and automations can change Contract objects, and which Actions they use. What is the most efficient way to answer?
A: Interview every application owner and compile their answers into a spreadsheet over several weeks
B: Use Workflow Lineage on Contract to list its Actions and the modules and automations using them
C: Search the codebase for the word "contract" and assume every match changes Contract objects
D: Tell the auditor that this information cannot be determined
K: B
G: ## Lineage for governance questions
The exam guide lists Workflow Lineage for understanding impact and troubleshooting access. The same view answers "what can change this object type?"
## Steps
- Open Contract in Workflow Lineage.
- List Actions that edit it and the modules, Functions and automations that call them.
- Export or document for the auditor; add owners.
Example: lineage shows three Actions used by two modules and one automation.
W: Workflow Lineage maps the Actions and their callers directly: the auditor gets an accurate answer from the platform's own record.
X: A=Interviews: slow, incomplete and dependent on owners remembering every path.
C=Text search: matches comments and reads, and misses configuration that is not in code.
D=Cannot be determined: the platform records these dependencies.
T: Answer "what changes this object type?" with Workflow Lineage.
V: Workflow Lineage

@ PLTR-APD D1 T1.2 applied comparison
S: Which link cardinality correctly models "each Ticket is assigned to at most one Agent at a time, and an Agent handles many Tickets"?
A: Many-to-many between Ticket and Agent, since agents and tickets are both numerous
B: Many-to-one from Ticket to Agent, backed by an agent id on the ticket
C: One-to-one between Ticket and Agent, since a ticket has exactly one agent
D: No link; store the agent's name as text on the ticket
K: B
G: ## Reading the relationship
The exam guide asks you to choose appropriate cardinality. "At most one agent per ticket, many tickets per agent" is many-to-one from Ticket to Agent.
- Backing: `agent_id` on the ticket (nullable for unassigned).
- Traversal: agent → tickets; ticket → agent.
Example: agent A-7 has 34 open tickets; ticket T-90 has one agent.
W: Many-to-one from Ticket to Agent: exactly the stated relationship, with a nullable foreign key for unassigned tickets.
X: A=Many-to-many: would allow a ticket to have several agents at once, contradicting the rule.
C=One-to-one: would limit each agent to a single ticket, which contradicts agents handling many tickets at once.
D=Name as text: no link to the Agent object, so traversal and permissions on agents are lost.
T: Translate business rules into cardinality carefully: "many of these to one of those" is many-to-one.
V: Ontology Manager

@ PLTR-APD D1 T1.3 applied use-case
S: A hospital wants an application where nurses record vital signs, and a doctor is alerted when readings cross thresholds. Nurses work on tablets; doctors receive alerts on their phones. Which assembly fits?
A: A spreadsheet that nurses update and doctors check every hour on their phones
B: A tablet Record Vitals Action, a threshold automation, and a notification to the doctor
C: An AI agent that reads all vitals continuously and decides on its own whether to call a doctor
D: A single desktop module that nurses must walk to a workstation to use
K: B
G: ## Workflow assembly across devices
The exam guide asks you to assemble workflows across Workshop, Actions and Automate and choose deployment channels for the user.
## Assembly
- Tablet module: Record Vitals Action with validation (plausible ranges).
- Automation: condition on thresholds; notify the responsible doctor.
- Audit of readings and alerts.
Example: a reading of 39.8 °C triggers a notification to the attending doctor within a minute.
W: A tablet-friendly Action, a threshold automation and notifications: each user works on the right device and alerts are deterministic and auditable.
X: A=Spreadsheet checked hourly: alerts could be an hour late and nothing is validated.
C=Autonomous AI agent: thresholds are explicit rules; an AI deciding alone adds unpredictability to a clinical alert.
D=Desktop only: nurses lose time walking to workstations and readings are recorded late.
T: Assemble device-appropriate modules, validated Actions and rule-based automations for operational alerts.
V: Workshop, Action types, Automate

@ PLTR-APD D1 T1.1 applied troubleshooting
S: Two teams created separate "Customer" object types for their applications. Reports now disagree on customer counts, and links from Orders point to one type or the other. What should be done?
A: Keep both object types and ask report authors to sum them, accepting some double counting
B: Consolidate on one Customer type with a stable key and migrate links, edits and apps
C: Delete one team's object type immediately, regardless of the applications that depend on it
D: Rename one type to "Customer2" so that the two are easier to tell apart
K: B
G: ## One entity, one object type
The exam guide asks you to model meaningful objects and plan changes without breaking live consumers. Duplicate types for one entity cause divergence.
## Plan
- Choose or create the canonical Customer type with a stable key.
- Map both sources; migrate links and edits.
- Update applications on a branch; retire the duplicate.
Example: both teams' modules now use one Customer type; counts agree.
W: Consolidate on one type with a planned migration: reports agree and links point to one identity.
X: A=Sum with double counting: customers present in both types are counted twice, so every report stays wrong by design.
C=Immediate deletion: breaks the dependent applications and loses edits.
D=Rename: makes the two types easier to tell apart but leaves the duplicated identity and disagreeing reports in place.
T: Consolidate duplicate object types for one entity through a planned migration.
V: Ontology Manager, Workflow Lineage

@ PLTR-APD D1 T1.4 advanced tradeoff
S: A property used by eight applications must change its meaning (from "estimated cost" to "approved cost"). Some applications need the old meaning for six more months. What is the safest approach?
A: Change the meaning in place and send an email asking the eight application owners to adapt their applications
B: Add a new property for the new meaning, keep the old one during transition, migrate apps via lineage, retire the old later
C: Keep the property and its name but change the pipeline that fills it, so that applications receive the new meaning silently
D: Freeze the property forever and create no new properties, so that no application ever has to change
K: B
G: ## Semantic changes need a transition
The exam guide's practice scenario: for a breaking property change affecting multiple applications, inspect consumers and lineage, introduce a compatible transition or versioned contract, and migrate deliberately.
## Plan
- New property `approved_cost`; old `estimated_cost` kept and documented as deprecated.
- Lineage: list the eight consumers; migrate one by one.
- Retire the old property after the last consumer moves.
Example: five apps migrate in month one; the last moves in month six.
W: A new property alongside the old with a planned migration: no application silently receives a different meaning.
X: A=Change in place: every app instantly shows the wrong meaning, some for months.
C=Silent pipeline change: the most dangerous option; the same name now means something else.
D=Freeze forever: the business genuinely needs the new meaning; refusing all change only pushes teams into workarounds.
T: Introduce semantic changes as new properties and migrate consumers deliberately.
V: Workflow Lineage, Ontology Manager
