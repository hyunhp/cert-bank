# PLTR-APD batch 35: Domain 2 round 5 (Action Types and Write-Back Patterns), 8 questions

@ PLTR-APD D2 T2.2 applied use-case
S: A Transfer Asset Action moves an asset between sites. The business requires the destination site to have capacity, the asset not to be under maintenance, and a reason to be recorded. How should the Action be configured?
A: A simple form with no checks, followed by a weekly review where supervisors reverse any transfers that broke the rules
B: A required reason, valid destination sites only, and criteria checking capacity and maintenance
C: A note on the form asking users to check capacity and maintenance status in another application before submitting
D: Remove the transfer Action and let users change the asset's site property directly in a table
K: B
G: ## Parameters, validation and criteria
The exam guide lists parameters, validation, submission criteria and forms among Action configuration.
## Configuration
- Required reason parameter.
- Destination: dropdown of valid sites.
- Criteria: destination capacity available; asset not under maintenance.
Example: transferring an asset under maintenance shows "Asset is under maintenance until 18 Oct."
W: Required parameters, constrained choices and execution-time criteria: invalid transfers are refused and every valid one carries its reason.
X: A=Weekly reversal: invalid transfers take effect and may cause real logistics problems before anyone reviews them.
C=Note to check elsewhere: users skip it under time pressure, and nothing stops a rule-breaking transfer.
D=Direct table edits: bypass validation, reasons and audit entirely.
T: Configure Actions with required parameters, constrained inputs and execution-time criteria.
V: Action types

@ PLTR-APD D2 T2.1 applied tradeoff
S: An Action currently recalculates a customer's total balance by loading all their invoices whenever any invoice is paid. For large customers it times out. What should change?
A: Keep loading all invoices but raise the Action's timeout so that large customers eventually finish
B: Update the balance incrementally or aggregate server-side instead of loading every invoice
C: Remove the balance property and ask users to sum invoices in a spreadsheet when they need it
D: Run the Action only for small customers and skip large ones
K: B
G: ## Efficient logic in function-backed Actions
The exam guide asks you to query and aggregate safely in functions behind Actions.
## Change
- Incremental update by the paid amount (with care for concurrency), or
- Server-side sum of open invoices.
- Periodic reconciliation to catch drift.
Example: paying an invoice updates the balance in milliseconds for a customer with 30,000 invoices.
W: Incremental updates or server-side aggregation: the Action's cost no longer grows with the customer's invoice history.
X: A=Raise the timeout: the work still grows with every invoice and eventually exceeds any limit again.
C=Spreadsheet sums: removes a property users rely on and moves work outside the platform.
D=Skip large customers: their balances become wrong, which is unacceptable for the largest accounts.
T: Avoid loading large histories in Actions; update incrementally or aggregate server-side.
V: Action types, Functions

@ PLTR-APD D2 T2.3 applied troubleshooting
S: A service-desk team can run the Reset Password Request Action for most users, but it fails for executives with a permission error. The Action has not changed. What is the most likely reason?
A: Executives' accounts are older, and the Action does not support older accounts in the platform
B: Executive records carry an extra marking or policy the team lacks
C: The service desk needs to run the Action twice for executives
D: The Action is broken and must be rebuilt from scratch
K: B
G: ## Object-level controls
The exam guide asks you to understand independent security layers for Action execution.
## Diagnosis
- Compare markings or policies on executive objects with others.
- Confirm the team's membership.
- Decide with owners whether the team should handle executives or route them elsewhere.
Example: executive records carry an "Exec Protected" marking; requests are routed to a privileged support group.
W: An object-level control on executive records: the Action is fine, but the team cannot edit those specific objects.
X: A=Account age: has no bearing on Action permissions; the pattern follows a group of protected objects.
C=Run twice: permission denials are deterministic and repeat every time.
D=Rebuild: the Action works for all other users, so it is not broken.
T: When an Action fails only for certain objects, look for object-level markings or policies.
V: Action types, markings

@ PLTR-APD D2 T2.4 applied use-case
S: A developer wants to confirm that a revised Action handles two users editing the same object at nearly the same time. What should the test plan include?
A: A single test by one user on one object, since concurrency problems are very rare in practice
B: A branch test with two submissions on the same object, checking validation and final state
C: Skipping concurrency testing and relying on users to coordinate with each other by chat
D: Testing only with administrator accounts, since they bypass concurrency issues
K: B
G: ## Testing concurrency
The exam guide lists concurrency among Action testing concerns.
## Plan
- Two near-simultaneous submissions on the same object.
- Expected: one succeeds and the other fails validation or sees updated state.
- Check the final object state.
Example: two dispatchers assign the same truck; the second sees "Truck already assigned".
W: A deliberate concurrency test checking validation and final state: the Action's behaviour under races is verified before users meet it.
X: A=Single test: cannot reveal race conditions between two users.
C=Chat coordination: users will not always coordinate, so conflicting submissions will happen without any test of the outcome.
D=Administrator tests: administrators hit the same race between two submissions, so the test would prove nothing special.
T: Include concurrency tests on the same object when testing Actions.
V: Action types, branches

@ PLTR-APD D2 T2.2 applied comparison
S: Which rule belongs in an Action's submission criteria rather than only in the form's input constraints?
A: The comment field must be at most 1,000 characters long
B: The asset must still be available when the Action actually runs
C: The date picker should start on the current month
D: The priority dropdown in the form should list its values in order from the lowest priority to the highest
K: B
G: ## Execution-time state checks
The exam guide asks you to validate close to the user and again at execution.
- Availability depends on state that can change between form load and submission: criteria at execution.
- Length, default month, list order: form settings.
Example: two users reserve the same asset; criteria refuse the second.
W: Availability can change after the form loads, so it must be checked when the Action executes.
X: A=Length limit: a parameter constraint the form can enforce directly.
C=Starting month: a usability default for the date picker; it enforces no rule about the object's state.
D=Dropdown order: purely presentation, with no effect on whether a submission is valid when it runs.
T: Put rules that depend on current object state into submission criteria.
V: Action types

@ PLTR-APD D2 T2.3 applied use-case
S: A Delete Record Action is powerful and should be available only to a small group, with every use reviewed later. How should this be configured?
A: Make the Action available to everyone and rely on a note telling users to delete records only when necessary
B: Restrict the Action's permissions to the small group, require a reason parameter, and review execution history
C: Hide the Delete button in one module but leave the Action available elsewhere
D: Ask the small group to share one account for deletions
K: B
G: ## Restrict, explain and review
The exam guide asks you to understand Action security layers and auditability.
## Configuration
- Permissions: the specific group.
- Required reason.
- Execution history reviewed regularly.
Example: a monthly review finds two deletions with weak reasons and follows up.
W: Restricted permissions, required reasons and regular review: deletions are limited to the right people and every one is explainable.
X: A=Everyone with a note: any user can still delete records; a note asks for restraint but enforces nothing.
C=Hide in one module: the Action remains callable from other modules and the API, so the restriction is cosmetic.
D=Shared account: deletions cannot be attributed to individuals.
T: Restrict powerful Actions to specific groups and require reasons for later review.
V: Action types, permissions

@ PLTR-APD D2 T2.4 applied troubleshooting
S: An Action began failing for everyone after a property it writes was changed from optional to required in the Ontology. The Action's rules do not set that property. What is the fix?
A: Revert the Ontology change permanently so that the property can never be made required for this object type again
B: Update the Action to set the required property, and coordinate such changes via lineage
C: Ask users to edit the property manually after each Action
D: Remove all validation from the object type
K: B
G: ## Coordinating schema and Actions
The exam guide asks you to plan changes without breaking live consumers.
## Fix
- Action sets the new required property (from a parameter or a default rule).
- Lineage: other Actions creating or editing the type.
- Release schema and Action changes together.
Example: the Create Order Action now asks for a channel; orders are created successfully again.
W: Update the Action to supply the required property and coordinate future schema changes: the failure is fixed and repeats are avoided.
X: A=Revert permanently: abandons a legitimate requirement that the property be present, just to avoid updating one Action.
C=Manual edits: the Action already fails before users can edit anything.
D=Remove validation: lets incomplete objects in for every writer, weakening data quality across the type.
T: When properties become required, update every Action that creates or edits the type.
V: Action types, Workflow Lineage

@ PLTR-APD D2 T2.1 advanced use-case
S: An Action approves a loan, sets its status, creates a disbursement object, updates the borrower's exposure total, and notifies an external system. Which design best balances atomicity and reliability?
A: Do everything, including the external call, inside one synchronous function-backed Action, failing all edits if the external system is slow
B: A function-backed Action applying the internal edits atomically, then an asynchronous, idempotent notification with visible status
C: Four separate Actions that users run in sequence, plus a manual email to the external system's team
D: An automation that approves loans automatically whenever a loan object is created
K: B
G: ## Internal atomicity, external reliability
The exam guide asks about atomicity for multi-object changes and reliable integration with failure visibility.
## Design
- Function-backed Action: status, disbursement, exposure in one submission.
- After success: asynchronous notification with idempotency key and status.
Example: the external system is down for an hour; approvals proceed and notifications deliver afterwards.
W: Atomic internal edits with asynchronous external delivery: the platform stays consistent and external outages do not block approvals.
X: A=Everything synchronous: external slowness blocks or rolls back valid approvals.
C=Four manual Actions: partial completion and inconsistent state.
D=Auto-approve on creation: removes the human loan decision entirely and approves every application automatically.
T: Keep internal multi-object edits atomic and deliver external notifications asynchronously.
V: Action types, Automate
