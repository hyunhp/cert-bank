# PLTR-APD batch 05: Domain 4 round 1 (Workshop Application Development), 8 questions

@ PLTR-APD D4 T4.1 applied use-case
S: A Workshop module has an object table of open tickets and a details panel that should show the ticket the user selects. How should the selection drive the panel?
A: Ask the user to type the selected ticket's id into a text box that the details panel reads
B: Use the table's selected-object output variable as the input to the details panel's widgets
C: Duplicate the details panel for every ticket and hide all but one with conditional visibility
D: Reload the whole module each time a ticket is clicked so the panel shows the latest ticket
K: B
G: ## Variables connect widgets
The exam guide lists variables, events and widgets among Workshop building blocks. A selection is an output variable consumed by other widgets.
## Design
- Object table outputs the selected ticket.
- Details widgets take that variable as input.
- Empty-state message when nothing is selected.
Example: clicking ticket T-88 updates the panel instantly with its properties and links.
W: Wire the table's selection variable into the panel: the panel follows the user's choice with no extra steps.
X: A=Type the id: makes users do the work a variable does automatically and invites typos.
C=Panel per ticket: one hidden panel per ticket cannot scale to thousands of tickets and is impossible to maintain.
D=Reload the module: slow, discards filters and other state, and is unnecessary when a variable already carries the selection.
T: Connect Workshop widgets through variables such as a table's selected-object output.
V: Workshop

@ PLTR-APD D4 T4.3 applied troubleshooting
S: Users report that after they submit an Action from a Workshop form, the table in the same module still shows the old value until they refresh the page. What should the developer check?
A: Whether the Ontology lost the edit, since a stale table always means the Action failed silently even when it reports success
B: Whether the table refreshes after the Action (an event or refresh setting) and dependent variables update
C: Whether users are pressing the submit button hard enough on their touchscreens
D: Whether the module should be rebuilt in a different application to avoid caching
K: B
G: ## Stale after write
The exam guide asks you to diagnose why an interface is stale, including variable dependencies and asynchronous event behaviour.
## Checks
- Action succeeded? (execution evidence)
- After-submit event: refresh the table or its object set variable.
- Dependent variables recompute.
Example: adding a refresh on Action success makes the new value appear immediately.
W: Configure refresh on Action success and check variable dependencies: the edit is there, the view simply was not told to reload.
X: A=Lost edit: a page refresh shows the new value, so the edit was saved.
C=Pressing hard: the Action ran and the edit was saved; the stale value comes from the view not being refreshed.
D=Different application: the behaviour is configurable in Workshop.
T: When Workshop views are stale after writes, configure refresh events and check variable dependencies.
V: Workshop, Action types

@ PLTR-APD D4 T4.2 applied use-case
S: A module must show, for a selected customer, a computed risk score from a function and let a manager trigger a review Action. How should the module connect these?
A: Copy the function's logic into a Workshop formula and build a custom form that edits the object directly without an Action
B: A function-backed variable for the selected customer's score, and an Action button with the customer as a parameter
C: Have the manager open a separate tool to compute the score and then return to Workshop to make edits
D: Hard-code the score for each customer in the module's text widgets
K: B
G: ## Functions and Actions in Workshop
The exam guide asks you to connect Workshop to Ontology data, Actions, Functions and AIP capabilities.
## Design
- Function-backed variable: risk(customer), recomputed on selection.
- Action button with the selected customer as default parameter.
- Permissions on the Action control who can trigger reviews.
Example: selecting a customer shows score 72; the manager clicks Review and the Action records the request.
W: A function-backed variable and a parameterized Action: logic and writes stay in governed components that Workshop calls.
X: A=Formula plus direct edit: duplicates logic and bypasses the Action's validation and audit.
C=Separate tool: the manager switches applications and loses the customer context the module already holds.
D=Hard-coded scores: the values are stale the moment data changes, and every customer needs manual maintenance.
T: Use function-backed variables and parameterized Actions to connect Workshop to logic and writes.
V: Workshop, Functions, Action types

@ PLTR-APD D4 T4.4 applied use-case
S: A Workshop module is embedded in three other modules owned by different teams. The developer wants to add a new required input variable to it. What should be considered?
A: Nothing; embedded modules always pick up new inputs automatically and supply sensible default values for every embedding
B: Treat the interface as a contract: add the input as optional with a default and coordinate with embedding teams
C: Remove the module from the other teams' applications so that the change cannot affect them
D: Ask the three teams to copy the module and maintain their own versions
K: B
G: ## Module interfaces are contracts
The exam guide asks you to preserve module interfaces when making changes. A new required input breaks every embedding that does not supply it.
## Approach
- Add the input as optional with a sensible default.
- Communicate; let embedding teams pass the value when ready.
- Make it required later only if necessary.
Example: `region` defaults to "All"; two teams set it within a week.
W: Treat the module's inputs as a contract and introduce changes compatibly: embedders keep working while they adopt the new input.
X: A=Automatic defaults: a required input without a value breaks the embedding modules.
C=Remove from other apps: breaks the other teams' applications outright.
D=Copies per team: three diverging versions that each need fixes, tests and upgrades separately.
T: Change embedded module interfaces compatibly and coordinate with embedding teams.
V: Workshop

@ PLTR-APD D4 T4.1 applied comparison
S: A page should show an approval panel only to users when the selected request is in "Pending" status. Which Workshop feature fits?
A: Remove the panel and ask users to check the status manually before using a separate approval module
B: Conditional visibility on the panel based on the selected request's status variable
C: A text widget asking users not to use the panel unless the request is pending
D: Two separate modules, one for pending requests and one for others
K: B
G: ## Conditional visibility
The exam guide lists conditional visibility among Workshop design features. The panel appears when the condition holds.
- Condition: selected request status = Pending.
- Action submission criteria still enforce the rule server-side.
Example: selecting an approved request hides the panel; a pending one shows it.
W: Conditional visibility tied to the status variable: the interface shows the panel only when it applies, while the Action still enforces the rule.
X: A=Manual check and separate module: friction and context switching.
C=Text instruction: users can still use the panel on an approved request; a sentence on the page enforces nothing.
D=Two modules: duplication for a condition one setting handles.
T: Use conditional visibility for interface elements that apply only in certain states, backed by Action criteria.
V: Workshop

@ PLTR-APD D4 T4.3 applied tradeoff
S: A module's main table loads 50,000 objects with a dozen derived columns, and the page takes 20 seconds to open. Users usually need only today's items. What is the best first change?
A: Keep loading all 50,000 objects with every derived column, but add a progress spinner so users know the page is working
B: Default the table to a filtered object set (today's items) with pagination, computing derived columns only for visible rows
C: Split the table into ten modules of 5,000 objects each
D: Ask users to open the module early in the morning before they need it
K: B
G: ## Load what users need
The exam guide lists performance refactoring and lazy loading among Workshop skills and warns against hiding slow work behind a spinner.
## Change
- Default filter to today; users can widen it.
- Pagination; derived columns computed for visible rows.
- Measure load time after the change.
Example: the page opens in 2 seconds with 600 rows; widening to a week takes 4 seconds.
W: Filter to the common case and paginate: load time matches what users actually need.
X: A=Spinner: hides slow work rather than fixing it, which the guide warns against.
C=Ten modules: fragmentation without addressing load size per view.
D=Open early: pushes the cost onto users' routines and leaves the 20-second load exactly as it was.
T: Default Workshop views to the needed subset with pagination instead of loading everything.
V: Workshop

@ PLTR-APD D4 T4.2 applied use-case
S: A product team wants an AI-generated summary of each case shown in a Workshop module, generated only when the user asks. How should it be integrated?
A: Generate summaries for every case in a nightly pipeline and store them, even though most of them are never viewed by anyone
B: A button calling an AIP Logic function for the selected case, showing the typed result with loading and error states
C: Ask users to copy the case text into an external chatbot and paste the summary back
D: Display the raw case text and label it as a summary
K: B
G: ## On-demand AI in Workshop
The exam guide asks you to connect Workshop to AIP capabilities and to provide status for longer work.
## Design
- Button triggers the Logic function with the selected case.
- Loading state, typed output, error message.
- Optional: store the result through an Action if others should see it.
Example: clicking Summarize shows a 5-line summary after 3 seconds.
W: User-triggered Logic call with typed output and states: AI is used when wanted, inside the governed application.
X: A=Nightly for all: wasteful when summaries are needed only on request.
C=External chatbot: case data leaves the platform's governance and the summary is disconnected from the case.
D=Raw text as summary: mislabels the full text as a summary and gives users nothing shorter to read.
T: Integrate on-demand AI into Workshop through function calls with typed outputs and clear states.
V: Workshop, AIP Logic

@ PLTR-APD D4 T4.4 advanced use-case
S: A Workshop application is used by field staff on tablets and by managers on desktops. Field staff need large controls and few fields; managers need dense tables. What deployment approach fits?
A: One module designed for desktops only, telling field staff to zoom in on their tablets
B: Audience-specific pages or modules sharing the same Actions and Functions, each laid out for its device
C: Two completely separate applications with their own copies of every Action and Function, one for each type of device
D: A single page with every control for both audiences, hidden behind tabs
K: B
G: ## Channels and audiences
The exam guide asks you to choose an appropriate deployment channel and design layouts for the user workflow.
## Approach
- Shared logic: same Actions and Functions.
- Audience-specific pages or modules: tablet layout with large controls; desktop with dense tables.
- Permissions per audience.
Example: technicians complete an inspection in three taps; managers review 200 inspections in one table.
W: Audience-specific layouts over shared components: each channel gets a usable interface while logic stays single-sourced.
X: A=Desktop only with zoom: dense tables and small controls are unusable on tablets in the field, whatever the zoom level.
C=Separate apps with copies: every Action and Function exists twice, and fixes in one copy are forgotten in the other.
D=Everything on one page: both audiences wade through controls meant for the other, and the tablet layout stays cramped.
T: Build audience-specific layouts over shared Actions and Functions for different devices.
V: Workshop
