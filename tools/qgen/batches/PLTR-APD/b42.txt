# PLTR-APD batch 42: Domain 1 round 6 (Ontology Schema Design and Workflow Assembly), 8 questions

@ PLTR-APD D1 T1.1 applied use-case
S: A maintenance app tracks Machines and their Parts. A part is installed in at most one machine at a time but moves between machines over its life, and technicians need both the current location and the installation history. How should this be modelled?
A: A machine_id property on Part that is overwritten at each move, with history reconstructed from technicians' memories when needed
B: An Installation object type (part, machine, installed, removed) linked to both, plus a derived current-machine link on Part
C: A list of part serial numbers on each Machine object, edited by hand whenever a part is moved to another machine
D: A copy of each Part object for every machine it has ever been installed in, so each copy has one fixed location
K: B
G: ## Current state plus history
The exam guide asks for meaningful relationships and appropriate cardinality. A time-bounded placement of a part in a machine is an entity with its own attributes.
## Model
- Installation: part, machine, installed_at, removed_at (null while installed).
- Links to Part and Machine; derived current-machine link on Part.
- Actions: Install and Remove create and close installations.
Example: part P-55 shows it is now in machine M-3 and was previously in M-1 and M-7.
W: Installation objects with a derived current link: the app answers "where is it now?" instantly and keeps a complete, queryable history of moves.
X: A=Overwritten property: every move erases the previous location, so the installation history the technicians need is lost.
C=Hand-edited lists on Machine: fragile, unvalidated and easily inconsistent when a part appears on two machines at once.
D=Copy per machine: duplicates the part's identity many times and breaks any count or link that refers to the physical part.
T: Model time-bounded placements as dated objects and derive the current placement from them.
V: Ontology Manager

@ PLTR-APD D1 T1.2 applied troubleshooting
S: A link from Ticket to Customer stopped resolving for all tickets after the customer pipeline started emitting keys in lowercase while tickets still store uppercase ids. What is the right fix?
A: Ask users to search for customers manually by name whenever a ticket's customer link appears empty in the application
B: Normalize both key and foreign key to one agreed format in the pipelines, and add a check that links resolve after each build
C: Delete the link type and recreate it, which rebuilds all links using whatever key format the data currently has
D: Change the Customer primary key to the customer name, which is the same in both systems
K: B
G: ## Agreed key formats
The exam guide asks you to choose stable identity and to check whether data supports relationships.
## Fix
- Agree on one canonical format (for example uppercase).
- Normalize in both pipelines.
- Expectation or check: unresolved link count is zero.
Example: after normalization, all 80,000 tickets link to their customers again.
W: One canonical key format enforced in both pipelines with a resolution check: links work again and the next format drift is caught at build time.
X: A=Manual searching: pushes the broken relationship onto every user and every ticket they open.
C=Recreate the link type: the mismatch is in the data, so a recreated link resolves no better than before.
D=Name as key: names are not unique or stable, which would create a different and worse identity problem.
T: Agree on canonical key formats and verify link resolution after builds.
V: Ontology Manager

@ PLTR-APD D1 T1.3 applied use-case
S: An expense workflow must let employees submit claims with receipts, run policy checks, let managers approve, and pay approved claims through a finance system. Which assembly fits?
A: Employees email receipts to their managers, who forward approved ones to finance for manual payment entry each week
B: Submit and Approve Actions, an automated policy check, and an automated finance call on approval
C: One AIP agent that reads receipts, approves claims and triggers payments without any manager decision
D: A nightly batch that approves every claim under a fixed amount and ignores all larger claims entirely
K: B
G: ## Assembling the workflow
The exam guide asks you to assemble workflows across Ontology entities, Workshop modules, Functions, Actions and Automate steps.
## Assembly
- Submit Claim Action (receipt upload, validation).
- Automation: policy Function flags issues on the claim.
- Approve/Reject Actions in the manager module.
- Automation: idempotent payment request to finance with status.
Example: a claim submitted Monday is flagged for a missing receipt, corrected, approved Tuesday and paid Wednesday.
W: Actions for each human step and automations for checks and payment: governed decisions with reliable, auditable follow-through.
X: A=Email forwarding: no validation, no audit and slow, error-prone manual payment entry.
C=Autonomous agent: removes the manager's approval from a financial decision.
D=Nightly auto-approval by amount: bypasses review and leaves larger claims stuck forever.
T: Assemble expense-style workflows from Actions for decisions and automations for checks and integrations.
V: Action types, Automate, Workshop

@ PLTR-APD D1 T1.4 applied use-case
S: A developer plans to change how a property is computed in the pipeline backing an object type. Before doing so, they want to know which applications display it and which automations trigger on it. What should they use?
A: A guess based on which applications they personally remember building in the past year
B: Workflow Lineage on the object type to list its consuming modules and automations
C: A message to every team in the company asking whether they use the property
D: The object type's description field, assuming it lists every consumer accurately
K: B
G: ## Impact analysis
The exam guide lists Workflow Lineage for understanding impact before change.
## Steps
- Lineage on the object type and property.
- List consumers; notify owners; test changes on a branch.
Example: lineage shows two modules display it and one automation triggers when it exceeds a threshold; the automation's threshold is reviewed before the change.
W: Workflow Lineage lists the real consumers, including automations that react to the property, so the change can be planned safely.
X: A=Memory: misses consumers built by others and anything created since the developer last looked.
C=Message every team: slow, noisy and still incomplete when teams forget.
D=Description field: rarely complete or current, and not derived from actual usage.
T: Use Workflow Lineage to find consumers before changing how a property is computed.
V: Workflow Lineage

@ PLTR-APD D1 T1.1 applied tradeoff
S: An Ontology has an object type "Event" used for meetings, deliveries, inspections and incidents, with 80 properties, most of them empty for any given event. Applications filter by type everywhere. What restructuring helps?
A: Keep the single Event type, since one broad type is always simpler than several smaller ones for everyone involved
B: Split into specific object types (Meeting, Delivery, Inspection, Incident), with an interface for shared properties
C: Remove most properties so that every event shares only the five properties common to all of them
D: Create a separate Ontology for each event kind with no links between them
K: B
G: ## Specific types with a shared interface
The exam guide warns against overly broad object types and lists interfaces among constructs.
## Restructuring
- Specific types with their own properties and validation.
- Interface for shared fields (time, location, owner).
- Migration on a branch; consumers updated.
Example: the inspection module now uses Inspection with required checklist fields; a timeline view uses the interface.
W: Specific object types plus a shared interface: each type has meaningful, validated properties, and cross-type views still work.
X: A=Keep the broad type: sparse properties, weak validation and filters on type everywhere continue.
C=Remove properties: discards information inspections, deliveries and incidents genuinely need, to make the schema look tidy.
D=Separate Ontologies: breaks links between event kinds and removes the shared timeline views users rely on.
T: Split overly broad object types into specific ones with an interface for shared properties.
V: Ontology Manager

@ PLTR-APD D1 T1.2 applied comparison
S: Which identity choice is most appropriate for a Shipment object fed by three carrier systems whose tracking numbers can collide?
A: The tracking number alone, since each carrier says its numbers are unique within that carrier's own system
B: A composite of carrier code and tracking number, built unambiguously and checked for uniqueness
C: A random value generated at every pipeline build, which is guaranteed to be unique each time
D: The shipment's destination address, which is usually different for each shipment
K: B
G: ## Unique identity across sources
The exam guide asks you to select stable identity.
- Namespacing by carrier makes keys unique across sources.
- Stable across builds; uniqueness checked.
Example: carriers A and B both use 77801; keys "A:77801" and "B:77801" remain distinct.
W: A carrier-namespaced composite key, built unambiguously and checked for uniqueness: identity stays distinct across the three carriers and stable across every rebuild.
X: A=Tracking number alone: collisions across carriers merge different shipments into one object.
C=Random per build: identity changes every build and detaches edits.
D=Destination address: many shipments go to the same address, and addresses change, so it is neither unique nor stable.
T: Namespace keys by source system when multiple sources feed one object type.
V: Ontology Manager

@ PLTR-APD D1 T1.3 applied troubleshooting
S: A workflow creates purchase orders through an Action and then an automation sends them to suppliers. Some suppliers received orders that were later cancelled within minutes in the app. What design change helps?
A: Prevent users from ever cancelling purchase orders once they have been created through the Action
B: Delay briefly and re-check status before sending, with a cancellation notice if sent
C: Send purchase orders only once a week to reduce mistakes
D: Ask users to phone suppliers whenever they cancel an order
K: B
G: ## Respect live state before external effects
The exam guide asks you to account for live changes in workflows.
## Design
- Short confirmation window; re-check status before sending.
- If already sent: automated cancellation notice.
Example: an order cancelled after 90 seconds is never sent; one cancelled after sending triggers a notice.
W: Re-check live status before sending and handle cancellations after sending: suppliers stop receiving orders that no longer exist.
X: A=Forbid cancellation: users must be able to correct mistakes.
C=Weekly sending: delays every purchase order by days to avoid a rare cancellation shortly after creation.
D=Phone calls: depend on users remembering to call each supplier, which is manual, slow and unreliable.
T: Re-check live state before external effects and handle reversals.
V: Automate, Action types

@ PLTR-APD D1 T1.4 advanced troubleshooting
S: A module shows correct data to most users, but a team in one region sees empty widgets after a new marking was applied to one backing dataset. The developer must find exactly which widgets depend on that dataset. What is the most efficient approach?
A: Remove the new marking immediately so that everyone can see everything again while the team investigates
B: Trace dependent widgets with Workflow Lineage, then decide marking membership per need
C: Ask the regional team to use a different module until the problem resolves itself
D: Rebuild the entire module and see whether the widgets work afterwards
K: B
G: ## Lineage plus access decisions
The exam guide lists Workflow Lineage for troubleshooting access and warns against over-permissioning.
## Steps
- Lineage: dataset → object types → widgets.
- Confirm the regional team lacks the marking.
- Decide with the data owner: grant membership where justified, or adjust the module.
Example: two widgets use the newly marked type; the team is granted the marking after approval.
W: Trace dependents with lineage and make a deliberate access decision: the right widgets are identified and protection stays in place.
X: A=Remove the marking: undoes a protection someone deliberately added.
C=Different module: sends the team elsewhere without deciding whether they should have access to the marked data.
D=Rebuild the module: the module works for other users; only access to one dataset changed for this team.
T: Use lineage to find widgets affected by new markings and resolve access deliberately.
V: Workflow Lineage, markings
