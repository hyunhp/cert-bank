@ PLTR-APD D4 T4.1 applied use-case
S: A module must let a supervisor review a queue of pending requests one by one, see each request's details, and approve or reject with a reason, then move to the next. How should it be designed?
A: A single text area listing all pending requests as plain text, with the supervisor emailing decisions to the requesters directly
B: A queue table, a details panel bound to the selection, and Approve/Reject Actions with reasons
C: A separate module for each request, opened from a link in an email that the supervisor receives for every new request
D: A spreadsheet export of pending requests that the supervisor fills in and uploads at the end of the day
K: B
G: ## Queue-based review design
The exam guide asks you to design pages, widgets, variables and events around a user workflow.
## Design
- Table of pending requests; selection variable.
- Details panel bound to the selection.
- Approve/Reject Actions with required reason; refresh queue after each.
Example: the supervisor clears 40 requests in 20 minutes without leaving the module.
W: A queue with selection-bound details and Actions: the supervisor works through requests efficiently, with every decision validated and recorded.
X: A=Plain text and emails: no validation, no audit, and decisions scattered across inboxes.
C=Module per request: impossible to maintain and slow to work through.
D=Daily spreadsheet: decisions delayed until evening and outside governance.
T: Build review workflows as queues with selection-bound details and Actions.
V: Workshop, Action types

@ PLTR-APD D4 T4.3 applied troubleshooting
S: After the developer added a new chart, the module became slow. The chart uses a function-backed variable that depends on the entire filtered object set, which updates every time a user selects a row in the table. What should change?
A: Remove the table from the module so that users can no longer select rows that trigger the chart's recomputation
B: Make the chart depend only on the filter, not on the row selection
C: Add a spinner so users understand the chart is recomputing
D: Ask users to select rows less often
K: B
G: ## Correct dependencies
The exam guide lists variable dependencies and performance refactoring among Workshop skills.
## Fix
- Inspect dependencies; remove the selection from the chart's inputs.
- Measure responsiveness.
Example: selecting rows is instant again; the chart only recomputes when filters change.
W: Remove the unnecessary dependency: the chart recomputes only when its real inputs change.
X: A=Remove the table: users lose the row-level detail they need to fix a dependency problem in the chart.
C=Spinner: shows that something is happening but leaves every row selection as slow as before.
D=Select less often: asks users to change how they work to compensate for a misconfigured dependency.
T: Keep Workshop variable dependencies limited to their real inputs.
V: Workshop

@ PLTR-APD D4 T4.2 applied use-case
S: A module needs to show an AI-generated "next best action" for the selected account, but generating it takes about ten seconds. Users only sometimes need it. How should it be integrated?
A: Generate it automatically on every account selection so that it is always visible, even though users wait ten seconds each time
B: Generate it on demand when the user clicks a button, with a loading state, and optionally store the result for reuse
C: Pre-generate it nightly for every account, even those nobody opens
D: Remove the feature because ten seconds is too long
K: B
G: ## On-demand AI with status
The exam guide asks you to connect Workshop to AIP and design for performance.
## Design
- Button triggers the Logic function for the selected account.
- Loading state and error handling.
- Optional storage for reuse by colleagues.
Example: users who need it click and wait; others browse accounts instantly.
W: On-demand generation with clear status: users pay the wait only when they want the result.
X: A=On every selection: makes every selection slow for users who did not ask.
C=Nightly for all: costly for unopened accounts and may be stale.
D=Remove: users who find the recommendation useful lose it because others do not want to wait for it.
T: Integrate slow AI features on demand with clear loading states.
V: Workshop, AIP Logic

@ PLTR-APD D4 T4.4 applied use-case
S: An embedded module's owner wants to change the default value of one of its input variables. Several parent modules rely on the current default without setting it. What should the owner do?
A: Change the default immediately, since defaults are internal details that parents should not rely on
B: Find parents via lineage and set the value explicitly where needed before changing the default
C: Remove the input variable so that parents can no longer depend on it
D: Create a copy of the module with the new default and keep both
K: B
G: ## Defaults are part of the interface
The exam guide asks you to preserve module interfaces when making changes.
## Approach
- Find parents relying on the default.
- Communicate; update parents to set values explicitly if they need the old behaviour.
- Change the default.
Example: two parents set "showArchived = false" explicitly; the default changes to true for new uses.
W: Treat defaults as part of the contract: parents relying on them are updated first, so the change does not silently alter their behaviour.
X: A=Change immediately: silently changes behaviour in parents that relied on the default.
C=Remove the input: parents that set or rely on the input break or change behaviour without warning.
D=Copy the module: two versions to maintain, differing only in a default, which will drift apart.
T: Treat embedded module defaults as part of the interface and migrate parents before changing them.
V: Workshop, Workflow Lineage

@ PLTR-APD D4 T4.1 applied comparison
S: Which Workshop feature is most appropriate for showing a "Escalate" button only when the selected ticket is older than 48 hours and still open?
A: A text widget at the top of the page telling users that they should only escalate tickets that are old and open
B: Conditional visibility from a derived variable, with Action criteria enforcing the same rule
C: A separate module for old tickets
D: Showing the button always and relying on users to judge
K: B
G: ## Visibility plus enforcement
The exam guide lists conditional visibility among Workshop features and asks you to validate at execution.
- Derived variable; conditional button.
- Action criteria enforce the rule for every path.
Example: the button appears for a 60-hour-old open ticket and not for a 10-hour-old one.
W: Conditional visibility with matching Action criteria: the interface guides users and the rule is enforced regardless.
X: A=Text instruction: no guidance in context and no enforcement.
C=Separate module: duplicates the ticket screens for a rule that a condition on one button handles.
D=Always visible: invites premature escalations and relies entirely on Action criteria to refuse them.
T: Combine conditional visibility with Action criteria for state-dependent buttons.

@ PLTR-APD D4 T4.3 applied use-case
S: A module loads a large table, three charts and a map on its first page, though most users only use the table. Load time is 18 seconds. What is the best first change?
A: Keep everything on the first page and tell users the module is slow because it is powerful
B: Move charts and map to tabs loaded on demand, keeping the table first
C: Remove the table since it is the largest widget
D: Split the module into four modules
K: B
G: ## Load the common path first
The exam guide lists lazy loading and performance refactoring among Workshop skills.
## Change
- Table on the first page.
- Charts and map in tabs loaded when opened.
- Measure load time.
Example: initial load falls to 3 seconds; charts appear in 2 seconds when their tab is opened.
W: Prioritize what most users need and defer the rest: the common path becomes fast without removing features.
X: A=Accept slowness: every user waits 18 seconds on each visit for widgets most of them never use.
C=Remove the table: removes the one widget most users actually need, to speed up the ones they do not.
D=Four modules: fragments one workflow across four places users must find and navigate between.
T: Defer rarely used widgets so that the common path loads quickly.
V: Workshop

@ PLTR-APD D4 T4.2 applied troubleshooting
S: A module's Action button submits successfully, but the table showing the updated objects never changes until the page is reloaded. Other modules show the new values. What is the likely cause?
A: The Action failed silently in the background even though it reported a successful submission to the user
B: The table is not refreshed after the Action; add a refresh on completion
C: The users' browsers cannot display updated values
D: The Ontology delays updates for one module only
K: B
G: ## Refresh after writes
The exam guide asks you to diagnose why the interface is stale. When other modules already show the new values, the edit succeeded and the problem lies in how this module reloads its data.
## Fix
- On Action success: refresh the table's object set.
- Check dependent variables.
Example: the table updates immediately after each Action.
W: Missing refresh after the Action: the data changed, but this module's view was not told to reload.
X: A=Silent failure: other modules already display the updated values, so the Action clearly succeeded.
C=Browser display: other modules in the same browser show the new values, so display is not the cause.
D=Per-module delay: the difference is the module's configuration.
T: Refresh Workshop views on Action completion.
V: Workshop, Action types

@ PLTR-APD D4 T4.4 advanced use-case
S: A team must deliver the same core workflow to internal staff in Workshop and to partners in an external portal. Partners need a reduced set of actions. What architecture fits?
A: Build the workflow twice from scratch, once in Workshop and once in the portal, with separate logic in each
B: Shared Actions and Functions, a Workshop module for staff, and a scoped OSDK portal
C: Give partners Workshop access to the staff module and hide staff-only buttons with conditional visibility
D: Email partners a weekly export of their data instead of providing a portal
K: B
G: ## Hybrid delivery
The exam guide asks you to choose Workshop, OSDK or a hybrid for internal and external audiences.
## Architecture
- Shared Actions and Functions as the single source of logic.
- Workshop for staff.
- OSDK portal with partner scopes and data permissions.
Example: a validation fix in the shared Action applies to staff and partners immediately.
W: Shared logic with audience-specific front ends and scopes: one place to maintain rules, appropriate access for each audience.
X: A=Build twice: two separate implementations of the same rules inevitably diverge and double maintenance.
C=Hidden buttons: conditional visibility hides controls but does not restrict what partners can call or read.
D=Weekly exports: partners cannot act on the workflow, and exported files sit outside governance.
T: Share Ontology logic across Workshop and OSDK front ends, scoped per audience.
V: Workshop, OSDK, Action types
