# PLTR-APD batch 22: Domain 5 round 3 (OSDK, APIs, and External Applications), 8 questions

@ PLTR-APD D5 T5.1 applied tradeoff
S: A team plans a customer-facing mobile app that reads order status and lets customers request changes. They debate building it on the OSDK versus embedding a Workshop module. Customers have no Foundry accounts. Which choice fits better?
A: Embed the internal Workshop module directly in the mobile app and give every customer a Foundry account to sign in with
B: An OSDK app with a backend using scoped service authentication and per-customer filtering
C: Email customers a daily PDF of their order status and ask them to reply with any change requests they have
D: Publish the order dataset publicly so that the mobile app can read it without any authentication at all
K: B
G: ## External audiences and the OSDK
The exam guide asks you to choose Workshop, OSDK or a hybrid and justify the security model. A public mobile audience without platform accounts needs a custom app and a backend.
## Design
- Backend with service credentials, scoped to order status and the change-request Action.
- Customer authentication in the app's own system; backend filters by customer.
- Rate limiting and audit at the backend.
Example: a customer sees three orders and submits a change request that creates an object for staff to review.
W: OSDK with a scoped service backend and per-customer filtering: customers get a tailored app without platform accounts or exposed data.
X: A=Embed with accounts for customers: inappropriate for a public audience and over-permissions them inside the platform.
C=Daily PDF by email: slow, ungoverned and not an application customers can act in.
D=Public dataset: exposes every customer's orders to anyone, with no authentication at all.
T: For public audiences, build OSDK apps with scoped service backends and per-user filtering.
V: OSDK, Developer Console

@ PLTR-APD D5 T5.3 applied use-case
S: An external reporting tool calls Foundry's REST API to list Ticket objects modified in the last hour, every five minutes. The response sometimes misses tickets. What is a likely cause and fix?
A: The REST API randomly drops objects from responses, so the tool should call it twice and merge the results each time
B: The tool reads only the first page of results; follow page tokens until the result set is exhausted on each call
C: Tickets modified in the last hour are not available through the API until the next day
D: The tool should call the API once per second instead of every five minutes to catch more tickets
K: B
G: ## Paginate fully
The exam guide lists paginating among API skills and diagnosing missing data among troubleshooting. Busy periods produce more results than fit one page.
## Fix
- Loop on page tokens until none remain.
- Log counts per call to detect truncation.
- Consider filtering more narrowly if volumes are high.
Example: at peak, 1,800 tickets change in an hour; with full pagination none are missed.
W: Follow page tokens to the end: missing tickets at busy times are the classic sign of reading only the first page.
X: A=Random drops: the API returns pages deterministically; the client stopped reading after one.
C=Next-day availability: modified objects are queryable promptly; the omission correlates with volume, not time.
D=Call every second: multiplies requests, risks rate limits and still truncates each response.
T: Always iterate through all pages of API results.
V: REST API, OSDK

@ PLTR-APD D5 T5.2 applied troubleshooting
S: A developer stored a service client secret in the front-end code of an internal web app so that it could call Foundry directly. Security flagged it. What is the correct remediation?
A: Obfuscate the secret in the JavaScript bundle so that it is harder to read for curious users
B: Rotate the secret, move secret-based calls server-side (or use user OAuth), and minimize scope
C: Keep the secret in the bundle but restrict the app to the corporate network, which makes any exposure of it impossible
D: Share the secret with the security team so that they can monitor its use
K: B
G: ## Secrets never in the browser
The exam guide asks you to choose authentication without exposing secrets.
## Remediation
- Rotate the exposed secret now.
- Move confidential calls to a backend, or use user-based OAuth for interactive users.
- Minimal scopes; monitoring of usage.
Example: the app switches to user-based OAuth; the old secret is revoked.
W: Rotate and redesign: the exposed credential is invalidated and secrets move to where browsers cannot read them.
X: A=Obfuscation: anyone can still extract the secret from the bundle with basic tools.
C=Network restriction: insiders and compromised devices can still read it, and it is already exposed.
D=Share with security: spreads the secret further without removing it from the browser.
T: Rotate exposed secrets and keep confidential credentials server-side.
V: OSDK, Developer Console

@ PLTR-APD D5 T5.4 applied troubleshooting
S: An OSDK application deployed last month suddenly receives errors after a teammate narrowed the application's scopes in the developer console. Reads of Orders still work, but listing Shipments fails. What happened?
A: The Shipment object type was deleted from the Ontology at the same time as the scope change by coincidence
B: Shipments are no longer in the app's scope, so access fails regardless of user permissions; restore it if needed
C: The OSDK package has expired and must be renewed each month
D: The users' permissions on Shipments were removed by the scope change
K: B
G: ## Scope changes affect every user
The exam guide lists scope intersections among OSDK diagnostics. Narrowing an app's scope removes resources for all users of that app.
## Fix
- Confirm the scope change.
- Decide: does the app need Shipments? If yes, restore with minimal access.
- Change management for scope edits.
Example: Shipment was removed during a cleanup; it is restored with read access only.
W: The scope no longer includes Shipments: the app cannot reach them for anyone, which matches the sudden failure after the edit.
X: A=Deleted object type: other apps still read Shipments; only this app's scope changed.
C=Expired package: generated SDK packages do not expire; the failure follows the scope edit exactly.
D=User permissions removed: scope edits change the application, not users' own permissions.
T: Treat app scope edits as changes that affect all users and verify needed resources remain in scope.
V: OSDK, Developer Console

@ PLTR-APD D5 T5.3 applied comparison
S: Which approach is best for an external app that must show, for each of 2,000 customers, their number of open tickets?
A: For each customer, fetch all their tickets and count them in the app, making 2,000 sequential requests
B: One aggregation request grouping open tickets by customer and returning counts
C: Download every ticket nightly into the app's own database and count there
D: Ask support staff to maintain a manual list of open ticket counts
K: B
G: ## One aggregation instead of thousands of requests
The exam guide lists aggregating among OSDK skills and rate limits among failure modes.
- Group by customer, count open tickets.
- One request; results for all customers.
Example: the page loads counts for 2,000 customers in under a second.
W: A single grouped aggregation: the platform counts open tickets per customer in one request, which is fast, stays within rate limits and is always current.
X: A=2,000 requests: thousands of sequential calls make the page slow and quickly run into rate limits.
C=Nightly copy: stale and duplicates governed data outside the platform.
D=Manual list: staff maintaining counts by hand fall behind immediately, so the numbers are always out of date.
T: Use grouped aggregations for per-entity counts rather than many individual requests.
V: OSDK

@ PLTR-APD D5 T5.1 applied use-case
S: An application team adds new features every week that need additional object types. They want to avoid failures caused by forgetting to update the OSDK. What practice helps?
A: Hand-edit generated SDK files whenever a new type is needed, to avoid waiting for regeneration
B: Put scope updates and OSDK regeneration in the release checklist and CI
C: Grant the application scope to all object types in the Ontology once, so that regeneration is never needed again
D: Stop using the OSDK and send raw HTTP requests without types
K: B
G: ## Regeneration as part of the workflow
The exam guide lists generating or regenerating the OSDK and diagnosing stale SDK packages.
## Practice
- Checklist: update scope, regenerate, bump dependency.
- CI: build fails on missing types.
- Review scope changes.
Example: a feature using `Shipment` cannot merge until the regenerated SDK includes it.
W: Scope updates and regeneration built into the release process: missing types are caught at build time, not in production.
X: A=Hand-edit generated files: drift and overwrites at the next generation.
C=All object types: over-scoping for convenience, so a compromised app could reach far more than it needs.
D=Raw HTTP without types: loses compile-time safety and still needs scopes.
T: Build OSDK regeneration and scope review into the release process.
V: OSDK

@ PLTR-APD D5 T5.4 applied use-case
S: An external app shows a spinner forever when Foundry is slow. Users don't know whether their request worked. What should the developer implement?
A: Increase the spinner's animation speed so that users perceive the application as faster while they wait for Foundry
B: Timeouts with clear errors, backoff retries for reads, and visible status for writes
C: Hide all errors so that users never see technical messages
D: Ask users to refresh the page whenever the spinner appears
K: B
G: ## Visible state for slow or failed calls
The exam guide's safe-UX guidance: distinguish invalid input, denied access, transient failure and completed work; do not hide slow work behind a spinner.
## Design
- Timeouts; clear messages.
- Retries with backoff for reads.
- Status for writes (pending, done, failed) so users do not resubmit blindly.
Example: a slow Action shows "submitted, processing"; a failure shows "not completed, try again".
W: Timeouts, clear states and safe retries: users always know whether their request succeeded.
X: A=Faster spinner: a cosmetic change; users still cannot tell whether their request succeeded or failed.
C=Hide errors: users cannot tell failures from successes and may assume a failed write went through.
D=Refresh manually: may resubmit a write that already succeeded and discards whatever the user was doing.
T: Give external apps timeouts, clear error states and visible status for writes.
V: OSDK

@ PLTR-APD D5 T5.2 advanced tradeoff
S: An internal analytics app currently uses one service identity for all users, so everyone sees all data. Auditors require that each user sees only what their permissions allow. What change is needed?
A: Keep the service identity and add a filter in the app's code that hides data based on the user's department name
B: Switch to user-based OAuth so calls use each user's permissions; keep service identity for background jobs
C: Give every user administrator rights so that the service identity is no longer needed
D: Ask users not to look at data outside their department
K: B
G: ## User permissions require user identity
The exam guide asks you to choose user-based or service-based authentication and separate user permissions from service identities.
## Change
- User-based OAuth for interactive use.
- Service identity only for headless tasks, narrowly scoped.
- Test with users of different permissions.
Example: an analyst in Sales sees only sales data; a finance analyst sees finance data.
W: User-based authentication enforces each user's real permissions; the service identity is kept only where no user is present.
X: A=App-side filter: reimplements authorization in custom code and can be bypassed.
C=Administrator rights: the opposite of what auditors require.
D=Ask users: a request not to look at data enforces nothing, and auditors require enforcement.
T: Use user-based authentication when results must reflect each user's permissions.
V: OSDK, permissions
