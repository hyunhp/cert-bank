# PLTR-APD batch 11: Domain 2 round 2 (Action Types and Write-Back Patterns), 8 questions

@ PLTR-APD D2 T2.2 applied use-case
S: A Create Purchase Request Action has a form with ten fields, but users frequently submit requests with a missing cost centre or an amount in the wrong currency. How should the form and Action be improved?
A: Leave the form as it is and correct bad requests manually after they have been submitted and noticed by the finance team
B: Make the cost centre a required parameter chosen from valid values, constrain currency, and validate again at submission
C: Remove the cost centre field from the form entirely, since users find it confusing and keep getting it wrong
D: Add a paragraph of instructions at the top of the form and trust users to read it before submitting
K: B
G: ## Validate close to the user and again at execution
The exam guide's safe-UX row: validate close to the user and again at execution; configure parameters, validation and forms.
## Improvements
- Required parameter with allowed values for cost centre.
- Currency constrained (dropdown or fixed default).
- Submission criteria re-check at execution.
Example: the form cannot be submitted without a valid cost centre; invalid currencies are impossible to enter.
W: Required, constrained parameters plus execution-time validation: bad requests are prevented rather than corrected later.
X: A=Manual correction: errors reach finance first and cost time to fix after the fact.
C=Remove the field: finance still needs the cost centre for every request.
D=Instructions only: users skim instructions; nothing prevents a bad submission.
T: Use required, constrained parameters and execution-time validation to prevent bad submissions.

@ PLTR-APD D2 T2.1 applied tradeoff
S: An Action updates a Shipment's status. A developer proposes rewriting it as a function-backed Action "for future flexibility", although the current logic is a single property update with one validation rule. What is the better choice?
A: Rewrite it as function-backed now, since function-backed Actions are always preferable regardless of complexity
B: Keep it declarative, since it is a direct governed edit; convert only when real computation is needed
C: Replace the Action with a Workshop variable that edits the property directly
D: Remove validation so that the declarative Action is even simpler
K: B
G: ## Smallest design that is correct
The exam guide says the best design is the smallest one that satisfies correctness, security, user experience, auditability and operations. Declarative rules fit direct edits.
## Reasoning
- Today: one property, one rule.
- A function adds code, tests and deployment for no current benefit.
- Revisit when requirements need computation or cascading edits.
Example: a year later, cascading updates to linked packages are required; the Action is then converted.
W: Keep the declarative Action until requirements demand more: simpler, governed and easier to maintain today.
X: A=Function-backed by default: adds code and maintenance for hypothetical future needs.
C=Variable edits: bypasses the Action's validation, permissions and audit.
D=Remove validation: makes the Action less safe, not simpler in any useful way.
T: Prefer declarative Actions for direct edits and convert only when logic requires functions.
V: Action types

@ PLTR-APD D2 T2.3 applied use-case
S: A Delete Customer Action should be available only to the data stewardship group, while everyone can view customers. How should this be configured?
A: Hide the Delete button in the Workshop module for everyone except stewards, without changing the Action itself
B: Restrict the Action's permissions to the stewardship group, so only its members can run it through any application or API
C: Give the stewardship group Owner on every project that contains customer data
D: Add a confirmation dialog asking users whether they are a steward before deleting
K: B
G: ## Action-level permissions
The exam guide asks you to understand the independent security layers for Action execution. Who may run an Action is configured on the Action, independent of any one interface.
## Configuration
- Action permission: stewardship group only.
- The button can also be hidden for others, but enforcement lives in the Action.
- Audit of executions.
Example: a non-steward calling the Action through the API is refused, just as in Workshop.
W: Restrict the Action itself: the rule holds for every application and API call, not only for one screen.
X: A=Hide the button only: the Action can still be run from other modules or the API.
C=Owner on all projects: grants far more than delete rights and still does not restrict others.
D=Self-declared dialog: any user can click "yes, I am a steward"; the question enforces nothing about who deletes customers.
T: Control who may run an Action with Action permissions, not by hiding buttons.

@ PLTR-APD D2 T2.4 applied troubleshooting
S: Users report that an Action "does nothing": they submit it, see no error, but the object does not change. Execution logs show the Action succeeded. What should the developer check?
A: Whether users are clicking the button twice, since a second click always cancels the first submission
B: Whether the edit rules target the intended object and property, and the module refreshes
C: Whether the Ontology ignores edits from users who joined recently
D: Whether the Action needs to be deleted and recreated to start working
K: B
G: ## Success with no visible change
The exam guide asks you to troubleshoot Actions with execution evidence and to check whether interfaces are stale.
## Checks
- Edit rules: right object parameter and property; not writing to a different object.
- Interface refresh after submission.
- Object history to confirm what was written.
Example: the rule wrote to the parameter's default object rather than the selected one; fixing the mapping solves it.
W: Inspect edit rules and refresh behaviour: a successful Action with no visible change either wrote elsewhere or was not reflected on screen.
X: A=Double click cancels: a second submission does not undo the first.
C=New users ignored: the Ontology applies edits regardless of when an account was created; account age is not a factor.
D=Recreate the Action: the configuration error would be recreated too.
T: When an Action succeeds without visible change, check its edit targets and the interface refresh.
V: Action types, Workshop

@ PLTR-APD D2 T2.2 applied comparison
S: Which requirement is best implemented as an Action's submission criteria rather than as form-level input validation alone?
A: A text field must not exceed 500 characters
B: An approver cannot approve their own request, checked against the object and user at execution
C: A date picker should default to today
D: A dropdown in the form should list all departments in alphabetical order so that users find theirs quickly
K: B
G: ## Execution-time rules
The exam guide asks you to validate close to the user and again at execution. Rules about the current object state and the current user must be checked when the Action runs.
- Length limits, defaults and ordering: form conveniences.
- Approver ≠ submitter: depends on object and user at execution.
Example: an API call bypassing the form is still refused by the criteria.
W: A rule tied to the current object and user must be enforced at execution, where every submission path passes through it.
X: A=Length limit: a parameter constraint that the form can enforce directly.
C=Default date: a usability setting in the form; it constrains nothing and needs no check at execution.
D=Alphabetical order: purely presentation; the order of a dropdown has no bearing on whether a submission is valid.
T: Put rules that depend on object state and the acting user in submission criteria.

@ PLTR-APD D2 T2.3 applied troubleshooting
S: An Action that edits Invoice objects fails for a group of users with a permission error, although they have Editor on the project. The invoices carry a "Finance" marking. What is the right fix?
A: Remove the Finance marking from all invoices so that every Editor can run the Action
B: Decide whether they should handle finance data; if so, grant the marking via its owner
C: Give the users administrator rights so that markings no longer apply to them
D: Copy the invoices into an unmarked project so that the Action can edit the copies there instead of the originals
K: B
G: ## Markings are a separate layer
The exam guide lists markings among controls and warns against over-permissioning. Project roles do not satisfy markings.
## Fix
- Decide with the data owner whether the users need finance data.
- If yes: marking membership through the proper process.
- If no: the failure is correct; adjust the workflow.
Example: two of the five users are added to the marking; the other three are routed to a different process.
W: Treat the marking as an independent control and grant it only where justified: access matches need without weakening protection.
X: A=Remove the marking: strips protection from all finance data.
C=Administrator rights: over-permissioning that bypasses the governance decision.
D=Copies in an unmarked project: creates an unprotected duplicate of sensitive data.
T: When markings block an Action, decide membership through the data owner instead of removing the control.
V: markings, Action types

@ PLTR-APD D2 T2.4 applied use-case
S: An Action changes a loan application's status and must leave an audit trail showing who changed it, when, and why. What should the Action include?
A: Nothing extra, since the Ontology does not need to record who changed an object or for what reason the change was made
B: A required reason parameter stored with the change, plus execution history for who and when
C: An email to the compliance team after each change, written by the user
D: A shared spreadsheet where users log their changes manually
K: B
G: ## Auditability in Actions
The exam guide lists auditability among Action design concerns. Actions record who ran them and when; the "why" must be captured as data.
## Design
- Required `reason` parameter (dropdown plus optional text).
- Stored on the object or a linked log object.
- Execution history for actor and time.
Example: an auditor sees "status: Declined, by J. Kim, 2026-10-12, reason: income not verified".
W: A required reason parameter plus execution history: who, when and why are all recorded through the governed change itself.
X: A=Nothing extra: auditors need the reason, which only the Action can capture reliably.
C=Manual emails: depend on every user remembering, and the record sits in inboxes, disconnected from the change itself.
D=Spreadsheet log: manual, incomplete and editable after the fact.
T: Capture the reason for consequential changes as an Action parameter alongside execution history.
V: Action types

@ PLTR-APD D2 T2.1 advanced use-case
S: Approving a claim must update the claim, create a payment object, adjust the policy's remaining coverage, and all three changes must succeed or fail together. How should this be implemented?
A: Three separate declarative Actions that users run one after another in the correct order
B: One function-backed Action validating preconditions and returning all three edits together
C: A declarative Action for the claim and an automation that later creates the payment and adjusts coverage
D: A Workshop button that edits the three objects directly through variables
K: B
G: ## Atomic multi-object changes
The exam guide asks you to reason about validation, preconditions and atomicity, and to use function-backed Actions for cascading changes.
## Implementation
- Function-backed Action: check claim status and coverage, compute the payment, return edits to claim, payment and policy.
- The edits apply together or not at all.
- Tests for insufficient coverage and concurrent approvals.
Example: an approval exceeding coverage is rejected and nothing changes.
W: One function-backed Action returning all edits: the three changes are validated together and applied atomically.
X: A=Three Actions in order: partial completion leaves inconsistent state if a user stops halfway.
C=Action plus later automation: a window of inconsistency and separate failure handling.
D=Direct edits via variables: no validation, permissions or atomicity.
T: Use one function-backed Action for multi-object changes that must succeed or fail together.
V: Action types, Functions
