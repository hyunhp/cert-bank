# PLTR-APD batch 17: Domain 8 round 2 (Application Security, Governance, and Operations), 8 questions

@ PLTR-APD D8 T8.1 applied use-case
S: An application shows Employee objects to all staff, but the salary property must be visible only to HR, while other properties remain visible to everyone. Which control fits?
A: Hide the salary column in the Workshop table for non-HR users while leaving the property readable through every other tool
B: A property-level security control (or a separate HR-only object or view) so non-HR users cannot read salary anywhere
C: Remove the salary property from the Ontology entirely so that nobody, including HR, can see it in any application
D: Ask non-HR staff in the onboarding training not to look at the salary column when it appears
K: B
G: ## Property-level protection
The exam guide asks you to apply governance controls and separate application access from data access. A sensitive property needs protection at the data layer, not only in one screen.
## Options
- Property security policy restricting salary to HR.
- Or a separate HR-only object type or view holding compensation.
- Verify with non-HR and HR test users across tools.
Example: an analyst querying Employee through another module sees no salary values; HR sees them.
W: Protect the property at the data layer: salary is hidden from non-HR users in every application and tool, while other properties stay visible.
X: A=Hide the column: the property remains readable through other modules, functions and APIs.
C=Remove the property: HR loses access to data it legitimately needs.
D=Training request: enforces nothing; the data remains visible.
T: Protect sensitive properties with data-layer controls, not by hiding UI columns.
V: permissions, Ontology Manager

@ PLTR-APD D8 T8.2 applied troubleshooting
S: A user cannot open an application at all and receives a resource permission error, while their teammates can. The data the application shows is not sensitive. What should be checked first?
A: Whether the user's data permissions on the underlying datasets include every marking that exists in the organization
B: Whether the user has access to the application resource itself (a role on its project or folder)
C: Whether the user's laptop has enough memory to load the application's widgets
D: Whether the application must be rebuilt from scratch for each new team member
K: B
G: ## Resource access first
The exam guide asks you to separate application/resource access from data access. Failing to open the app is a resource access problem.
## Checks
- Role on the project or folder containing the module.
- Group membership compared with teammates.
- Then, once the app opens, data access for its contents.
Example: the user was not in the team's group that holds Viewer on the applications folder.
W: Resource access comes first: the user cannot open the module, so the role on its location is the layer to check.
X: A=All markings: data permissions do not affect opening the module, and granting every marking is over-permissioning.
C=Laptop memory: a resource permission error is an authorization result, not a client capacity problem.
D=Rebuild per member: applications are shared resources; access is granted, not rebuilt.
T: Diagnose "cannot open the app" as resource access before investigating data access.
V: permissions, Workshop

@ PLTR-APD D8 T8.3 applied comparison
S: Which statement correctly distinguishes user-scoped from project-scoped execution for an Action or Function?
A: User-scoped and project-scoped execution are the same; the terms describe where the code is stored, not whose permissions apply
B: User-scoped runs with the invoker's permissions; project-scoped runs with a configured identity's
C: Project-scoped execution always has administrator rights across the whole organization
D: User-scoped execution ignores markings, because users are already authenticated
K: B
G: ## Whose permissions apply
The exam guide asks you to understand user-scoped versus project-scoped execution and service identities.
- User-scoped: results and writes reflect the invoking user's access.
- Project-scoped: a configured identity acts within the project's scope; use for controlled elevation with least privilege.
Example: a search function runs user-scoped; an audit-writing Action runs project-scoped with narrow write access.
W: User-scoped follows the invoker; project-scoped follows a configured identity: the distinction decides what each execution can see and change.
X: A=Same thing: the two modes apply different permissions, which is the whole point of choosing between them.
C=Administrator rights: project-scoped execution should be least-privilege, not organization-wide administration.
D=Ignores markings: markings apply to users regardless of authentication.
T: Choose user-scoped execution to reflect the invoker's access and project-scoped for controlled, least-privilege elevation.
V: permissions, Functions

@ PLTR-APD D8 T8.4 applied use-case
S: An application's automation started failing at 03:00 and users noticed at 09:00. The team wants to detect this kind of failure within minutes in future. What should be set up?
A: A weekly review meeting where the whole team looks through the automation's run history together on a shared screen
B: Alerts on failed and missing runs, routed to the owning team's rotation, with a runbook
C: Ask users to report problems as soon as they arrive at work in the morning
D: Restart the automation every night at 02:55 to prevent failures at 03:00
K: B
G: ## Monitoring automation health
The exam guide asks you to monitor automation health and route issues to owners.
## Setup
- Alert on failed runs and on expected runs that did not happen.
- Route to the owning team's rotation.
- Runbook for common failures.
Example: the next 03:00 failure pages the on-call engineer at 03:02.
W: Failure and missing-run alerts routed to an owner with a runbook: failures surface in minutes instead of hours.
X: A=Weekly review: a failure on Tuesday night goes unnoticed until the next meeting, days after users were affected.
C=Users report: detection depends on users arriving in the morning, leaving hours of overnight failure unnoticed.
D=Nightly restart: guesses at a cause, detects nothing, and leaves any other failure just as invisible as before.
T: Alert on automation failures and missed runs, routed to owning teams.
V: Automate, monitoring

@ PLTR-APD D8 T8.1 applied tradeoff
S: An application team wants all members to be able to merge changes to production Actions instantly to move faster. A security reviewer objects. What is a balanced approach?
A: Let everyone merge directly to production, since speed is more important than review for internal applications
B: Branch protection with required review, kept fast with small changes and quick branch builds
C: Freeze all changes to production Actions permanently so that nothing can go wrong
D: Allow merges only once a quarter in a large release
K: B
G: ## Control with speed
The exam guide lists branch protection among governance controls. Review need not be slow if branches build quickly and reviews are focused.
## Approach
- Protected main; one approving review.
- Fast branch builds and tests.
- Small changes reviewed quickly.
Example: median time from change to merge is two hours, and a removed validation rule is caught in review.
W: Required review with fast workflows: changes stay controlled without becoming slow.
X: A=Unreviewed merges: production Actions change without any second check.
C=Freeze: blocks every fix and improvement to production Actions, which is a different failure from moving too fast.
D=Quarterly releases: large, risky batches that are hard to review and leave urgent fixes waiting for months.
T: Use branch protection with lightweight, fast reviews to balance speed and control.
V: branches

@ PLTR-APD D8 T8.2 applied use-case
S: A module is shared with a partner organization's users, who should see only partner-related objects. Internal users see everything. How should access be designed?
A: Share the module with the partner organization and rely on the module's filters to hide internal objects from them
B: Give the partner's users the module and data-level controls limiting them to partner objects
C: Give partner users accounts in the internal organization so that they can see everything internal users see
D: Copy the partner objects into a separate dataset each night and email it to the partner
K: B
G: ## Organizations and data-level controls
The exam guide lists organizations, markings and restricted views among controls and asks you to separate application access from data access.
## Design
- Module access for the partner organization's group.
- Data: restricted views or object security so partner users read only partner objects; internal data protected by markings or organization boundaries.
- Test with a partner identity.
Example: a partner user opens the module and sees 120 partner objects; internal objects are not readable through any tool.
W: Module access plus data-level restrictions: partners use the same application while internal data stays protected everywhere.
X: A=Rely on module filters: filters are not access control; data remains readable through other tools.
C=Internal accounts: grants partners internal visibility and blurs organization boundaries.
D=Nightly email: data leaves the platform without egress governance, and partners work from a day-old copy.
T: Share applications across organizations with data-level controls, not UI filters.
V: organizations, restricted views

@ PLTR-APD D8 T8.3 applied troubleshooting
S: A function-backed Action runs project-scoped under a service identity. After a security review, the identity's permissions were reduced, and now the Action fails for everyone. What should the developer do?
A: Restore the identity's original broad permissions immediately so that the Action works again
B: Identify exactly what the Action reads and writes, grant only that to the identity, and test
C: Switch the Action to run as an administrator account
D: Delete the Action and ask users to edit objects directly
K: B
G: ## Least privilege after a review
The exam guide asks you to understand service identities and apply least privilege without over-permissioning.
## Steps
- Determine the Action's real reads and writes (code, lineage).
- Grant exactly those to the identity.
- Test on a branch; document.
Example: the Action needs write on Claim and read on Policy; nothing else is granted.
W: Grant exactly what the Action needs: it works again while the review's reduction of excess privilege stands.
X: A=Restore broad permissions: undoes the security review instead of right-sizing.
C=Administrator account: replaces a reduced identity with an unrestricted one, the exact opposite of what the review aimed for.
D=Direct edits: users would change objects without the Action's validation, permissions and audit trail.
T: After reducing a service identity's access, restore only the specific permissions the workflow requires.
V: permissions, Action types

@ PLTR-APD D8 T8.4 advanced troubleshooting
S: Users report that an AI-assisted application has become slow and occasionally returns errors since yesterday. The application uses Ontology queries, a Function and an AIP Logic call. How should the developer locate the cause efficiently?
A: Rewrite all three components in parallel, assuming they are all responsible for the slowdown
B: Use per-component monitoring and traces to find which step's latency or errors changed
C: Ask users to retry their requests until they succeed
D: Switch the AIP Logic call to a larger model, since AI is usually the slowest part
K: B
G: ## Monitor, then narrow
The exam guide asks you to monitor application, Ontology, automation, indexing and AIP health and to diagnose from evidence.
## Steps
- Per-component latency and error metrics; traces of slow requests.
- Find the step that changed (for example, the Function after a data growth spike).
- Fix that step; verify.
Example: traces show the Function's query time tripled after a new data source doubled object counts; adding a filter restores speed.
W: Per-component monitoring and traces locate the changed step: the fix targets the real cause instead of every component.
X: A=Rewrite everything: expensive and unlikely to target the actual change.
C=User retries: hides the symptom from the team, adds load to whatever is struggling, and fixes nothing.
D=Larger model: may make AI slower and costlier, and the AI step may not be the cause.
T: Use per-component monitoring and traces to locate performance regressions before changing anything.
V: monitoring, AIP Observability
