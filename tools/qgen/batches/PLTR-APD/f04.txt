@ PLTR-APD D5 T5.2 advanced tradeoff
S: A partner integration needs to read orders for one partner only. Options: a service client scoped to all orders with filtering in the integration code, or access restricted at the data level to that partner's orders. Which is better and why?
A: The service client with code filtering, because a code review can confirm the filter and it is simpler to maintain
B: The service client with code filtering, plus an alert that fires when a response contains another partner's order
C: Grant the full orders dataset under a usage agreement that forbids the integration from reading other partners' rows
D: Scope the credential's own permissions to the one partner, with the integration's filter kept as an extra check
K: D
G: ## Enforce at the data layer
The exam guide asks you to apply least privilege and governance controls rather than rely on application code.
## Reasoning
- Code filtering can be bypassed by bugs or compromise.
- Data-level restriction limits what the credential can ever read.
Example: a bug in the integration's filter cannot expose other partners' orders because the client cannot read them.
W: Restrict at the data level, keep the filter as a second layer: the credential itself can only read that partner's orders, so even a bug in the filter or a leaked credential cannot reach other partners' data.
X: A=Code filtering only: a review checks the code once, but one later bug or a leaked credential still exposes every order, because the client is allowed to read all of them.
B=Code filtering plus an alert: the alert only reports exposure after another partner's order has already left the platform; it is a detective control, not a restriction on what can be read.
C=Full dataset under a usage agreement: an agreement is not a technical control, so a mistake or compromise would expose every partner's orders.
T: Restrict external credentials at the data layer, not only in integration code or by agreement.

@ PLTR-APD D4 T4.3 applied troubleshooting
S: A Workshop page with ten widgets loads in 15 seconds. Profiling shows each widget makes its own heavy query for the same base object set, and two function-backed variables run on load although they are only used in a collapsed section. What should be changed?
A: Feed every widget from one shared variable and run the two hidden functions only when they are needed
B: Ask users to keep the module open all day so that they only pay the 15-second load time once per day
C: Add a progress bar that explains the delay, and keep each widget's query and variable as they are now
D: Split the page into ten pages, one per widget, so that each widget's base object set query loads alone
K: A
G: ## Remove duplicate work and defer the rest
The exam guide lists variable dependencies, lazy loading and performance refactoring among Workshop skills.
## Refactor
- One base object set variable reused by all widgets.
- Lazy loading for collapsed sections and their functions.
- Measure load time before and after.
Example: load time falls from 15 seconds to 3; the collapsed section takes a second when opened.
W: Reuse the base query and defer hidden work: one shared object set variable removes the nine duplicate queries, and lazy loading runs the two functions only when the section is opened, so neither costs anything at page load.
X: B=Keep it open: shifts the cost to users and fails after every refresh.
C=Progress bar: hides the slowness, which the guide warns against, and fixes nothing.
D=Ten pages: fragments the workflow and still runs the same heavy query once per page, so the duplicated work remains.
T: Share base object sets across widgets and lazy-load hidden sections.
V: Workshop

@ PLTR-APD D1 T1.4 applied use-case
S: A developer must rename a property on an object type that several applications use. Before changing anything, they want to know which Workshop modules, Functions and Actions depend on it. Which capability helps most?
A: Workflow Lineage, which traces the resources that sit downstream of an Ontology element
B: Searching every project folder by hand and opening each module to look for the property name
C: Asking in the team chat which applications use the property and collecting the answers in a list
D: Renaming the property and then watching which applications report errors over the following days
K: A
G: ## Impact analysis before change
The exam guide asks you to use Workflow Lineage to understand impact, troubleshoot access and plan changes without breaking live consumers.
## Use
- Open the object type in Workflow Lineage; trace dependent modules, Functions, Actions and automations.
- List owners; plan a compatible transition (new property, migration, removal).
Example: lineage shows two modules and one Function using the property; they are updated on a branch before the rename merges.
W: Workflow Lineage: it shows the modules, Functions, Actions and automations that depend on the object type and property, so the rename can be planned before any live consumer breaks.
X: B=Manual search: slow, incomplete and misses Functions and automations that never show the property name in a module.
C=Ask in chat: people forget, leave or never knew; recollections miss Functions and automations that use the property.
D=Rename and watch: every dependent module and Function breaks in production before anyone has a plan to fix it.
T: Use Workflow Lineage to find dependents before changing Ontology resources.
V: Workflow Lineage

@ PLTR-APD D8 T8.2 applied use-case
S: A module will be shared with an external auditor for two weeks. The auditor should see only specific objects and no Actions. How should access be configured?
A: A separate view-only module without write-back, with data permissions on the needed objects and an end date
B: Export the objects to a spreadsheet and email it, so that the auditor never has to sign in to the platform
C: An internal employee account in the auditor's name that an administrator disables when the review ends
D: The full internal module, with a note in the invitation asking the auditor not to click any of the buttons
K: A
G: ## Scoped, time-bound external access
The exam guide asks you to separate application access from data access and apply least privilege.
## Design
- Read-only module without Actions.
- Data permissions limited to audit objects.
- Expiry after two weeks.
Example: the auditor reviews 300 contracts; access ends automatically.
W: Dedicated read-only module with restricted data and an end date: the module offers no Actions, data permissions limit what the auditor can see to the audit objects, and access ends after two weeks.
X: B=Spreadsheet export: the data leaves every access control, copies persist after the audit, and the auditor cannot verify the evidence in the platform.
C=Employee account: grants internal access far beyond the audit, attributes the auditor's activity to an internal identity and depends on someone remembering to disable it.
D=Full module with a note: the Actions and all of the module's data remain available; a request is not a control.
T: Give external reviewers read-only, scoped, time-bound access.
V: permissions, Workshop
