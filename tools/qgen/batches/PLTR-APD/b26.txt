# PLTR-APD batch 26: Domain 1 round 4 (Ontology Schema Design and Workflow Assembly), 8 questions

@ PLTR-APD D1 T1.1 applied use-case
S: A logistics app needs to show each Truck's current driver and the full history of which drivers drove it and when. Drivers change trucks often. How should this be modelled for both the current view and the history?
A: A single "driver" property on Truck that is overwritten at each change, with history reconstructed from old screenshots if anyone needs it
B: A DriverAssignment object type with start and end times linked to Truck and Driver, plus a derived current-driver link on Truck
C: A list property on Truck holding every driver's name in the order they drove it, with no times recorded anywhere
D: A separate Truck object for each driver who has ever driven it, so each copy holds exactly one driver
K: B
G: ## History and current state
The exam guide asks for meaningful relationships with appropriate cardinality. A time-bounded relationship between two entities is itself an entity.
## Model
- DriverAssignment: truck, driver, start, end (null while active).
- Links to Truck and Driver.
- Current driver: derived from the open assignment.
Example: truck T-14 shows driver D-3 now and eleven past assignments with dates.
W: Dated assignment objects with a derived current link: the app shows the present instantly and keeps a queryable history.
X: A=Overwritten property: every change erases the previous driver, so history cannot be answered from the Ontology at all.
C=Name list without times: no dates, no links to Driver objects, and no way to answer who drove the truck on a given day.
D=Truck per driver: duplicates the truck's identity many times and breaks every link and count that refers to it.
T: Model time-bounded relationships as dated objects and derive the current state from them.
V: Ontology Manager

@ PLTR-APD D1 T1.2 applied comparison
S: Which choice of primary key for an Employee object type is most stable?
A: The employee's email address, since it is unique and easy to read for anyone looking at the data
B: The employee number assigned once by the HR system of record and never reused
C: The employee's full name combined with their department, since that combination is usually unique
D: The row number of the employee in the backing dataset, since it is always unique within a build
K: B
G: ## Stable identifiers
The exam guide asks you to select stable identity. A key must not change over the entity's life.
- Employee number from HR: assigned once, never reused.
- Email, name and department change; row numbers shift with every rebuild.
Example: an employee who marries and changes department keeps E-10482 and all their linked records.
W: The HR employee number never changes for the life of the person's record, so edits and links stay attached through every name, email or department change.
X: A=Email: changes with name changes or domain migrations, detaching edits and links each time.
C=Name and department: both change, and two people can share them.
D=Row number: shifts whenever data is reordered or rebuilt, so identity is lost every build.
T: Key objects on identifiers assigned once by the system of record.
V: Ontology Manager

@ PLTR-APD D1 T1.3 applied use-case
S: A procurement workflow needs: requesters submit purchase requests, a policy check runs automatically, approvers decide, and approved requests create purchase orders in an external ERP. Which assembly fits?
A: Requesters email approvers, who forward approved emails to the purchasing team for manual ERP entry
B: A request Action, an automation running a policy Function, an approval module and Action, then an automation calling the ERP
C: A single AIP Logic function that reads the request, decides approval and writes to the ERP without human involvement
D: A spreadsheet of requests reviewed weekly by finance, with approved rows uploaded to the ERP manually
K: B
G: ## End-to-end assembly
The exam guide asks you to assemble workflows across Ontology entities, Workshop modules, Functions, Actions and Automate steps.
## Assembly
- Submit Request Action (validated).
- Automation: policy Function flags issues.
- Approver module with Approve/Reject Actions.
- Automation: create PO in ERP, idempotent, with sync status.
Example: a request submitted at 09:00 is policy-checked at 09:01, approved at 11:30 and in the ERP at 11:31.
W: Actions for each human decision and automations for checks and integration: every step is governed, auditable and reliable.
X: A=Email chains: no validation, no audit and slow manual ERP entry that invites typing errors.
C=Fully automated AI approval: removes the approver from a consequential financial decision.
D=Weekly spreadsheet: days of delay and ungoverned manual uploads to the ERP.
T: Build workflows from Actions for decisions and automations for checks and integrations.
V: Action types, Automate, Workshop

@ PLTR-APD D1 T1.4 applied troubleshooting
S: After a developer changed a link type's cardinality from one-to-many to many-to-many, a Workshop module started showing errors and an automation stopped running. What should have been done first?
A: Nothing different; cardinality changes never affect existing consumers, so the errors must be unrelated
B: Review the link's consumers in Workflow Lineage and migrate them on a branch first
C: Delete the module and the automation before making any Ontology change, then rebuild them later
D: Make the change on a Friday evening so that fewer users notice the errors
K: B
G: ## Change impact
The exam guide asks you to use Workflow Lineage to plan changes without breaking live consumers.
## Practice
- Lineage on the link type: modules, Functions, automations.
- Assess: code expecting a single linked object breaks with many-to-many.
- Branch: update consumers with the change; merge together.
Example: the automation assumed one linked owner; it is updated to handle several before the cardinality changes.
W: Lineage-based impact analysis and coordinated migration: consumers are updated with the change instead of breaking after it.
X: A=Never affects consumers: code and widgets that assume one linked object break when several are returned.
C=Delete consumers first: needlessly destroys working applications and their configuration.
D=Friday evening: the breakage still happens, only with fewer people around to fix it.
T: Check lineage and migrate consumers before changing link cardinality.
V: Workflow Lineage

@ PLTR-APD D1 T1.1 applied tradeoff
S: A team wants to add 40 rarely used properties to a core Customer object type because one new application needs them. Other applications use Customer heavily. What is a sensible approach?
A: Add all 40 properties to Customer immediately, since more properties on a core type never cause problems for other applications
B: Model the new data as a linked object type (for example CustomerProfileDetail) used by the new application, keeping Customer focused
C: Create a second Customer object type for the new application with all existing and new properties copied over
D: Store the 40 values as one JSON text property on Customer so the type's schema does not change
K: B
G: ## Keep core types focused
The exam guide warns against overly broad object types and asks for meaningful structure.
## Design
- Linked object type for the application-specific details.
- One-to-one link to Customer.
- Permissions can differ for the detail type.
Example: the new app reads CustomerProfileDetail; other apps continue using Customer unchanged.
W: A linked detail type keeps the core type stable and focused, while the new application gets its data with separate permissions if needed.
X: A=Add 40 properties: bloats a heavily used type and couples every consumer to one app's needs.
C=Second Customer type: duplicates the entity and creates two sources of truth.
D=JSON property: unqueryable, unvalidated and hidden from filters and Actions.
T: Put application-specific attributes in linked object types rather than bloating core types.
V: Ontology Manager

@ PLTR-APD D1 T1.2 applied troubleshooting
S: A link from Invoice to Customer uses the customer code on the invoice. For one source system, codes have a prefix ("ACME-C123") while the Customer key is "C123". Those invoices show no customer. What is the correct fix?
A: Add the prefixed codes as additional primary keys on the Customer object type so that both forms of the code match
B: Normalize the foreign key to the Customer key format and check every invoice resolves
C: Ask users to look up customers manually for invoices from that source system
D: Change every Customer key to include the prefix, breaking the other systems' links
K: B
G: ## Keys must match exactly
The exam guide asks you to check whether the data supports a relationship.
## Fix
- Normalize foreign keys in the backing pipeline (coordinate with the data owner).
- Expectation or check: unresolved invoice links count = 0.
Example: after normalization, 12,000 invoices link to their customers.
W: Normalize the foreign key to the target key format and monitor resolution: links work for every source system.
X: A=Multiple primary keys: an object type has one key; adding variants is not how identity works.
C=Manual lookup: users repeat work the link should do for them.
D=Change every Customer key: breaks every other system's links to fix one source.
T: Fix link mismatches by normalizing foreign keys to the target's key format.
V: Ontology Manager

@ PLTR-APD D1 T1.3 applied comparison
S: Which component should own each step of "a user submits a leave request, and if approved, the HR system is updated"?
A: A Workshop variable submits the request, and a Function updates the HR system directly from the browser
B: Actions for submission and approval, and an automation updating the HR system afterwards
C: An AIP agent submits, approves and updates on its own without any user confirmation
D: A pipeline transform submits requests nightly and updates the HR system from a dataset
K: B
G: ## Right component per step
The exam guide's decision table: Actions for governed state changes, Automate for triggers and orchestration, integrations for external systems.
- Submit and approve: Actions with validation and permissions.
- After approval: automation calls the HR system with retries and status.
Example: approval at 10:00 updates the HR system at 10:01, with status visible on the request.
W: Actions for user decisions and an automation for the external update: each step uses the component designed for it.
X: A=Variable and browser call: bypasses validation and exposes integration from the client.
C=Autonomous agent: removes the human approval the process requires.
D=Nightly pipeline: user requests are not batch data; responses would be a day late.
T: Map user decisions to Actions and post-decision integrations to automations.
V: Action types, Automate

@ PLTR-APD D1 T1.4 advanced use-case
S: A team must change the primary key of a heavily used object type because the old key was unstable. Many applications, Functions and user edits depend on it. What plan fits?
A: Change the key in place during business hours and ask users to re-enter any of their edits that happen to disappear
B: Map old to new keys, migrate edits and links, update consumers on a branch, then validate
C: Create a new object type with the new key and leave the old one running forever alongside it
D: Postpone the change indefinitely, since key changes are always too risky to attempt
K: B
G: ## Planned key migration
The exam guide asks you to plan changes without breaking live consumers and to select stable identity.
## Plan
- Mapping dataset old → new key.
- Migrate edits and links.
- Lineage: consumers; update them on a branch.
- Switch, validate counts and edits; communicate.
Example: 150,000 objects move to stable keys; all 4,000 user edits are preserved.
W: Mapping, migration, consumer updates and validation: the key becomes stable without losing edits or breaking applications.
X: A=In place with re-entry: users lose edits and applications break during working hours.
C=Two types forever: duplicated entities and consumers split between them.
D=Postpone forever: the unstable key keeps re-identifying objects and detaching users' edits every time it changes.
T: Migrate primary keys with a mapping, edit migration and coordinated consumer updates.
V: Ontology Manager, Workflow Lineage
