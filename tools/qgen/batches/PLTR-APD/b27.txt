# PLTR-APD batch 27: Domain 2 round 4 (Action Types and Write-Back Patterns), 8 questions

@ PLTR-APD D2 T2.2 applied use-case
S: A Schedule Maintenance Action takes a date parameter. Users sometimes pick dates in the past or on public holidays, causing rework. How should the Action handle this?
A: Accept any date and let the maintenance team reschedule invalid bookings by phone after they notice them
B: Limit the date to future dates and validate against a holiday reference at submission
C: Remove the date parameter and schedule all maintenance for the first day of the next month
D: Add a note under the date field asking users not to choose holidays or past dates
K: B
G: ## Validate close to the user and at execution
The exam guide's safe-UX guidance: validate close to the user and again at execution.
## Configuration
- Form: date picker limited to future dates.
- Submission criteria: date not in the holiday reference data.
- Message naming the problem.
Example: choosing 25 December shows "Maintenance cannot be scheduled on public holidays."
W: Form constraints plus execution-time validation against reference data: invalid dates are prevented with a helpful message.
X: A=Accept anything: the maintenance team absorbs rework for errors the Action could have prevented at submission.
C=Fixed date for everything: removes legitimate scheduling flexibility to avoid a validation problem.
D=Note under the field: users skim notes, and nothing stops an invalid date from being submitted.
T: Constrain inputs in the form and validate rules again at execution.

@ PLTR-APD D2 T2.4 applied troubleshooting
S: An Action works when tested by the developer on a branch, but after merge it fails for all users with a validation error referencing a property that exists only on the branch. What went wrong?
A: The platform deleted the property during the merge as part of its normal cleanup of branch resources
B: The Action merged before the Ontology change adding the property it uses
C: Users lack a special permission that only the developer has for properties created on branches
D: Branch testing is unreliable, so Actions should be tested directly in production instead
K: B
G: ## Merge dependent changes together
The exam guide lists branches among testing tools for Actions. Changes that depend on each other must be released together.
## Fix
- Merge the Ontology change with the Action, or revert the Action until the property exists.
- Release checklist: dependencies merged together.
Example: the property and Action merge together; the Action succeeds for users.
W: The Action and the Ontology change it depends on were released separately: merging them together resolves it and prevents a repeat.
X: A=Platform cleanup: properties are not deleted by merges; this one was never merged.
C=Special permission: the error is a missing property, not a permission denial.
D=Test in production: the branch test was valid; the release step was incomplete.
T: Merge Actions together with the Ontology changes they depend on.
V: Action types, branches

@ PLTR-APD D2 T2.1 applied comparison
S: Which requirement can be met with a declarative Action rather than a function-backed one?
A: Set an Incident's status to Resolved and record the resolver and time
B: Close an Incident and recompute the SLA breach flag from the incident's timeline of linked events
C: Resolve an Incident and close all of its linked child tasks, cascading through several levels of links
D: Resolve an Incident and calculate a penalty amount based on contract terms stored on a linked Contract
K: A
G: ## Declarative for direct edits
The exam guide recommends declarative rules for direct, governed edits and function-backed Actions for computation, branching or cascading changes.
- Setting properties from parameters and context: declarative.
- Recomputing flags, cascading through links, contract-based calculations: function-backed.
Example: the Resolve Action sets status, resolved_by and resolved_at with no code.
W: Setting properties from parameters and the current user is a direct edit that declarative rules handle simply and safely.
X: B=Recompute SLA from linked events: computation over linked objects needs a function.
C=Cascading closure: multi-level edits across links need logic.
D=Penalty calculation from contract terms: computation needs a function.
T: Use declarative Actions for direct property edits; reserve functions for computation and cascades.
V: Action types

@ PLTR-APD D2 T2.3 applied use-case
S: An Action lets agents issue goodwill credits. Agents may issue up to 50; team leads up to 500; above that requires finance. How should this be implemented?
A: One Action available to everyone, with a note in the form explaining the credit limits that apply to each role
B: Criteria comparing the amount with the user's role limit, plus an approval path above 500
C: Three separate Actions with no limits, and trust that people use the one matching their role
D: Let anyone issue any amount and have finance audit the credits once a quarter
K: B
G: ## Role-based limits in criteria
The exam guide lists submission criteria and independent security layers among Action configuration.
## Design
- Criteria: amount ≤ limit derived from the user's group (agent, lead).
- Above 500: create an approval request for finance instead of applying.
- Audit of all credits.
Example: an agent entering 120 is told "Limit 50 for agents; request a lead's approval."
W: Criteria tied to the user's role plus an approval path: limits are enforced for every submission while larger credits still have a route.
X: A=Note in the form: limits are stated but not enforced; any agent can issue any amount.
C=Three unlimited Actions: nothing stops a user from picking the wrong one.
D=Quarterly audit: excessive credits are paid out before anyone notices.
T: Enforce role-based limits with submission criteria and route exceptions to approval.

@ PLTR-APD D2 T2.2 applied troubleshooting
S: A webhook configured on an Action posts to an external system. Users report that the Action succeeds but the external system sometimes has no record. Execution evidence shows occasional webhook errors that users never see. What should change?
A: Nothing, since the Action succeeded and the external system is not the developer's responsibility
B: Surface webhook failures with status and alerts, retry idempotently, and allow resending
C: Remove the webhook and ask users to update the external system manually after every Action
D: Make the Action fail whenever the webhook fails, even if the Ontology change is already valid
K: B
G: ## Visible, recoverable side effects
The exam guide asks you to check failure visibility, retries and idempotency for side effects and integrations.
## Changes
- Status on the object: synced or failed.
- Retries with idempotency keys for transient errors.
- Alerts to owners; a resend option.
Example: a failed post shows "sync failed"; the owner resends after the external outage.
W: Make webhook failures visible and recoverable with safe retries: no silent gaps between the platform and the external system.
X: A=Not our responsibility: silent failures leave the two systems inconsistent and nobody knows.
C=Manual updates: users repeat every change by hand in the external system, doubling work and creating mismatches.
D=Fail the Action: blocks valid internal changes because an external system was briefly unavailable.
T: Make Action side effects visible, retryable and recoverable.
V: Action types, webhooks

@ PLTR-APD D2 T2.4 applied use-case
S: An auditor asks the team to prove that a specific Approve Payment Action was executed by an authorized user with valid inputs last March. What evidence should the developer provide?
A: A written statement from the team confirming that the Action has always worked correctly since the day it was released
B: Execution history (user, time, inputs, outcome) plus the permissions and criteria then
C: A screenshot of the current Action configuration taken today
D: The source code of the Workshop module that displays the Approve button
K: B
G: ## Execution evidence
The exam guide lists execution evidence among tools for Actions and asks you to reason about auditability.
## Evidence
- Execution record: who, when, parameters, result.
- Configuration history: permissions and criteria at that date.
- Object state before and after.
Example: the record shows approver A. Lee, 14 March, amount 3,200, criteria passed under version 6.
W: Execution history combined with the configuration in force at the time: the auditor can verify who did what under which rules.
X: A=Team statement: an assertion from the people being audited, with no record of who ran the Action or with what inputs.
C=Current screenshot: today's configuration may differ from March.
D=Module source: shows the button, not the execution or its authorization.
T: Prove Action executions with execution history and the configuration in force at the time.

@ PLTR-APD D2 T2.1 applied tradeoff
S: An Action creates a Booking and must also reserve inventory on a linked Product. Occasionally two users book the last unit at the same time, and both succeed, overselling. What design addresses this?
A: Ask users to check inventory in a separate screen before booking and trust them to notice the last unit
B: A function-backed Action checking availability and reserving atomically, failing on conflict
C: Allow overselling and reconcile with customers by email at the end of the week
D: Restrict booking to one user per day so that conflicts cannot happen
K: B
G: ## Concurrency in Actions
The exam guide asks you to reason about validation, preconditions, atomicity and concurrency.
## Design
- Function reads available quantity and returns booking plus inventory decrement together.
- Precondition at execution: quantity > 0; conflicting concurrent edits rejected.
- User sees "no longer available" on conflict.
Example: two users try to book the last unit; one succeeds and the other sees a clear message.
W: Atomic check-and-reserve with execution-time preconditions: concurrent bookings cannot oversell, and the losing user gets a clear message.
X: A=Users check manually: two users can still see one unit at the same moment.
C=Allow overselling: customers are promised items that do not exist, followed by weekly apologies and manual cleanup.
D=One user per day: absurd restriction that destroys throughput.
T: Combine availability checks and reservations atomically in function-backed Actions.
V: Action types, Functions

@ PLTR-APD D2 T2.3 advanced troubleshooting
S: After a reorganization, an entire team cannot run the Close Case Action they used yesterday. They can still view cases. No one changed the Action. What is the most likely cause and the correct fix?
A: The Action has a daily usage quota that the team exhausted yesterday, so they must wait until tomorrow
B: Their group membership changed and no longer matches the Action's permitted groups
C: The cases became read-only for everyone overnight, so nobody in the company can close them
D: Grant the team administrator rights on the project so that they can run any Action
K: B
G: ## Group changes and Action permissions
The exam guide asks you to identify the exact permission involved and avoid over-permissioning.
## Steps
- Compare the team's current groups with the Action's permitted groups.
- Restore the right membership or update the Action's permissions intentionally.
- Verify with one affected user.
Example: the team moved from "Support-EU" to "Support-Europe"; the Action listed only the old group.
W: A group change removed the team from the Action's permitted set: fixing membership or the permission restores access precisely.
X: A=Daily quota: Actions have no such per-team daily quota that matches this pattern.
C=Read-only for everyone: other teams can still close cases today, so the cases have not become read-only.
D=Administrator rights: over-permissioning that ignores the cause.
T: When teams lose Action access after reorganizations, check group membership against Action permissions.
V: Action types, permissions
