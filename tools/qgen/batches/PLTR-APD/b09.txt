# PLTR-APD batch 09: Domain 8 round 1 (Application Security, Governance, and Operations), 8 questions

@ PLTR-APD D8 T8.2 applied troubleshooting
S: A user can open a Workshop application but every table in it is empty, while colleagues see data. The user has Viewer on the application's project. What does the exam guide's distinction between application access and data access suggest?
A: Viewer on the application project automatically grants read access to all data the application displays, so the platform is malfunctioning
B: Opening the app differs from reading its data; check the user's access to the object types and backing data
C: The user's screen resolution is too low to display table rows, so the tables appear empty on their device only
D: The application must be republished every time a new user is added so that their tables populate
K: B
G: ## Application access versus data access
The exam guide asks you to separate application/resource access from data access. A user can open the module and still lack permission to read what it shows.
## Checks
- Object type and backing data permissions for this user.
- Markings, restricted view policies and project roles on the data.
- Grant the specific missing access if appropriate; avoid over-permissioning the application.
Example: the data lives in a project the user has no role on; the data owner grants Viewer to the user's team.
W: Resource access and data access are separate: the user passes the first and fails the second, which is exactly why the tables are empty.
X: A=Viewer grants everything: project roles on the app's project do not grant access to data held elsewhere or protected by markings.
C=Screen resolution: the tables have no rows for this user regardless of the device or display used.
D=Republish per user: publishing does not change who may read the underlying data.
T: Separate the ability to open an application from the ability to read its data, and fix the exact data permission.
V: permissions, Workshop

@ PLTR-APD D8 T8.1 applied use-case
S: An application's Actions and Functions are developed by a small team, and production changes must be reviewed before release. Which control enforces this?
A: A written team agreement that developers will always ask a colleague for review before merging, with no technical enforcement
B: Branch protection requiring approval before changes merge into the production branch
C: Giving only one developer Editor rights so that nobody else can make changes at all
D: A monthly audit that reverts any unreviewed change found in production
K: B
G: ## Branch protection
The exam guide lists branch protection among security and governance controls for applications.
## Configuration
- Developers work on branches.
- Protected main: merges require approval.
- Review checklist includes permissions and validation changes.
Example: a developer's Action change waits for approval; the reviewer spots a removed validation rule before merge.
W: Protected branches with required approval: review is enforced by the platform rather than by memory.
X: A=Agreement only: easy to skip under pressure; nothing prevents an unreviewed merge.
C=One editor: a bottleneck that still lacks review of that person's changes.
D=Monthly audit: unreviewed changes run in production for up to a month before being found.
T: Enforce review of production changes with branch protection and required approvals.
V: branches

@ PLTR-APD D8 T8.3 applied use-case
S: An Action must create records in a restricted Audit object type that ordinary users cannot edit directly, while the Action itself is available to all users. How can this be designed safely?
A: Give all users edit permission on the Audit object type so that the Action can write audit records on their behalf
B: A function-backed Action that writes under a scoped service identity, which users may only invoke
C: Ask users to email the audit details to an administrator who creates the records manually
D: Store audit records in a free-text property on each user's profile instead
K: B
G: ## Elevated execution for controlled writes
The exam guide asks you to understand user-scoped versus project-scoped execution and service identities, and to separate user permissions from execution identity.
## Design
- Action invocable by all users.
- Execution identity with write permission on Audit objects only.
- Validation on inputs; audit of invocations.
Example: users record events through the Action; nobody can edit Audit objects directly.
W: A scoped execution identity behind an invocable Action: users trigger controlled writes without receiving direct edit rights on the restricted type.
X: A=Edit for all: users could alter or delete audit records directly, defeating their purpose.
C=Email an administrator: slow, error-prone and unaudited until someone transcribes it.
D=Profile text: unstructured, editable by the user and not an audit trail.
T: Use scoped execution identities behind Actions for writes users must not perform directly.
V: Action types, permissions

@ PLTR-APD D8 T8.4 applied troubleshooting
S: Users report that an application occasionally shows outdated object values for up to an hour after data updates. Actions and builds succeed. What operational signal should the developer check?
A: The users' internet connection speed, since outdated values in applications usually come from slow or unstable networks
B: Ontology indexing health and latency for the object type, since built data must be indexed before apps show it
C: The Workshop module's colour theme, which can cache values when certain themes are used
D: The number of users online, since busy periods always produce outdated values
K: B
G: ## Indexing between data and application
The exam guide lists monitoring Ontology and indexing health among operational responsibilities. A build can succeed while indexing lags.
## Checks
- Indexing status and latency for the object type.
- Failed or delayed index jobs; size changes that slowed indexing.
- Alerting on indexing lag.
Example: a schema change triggered a full reindex taking an hour; the team schedules such changes off-peak and monitors lag.
W: Ontology indexing health: the layer between a successful build and what the application shows, and the place where an hour of lag appears.
X: A=Network speed: a slow network delays loading, not the age of the values once loaded.
C=Colour theme: a visual theme has no effect on which data the application loads or how fresh that data is.
D=Users online: load does not explain values that are an hour old after successful builds.
T: When applications lag behind successful builds, check Ontology indexing health and latency.
V: Ontology Manager, monitoring

@ PLTR-APD D8 T8.1 applied comparison
S: Which control is appropriate for ensuring that only users in the "EMEA" region see EMEA customer rows in an application's table?
A: A Workshop filter defaulting to EMEA that users can change to other regions whenever they need to see more rows
B: A row-level control on the data (restricted view or object security policy) on the user's region
C: A marking named EMEA applied to the whole customer dataset
D: A note above the table asking non-EMEA users not to look at EMEA rows
K: B
G: ## Row-level controls on data
The exam guide lists restricted views and governance controls for application security. Row visibility by user attribute is a data-level policy, not a UI default.
- Restricted view or object security policy: rows filtered by region attribute for every access path.
- A marking applies to the whole dataset, not to rows.
Example: an EMEA user sees 4,000 rows; an APAC user sees none of them in any application.
W: A row-level policy on the data: enforced for every application and tool, matching rows to the user's region.
X: A=Workshop filter: a UI default that users can change, and other tools ignore it entirely.
C=Marking on the dataset: all-or-nothing access, not row selection.
D=Note: a request on the screen enforces nothing; non-EMEA users still see every EMEA row.
T: Enforce row visibility with data-level policies, not application filters.
V: restricted views, permissions

@ PLTR-APD D8 T8.4 applied use-case
S: A team operates an application with Actions, Functions and automations. They want early warning of problems before users report them. What should they monitor?
A: Only the number of users who opened the application each day, which shows whether the application is working as intended
B: Action failures, Function errors and latency, automation failures, indexing lag and AIP health, alerted to owners
C: The application's page title and logo, which change when something goes wrong
D: Nothing, since users will report problems quickly if anything breaks
K: B
G: ## Operational monitoring for applications
The exam guide asks you to monitor application, Ontology, automation, indexing and AIP health and use lineage and access tools to investigate.
## Signals
- Action outcomes and rejection reasons.
- Function errors and latency.
- Automation failures and retries.
- Indexing lag; AIP latency and cost.
- Alerts to the owning team.
Example: a spike in Action rejections after a data change alerts the team an hour before the first complaint.
W: Monitor each component's health with routed alerts: problems are visible to the owners before users have to report them.
X: A=Daily opens: usage says nothing about failures within sessions.
C=Title and logo: static branding does not change when Actions, Functions or automations fail behind it.
D=Wait for users: reports arrive late and incomplete, after users have already been blocked or misled.
T: Monitor Actions, Functions, automations, indexing and AI health with alerts to owners.
V: monitoring, Automate

@ PLTR-APD D8 T8.2 applied tradeoff
S: To fix a user's access error in an application quickly, a colleague suggests granting the user Owner on every project the application touches. What does the exam guide recommend instead?
A: Accept the suggestion, since unblocking the user quickly matters more than least privilege when work is waiting
B: Identify the exact failing permission or control and change only that, rather than over-permissioning
C: Remove all permissions from the application so that every user has the same experience
D: Create a new shared account with Owner rights that blocked users can borrow
K: B
G: ## Fix the exact control
The exam guide's self-check: identify the exact permission or governance control that should change without solving an access problem by over-permissioning.
## Approach
- Reproduce as the user; check the failing layer (role, marking, view, Action permission).
- Change that one control through the right owner.
Example: the user lacked one marking; the data owner approves membership; no broad role is granted.
W: Precise diagnosis and a targeted change: the user is unblocked while least privilege holds everywhere else.
X: A=Owner everywhere: grants delete and admin rights on unrelated resources.
C=Remove permissions: makes the application unusable for every user instead of fixing one user's access.
D=Shared account: actions can no longer be attributed to individuals, destroying identity and the audit trail.
T: Resolve access errors by changing the exact failing control, never by broad grants.
V: permissions

@ PLTR-APD D8 T8.3 advanced troubleshooting
S: A scheduled automation that updates Order objects began failing after its original creator left the company. Nothing else changed. What is the likely cause and the durable fix?
A: The automation expired automatically because it was older than one year, and it must be recreated once every year
B: It ran as the creator, whose access ended; move it to a team-owned, scoped service identity
C: The Order object type was locked when the user left and must be unlocked by support
D: Give the departed user's account back its permissions so that the automation keeps working
K: B
G: ## Execution identity outlives people
The exam guide asks you to understand service identities and separate user permissions from execution identity.
## Fix
- Diagnose: the automation's execution identity was a personal account now deactivated.
- Move execution to a service identity with only the needed permissions.
- Ownership: a team; alerts routed to it.
Example: the automation runs again under `svc-orders-automation` with write access to Order only.
W: Replace the personal execution identity with a scoped, team-owned service identity: the automation no longer depends on any one person's employment.
X: A=Annual expiry: the failure coincides with the departure, not with an age limit.
C=Locked object type: object types are not locked when users leave.
D=Restore a departed user's access: keeps an orphaned account active, which is a security risk.
T: Run production automations under scoped service identities owned by teams, not personal accounts.
V: Automate, permissions
