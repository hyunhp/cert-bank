# PLTR-APD batch 30: Domain 5 round 4 (OSDK, APIs, and External Applications), 8 questions

@ PLTR-APD D5 T5.1 applied use-case
S: A team is registering a new external application that will read Products and invoke a Create Quote Action for signed-in sales staff. Which registration settings matter most for security?
A: Request every scope available in the Ontology so that future features never require changes to the application's registration
B: User-based OAuth, scopes limited to Products and Create Quote, and exact redirect URLs per environment
C: A shared service secret embedded in the app so that sales staff do not have to sign in each time they use it
D: No registration at all; call the Ontology anonymously from the browser to keep the setup simple
K: B
G: ## Registration basics
The exam guide covers registering applications, configuring OAuth and scoping Ontology resources.
## Settings
- Flow: user-based OAuth so staff act as themselves.
- Scopes: Products (read), Create Quote (Action).
- Redirect URLs: exact values for development and production.
Example: a quote created in the app is attributed to the salesperson who submitted it.
W: User-based OAuth with minimal scopes and exact redirects: staff act under their own permissions and the app can reach only what it needs.
X: A=Every scope: over-scoping that turns any app compromise into broad exposure of unrelated data.
C=Shared embedded secret: extractable from the app and removes per-user attribution of every quote.
D=Anonymous calls: unauthenticated access is not supported and would expose data and Actions to anyone.
T: Register OSDK apps with the right auth flow, minimal scopes and exact redirect URLs.
V: OSDK, Developer Console

@ PLTR-APD D5 T5.3 applied troubleshooting
S: An external app invokes an Approve Order Action through the OSDK. Some calls fail with a validation error that the Workshop version of the same Action shows to users as a friendly message. External users see a generic "error" instead. What should the developer do?
A: Remove the Action's validation so that external calls never fail with validation errors
B: Show users the Action's specific validation message instead of a generic error
C: Retry the Action automatically until the validation passes
D: Call the Action twice to increase the chance of success
K: B
G: ## Surface validation results
The exam guide asks you to distinguish invalid input, denied access, transient failure and completed work, and to invoke Actions via the OSDK.
## Change
- Inspect the Action's response for validation failures.
- Show the criterion's message to the user.
- Treat validation failures differently from transient errors.
Example: "Order cannot be approved: payment not received" appears in the external app.
W: Surface the Action's validation messages: users understand why the request was refused and what to change.
X: A=Remove validation: lets invalid approvals through to make errors disappear.
C=Automatic retries: validation fails deterministically; retrying changes nothing.
D=Call twice: same validation, same result, plus duplicate traffic.
T: Present Action validation failures from OSDK calls as specific user messages, not generic errors.
V: OSDK, Action types

@ PLTR-APD D5 T5.2 applied comparison
S: Which statement about user-based and service-based authentication for OSDK applications is correct?
A: Service-based authentication should always be preferred because it never requires users to sign in to anything
B: User-based auth applies each user's permissions; service-based suits headless processes
C: User-based authentication requires embedding a client secret in the browser to work properly
D: Service-based and user-based authentication give identical access results for every user
K: B
G: ## Choosing the auth model
The exam guide asks you to choose user-based or service-based authentication without exposing secrets.
- User-based: each user's permissions and audit attribution.
- Service-based: no user present; minimal scope; secret kept server-side.
Example: a dashboard uses user-based auth; a nightly sync uses service-based auth.
W: User-based for people acting as themselves and service-based for headless processes: the correct division of roles.
X: A=Always service-based: everyone would share one identity and its permissions, losing attribution.
C=Secret in the browser for user-based: user-based OAuth does not require embedding confidential secrets in the client.
D=Identical results: a service identity's permissions differ from each user's.
T: Use user-based auth for people and service-based auth for headless processes.
V: OSDK

@ PLTR-APD D5 T5.4 applied troubleshooting
S: An external app was working until a new OSDK package version was installed. Now some object fields come back undefined. The developer did not change the code. What is likely and what should be done?
A: The Ontology lost data during the package upgrade, so the data team must restore it from backups
B: The new package reflects a changed Ontology; review the types, update the code, and pin versions
C: The OSDK randomly drops fields on new installs, so the app should be reinstalled until the fields return
D: The users' browsers need clearing; undefined fields are always a caching problem
K: B
G: ## SDK changes reflect Ontology changes
The exam guide lists stale SDK packages and regeneration among OSDK diagnostics.
## Steps
- Compare old and new generated types.
- Update code for renamed or removed properties.
- Pin package versions and upgrade deliberately; coordinate with Ontology owners.
Example: `phoneNumber` became `primaryPhone`; the compiler highlights every use after enabling strict types.
W: The regenerated package follows a changed Ontology: reviewing types and updating code restores the fields, and pinning prevents surprises.
X: A=Data loss: the data exists; the field names in the package changed.
C=Random drops: generated field mappings are deterministic; the same field is undefined on every call, which points to a renamed property.
D=Browser caching: the problem is the code reading fields that no longer exist under those names.
T: Review generated type changes after OSDK upgrades and pin package versions.
V: OSDK

@ PLTR-APD D5 T5.3 applied use-case
S: An external dashboard needs to show, every few seconds, the count of open alerts per site for 500 sites. What is the most efficient approach?
A: Fetch every alert object every few seconds and count the open alerts for each site in the user's browser
B: A grouped aggregation (count of open alerts by site) on a sensible refresh interval, with caching
C: Call the API once per site every few seconds, making 500 requests each time
D: Export alerts to a file every minute and have the dashboard parse it
K: B
G: ## Efficient repeated reads
The exam guide lists aggregating and rate limits among OSDK skills.
## Approach
- One grouped aggregation per refresh.
- Refresh interval matched to need (for example 15 seconds).
- Cache between refreshes.
Example: 500 site counts arrive in one response every 15 seconds.
W: One aggregation per refresh at a sensible interval: current counts without exhausting rate limits.
X: A=Fetch every alert: transfers thousands of objects repeatedly and counts them in the browser.
C=500 requests per refresh: thousands of calls a minute quickly hit rate limits and make the dashboard slower, not faster.
D=File export each minute: the dashboard shows data up to a minute old from files that sit outside the platform's permissions.
T: Use grouped aggregations at sensible intervals for frequently refreshed external dashboards.
V: OSDK

@ PLTR-APD D5 T5.1 applied tradeoff
S: An internal team asks whether to build a new approval tool in Workshop or as a custom web app with the OSDK. Users are internal, the UI is forms and tables, and the team has little front-end experience. What should guide the choice?
A: Always build a custom web app, since custom apps are more professional than native tools
B: Prefer Workshop when it meets an internal forms-and-tables need; use the OSDK for custom needs
C: Build both and let users vote on which one they prefer after a month
D: Use neither and keep approvals in email
K: B
G: ## Fit the tool to the requirement
The exam guide asks you to choose Workshop, OSDK or a hybrid and justify it.
## Reasoning
- Internal users, standard UI: Workshop's strengths.
- Little front-end experience: custom apps add risk and maintenance.
- OSDK when Workshop cannot meet UX or audience needs.
Example: the approval tool ships in Workshop in days; a later customer portal uses the OSDK.
W: Choose Workshop when it meets an internal, standard-UI need: less code, faster delivery and native governance.
X: A=Always custom: adds build, hosting and maintenance without a requirement that needs it.
C=Build both: doubles the build and maintenance effort and leaves users unsure which tool is the real one.
D=Email approvals: decisions happen outside the platform with no validation, permissions or audit trail.
T: Prefer Workshop for internal standard UIs and use the OSDK when requirements demand it.
V: Workshop, OSDK

@ PLTR-APD D5 T5.4 applied use-case
S: An external app's calls fail intermittently with rate-limit errors during a nightly import that loops over 50,000 objects and calls an Action for each. What change best fits?
A: Remove all delays from the import loop so that it finishes faster before rate limits apply
B: Batch where possible, pace calls with backoff, and make Action calls idempotent
C: Split the import across many separately registered applications to multiply the rate limit
D: Run the import during business hours when more capacity is available
K: B
G: ## Bulk operations within limits
The exam guide lists rate limits among OSDK diagnostics and idempotency among safe-retry practices.
## Changes
- Batch requests where the API supports it.
- Pace calls; exponential backoff with jitter on rate-limit responses.
- Idempotent Actions so retries are safe.
Example: the import completes in 90 minutes with no failures, retrying a few throttled calls safely.
W: Batching, pacing and idempotent retries: the import finishes reliably within the platform's limits.
X: A=No delays: increases the request rate and triggers more rate-limit errors.
C=Many applications: circumvents limits instead of respecting them and complicates governance.
D=Business hours: competes with users and has no basis in how limits work.
T: Batch, pace and retry idempotently for bulk OSDK operations.
V: OSDK, Action types

@ PLTR-APD D5 T5.2 advanced use-case
S: A partner integration currently uses a long-lived service secret that was emailed to the partner two years ago and never rotated. The security team asks for remediation. What is the right plan?
A: Leave the secret in place since nothing bad has happened in two years
B: Issue a new scoped credential securely, migrate the partner, revoke the old secret, and rotate it
C: Email the same long-lived secret again to the partner's new technical contact so that they also have it on file
D: Disable the integration permanently since secrets are inherently insecure
K: B
G: ## Credential hygiene
The exam guide asks you to choose authentication without exposing secrets and diagnose authentication issues.
## Plan
- New credential with minimal scope, delivered securely.
- Partner switches; old secret revoked.
- Rotation schedule and usage monitoring.
Example: the new client has read access to two object types only; the old one is revoked a week later.
W: Re-issue, migrate, revoke and rotate with monitoring: the exposure is closed and future risk is controlled.
X: A=Leave it: a two-year-old secret sent by email may already be compromised.
C=Email again: sends the same long-lived secret through the same insecure channel, repeating the original exposure.
D=Disable permanently: breaks a legitimate integration instead of securing it.
T: Rotate and minimally scope service credentials, and deliver them securely.
V: OSDK, Developer Console
