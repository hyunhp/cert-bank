@ PLTR-APD D3 T3.2 applied use-case
S: A function must compute, for a selected supplier, the average delivery delay over the last 12 months from up to 50,000 Delivery objects. Which implementation fits?
A: Load all 50,000 Delivery objects into the function, compute each delay in a loop, and average the results in memory
B: Filter the supplier's deliveries to the last 12 months server-side and use an aggregation to compute the average delay
C: Return all deliveries to Workshop and let a chart widget compute the average delay in the browser on every load
D: Ask the procurement analyst to export the deliveries and compute the average in a spreadsheet each month
K: B
G: ## Aggregate where the data lives
The exam guide lists filtering and aggregating among function skills.
## Implementation
- Filter: supplier and date range.
- Aggregate: average of delay (stored or derived property).
Example: the average returns in under a second for the largest supplier.
W: Server-side filtering and aggregation: the average is computed efficiently no matter how many deliveries a supplier has.
X: A=Load all into memory: work grows with each delivery and risks timeouts for the largest suppliers.
C=Browser calculation: moves tens of thousands of objects to the client to produce one number.
D=Monthly spreadsheet: manual, stale and outside the platform.
T: Use server-side aggregations for statistics over large linked object sets.

@ PLTR-APD D3 T3.4 applied troubleshooting
S: A function returns a wrong total for orders containing discounted items. Tests pass because they only contain full-price items. What should the developer do?
A: Apply a fixed correction to the total whenever an order contains any discounted items
B: Add tests with discounted and mixed items, fix the calculation, and verify against known totals
C: Remove discounted items from the total entirely to avoid the error
D: Ask finance to adjust totals manually for discounted orders
K: B
G: ## Tests must cover real cases
The exam guide asks you to test functions and diagnose failures.
## Steps
- Reproduce with a discounted order.
- Add tests: discounts, zero price, mixed baskets.
- Fix; confirm against reference totals.
Example: the bug applied the discount twice; the new test catches it and the fix passes all cases.
W: Expand tests to the failing cases, then fix and verify: the bug is removed and similar regressions are caught later.
X: A=Fixed correction: a fudge that is wrong for every order whose discount differs from the assumed amount.
C=Remove discounted items: makes totals wrong in a different way.
D=Manual adjustments: finance repeats corrections for every discounted order to compensate for a fixable code defect.
T: Add tests for the inputs that fail before fixing function logic.

@ PLTR-APD D3 T3.1 applied comparison
S: Which requirement most clearly calls for TypeScript v2 over AIP Logic?
A: Writing a friendly, personalized message to a customer explaining the reasons for their delayed shipment
B: Validating weight limits and computing the exact fee from a rate table
C: Summarizing a long customer complaint into three sentences
D: Classifying free-text feedback into themes
K: B
G: ## Exact rules belong in code
The exam guide asks you to choose a paradigm by determinism and LLM needs.
- Limits and rate-table fees: exact, deterministic code.
- Messages, summaries, classification of text: AI-suited.
Example: a 32 kg parcel to zone 4 always costs the same calculated fee.
W: Exact validation and fee calculation need deterministic code, which is what TypeScript v2 provides.
X: A=Personalized message: writing friendly, situation-specific text is language generation, which suits AIP Logic.
C=Summarizing a complaint: language understanding suits AIP Logic.
D=Theme classification of free text: interpretation suits AIP Logic.
T: Use code for exact rules and calculations; use AIP Logic for language tasks.
V: Functions, AIP Logic

@ PLTR-APD D3 T3.3 applied use-case
S: A function used by an Action is about to change its rounding rule. Past results must remain reproducible for audit. What should the team do?
A: Change the rounding in place and update all stored results to the new rule so that everything is consistent
B: Publish a new version, keep the old one available, and record the version per result
C: Keep the old rule forever so that results never change
D: Delete old results so that only new-rule values exist
K: B
G: ## Versioning for reproducibility
The exam guide lists versioning and provenance among function concepts.
## Approach
- New version with the new rule.
- Old version retained.
- Version recorded with each result.
Example: an auditor reproduces a March figure using v3 even though v4 is current.
W: New versions with recorded provenance: past results remain explainable while new results use the new rule.
X: A=Rewrite stored results: changes historical figures that were correct under the rule in force.
C=Old rule forever: blocks a legitimate business change just to keep past results reproducible, which versioning achieves anyway.
D=Delete old results: destroys the audit history the requirement says must remain reproducible.
T: Version functions and record versions so past results stay reproducible.

@ PLTR-APD D3 T3.2 applied troubleshooting
S: A function edits objects in a loop and sometimes fails halfway, leaving some objects updated and others not. It is called from an Action. What design change ensures consistency?
A: Wrap each edit in its own Action call so that each object is updated independently and failures only affect one object
B: Have the function return all edits together for the Action to apply in one submission, validating inputs first
C: Add a retry loop around each edit inside the function
D: Ask users to check which objects were updated and fix the rest by hand
K: B
G: ## Edits applied together
The exam guide asks about atomicity and safe edits in function-backed Actions.
## Change
- Compute and validate first.
- Return all edits; the Action applies them together.
Example: a failure during computation means no objects change, not half of them.
W: Returning all edits for one Action submission: the change is applied completely or not at all.
X: A=Separate Action calls: makes partial completion the normal outcome.
C=Retries per edit: can still fail halfway and may duplicate effects.
D=Manual fixes: users must find which objects changed and repair the rest by hand, which is unreliable.
T: Return all edits from function-backed Actions so they apply together.

@ PLTR-APD D3 T3.4 applied use-case
S: A team needs to diagnose why a function is slow for some inputs. What evidence is most useful?
A: The function's source code line count, since longer functions are always slower
B: Execution traces and timings showing which steps are slow for which inputs
C: User complaints describing how slow the function feels
D: The time of day when the developer last edited the function
K: B
G: ## Diagnose with execution evidence
The exam guide asks you to test and diagnose functions using execution evidence.
## Evidence
- Per-call timings and query details.
- Inputs associated with slow calls.
Example: slow calls all involve customers with over 10,000 orders; the order traversal is the bottleneck.
W: Traces and timings tied to inputs: the slow step and the inputs that trigger it are identified directly.
X: A=Line count: a short function can be slow and a long one fast; length says nothing about where time is spent.
C=Complaints: tell the team that something feels slow, not which step or which inputs cause it.
D=Edit time: when the developer last edited the function has no bearing on why certain inputs are slow.
T: Diagnose slow functions with execution traces and timing per input.

@ PLTR-APD D3 T3.3 applied comparison
S: Which statement about calling an Ontology function from an external application is correct?
A: External applications call functions by copying their source code into the application
B: They call published functions through generated OSDK bindings reflecting types and versions
C: Functions cannot be called from outside the platform under any circumstances
D: External applications should call functions by scraping the Workshop module that uses them
K: B
G: ## SDK bindings for functions
The exam guide lists generated SDK bindings among function concepts.
- Published functions exposed through the OSDK.
- Types and versions reflected in bindings.
Example: an external app calls `estimateCost` with typed inputs and receives a typed result.
W: Generated OSDK bindings expose published functions with their types: external apps call them safely and stay in sync through regeneration.
X: A=Copy source code: duplicates the logic outside the platform, where it drifts from the published version.
C=Never callable: published functions are exposed to external applications through the OSDK.
D=Scraping Workshop: breaks whenever the module's layout changes and bypasses the supported interface.
T: Call functions from external apps through generated OSDK bindings.

@ PLTR-APD D3 T3.1 advanced use-case
S: A function must validate insurance claims against 30 explicit policy rules and also flag claims whose free-text description seems inconsistent with the claimed damage. Which design fits?
A: Put all 30 rules and the consistency check into one AIP Logic prompt and let the model decide
B: Implement the 30 rules in code, and use AIP Logic only for the consistency check
C: Implement everything in code, including the consistency check, using keyword matching on the description
D: Have adjusters apply all rules and checks manually
K: B
G: ## Rules in code, interpretation in AI
The exam guide asks when AI adds value over deterministic logic.
## Design
- 30 rules: deterministic, tested function.
- Consistency check: AIP Logic with typed output (consistent / inconsistent / unsure) and reasons.
- Inconsistent or unsure claims routed to adjusters.
Example: a claim for hail damage with a description of a burst pipe is flagged for review.
W: Deterministic rules plus AI for interpretation: exact rule checks and useful flagging of textual inconsistencies.
X: A=All in a prompt: the 30 explicit rules would be applied nondeterministically and could not be audited reliably.
C=Keyword matching: misses paraphrases and context, so most genuine inconsistencies in descriptions go unflagged.
D=Manual: adjusters applying 30 rules and reading every description by hand is slow and inconsistent at volume.
T: Combine deterministic rule checks with AI only for interpretation of free text.
V: Functions, AIP Logic
