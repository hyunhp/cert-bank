# PLTR-APD batch 14: Domain 5 round 2 (OSDK, APIs, and External Applications), 8 questions

@ PLTR-APD D5 T5.3 applied use-case
S: An external application must display a paginated list of 80,000 Supplier objects sorted by name, letting users page through 50 at a time. How should it fetch the data?
A: Fetch all 80,000 objects in one request when the application starts and keep them in the browser's memory for paging later
B: Use OSDK pagination with ordering by name, requesting one page of 50 at a time with the returned page token
C: Export all suppliers to a JSON file nightly and bundle it with the application's front-end code
D: Request each supplier individually by id, looping over a list of all 80,000 ids stored in the application
K: B
G: ## Paginate with the OSDK
The exam guide lists fetching and paginating among OSDK skills. Large result sets are read page by page with server-side ordering.
## Implementation
- Ordered query (name ascending), page size 50.
- Use the page token to fetch the next page.
- Optional filters applied server-side.
Example: the first page loads in 200 ms; later pages load as the user clicks through.
W: Server-ordered pagination with page tokens: the application loads only what the user is viewing, quickly and within limits.
X: A=Fetch everything at start: a slow first load, heavy memory use in the browser and data that grows stale during the session.
C=Nightly JSON in the bundle: stale data, no per-user permissions, and supplier data shipped to every browser that loads the app.
D=One request per id: 80,000 calls quickly hit rate limits and take far longer than paginated queries.
T: Use OSDK pagination with server-side ordering for large object lists.
V: OSDK

@ PLTR-APD D5 T5.1 applied troubleshooting
S: After an object type was added to an external application's features, the developer updated the code, but the build fails because the new type does not exist in the SDK. What step was missed?
A: The object type must be manually copied into the application's source code as a hand-written TypeScript interface
B: Add the object type to the application's scope and regenerate the OSDK package so the bindings include it
C: Restart the developer's laptop so that the SDK cache is cleared and the new type appears automatically
D: Rename the object type in the Ontology so that it matches the name used in the application code
K: B
G: ## Scope and generation go together
The exam guide lists scoping Ontology resources and generating or regenerating the OSDK among application setup steps.
## Steps
- Add the object type to the application's scope.
- Regenerate the OSDK package; update the dependency.
- Build and test.
Example: after regeneration, `Supplier` appears in the SDK and the build passes.
W: Scope plus regeneration: the SDK only contains resources the application is scoped to at generation time.
X: A=Hand-written interface: drifts from the Ontology and bypasses the generated, type-safe client entirely.
C=Restart the laptop: the SDK package itself lacks the type; a restart does not regenerate anything.
D=Rename the object type: changes the Ontology for every consumer to paper over a missing generation step.
T: When an OSDK lacks a resource, add it to the app's scope and regenerate the package.
V: OSDK, Developer Console

@ PLTR-APD D5 T5.2 applied troubleshooting
S: An internal OSDK application works for most employees, but one team receives authentication errors after signing in. Their accounts are in a different organization than the application's resources. What should be checked?
A: Whether the team's laptops have outdated operating systems that do not support OAuth sign-in flows
B: Whether the app is enabled for that organization's users and whether they may access its resources
C: Whether the team should share one colleague's account from the main organization to sign in instead
D: Whether the OAuth flow should be replaced with a hard-coded service secret in the application for all users
K: B
G: ## Organization boundaries and app access
The exam guide asks you to diagnose authentication failures and scope intersections, and lists organizations among governance controls.
## Checks
- Is the application enabled for users of the other organization?
- Do those users have access to the scoped resources?
- Resolve through proper cross-organization configuration, not shared credentials.
Example: the application was registered for one organization only; an administrator extends it after review.
W: Check the organization boundary for both the application and the resources: the failure follows the team's organization, not their devices.
X: A=Outdated operating systems: the same sign-in works for colleagues; the variable is the organization.
C=Shared account: destroys individual identity and audit, and bypasses the organization boundary improperly.
D=Hard-coded service secret: exposes a credential and removes per-user permissions for everyone.
T: When only one organization's users fail, check the application's availability and resource access across organizations.
V: OSDK, organizations

@ PLTR-APD D5 T5.3 applied comparison
S: Which task is best done by invoking an Action through the OSDK rather than writing data another way?
A: Reading a list of open tickets with their priorities to display in an external dashboard for the support team
B: Changing a ticket's status from an external application with validation and audit
C: Counting tickets per priority for a chart
D: Downloading ticket attachments for offline viewing
K: B
G: ## Writes through Actions
The exam guide lists invoking Actions among OSDK capabilities and separates reading from changing state.
- Reads and aggregations: queries.
- Status change: an Action, so validation, permissions and audit apply from any client.
Example: the external app calls `closeTicket` with the ticket id; criteria reject closing a ticket with open subtasks.
W: A governed state change from an external app should use an Action: the same rules apply as inside the platform.
X: A=Reading open tickets: a query; no state changes, so no Action is involved.
C=Counting per priority: an aggregation request that only reads data.
D=Downloading attachments: a read operation that does not change any object's state.
T: Use Actions through the OSDK for state changes; use queries for reads.
V: OSDK, Action types

@ PLTR-APD D5 T5.4 applied troubleshooting
S: A newly deployed external application cannot complete sign-in: after login, users are redirected to an error page. It worked on the developer's machine. What is the likely cause?
A: The production database is down, so sign-in cannot complete for any external application at all
B: The OAuth redirect URL registered for the application does not include the production URL; register it
C: Users are typing their passwords incorrectly only in production
D: The OSDK package is too large to load in production browsers
K: B
G: ## Deployment configuration for OAuth
The exam guide lists deployment issues among OSDK diagnostics. OAuth redirects must match registered URLs.
## Fix
- Add the production redirect URL to the application registration.
- Keep development and production URLs explicit.
- Retest sign-in.
Example: `https://portal.example.com/callback` is registered; logins succeed.
W: An unregistered production redirect URL: login completes at the provider but the redirect back is refused, exactly matching the symptom.
X: A=Database down: other applications sign in normally; the failure is specific to this app's redirect.
C=Wrong passwords: login succeeds; the failure happens on the way back to the application.
D=Package too large: a large bundle loads slowly but does not cause a post-login redirect error.
T: After deploying OSDK apps, register production redirect URLs for OAuth.
V: OSDK, Developer Console

@ PLTR-APD D5 T5.2 applied tradeoff
S: An internal tool runs in the background every hour to update statuses, and also has a screen where employees view results. How should authentication be split?
A: Use one service identity for both the background job and the screen, so employees see whatever the service sees
B: Service-based auth for the background job with minimal scope, and user-based auth for the screen
C: User-based authentication for both, requiring an employee to stay logged in for the background job to run each hour
D: No authentication for the screen, since it is internal and only employees can reach it
K: B
G: ## Match identity to the actor
The exam guide asks you to choose user-based or service-based authentication per need and separate user permissions from service identities.
- Background job: no user; service client scoped to the statuses it updates.
- Screen: employees act as themselves; permissions apply.
Example: an employee sees 40 of 300 records because the rest are outside their region.
W: Service identity for the headless job and user identity for the screen: each actor gets the right access and audit.
X: A=One service identity for both: employees would see everything the service can see, ignoring their own permissions.
C=User-based for the job: the job fails whenever that employee logs out or leaves.
D=No authentication: internal network access is not authorization; data would be exposed to anyone inside.
T: Use service identities for headless work and user identities for interactive screens.
V: OSDK

@ PLTR-APD D5 T5.1 applied use-case
S: A product team wants to embed a Foundry-backed view inside their existing customer-support web application rather than sending agents to a separate Foundry tab. What approach fits?
A: Recreate the entire Foundry view in the support app by copying data into the support app's own database every night
B: Use the OSDK (or embedding) to show the needed objects and Actions inside the support app
C: Ask agents to keep both applications open and copy case numbers between them manually
D: Send agents screenshots of the Foundry view by email when they need the information
K: B
G: ## Embedded and hybrid applications
The exam guide asks you to choose Workshop, OSDK or a hybrid for internal, external or embedded requirements.
## Approach
- OSDK in the support app: fetch the needed objects, invoke Actions.
- Authentication as the agent; scopes limited.
- Or embed a Workshop module where that suits the host app.
Example: the support app shows the customer's orders and a "Request refund" Action inside the existing case screen.
W: OSDK-based or embedded integration with proper authentication and scope: agents get Foundry data and Actions where they already work.
X: A=Nightly copy: stale data, duplicated storage and no access to governed Actions.
C=Two apps and manual copying: slow, error-prone and the context switching the team wants to avoid.
D=Emailed screenshots: static images that are outdated the moment they are sent and sit outside any access control.
T: Bring Foundry data and Actions into existing apps with the OSDK or embedding, not copies.
V: OSDK, Workshop

@ PLTR-APD D5 T5.4 advanced troubleshooting
S: An external application's calls intermittently fail with authorization errors about an hour after users sign in, then succeed after they sign in again. What is the likely cause and fix?
A: Users are being hacked every hour, so the application should be shut down until security investigates
B: Access tokens expire and the app does not refresh them; implement refresh and handle expiry
C: The Ontology is unavailable for a few minutes every hour for maintenance
D: The application must request every scope in the Ontology to avoid authorization errors
K: B
G: ## Token lifecycle
The exam guide asks you to diagnose authentication failures. Tokens expire; clients must refresh them.
## Fix
- Use the OAuth refresh flow (or prompt re-authentication) before expiry.
- On an expired-token error, refresh and retry once.
- Never store long-lived secrets in the browser.
Example: after adding refresh logic, sessions continue all day without errors.
W: Missing token refresh: the timing and the recovery after sign-in match token expiry exactly.
X: A=Hourly hacking: a regular one-hour pattern that clears on re-login is token expiry, not an attack.
C=Hourly maintenance: other clients would fail at the same times regardless of when users signed in.
D=Every scope: scope breadth does not prevent tokens from expiring and adds unnecessary exposure.
T: Implement token refresh in OSDK applications and handle expiry gracefully.
V: OSDK
