@ PLTR-APD D1 T1.4 applied use-case
S: A developer plans to rename a widely used property and wants to validate the effect on dependent modules, Functions and automations without changing anything that users currently rely on. Which approach fits?
A: Make the rename directly on the main version and fix whatever breaks as users report it over the following days
B: Duplicate the object type under a new name and ask every team to migrate their resources on their own schedule
C: Inspect and edit on a Workflow Lineage global branch, validate dependents, then merge
D: Ask each team in a meeting whether they use the property and rename it once nobody objects
K: C
G: ## Safe change with Workflow Lineage
Workflow Lineage shows the resources that make up a workflow (object types, Functions, Workshop modules, automations) and how they depend on each other. The documentation describes working on global branches to inspect, edit and validate resources before merging changes into `main`.
## Safe-change pattern
- Open the affected workflow and read its dependents instead of guessing.
- Make and validate the change on a branch.
- Merge to `main` only when dependents are verified.
Example: renaming `estCost` to `estimatedCost` on a branch exposes two Functions that still reference the old name before any user is affected.
W: Global branch in Workflow Lineage: the change and its dependents are inspected and validated in isolation, and only merged when verified.
X: A=Rename on main and fix reports: users meet the breakage first and production resources fail while the team reacts.
B=Duplicate object type: creates a second source of truth and pushes migration work and drift onto every team without showing who depends on what.
D=Meeting poll: relies on memory, so forgotten automations and Functions that use the property are missed.
T: Validate renames on a branch and read dependents in Workflow Lineage before merging.

@ PLTR-APD D1 T1.1 applied comparison
S: Truck, Drone and Boat object types all have a location and a status, and a dispatcher's Workshop map must list any of them together. Which modelling choice supports this best?
A: Merge all three into one large object type with a type property and null columns for fields that do not apply
B: Create a shared interface for location and status, and implement it on each type
C: Copy the three datasets into a fourth dataset and ignore the original object types from then on
D: Keep three separate object types and build three separate widgets, one per vehicle type, on the page
K: B
G: ## Interfaces for shared shape
An interface describes the common shape (properties and links) that several object types can implement, so that applications can work with "anything that has a location and status" without caring which type it is. Object types keep their own distinct properties and identity.
## Why not merge
- A single wide type loses clear identity and has many null properties.
- Per-type widgets multiply maintenance every time a field changes.
Example: a new Bus type implements the interface and appears on the dispatcher map without further changes.
W: Shared interface: each type stays distinct while the map and Functions use the common location and status shape.
X: A=One wide type: mixes unrelated entities, leaves many properties null and weakens clear identity and permissions per kind of vehicle.
C=Fourth dataset: duplicates data, drifts from the sources and abandons the typed objects Actions and links depend on.
D=Three widgets: triples the build and upkeep work and the combined view still cannot sort or filter across all types.
T: Use interfaces when different object types share a shape that applications should treat uniformly.

@ PLTR-APD D1 T1.2 applied use-case
S: A doctor works at several clinics and a clinic employs many doctors. The only facts to store are who works where; the pairing has no attributes of its own. Which link design fits?
A: A many-to-many link type between Doctor and Clinic, backed by a datasource of pairings
B: A comma-separated list of clinic identifiers kept in a text property on every Doctor object
C: A one-to-many link type from Clinic to Doctor, so each doctor is tied to one clinic only
D: A separate Doctor object for each clinic, copying the doctor's details for every employment
K: A
G: ## Many-to-many links
A link type connects two object types. When both sides can have many partners and the relationship has no data of its own, a many-to-many link type is enough. The Ontology documentation explains that for many-to-many cardinality the link type itself is backed by a datasource that lists the pairs, instead of a key on one of the object types.
## Design
- Doctor and Clinic keep their own primary keys.
- The pairing datasource holds one row per doctor and clinic.
- Add attributes of the pairing (start date, grade) only if needed; then an intermediate object type is the better design.
Example: a doctor at three clinics appears in three pair rows, and each clinic lists all of its doctors by traversing the link.
W: Many-to-many link type: both sides keep their identity and a pair datasource records who works where, with no duplicated objects.
X: B=Text list of clinics: a delimited string cannot be traversed, filtered by link or kept consistent with Clinic objects.
C=One-to-many from Clinic: allows each doctor only one clinic, which contradicts the stated facts.
D=Doctor copy per clinic: duplicates the person, so the same doctor has several identities that drift apart.
T: Use a many-to-many link type, backed by a pair datasource, when both sides have many partners and the pairing carries no data.

@ PLTR-APD D2 T2.1 applied use-case
S: An Action must set a ticket's status to Closed, stamp the user who closed it and the time of closing, and nothing else. Which implementation is the simplest that meets this?
A: A function-backed Action in which TypeScript code is written to read the user and clock before editing the ticket
B: A declarative Action with property edits that use the current user and time values
C: An automation that waits for the status change and then writes the user and the time afterwards
D: An external service called by webhook, which updates the ticket and the audit fields in its own database
K: B
G: ## Declarative first
Declarative edit rules cover straightforward modifications: set a property to a parameter, to a fixed value, or to values such as the current user and current time. Function-backed Actions are for logic the rules cannot express, such as loops, multi-object computation or conditional branching.
## Choosing
- Fixed fields, no branching: declarative rules.
- Computed edits across many objects: function-backed.
Example: Close Ticket sets `status = Closed`, `closedBy = current user`, `closedAt = current time` in one rule.
W: Declarative rules: the three property edits need no code, are visible in the Action's definition and are easy to test.
X: A=Function-backed Action: adds code, tests and a deployment path for edits that simple rules express directly.
C=Follow-up automation: separates the stamp from the status change, so the ticket can be closed without the audit fields for a while.
D=External webhook: moves Ontology edits out of the platform and loses governed write-back.
T: Prefer declarative rules when the edits are fixed or use current user and time.

@ PLTR-APD D2 T2.4 applied use-case
S: When a manager reassigns a ticket, the assignee must change and a history record must be created for the same event. Which design keeps the two edits together?
A: One Action type with a rule that modifies the ticket and a rule that creates the history object
B: A Workshop button that submits an Update Ticket Action and then a separate Create History Action
C: An automation that creates the history object some time after it notices that the assignee changed
D: A manual step in which the manager fills in a history form once the reassignment is finished
K: A
G: ## One Action, several rules
An Action type can hold more than one rule, for example a rule that modifies an object and a rule that creates another. The user submits one Action with one set of parameters, and the platform applies the defined edits as part of that submission. Submission criteria and permissions are checked once for the whole Action.
## Why keep them together
- Edits that must always go together belong in one definition.
- Separate submissions can leave the ticket changed with no history entry if the second one fails or is never made.
Example: Reassign Ticket takes the ticket and the new assignee, sets `assignee`, and creates a `TicketHistory` object with the old and new values.
W: Single Action with two rules: the ticket change and the history object are defined and submitted together, so a reassignment cannot be recorded without its history by design.
X: B=Two Actions in sequence: the second submission can fail, be cancelled or be skipped, leaving a reassignment with no history.
C=Delayed automation: the gap between change and record lets the ticket change without history for a while, and adds a second moving part.
D=Manual form: depends on the manager remembering, so history is incomplete in practice.
T: Put edits that must happen together into one Action with several rules.

@ PLTR-APD D3 T3.4 advanced troubleshooting
S: A developer improved a TypeScript function and published a new version. The Workshop module still shows the old calculation. The new version returns correct values when tested directly. What is the most likely cause?
A: The module is using a pinned older function version and must be upgraded to the new one
B: The new version is correct, so the Ontology must be recomputing the old values in the background
C: The function must be rewritten in Python v2, since TypeScript output is stored permanently after a run
D: Users need Owner rights on the function repository to see output of the newer versions
K: A
G: ## Versions are consumed explicitly
Published Functions are versioned, and a consumer can be configured to call a particular version. Publishing a new version does not by itself change what an existing consumer calls; the consumer sees new behaviour once it is moved to the new version.
## Diagnosis
- Test the new version directly (done).
- Check which version the module's function-backed variable uses.
Example: the module references 1.2.0 while the fix is in 1.3.0.
W: Pinned older version: the consumer still calls the previous version, so the fix is correct but not yet used.
X: B=Background recomputation: Ontology does not recompute function results; the module simply calls the old code.
C=Rewrite in Python v2: language is irrelevant, and function results are not permanently stored after a run.
D=Owner rights: callers need to be allowed to run the function, not to own its repository.
T: When a fix does not appear, check which function version the consumer calls.

@ PLTR-APD D3 T3.2 advanced tradeoff
S: A function needs each customer's open orders for 200 selected customers. Which implementation is the better trade between correctness and performance?
A: Traverse links from the selected customers to their open orders using object set operations
B: Load every Order object into memory and filter in code to those belonging to the selected customers
C: Loop over the customers and run a separate full search of the orders for each customer
D: Ask the user to paste the list of order identifiers for the customers into a parameter
K: A
G: ## Let the platform do the set work
Object sets support filtering and link traversal, which run in the Ontology query layer. Pulling all objects into function memory and filtering there is slow and can hit limits; running one search per item multiplies round trips.
## Pattern
- Start from the selected customers' object set.
- Traverse the link to orders and filter by status.
- Load only what you need to return.
Example: 200 customers resolve to their open orders in one traversal.
W: Link traversal over object sets: filtering happens where the data lives, with one query rather than hundreds.
X: B=Load all orders: heavy on memory and time, and gets worse as the order table grows.
C=Per-customer searches: 200 separate full queries instead of one traversal, with slow and uneven response times.
D=Pasting identifiers: puts a data lookup on the user and invites typos and omissions.
T: Use object set traversal and filters instead of loading data into memory.

S: An external app fetches Customer objects through the OSDK and writes them into its own database for faster search. A security reviewer notes that other staff of that app can now see properties that Foundry hid from them. What explains this?

@ PLTR-APD D5 T5.3 applied use-case

@ PLTR-APD D5 T5.1 advanced troubleshooting
S: A browser-only app is registered as a public client. Its developer requests a token with the client credentials grant and the request is refused. What is the right way forward?
A: Register a confidential client and keep its secret inside the browser bundle so the grant is accepted
B: Use the authorization code grant with PKCE, so each signed-in user receives a token
C: Request additional scopes in the same call, since the refusal is caused by missing scopes
D: Ask an administrator to raise the app's rate limit so that the grant request is processed
K: B
G: ## Client types
When a third-party application is registered, the client type states whether the client can keep a secret safely. A confidential client, such as a server-side application, can use the authorization code grant or the client credentials grant. A public client, such as a browser-based application, cannot hold credentials securely, so it supports only the authorization code grant with PKCE; the `code_verifier` and `code_challenge` parameters are required, and the client credentials grant is not supported.
## Consequences
- Browser and native apps: public client, authorization code with PKCE, tokens for the signed-in user.
- Servers and jobs with no user present: confidential client, where the client credentials grant is available.
Example: the single-page app redirects the user to sign in and exchanges the code plus `code_verifier` for a token, with no secret in the bundle.
W: Authorization code with PKCE: it is the grant a public client supports, and it gives each user a token without any secret in browser code.
X: A=Confidential client with a bundled secret: anyone can read the bundle, so the secret is not secret and the client type no longer matches the real environment.
C=More scopes: scopes define what may be accessed; they do not change which grants a client type supports.
D=Rate limit increase: the request is refused because of the client type, not because of volume.
T: Browser apps are public clients and use authorization code with PKCE; client credentials need a confidential client.

@ PLTR-APD D6 T6.1 applied comparison

@ PLTR-APD D6 T6.2 advanced troubleshooting
S: An automation has two Action effects: the first creates a Shipment, the second sets the related Order to Shipped and assumes the shipment already exists. Sometimes the Order update runs first and fails. What is the right fix?
A: Rely on the order in which the effects were listed, since the configuration is applied in sequence
B: Add a delay in front of the second effect so that the Shipment is more likely to exist by then
C: Combine the dependent edits into one Action, or make the second step independent of the first
D: Move the Order update into a Workshop button so that people trigger it by hand each time
K: C
G: ## Effect order is not guaranteed
The Automate documentation states that the execution sequence is not guaranteed when several Actions are configured: they may run in any order. An effect that depends on another effect's result is therefore unreliable.
## Design
- Put edits that depend on each other into a single Action, whose rules are defined together.
- Otherwise make each effect valid on its own, so it does not matter which one runs first.
Example: one Ship Order Action creates the Shipment and sets the Order status, so no ordering question arises.
W: One combined Action (or independent effects): the design no longer depends on an execution order that the platform does not promise.
X: A=Listing order: the documentation says effects may run in any order, so the list position proves nothing.

@ PLTR-APD D7 T7.1 applied use-case
S: An AIP Logic function answers customers' questions about stock for a product. Answers must reflect current stock levels, which change hourly. Which design is correct?

- Instruction: answer only from tool results.

@ PLTR-APD D8 T8.3 applied comparison
S: An automation owned by an administrator edits objects through an Action effect when a user submits a request. Low-privilege users can now cause edits that they could not make directly. What is the correct reading?
A: The edits run as the automation owner, so scope the owner's permissions and criteria deliberately
B: The platform runs every effect as the user who triggered it, so this cannot be happening
C: Automations are exempt from permissions altogether, which makes the owner's role irrelevant
D: The administrator's role is applied to the users, which changes their rights everywhere
K: A
G: ## Whose permissions
Action and Logic effects in an automation run as the automation owner. A broad owner means the automation can do more than the person who caused the event. That can be intended, but it must be a conscious decision with matching criteria and limited owner rights.
## Practice
- Give owners only the access the automation needs.
- Put checks in submission criteria.
Example: an owner limited to the Request object type cannot edit unrelated objects even if triggered by anyone.
W: Owner execution: effects use the owner's permissions, so owner scope and criteria define what the automation can do.
X: B=Triggering user's permissions: effects are run as the owner, not as the triggering user.
C=Exempt from permissions: automations are subject to the owner's access.
D=Role applied to users: users keep their own rights; only the effect uses the owner's.
T: Automation effects run with the owner's permissions, so design owner scope carefully.
