@ PLTR-APD D1 T1.4 applied use-case
S: A developer plans to rename a widely used property and wants to validate the effect on dependent modules, Functions and automations without changing anything that users currently rely on. Which approach fits?
A: Make the rename directly on the main version and fix whatever breaks as users report it over the following days
B: Duplicate the object type under a new name and ask every team to migrate their resources on their own schedule
C: Inspect and edit on a Workflow Lineage global branch, validate dependents, then merge
D: Ask each team in a meeting whether they use the property and rename it once nobody objects
K: C
G: ## Safe change with Workflow Lineage
Workflow Lineage shows the resources that make up a workflow (object types, Functions, Workshop modules, automations) and how they depend on each other. The documentation describes working on global branches to inspect, edit and validate resources before merging changes into `main`.
## Safe-change pattern
- Open the affected workflow and read its dependents instead of guessing.
- Make and validate the change on a branch.
- Merge to `main` only when dependents are verified.
Example: renaming `estCost` to `estimatedCost` on a branch exposes two Functions that still reference the old name before any user is affected.
W: Global branch in Workflow Lineage: the change and its dependents are inspected and validated in isolation, and only merged when verified.
X: A=Rename on main and fix reports: users meet the breakage first and production resources fail while the team reacts.
B=Duplicate object type: creates a second source of truth and pushes migration work and drift onto every team without showing who depends on what.
D=Meeting poll: relies on memory, so forgotten automations and Functions that use the property are missed.
T: Validate renames on a branch and read dependents in Workflow Lineage before merging.

@ PLTR-APD D1 T1.1 applied comparison
S: Truck, Drone and Boat object types all have a location and a status, and a dispatcher's Workshop map must list any of them together. Which modelling choice supports this best?
A: Merge all three into one large object type with a type property and null columns for fields that do not apply
B: Create a shared interface for location and status, and implement it on each type
C: Copy the three datasets into a fourth dataset and ignore the original object types from then on
D: Keep three separate object types and build three separate widgets, one per vehicle type, on the page
K: B
G: ## Interfaces for shared shape
An interface describes the common shape (properties and links) that several object types can implement, so that applications can work with "anything that has a location and status" without caring which type it is. Object types keep their own distinct properties and identity.
## Why not merge
- A single wide type loses clear identity and has many null properties.
- Per-type widgets multiply maintenance every time a field changes.
Example: a new Bus type implements the interface and appears on the dispatcher map without further changes.
W: Shared interface: each type stays distinct while the map and Functions use the common location and status shape.
X: A=One wide type: mixes unrelated entities, leaves many properties null and weakens clear identity and permissions per kind of vehicle.
C=Fourth dataset: duplicates data, drifts from the sources and abandons the typed objects Actions and links depend on.
D=Three widgets: triples the build and upkeep work and the combined view still cannot sort or filter across all types.
T: Use interfaces when different object types share a shape that applications should treat uniformly.

@ PLTR-APD D1 T1.2 applied use-case
S: Customers can enrol in many courses and each course has many customers, and the business must also record the enrolment date and grade for each pairing. Which relationship design fits?
A: A many-to-many link type with the date and grade stored as properties of the course object type
B: Separate "date" and "grade" lists stored inside the customer object as arrays of mixed values
C: An Enrolment object type linked to both Customer and Course, holding date and grade
D: One link type per course, created each time the business adds a new course to the catalogue
K: C
G: ## Relationship with its own data
A plain link only says that two objects are related. When the relationship has facts of its own (date, grade, status), the relationship deserves its own object type, linked to both sides, so those facts have a stable identity and can be edited through Actions.
## Design
- `Enrolment` with primary key, `enrolledOn`, `grade`.
- Links Enrolment to Customer and Enrolment to Course (many-to-one each).
Example: one customer in three courses has three Enrolment objects, each with its own grade.
W: Intermediate Enrolment object: date and grade belong to the pairing, so they live on an object that is linked to both customer and course.
X: A=Properties on course: a grade on the course would be shared by all customers and cannot differ per pairing.
B=Arrays inside the customer: unstructured values cannot be queried, validated or edited per enrolment in a reliable way.
D=Link type per course: schema changes with every new course and still gives no place for the pairing's own data.
T: Model a relationship that carries its own data as an object type linked to both sides.

@ PLTR-APD D2 T2.1 applied use-case
S: An Action must set a ticket's status to Closed, stamp the user who closed it and the time of closing, and nothing else. Which implementation is the simplest that meets this?
A: A function-backed Action in which TypeScript code is written to read the user and clock before editing the ticket
B: A declarative Action with property edits that use the current user and time values
C: An automation that waits for the status change and then writes the user and the time afterwards
D: An external service called by webhook, which updates the ticket and the audit fields in its own database
K: B
G: ## Declarative first
Declarative edit rules cover straightforward modifications: set a property to a parameter, to a fixed value, or to values such as the current user and current time. Function-backed Actions are for logic the rules cannot express, such as loops, multi-object computation or conditional branching.
## Choosing
- Fixed fields, no branching: declarative rules.
- Computed edits across many objects: function-backed.
Example: Close Ticket sets `status = Closed`, `closedBy = current user`, `closedAt = current time` in one rule.
W: Declarative rules: the three property edits need no code, are visible in the Action's definition and are easy to test.
X: A=Function-backed Action: adds code, tests and a deployment path for edits that simple rules express directly.
C=Follow-up automation: separates the stamp from the status change, so the ticket can be closed without the audit fields for a while.
D=External webhook: moves Ontology edits out of the platform and loses governed write-back.
T: Prefer declarative rules when the edits are fixed or use current user and time.

@ PLTR-APD D3 T3.4 advanced troubleshooting
S: A developer improved a TypeScript function and published a new version. The Workshop module still shows the old calculation. The new version returns correct values when tested directly. What is the most likely cause?

@ PLTR-APD D3 T3.2 advanced tradeoff
S: A function needs each customer's open orders for 200 selected customers. Which implementation is the better trade between correctness and performance?
A: Traverse links from the selected customers to their open orders using object set operations
B: Load every Order object into memory and filter in code to those belonging to the selected customers
C: Loop over the customers and run a separate full search of the orders for each customer
D: Ask the user to paste the list of order identifiers for the customers into a parameter
K: A
G: ## Let the platform do the set work
Object sets support filtering and link traversal, which run in the Ontology query layer. Pulling all objects into function memory and filtering there is slow and can hit limits; running one search per item multiplies round trips.
## Pattern
- Start from the selected customers' object set.
- Traverse the link to orders and filter by status.
- Load only what you need to return.
Example: 200 customers resolve to their open orders in one traversal.
W: Link traversal over object sets: filtering happens where the data lives, with one query rather than hundreds.
X: B=Load all orders: heavy on memory and time, and gets worse as the order table grows.
C=Per-customer searches: 200 separate full queries instead of one traversal, with slow and uneven response times.
D=Pasting identifiers: puts a data lookup on the user and invites typos and omissions.
T: Use object set traversal and filters instead of loading data into memory.

@ PLTR-APD D5 T5.3 advanced troubleshooting
S: An external app fetches Customer objects through the OSDK and writes them into its own database for faster search. A security reviewer notes that other staff of that app can now see properties that Foundry hid from them. What explains this?
A: The OSDK has a defect that ignores property security, so it should be replaced by REST calls

X: A=OSDK defect: the OSDK is behaving as documented; the gap is in downstream handling.
C=Encryption in transit: protects transport, not who may view data stored later.
D=Markings follow automatically: an external copy has no such link unless the app enforces equivalent controls.
T: Foundry access controls apply when data is read; protect copies yourself.

@ PLTR-APD D5 T5.1 applied use-case
S: A single-page browser app will be registered to sign users in with OAuth. A teammate proposes embedding a client secret in the JavaScript bundle so that the app can authenticate. What is the right guidance?
A: Embed the secret but rename it so it is harder to find in the bundle
B: Share one secret between all users and rotate it only when someone leaves
C: Use a public client with the authorization code flow and no embedded secret
D: Store the secret in a browser cookie so that only logged-in users can read it
K: C
G: ## Secrets and browsers
Code delivered to a browser can be read by anyone, so a client secret placed there is not secret. Browser apps register as public clients and use the authorization code flow (with PKCE) so that each user signs in and the app receives a token with only the user's rights and the app's scopes. Confidential clients with secrets belong on a backend.
## Rule
- No secrets in front-end code.
- Backend services keep secrets in secure storage.
Example: the SPA redirects to sign-in and receives a user-scoped token, with no secret in the bundle.
W: Public client with authorization code: the app proves nothing with a secret, and the token reflects the signed-in user.
X: A=Renaming the secret: obscurity only; anyone can read the bundle and reuse the secret.
B=Shared secret for all users: one leak compromises everyone and removes per-user attribution.
D=Secret in a cookie: still delivered to the browser, so readable by scripts and users.
T: Browser apps use public clients; secrets stay on backends.

T: Handle rate limits with backoff, lower request volume and caching.

@ PLTR-APD D6 T6.1 applied comparison
S: Managers want one notification when an invoice first becomes overdue, not a message every time an already overdue invoice is edited. Which trigger design fits?

T: To act once on a transition, trigger on objects entering a set.
