@ PLTR-APD D8 T8.3 applied comparison
S: A team is documenting how its automations execute so that auditors understand whose permissions are used. Which statement about automation execution identity matches how Automate works?
A: Automations run with the permissions of whichever user triggered the event, so each run reflects that user's own access
B: Action and Logic effects run as the automation's owner, so ownership by a scoped third-party app's service user keeps it independent of staff
C: Project-scoped automations stop using the owner's permissions and instead run with the combined permissions of everyone on the project
D: Automations always run with administrator rights so that conditions and effects can never fail on permissions
K: B
G: ## Automations execute as their owner
Foundry's Automate documentation states that condition evaluation and Action and Logic effects use the **automation owner's** permissions in every scoping mode; notification effects use each recipient's permissions. Saving an automation can transfer ownership to the person who saved it, which changes whose access future runs use. An automation owned by a **third-party application** runs as that application's service user, which the docs describe as providing continuity when individuals leave.
## Practice
- Make the owner a scoped third-party application (service user) with only the permissions the automation needs.
- Be deliberate about ownership when editing.
- Project scope is about run-history visibility and imported resources, not about whose permissions apply.
Example: an automation owned by `svc-order-automation` keeps working when the engineer who built it moves teams.
W: Effects run as the owner, so choosing a scoped service-user owner gives predictable, least-privilege execution that does not depend on any individual employee.
X: A=Triggering user's permissions: Action and Logic effects run as the owner, not as the user whose change triggered the event.
C=Combined project permissions: the docs state that project-scoped automations still run as their owner; scoping changes history visibility.
D=Administrator rights: automations use the owner's own access level; nothing grants them administrator rights.
T: Automations run as their owner; use a scoped service-user owner for continuity and least privilege.

@ PLTR-APD D6 T6.2 applied use-case
S: An automation in a project with sensitive data sends summaries to a Slack channel. The security team asks how to make sure it cannot read beyond what the summaries need. What should be configured?
A: Make an administrator the automation's owner so that it never fails, and trust the summary content to be safe
B: Make the owner a service user with access only to what the summaries need, since effects run as the owner
C: Switch the automation to project-scoped mode, which on its own prevents it from reading anything outside the project
D: Remove the automation and ask analysts to post summaries manually
K: B
G: ## Least privilege through the owner
Foundry's Automate documentation states that condition evaluation and Action and Logic effects use the automation owner's permissions, and that this holds regardless of scoping mode. What the automation can read is therefore decided by who owns it.
## Configuration
- Owner: a third-party application's service user with read access only to the objects the summaries use.
- Project-scoped mode for shared run history (it does not narrow permissions by itself).
- Review what the summary includes and where it is sent.
Example: the service-user owner can read the case objects in its project but not HR data elsewhere, so the summaries cannot include it.
W: A least-privilege service-user owner: because effects run as the owner, its narrow access is exactly what bounds what the automation can read.
X: A=Administrator owner: the automation would run with administrator access, the opposite of what security asked for.
C=Project-scoped mode alone: the docs state that project-scoped automations still run as their owner; scoping changes history visibility, not the owner's access.
D=Manual posting: removes useful automation instead of scoping its owner's access.
T: Bound what an automation can read by giving it a least-privilege owner, since effects run as the owner.
