@ TF-TA004 D1 T1.1 advanced use-case
S: A team provisions 30 load balancers with shell scripts that call the cloud CLI step by step. Re-running a script after a partial failure creates duplicate load balancers, and reviewers cannot see what a run will change before it starts. The team wants re-runs to be safe and a preview of every change, without writing existence checks into each script. Which approach meets these goals with the LEAST custom code?
A: Replace the scripts with Terraform provisioners that call the same CLI commands, so the existing step-by-step logic runs inside `terraform apply`
B: Keep the scripts but add a describe call before each create command, and print the planned commands to the console for reviewers before running them
C: Wrap the scripts in a CI job that runs them twice and compares the second run's output with the first, so duplicates are detected before approval
D: Describe each load balancer in Terraform configuration, let state map it to its real object, and review the `terraform plan` output before every apply
K: D
G: ## Imperative scripts versus declarative configuration
An imperative script is a list of steps: "create load balancer", "attach listener". It has no memory of what it did last time, so running it again repeats the steps and creates duplicates unless every step first checks whether its object already exists.

Terraform is **declarative**: configuration files describe the end state, and Terraform works out the steps. Two pieces make re-runs safe:
- **State** records which real object belongs to each resource block, so a second apply finds the existing load balancer instead of creating another.
- **Plan** compares configuration, state and the real objects and lists every create, update and destroy before anything happens.

## Example
`resource "aws_lb" "api" { name = "api" ... }` applied twice in a row creates one load balancer on the first run and reports "No changes" on the second.
W: Declarative configuration: state binds each block to one real load balancer, so a re-run converges instead of duplicating, and the plan gives reviewers the preview, with no existence checks to write.
X: A=Provisioners: provisioners run commands during apply but Terraform does not track what those commands create, so the duplicates and the missing preview remain.
B=Describe calls: this works only by adding the existence checks the team wants to avoid, in every script, and printed commands are not a reliable preview of the API's results.
C=Run twice: running the scripts twice creates more duplicates instead of preventing them, and comparing outputs only detects the damage after it happened.
T: Declarative configuration plus state makes re-runs idempotent, and the plan previews every change before it happens.

@ TF-TA004 D1 T1.1 advanced definition
S: A company moves its 12 production networks from console changes to Terraform. Configuration lives in Git, a CI pipeline runs plan and apply on merge, and engineers keep read-only console access. The security lead must tell auditors which outcomes this IaC workflow provides by itself and which still need separate controls, because the audit plan depends on the answer. Which THREE outcomes does the workflow provide without extra tooling? (Select THREE)
A: Terraform blocks any change made outside the pipeline, so no resource can drift from its configuration between two pipeline runs
B: Each run shows a plan of every create, update and destroy, so reviewers approve exact changes before they happen
C: Commits and pull requests record who changed which resource definition, when and why, giving a reviewable history of every change
D: Terraform reverts out-of-band changes as soon as they happen, without waiting for the next plan and apply run in the pipeline
E: Terraform rolls every resource back to its previous settings automatically whenever an apply fails partway through the run
F: Applying the same configuration in a new account produces the same set of resources, which makes environments repeatable from code
K: B,C,F
G: ## What an IaC workflow gives you
Terraform describes infrastructure in human-readable files that you can **version, reuse and share**. Combined with Git and a pipeline, that gives:
- **Preview**: `terraform plan` lists every action before apply, so approval covers the real change.
- **Repeatability**: the same configuration with the same inputs builds the same resources in another account or region.
- **History**: version control records each change to the definitions and the review that approved it.

## What it does not do on its own
- Terraform does not watch the cloud continuously. A console change is noticed only when the next plan or a drift check runs.
- Terraform does not block API calls made outside Terraform; that needs permissions on the cloud side.
- Terraform has no automatic rollback. When an apply fails, it records what was done in state and stops; you fix the problem and apply again.
W: B=Plan preview: every run computes and shows the actions before apply, which is exactly the review point auditors want.
C=Version history: keeping the files in Git gives a who, what, when and why record through commits and reviewed pull requests.
F=Repeatable builds: declarative configuration produces the same resources each time it is applied with the same inputs.
X: A=Blocks outside changes: Terraform cannot stop someone with write access from changing a resource through the console or API; cloud permissions do that.
D=Instant revert: Terraform acts only when a run happens, so out-of-band changes persist until the next plan and apply.
E=Automatic rollback: a failed apply stops after recording completed changes in state; there is no built-in rollback.
T: IaC with Terraform gives preview, repeatability and history, but drift prevention and rollback need other controls.

@ TF-TA004 D1 T1.2 advanced troubleshooting
S: A Friday release changed a load balancer listener and two security group rules through Terraform, and customers started seeing errors. The configuration lives in Git, a pipeline runs plan and apply on merge, and the previous release is tagged. The change board requires the fix to pass through the same reviewed pipeline and to restore exactly the previous settings. Which action restores service while meeting the change board's rule?
A: Revert the release commit in Git, open a pull request, review the resulting plan, and let the pipeline apply the previous configuration
B: Restore the previous version of the state file in the backend, so Terraform's records match the old release and resources follow automatically
C: Edit the listener and rules in the console back to their old values, then run `terraform apply -refresh-only` so state records them
D: Run Terraform's built-in rollback command for the last apply, which restores the previous state file and the matching resource settings
K: A
G: ## Rolling back with IaC
Because infrastructure is defined in versioned files, "the previous settings" are simply the previous commit. Reverting that commit and running the normal workflow makes Terraform plan the changes that turn today's infrastructure back into the old definition.

Key points:
- Terraform has **no rollback command**. Going back means applying an older configuration.
- **State is a record, not a control**. Changing or restoring the state file does not change any real object; it only changes what Terraform believes exists, which usually makes the next plan confusing or wrong.
- A console fix bypasses review, and `-refresh-only` would then make the unreviewed values the recorded truth while the configuration still holds the faulty release.

## Example
`git revert <release-commit>` followed by a pull request shows a plan such as `~ aws_lb_listener.https` and `~ aws_security_group_rule.app`, which reviewers approve before the pipeline applies it.
W: Revert and re-apply: the old commit is the exact previous definition, and running it through the same pull request and pipeline keeps the review and audit trail the board requires.
X: B=Restore state: an older state file changes only Terraform's records, not the listener or rules, and leaves state out of step with real infrastructure.
C=Console then refresh-only: the console edit skips the reviewed pipeline, and the configuration in Git still describes the broken release, so the next normal apply would bring the errors back.
D=Rollback command: Terraform has no built-in rollback, so this step cannot be run at all.
T: With IaC, a rollback is a revert of the configuration applied through the normal reviewed workflow.

@ TF-TA004 D1 T1.3 advanced use-case
S: Each new microservice needs a GitHub repository with branch protection, a PagerDuty service, a Datadog monitor and a Kubernetes namespace. Today four teams set these up by hand over a week, and the settings differ between services. The platform team wants one reviewed change per new service that creates all four objects, with the monitor's query referring to the namespace name. Which approach fits best?
A: Write one Terraform module that uses the GitHub, PagerDuty, Datadog and Kubernetes providers, passes values between them, and is called once per service
B: Ask each vendor team to keep its own Terraform configuration and state, and send the namespace name to the monitoring team for each new service
C: Use Terraform only for the Kubernetes namespace, because providers exist for cloud and container platforms but not for SaaS tools like PagerDuty
D: Keep one configuration per vendor and run all four from a wrapper script, passing the namespace name to each `terraform apply` as a flag
K: A
G: ## Service-agnostic workflows
Terraform talks to platforms through **providers**, and providers exist for far more than clouds: GitHub, PagerDuty, Datadog, Kubernetes, DNS services and thousands more in the Terraform Registry. One configuration can use several providers at once.

Because all resources live in one dependency graph, one resource can refer to another resource from a different provider, for example a monitor query that uses `kubernetes_namespace.svc.metadata[0].name`. Terraform orders the work from those references.

## Why a module
Wrapping the four resources in a module gives every service the same settings, and calling it once per service gives one plan, one review and one apply for the whole set.
W: One multi-provider module: a single plan covers all four objects, references between providers keep the monitor tied to the namespace, and the module makes every service identical.
X: B=Separate team configurations: this keeps four reviews and a manual hand-off of the namespace name, which is the slow, inconsistent process the team wants to replace.
C=Kubernetes only: Terraform providers exist for GitHub, PagerDuty and Datadog as well, so limiting Terraform to the namespace leaves three manual steps.
D=Wrapper script: four configurations still mean four plans and four applies, so there is no single reviewed change, and the flag passing is custom glue.
T: Terraform providers cover SaaS tools too, so one module can create and link resources across several services in one reviewed plan.

@ TF-TA004 D1 T1.2 advanced use-case
S: A team copied the same 400-line network configuration into three regional folders and edits values in each copy by hand. Last month a firewall fix reached only two of the regions, and the third stayed exposed for weeks. The team wants future fixes to reach every region from a single change, while each region keeps its own CIDR ranges and instance sizes. Which IaC practice addresses this most directly?
A: Keep the three folders but add a pull-request checklist that reminds reviewers to copy every change into the other two regional folders
B: Keep the three folders and run `terraform fmt -recursive` across them after every fix, so the copies stay structurally identical over time
C: Put the shared code in one module with inputs for CIDRs and sizes, then call it once per region with regional values
D: Merge the three folders into one configuration with a single set of values, and accept identical CIDR ranges and sizes in all regions
K: C
G: ## Reuse instead of copy
Copying configuration creates several sources of truth that drift apart. A **module** is a reusable package of configuration with **input variables** for whatever differs between uses.

```
module "net_eu" {
  source       = "./modules/network"
  cidr_block   = "10.10.0.0/16"
  instance_size = "m6i.large"
}
```
Each region calls the same module with its own values. A firewall fix in `./modules/network` reaches every caller the next time each region is planned and applied, so no copy can be forgotten.
W: Shared module with inputs: the code exists once, so one fix reaches every region, while variables keep each region's CIDRs and sizes separate.
X: A=Checklist: it relies on people remembering to copy changes, which is exactly how the third region was missed.
B=fmt across folders: `terraform fmt` only rewrites layout and spacing; it never copies a rule from one folder into another.
D=Single set of values: this removes the copies but breaks the requirement that each region keeps its own CIDR ranges and sizes.
T: A module with input variables keeps one copy of the logic while letting each caller supply its own values.

@ TF-TA004 D2 T2.1 advanced use-case
S: Laptops and the CI runner share a root module that requires `aws` with `version = "~> 5.70"`. The repository's `.gitignore` excludes `.terraform.lock.hcl`, and last week CI selected a newer 5.x release than the laptops and produced a surprising plan. The team wants every machine to use the same provider build until someone deliberately upgrades it, with the LEAST ongoing effort. What should they do?
A: Run `terraform init -upgrade` at the start of every CI job and on every laptop each morning, so all machines move to the newest release together
B: Change the constraint to an exact version such as `= 5.74.1`, keep ignoring the lock file, and edit the constraint by hand for every release
C: Delete the `.terraform` directory on every machine before each run, so that `terraform init` always downloads the same provider version again
D: Commit `.terraform.lock.hcl` to the repository and run `terraform init -upgrade` only in a reviewed change when an upgrade is wanted
K: D
G: ## The dependency lock file
`terraform init` writes the selected provider version and its checksums to `.terraform.lock.hcl`. HashiCorp recommends **committing this file to version control**.

- When a provider already has a selection in the lock file, `terraform init` re-selects that version, even if a newer one matching the constraint exists.
- `terraform init -upgrade` ignores the recorded selection, picks the newest version allowed by the constraint, and updates the file, which you then review and commit.

So the constraint (`~> 5.70`) says which versions are acceptable, and the lock file says which one is in use right now. Without the committed file, each machine picks the newest acceptable release at the time of its own first init.
W: Commit the lock file: every machine re-selects the recorded version and checksums, and upgrades happen only through a deliberate `-upgrade` change that is reviewed.
X: A=Upgrade every run: this moves every machine to whatever is newest each day, which is the opposite of staying on one build until a deliberate upgrade.
B=Exact constraint: an exact pin stops drift but needs a manual edit for every release and still lacks the checksum verification the lock file provides, so it is more effort.
C=Delete .terraform: without a lock file, a fresh download selects the newest version allowed by `~> 5.70`, so machines still diverge whenever a release appears.
T: The committed lock file pins the exact provider build, and `terraform init -upgrade` is the deliberate way to move it.

@ TF-TA004 D2 T2.1 advanced use-case
S: A root module requires `aws` with `version = "~> 5.60"`. It calls a network module that declares `version = ">= 5.50"` and a logging module that declares `version = ">= 5.40, < 5.80"`. Nobody has run init in this directory before, so there is no lock file yet, and the registry lists 5.59.0, 5.79.2, 5.83.0 and 6.1.0. Which provider installation results when the team runs `terraform init`?
A: Terraform stops with an error, because each module declares a different constraint for the same provider and Terraform needs them to match
B: Terraform installs 5.83.0 for the root and network module and a separate 5.79.2 copy for the logging module, one per constraint set
C: Terraform installs 6.1.0, because the network module's minimum-only constraint lets the newest release override the root module's constraint
D: Terraform installs one copy, 5.79.2, because it is the newest release that satisfies the root and both module constraints together
K: D
G: ## One provider version for the whole configuration
Terraform selects a **single version per provider** that every module is compatible with. The root module and child modules are treated as equal: all of their constraints must hold at once.

## Working the example
- `~> 5.60` allows `>= 5.60` and `< 6.0`, which removes 5.59.0 and 6.1.0.
- `>= 5.50` from the network module removes nothing more.
- `>= 5.40, < 5.80` from the logging module removes 5.83.0.
- The newest remaining release is **5.79.2**, and it is recorded in the new lock file.

Different constraints are normal and are intersected; Terraform only fails when the intersection is empty. HashiCorp recommends that reusable modules declare only a minimum (`>=`) and leave the upper bound to the root module.
W: One intersected version: 5.79.2 is the newest release inside `~> 5.60`, `>= 5.50` and `< 5.80` at the same time, and Terraform installs only that version.
X: A=Constraints must match: constraints may differ; Terraform intersects them and errors only when no available version satisfies all of them.
B=Copy per module: Terraform never installs two versions of one provider for one configuration; it picks one version that all modules accept.
C=Newest wins: a minimum-only constraint in one module does not cancel the root's `~> 5.60`, which excludes every 6.x release.
T: Terraform intersects provider constraints from all modules and installs the newest single version that satisfies them all.

@ TF-TA004 D2 T2.3 advanced use-case
S: Every resource in a root module uses `provider "aws" { region = "eu-west-1" }`. A new CloudFront distribution needs an ACM certificate that must be created in `us-east-1`, while all other resources stay in eu-west-1. The team wants one configuration and one state, must not change the region of existing resources, and reviewers want the exception to be visible on the certificate resource itself. Which configuration does this?
A: Add a second `provider "aws"` block without an alias that sets `region = "us-east-1"`, and Terraform picks it for the certificate automatically
B: Change the default provider to `us-east-1`, add an aliased `eu-west-1` configuration, and set `provider = aws.euw1` on every existing resource
C: Add `provider "aws" { alias = "use1" region = "us-east-1" }` and set `provider = aws.use1` on the certificate resource only
D: Set `region = "us-east-1"` inside a `lifecycle` block on the certificate resource, which overrides the provider's region for that resource only
K: C
G: ## Several configurations of one provider
A `provider` block without `alias` is the **default configuration** for that provider. Additional configurations of the same provider need a unique `alias`:

```
provider "aws" { region = "eu-west-1" }
provider "aws" {
  alias  = "use1"
  region = "us-east-1"
}
resource "aws_acm_certificate" "cdn" {
  provider = aws.use1
  ...
}
```
Resources without a `provider` argument keep using the default configuration, so nothing else moves. The `provider = aws.use1` line on the certificate is the visible exception reviewers asked for, and everything stays in one state.
W: Aliased configuration: the alias adds a us-east-1 configuration next to the default one, and only the certificate opts into it with its `provider` argument.
X: A=Second unaliased block: two default configurations for one provider are not allowed; every extra configuration needs an alias, and Terraform never chooses one automatically.
B=Swap the default: it works only by editing every existing resource, which the team ruled out, and it moves the exception away from the certificate.
D=Region in lifecycle: the lifecycle block only holds rules such as `create_before_destroy` and conditions; it cannot change which provider configuration or region a resource uses.
T: Use an aliased provider configuration and select it with the `provider` meta-argument on the resources that need it.

@ TF-TA004 D2 T2.4 advanced troubleshooting
S: Two teams each have their own Terraform configuration and state, and both contain an `aws_s3_bucket_versioning` resource for the same bucket. Team A's configuration enables versioning, Team B's suspends it, and every apply by either team flips the setting back, without any error. The bucket must keep versioning enabled, and only Team A should manage it from now on. What explains the behavior and fixes it?
A: The provider caches the versioning value between runs, so each team sees stale data; running `terraform apply -refresh-only` first fixes it
B: Terraform merges both states into one view of the bucket during refresh, so the last team wins; moving both teams into one workspace fixes it
C: State locking failed between the two backends, so both applies wrote together; enabling locking in both backends stops the setting from flipping
D: Each state binds the same real object independently, so each apply enforces its own configuration; drop it from Team B's state and configuration only
K: D
G: ## One real object, one resource instance
State maps each resource instance to one real object. Terraform expects that **each remote object is bound to only one resource instance**. It can guarantee this for objects it creates, but nothing stops two separate configurations from both claiming the same object.

When that happens, each configuration sees the other's change as drift and "fixes" it on its next apply, so the setting flips back and forth. There is no error, because from each configuration's point of view it is doing its job.

## Fix
Keep exactly one owner. Team B removes the resource from its configuration and its state without destroying the real object (for example with a `removed` block that sets `destroy = false`). If Team B needs values from the bucket, it reads them with a `data` source.
W: One owner per object: two states each bind the bucket's versioning to their own resource, so each apply reverts the other; removing it from Team B leaves Team A as the single owner.
X: A=Provider cache: providers read the current value on every refresh, and refreshing first would only show the other team's setting before overwriting it again.
B=Merged states: Terraform never merges separate states; each configuration plans only against its own state.
C=Locking failure: locks protect one state from concurrent writers; these are two separate states, and the flipping happens even when the applies run hours apart.
T: Each real object should be managed by exactly one resource instance in one state; others should read it with a data source.

@ TF-TA004 D2 T2.2 advanced use-case
S: A CI runner in an isolated network cannot reach registry.terraform.io or any other internet host. The configuration needs `hashicorp/aws` and `hashicorp/random`. A separate build machine with internet access may prepare files that are then copied into the isolated network. Terraform must install both providers on the runner during `terraform init` without contacting any registry. Which TWO approaches work? (Select TWO)
A: Change each `source` in `required_providers` to a relative path such as `./providers/aws`, so Terraform loads the provider binaries from the repository
B: Run `terraform providers mirror` on the isolated runner itself, so that Terraform fills a local directory with the providers before `terraform init`
C: On the connected machine run `terraform providers mirror` into a directory, copy it in, and configure only a `filesystem_mirror` for it
D: Set `TF_REGISTRY_DISCOVERY_RETRY=0` on the runner, so Terraform skips registry discovery and uses provider binaries found on the system path
E: On the runner, run `terraform init -plugin-dir=PATH` with PATH pointing at the copied mirror directory, so installation reads only from that directory
K: C,E
G: ## How Terraform finds provider packages
By default `terraform init` downloads providers from their origin registry. For machines without that access, Terraform supports **mirrors**:
- `terraform providers mirror <dir>` runs on a machine that *can* reach the registry and writes the required provider packages into a directory layout that Terraform understands.
- A `provider_installation` block in the CLI configuration file (for example `~/.terraformrc`) with a `filesystem_mirror { path = "..." }` makes init read from that directory. If you keep a `direct` method as well, Terraform may still try the registry, so leave it out for an isolated host.
- `terraform init -plugin-dir=PATH` is a one-time override that installs only from PATH, as if it were configured as a filesystem mirror.

Provider `source` addresses are always registry-style addresses such as `hashicorp/aws`; they are not file paths.
W: C=Mirror plus filesystem_mirror: the connected machine builds the mirror, and a CLI configuration with only a filesystem mirror makes init install from the copied directory.
E=-plugin-dir: init reads plugins only from the given directory, so the copied mirror is enough and no registry is contacted.
X: A=Relative source path: provider source addresses take the form hostname/namespace/type; a file path is not a valid provider source.
B=Mirror on the isolated runner: `terraform providers mirror` downloads from the registry, so it cannot run on a host without internet access.
D=Discovery retry setting: this variable controls retries when talking to a registry; it does not switch Terraform to binaries on the system path.
T: Build a mirror with `terraform providers mirror` on a connected host, then install from it with a filesystem mirror or `-plugin-dir`.

@ TF-TA004 D3 T3.2 advanced use-case
S: An initialized working directory already uses the `aws` provider, locked at 5.72.0, and a registry module installed at 2.3.1. An engineer adds a new `module "dns"` block and a `cloudflare` provider requirement, and `terraform plan` now reports that a module is not installed. The engineer worries that re-running init will upgrade the existing provider or module, or touch the state. What does a plain `terraform init` do?
A: It installs everything that is missing and then runs a refresh, updating state with the latest attributes of every resource before plan runs
B: It installs the new module but refuses to add the Cloudflare provider until `-upgrade` is given, because the lock file already exists here
C: It installs the new module and the Cloudflare provider, keeps aws 5.72.0 and module 2.3.1 unchanged, and does not change state or infrastructure
D: It reinstalls every module and provider at the newest versions allowed by the constraints, because init treats each run as a fresh installation
K: C
G: ## Re-running init is safe
`terraform init` is designed to be run again whenever the configuration's dependencies change.
- **Modules**: re-running init installs modules that were added since the last init but does not change modules that are already installed. Use `-upgrade` to update them.
- **Providers**: a provider with a selection in the lock file is re-selected at that version. A provider with no selection yet gets the newest version that matches its constraint, and the lock file gains an entry for it.
- **State and infrastructure**: init prepares the working directory and backend; it does not plan, refresh or apply anything.

## Example output
`- Reusing previous version of hashicorp/aws from the dependency lock file` next to `- Installing cloudflare/cloudflare v...`.
W: Plain init: missing modules and providers are added, locked and installed ones stay at their versions, and no state or resource is touched.
X: A=Refresh during init: init never refreshes or writes resource attributes to state; that happens during plan or apply.
B=Refuses new provider: a provider with no lock entry is simply selected and added; `-upgrade` is needed only to move providers that already have a selection.
D=Fresh install: newer versions are considered only with `-upgrade`; without it, recorded and installed versions are kept.
T: A plain `terraform init` adds what is missing and keeps locked providers and installed modules unchanged.

@ TF-TA004 D8 T8.3 advanced troubleshooting
S: In an HCP Terraform workspace, the Terraform variable `azs` was entered with the value `["eu-west-1a", "eu-west-1b"]`, and the configuration declares `variable "azs" { type = list(string) }`. G: ## Workspace variable values are strings by default
HCP Terraform workspace variables come in two categories: **Terraform variables** (input variables of the configuration) and **environment variables** (shell variables for the run, such as provider credentials).

A Terraform variable's value is a **string** unless you enable its **HCL** option. With HCL enabled, the value is interpreted with the same syntax you would write in Terraform code, so `["eu-west-1a", "eu-west-1b"]` becomes a list and `{ env = "prod" }` becomes a map. The HCL option exists only for Terraform variables, not environment variables.

Marking a variable sensitive only hides its value; it does not change its type.
W: HCL option: interpreting the value as HCL turns the bracketed text into a list that matches `list(string)`.
X: A=Environment variable: an environment variable named `azs` is not an input variable at all, and environment variables cannot use HCL.
B=Sensitive: the sensitive flag hides the value in the UI and API but leaves it a string.
C=Comma-separated: a comma-separated value is still one string; no automatic split into a list happens.
T: Enable the HCL option on a workspace Terraform variable to pass lists and maps instead of strings.
