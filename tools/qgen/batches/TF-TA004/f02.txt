@ TF-TA004 D4 T4.4 applied use-case
S: A variable describes server definitions: each server has a name (string), a cpu_count (number) and a list of tags (list of strings). Which type constraint models one server most precisely?
A: map(string), with the keys name, cpu_count and tags, so every one of the values must convert to text
B: set(number), an unordered collection of unique numbers that could carry cpu_count but no name or tags
C: list(string), a sequence holding the name, the cpu_count and each tag as text values found by position
D: object({ name = string, cpu_count = number, tags = list(string) }), a structural type with named attributes
K: D
G: ## Structural versus collection types
Terraform has two families of complex types.
- **Collections** hold many values of ONE type: `list(T)` (ordered, indexed by number), `set(T)` (unordered, unique), `map(T)` (string keys, all values of type T).
- **Structural types** hold values of DIFFERENT types: `object({...})` has named attributes, each with its own type; `tuple([...])` has a fixed sequence of positions with individual types.
A record with a string, a number and a list is the standard case for an `object`. `map(string)` could carry the name and a number converted to text, but not a list.
W: object: a structural type gives every named attribute its own type, so name stays a string, cpu_count a number and tags a list of strings, and Terraform validates each one.
X: A=map(string): every value must be a string. The name and cpu_count convert to text, but a list of tags does not convert to a string, so the input fails the type check.
B=set(number): a set holds unique numbers only. It cannot hold a name, tags or any named structure.
C=list(string): it is a sequence of strings with no named attributes, so it cannot tell a name from a tag, it turns cpu_count into text, and it cannot hold a nested list.
T: Mixed types per record means object (or tuple by position); collections hold one type only.

@ TF-TA004 D4 T4.2 applied troubleshooting
S: A resource sets count = length(aws_subnet.private[*].id), and the subnets are created in the same run from a list that is only known after apply. Plan reports that the count value cannot be determined. What is the cause?
A: Splat expressions are not allowed inside a count expression, so the reference to aws_subnet.private[*].id must be replaced with an index
B: The count meta-argument rejects the length function, because count accepts only literal whole numbers
C: Terraform has to settle how many instances to create while it builds the plan, and the subnet IDs do not exist yet at that point
D: A resource may not reference another resource in the same module for its count, so it must be moved into a child module
K: C
G: ## Why count and for_each need known values
Terraform decides how many instances a resource has while building the plan, because the plan lists each instance. So `count` (and the keys of `for_each`) cannot use a value that can be learned only during apply, such as a computed attribute of a resource that does not exist yet.
If the number of items is derivable from input variables or other values known at plan time, use those, for example `length(var.subnet_cidrs)`. Referencing computed attributes of other resources to size a collection is a common cause of this error.
W: Unknown at plan time: count must be a known whole number while the plan is built, because the plan lists every instance, and the number of subnet IDs depends on values available only during apply, so Terraform cannot create the plan.
X: A=Splat restriction: splat expressions are normal expressions and are allowed in count. The problem is the unknown value inside them.
B=Literal-only count: count accepts any expression that returns a whole number, including function calls such as length().
D=Same-module restriction: resources can reference each other in one module. The issue is when the value becomes known, not where the resource lives.
T: count and for_each need values known during plan, so they cannot depend on attributes only known after apply.
