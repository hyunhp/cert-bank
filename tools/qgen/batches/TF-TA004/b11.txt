@ TF-TA004 D1 T1.2 expert use-case
S: After an outage review, a company lists what went wrong with its hand-built infrastructure. A firewall rule changed in the console at 02:10 had no record of who made it or why. Staging and production differed in 14 settings, although both were meant to be identical apart from instance sizes. Rebuilding the production network in a second region took nine hours. The new standard says every change must be reviewed before it happens and traceable afterwards, environments may differ only in declared sizes, and a full rebuild must be possible from code in under an hour. The company will use only Terraform and Git, and from now on engineers keep read-only console access. Which THREE practices meet the new standard? (Select THREE)
A: Run `terraform import` every week for resources created in the console, so state always catches up with changes made outside the pipeline
B: Schedule a nightly `terraform apply -refresh-only -auto-approve`, so any console change is recorded in state and becomes the approved baseline
C: Keep all configuration in Git and require a pull request showing the `terraform plan` output before the pipeline applies any change
D: Rebuild a region by applying the same reviewed configuration with that region's provider settings, rather than recreating resources by hand
E: Build both environments from one module whose only environment-specific inputs are the instance sizes, each set in its own variables file
F: Copy the production directory into a separate staging directory and edit sizes there, so each environment is reviewed and applied on its own
K: C,D,E
G: ## Turning findings into IaC practices
Each finding maps to one benefit of infrastructure as code:
- **No record of the change** is solved by keeping configuration in version control and making the plan part of the review. The pull request records who proposed what and why, and the plan shows exactly which objects will change.
- **Environments that drift apart** are solved by reuse: one module, with variables only for what may differ (here, instance sizes). A fix to the module reaches both environments.
- **Slow rebuilds** are solved by reproducibility: the same configuration applied with another region's provider settings recreates the network in the time the apply takes.

## Practices that undermine the standard
Accepting console changes into state, copying directories, and importing after the fact all treat unreviewed changes as normal. They keep the old problems and add process around them.
W: C=Reviewed plans in Git: every change is proposed in a pull request with its plan before apply, and the history stays in Git, which covers review and traceability.
D=Rebuild from code: applying the reviewed configuration to a new region recreates the network quickly and the same way every time.
E=One module, size inputs only: sharing the code leaves instance size as the only possible difference between staging and production.
X: A=Weekly import: importing console-made resources after the fact accepts unreviewed changes and cannot explain who made them or why.
B=Nightly refresh-only auto-approve: it silently turns unreviewed console changes into the recorded baseline, the opposite of reviewing changes before they happen.
F=Copied directories: two copies edited separately drift apart again, which is how the 14 differences appeared in the first place.
T: Version-controlled configuration with plan review, a shared module for all environments, and rebuilds from code turn outage findings into IaC controls.

@ TF-TA004 D1 T1.1 expert troubleshooting
S: A configuration declares `resource "aws_instance" "web" { count = 3 ... tags = { Name = "web" } }`, applied last week with default settings. Yesterday an operator terminated `web[1]` in the console and, to help, launched two new instances by hand from the same AMI, also tagged `Name = "web"`. Nobody touched the configuration or the state. Today a teammate runs `terraform plan` with default options. The change advisory board must know exactly what the plan proposes before it approves the run, including what happens to the two hand-made instances, which a cost report already flags as duplicates. Which plan should they expect?
A: A plan to destroy both hand-made instances because they carry a tag the configuration declares, and to create `aws_instance.web[1]` again
B: A plan to create one instance for `aws_instance.web[1]`, with nothing proposed for the two hand-made instances because state does not record them
C: No changes, because the refresh finds at least three running instances tagged `Name = "web"`, which already satisfies `count = 3` in the configuration
D: Terraform adopts the hand-made instances because their tags match, records one as `aws_instance.web[1]`, and plans to destroy the other one
K: B
G: ## How Terraform decides what exists
Terraform knows which real objects it manages through **state**, which binds each resource instance to one object ID. It never discovers objects by searching for matching tags or settings.

## Working the example
- During refresh, Terraform reads the three IDs recorded for `web[0]`, `web[1]` and `web[2]`. The object for `web[1]` no longer exists, so it is dropped from the refreshed state.
- The configuration still declares three instances, so the plan proposes `+ aws_instance.web[1]` (1 to add).
- The two hand-made instances are not in state. Terraform does not know about them and proposes nothing for them, so they keep running and costing money until someone imports or deletes them.

Tags are just arguments. They do not make an object part of a configuration.
W: Create web[1], ignore the rest: state shows `web[1]` missing, so one create is planned, and objects that state does not record are invisible to Terraform whatever their tags.
X: A=Destroy by tag: Terraform only destroys objects recorded in its state, so unmanaged instances are never planned for deletion.
C=Count by tag: `count = 3` refers to three instances tracked in state, not to any three running instances with a matching tag.
D=Adopt by tag: Terraform never adopts existing objects by matching tags; bringing an object under management takes an import.
T: Terraform manages only the objects recorded in its state; matching tags neither adopt nor destroy unmanaged objects.

@ TF-TA004 D2 T2.1 expert troubleshooting
S: A root module requires `aws` with `version = "~> 5.40"` and calls two modules: a public network module that declares `>= 5.50`, and an internal logging module, written years ago, that declares `version = "~> 5.55.0"`. The committed lock file records 5.55.3. The registry now lists 5.55.3, 5.58.1, 5.61.0 and 6.0.0, and a bug fix the team needs ships in 5.61.0. An engineer runs `terraform init -upgrade`, yet the lock file still shows 5.55.3. Team policy says reusable modules must follow HashiCorp's provider-constraint guidance, and the root module must keep blocking major upgrades. Which change lets the next `terraform init -upgrade` select 5.61.0?
A: Change the root module's constraint to `~> 5.61.0`, because the root module's requirement overrides child modules when Terraform selects versions
B: Change the network module's constraint to `>= 5.61`, because Terraform installs the highest minimum version declared among all the modules
C: Change the logging module's constraint to the minimum-only `>= 5.55`, leaving the root module's `~> 5.40` to block 6.0.0
D: Delete `.terraform.lock.hcl` and run `terraform init` without `-upgrade`, because the lock file is what holds the provider at 5.55.3 today
K: C
G: ## Why -upgrade stayed on 5.55.3
`-upgrade` ignores the lock file and picks the newest version that satisfies **all** constraints from the root and every child module. Here:
- `~> 5.40` allows `>= 5.40, < 6.0`.
- `>= 5.50` allows anything from 5.50 up.
- `~> 5.55.0` allows only the right-most component to grow: `>= 5.55.0, < 5.56.0`.

The intersection is 5.55.x, so 5.55.3 is already the newest acceptable version. The logging module's patch-level `~>` is the cap.

## HashiCorp's guidance
Reusable modules should declare only a **minimum** version (`>=`), and root modules should use `~>` to set both bounds. Changing the logging module to `>= 5.55` removes the cap, the root's `~> 5.40` still blocks 6.0.0, and `-upgrade` selects 5.61.0.
W: Minimum-only module constraint: removing the module's `~> 5.55.0` cap lets the intersection reach 5.61.0, while the root's `~> 5.40` keeps 6.0.0 out, matching both policies.
X: A=Root overrides: root and child constraints are equal and are intersected; `~> 5.61.0` and `~> 5.55.0` have no version in common, so init would fail.
B=Highest minimum: raising the network module's minimum to 5.61 conflicts with the logging module's `< 5.56.0`, so no version satisfies both.
D=Delete the lock file: without a lock file Terraform still applies every constraint, so the logging module's cap selects 5.55.3 again.
T: Provider constraints from all modules are intersected; reusable modules should set only a minimum so the root module controls the upper bound.

@ TF-TA004 D2 T2.3 expert troubleshooting
S: A root module had `provider "aws" { alias = "dr" region = "us-west-2" }` and one resource that used it, `aws_s3_bucket.replica` with `provider = aws.dr`. The disaster-recovery bucket is no longer needed, so in one commit an engineer deleted both the bucket's resource block and the `dr` provider block, reasoning that nothing would use the alias any more. Now `terraform plan` fails with an error that `aws_s3_bucket.replica` requires its original provider configuration `aws.dr`, which is no longer present. The bucket must be deleted, state must stay consistent, and the team allows no manual state edits. What is the correct way forward?
A: Restore only the `aws.dr` provider block, apply so Terraform destroys the bucket through it, and remove the provider block in a later commit
B: Restore only the bucket's resource block without a `provider` argument, so the default configuration destroys the bucket on the next apply
C: Run `terraform state rm aws_s3_bucket.replica` and delete the bucket in the console, since Terraform cannot destroy it without its resource block
D: Add `provider = aws` to a `removed` block for the bucket, so the default provider configuration performs the destroy of the deleted resource
K: A
G: ## Provider configurations outlive their resources
Terraform uses a resource's provider configuration for every operation on it, **including destroying it**. State records which provider configuration last managed each resource. When the resource block is deleted, that record tells Terraform which configuration to use for the destroy.

So all resources that belong to a provider configuration must be destroyed **before** the configuration's block is removed. If state still holds such a resource and the configuration is gone, the plan fails and asks you to reintroduce the provider configuration.

## Safe order
1. Delete the resource block but keep `provider "aws" { alias = "dr" ... }`.
2. Apply: Terraform destroys the bucket in us-west-2 through `aws.dr`.
3. Remove the provider block in a later change.
W: Restore the alias first: with `aws.dr` back, Terraform can destroy the bucket through the configuration recorded in state, and the block can go once nothing references it.
X: B=Default provider: the default configuration targets a different region and is not the one recorded for the bucket, and restoring the block keeps the bucket instead of deleting it.
C=state rm and console: this is the manual state edit the team forbids, and Terraform can destroy resources whose blocks are gone as long as their provider configuration exists.
D=provider in removed block: `removed` blocks accept `from`, `lifecycle` and provisioner settings, not a provider override, and they do not fix the missing configuration.
T: Destroy every resource of a provider configuration before deleting that configuration's block.

@ TF-TA004 D3 T3.4 expert use-case
S: At 10:00 a pipeline runs `terraform plan -out=release.tfplan` for commit A, and the change board approves the plan output at 10:40. Meanwhile, at 10:20, a developer pushed commit B to the same branch, which adds a required `owner` tag to every instance. The pipeline's apply job checks out commit B and runs `terraform apply release.tfplan` at 10:45. Nobody else changed the infrastructure or the state between 10:00 and 10:45. Auditors require that what is applied is exactly what was approved and nothing else. What happens, and is the audit requirement met?
A: Terraform applies commit B's configuration and uses the plan file only for approval metadata, so the tags go out unreviewed and the rule fails
B: Terraform merges commit B's tag change into the saved plan before applying, so unapproved changes are applied and the audit requirement fails
C: Terraform rejects the saved plan as stale because the checked-out files differ from commit A, so nothing is applied until a new plan is approved
D: Commit A's approved changes are applied from the plan file's own configuration copy; the tags wait for a later plan, meeting the rule
K: D
G: ## What a saved plan contains
`terraform plan -out=FILE` writes a plan file that contains the **full configuration**, all values associated with the planned changes, and the plan options including input variables. `terraform apply FILE` performs exactly those actions without prompting.

So the files checked out in the working directory at apply time do not change what is applied. Commit B's tags are not in the plan and will appear in the next plan.

## When a saved plan is rejected
A saved plan is rejected as stale when the **state** changed after the plan was made, for example because another apply ran. Here nobody touched state, so the plan applies normally. Because the plan file holds the configuration and any secrets in clear text, treat it as a sensitive artifact.
W: Plan file is self-contained: it carries commit A's configuration and planned actions, so only the approved changes are applied and the tag change waits for its own reviewed plan.
X: A=Metadata only: the plan file is the source of the actions applied, not just a record of approval.
B=Merging changes: Terraform never adds new configuration to a saved plan; it executes the plan as written.
C=Stale on file changes: staleness is detected against state, not against the configuration files in the working directory, and state did not change.
T: Applying a saved plan executes exactly the planned actions from its own configuration snapshot, regardless of later file edits.

@ TF-TA004 D3 T3.2 expert troubleshooting

The state at the old location must be copied to the new one, the old object must stay in place for a possible rollback, and the job runs with `-input=false` because nobody can answer prompts in CI. The first run of `terraform init -input=false` stops with an error saying the backend configuration has changed and that a migration or reconfiguration option is required. Which command lets the job continue as required?
A: `terraform init -upgrade -input=false`, which upgrades the backend to the new bucket and carries the state along with the provider plugins
B: `terraform init -migrate-state -force-copy -input=false`, which copies the state to the new bucket and answers the migration prompts with yes
C: `terraform init -migrate-state -input=false`, which copies the state silently because `-input=false` answers every migration prompt with yes
D: `terraform init -reconfigure -input=false`, which switches to the new bucket and copies the state there without asking any migration question

When the `backend` block changes in an initialized directory, `terraform init` must be told what to do with the existing state:

@ TF-TA004 D4 T4.4 expert troubleshooting
S: A storage module declares `variable "buckets" { type = map(object({ versioning = optional(bool, false), encrypted = optional(bool, false) })) }`. A team's tfvars file sets `buckets = { audit = { versioning = true, encrpyted = true } }`, with the attribute name misspelled. `terraform plan` succeeds with no error or warning, yet the audit bucket is planned without encryption, and compliance requires every audit bucket to be encrypted. The module is shared by 30 teams, so its authors must first explain to the auditors exactly why the plan looked valid. Which explanation is correct?
A: Terraform treats `encrpyted` as a new optional attribute with no default, stores it as `null`, and the provider reads `null` as unencrypted
B: The object type keeps only declared attributes, so `encrpyted` is discarded during conversion and `encrypted` falls back to its default `false`
C: Terraform reports undeclared attributes only for root module variables, so the module ignores it quietly, while a root variable would fail
D: The tfvars file is read after the defaults are applied, so `optional(bool, false)` overrides the value the team set for the audit bucket
K: B
G: ## Converting values to object types
An `object(...)` type constraint lists the attributes a value must have. When a value is converted to that type:
- every declared attribute must be present, unless it is declared with `optional(...)`;
- missing optional attributes get their default (or `null` without a default);
- **extra attributes are discarded during type conversion**, without an error.

## Working the example
`{ versioning = true, encrpyted = true }` has `versioning` (kept), no `encrypted` (optional, so the default `false` is used) and an unknown `encrpyted` (discarded). The result is `{ versioning = true, encrypted = false }`, which is a valid value, so plan succeeds.

Defaults fill only missing attributes; they never override a value that was supplied under the correct name.
W: Extra attribute discarded: conversion keeps only declared attributes, so the typo disappears and the optional default `false` applies to `encrypted`.
X: A=New attribute stored as null: object types cannot gain attributes; anything not declared is dropped, not kept as `null`.
C=Root modules reject extras: the same conversion rules apply to root and child module variables, so a root variable would drop the typo too.
D=Defaults override values: optional defaults apply only when an attribute is absent and never replace a supplied value.
T: Object type constraints silently discard attributes they do not declare, so a misspelled optional attribute falls back to its default.

@ TF-TA004 D4 T4.6 expert use-case
S: `aws_instance.app` uses `count = var.app_count` and `ami = data.aws_ami.base.id`, where the data source picks the newest image tagged `approved = true` with `most_recent = true`. Security publishes a new approved image every week, and every plan now proposes replacing all running instances. Operations wants existing instances left alone until a planned rollout, but any instance added by raising `app_count` must start from the newest approved image, and the data source must keep tracking new images for other consumers. Raising the count happens in the same applies as other routine changes. Which change meets all of these requirements?
A: Add `lifecycle { ignore_changes = [ami] }`, so updates ignore the new AMI ID while new instances still use it
B: Add `lifecycle { prevent_destroy = true }` to the instance, so replacements are refused while new instances still use the newest AMI
C: Add `depends_on = [data.aws_ami.base]` to the instance, so the AMI is read once at creation time and not evaluated again by later plans
D: Set `most_recent = false` on the data source, so it keeps returning the image that was selected when the instances were first created
K: A
G: ## ignore_changes applies to updates, not creation
`ignore_changes` lists attributes that Terraform **considers when planning a create** but **ignores when planning an update**. With `ignore_changes = [ami]`:
- existing instances keep their current AMI, even though the data source now returns a newer ID, so no replacement is planned;
- a new instance created because `app_count` grew uses the current value of `ami`, which is the newest approved image;
- the data source itself is unchanged and keeps tracking new images.

A planned rollout can later replace instances deliberately, for example with `terraform apply -replace=...` for each instance.

## The other options
`prevent_destroy` makes any plan containing a replacement fail, so every plan would error. Setting `most_recent = false` usually makes the lookup fail when several images match, and does not freeze the old image. `depends_on` only orders operations.
W: ignore_changes on ami: updates ignore the new AMI ID so running instances stay, while creation still uses the current lookup, so new instances get the newest image.
X: B=prevent_destroy: plans that include a replacement fail with an error, so every weekly plan breaks instead of leaving the instances alone.
C=depends_on on the data source: dependencies only order operations; the data source is still read on every plan and the replacements remain.
D=most_recent false: the data source stops tracking the newest image, which breaks the requirement for new instances and other consumers.
T: `ignore_changes` keeps existing resources from updating on an attribute while new instances are still created with its current value.
