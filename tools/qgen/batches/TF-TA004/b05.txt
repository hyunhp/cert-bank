@ TF-TA004 D5 T5.1 applied definition
S: A team keeps a reusable network module in the folder `modules/vpc` next to the root configuration. Which `source` value tells Terraform to load it from the local disk?
A: `source = "modules/vpc"`
B: `source = "./modules/vpc"`
C: `source = "local::modules/vpc"`
D: `source = "file:modules/vpc"`
K: B
G: ## How Terraform reads a module source
The `source` argument of a `module` block is a literal string, and Terraform decides what kind of location it is from the way the string starts.
- `./` or `../` means a path on local disk, relative to the calling module.
- `<NAMESPACE>/<NAME>/<PROVIDER>` (three parts) means the public Terraform Registry.
- `github.com/...`, `git::...`, `s3::...`, `gcs::...` and similar prefixes select a remote location.
A local module is not copied or downloaded as a separate package: it is loaded from the same repository as its caller, so it always has the caller's version.
W: The `./` prefix marks a local path. Terraform loads the module directly from the `modules/vpc` directory with no download step.
X: A=Bare relative path: without `./` or `../`, a two-part string like `modules/vpc` is not recognized as a local path; Terraform tries to interpret it as a registry address, which needs namespace, name and provider, and fails.
C=local:: prefix: Terraform has no `local::` source prefix. Local paths are recognized by `./` and `../`, not by a forced-getter prefix.
D=file: prefix: there is no `file:` form for module sources, so Terraform cannot classify the string as a valid location.
T: Local module sources must start with `./` or `../`; anything else is treated as a registry or remote address.

@ TF-TA004 D5 T5.1 applied definition
S: A platform team wants to use the public module published as `consul` by the `hashicorp` namespace for the `aws` provider. Which `source` address is correct?
A: `aws/consul/hashicorp`
B: `registry.terraform.io/consul-hashicorp-aws`
C: `terraform-aws-consul/hashicorp`
D: `hashicorp/consul/aws`
K: D
G: ## Registry module addresses
Modules in the public Terraform Registry are addressed as `<NAMESPACE>/<NAME>/<PROVIDER>`:
- the namespace is the publisher (for example `hashicorp`),
- the name describes what the module builds (for example `consul`),
- the provider is the main provider the module uses (for example `aws`).
Registry modules are the only kind that supports the `version` argument, because the registry protocol supports module versioning.
W: `hashicorp/consul/aws` follows the namespace, name, provider order that the public registry uses, so `terraform init` can look it up and download it.
X: A=Reversed order: `aws/consul/hashicorp` puts the provider first and the namespace last, so it points to a different (non-existent) module.
B=Hyphenated name: the registry has no single hyphen-joined address form; the three parts are separated by slashes.
C=Repository name: `terraform-<PROVIDER>-<NAME>` is the naming convention of the GitHub repository behind a published module, not the address used in `source`.
T: Public registry source = namespace/name/provider.

@ TF-TA004 D5 T5.1 applied use-case
S: Your company hosts modules in its HCP Terraform private registry (organization `example-corp`). The module `k8s-cluster` targets the `azurerm` provider. Which source address installs it?
A: `app.terraform.io/example-corp/k8s-cluster/azurerm`
B: `example-corp/k8s-cluster/azurerm`
C: `https://registry.terraform.io/example-corp/k8s-cluster`
D: `tfc::example-corp/k8s-cluster/azurerm`
K: A
G: ## Public versus private registry addresses
The three-part address with no hostname always refers to the public registry. Private registries live on a host of their own, so the host is added in front.
- HCP Terraform private registry: `app.terraform.io/<NAMESPACE>/<NAME>/<PROVIDER>`, where the namespace is the organization name.
- Terraform Enterprise: `<HOSTNAME>/<NAMESPACE>/<NAME>/<PROVIDER>` with your deployment hostname.
Private registry modules support the `version` argument in the same way as public ones.
W: Prefixing the address with `app.terraform.io` sends the request to the HCP Terraform private registry of the organization instead of the public registry.
X: B=No hostname: `example-corp/k8s-cluster/azurerm` is looked up in the public registry, where this organization's private module does not exist.
C=Registry website URL: a browser URL of the public registry is not a module source address; the registry protocol uses the short host-and-path form.
D=Invented prefix: Terraform has no `tfc::` getter; the supported prefixes are things like `git::`, `s3::` and `gcs::`.
T: Add the registry hostname in front of namespace/name/provider for any registry other than the public one.

@ TF-TA004 D5 T5.1 applied use-case
S: A module lives in a Git repository and the team must always install the code tagged `v1.2.0`, not the default branch. Which configuration does that?
A: `source = "git::https://example.com/vpc.git"` with `version = "v1.2.0"`
B: `source = "git::https://example.com/vpc.git#v1.2.0"`
C: `source = "git::https://example.com/vpc.git?ref=v1.2.0"`
D: `source = "git::https://example.com/vpc.git"` with `tag = "v1.2.0"`
K: C
G: ## Selecting a revision from Git
Without extra information, Terraform runs `git clone` and uses the default branch referenced by `HEAD`. To choose another revision, add the `ref` query parameter to the source URL. It accepts a branch name, a tag, or a short or full SHA-1 commit hash.
- `?ref=v1.2.0` selects a tag.
- `?ref=51d462976d84fdea54b47d80dcabbf680badcdb8` selects an exact commit.
- `?depth=1` makes a shallow clone; combine with `&ref=...`.
The `version` argument is not available for Git sources, because only registries understand versions.
W: `?ref=v1.2.0` on the source URL makes Terraform check out the tagged revision when it clones the repository.
X: A=version with Git: the `version` argument works only for modules listed in a registry; Terraform rejects it for a Git source.
B=Fragment syntax: `#v1.2.0` is the Mercurial-style revision suffix, not a Git form; a Git URL uses the `ref` query parameter.
D=tag argument: the `module` block has no `tag` argument, so Terraform reports an unsupported argument.
T: Pin Git modules with `?ref=` on the source; `version` is for registry modules only.

@ TF-TA004 D5 T5.1 advanced use-case
S: The Git repository `network.git` holds several modules, and the one you need is in `modules/vpc`. You also want tag `v1.2.0`. Which source is written correctly?
A: `git::https://example.com/network.git//modules/vpc?ref=v1.2.0`
B: `git::https://example.com/network.git?ref=v1.2.0//modules/vpc`
C: `git::https://example.com/network.git/modules/vpc?ref=v1.2.0`
D: `git::https://example.com/network.git::modules/vpc?ref=v1.2.0`
K: A
G: ## Sub-directories inside a package
A repository or archive that Terraform downloads is called a package. A double slash `//` marks where the package address ends and the path to the module inside it begins.
- Terraform extracts the entire package, then reads the module from the sub-directory.
- Query parameters such as `ref` go after the sub-directory.
- Other modules in the same package can then be referenced with relative paths such as `../shared`.
The same `//` syntax works for registry modules (`hashicorp/consul/aws//modules/consul-cluster`) and archives.
W: The `//` separates the repository from `modules/vpc`, and `?ref=v1.2.0` follows the sub-directory, as Terraform expects.
X: B=Query before sub-directory: the `ref` parameter must come after the `//` sub-directory path; placed earlier, the path is parsed as part of the query value.
C=Single slash: with one slash the whole string is just a longer repository path, so Terraform would try to clone a repository named `network.git/modules/vpc`.
D=Double colon: `::` is used for the getter prefix such as `git::`, not to select a directory in the package.
T: Use `//` to pick a sub-directory and put `?ref=` after it.

@ TF-TA004 D5 T5.1 applied use-case
S: A team stores a packaged module as `vpc.zip` in an Amazon S3 bucket and installs it with `terraform init`. Which TWO statements are accurate? (Select TWO)
A: The `source` must start with `s3::` followed by the object URL, and the object must be an archive such as `.zip` or `.tar.gz`.
B: The `source` can point to an S3 bucket prefix that holds plain `.tf` files, and Terraform downloads every file under it.
C: Terraform looks for AWS credentials in the usual places, such as the `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY` environment variables or the default shared credentials profile.
D: Credentials are read from the access key arguments that must be placed inside the `module` block.
E: The `version` argument selects the S3 object version to download.
K: A,C
G: ## Object storage as a module source
Terraform can fetch a module from an archive in Amazon S3 (`s3::`) or Google Cloud Storage (`gcs::`). The installer extracts the archive, so the stored object must be a supported archive format (`.zip`, `.tar.gz`, `.tgz`, `.tar.bz2`, `.tar.xz` and similar).
An example is `s3::https://s3-eu-west-1.amazonaws.com/examplecorp-terraform-modules/vpc.zip`.
## Credentials
The installer does not take secrets in the `module` block. For S3 it checks the AWS environment variables, then the default profile in the shared credentials file, then the instance profile when running on EC2. For GCS it uses Google Cloud credentials such as `GOOGLE_APPLICATION_CREDENTIALS`.
W: A=s3:: archive source: the `s3::` prefix with an object URL is the S3 form, and the object has to be an archive that Terraform can extract.
C=Standard AWS credential lookup: the module installer finds credentials from the environment variables, the default profile, or an EC2 instance profile.
X: B=Plain files in a prefix: the installer fetches one archive object and extracts it; it does not copy a folder of loose `.tf` files.
D=Credentials in the module block: the `module` block has no credential arguments; unknown arguments are treated as module inputs and would fail validation.
E=version for S3: `version` applies only to registry modules; S3 sources have no module versioning mechanism of their own.
T: S3 and GCS sources are archives extracted at init, authenticated with the cloud's normal credential chain.

@ TF-TA004 D5 T5.1 applied definition

Some sources need a prefix so Terraform knows which download method to use. `git::`, `hg::`, `s3::` and `gcs::` are such prefixes. For Google Cloud Storage the prefix is followed by the object's JSON API URL, in the form `gcs::https://www.googleapis.com/storage/v1/BUCKET_NAME/PATH/TO/module.zip`.

@ TF-TA004 D5 T5.1 applied troubleshooting
S: A new engineer clones the repository, runs `terraform init`, and asks where the module code was downloaded, since there is no folder for it next to the `.tf` files. What is the answer?
A: Terraform keeps modules only in memory during the run and re-downloads them for every `plan`.
B: Terraform copies the module into a `modules/` folder at the root of the working directory, next to `main.tf`.
C: Terraform stores it in the state file, which carries the module source code with the resources.
D: Terraform clones the module into a hidden subdirectory of the working directory (under `.terraform`).
K: D
G: ## What init does for modules
During `terraform init`, Terraform scans the configuration for `module` blocks and retrieves the source code of each one from its `source`. The code is placed in a hidden subdirectory of the working directory, so the files stay out of your way and are normally excluded from version control.
Because the downloaded copy is local, later `plan` and `apply` runs do not need to download again. Re-running `init` installs only modules added since the last run unless you pass `-upgrade`.
W: The hidden `.terraform` subdirectory is where `terraform init` installs module sources, which is why nothing new appears beside the configuration files.
X: A=In memory only: modules are installed to disk once at init, and later commands read them from there.
B=Visible modules folder: a `modules/` directory in your repository is something a team creates for its own local modules; Terraform does not write there.
C=In the state file: state records resource instances and their attributes, not the module source code.
T: `terraform init` installs module code into the hidden `.terraform` directory.

@ TF-TA004 D5 T5.2 applied troubleshooting
S: The root module declares `variable "region"`. The child module in `./modules/app` uses `var.region` but declares no variable, and the `module` block passes nothing. What does Terraform do?
A: It reads the root module's `region` value automatically because both are in the same configuration.
B: It uses the provider's configured region as a fallback value for `var.region`.
C: It reports an error because `var.region` is not declared in the child module.
D: It prompts for `region` at the command line during `terraform apply`.
K: C
G: ## Each module has its own scope
A module is a self-contained unit. Its variables, locals and resources exist only inside it, and nothing flows in unless a value is passed explicitly.
- To give a child a value, declare `variable "region" {}` in the child and set `region = var.region` in the `module` block.
- A child cannot read the parent's variables, locals or resources; there is no inheritance, even for the same name.
Without the declaration, Terraform reports "Reference to undeclared input variable" for `var.region` in the child.
W: The child module has no `region` input variable, so its reference is invalid. The fix is to declare the variable there and pass the root value in the `module` block.
X: A=Automatic inheritance: variables are not shared between modules; names matching in parent and child are unrelated.
B=Provider fallback: a provider block's region has no connection to input variables; `var.region` only exists when declared.
D=Prompt: interactive prompting applies to unset root module variables; the error here is about an undeclared reference, found before any prompt.
T: Modules do not see their parent's variables; declare an input and pass it in the `module` block.

@ TF-TA004 D5 T5.2 applied use-case
S: The child module `./modules/network` creates `aws_vpc.this`. The root module needs the VPC ID for a security group. What should the team do?

Resources inside a child module are encapsulated. The caller can see only what the module author exposes through `output` blocks, using `module.<LABEL>.<OUTPUT_NAME>`.
This keeps the interface small: the module may rename or replace internal resources, as long as the outputs stay stable.
Variables work the other way around: they bring values in. They cannot return a value to the caller.
W: An `output` in the child exposes the ID, and the root reads it with `module.network.vpc_id`, the supported way to pass a value upward.
X: A=Direct resource reference: the root cannot address resources inside a child module; only declared outputs are available through the `module.<label>` reference.

@ TF-TA004 D5 T5.2 applied comparison
S: Which TWO statements about scope between a root module and its child module are accurate? (Select TWO)
A: Local values defined in a child module can be read by the root module as `module.<label>.local.<name>`.

K: C,D
G: ## One-way, explicit interfaces
A module has two public surfaces: inputs (variables) going in and outputs coming out. Everything else, including locals and resources, is private.
- Parent to child: `module` block arguments set the child's input variables.
- Child to parent: `output` blocks, read as `module.<label>.<output>`.
- Locals are private naming helpers; they cannot be reached from outside the module that defines them.
W: C=Outputs as the only exit: the root sees a child's resource attributes only when an output exposes them.
D=Inputs as the only entry: the child's variables are filled from arguments in the `module` block (or defaults), and nothing else crosses the boundary.
X: A=Reading child locals: locals are private to their module; the `module.<label>` reference exposes outputs only.
B=Reading parent locals: locals do not cross module boundaries in either direction, so the child cannot use the root's local value.
E=Reading all root variables: a child cannot use the root's variables; it has to declare its own and receive the values.
T: Only inputs go in and outputs come out; locals, variables and resources of another module are out of reach.
