@ TF-TA004 D2 T2.4 applied troubleshooting
S: Which TWO risks come from the default local state file `terraform.tfstate`? (Select TWO)
A: It can hold sensitive values, such as initial database passwords, as plaintext JSON.
B: It is unreadable by `terraform show` until it has been encrypted with a customer key.
C: Keeping it in Git risks leaking secrets and losing data, because Git has no state locking.
D: It has to be regenerated by running `terraform init` before each new plan is created.
E: It is kept in sync for each team member who clones the repository, without extra setup.
K: A,C
G: ## What is in the state file
State is a JSON file recording the attributes of every managed resource, and those attributes can include sensitive values like passwords or tokens, whether or not your configuration marks them sensitive. By default it is stored locally as `terraform.tfstate` (with `terraform.tfstate.backup` for the previous version), in plaintext.
- Treat it as sensitive data and keep it out of Git; a version control system gives neither locking nor access control suited to state.
- For teams, use HCP Terraform or a remote backend so everyone works with the same, secured state.
W: A=Plaintext secrets: resource attributes, including secrets, are written to the local state file.
C=Keeping it in Git: VCS lacks state locking and secure access control, so storing state there risks data loss and exposure of secrets.
X: B=Needs encryption to be read: `terraform show` reads plaintext state directly.
D=Regenerated by init: `init` does not create or rebuild state; state is written by apply and refreshed by plan.
E=Kept in sync for clones: it is only shared if committed, which is discouraged; otherwise each clone has its own, or no, state.
T: State holds plaintext secrets and needs secure, shared storage rather than Git.

@ TF-TA004 D8 T8.4 applied comparison
S: A company runs a self-hosted Terraform Enterprise instance at `tfe.example.com` and wants developers' CLIs to use its workspaces. Which statement is accurate?
A: Terraform Enterprise needs a `backend "enterprise"` block, since the `cloud` block targets HCP Terraform
B: Self-hosted instances run VCS-driven workflows, and the CLI-driven workflow is reserved for HCP Terraform
C: A `cloud` block with `hostname = "tfe.example.com"` plus `terraform login tfe.example.com` on each machine
D: Developers first create an HCP Terraform organization, since Terraform Enterprise delegates CLI logins to it
K: C
G: ## HCP Terraform and Terraform Enterprise
HCP Terraform is the hosted service at `app.terraform.io`. Terraform Enterprise is the self-hosted distribution of the same platform that you run in your own environment. The workflows (VCS, CLI, API), workspaces, projects, teams, policy enforcement and registry are shared concepts.
To point the CLI at a Terraform Enterprise instance:
```
terraform {
  cloud {
    hostname     = "tfe.example.com"
    organization = "acme"
    workspaces { name = "app-prod" }
  }
}
```
`terraform login tfe.example.com` then obtains a token for that host, as the login command works with any server that supports the login protocol. Without `hostname`, the block targets `app.terraform.io`.
W: Hostname in the cloud block: the same block and login command work against Terraform Enterprise once the host name is set; without `hostname` the block targets `app.terraform.io`.
X: A=backend enterprise: no such backend exists; the `cloud` block is used for both HCP Terraform and Terraform Enterprise.
B=CLI reserved for HCP Terraform: CLI-driven runs are supported by the same platform on self-hosted instances.
D=HCP organization first: Terraform Enterprise has its own organizations and tokens; HCP Terraform is not involved.
T: Same cloud block for both products; set hostname (and log in to that host) for Terraform Enterprise.
