@ TF-TA004 D4 T4.1 applied troubleshooting
S: One configuration creates aws_vpc.main and also has a data "aws_subnets" block whose filter uses aws_vpc.main.id. On the first plan, the VPC does not exist yet. What does Terraform do with the data block?
A: It fails the plan with an error, because a data source can only look up objects that already exist before the plan starts
B: It postpones the read to the apply phase and shows the data source's attributes as known after apply in the plan
C: It reads the data source twice, once with an empty filter during plan and again with the real VPC ID during apply
D: It silently creates the subnets that the filter would have matched, so that the data source always has a result
K: B
G: ## When Terraform reads a data source
Terraform tries to query data sources while planning. If every argument is already known, it reads the data during the refresh phase of the plan, so the plan shows the real values.

When an argument refers to something Terraform cannot predict yet, such as an attribute of a resource that is being created in this plan, the read is **deferred to the apply phase**. The plan output tells you this, and every attribute of that data source is shown as computed (known after apply).

A consequence is that resources whose arguments use the data source's results can only be fully evaluated during apply.
W: Deferred read: the filter depends on aws_vpc.main.id, which is unknown until the VPC exists, so Terraform waits and reads the data during apply, marking its attributes as known after apply.
X: A=Plan error: a plan with an unknown argument is not an error. Terraform simply postpones the lookup instead of failing.
C=Two reads: Terraform does not run a data source with a placeholder filter. It reads the data once, when all arguments are known.
D=Creating objects: data sources are read-only and never create or change anything, so no subnet is created to satisfy a lookup.
T: A data block that depends on a value unknown at plan time is read during apply, and its attributes show as known after apply.

@ TF-TA004 D4 T4.1 applied comparison
S: A team deletes both a resource "aws_s3_bucket" "logs" block and a data "aws_s3_bucket" "shared" block from the configuration, then runs terraform apply and accepts the plan. What happens to the real buckets?
A: Both buckets are destroyed, because Terraform removes every object that no longer appears in the configuration
B: Neither bucket is touched, because Terraform only compares configuration with state when a block is edited and not when it is deleted
C: The bucket from the resource block is destroyed, and the bucket from the data block is left alone because Terraform only read it
D: The bucket from the data block is destroyed first, and the bucket from the resource block is kept so the state can be rebuilt
K: C
G: ## Managed objects versus read-only lookups
Terraform compares the configuration with the objects recorded in state. A `resource` block declares an object that Terraform **manages**. If the block disappears from configuration but the object is still in state, the plan proposes to destroy it.

A `data` block only reads. Removing it stops Terraform from querying the object, but the real object was never owned by this configuration, so nothing is deleted.

To stop managing a resource without destroying the real object, you would remove it from state or use a `removed` block with `destroy = false`, which are covered in the state sections of the exam.
W: Resource versus data: the managed bucket is in state and no longer configured, so the plan destroys it. The looked-up bucket was only read, so deleting the data block has no effect on the real bucket.
X: A=Everything destroyed: only objects Terraform manages are planned for destruction. A data source never gave Terraform ownership of the bucket.
B=No change on delete: deleting a managed block is exactly what triggers a destroy action in the plan, so the claim that nothing happens is wrong for the managed bucket.
D=Data bucket destroyed: this reverses the roles. Terraform never destroys what a data block merely reads, and it does not keep the managed bucket to rebuild state.
T: Removing a resource block plans a destroy of the real object, while removing a data block changes nothing in the cloud.

@ TF-TA004 D4 T4.1 advanced definition
S: Which TWO statements about meta-arguments and lifecycle rules on data blocks are accurate? (Select TWO)
A: A data block can use count or for_each, and the reference then returns a list or a map of the queried objects
B: A data block can set lifecycle prevent_destroy = true to keep the looked-up object from being deleted
C: A data block accepts provisioner blocks, which run after the lookup and can change the queried object
D: A data block can contain a lifecycle block with a postcondition that checks the result of the lookup
E: A data block can set create_before_destroy so the lookup runs before the old query result is discarded
K: A,D
G: ## What a data block shares with a resource block
Data blocks are read-only, but they still take part in the dependency graph and support several of the built-in arguments: `count`, `for_each`, `depends_on` and `provider`. With `count`, `data.<TYPE>.<NAME>` becomes a list of objects, and with `for_each` it becomes a map of objects.

A data block may also contain custom conditions in a `lifecycle` block. A `postcondition` runs after the data source is read and can use `self` to check what came back, for example that an AMI has the expected architecture.

Lifecycle rules that concern destroying or replacing objects make no sense for a lookup, because a data source never creates, updates or destroys anything.
W: A=count and for_each: data blocks accept both, so one block can query several objects and the reference becomes a list or a map.
D=Postcondition: a lifecycle postcondition on a data block verifies the result right after the read and stops the run with its error message if the guarantee does not hold.
X: B=prevent_destroy: there is nothing to destroy, because Terraform never deletes what a data block reads. The rule applies to resource blocks.
C=Provisioners: provisioners run on managed resources that Terraform creates. A read-only data block cannot change the queried object.
E=create_before_destroy: this controls the order of replacing a managed object. Data blocks are not replaced, so it does not apply.
T: Data blocks support count, for_each and postconditions, but not destroy-related lifecycle rules or provisioners.

@ TF-TA004 D4 T4.2 applied troubleshooting
S: aws_instance.web uses count = 2. An output sets value = aws_instance.web.id, and terraform plan fails. Which change fixes the reference to return every instance ID?

`<TYPE>.<NAME>` is an **object** only when the resource has neither `count` nor `for_each`. With `count`, the reference is a **list** of instance objects, so a bare `aws_instance.web.id` has no `id` attribute at that level and Terraform reports an error.

- `aws_instance.web[*].id` is a splat expression that returns a list of all the `id` values.

W: Splat expression: with count the resource is a list of instances, and [*].id collects the id attribute from every element into a list.
X: B=each.id: there is no each attribute on a resource reference. each.key and each.value exist only inside a resource that uses for_each.
C=count.id: count.index is available inside the counted block, but a reference to another resource has no count attribute.
D=data prefix: a data. reference points to a data block. The instances are managed resources, so this address would not exist.

@ TF-TA004 D4 T4.2 applied definition
S: A module has locals { region = "us-east-1" } and also variable "region" with a different default. A resource argument must use the value from the locals block. Which reference is correct?

Every named value in a module is read with a fixed prefix, which is separate from the name of the block that declares it:
- `var.<NAME>` is an input variable.
- `local.<NAME>` is a local value, even though it is declared in a `locals` block.

@ TF-TA004 D4 T4.4 applied use-case
S: A variable must hold exactly three values in this order: a hostname (string), a port (number) and a TLS flag (bool), for example ["web", 443, true]. Which type constraint enforces both the length and the type of each position?
A: list(any), which lets Terraform pick one element type for the list and accepts any length, including exactly three entries
B: list(string), which converts the port and the flag to strings, accepts any length, and so enforces neither position nor type
C: tuple([string, number, bool]), which requires exactly three elements with matching types by position
D: object({ host = string, port = number, tls = bool }), which names each attribute and accepts the three-item list directly
K: C
G: ## Tuples versus lists
- `list(T)` is a sequence where **every** element has the same type, and it can have any length.
- `tuple([T1, T2, T3])` is a sequence with a fixed length where **each position has its own type**.
- `object({ ... })` has named attributes, so a bare list does not match it.

`tuple([string, number, bool])` matches `["web", 443, true]` and rejects values with two or four elements. Use tuples when position carries meaning and types differ; use lists for homogeneous collections.
W: Tuple: the constraint lists a type per position and fixes the number of elements, so it accepts the required three-item value and nothing longer or shorter.
X: A=list(any): any picks a single element type for the whole list, so mixed types would be converted or rejected, and the length is not limited to three.
B=list(string): it would turn 443 and true into strings and accept lists of any length, so neither the length nor the types are enforced.
D=object: an object needs named attributes, so a list literal does not match. Use it for maps with known keys, not positional values.
T: A tuple fixes length and per-position types; a list has one element type and any length.

@ TF-TA004 D4 T4.4 advanced troubleshooting
S: A module declares variable "limits" with type = map(string). A caller passes { cpu = 2, memory = "4Gi" }. What happens?
A: Terraform rejects the value, because the number 2 is not a string and no conversion is ever done for variable types
B: Terraform accepts the value and converts 2 to the string "2" so every map element matches the declared string type
C: Terraform accepts the value only after the caller turns it into an object type, because a map cannot hold a number
D: Terraform keeps cpu as a number and memory as a string, because a map allows a different type for each value

G: ## Automatic type conversion
Terraform converts values to match a type constraint when it can. For primitives, a `number` or `bool` converts to `string` and back as long as the text is a valid number or boolean. In a `map(string)`, a value `2` becomes `"2"`.

Conversion fails only when a value is incompatible, for example a list given where a string is expected, which produces a type mismatch error.

All values in a `map(...)` share one element type. If you need different types per key, use an `object({ ... })` type with named attributes.
W: Element conversion: a map(string) requires string elements, and Terraform converts the number 2 to "2" automatically, so the value is accepted.
X: A=No conversion: Terraform does automatic conversion between primitive types whenever the value is a valid representation, so the number is accepted.
C=Object-only numbers: a map can hold numbers (map(number)); the caller does not need an object. Here the element is simply converted.
D=Mixed element types: a map has one element type. The value cpu = 2 does not stay a number under map(string).
T: A map(string) converts numbers and bools to strings, while an object type is needed for different types per key.

@ TF-TA004 D4 T4.4 applied troubleshooting
S: A variable has type = set(string). The configuration uses var.zones[0] and fails. Which statement explains the failure and a fix?
A: Sets are unordered and have no index, so convert with tolist(var.zones) first, or declare the variable as list(string)
B: Sets only hold numbers, so the values must be converted with tonumber before they can be indexed
C: Square-bracket indexing works only on maps, so the variable must be declared as map(string) to use [0]
D: Sets can be indexed only inside a for_each block, so the expression must move into a resource that uses for_each
K: A
G: ## Sets have no positions
A `set(T)` is a collection of **unique** values with no ordering and no secondary identifiers. Because there is no position, `var.zones[0]` is not valid. Converting a list to a set also drops duplicates and loses the order.

If you need an index, declare `list(string)`, or convert with `tolist()`. For a set of strings the converted list is in lexicographical order, but sets of other types do not guarantee any order.

Sets are the natural input for `for_each`, which needs unique keys.
W: No positions: a set has no order, so numeric index access fails. Converting it with tolist(), or choosing a list type from the start, gives a sequence that can be indexed.
X: B=Numbers only: sets can hold any element type, such as set(string), and the type here is already string.
C=Maps only: lists and tuples are indexed with numbers. Maps use string keys, so declaring map(string) would not make [0] meaningful.
D=for_each only: indexing is an expression feature and does not depend on for_each. A set simply has no index to look up.
T: A set has no order or index; convert it with tolist() or use a list when you need positions.

@ TF-TA004 D4 T4.6 applied use-case

`prevent_destroy = true` makes Terraform reject any plan that would destroy or replace the object **while the argument is present in the configuration**. It also stops `terraform destroy`.

@ TF-TA004 D4 T4.6 applied use-case
S: A security tool adds tags to EC2 instances after creation. The resource sets lifecycle { ignore_changes = [tags] }. Later an engineer changes the tags argument in the configuration. What does terraform plan show for the tags?
A: No change for tags, because the attribute is ignored when planning updates to the existing instance
B: An update that replaces the tags written by the tool, because configuration changes always override ignored attributes
C: A replacement of the whole instance, because changing an ignored attribute forces recreation
D: An error, because ignore_changes cannot be used with attributes that also appear in the configuration
K: A
G: ## What ignore_changes does
Normally Terraform compares the configuration with the real object and plans an update for every difference. `ignore_changes` names attributes that Terraform should **ignore when planning updates** to an existing object. It is useful when another process also manages an attribute, such as tags added by a tool or a desired capacity changed by autoscaling.

Important details:
- The attribute is still used when the object is first created.
- Edits to the ignored attribute in configuration also produce no update later.
- `ignore_changes = all` ignores every attribute, so Terraform can create and destroy the object but never update it.
- Only literal attribute names are allowed, and you cannot ignore meta-arguments.
W: Ignored attribute: Terraform leaves the existing tags alone in the plan, whether the difference comes from the tool or from a later edit of the configuration.
X: B=Override: the whole point of ignore_changes is that neither external changes nor later configuration edits create an update for that attribute.
C=Forced replacement: ignoring an attribute removes it from the diff. It never causes recreation.
D=Configuration conflict: the attribute is normally set in the configuration, so the setting is allowed and used when the object is created.
T: ignore_changes removes the listed attributes from update planning, including later configuration edits.

@ TF-TA004 D4 T4.6 advanced definition
S: Which TWO statements about the depends_on meta-argument are accurate? (Select TWO)
A: It is meant for hidden dependencies, where one object relies on the behavior of another without referencing any of its attributes
B: It accepts any expression, such as a conditional or a function call, as long as the final result is a list of resource address strings
C: It can be set in module blocks as well as in resource blocks, and it takes a list of references to resources or modules
D: It is required whenever one resource uses an attribute of another resource, otherwise the order is undefined
E: It replaces the implicit dependency created by a reference, so the reference is then ignored
K: A,C
G: ## Explicit dependencies
Most dependencies are **implicit**: when an argument refers to another object's attribute, Terraform orders them automatically. `depends_on` handles the rare **hidden** dependency, such as an IAM policy that must exist before an instance's startup script can call an API, when the instance never mentions the policy.

Rules:
- It works in `resource` blocks (all types) and in `module` blocks.
- The value is a **list of references** to resources or child modules in the same calling module. Arbitrary expressions are not allowed, because the value must be known before Terraform can evaluate expressions.
- It adds to the graph and never removes dependencies created by references.

Use it sparingly, because it can make plans less precise.
W: A=Hidden dependencies: use depends_on when the relationship cannot be seen from attribute references, for example an instance that needs a policy attachment to exist first.
C=Resources and modules: the argument is available in resource and module blocks and requires a list of references, not values.
X: B=Arbitrary expressions: the list must be static references, since it must be known before expressions can be evaluated.
D=Required for references: a reference already creates the dependency automatically, so depends_on is unnecessary there.
E=Replaces references: depends_on only adds edges. Implicit dependencies from references still apply.
T: depends_on is a list of resource or module references for hidden dependencies; it adds to, not replaces, implicit ones.

@ TF-TA004 D4 T4.7 applied use-case
S: A data "aws_ami" block looks up an image, and the team wants the lookup itself to stop the run with a clear message when the returned image is not x86_64. Which placement is correct?
A: A precondition block in the instance that uses the AMI, which attaches the rule to the consumer and not to the lookup
B: A check block with a data block named after the AMI, which warns but lets the instance be created anyway
C: A validation block in the variable that holds the AMI name, which tests the architecture of the result
D: A postcondition in the data block's lifecycle that tests self.architecture == "x86_64"
K: D
G: ## Guarantees on a data source
Custom conditions are written inside a `lifecycle` block on resources and data sources. A `postcondition` runs after Terraform reads the data source (or applies the resource), and it can use `self` to refer to the object's own attributes. It is the right tool for a **guarantee** about the result, like an architecture.

```
data "aws_ami" "app" {
  owners = ["self"]
  lifecycle {
    postcondition {
      condition     = self.architecture == "x86_64"
      error_message = "The image must be x86_64."
    }
  }
}
```
If a postcondition fails, Terraform stops with the error message. A `check` block would only warn, and variable validation runs before any lookup, so it cannot see the result.
W: Postcondition on the data block: it runs immediately after the read, can inspect the result through self, and blocks the run with the error message if the architecture is wrong.
X: A=Instance precondition: an instance precondition can test the image, but it is attached to the consumer and runs before the instance is created, so it does not make the lookup itself fail. Data blocks can hold conditions.
B=check block: a failed check only reports a warning and the operation continues, so the instance would still be created.
C=Variable validation: validation runs before planning and can only test the input value, not the attributes returned by a later lookup.
T: Use a postcondition with self on the data block to guarantee properties of what the lookup returns.

@ TF-TA004 D4 T4.7 applied definition
S: A check block contains a nested data "http" "status" block. Which statement about that data source is accurate?
A: It can be referenced from any resource in the module, and its result is stored in state for later runs
B: It runs only when the check block is placed inside a resource block as a lifecycle rule
C: It is scoped to the check block and can be referenced only from that block's assert conditions
D: It is required to be a managed resource, so the block fails if a data source is used
K: C
G: ## Scoped data sources in check blocks
A `check` block runs as the last step of plan or apply and holds one or more `assert` blocks. A check can contain a nested `data` block, called a **scoped data source**, to fetch a value only for the assertion, such as the status code of a website.

```
check "health" {
  data "http" "site" {
    url = "https://example.com"
  }
  assert {
    condition     = data.http.site.status_code == 200
    error_message = "Site unhealthy"
  }
}
```
The data block can be referenced only inside its parent check. If the scoped data source itself fails to read, Terraform reports a warning rather than an error, so the check never blocks the run.
W: Scoped data source: the nested data block exists only for its check and can be referenced by that check's asserts, which keeps validation lookups separate from the real configuration.
X: A=Usable everywhere: the data source cannot be referenced outside its parent check, which prevents resources from depending on a lookup meant only for testing.
B=Lifecycle rule: check is a top-level block and not a lifecycle setting. It runs at the end of plan and apply.
D=Managed resource: the nested block must be a data block. Checks are for read-only validation and do not manage anything.
T: A data block inside a check is scoped to that check and is used by its asserts only.

@ TF-TA004 D4 T4.7 advanced comparison
S: Which statement about when Terraform evaluates custom validations during a run is accurate?
A: Input variable validations run first, before Terraform generates a plan, and check blocks run last
B: Preconditions run after the apply finishes, in the same step as postconditions
C: Check block assertions run first in the operation, so a failed check can stop resources from being created
D: Variable validations are skipped during plan and only run when the variable is used by a resource
K: A
G: ## Order of validations
1. **Input variable validation** runs immediately, before a plan is generated.
2. **Preconditions** run after the plan is generated but before the resource, data source or output is created.
3. **Postconditions** run after planning and applying changes to a resource, or after reading a data source.
4. **Check blocks** run at the end of plan and apply, after everything else.

Variable validation, preconditions and postconditions block the operation when they fail. Only `check` blocks produce warnings and continue. When a value is known during planning, Terraform may evaluate the condition during the plan phase.
W: Variables first, checks last: variable validation is the earliest step and check blocks are the final step of plan and apply, with preconditions and postconditions in between.
X: B=Preconditions after apply: preconditions run before the object is created, so they can prevent a bad change and cannot verify the result.
C=Checks first: a check runs last and only warns, so it can never stop resource creation.
D=Skipped in plan: variable validation does not wait for a resource to use the variable, and it fails early.
T: Variable validation runs first, preconditions before creation, postconditions after, and checks last as warnings.

@ TF-TA004 D4 T4.8 applied use-case
S: A resource sets password_wo = ephemeral.random_password.db.result and password_wo_version = 1. Months later security wants to rotate the password. What should the engineer do so the database receives a new value?
A: Change the ephemeral resource only, because Terraform compares write-only values in state and notices the new password
B: Increase password_wo_version, because Terraform cannot read write-only values back and uses the version to detect a change
C: Run terraform refresh, because it reads the write-only value from the provider and updates state
D: Mark password_wo with sensitive = true, because sensitive values are re-sent on every plan
K: B
G: ## Write-only arguments and versions
A write-only argument is available during the current operation only. Terraform sends the value to the provider and **never stores it in state or plan files**. A consequence is that Terraform has nothing to compare with next time, so a changed value alone does not appear as a difference.

Providers therefore pair a write-only argument with a companion version argument, for example `password_wo` and `password_wo_version`. To make the provider send a new value, change the version number, such as from `1` to `2`. The difference in the version (which is stored) tells Terraform to update the resource and send the current ephemeral value.

Write-only arguments need Terraform 1.11 or later, and each provider defines which ones exist.
W: Bump the version: the write-only value is not stored, so Terraform cannot detect a new password. A changed version number is stored, shows in the plan as an update, and triggers sending the current value.
X: A=Compare in state: write-only values are not in state, so there is no stored value to compare and a changed ephemeral value is invisible.

@ TF-TA004 D4 T4.8 applied definition
S: Which TWO places can reference an ephemeral resource, such as ephemeral.random_password.db.result, without a plan error? (Select TWO)
A: A normal argument of a managed resource, because the value is discarded after the apply
B: A write-only argument of a managed resource

D: The provider block, for example to configure a provider with a temporary credential
E: A resource attribute that Terraform stores in state so later runs can compare it
K: B,D
G: ## Where ephemeral values can be used
Ephemeral resources exist only during a Terraform operation and are not saved in state or plan files. Terraform therefore allows them only in **ephemeral contexts**, where the value will not be persisted:
- a managed resource's write-only argument
- another `ephemeral` block
- `locals`
- `variable` blocks with `ephemeral = true`
- child module `output` blocks with `ephemeral = true`
- a `provider` block
- provisioner and connection configuration

Using one in a normal resource argument, or in an output that would be saved, would persist it, so Terraform raises an error while planning.
W: B=Write-only argument: the provider receives the value during the operation and Terraform discards it, so it never reaches state.
D=Provider block: provider configuration is not persisted in state, so a temporary credential from an ephemeral resource is allowed.
X: A=Normal argument: stored arguments are written to state, so the value would persist. Terraform rejects this.
C=Plain root output: outputs are saved in state, so a non-ephemeral output cannot take an ephemeral value. Only child module outputs marked ephemeral are allowed.
E=Stored attribute: this describes the same persistence problem. Any attribute saved in state is not an ephemeral context.
T: Ephemeral values may feed write-only arguments, providers, locals and other ephemeral contexts, never stored attributes.

@ TF-TA004 D4 T4.8 advanced tradeoff
S: A configuration needs a Vault secret to configure a database. Which statement correctly compares reading it with a Vault data source and with a Vault ephemeral resource?
A: Both store the secret in state, but the ephemeral resource encrypts it first so it is safe to commit

D: The ephemeral resource is read only during terraform init and its value is cached in the dependency lock file
K: C
G: ## Vault secrets and state
A `data` block that reads a secret stores its result like any other data source, so the secret ends up in state and plan files, readable by anyone with state access. Marking it sensitive only hides it in CLI output.

An `ephemeral` block for a Vault secret is different. Terraform **opens** the resource (the Vault provider obtains a lease and returns the secret), **renews** it if the operation runs long, and **closes** it by ending the lease so Vault revokes the credentials. Nothing is written to state or plan files.

The secret can then be used in an ephemeral context, such as a write-only argument or provider configuration.
W: Ephemeral Vault secret: Terraform opens the resource to get the secret with a lease, uses it in ephemeral contexts, never persists it, and closes it to end the lease.
X: A=Encrypted state: Terraform does not encrypt individual values in state. Data source results are stored in plain form in state.
B=Plan file leak reversed: the data source is the one whose result is persisted. Ephemeral resources are omitted from both state and plan files.
D=Read at init: ephemeral resources are opened while planning and applying, and the lock file records provider versions, not secrets.
T: Ephemeral Vault resources keep secrets out of state and plans and close their lease when done; data sources persist the result.
