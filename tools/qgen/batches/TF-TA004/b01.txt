@ TF-TA004 D1 T1.1 applied definition
S: A team replaces its console click-through runbook with files that describe each network, server and DNS record. Which statement best defines what they have adopted?
A: Infrastructure as code: infrastructure described in readable files that are versioned, reviewed and applied by a tool
B: Configuration drift: real infrastructure slowly stops matching the original runbook and is hard to rebuild
C: Continuous monitoring: a tool samples running resources and raises alerts when utilization crosses a threshold
D: Disaster recovery: a standby copy of every resource is kept in a second region so that it can take over
K: A
G: ## What infrastructure as code means
Infrastructure as code (IaC) manages infrastructure through machine-readable definition files instead of manual steps in a console or ticket queue. Terraform's own description is a tool that lets you "define both cloud and on-prem resources in human-readable configuration files that you can version, reuse, and share".
- The files are the specification: networks, virtual machines, DNS records and SaaS settings are all written down.
- A tool reads the files and performs the API calls that make real infrastructure match them.
- Because the definition is a text file, everything that works for source code (version control, review, reuse) also works for infrastructure.
W: Infrastructure as code: replacing a click-through runbook with versionable definition files that a tool applies is exactly the practice IaC names.
X: B=Configuration drift: drift is the problem of reality diverging from the recorded definition, which a manual runbook tends to cause; it is not the practice of writing definitions.
C=Continuous monitoring: monitoring observes running resources and alerts; it does not describe or create them from files.
D=Disaster recovery: keeping a standby copy in another region is a resilience design, and says nothing about how infrastructure gets defined.
T: IaC means infrastructure is defined in versionable text files that a tool turns into real resources.
V: Terraform

@ TF-TA004 D1 T1.1 applied comparison
S: Which statement correctly describes the difference between a declarative and an imperative approach to provisioning infrastructure?
A: Declarative tools take the desired end state and derive the steps, while imperative tools take the ordered steps
B: A declarative tool must be run from a console, while an imperative tool can only be run from a command line
C: Declarative tools rerun every instruction on each execution, while imperative tools skip steps already done
D: A declarative tool supports only one cloud vendor, while an imperative tool works with any vendor through scripts
K: A
G: ## Two ways to say what you want
- **Imperative**: you write the procedure. "Create a network, then create subnet A, then launch two servers in it." The script must also handle what happens if it runs a second time or if something already exists.
- **Declarative**: you write the result. "There is one network, one subnet and two servers." The tool compares that with what exists and decides which operations are needed.
Terraform configuration is declarative: it "describes the end state of your infrastructure", and Terraform builds a resource graph to work out order and parallelism.
W: Declarative versus imperative: declarative input is the end state and the tool derives the steps, whereas imperative input is the step sequence itself.
X: B=Console versus command line: the distinction is about what you express (a result or a procedure), not which interface launches the tool.
C=Re-running everything: it is the opposite; a declarative tool compares desired and current state and changes only the difference, while a naive imperative script may repeat steps unless the author guards them.
D=Vendor coverage: neither style is tied to a vendor count; Terraform is declarative and works with thousands of providers.
T: Declarative = describe the end state and let the tool plan the steps; imperative = script the steps yourself.
V: Terraform

@ TF-TA004 D1 T1.1 applied use-case
S: An engineer reads this configuration and asks what Terraform does when it is applied twice in a row with no edits.
resource "aws_s3_bucket" "logs" {
  bucket = "acme-audit-logs"
}
What happens on the second apply?
A: Terraform finds the bucket already matches the configuration and proposes no changes
B: Terraform creates a second bucket with the same name and fails with a duplicate error
C: Terraform deletes the bucket and creates it again so the result is predictable
D: Terraform asks for the bucket name again because it does not remember the previous run
K: A
G: ## Idempotence comes from declaring an end state
A declarative configuration states that a resource should exist with given arguments. Terraform records what it manages in state, compares it with the configuration (after refreshing from the provider API), and plans only the difference.
- Nothing differs, so the plan reports no changes and apply does nothing.
- Only an edit to the configuration, or a change made outside Terraform, produces actions.
This is why you can run the same configuration repeatedly without piling up duplicates.
W: No changes: the declared end state already holds, so the plan contains no operations and the second apply is a no-op.
X: B=Duplicate creation: Terraform tracks the bucket in state and does not issue a create for something it already manages.
C=Delete and recreate: replacement happens only when a changed argument cannot be updated in place; an unchanged resource is left alone.
D=Prompting again: values come from the configuration and state files; Terraform does not need to be told the name again.
T: Applying an unchanged declarative configuration is a no-op because Terraform converges on the end state.
V: Terraform, Amazon S3

@ TF-TA004 D1 T1.1 applied definition
S: Which statement about the role of Terraform providers in the IaC workflow is accurate?
A: Providers are plugins that translate resource definitions into API calls to a platform or service
B: Providers are cloud accounts that must be created before Terraform can read any configuration file
C: Providers are state files that record the remote identifier of every managed resource
D: Providers are reusable folders of configuration that package several resources behind input variables
K: A
G: ## Terraform core and providers
Terraform "creates and manages resources on cloud platforms and other services through their application programming interfaces (APIs). Providers enable Terraform to work with virtually any platform or service with an accessible API."
- Terraform core reads configuration, builds the graph and produces the plan.
- A provider is a separate plugin that knows one API: it defines the resource types and performs create, read, update and delete calls.
- Thousands of providers are published on the Terraform Registry, and you can write your own.
W: Providers as plugins: they implement a platform's API for Terraform, which is what lets one workflow reach AWS, Azure, Kubernetes or SaaS tools.
X: B=Cloud accounts: an account belongs to the platform; the provider is the plugin that authenticates to it with credentials you supply.
C=State files: state is a separate artifact that stores resource mappings; a provider is code, not data.
D=Reusable folders: that describes a module, which composes resources; a provider supplies the resource types themselves.
T: Providers are API-translating plugins; modules are packaged configuration; state is the record of managed objects.

@ TF-TA004 D1 T1.1 applied comparison
S: A team lead says, "Terraform is our configuration manager, so we will use it to install packages and edit config files inside running servers." Which statement is accurate?
A: Terraform mainly provisions infrastructure, while in-guest setup usually belongs to Ansible, Chef or Puppet
B: Terraform replaces in-guest tools because providers include package and service resources for the operating system
C: Terraform can manage in-guest software only when the servers run on-premises, not in a public cloud
D: Terraform and configuration managers are the same category, so the choice between them is purely a matter of syntax preference
K: A
G: ## Provisioning versus configuration management
- **Provisioning (what Terraform does)**: create, change and destroy infrastructure objects such as networks, instances, databases, buckets and DNS records by calling platform APIs.
- **Configuration management (Ansible, Chef, Puppet, Salt)**: log in to a machine, or run an agent on it, to install packages, template files and manage services.
The two are complementary. A common pattern is that Terraform creates the instance (or an image-based fleet) and a configuration tool, or a pre-built machine image, supplies the software. Terraform's docs describe an immutable approach: replace infrastructure from a new definition instead of patching it in place.
W: Provisioning focus: Terraform builds the infrastructure objects, while package and file management inside a server is the usual job of a configuration manager or a baked image.
X: B=Replaces in-guest tools: providers expose platform APIs, not an operating system package manager, so Terraform does not take over that role.
C=On-premises only: the limitation is not about location; provisioning provider-managed resources works equally on public clouds and on-premises platforms.
D=Same category: the tools overlap at the edges, but one provisions infrastructure through APIs and the other converges the inside of machines.
T: Terraform provisions infrastructure; it is not a configuration manager for software inside servers.

@ TF-TA004 D1 T1.1 applied use-case
S: Which statements correctly describe the "write, plan, apply" workflow that Terraform brings to IaC? (Select TWO)
A: Plan produces an execution plan describing what will be created, updated or destroyed, based on the configuration and existing infrastructure
B: Write is the stage where Terraform contacts every provider and creates the declared resources
C: Apply performs the proposed operations in dependency order once the plan is approved
D: Plan automatically changes resources whose arguments differ so that apply has less work to do
E: Apply must be preceded by a manual export of the remote state to a local file
K: A,C
G: ## The three stages
- **Write**: you author configuration, possibly spanning several clouds and services. Nothing is contacted yet.
- **Plan**: Terraform compares configuration, state and the real objects and shows the create, update and destroy actions it proposes.
- **Apply**: on approval Terraform performs the actions, respecting dependencies (it would recreate a VPC before scaling the machines that depend on it) and parallelizing independent work.
The separation is what makes IaC changes reviewable before anything happens.
W: A=Plan: it is a preview of the exact create, update and destroy operations, which humans or automation can review.
C=Apply: after approval it executes the plan in an order that respects resource dependencies.
X: B=Write contacts providers: writing is editing files; no API call is made until plan or apply.
D=Plan changes resources: plan is read-only with respect to infrastructure; only apply changes real objects.
E=Manual state export: state is read automatically from the configured backend; no manual export step exists in the workflow.
T: Write defines, plan previews, apply executes in dependency order.
V: Terraform

@ TF-TA004 D1 T1.1 applied troubleshooting
S: A script that creates a VPC and then four servers is run a second time after a network error. It now fails because the VPC already exists. Which characteristic of declarative IaC removes this failure mode?
A: The tool compares the desired end state with what exists and only creates the missing parts
B: The tool deletes the whole environment first so that every run begins from an empty account
C: The tool requires the operator to type each step again and confirm it individually
D: The tool stores a log of past commands and replays them in the same order
K: A
G: ## Why scripts break on re-runs
An imperative script encodes "create the VPC". Running it twice means two create calls, and the second fails because the VPC exists. Authors must add existence checks around every step, which is hard to do reliably.
A declarative tool receives "a VPC exists" and works out which operations bring reality to that statement. After a partial failure, the next run finds the VPC and creates only the servers that are missing, because the plan is derived from the current situation.
W: Compare and converge: the plan contains only the operations still needed, so a re-run after partial failure completes the job instead of failing on step one.
X: B=Delete first: destroying everything each run would be slow and destructive; it is not how convergence works.
C=Manual re-entry: that is more manual effort and does not address the duplicate create at all.
D=Replaying history: replaying past commands repeats the failing create; a declarative tool plans from current state, not from a command log.
T: Declarative tools plan the difference between desired and actual, so re-runs after partial failures are safe.
V: Terraform

@ TF-TA004 D1 T1.1 applied definition
S: Which statement about the language used to write Terraform configuration is accurate?
A: Configuration is written in HCL, a declarative language, with a JSON-compatible syntax also available
B: Configuration must be written as Go programs that are compiled before they can be planned
C: Configuration is written as a sequence of shell commands that Terraform runs line by line from top to bottom
D: Configuration is stored only as binary plan files that cannot be read by humans
K: A
G: ## HCL
Terraform uses the HashiCorp Configuration Language (HCL) for files ending in `.tf`. It is declarative: blocks such as `resource`, `variable` and `output` describe objects and relationships, and the order of blocks in a file does not control execution order. References between resources create dependencies, from which Terraform builds its graph. A JSON-compatible alternative syntax (`.tf.json`) exists for machine-generated configuration.
W: HCL: a readable declarative language, with a JSON variant for tools that generate configuration.
X: B=Go programs: providers are written in Go, but practitioners write configuration in HCL with no compile step.
C=Shell commands: configuration is not a script run top to bottom; it is a set of declarations whose order is derived from references.
D=Binary only: saved plan files are binary artifacts, but the source of truth is human-readable configuration.
T: Terraform configuration is declarative HCL (or JSON), with execution order inferred from dependencies.
V: Terraform

@ TF-TA004 D1 T1.1 applied use-case
S: A team writes this configuration. Which statement describes how Terraform decides the creation order?
resource "aws_subnet" "app" {
  vpc_id     = aws_vpc.main.id
  cidr_block = "10.0.1.0/24"
}
resource "aws_vpc" "main" {
  cidr_block = "10.0.0.0/16"
}
A: The VPC id reference creates a dependency, so the VPC is created first despite appearing later
B: The subnet is created first because it appears first in the file
C: Terraform asks the operator which resource to create first
D: Both resources are created in an arbitrary order, and the subnet is retried automatically until the VPC exists
K: A
G: ## Order comes from the graph
Terraform does not execute files line by line. It reads every block, finds references such as `aws_vpc.main.id`, and builds a dependency graph. Resources without dependencies on each other are created in parallel; a resource that references another waits for it.
This is part of why declarative IaC is easier to maintain than scripts: you can reorder or split files freely, and the tool derives the sequence.
W: Implicit dependency: referencing the VPC's attribute makes the subnet depend on it, so the graph puts the VPC first regardless of file position.
X: B=File order: block position in the file has no effect on execution order.
C=Asking the operator: ordering is computed from the graph without input.
D=Random with retries: Terraform does not guess; it orders operations from known dependencies.
T: Terraform orders operations from references in a dependency graph, not from file position.

@ TF-TA004 D1 T1.2 applied troubleshooting
S: Over the weekend someone opened a port in the console on a server that Terraform manages. On Monday the team runs a plan with no configuration edits. What should they expect?

G: ## Drift
Drift is the gap between what the configuration says and what actually exists, usually caused by out-of-band changes. During a plan Terraform refreshes its view of each managed object from the provider API, compares it with the configuration, and proposes the actions that restore the declared state.
- Reviewing the plan makes the drift visible instead of silent.
- If the manual change was intended, you update the configuration so the code matches reality.
IaC reduces drift because the code is a standing reference that every run converges back to.
W: Plan detects drift: the refreshed attribute differs from the declared one, so a change to restore the configured value is proposed.
X: B=No provider contact: planning reads current object data from the provider by default, which is how drift shows up.
C=Whole server deleted: a changed attribute that can be updated in place leads to an update, not removal of the resource.
D=Updating the file: Terraform never edits configuration; humans decide whether code or reality should change.

@ TF-TA004 D1 T1.2 advanced use-case
S: A change lowers the instance count from 3 to 2 and also changes an AMI id. A reviewer wants to be sure the apply will not destroy more than expected. What should the reviewer rely on?
