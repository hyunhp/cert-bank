@ TF-TA004 D7 T7.1 applied definition
S: A team wants to bring an existing S3 bucket under Terraform management using an `import` block. Which statement about that block is accurate?
A: It names the destination address in `to` and the provider's ID for the bucket in `id`, and a matching `resource` block represents the bucket.
B: It names the bucket's ARN in `from` and a new state file in `to`, and Terraform builds the `resource` block from the cloud API automatically.
C: It names the module source in `to` and the account number in `id`, and Terraform imports every bucket found in that account.
D: It names the provider alias in `id` and the resource type in `to`, and Terraform adopts the first bucket that matches the type.
K: A
G: ## What an import block does
Terraform only manages objects that are bound to a resource address in state. An `import` block tells Terraform to create that binding for an object that already exists.
- `to` is the address of the resource instance that will track the object, for example `aws_s3_bucket.this`.
- `id` is the identifier the provider uses for that kind of object (for an S3 bucket, its name). The value must be known during planning.
- A `resource` block at the same address represents the object in configuration.
```
import {
  to = aws_s3_bucket.this
  id = "example-bucket"
}
resource "aws_s3_bucket" "this" {
}
```
Terraform never scans an account and adopts objects on its own; each import names one object (or uses `for_each` for several).
W: Import block: `to` is the address in state, `id` is the provider's ID of the real object, and a `resource` block at that address holds the configuration.
X: B=from and ARN: the block has no `from` argument and no state-file destination, and Terraform does not turn the cloud object into a `resource` block unless you ask for generated configuration.
C=Module source and account: `to` takes a resource address, not a module source, and an `id` identifies one object, so nothing is discovered in bulk by naming an account.
D=Alias and type: the provider alias goes in the separate `provider` argument, and `id` is the object's identifier; Terraform does not guess a match by type.
T: An import block binds one real object (`id`) to one address (`to`) that a resource block describes.

The big advantage of the `import` block over the CLI command is that the import is part of the normal workflow:
- `terraform plan` shows the import in the summary (a line such as `Plan: 1 to import, 0 to add, 0 to change, 0 to destroy`), along with any changes Terraform would make after the import.

T: An import block is reviewed in plan and takes effect in apply.

@ TF-TA004 D7 T7.1 applied comparison
S: Which TWO statements correctly contrast the `import` block with the `terraform import` command? (Select TWO)
A: The `import` block is reviewed in `terraform plan` and applied with `terraform apply`, and it can import several resources in one run.

- **`import` block**: declarative, lives in configuration, goes through plan and apply, supports `for_each`, and can be paired with generated configuration.
- **`terraform import ADDRESS ID`**: an imperative CLI command that writes the object into state right away. You must write the `resource` block first, and the command generates no configuration.

@ TF-TA004 D7 T7.1 applied use-case
S: Three buckets exist as `bucket1`, `bucket2` and `bucket3`. A `locals` map `buckets` maps the keys `staging`, `uat` and `prod` to those names, and `resource "aws_s3_bucket" "this"` uses `for_each = local.buckets`. One `import` block sets `for_each = local.buckets`. Which `to` and `id` arguments import every bucket into its matching instance?

G: ## import with for_each
The `import` block accepts `for_each` with a map or a set of strings. Inside the block, `each.key` and `each.value` identify the current element, and `to` must name the matching instance of the resource.
```
import {
  for_each = local.buckets
  to       = aws_s3_bucket.this[each.key]
  id       = each.value
}
```
- Resource instance addresses use the same keys as the resource's `for_each`, so `aws_s3_bucket.this["staging"]` receives `bucket1`.

X: B=count.index: the import block has no `count`, so `count.index` is not available, and the resource instances are keyed by map keys, not numbers.
C=Single address: `to` without the key points to the whole resource, and `each.key` is the label (`staging`), not the bucket name the provider expects.
D=Swapped key and value: the instance keys are the map keys, so `[each.value]` names an instance such as `["bucket1"]` that does not exist, and the provider ID would be the label instead of the bucket name.
T: Use `for_each` in an import block and address each instance with `each.key`.

@ TF-TA004 D7 T7.1 applied troubleshooting

@ TF-TA004 D7 T7.1 applied tradeoff
S: Two resource blocks, `aws_instance.web` and `aws_instance.web_old`, are each imported with the same instance ID because a teammate wants two names for one server. What does HashiCorp advise?
A: Import each remote object to exactly one resource address, since binding it twice can cause unwanted behavior.
B: Import it to both addresses, because Terraform merges the entries into one instance.
C: Import it to both addresses and set `prevent_destroy` on one of them so that only one block can delete it.
D: Import it once and add a second `import` block with `provider` set to the same alias.
K: A
G: ## One object, one address
Terraform's model assumes each remote object belongs to exactly one resource instance. If two addresses track the same object:
- Each address keeps its own copy of the attributes, which drift apart.
- Changing or destroying one address can change or delete the object while the other still thinks it exists.
Use `terraform state mv` to move an existing binding to a different address, and use modules or outputs to share an object's attributes between places.
W: Each remote object should be bound to a single address; the docs warn that importing the same object more than once may give unwanted behavior.
X: B=Merged entries: Terraform keeps separate state entries per address and does not merge them.
C=prevent_destroy on one: this lifecycle setting blocks destroy plans for that address only; it does not fix two copies of state for the same object.
D=Second block with the alias: the `provider` argument selects a provider configuration and does not make a second binding safe.
T: Bind each real object to one address only.

@ TF-TA004 D7 T7.2 applied troubleshooting
S: A developer renames `resource "aws_instance" "worker"` to `"helper"` in the configuration, and `terraform plan` proposes to destroy `aws_instance.worker` and create `aws_instance.helper`. The server must keep running. Which command fixes the binding?
A: `terraform state mv aws_instance.worker aws_instance.helper`
B: `terraform state rm aws_instance.worker` followed by `terraform apply`
C: `terraform import aws_instance.helper aws_instance.worker`
D: `terraform state show aws_instance.worker aws_instance.helper`
K: A
G: ## Renaming without replacing
Terraform finds a resource's state entry by its address. If you rename a block, the old address no longer exists in configuration (so the old object looks orphaned and is destroyed) and the new address has no entry (so a new object is created).
`terraform state mv SOURCE DESTINATION` moves the binding to a new address so the same remote object is tracked there:
```
terraform state mv aws_instance.worker aws_instance.helper
```
- It changes state only; no real infrastructure is touched.
- Source and destination must be the same kind of object, and for resources the same resource type.
- For code refactoring, the `moved` block (covered with the other state-refactoring topics) records the same rename in configuration.
