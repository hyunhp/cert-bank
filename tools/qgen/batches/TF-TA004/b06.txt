@ TF-TA004 D6 T6.1 applied definition
S: A new project has no `backend` block, and an engineer runs `terraform apply` for the first time in the working directory. Which statement about where Terraform keeps state is accurate?
A: Terraform writes `terraform.tfstate` in the working directory and keeps the prior snapshot in `terraform.tfstate.backup`.
B: Terraform creates a hidden S3 bucket in the provider account and writes the state file there under the workspace name.
C: Terraform writes `terraform.tfstate` inside the `.terraform` directory and deletes the file again when the apply finishes.
D: Terraform keeps state only in memory during the run and rebuilds it from the provider APIs at the start of the next plan.
K: A
G: ## The default backend
A backend defines where Terraform stores its state and how operations run. When no `backend` block exists, Terraform uses the `local` backend.
- The `local` backend stores state as a file on disk, by default `terraform.tfstate` in the root module directory.
- Before writing a new snapshot, Terraform keeps the previous one in `terraform.tfstate.backup`.
- Nothing needs configuring, which is convenient for learning, but the file is not shared and a lost laptop means lost state.
The `.terraform/` directory is something else: it holds downloaded providers, modules and the recorded backend configuration, not your infrastructure state.
W: The local backend writes `terraform.tfstate` next to the configuration and rotates the previous snapshot into `terraform.tfstate.backup`.
X: B=Hidden S3 bucket: Terraform never provisions remote storage on its own; a remote location exists only if you configure a backend that points at it.
C=State in `.terraform`: that directory holds plugins, modules and backend settings, and the state file persists after the run because plans depend on it.
D=Memory only: Terraform cannot rebuild bindings between resource instances and real objects from provider APIs alone, so it must persist state between runs.
T: With no backend block, state lives in a local `terraform.tfstate` file plus a `.backup` copy.

@ TF-TA004 D6 T6.1 applied use-case
S: A team keeps the default local backend but wants the state file stored as `state/dev.tfstate` inside the root module directory. Which setting does this?

The local backend accepts a small set of arguments inside a nested `backend "local"` block:
- `path`: the location of the state file; it defaults to `terraform.tfstate` relative to the root module.

```hcl
terraform {

    path = "state/dev.tfstate"
  }
}
```

W: The `path` argument of the `local` backend sets the state file location, replacing the default `terraform.tfstate`.
X: B=`workspace_dir`: this argument sets the directory for non-default workspaces, not the file used for the default workspace's state.

D=`-output-state` flag: this flag does not exist; the legacy local-backend flags are `-state`, `-state-out` and `-backup`, and they are not recommended for new systems.

@ TF-TA004 D6 T6.1 applied troubleshooting
S: To share state, a team commits `terraform.tfstate` to the Git repository next to the configuration. Which problem does HashiCorp's guidance single out about this approach?
A: A version control system provides no state locking and no fine-grained access control, so concurrent applies can lose data and secrets in the file are exposed.
B: Git refuses to store JSON files larger than the limit of the default local backend, so large states are truncated on commit.
C: Terraform detects the file in the repository and disables the `plan` command until the file is removed from version control.
D: Every commit that changes the file automatically rotates the provider credentials stored inside it and then breaks the same credentials on all other branches.
K: A
G: ## Why Git is a poor place for state
The state documentation warns against storing state in a version control system or any storage that does not support state locking and secure access control, because this can result in data loss or exposure of secrets.
- Two engineers can each pull the file, apply from their own branch, and push conflicting snapshots; no lock stops them.
- State can hold plaintext resource attributes such as initial database passwords, which then spread to every clone and the repository history.
- The recommended fix is a remote backend (or HCP Terraform) with locking, encryption and access control. Keep `terraform.tfstate` out of Git via `.gitignore`.
W: Git lacks locking and access control, so concurrent applies can clobber state and secrets in it are exposed to everyone with repository access.
X: B=File size limit: Git imposes no such limit tied to the local backend, and nothing is truncated on commit.
C=Disabled plan: Terraform does not inspect whether state is committed and never blocks commands because of version control.
D=Credential rotation: committing a file changes nothing in the provider account; the problem is exposure, not automatic rotation.
T: Never use Git as the shared state store: it has no locking and no access control for secrets.

@ TF-TA004 D6 T6.2 applied use-case
S: Two engineers run `terraform apply` against the same S3-backed configuration within seconds of each other. What does Terraform do for the second engineer?
A: It tries to acquire the state lock, fails because the first run holds it, and stops without changing anything.
B: It merges both change sets into one plan and applies the combined result to the shared state snapshot.
C: It silently waits forever and starts only when the first engineer closes the terminal session.
D: It skips locking because only `destroy` operations take a lock, and applies its own plan in parallel.
K: A
G: ## Automatic state locking
If the backend supports locking, Terraform locks the state for every operation that could write state. You see no message while it happens. The lock prevents others from acquiring it and potentially corrupting the state.
- If acquiring the lock fails, Terraform does not continue and reports the lock holder and a lock ID.
- If acquiring takes longer than expected, Terraform prints a status message.
- Locking applies to `apply`, `destroy`, `plan` (it may refresh state) and similar operations, not only to destroy.
Not every backend supports locking; the documentation of each backend says whether it does.
W: The second run cannot get the lock held by the first, so Terraform stops with an error instead of continuing.
X: B=Merged plans: Terraform never merges concurrent runs; the lock exists precisely to serialize them.
C=Wait forever: by default Terraform fails when the lock is held; waiting only happens if you pass `-lock-timeout`, and then for a limited duration.
D=Only destroy locks: locking covers all operations that could write state, so apply is protected too.
T: State locking makes a second concurrent write fail instead of corrupting state.

@ TF-TA004 D6 T6.2 applied troubleshooting

G: ## Stale locks and force-unlock
A crash can leave the lock behind. `terraform force-unlock LOCK_ID` removes the lock for the current configuration; it never changes your infrastructure.
- The lock ID acts as a nonce so that you unlock exactly the lock you meant to.
- Use it only to release your own lock after automatic unlocking failed. Unlocking while someone else really holds the lock can produce multiple writers and corrupt state.
- Before running it, verify that the interrupted run is truly dead.
Disabling locking with `-lock=false` is discouraged because it removes the protection rather than fixing the stale lock.
W: After verifying no run is active, `force-unlock` with the reported lock ID releases the stale lock without touching infrastructure.

D=`init -reconfigure`: it re-reads backend settings and does not release locks.
T: Verify nobody is running, then clear a stale lock with `terraform force-unlock LOCK_ID`.

@ TF-TA004 D6 T6.2 applied use-case
S: A pipeline serialises deployments by queueing jobs, but occasionally a job starts a second before the previous one releases the lock and fails at once. Which option makes Terraform retry the lock instead of failing immediately?
A: Add `-lock-timeout=5m` to the plan and apply commands.
B: Add `-lock=false` to the plan and apply commands.
C: Add `-refresh=false` to the plan and apply commands.
D: Add `-parallelism=1` to the plan and apply commands.
K: A
G: ## Waiting for a lock
By default, if another process holds the lock, Terraform stops with an error. `-lock-timeout=DURATION` (for example `30s` or `5m`) tells commands that take a lock to keep retrying for that period before giving up.
- `-lock=false` disables the lock entirely; it avoids the error but also the protection.
- `-refresh=false` only skips the refresh of existing objects.
- `-parallelism=N` limits concurrent resource operations within one run; it has no relation to cross-run locks.
W: `-lock-timeout` keeps retrying acquisition for the given duration, which absorbs short overlaps between queued jobs.
X: B=`-lock=false`: it turns locking off, so overlapping runs could write state at the same time.
C=`-refresh=false`: it skips reading remote objects; the lock is still requested and still fails.
D=`-parallelism=1`: this throttles operations inside a single run and does not affect how the run acquires the state lock.
T: `-lock-timeout` retries a held lock for a set time; `-lock=false` removes protection.

@ TF-TA004 D6 T6.2 advanced tradeoff
S: An engineer proposes running `terraform force-unlock` whenever a colleague's apply seems slow so that the team can proceed in parallel. Which statement is accurate?
A: This is risky, because unlocking a lock that another live run holds can create multiple writers and corrupt the state.

D: This is risky, because force-unlock rolls back the other run's changes to the real infrastructure first.
K: A
G: ## Force-unlock is for your own stale lock
The documentation warns to be very careful with `force-unlock`: if you release a lock that someone else is actively holding, several writers may modify state at once.
- The lock ID makes sure you target the intended lock, but it does not prove the holder has died.
- The command does not modify infrastructure and does not roll anything back.
- Use it only for your own lock when automatic unlocking failed. For slow runs, wait or use `-lock-timeout`.
W: Releasing a live run's lock allows multiple writers, which can corrupt state; use it only for your own stale lock.
X: B=Pause and restore: force-unlock simply removes the lock; the other run keeps going without any lock.

D=Rollback: the command never alters real infrastructure, and nothing is rolled back.
T: Force-unlock only for your own stale lock, never to hurry a running operation.

G: ## Plans carry backend settings
When you apply a saved plan, Terraform uses the backend configuration recorded in the plan file, not the current settings. The plan captures what is in `.terraform/terraform.tfstate` when the plan was created, so that it is applied to the same infrastructure.
