@ TF-TA004 D2 T2.1 applied use-case
S: A root module declares `aws = { source = "hashicorp/aws", version = "~> 5.2" }`. There is no `.terraform.lock.hcl` yet, and the registry offers 5.1.0, 5.2.9, 5.40.1 and 6.0.0. Which version does the first `terraform init` install?
A: 5.2.9
B: 6.0.0
C: 5.40.1
D: 5.1.0
K: C
G: ## What a version constraint does
A constraint in `required_providers` defines which provider versions the configuration accepts. When nothing is recorded yet, `terraform init` picks the newest available version that satisfies the constraint.
## The `~>` operator
`~>` is the "pessimistic" operator: only the right-most component you wrote may increase.
- `~> 5.2` allows `5.2`, `5.3`, `5.40.1` and so on, but not `6.0.0` (the left component `5` is fixed, the minor part may grow).
- `~> 5.2.0` would allow only patch releases such as `5.2.9`, not `5.3.0`.
Because there is no lock file, nothing pins an older acceptable version.
W: 5.40.1 is the newest release that satisfies `~> 5.2`: the major version stays 5 and the minor version may rise from 2 upward, so 5.40.1 beats 5.2.9, and 6.0.0 is outside the range.
X: A=5.2.9: that is the newest version only for the stricter `~> 5.2.0`, which limits changes to the patch component. With `~> 5.2` the minor version can also rise.
B=6.0.0: the newest release overall is not chosen; `~> 5.2` fixes the major version at 5, so a new major release is excluded.
D=5.1.0: it is lower than the stated minimum of 5.2, so it does not satisfy the constraint, and Terraform picks the newest match anyway, not the oldest.
T: With `~> X.Y` only the minor part may grow; with `~> X.Y.Z` only the patch part may grow; init picks the newest match when nothing is locked.

@ TF-TA004 D2 T2.1 applied use-case
S: A configuration uses `version = ">= 3.0.0, < 3.5.0, != 3.4.2"` for a provider. The registry lists 3.0.0, 3.4.2, 3.4.9, 3.5.0 and 3.6.1, and no lock file exists. Which version does Terraform select?
A: 3.4.2
B: 3.4.9
C: 3.6.1
D: 3.5.0
K: B
G: ## Combining conditions
A version constraint string can hold several conditions separated by commas. Terraform only uses versions that meet all of them, and from those it takes the newest.
- `>=` and `<` set a lower and an upper bound.
- `!=` removes one exact version, for example a release known to have a bug.
- `=` (or no operator) allows exactly one version and cannot be combined with other conditions.
## Walk through
`>= 3.0.0, < 3.5.0` leaves 3.0.0, 3.4.2 and 3.4.9. The `!= 3.4.2` condition removes 3.4.2, so 3.0.0 and 3.4.9 remain, and the newest of them is 3.4.9.
W: 3.4.9 satisfies the lower bound, is below the 3.5.0 upper bound and is not the excluded 3.4.2, and it is the newest version that passes all three conditions.
X: A=3.4.2: it fits the range but is explicitly excluded by `!= 3.4.2`, which is typically used to skip a known-bad release.
C=3.6.1: the newest release overall would break the `< 3.5.0` upper bound, so it is not eligible.
D=3.5.0: the `<` operator is exclusive, so 3.5.0 itself is not allowed; only `<=` would include it.
T: Comma-separated conditions are ANDed; Terraform takes the newest version that satisfies every one.

@ TF-TA004 D2 T2.1 applied definition
S: A team wants to test the pre-release build `4.0.0-beta2` of a provider. Which `version` constraint lets Terraform install it?
A: `version = ">= 4.0.0-beta1"`
B: `version = "~> 4.0.0-beta"`
C: `version = "4.0.0-beta2"`
D: `version = "> 3.9.0"`
K: C
G: ## Pre-release versions
A pre-release version carries a suffix introduced by a dash, such as `1.2.0-beta`. Terraform deliberately avoids them: the comparison operators `>`, `>=`, `<`, `<=` and `~>` never match a pre-release version.
The only way to select one is to name it exactly, either with `=` or with no operator at all.
W: An exact version string, with or without `=`, is the one form that selects a pre-release build, so `4.0.0-beta2` is installed.
X: A=`>= 4.0.0-beta1`: range operators skip pre-release versions even when the written bound is itself a beta, so beta2 is not matched.
B=`~> 4.0.0-beta`: the pessimistic operator is also a range operator and does not match pre-release versions.
D=`> 3.9.0`: this would select the newest stable release above 3.9.0 and never a pre-release.
T: To use a pre-release provider, pin that exact version; range operators ignore pre-releases.

@ TF-TA004 D2 T2.1 applied definition
S: A configuration requires a provider with `source = "hashicorp/random"`. Which fully qualified address does Terraform use for it?
A: `terraform.io/builtin/random`
B: `registry.terraform.io/random/hashicorp`
C: `releases.hashicorp.com/hashicorp/random`
D: `registry.terraform.io/hashicorp/random`
K: D
G: ## Anatomy of a source address
A provider source address has three parts separated by slashes: `[HOSTNAME/]NAMESPACE/TYPE`.
- **Hostname** (optional) is the registry that distributes the provider; the default is `registry.terraform.io`, the public Terraform Registry.
- **Namespace** is the publishing organization, here `hashicorp`.
- **Type** is the short name of the system the provider manages, here `random`.
Messages usually show the shortened form `hashicorp/random`; the three-part form is called the fully qualified address.
W: With the hostname omitted it defaults to the public registry, so `hashicorp/random` expands to `registry.terraform.io/hashicorp/random`.
X: A=builtin address: `terraform.io/builtin/...` is reserved for the single provider built into Terraform (`terraform`), not for `random`, which is a normal downloadable plugin.
B=Reversed order: the format is namespace first, then type, so `random/hashicorp` would mean a publisher called random.
C=releases.hashicorp.com: that host serves Terraform CLI and tool binaries, but it is not the provider registry hostname that source addresses default to.
T: Short form `NAMESPACE/TYPE` means `registry.terraform.io/NAMESPACE/TYPE`.

@ TF-TA004 D2 T2.1 applied comparison
S: Which TWO version constraint practices does HashiCorp recommend? (Select TWO)
A: A reusable module declares only a minimum provider version, such as `>= 4.0`.
B: A reusable module sets `~> 5.0` so consumers cannot upgrade to a new major version.
C: A root module omits `version` because the lock file makes a constraint unnecessary.
D: A reusable module pins an exact provider version so every caller gets identical behavior.
E: A root module uses `~>`, for example `~> 5.31`, to set both a lower and an upper bound.
K: A,E
G: ## Who owns the upper bound
Many root and child modules share one selected version per provider, so every module's constraint must be satisfied together. Constraints in reusable modules therefore need to stay loose.
- **Reusable module**: declare the minimum version known to work (`>= 4.0`). Maximum bounds force every caller to update many modules at once during routine upgrades.
- **Root module** (where you run `terraform apply`): use `~>` for a lower bound and an upper bound that avoids accidental upgrades to incompatible new versions.
The lock file records what was chosen but does not replace the constraint.
W: A=Minimum only in reusable modules: it avoids known incompatibilities and leaves the upper limit to the root module.
E=`~>` in the root module: it bounds the provider from below and above so a new incompatible major version is not pulled in by accident.
X: B=Maximum in a reusable module: HashiCorp advises against `~>` or other maximum constraints in reusable modules because they can block consumers from upgrading.
C=No version in the root: the lock file pins what is selected, but without a constraint a provider upgrade with `-upgrade` could jump to any version, and the constraint documents the intent.
D=Exact pin in a module: pinning makes the module conflict with any caller that needs another version, and only the root module should pin tightly.
T: Reusable modules state a minimum; the root module sets the range with `~>`.

@ TF-TA004 D2 T2.1 applied definition
S: Which statement about the dependency lock file `.terraform.lock.hcl` is accurate?
A: It is generated inside `.terraform/` and should be excluded from version control.
B: It stores the selected provider versions and checksums, and it belongs in version control.
C: It is hand-written HCL where you list the provider versions you want installed.
D: It records the selected version of every remote module and provider used by the configuration.
K: B
G: ## Purpose of the lock file
Version constraints tell Terraform which versions are acceptable; the lock file remembers which version it actually picked so the same decision is repeated later.
- It lives in the working directory next to the root module's `.tf` files, always named `.terraform.lock.hcl`.
- Each `provider` entry holds `version`, the informational `constraints` that were considered, and `hashes` (checksums of acceptable packages).
- `terraform init` creates and updates it. Commit it so changes to dependencies are reviewed like code changes.
It tracks providers only.
W: The file stores the selected version and package checksums for each provider, and committing it gives every teammate and CI run the same provider builds.
X: A=Inside `.terraform`: the file sits beside the configuration, not in the cache directory `.terraform`, and HashiCorp recommends committing it.
C=Hand-written: Terraform maintains it automatically during `init`; you review its diffs rather than author it, and the `constraints` field is informational only.
D=Modules as well: the lock file tracks only providers; remote module versions are not remembered and need exact constraints to stay fixed.
T: Commit `.terraform.lock.hcl`: it pins the provider selection and package hashes for everyone.

@ TF-TA004 D2 T2.1 applied troubleshooting
S: The lock file pins `hashicorp/aws` to 5.20.0 and the constraint is `~> 5.0`. A colleague wants 5.30.0, which was released later and satisfies the constraint. Which command moves the lock file to the newest matching version?
A: `terraform init -reconfigure`
B: `terraform get -update`
C: `terraform init -upgrade`
D: Delete `.terraform` and run `terraform init` again
K: C
G: ## Locked versions are sticky
When a provider already has an entry in the lock file, `terraform init` re-selects exactly that version even if newer ones exist. This is what makes runs repeatable.
To move forward on purpose, tell Terraform to ignore the recorded selection with `terraform init -upgrade`. It picks the newest version matching the constraint and rewrites the lock entry (version and hashes), which you then commit after review. Changing the constraint in `required_providers` and re-running init is the other way to shift the selection.
W: `terraform init -upgrade` disregards the recorded selection and installs the newest version that still satisfies `~> 5.0`, then updates the lock file.
X: A=`-reconfigure`: this flag re-initializes the backend configuration, ignoring the saved backend settings; it does not change provider selections.
B=`terraform get -update`: this downloads and updates modules, and the lock file does not track modules.
D=Delete `.terraform`: that only clears the local cache; the lock file remains and init reinstalls the pinned 5.20.0 again.
T: The lock file wins over a newer release until you run `terraform init -upgrade` (or change the constraint).

@ TF-TA004 D2 T2.1 applied troubleshooting
S: After a provider is updated, `terraform init` fails with "the current package for registry.terraform.io/hashicorp/azurerm 2.1.0 doesn't match any of the checksums previously recorded in the dependency lock file". What does this error mean?
A: The downloaded package matches none of the recorded checksums, so Terraform refuses it.
B: The state file records a different azurerm version than the one in the configuration.
C: The `required_providers` constraint excludes version 2.1.0, so the install is rejected.
D: The registry credentials are missing, so Terraform cannot fetch the package signature to verify.
K: A
G: ## Trust on first use
When a provider is first added, Terraform records checksums of the packages (`zh:` zip hashes and `h1:` content hashes) in the lock file. On later installs it verifies that the package matches at least one recorded checksum, and fails if none match.
This model is called trust on first use: you validate the provider when you first add it, and Terraform alerts you if the same version later arrives as different bytes (a corrupted download, a replaced package or a tampered mirror). Do not simply delete the lock entry before finding out why.
W: Terraform verifies each installed package against the lock file's recorded hashes and stops when none match, protecting against swapped or altered provider binaries.
X: B=State mismatch: provider version compatibility with state is a different check; this message is about package checksums in the lock file.
C=Constraint excludes 2.1.0: a constraint problem produces a "no available releases match" style error, and this message names a downloaded package.
D=Missing credentials: public registry providers are downloaded without credentials, and the failure here is a verification result, not an authentication problem.
T: A checksum mismatch means the package differs from what was trusted at first use: investigate before updating the lock file.

@ TF-TA004 D2 T2.1 applied use-case
S: Developers on macOS and a CI runner on Linux share a configuration. The team installs providers from an internal network mirror, and the pipeline fails verifying packages that the lock file lacks hashes for. What should the team run to add hashes for both platforms?
A: `terraform init -upgrade` on the CI runner after deleting `.terraform`
B: `terraform providers lock -platform=darwin_arm64 -platform=linux_amd64`
C: `terraform providers mirror -platform=linux_amd64 ./mirror`
D: `terraform validate -platform=darwin_arm64 -platform=linux_amd64`
K: B
G: ## Why platform hashes can be missing
If a provider comes from its origin registry, Terraform records signed checksums that cover all platforms. When it comes from a filesystem or network mirror, Terraform can verify only the package for the platform running `init`, so the lock file contains hashes for that one platform and other platforms cannot verify their packages.
`terraform providers lock` fixes that without installing anything: it downloads the official packages from the origin registry for the listed platforms and writes both `zh:` and `h1:` checksums. Later `init` runs against the mirror then verify against them.
```
terraform providers lock -platform=darwin_arm64 -platform=linux_amd64
```
W: `terraform providers lock` with one `-platform` flag per target pre-populates verified hashes for every platform that will run the configuration.
X: A=`init -upgrade` on CI: this would record only the CI platform's hash and may change the selected version, leaving the macOS machines unverified.
C=`providers mirror`: this command writes provider packages into a local directory to build a mirror; it does not update lock file hashes.
D=`validate -platform`: `terraform validate` checks syntax and consistency and has no platform option.
T: Mirror installs only record the local platform's hashes; run `terraform providers lock -platform=...` to cover every platform.
