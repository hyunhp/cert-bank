@ TF-TA004 D4 T4.1 applied use-case
S: The network team created a VPC outside your Terraform configuration, and your configuration must place new subnets in that existing VPC without managing, changing or deleting it. Which approach is correct?
A: Declare a data "aws_vpc" "shared" block that looks the VPC up by tag or ID, then reference data.aws_vpc.shared.id in the subnet resources
B: Declare a resource "aws_vpc" "shared" block with the same CIDR, so Terraform detects the existing VPC and adopts it during the next apply
C: Declare a variable "vpc_id" block with a type constraint of aws_vpc so Terraform reads the VPC object directly from the provider
D: Declare a locals block named shared_vpc and let Terraform query the provider API whenever the local value is referenced
K: A
G: ## Resource blocks versus data blocks
- A `resource` block describes an infrastructure object that Terraform **manages**: it creates, updates and destroys it, and records it in state.
- A `data` block describes an existing object that Terraform only **reads**. It never creates or deletes anything. Terraform queries the provider and exposes the result as attributes you reference with the `data.` prefix.
Typical uses are looking up an AMI, a VPC built by another team, or an account ID. The lookup arguments are filters (an ID, a name, a tag), and the returned attributes (such as `id` or `cidr_block`) feed other blocks.
```
data "aws_vpc" "shared" {
  tags = { Name = "shared-network" }
}
```
W: Data source: it reads the existing VPC through the provider, makes its attributes available as data.aws_vpc.shared.id, and leaves the VPC itself unmanaged, so destroying your configuration never deletes it.
X: B=Duplicate resource block: a resource block always plans a new object. Terraform does not match it to an existing VPC by CIDR, so apply would try to create a second VPC. Adoption of existing objects needs an import, which is a different feature.
C=Typed variable: a variable only receives values from the caller. Type constraints describe the shape of a value and have no way to make Terraform query a provider for an object.
D=Locals block: locals name expressions that are computed from other values. They do not call provider APIs, so a local cannot discover an existing VPC.
T: Manage it with a resource block; only read something that already exists with a data block.

@ TF-TA004 D4 T4.1 applied definition
S: Which TWO statements about data sources in Terraform are accurate? (Select TWO)
A: Terraform reads a data source during the plan whenever its arguments are already known, and reads it later in the apply when they depend on unknown values
B: Running terraform destroy deletes the real object that a data block looks up, because the block is part of the configuration
C: A data block creates the object it describes when the lookup finds nothing, so the same block works for both new and existing infrastructure
D: Attributes of a data source are referenced with the data. prefix followed by type and name, for example data.aws_ami.ubuntu.id
E: A data block is evaluated only after every resource block in the configuration has been applied, so no resource can depend on it
K: A,D
G: ## How data sources behave
A data source is a read-only query. Terraform evaluates it like any other node in the dependency graph: when its arguments are known during planning (a literal tag, a variable), it reads the data at plan time. When an argument depends on a value that is only known after another resource is created, the read is deferred until apply.
Because it only reads, a data source has no destroy side effect on the real object. Its results are referenced as `data.<TYPE>.<NAME>.<ATTRIBUTE>`, and resources can depend on them, for example using a looked-up AMI ID as an instance argument.
W: A=Plan-time read: known arguments let Terraform read the data during plan, which is why plans can show values from the lookup. Unknown arguments postpone the read to apply.
D=data. prefix: data sources live in their own namespace, so a reference always begins with data. then the type, name and attribute. Without the prefix, the address would be read as a managed resource.
X: B=Destroy deletes the object: destroy removes only the objects Terraform manages through resource blocks. A data block only reads, so the looked-up object stays untouched.
C=Creates missing objects: a data source never creates anything. If the lookup matches nothing, Terraform reports an error and the operation stops.
E=Evaluated last: data sources take part in the dependency graph and are commonly read first so resources can use their values, for example an AMI ID passed to an instance.
T: Data blocks read (at plan when arguments are known), never create or destroy, and are addressed with the data. prefix.

@ TF-TA004 D4 T4.1 applied comparison
S: A configuration contains resource "aws_s3_bucket" "logs" {} and, in the same module, resource "aws_s3_bucket_versioning" "logs" {}. A reviewer says the shared name logs is an error. Which statement is accurate?
A: The configuration is valid, because a resource is identified by the combination of its type and its name, and the two types differ
B: The configuration is invalid, because Terraform requires every resource name to be unique across all resource types within a single module
C: The configuration is valid only if the second block adds depends_on pointing at the first one
D: The configuration is invalid unless the second block is moved into a child module of its own
K: A
G: ## How Terraform identifies a resource
Every managed resource has an address made of its **type** and its **local name**: `aws_s3_bucket.logs`, `aws_s3_bucket_versioning.logs`. The local name only has to be unique among resources of the same type in the same module. The name is private to your configuration and is not the name of the real object in the cloud.
This is why teams often reuse a descriptive name (`logs`, `main`, `this`) across related resource types, and the references stay unambiguous because the type is part of the address. Duplicate type-and-name pairs in one module raise a "duplicate resource" error.
W: Type plus name: the two addresses are different (aws_s3_bucket.logs versus aws_s3_bucket_versioning.logs), so there is no clash. Uniqueness is checked per resource type in a module.
X: B=Names unique across types: the uniqueness rule applies to the pair of type and name, not to the name alone. Reusing a name for different types is common and valid.
C=Requires depends_on: a dependency is not needed for a naming rule. The versioning resource would normally reference the bucket's ID, which already creates an implicit dependency.
D=Requires a child module: modules are for reuse and encapsulation. Nothing about two differently typed resources sharing a name needs a separate module.
T: A resource address is TYPE.NAME; only a repeated pair in the same module is a duplicate.

@ TF-TA004 D4 T4.2 applied use-case
S: A web server resource sets vpc_security_group_ids = [aws_security_group.web.id] and the configuration has no depends_on anywhere. When the plan is applied from scratch, what does Terraform do?
A: It creates the group first and the server after it, because the reference to the group's id forms an implicit dependency
B: It creates both objects in parallel, because only depends_on can express ordering between two resources
C: It creates the objects in the order the blocks appear in the files, so the security group must be written above the server block
D: It creates the server first and attaches the security group afterwards by running a second internal update
K: A
G: ## Implicit dependencies
Terraform builds a graph of everything in the configuration. When one block refers to an attribute of another, such as `aws_security_group.web.id`, Terraform adds an edge from the referenced object to the referencing one. It creates dependencies first and destroys them last.
- Block order in files does not matter.
- Objects with no edges between them are created in parallel (by default up to 10 operations at once).
- `depends_on` is only for hidden dependencies that no reference expresses.
W: Implicit dependency: the attribute reference tells Terraform the server needs the group's ID, which exists only after the group is created, so the group is built first without any extra argument.
X: B=Parallel creation: parallelism applies only to objects without an edge between them. A reference creates an edge, so depends_on is not needed for this ordering.
C=File order: Terraform ignores the order of blocks and files. The dependency graph decides the order, so the group may sit anywhere in the configuration.
D=Second internal update: Terraform does not create an object without a required value and patch it afterwards. The ID is unknown until the group exists, so the server's creation waits.
T: A reference to another resource's attribute is an implicit dependency; file order is irrelevant.

@ TF-TA004 D4 T4.2 applied troubleshooting
S: A configuration creates subnets with count = length(var.cidrs) and cidr_block = var.cidrs[count.index]. The list is ["10.0.1.0/24", "10.0.2.0/24", "10.0.3.0/24"], and the team removes the first entry. The plan wants to change two subnets and destroy one, although only a single subnet should disappear. What is the best fix?
A: Create the subnets with for_each over a map keyed by a stable name, so each subnet keeps its address when another entry goes
B: Keep count but wrap var.cidrs in sort(), so the list order never changes between runs
C: Add lifecycle { prevent_destroy = true } to the subnet resource so Terraform refuses plans that remove any instance
D: Use terraform apply -target with the index of the subnet to be destroyed, then run the normal apply afterwards
K: A
G: ## count versus for_each
Both meta-arguments create several instances from one block, but they identify instances differently.
- `count` uses a **number** and identifies instances by position: `aws_subnet.main[0]`, `[1]`, `[2]`. Removing an item from the middle or start of the list shifts every later element to a lower index, so Terraform sees changed arguments for the remaining instances and destroys the highest index.
- `for_each` uses a **map or set of strings** and identifies instances by key: `aws_subnet.main["a"]`. Removing a key only affects the instance with that key.
Use `count` for "N identical copies or on/off switch" and `for_each` when each instance is a distinct item that may come and go.
W: for_each with stable keys: every subnet is tied to its key, so deleting one entry plans a single destroy and leaves the other subnets alone.
X: B=sort(): sorting only fixes the order of the list. Removing the first entry still shifts the remaining items to lower indexes, so the same extra changes would appear.
C=prevent_destroy: this makes Terraform fail when a plan would destroy the resource. It would block the plan instead of correcting it.
D=-target workaround: targeting is meant for exceptional recovery, still addresses by index, and does not remove the fragility. The next normal plan would show the same shifting.
T: Items that come and go need stable identity, so use for_each with keys instead of count with indexes.

@ TF-TA004 D4 T4.2 applied definition
S: A resource block sets for_each = toset(["ann", "bob"]) on aws_iam_user.staff. Which expression correctly refers to the ARN of the user for "bob"?
A: aws_iam_user.staff["bob"].arn
B: aws_iam_user.staff[1].arn
C: aws_iam_user.staff.bob.arn
D: aws_iam_user.staff.arn["bob"]
K: A
G: ## Referencing instances of a for_each resource
A resource with `for_each` becomes a **map of instances** keyed by the keys of the map or the elements of the set. Individual instances are addressed with square brackets and the key as a string: `aws_iam_user.staff["bob"]`. Attributes follow after the instance.
- A resource with `count` is a list of instances, so it uses numeric indexes: `aws_iam_user.staff[0]`.
- Inside the block itself, `each.key` and `each.value` refer to the current element; they are not available from other blocks.
- To collect one attribute from all instances you can use a `for` expression, for example `[for u in aws_iam_user.staff : u.arn]`.
W: Key lookup: the instances are keyed by the set elements, so the bracket with the string "bob" selects that instance, and .arn then reads its attribute.
X: B=Numeric index: numeric indexes belong to count. With for_each the instances have string keys, and the number 1 is not a key, so the lookup fails.
C=Dot notation on the key: dot syntax reads attribute names, and the instances collection has no attribute called bob. Keys must be passed with brackets.
D=Attribute first: the resource itself is a collection, not an object, so it has no arn attribute. The key has to come before the attribute.
T: for_each instances are addressed by key, TYPE.NAME["key"].attribute; count instances by index.

@ TF-TA004 D4 T4.2 applied definition
S: Which TWO statements about the count and for_each meta-arguments are accurate? (Select TWO)
A: The value given to for_each must be a map or a set of strings, so a list of strings has to be converted first, for example with toset()
B: A single resource block may set both count and for_each, in which case for_each decides which instances exist and count caps their number
C: The keys used by for_each may be taken from attributes that Terraform will only learn after another resource is created
D: A single resource block cannot use both count and for_each together; Terraform rejects the configuration
E: Inside a for_each block, count.index gives the position of the current instance in the original collection
K: A,D
G: ## Rules for repeating resources
- `for_each` accepts a **map** or a **set of strings**. A list must be converted (`toset(var.names)`); a list could contain duplicates and has no natural keys.
- `count` and `for_each` are **mutually exclusive** on one block.
- The set or map keys that `for_each` uses must be known during planning, because Terraform needs them to name instances. Values may be unknown, keys may not.
- `count.index` exists only with `count`; with `for_each` you use `each.key` and `each.value`.
W: A=Map or set of strings: this is the documented input type, so lists are converted with toset() and each element becomes a key.
D=Mutually exclusive: Terraform reports an error if both meta-arguments appear in the same block, because it could not decide how to name the instances.
X: B=Both together: there is no combination behaviour where one limits the other. They are alternatives, and the configuration is rejected.
C=Keys from unknown values: for_each keys must be known at plan time. Keys derived from an attribute only available after apply produce an error asking for a map or set whose keys are known.
E=count.index with for_each: count.index is defined only for count. A for_each block uses each.key and each.value.
T: for_each takes a map or a set of strings, and count and for_each cannot share one block.

@ TF-TA004 D4 T4.3 applied use-case
S: The variable instance_type has default "t3.micro". The directory contains terraform.tfvars (instance_type = "t3.small") and prod.auto.tfvars (instance_type = "t3.medium"), and the shell exports TF_VAR_instance_type=t3.large. Which value does terraform apply use when it is run with no other options?
A: t3.medium, because *.auto.tfvars files outrank terraform.tfvars, TF_VAR_ variables and the default
B: t3.large, because environment variables are the highest-priority way to set a variable
C: t3.small, because terraform.tfvars is always loaded last so it overrides every other source
D: t3.micro, because the default argument in the variable block wins unless a value is passed with -var
K: A
G: ## Variable precedence
When the same variable receives values from several sources, Terraform applies them from lowest to highest priority, and the later one wins:
- the `default` in the `variable` block (lowest)
- environment variables named `TF_VAR_<name>`
- `terraform.tfvars`
- `terraform.tfvars.json`
- `*.auto.tfvars` and `*.auto.tfvars.json` in lexical order
- `-var` and `-var-file` options on the command line, in the order given (highest), and values from HCP Terraform workspaces
So in this scenario environment, tfvars and auto.tfvars each supply a value, and the auto file overrides the two below it.
W: *.auto.tfvars: the file prod.auto.tfvars sits above terraform.tfvars, the TF_VAR_ environment variable and the default in the order of precedence, and no -var option is present to outrank it.
X: B=Environment variable first: TF_VAR_ values rank below both tfvars files, so they only win over the variable's default.
C=terraform.tfvars last: that file is loaded before auto.tfvars files, which override it, and the command line overrides both.
D=Default wins: the default is the lowest level and is used only when no other source provides a value.
T: Lowest to highest: default, TF_VAR_ environment, terraform.tfvars, auto.tfvars, then -var and -var-file.

@ TF-TA004 D4 T4.3 applied use-case
S: prod.tfvars sets region = "us-west-2". An engineer runs terraform apply -var="region=eu-west-1" -var-file="prod.tfvars". Which region is used for the variable region?
A: us-west-2, because command-line options apply in the order given and the later -var-file replaces the earlier -var
B: eu-west-1, because -var always takes precedence over any variable definition file
C: Terraform stops with a conflict error, because the same variable name is assigned twice among the command-line options of one run
D: eu-west-1, because values supplied on the command line override only when they appear last
K: A
G: ## Command-line values are ordered
`-var` and `-var-file` share the same precedence tier, the highest one that Terraform offers on the CLI. Within that tier, Terraform applies them **in the order they appear**, so a later option replaces the value from an earlier one.
- `terraform apply -var-file=prod.tfvars -var=region=eu-west-1` ends with `eu-west-1`.
- `terraform apply -var=region=eu-west-1 -var-file=prod.tfvars` ends with the value in the file.
Assigning the same variable twice inside one file is an error, but across separate sources and repeated command-line options the later value simply replaces the earlier one.
W: Later option wins: the file is given after -var, so its region replaces the earlier eu-west-1. Terraform does not rank -var above -var-file.
X: B=-var always wins: the two options have equal rank, and only their order decides. A -var placed before the file loses.
C=Conflict error: overlapping values across separate command-line options are legal, and the later option replaces the earlier. Only assigning a variable twice within one file is rejected.
D=Wrong value: it names the right idea (position on the command line decides) but applies it backwards. The file is the last option here, so its value replaces eu-west-1.
T: -var and -var-file have equal rank, and the last one on the command line wins.

@ TF-TA004 D4 T4.3 applied use-case
S: A module accepts a variable env, and the team wants a clear error during plan, before any resource is touched, when someone passes a value other than dev, stage or prod. Which configuration achieves this?
A: A validation block inside variable "env" with condition = contains(["dev", "stage", "prod"], var.env) plus an error_message
B: A postcondition block inside variable "env" that tests contains(["dev", "stage", "prod"], self) after the plan is built
C: A type constraint of enum(["dev", "stage", "prod"]) on variable "env"
D: A check block inside variable "env" that warns when the value is outside the allowed list
K: A
G: ## Validating input variables
A `variable` block can hold one or more `validation` blocks. Each has a `condition` (an expression that must be true) and an `error_message`. Terraform checks them when it evaluates the inputs at the start of a plan, so a bad value stops the run before any resource is planned.
```
variable "env" {
  type = string
  validation {
    condition     = contains(["dev", "stage", "prod"], var.env)
    error_message = "env must be dev, stage or prod."
  }
}
```
Type constraints control the shape (string, number, list, object); they cannot list allowed values.
W: Variable validation: the validation block is the feature built for input checks, it fails the run with the message you supply, and it happens before resources are planned.
X: B=postcondition in a variable: postconditions belong to resource and data lifecycle blocks, where self refers to the object. A variable block has no lifecycle and no self.
C=enum type: Terraform has no enum type. Type constraints such as string or list(string) describe shape only, so allowed values need validation.
D=check inside a variable: check is a top-level block, not nested in a variable, and its assertion only produces a warning, so it would not stop a bad value.
T: Restrict input values with validation blocks in the variable; types only describe shape.

@ TF-TA004 D4 T4.4 applied use-case
S: A variable describes server definitions: each server has a name (string), a cpu_count (number) and a list of tags (list of strings). Which type constraint models one server most precisely?
A: object({ name = string, cpu_count = number, tags = list(string) })
B: map(string), a collection of string keys whose values must all be converted to text
C: list(string), a plain ordered sequence of text values addressed by position
D: set(number), an unordered collection of unique numbers with no names or text
K: A
G: ## Structural versus collection types
Terraform has two families of complex types.
- **Collections** hold many values of ONE type: `list(T)` (ordered, indexed by number), `set(T)` (unordered, unique), `map(T)` (string keys, all values of type T).
- **Structural types** hold values of DIFFERENT types: `object({...})` has named attributes, each with its own type; `tuple([...])` has a fixed sequence of positions with individual types.
A record with a string, a number and a list is the standard case for an `object`. `map(string)` could carry the name and a number converted to text, but not a list.
W: object: every attribute gets its own type, so name stays a string, cpu_count a number and tags a list of strings, and Terraform validates each one.
X: B=map(string): every value must be a string. A list of tags does not convert to a string, so the input fails the type check.
C=list(string): it is a sequence of strings with no named attributes, so it cannot tell a name from a tag or carry a number.
D=set(number): a set holds unique numbers only. It cannot hold a name, tags or any named structure.
T: Mixed types per record means object (or tuple by position); collections hold one type only.

@ TF-TA004 D4 T4.4 applied definition
S: Which TWO statements about Terraform's complex types are accurate? (Select TWO)
A: A tuple has a fixed number of elements and each position can have its own type, for example tuple([string, number, bool])
B: An object has named attributes and each attribute can have a different type, for example object({ port = number, host = string })
C: A list may contain elements of different types as long as the list is declared with the type any
D: A set keeps the insertion order of its elements and allows duplicate values, which makes it ideal for ordered output
E: A map may use numbers as keys, and its values may mix strings, numbers and lists freely
K: A,B
G: ## Choosing a complex type
- `list(T)`: ordered collection, every element the same type `T`, indexed from 0.
- `set(T)`: unordered collection of **unique** values of one type; it has no index, and duplicates collapse.
- `map(T)`: string keys, all values of type `T`.
- `tuple([T1, T2, ...])`: structural; a fixed number of positions, each with its own type.
- `object({ a = T1, b = T2 })`: structural; named attributes, each with its own type.
`any` is a placeholder that lets Terraform infer one concrete type; it does not allow different element types in one list.
W: A=Tuple: positions are typed one by one and the length is fixed by the declaration, which suits a short mixed sequence.
B=Object: it is the structural type with named attributes, each with an individual type, which is what makes it suitable for settings records.
X: C=List with any: a list still has a single element type. With any, Terraform picks one type for the whole list and converts values to it if it can.
D=Set order and duplicates: a set discards duplicates and has no defined order, so it is the wrong choice for ordered output.
E=Mixed map: map keys are strings, and all values must share one element type. Mixed value types need an object.
T: Collections (list, set, map) hold one element type; tuples and objects mix types by position or name.

@ TF-TA004 D4 T4.4 applied use-case
S: A module takes an object variable named listener with attributes protocol and port. Callers must always set protocol, but port should default to 8080 when a caller leaves it out. Which type constraint does this?
A: object({ protocol = string, port = optional(number, 8080) })
B: object({ protocol = string, port = number }) with default = { port = 8080 } on the variable
C: map(any) with a lookup() call in every resource that reads the port
D: tuple([string, number]) where the second element is skipped when it is not needed
K: A
G: ## Optional object attributes
By default every attribute declared in an `object({...})` type is required. Wrapping the type in `optional(...)` makes the attribute optional. The second argument is the **default** Terraform fills in when the caller omits the attribute.
```
variable "listener" {
  type = object({
    protocol = string
    port     = optional(number, 8080)
  })
}
```
A caller that passes `{ protocol = "HTTPS" }` gets `port = 8080` automatically, and one that passes `port = 443` keeps it. Without a default, an omitted optional attribute becomes `null`.
W: optional with default: protocol stays required, and an omitted port is replaced by 8080 by the type system itself, so every consumer sees a complete object.
X: B=Variable default: a default applies only when the whole variable is not set. If the caller passes an object without port, the attribute is still missing, and a default without protocol would not satisfy the type either.
C=map(any) with lookup: this loses type checking of the attributes and spreads the default over every place that reads the port, instead of defining it once.
D=Tuple: tuples have a fixed length, and an element cannot be skipped. A shorter tuple fails the type check.
T: Use optional(type, default) inside object types for attributes callers may omit.

@ TF-TA004 D4 T4.5 applied use-case
S: var.servers is a list of objects with attributes name (string) and enabled (bool). Which expression returns a list of only the names of the enabled servers?
A: [for s in var.servers : s.name if s.enabled]
B: var.servers[*].name
C: { for s in var.servers : s.name => s.enabled }
D: [for s in var.servers : s.name where s.enabled == true]
K: A
G: ## for expressions
A `for` expression transforms and filters a collection into a new one.
- Square brackets build a **list/tuple**: `[for x in var.list : upper(x)]`.
- Curly braces build a **map/object**: `{ for k, v in var.map : k => v.id }`, using `=>` between key and value.
- An optional `if` clause at the end filters elements: `[for x in var.list : x if x != ""]`.
There is no `where` keyword in the HCL syntax. A splat (`[*]`) is a shorter form for simple attribute extraction without filtering.
W: List for expression with if: brackets produce a list, s.name picks the attribute, and the trailing if keeps only elements whose enabled value is true.
X: B=Splat expression: var.servers[*].name returns the names of every server. A splat has no filtering clause, so disabled servers stay in.
