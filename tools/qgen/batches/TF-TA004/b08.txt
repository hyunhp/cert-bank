@ TF-TA004 D8 T8.1 applied use-case
S: A team keeps its configuration in a local folder and wants `terraform plan` and `terraform apply` to execute in the HCP Terraform workspace `app-prod` of organization `acme`, using the variables stored in that workspace. Which setup achieves this?
A: Add a `provider "tfe"` block for organization acme and run `terraform apply`, which then ships the configuration to the workspace for execution
B: Set the `TF_WORKSPACE` environment variable to app-prod and run `terraform apply`, with no further block in the configuration
C: Add a `backend "local"` block whose path is `acme/app-prod`, so state and execution both move to the workspace
D: Add a `cloud` block under `terraform` naming the organization and workspace, run `terraform login`, then run `terraform init`
K: D
G: ## The CLI-driven workflow
HCP Terraform has three run workflows: UI/VCS-driven, API-driven and CLI-driven. In the CLI-driven workflow you keep using the normal `terraform plan` and `terraform apply` commands, but the run executes remotely in an HCP Terraform workspace and its output streams to your terminal.
Three things connect the working directory to a workspace:
- Credentials: `terraform login` obtains an API token (or you configure one manually in the CLI configuration).
- Connection settings: a `cloud` block inside the `terraform` block names the organization and the workspace (by `name`, or by `tags`).
- Initialization: `terraform init` completes the link.
```
terraform {
  cloud {
    organization = "acme"
    workspaces {
      name = "app-prod"
    }
  }
}
```
Because the run happens in the workspace, it uses the workspace's variables and state, and policy checks apply, without secrets being copied to your laptop.
W: Cloud block with login and init: this is the documented CLI integration. The block names the organization and workspace, the login supplies a token, and init links the directory, so later plan and apply run remotely with the workspace variables.
X: A=tfe provider: the `tfe` provider manages HCP Terraform resources such as workspaces and variables. It does not make `terraform apply` run remotely, so a provider block cannot connect the CLI to a workspace.
B=TF_WORKSPACE only: that variable selects among workspaces of a configuration that already has a backend or cloud block. Without a `cloud` block the CLI has no idea where HCP Terraform is.
C=Local backend path: the local backend writes a state file to a path on disk. It is not an HCP Terraform address, and it never moves execution to remote workers.
T: CLI-driven runs need a token (terraform login), a cloud block and terraform init; then plan and apply run in the workspace.

@ TF-TA004 D8 T8.1 applied use-case
S: A workspace is linked to a VCS repository. A developer opens a pull request against the tracked branch that adds a new security group. What does HCP Terraform do?
A: It queues a standard run on the workspace and blocks later runs until a reviewer confirms or discards it from the VCS provider
B: It starts a speculative plan and links it in the pull request, showing possible changes and policy results but never applying them
C: It ignores the pull request, because a VCS-linked workspace processes only commits that are merged into the tracked branch
D: It starts a run that applies automatically to a temporary copy of the infrastructure so the reviewer can test the change
K: B
G: ## Plan-only runs
A **speculative plan** is a plan-only run. It shows what Terraform would change and which policies the change affects, but it can never be applied. Because it does not touch real infrastructure it does not wait for other runs and does not block the run queue.
Ways to start one:
- Opening a pull (merge) request against the branch tracked by a VCS-linked workspace. The plan is linked from the pull request, and re-run when the pull request is updated.
- Running `terraform plan` with the CLI integration.
- Choosing Plan only in the UI, or the API with `plan-only`.
Merging the pull request is what starts the normal (applyable) run in a VCS-driven workspace.
W: Speculative plan on pull requests: this is the default for VCS-linked workspaces. Reviewers see the plan and policy results before merging, and the plan cannot change infrastructure.
X: A=Standard run queued: a standard run would plan and then wait to be applied, blocking the queue. Pull requests start plan-only runs instead, which never block other runs.
C=Ignored until merge: the commit-triggered run happens after merge, but pull requests do trigger speculative plans (automatic speculative plans are on by default).
D=Temporary copy: HCP Terraform has no feature that applies a pull request to a throwaway copy. Speculative plans are plan-only.
T: Pull request opened means speculative plan (plan-only, not applyable); merge means a normal run.

@ TF-TA004 D8 T8.1 applied comparison
S: A workspace has a linked VCS repository. An engineer who uses a `cloud` block runs `terraform plan` from a laptop. Which statement is accurate?
A: It starts a speculative plan in the workspace from the local files; this works with VCS-linked workspaces but the plan cannot be applied
B: It is rejected, because a VCS-linked workspace accepts runs only from webhooks that the VCS provider sends
C: It runs locally against a local state file, because only `terraform apply` is ever a remote operation
D: It creates a saved plan that the engineer must apply from the same laptop with `terraform apply` and the plan file name
K: A
G: ## CLI-driven run types
With the CLI integration:
- `terraform plan` starts a **speculative plan** in the workspace using your local files. It works with all workspaces and can co-exist with the VCS-driven workflow; you can check results (including policy checks) without copying sensitive variables to your machine.
- `terraform apply` starts a standard plan and apply, but remote apply is for workspaces **without** a linked VCS repository.
- `terraform plan -out FILE` followed by `terraform apply FILE` runs a two-part saved-plan run, also for workspaces without a linked repository (CLI 1.6 or later).
So in a VCS-linked workspace the source of truth for real runs stays in version control, while engineers can still preview local edits.
W: Speculative plan from the CLI: plan is always allowed as a plan-only remote run, even when a repository is linked, and the result cannot be applied.
X: B=Webhooks only: webhooks start the VCS-driven runs, but speculative plans from the CLI are explicitly supported next to them.
C=Local plan: with the CLI integration both plan and apply are remote operations. The plan output streams to the terminal while it executes in the workspace.
D=Saved plan: a saved plan needs `-out`; a plain `terraform plan` makes a speculative plan, and saved plans are for workspaces without a linked repository anyway.
T: `terraform plan` through the cloud block is a remote speculative plan, valid even in VCS-linked workspaces; remote `terraform apply` is for workspaces without VCS.

@ TF-TA004 D8 T8.1 applied use-case
S: A company's tooling generates Terraform files from another data source and decides itself when a run should happen. The files are not in a version control system HCP Terraform supports, and build agents must call HTTPS endpoints without the Terraform CLI. Which run workflow fits?
A: The UI/VCS-driven workflow, where HCP Terraform fetches the code after a webhook and starts a run on each new commit
B: The CLI-driven workflow with `terraform plan -out`, because saved plans work without any Terraform binary on the agent
C: The API-driven workflow, where the tooling packages the files as a `.tar.gz`, uploads a configuration version and creates a run
D: A workspace in Local execution mode, where the build agents execute the plan and only push the state to the workspace
K: C
G: ## API-driven runs
In the API-driven workflow a workspace is not tied to a VCS repository and no VCS webhook drives runs. Your own tooling (usually CI) decides when configuration has changed and then calls the HCP Terraform API:
1. Create a configuration version for the workspace.
2. Upload the configuration as a `.tar.gz` archive, with the `.tf` files at the root of the archive.
3. Create a run for that configuration version and poll or confirm it.
This is the most flexible workflow, and it allows generated configuration or unsupported version control systems, but you must build the tooling. When the team can use the Terraform CLI, the CLI-driven workflow is the simpler choice.
W: API-driven workflow: HCP Terraform does not need to fetch code, since the tooling uploads a configuration version and starts the run through the `runs` and `configuration-versions` APIs, with no CLI required.
X: A=VCS-driven: this workflow requires a supported VCS repository and webhooks, which this team does not have.
B=Saved plan: `terraform plan -out` and `terraform apply FILE` are Terraform CLI commands, so they need the binary on the agent, which the scenario excludes.
D=Local execution mode: it turns off remote operations. The agents would need Terraform installed to run it, and HCP Terraform would only store state.
T: Custom tooling that uploads configuration and creates runs over HTTPS is the API-driven workflow.

@ TF-TA004 D8 T8.1 applied troubleshooting
S: After a workspace's execution mode was changed to Local, engineers run `terraform apply` on their laptops. They find that the variables stored in the workspace are ignored and no policy checks run. Which statement explains this?
A: In Local mode the workspace only stores state and runs happen on the workstation, so workspace variables and features that need remote runs, such as policy enforcement, are not used
B: Local mode puts the workspace in a read-only state until an organization owner approves every run from the workspace page
C: Workspace variables and policy checks apply only to speculative plans, and a standard apply from a laptop never uses either
D: Variables are injected only into runs started from the UI, and policy checks need a VCS repository to be linked to the workspace
K: A
G: ## Execution modes
Each workspace has an execution mode that decides where Terraform runs:
- **Remote** (the default for new workspaces): runs on disposable HCP Terraform workers. Variables, policy enforcement, notifications and the run queue all work.
- **Agent**: runs on HCP Terraform agents you host, to reach private networks.
- **Local**: runs on your own workstation or CI worker using the CLI integration. The workspace acts only as a remote backend that stores state (the Variables page is not evaluated).
Local mode suits teams that only want hosted state. Features that depend on remote execution, such as Sentinel or OPA policy enforcement and run notifications, are not available when you run locally.
W: Local execution mode: the workspace becomes a state store. Terraform runs on the laptop, so the workspace's variables and variable sets are not evaluated and remote-run features such as policy enforcement do not run.
X: B=Read-only until approved: Local mode does not block the workspace. It simply moves execution to the workstation.
C=Speculative plans only: workspace variables and policy checks apply to standard remote runs as well, which is why this is not the cause.
D=UI-started runs only: variables are used by any remote run, whatever started it, and policy checks do not depend on a VCS link.
T: Local execution mode means state only; variables, policy checks and other remote-run features need Remote or Agent mode.

HCP Terraform is an execution platform. A Terraform run managed by it is a **remote operation**: it runs on HCP Terraform's own disposable workers, with the workspace's configuration version, variables and state.
Runs can be started by VCS webhooks, the UI, the API or the Terraform CLI. With the CLI the output is streamed back to your terminal, so it feels like a local run. E=Parallel applies: a workspace processes runs one at a time, and a pending run waits for the current one to finish.

S: A `cloud` block names the workspace `payments-dev`, which does not exist yet. An engineer runs `terraform init`, then `terraform plan`, and the plan fails with an authentication error from the cloud provider. Which statement explains this?

@ TF-TA004 D8 T8.1 applied troubleshooting
S: Run A in a workspace has finished planning and is waiting for someone to confirm it. A teammate merges another commit to the tracked branch, which creates run B. What happens to run B?
A: Run B is planned immediately and the two plans are combined into one apply to save time
B: Run B cancels run A automatically, since only the newest configuration version may be applied
C: Run B is planned in parallel, and whichever run is confirmed first applies while the other is discarded
D: Run B stays pending and is not planned until run A is applied or discarded, because the workspace processes runs in order
K: D
G: ## The run queue
Every workspace keeps its own ordered queue. A new run is added to the end, and while another run is in progress, the new one stays **pending**: HCP Terraform does not even plan it, because the current run may change what a later run would do. A run that finished planning keeps the workspace busy until someone applies or discards it.
Exceptions that never block or wait: plan-only (speculative) runs, and the planning stage of saved-plan runs. A workspace can also be locked on purpose; then runs are created but do not start until it is unlocked.
Each run is bound to the configuration version and variables that existed when it started, so later commits affect only later runs.
W: Pending behind run A: runs are serialized per workspace. Run B waits until A is applied or discarded, which also protects the state from conflicting plans.
X: A=Combined plans: HCP Terraform never merges plans. Each run has its own plan and applies exactly that plan.
B=Automatic cancellation: a newer run does not cancel one that awaits confirmation. A user must apply or discard it.
C=Parallel plans: standard runs do not plan in parallel in one workspace. Only plan-only runs and the planning stage of saved plans skip the queue.
T: Standard runs are serialized per workspace: a plan that awaits confirmation holds back later runs until it is applied or discarded.

@ TF-TA004 D8 T8.2 applied use-case
S: A policy set with a Sentinel policy at the soft mandatory enforcement level fails during a run. What happens?
A: The run continues to apply, and the failure appears only as a warning in the policy results
B: The run is discarded and the workspace is locked until an organization owner unlocks it
C: The run stops before apply, and a user with the permission to override policies can let it continue
D: The run stops, and nobody can continue it until the policy is changed in version control
K: C
G: ## Policy enforcement
Policies are rules that check a Terraform plan against security rules and best practices. HCP Terraform evaluates them during the run, after the plan and before the apply. Policies are written in Sentinel (HashiCorp's policy-as-code framework) or in OPA (Open Policy Agent, Rego).
Each policy has an enforcement level:
- **Advisory**: a failure never stops the run; it is only shown in the results.
- **Soft mandatory**: a failure stops the run, but a user with the right permission can override it and continue.
- **Hard mandatory**: a failure stops the run until the cause is fixed, unless the policy set is configured to allow overrides.
(OPA policies use the names advisory, mandatory overridable and mandatory.)
W: Soft mandatory: it blocks the apply by default but allows an authorized user to override the failed policy, which makes it suitable for rules that need an exception path.
X: A=Warning only: this describes the advisory level. Soft mandatory failures stop the run.
B=Discard and lock: policies do not lock workspaces. A failed policy only affects the current run.
D=Fix in VCS only: that is the strictest behavior (hard mandatory without overrides). Soft mandatory is designed to be overridable.
T: Advisory warns, soft mandatory blocks but can be overridden, hard mandatory blocks until fixed.

@ TF-TA004 D8 T8.2 applied comparison
S: A team has the organization permission Manage all workspaces and also holds only the Read role on the workspace `billing`. What can the team do in `billing`?
A: Only read, because a workspace-level role replaces what the organization granted for that workspace
B: Only read, because the lower of the two permission levels always applies under least privilege
C: Everything allowed by Manage all workspaces, because permissions from all scopes are additive and the highest level of access applies
D: Nothing until an owner chooses which of the two permission sets is active for the team on that workspace

G: ## Effective permissions
You can grant permissions at three scopes: organization, project and workspace. HCP Terraform adds them together: a team's effective permissions are the sum of what it receives from every scope, and the most permissive result applies to each resource. The scope that granted a permission does not matter.
- Manage all workspaces (organization) plus Read (workspace) gives Manage all workspaces on that workspace.
- Conversely, a broad read permission at the organization does not cap or override a Write role on one workspace.
Recommended practice is least privilege: grant only what each team needs, at the narrowest scope that works.
W: Additive permissions: the broader grant is not reduced by the narrower role, so the team can manage the workspace.
X: A=Workspace role replaces: roles never subtract or replace permissions from other scopes.
B=Lower level wins: HCP Terraform takes the highest level, not the lowest. Least privilege is advice for how you assign grants.
D=Owner chooses: no selection step exists. Permissions combine automatically.
T: Team permissions at organization, project and workspace scope add up; the most permissive one wins.

@ TF-TA004 D8 T8.2 applied use-case
S: A platform team wants every non-root module used in any workspace to come from the organization's own registry, and a run that violates this must stop. Which feature enforces it?
A: A required_providers block in each root module that limits the hostnames providers may use
B: A variable validation block in each module that rejects module source addresses outside the registry

G: ## Governing module usage
The private registry lets teams share modules, but sharing alone does not stop a team from sourcing a module from somewhere else. To enforce a rule, use **policy enforcement**: a Sentinel or OPA policy can inspect the module calls of the configuration and the plan. `terraform login tfe.example.com` then obtains a token for that host, as the login command works with any server that supports the login protocol. Without `hostname`, the block targets `app.terraform.io`.
W: Hostname in the cloud block: the same block and login command work against Terraform Enterprise once the host name is set.
X: A=backend enterprise: no such backend exists; the `cloud` block is used for both HCP Terraform and Terraform Enterprise.
