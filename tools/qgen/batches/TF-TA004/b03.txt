@ TF-TA004 D3 T3.1 applied definition
S: Which statement correctly describes the core Terraform workflow?
A: Write configuration as code, plan to preview the proposed changes, then apply to provision the infrastructure.
B: Initialize the backend, validate against the provider APIs, then deploy the changes straight to the target environment.
C: Draft the resources in the console, export them to a state file, then run a test suite to approve the release.
D: Plan the desired state, write the plan file by hand, then apply it after a manual review by the provider.
K: A
G: ## The three-step loop
HashiCorp describes the core workflow as three steps that repeat for every change:
- **Write**: author infrastructure as code in `.tf` files, normally kept in version control.
- **Plan**: Terraform compares the configuration with the state and the real objects and previews what it would create, change or destroy.
- **Apply**: Terraform carries out the plan and records the result in state.
Commands such as `terraform init`, `validate` and `fmt` support these steps, and `destroy` ends the life of the infrastructure, but they are not separate stages of the three-step description.
W: Write, Plan, Apply is the documented core workflow: you author code, preview the changes, and only then provision them.
X: B=Init, API validation, deploy: `terraform validate` never contacts provider APIs or remote services, and the workflow has a plan preview before anything is deployed.
C=Console, export, test suite: Terraform is driven by configuration you write first; state is produced by apply, not exported from console work, and there is no built-in release test stage.
D=Hand-written plan file: plan files are generated by `terraform plan -out`, never written by hand, and the provider does not review them.
T: The core workflow is Write, Plan, Apply, repeated for every change.

@ TF-TA004 D3 T3.1 applied use-case
S: A teammate cloned a repository that already has an initialized working directory. Before running `terraform plan`, which TWO things should you expect the plan to do by default? (Select TWO)
A: Read the current state of existing remote objects to check that the state is up to date.
B: Compare the current configuration with the prior state and note the differences.
C: Create the missing resources so the infrastructure matches the configuration.
D: Rewrite the dependency lock file with the newest provider versions available.
E: Format the configuration files so they follow the canonical style.
K: A,B
G: ## What plan does
`terraform plan` creates an execution plan, a preview. By default it does three things in order:
- Reads the current state of already-existing remote objects so that Terraform's view is up to date.
- Compares the configuration with the prior state and notes the differences.
- Proposes actions that would make the remote objects match the configuration.
It stops there. Changes happen only in `apply` (or when you run `apply` on a saved plan).
W: A=Refresh remote objects: plan reads existing remote objects first so the comparison uses their current attributes.
B=Compare configuration and state: the differences between the configuration and prior state are what become the proposed create, update or destroy actions.
X: C=Create the missing resources: plan only proposes actions; nothing is created until apply runs.
D=Rewrite the lock file: provider versions are selected by `terraform init` (and changed only with `init -upgrade`), not by plan.
E=Format files: formatting is the job of `terraform fmt`; plan never rewrites your source files.
T: Plan refreshes, compares and proposes; it never changes infrastructure.

@ TF-TA004 D3 T3.1 applied troubleshooting
S: An apply that creates a network, a subnet and a database fails on the database with a quota error. The network and subnet were created successfully. What is the state of things and what should you do?
A: Terraform rolled back the network and subnet, so you can run the same apply again from a clean start.
B: Terraform recorded the network and subnet in state and left them in place, so fix the cause and apply again.
C: Terraform locked the workspace permanently, so you must destroy everything before attempting another apply.
D: Terraform discarded the state update, so you must import the network and subnet before the next apply.
K: B
G: ## Apply is not transactional
When a resource fails during `terraform apply`, Terraform logs the error, updates the state file with the changes that did succeed, releases the state lock, and exits. It does not roll back the partially-completed apply.
After you fix the cause (here, the quota), you run `terraform apply` again. Terraform sees that the network and subnet already exist in state and only creates the database.
W: Created objects stay in state and in the real environment; a second apply continues from there and creates what is missing.
X: A=Automatic rollback: Terraform has no rollback mechanism, so the network and subnet remain.
C=Permanent lock: the state lock is released when the apply exits; nothing forces a destroy.
D=Discarded state update: Terraform writes the successful changes to state before exiting, so importing is unnecessary and would conflict with existing state entries.
T: A failed apply keeps what succeeded in state; fix the error and apply again.

@ TF-TA004 D3 T3.2 applied definition
S: A new engineer asks what `terraform init` does in a freshly cloned repository. Which TWO activities are part of initialization? (Select TWO)
A: Installs the provider plugins the configuration needs and records the selections in the dependency lock file.

K: A,C
G: ## What init prepares
`terraform init` prepares a working directory. It:
- Initializes the backend named in the configuration.
- Downloads child modules from their `source` arguments.
- Installs provider plugins and writes `.terraform.lock.hcl`.
It is the first command after writing or cloning a configuration, and it is safe to run many times. It never creates infrastructure.
W: A=Provider installation and lock file: init finds, downloads and installs providers, then records the selected versions in the lock file.
C=Backend initialization: init configures the backend settings so state operations work in later commands.
X: B=Create infrastructure: only apply creates resources and state entries for them.
D=Proposed changes: producing a list of changes is plan's job.
E=Argument checks against the API: init does not validate argument values against remote services, and `validate` does not either.
T: Init installs providers and modules and sets up the backend; it never changes infrastructure.

@ TF-TA004 D3 T3.2 applied use-case
S: The lock file pins a provider to 5.40.0, and the configuration constraint is `~> 5.0`. You want the newest 5.x release. Which command does that?
A: `terraform init -reconfigure`
B: `terraform plan -refresh-only`
C: `terraform init -upgrade`
D: `terraform apply -replace=provider`
K: C
G: ## init -upgrade and the lock file
After a successful init, the selected provider versions are written to the dependency lock file, and later init runs reuse them. `terraform init -upgrade` ignores the selections in the lock file and installs the newest versions that still match the version constraints. It also updates installed modules to the latest available source code.
The result is a changed `.terraform.lock.hcl`, which you review and commit.
W: `init -upgrade` is the supported way to move to newer allowed provider versions.
X: A=`-reconfigure`: this concerns backend configuration and has no effect on provider versions.
B=`plan -refresh-only`: it syncs state with remote objects and does not touch installed plugins.
D=`apply -replace=provider`: `-replace` takes a resource instance address, and providers are not resources that can be replaced.
T: Use `terraform init -upgrade` to move past the versions pinned in the lock file within your constraints.

@ TF-TA004 D3 T3.2 applied use-case
S: A configuration has used the default local backend. A `backend "s3"` block is added, and the existing state must move to the bucket. Which command accomplishes this?
A: `terraform init -migrate-state`
B: `terraform init -reconfigure`
C: `terraform apply -refresh-only`

G: ## Changing backends
Re-running init after a backend change requires either `-reconfigure` or `-migrate-state` to update the settings.
- `-migrate-state` copies the existing state to the new backend and may prompt you to confirm moving workspace states. `-force-copy` answers those prompts with yes (and implies `-migrate-state`).
- `-reconfigure` disregards the existing configuration and does not migrate any state.
W: `-migrate-state` copies the current state into the new S3 backend so Terraform keeps tracking the same resources.
X: B=`-reconfigure`: this starts using the new backend without copying state, so Terraform would see an empty state and plan to recreate everything.
C=`apply -refresh-only`: it updates state from remote objects in the current backend and does not move state.
D=`-backend=false`: it skips backend configuration entirely, so nothing is migrated.
T: Use `init -migrate-state` to carry existing state to a new backend.
