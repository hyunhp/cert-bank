S: A V2 pipeline in tooling account 111111111111 (us-east-1) deploys a CloudFormation stack into workload account 222222222222 in us-east-1 and, since this week, also in eu-west-1. Each deploy action assumes DeployRole in the workload account. The us-east-1 action keeps succeeding, but the eu-west-1 action fails, and tooling-account CloudTrail in eu-west-1 shows kms:Decrypt AccessDenied for DeployRole on key-euw1. Company policy forbids sharing one KMS key across Regions, and DeployRole must not reach artifact buckets of other pipelines. What should the team change?
A: Grant DeployRole kms:Decrypt and kms:DescribeKey in key-euw1's key policy, plus s3:GetObject on this pipeline's prefix in the eu-west-1 bucket
B: Add DeployRole to key-use1's key policy for kms:Decrypt and kms:DescribeKey, because a cross-Region action reads artifacts that the pipeline Region encrypted

K: A
G: ## Artifacts for cross-Region actions
A pipeline needs an artifact bucket in its own Region and **one artifact bucket per Region where it runs actions**, listed in `artifactStores`. Each bucket and its KMS key must be in the **same Region as the action** and in the **same account as the pipeline**. CodePipeline copies artifacts into the action's Regional store before the action runs.
## Cross-account deploys
The action assumes a role in the target account. That role reads the artifact from the Regional bucket, so the bucket policy (or role policy) must allow `s3:GetObject`, and the **key policy of that Region's key** must allow `kms:Decrypt` (and `kms:DescribeKey`).
## Reading the evidence
The us-east-1 action works, so DeployRole already has access to key-use1 and its bucket. The denial names key-euw1, so the missing grant is on the eu-west-1 key.
W: Grant on key-euw1 and the eu-west-1 prefix: the eu-west-1 action reads the copy stored in the eu-west-1 artifact store, so DeployRole needs that key and only that pipeline's objects, which also respects the least-privilege rule.
X: B=Grant on key-use1: DeployRole already has it, and the eu-west-1 action never reads the us-east-1 copy; CloudTrail shows the denial on key-euw1.
C=Multi-Region replica: it uses one key across Regions, which policy forbids, and each replica has its own key policy anyway, so the us-east-1 grant would not carry over.
D=Key in the workload account: the key for an artifact store must be in the same account as the pipeline, so this artifact store configuration is not valid.
T: Each cross-Region action uses its Region's artifact store and key; a cross-account action role needs Decrypt on that Regional key, not the pipeline Region's key.

S: An in-place CodeDeploy deployment group targets an Auto Scaling group of 20 instances behind an ALB, and a full deployment takes about 70 minutes. Last Tuesday a deployment started at 07:30; the ten instances launched at 08:00 served the previous release until the next deployment three days later, although the deployment itself succeeded. Which TWO statements explain the evidence? (Select TWO)
A: Instances launched during an in-place deployment receive the revision that was last deployed successfully, not the revision that is being deployed at that moment
B: Instances launched during an in-place deployment wait in Pending:Wait until the running deployment ends, and then receive the newest revision from the launch hook
C: With outdated instances set to IGNORE, CodeDeploy does not start the follow-on deployment that would bring instances launched mid-deployment up to date
D: With outdated instances set to IGNORE, CodeDeploy delays the follow-on deployment until the next scheduled scaling action, which came three days later

G: ## What a launch deployment installs
CodeDeploy adds a **launch lifecycle hook** to the Auto Scaling group. When an instance launches, CodeDeploy runs a launch deployment while the instance waits in `Pending:Wait`. If a deployment is **in progress** at that moment, the new instance gets the revision that was **previously deployed**, not the one being rolled out.
## Follow-on deployments
To fix those instances, CodeDeploy by default starts a **follow-on deployment** right after the first one ends. This behavior can be changed through the API or CLI so that outdated instances are left on the old revision (the outdated instances strategy `IGNORE` instead of `UPDATE`).
## Suspending processes
You can ask CodeDeploy to suspend the `ScheduledActions` process during deployments; scheduled actions that start meanwhile are skipped, not run later. It is not the default, and it does not stop scaling policies.

C=IGNORE suppresses the follow-on: the history shows no deployment after Tuesday's, which is exactly what the changed outdated-instances setting does.
X: B=Waiting for the deployment to end: launch deployments do not wait for the running deployment; they install the last successful revision.
D=Delayed follow-on: with IGNORE there is no follow-on at all; scheduled actions have nothing to do with when follow-ons run.
E=ScheduledActions suspended by default: suspension is optional, and suspended scheduled actions are skipped rather than run later, which does not match instances launching at 08:00.

@ DOP-C02 D1 T1.4 expert troubleshooting
S: A V2 pipeline in QUEUED mode deploys to production in its Prod stage. On Monday an engineer added a smoke-test action to Prod and an On Failure condition with the Rollback result, saving a new pipeline structure version. Prod's last successful executions all ran the previous Friday. On Tuesday the first execution after the edit failed in Prod at the new smoke test; the stage shows Failed, and no rollback execution appears in the history. Customers are seeing errors now, the team must restore Friday's release within 15 minutes, and the release manager wants automatic rollback to work for later failures. What explains this, and what should the team do now?
A: Rollback targets must come from the current structure version, so start an execution now with a source revision override for Friday's commit
B: On Failure rollback requires automatic retry on stage failure, so turn on stage retry for Prod and rerun the failed execution to trigger the rollback
C: Stage rollback is not supported in QUEUED mode, so switch the pipeline to SUPERSEDED mode and roll the Prod stage back to Friday's execution by hand
D: A rollback can target only executions of the rollback type, so start a manual rollback of Prod and choose the most recent failed Tuesday execution
K: A
G: ## Stage rollback rules
A stage rollback starts a new execution of the stage using the source revisions and variables of an earlier **successful** execution of that stage. Limits:
- The target must have been started in the **current pipeline structure version**. Editing the pipeline creates a new version, so older successes are no longer valid targets.
- You cannot roll back to an execution that is itself a rollback, and source stages cannot be rolled back.
- Rollback is unavailable in PARALLEL mode; QUEUED and SUPERSEDED both support it.
- Automatic stage retry cannot be combined with On Failure conditions.
## Source revision overrides
A V2 pipeline can be started with a **source revision override** (for example a specific commit ID), which redeploys a known revision through the normal stages.
W: Structure version plus a source override: Friday's executions predate Monday's edit, so the condition had no valid target; starting an execution pinned to Friday's commit restores production now, and future failures will have a valid target once this version has a successful run.
X: B=Turn on stage retry: automatic retry cannot be used together with On Failure conditions, and retrying the smoke test does not restore Friday's release.
C=Switch to SUPERSEDED: QUEUED mode supports stage rollback; only PARALLEL does not. Switching modes also edits the structure again.
D=Rollback-type target: it is the reverse, a rollback can never target a rollback execution, and a failed execution is never a valid target.
T: CodePipeline stage rollback needs a successful target execution from the current structure version; after editing a pipeline, redeploy with a source revision override if needed.

@ DOP-C02 D2 T2.1 expert use-case
S: Stack app-core owns a security group, an Auto Scaling group with a target tracking policy, and an RDS DB instance with AutoMinorVersionUpgrade set to true. Stack team-b, owned by another team, adds port 9000 to that security group with an AWS::EC2::SecurityGroupIngress resource. During an incident an engineer added port 22 to the group in the console and tagged the Auto Scaling group with a CostCenter key that is not in the template. The group now runs 14 instances because of scaling, and RDS applied a minor engine upgrade. The team creates a drift-aware change set for app-core whose template only raises MaxSize. Which THREE results should they expect when they execute it? (Select THREE)
A: The port 22 rule that the engineer added in the console is removed from the security group, because it is not in the template
B: The port 9000 rule that team-b's stack attaches is removed too, because an attachment from another stack is seen as drift
C: The Auto Scaling group keeps 14 instances, because its desired capacity is managed by the scaling policy as an AWS-managed property
D: The CostCenter tag key is removed from the Auto Scaling group, because tag keys that are not in the template count as drift
E: The DB instance's engine is returned to the minor version that the template recorded, because the upgrade happened outside CloudFormation
F: If the execution fails, resources roll back to the previous template's values, which also removes the changes made outside CloudFormation
K: A,B,C
G: ## Drift-aware change sets
A change set created with `--deployment-mode REVERT_DRIFT` compares three states: the **actual** configuration read from the service APIs, the **previous deployment**, and the **desired** template. Executing it brings every resource to the desired state, even resources the template did not change.
## The exceptions to know
- **AWS-managed properties** keep their actual values when the template does not change them, for example desired capacity driven by a scaling policy, capacity managed by Application Auto Scaling, and minor versions applied through `AutoMinorVersionUpgrade`.
- **External tag keys** that are not in the template are left alone (to protect ABAC tags).
- **Cross-stack attachments** such as `AWS::EC2::SecurityGroupIngress` or `AWS::IAM::Policy` from another stack are seen as drift and can be reverted.
- Immutable properties are not reconciled, and write-only properties are compared with the previous deployment.
- If execution fails, CloudFormation rolls back to the **actual pre-deployment state**, keeping out-of-band changes.
W: A=Console rule removed: port 22 is drift on a property the template defines, so the change set reverts it.
B=team-b's rule removed: attachments from another stack look like drift on app-core's group and are reverted, a real risk to coordinate before executing.
C=Desired capacity kept: capacity set by the scaling policy is an AWS-managed property, so the group stays at 14.
X: D=CostCenter removed: drift-aware change sets do not remove or modify tag keys that are not in the template.
E=Engine version reverted: an automatic minor upgrade under AutoMinorVersionUpgrade is AWS-managed drift and is left untouched.
F=Rollback to template values: a failed drift-aware deployment rolls back to the actual pre-deployment state and preserves out-of-band changes.
T: Drift-aware change sets revert out-of-band changes and cross-stack attachments, but keep AWS-managed properties and external tag keys, and roll back to actual state.
V: AWS CloudFormation, Amazon EC2 Auto Scaling, Amazon RDS

@ DOP-C02 D2 T2.1 expert troubleshooting
S: A security team built a custom CloudFormation Hook with a RESOURCE target for AWS::DynamoDB::Table and a preDelete handler that fails when the table carries the tag data-class=critical. It runs in FAIL mode in all 50 accounts, and it correctly blocked a developer who tried to delete a whole stack. Last week another developer removed a critical table from a template and updated the stack; the table was deleted while the stack was in UPDATE_COMPLETE_CLEANUP_IN_PROGRESS, and the Hook's invocation history shows no call. Critical tables must survive any template change, while ordinary schema and capacity updates must keep working. Which TWO measures meet these requirements? (Select TWO)
A: Add DeletionPolicy and UpdateReplacePolicy set to Retain on each critical table, so removal or replacement leaves the table in place
B: Apply a stack policy denying Update:Delete and Update:Replace on the critical tables' logical IDs, so updates that remove them fail
C: Add a preUpdate handler for AWS::DynamoDB::Table to the Hook, so a stack update that drops the table from the template is rejected beforehand
D: Raise the Hook's handler timeout and retry count, because the cleanup phase gave the preDelete handler too little time to evaluate the tag
E: Change the Hook's target from RESOURCE to CLOUD_CONTROL, so deletions during stack cleanup are evaluated through the Cloud Control API
K: A,B
G: ## When Hooks do not run
Resource Hooks run before CloudFormation creates, updates or deletes a resource during stack operations. One important gap: **stack operations that end in the UpdateCleanup phase do not invoke a Hook**. That includes an update after a resource was removed from the template, and deleting the old resource after a replacement. So a `preDelete` handler never sees these deletions.
Hooks also have a fixed 30-second timeout per invocation and up to 3 retries.
## Protections that do apply
- **DeletionPolicy: Retain** keeps the physical resource when it is removed from the template or the stack is deleted; **UpdateReplacePolicy: Retain** keeps the old resource on replacement.
- A **stack policy** can deny `Update:Delete` and `Update:Replace` on chosen logical IDs while still allowing `Update:Modify`, so normal property changes keep working.
W: A=Retain policies: even if the table leaves the template or is replaced, CloudFormation keeps the physical table.
B=Stack policy: an update that would delete or replace a critical table fails, while ordinary modifications are still allowed.
X: C=preUpdate handler: removing a table from the template is not an update of that table; the deletion happens in cleanup, where Hooks are not invoked.
D=Longer timeout and retries: the Hook was never invoked, so timing is not the issue, and the 30-second limit and 3 retries are fixed.
E=CLOUD_CONTROL target: that target evaluates operations made through the Cloud Control API, not CloudFormation stack cleanup.
T: CloudFormation Hooks are not invoked in UpdateCleanup, so protect critical resources with Retain policies and stack policies, not only with preDelete Hooks.

B=Complete the second pause: the same hook pauses the instance again in Pending:Wait when it leaves the pool; something must complete it quickly, or every scale-out waits for the hook timeout.
X: C=Running pool state: it would avoid the stop, but finance requires the pool to stay Stopped.
D=Longer grace period: the instances already pass health checks; a longer grace period does not finish the interrupted bootstrap.
E=New AMI: it is a valid pattern in general, but the AMI pipeline belongs to another team and cannot change.
T: With warm pools, use a launch lifecycle hook so bootstrap finishes before the stop, and remember the hook pauses again when the instance leaves the pool.
