@ DOP-C02 D2 T2.1 advanced use-case
S: A stack update changes a property of an RDS DB instance that requires replacement. The team must never lose data if this happens by mistake and wants to see the impact before executing. What should it do?
A: Run drift detection on the stack first, then execute the update once it reports no drift.
B: Set UpdateReplacePolicy and DeletionPolicy to Snapshot, then review a change set first.
C: Set DeletionPolicy to Snapshot alone, then run the update directly from the console.
D: Enable stack termination protection, then check the stack events after the update.
K: B
G: ## Replacement during a stack update
Some property changes cannot be applied in place. For an `AWS::RDS::DBInstance`, changing properties such as the DB instance identifier or certain storage settings makes CloudFormation create a **new** DB instance and then delete the old one. Without protection, the old database and its data are gone.
## The two attributes that protect data
- `DeletionPolicy` controls what happens when the resource is removed from the template or the stack is deleted.
- `UpdateReplacePolicy` controls what happens to the **old physical resource when an update replaces it**.
Both accept `Delete`, `Retain` and, for resources that support it such as RDS, `Snapshot`. Setting both to `Snapshot` or `Retain` covers deletion and replacement.
## Seeing the impact first
A **change set** lists each resource change with its `Action` and a `Replacement` field (`True`, `False` or `Conditional`). Reviewing it before executing reveals an accidental replacement before anything happens.
W: UpdateReplacePolicy and DeletionPolicy plus a change set: `UpdateReplacePolicy` decides what happens to the old DB instance when an update replaces it, and `DeletionPolicy` covers removal or stack deletion, so `Snapshot` on both keeps the data either way. The change set shows `Replacement: True` for the DB instance before anything is executed, which is the impact review the team asked for.
X: A=Drift detection first: drift detection compares live resources with the template to find changes made outside CloudFormation. A clean drift result says nothing about what the update will replace, and it does not preserve the old database.
C=DeletionPolicy alone, update directly: `DeletionPolicy` does not apply to the old resource that a replacement removes; that is governed by `UpdateReplacePolicy`. Running the update directly also skips the requested preview.
D=Termination protection, then stack events: termination protection only blocks deleting the whole stack, not an update that replaces one resource inside it, and reading stack events afterwards shows the damage only once it has happened.
T: Replacement is governed by UpdateReplacePolicy, not just DeletionPolicy; pair both with a change set review to see the replacement before it happens.
V: AWS CloudFormation

@ DOP-C02 D5 T5.2 advanced use-case
S: A company wants EC2 instances that deviate from a required configuration to be automatically corrected, not just reported. Which approach fits?
A: Tag policies in AWS Organizations that standardize an owner tag on noncompliant instances
B: A weekly Config compliance report emailed to the operations team, who then fix each instance
C: Config rules with automatic remediation, or State Manager associations enforcing configuration
D: CloudTrail trails with CloudWatch Logs metric filters that alert on configuration API calls
K: C
G: ## Reporting versus enforcing configuration
Detection alone lists drift; the requirement here is correction without human work. Two AWS mechanisms do that:
- **AWS Config rules with automatic remediation**: when a rule marks an instance `NON_COMPLIANT`, Config runs an SSM Automation document to fix it, such as enabling detailed monitoring or attaching a required IAM instance profile.
- **Systems Manager State Manager associations**: an association applies a document (for example `AWS-RunPatchBaseline`, `AWS-ConfigureAWSPackage`, or a custom Command document) to targeted instances on a schedule, re-applying it if the instance drifts from the desired state inside the OS.
## Example
An association runs every 30 minutes and ensures the CloudWatch agent is installed and running on every instance tagged `env=prod`. If someone stops the agent, the next association run starts it again, and association compliance shows which instances were fixed.
W: Config remediation or State Manager associations: a Config rule with automatic remediation runs an SSM Automation document as soon as an instance becomes `NON_COMPLIANT`, and a State Manager association re-applies the desired configuration on a schedule, so drift is corrected without people doing the work.
X: A=Tag policies: they standardize tag keys and values across an organization; they do not change instance configuration and cannot fix drift.
B=Weekly emailed compliance report: Config detects the drift correctly, but a report still leaves people to fix each instance by hand, and drift stays in place for up to a week. The requirement is correction, not reporting.
D=CloudTrail with metric filters: CloudTrail records AWS API calls, so an alert fires when someone calls an API. It does not see drift inside the operating system and it changes nothing back; it is detection only.
T: "Corrected, not just reported" = automatic remediation (Config + Automation) or desired-state enforcement (State Manager).
V: AWS Config, AWS Systems Manager

@ DOP-C02 D4 T4.2 applied use-case
S: A team needs to monitor an API's availability from multiple geographic locations every minute. Which feature fits?
A: CloudWatch Synthetics canaries
B: CloudWatch Logs Insights queries
C: AWS Config managed rules
D: AWS CloudTrail event history
K: A

Metrics collected by the application only show requests that actually arrive. To know whether users can reach an API, you need **synthetic monitoring**: scripted requests sent on a schedule.

- Run on a schedule as often as once per minute.
- Call endpoints, check status codes and response content, and can take screenshots of UI flows.
- Publish metrics such as `SuccessPercent` and `Duration`, which alarms can use.
Blueprints such as the API canary and heartbeat monitor give a starting script. A canary runs in the Region where it is created, so checking from several geographic locations means deploying canaries in several Regions.
W: Synthetics canaries: canaries are scripted requests that run as often as once per minute, check status codes and response content, and publish `SuccessPercent` and `Duration` metrics. Deploying them in several Regions tests the API from several geographic locations.
X: B=Logs Insights queries: they query logs after the fact and send no requests to the API, so they cannot test availability from other locations.
C=Config managed rules: they evaluate whether resource configuration is compliant, not whether an endpoint responds to callers.
D=CloudTrail event history: it lists AWS API calls made in the account, not the health or reachability of the company's own API.
T: Proactive, scheduled availability checks from multiple locations are CloudWatch Synthetics canaries, deployed in each Region you want to test from.

S: A company has 40 microservices, each with its own repository. It wants a consistent CI/CD pipeline for every service without maintaining 40 hand-written pipeline definitions. Which approach fits?
A: Use one shared pipeline whose build stage compiles and deploys the 40 services together per commit
B: Define a reusable pipeline template in IaC and instantiate it per service with its own parameters
C: Publish a pipeline style guide on the wiki and let each team write its own pipeline definition

K: B
G: ## Pipelines as reusable templates
When many services need the same CI/CD flow (source, build, test, deploy), the pipeline itself should be infrastructure as code, written once and **instantiated per service with parameters** such as repository name, branch, build image and target accounts.
Common ways to do this on AWS:
- A **CDK construct** (for example a `ServicePipeline` class) that each service instantiates with its own properties.
- A **CloudFormation template** with parameters, deployed once per service, optionally distributed through AWS Service Catalog as a product teams can launch.

- Consistency: every service gets the same stages, security scans and approvals.
- Central change: improving the template (adding a scan stage, for example) rolls out to all 40 pipelines by redeploying.
- Independence: each service still has its own pipeline, so one service's failed build does not block the others.
W: Reusable IaC pipeline template per service: the pipeline is written once (a CDK construct or a parameterized CloudFormation template) and deployed per service with its repository, branch and targets, so all 40 services get identical, independently running pipelines that are improved in one place.
X: A=One shared pipeline for all services: each commit rebuilds and redeploys all 40 services, coupling their releases so one failing service blocks the rest and builds become slow.
C=Style guide plus team-written pipelines: a written guide is not enforced, so the result is 40 hand-written definitions that differ over time, which is what the company wants to avoid.
D=Console clones per service: each clone is another hand-made definition that drifts from the original, and every improvement has to be repeated 40 times.
T: Define the pipeline once as a parameterized IaC template and stamp it out per service; one shared pipeline couples releases and copies drift.
V: AWS CodePipeline, AWS CloudFormation

@ DOP-C02 D4 T4.1 advanced use-case
S: A company has 40 workload accounts. The operations team wants to view metrics, logs, and traces from all accounts in one monitoring account and build cross-account dashboards without copying data. Which approach fits BEST?
A: CloudWatch cross-account observability, linking source accounts to a monitoring account sink.
B: Export the log groups to S3 nightly and query them with Athena from the monitoring account.
C: Subscribe each log group to a Kinesis stream in the monitoring account and index it there.
D: Create IAM users for the operations team in each workload account and switch between them.
K: A
G: ## CloudWatch cross-account observability
CloudWatch cross-account observability lets one **monitoring account** see telemetry that stays stored in many **source accounts**. It is built on Observability Access Manager (OAM):
- In the monitoring account you create a **sink** and a sink policy saying which accounts or which organization may link to it.
- In each source account you create a **link** to that sink and choose the data types to share, such as CloudWatch metrics, log groups and X-Ray traces (and related features like Application Signals).
Links can be rolled out to all accounts in an organization, for example with a CloudFormation StackSet.
## What the monitoring account gets
Operators in the monitoring account can graph metrics from any linked account on one dashboard, create alarms on them, run Logs Insights queries across accounts and view cross-account X-Ray trace maps. The data is not copied: queries read it where it lives, so there is no pipeline to build or keep in sync.
W: Cross-account observability: an Observability Access Manager sink in the monitoring account and a link in each source account share metrics, log groups and traces. Operators then build dashboards, alarms and Logs Insights queries across the 40 accounts while the data stays where it is.
X: B=Nightly S3 export with Athena: this copies the data, is up to a day old, covers logs but not metrics or traces, and gives no metric dashboards.
C=Kinesis subscription per log group: it copies log data into another account, needs a subscription on each log group, and still does not bring metrics or traces together.
D=IAM users per account: operators would sign in to 40 accounts separately with no single view, and it adds 40 sets of long-term credentials to manage.
T: Use CloudWatch cross-account observability (sink and links) to view telemetry in place across accounts, instead of exporting or streaming copies.
V: Amazon CloudWatch

@ DOP-C02 D5 T5.3 advanced use-case
S: Several EC2 instances in a production Auto Scaling group unexpectedly began failing health checks and were replaced by the group. Reviewing AWS Health events for the account reveals a scheduled EC2 instance retirement event listing those exact instance IDs, issued due to underlying hardware degradation. What is the most appropriate root-cause conclusion and follow-up action?
A: Hardware degradation per the Health event; confirm impact and automate replacement via EventBridge.
B: A short health check grace period in the group; lengthen it and treat the Health event as noise.
C: A misconfiguration on the instances; open a support case asking AWS to withdraw the retirement.
D: Expected Auto Scaling behavior; close the incident because the group already restored capacity.
K: A
G: ## AWS Health and instance retirement
**AWS Health** reports events that affect your specific resources, not only general service status. One common event type is **EC2 instance retirement**: AWS detects that the underlying host hardware is degraded or failing and schedules the instances on it to be stopped or terminated.
- The event lists the affected instance IDs and a retirement date.
- Instances can fail, or be stopped or terminated, when the hardware fails or the date arrives.
- Stopping and starting an EBS-backed instance moves it to healthy hardware; in an Auto Scaling group, replacing the instance does the same.
## Acting on it
AWS Health events are delivered to **Amazon EventBridge**, so they can trigger automation. For example, an EventBridge rule for `AWS_EC2_INSTANCE_RETIREMENT_SCHEDULED` can start an SSM Automation runbook or Lambda function that replaces or stop-starts the instance during a quiet period, well before the retirement date.
W: Hardware degradation with proactive automation: the retirement event names exactly the instances that failed, so the root cause is degraded host hardware. Confirm the impact, then route `AWS_EC2_INSTANCE_RETIREMENT_SCHEDULED` events through EventBridge to a runbook that replaces the instances in a quiet period before the hardware fails.
X: B=Grace period and Health event as noise: the grace period only delays when health checks start counting for new instances; it does not make running instances fail. Account-specific Health events describe real impact on your resources, and this one lists the failed instances.
C=Misconfiguration and support case: retirement events come from AWS detecting degraded hardware, not from customer configuration, so there is nothing to dispute.
D=Expected behavior, close the incident: Auto Scaling did restore capacity, but the instances failed unexpectedly first; acting on retirement events ahead of time avoids that unplanned loss next time.
T: When AWS Health lists the failing instances in a retirement event, the cause is hardware; route Health events to EventBridge and replace instances before they fail.
V: AWS Health, Auto Scaling, EC2

@ DOP-C02 D3 T3.2 applied comparison
S: A DevOps engineer must choose between a step scaling policy and a target tracking scaling policy for an Auto Scaling group backing a workload where the relationship between load and required capacity is well understood and stable over time. Which is generally the recommended approach, and why?
A: Step scaling, because its fixed step sizes react faster than target tracking's calculations.
B: Step scaling, because target tracking supports just the predefined CPU and network metrics.
C: Scheduled scaling, because a stable load-to-capacity ratio lets capacity follow a timetable.
D: Target tracking, which adjusts capacity to hold a chosen metric at a target value.
K: D
G: ## Step scaling versus target tracking
- **Step scaling**: you create CloudWatch alarms and define steps yourself, for example "CPU 60-80%: add 2 instances; above 80%: add 4". You tune thresholds, step sizes and alarms, and must write matching scale-in steps.
- **Target tracking**: you pick a metric and a value, such as average CPU at 50% or `ALBRequestCountPerTarget` at 1,000. Auto Scaling creates and manages the alarms and calculates how much to scale out or in to keep the metric near that value.
## When to use which
When capacity rises roughly in proportion to load, such as twice the traffic needing about twice the instances, target tracking is the recommended default: less to configure and it adjusts proportionally in both directions. It supports predefined metrics, custom metrics and metric math. Step scaling fits cases that need precise, custom responses at specific thresholds.
W: Target tracking: with a well-understood, stable relationship between load and capacity, you pick a metric and a value (for example average CPU at 50%), and Auto Scaling creates the alarms and scales out and in proportionally to keep the metric there, with far less tuning than step scaling.
X: A=Step scaling reacts faster: speed depends on the alarms, metrics and warm-up settings; step scaling is not inherently faster and needs more manual tuning of thresholds and step sizes.
B=Target tracking limited to predefined metrics: target tracking supports custom CloudWatch metrics and metric math, not only the predefined ones.
C=Scheduled scaling: a stable ratio between load and capacity says nothing about when load arrives. Schedules follow the clock, so any traffic change outside the schedule is missed.
T: When load and capacity scale proportionally, target tracking is the recommended, low-maintenance choice; step scaling is for custom threshold responses.
V: EC2 Auto Scaling, CloudWatch

@ DOP-C02 D2 T2.3 advanced troubleshooting
S: A Step Functions state machine automates a multi-account resource cleanup task. One Task state invokes a Lambda function that occasionally fails due to a downstream API's transient throttling, causing the entire execution to fail immediately without retrying. The team wants the state machine to automatically retry that specific step a few times with exponential backoff before giving up and routing to a cleanup and notification path if all retries are exhausted. What should they add to the state machine definition?
A: Wrap the Task in a single-branch Parallel state, which reruns a failed branch with backoff.
B: Add a 30-second Wait state before the Task to space out the calls to the downstream API.
C: Add a Retry with exponential backoff on the Task, plus a Catch to the cleanup state.
D: Leave it unchanged, since Step Functions retries a failed Task three times by default.
K: C
G: ## Error handling in Step Functions
When a Task state fails, the whole execution fails unless the state says otherwise. Task, Parallel and Map states have two fields for this:
- **Retry**: a list of retriers. Each one matches errors (`ErrorEquals`, such as `Lambda.TooManyRequestsException` or `States.TaskFailed`) and sets `IntervalSeconds`, `MaxAttempts` and `BackoffRate`. With interval 2, backoff 2 and 3 attempts, the waits are 2 s, 4 s and 8 s. `JitterStrategy: FULL` adds randomness.
- **Catch**: runs after retries are used up. It matches errors and sends the execution to another state with `Next`, for example a `Cleanup` state that tidies up and publishes an SNS notification. `ResultPath` can keep the error details for that path.
## Example
A Task with `Retry: [{ErrorEquals: ["States.TaskFailed"], IntervalSeconds: 2, MaxAttempts: 3, BackoffRate: 2}]` and `Catch: [{ErrorEquals: ["States.ALL"], Next: "NotifyAndCleanup"}]` retries the throttled call three times, then routes to the cleanup path instead of failing the execution.
W: Retry with backoff plus Catch: a retrier on the Task matches the throttling error and waits `IntervalSeconds`, multiplied by `BackoffRate` on each attempt, up to `MaxAttempts`; when the retries are exhausted, the Catch sends the execution to the cleanup and notification state instead of failing it.
X: A=Single-branch Parallel state: a Parallel state runs branches concurrently and retries nothing unless you add a Retry field to it; a retry there would rerun the whole branch, and it still needs a Catch for the failure path.
B=Wait state before the Task: a fixed pause does not stop a downstream API from throttling under load, and it gives no retry or failure routing when the call still fails.
D=Default retries: Step Functions does not retry a Task unless a Retry field is defined; without one, the first error fails the execution, which is exactly the behavior described.
T: In Step Functions, transient failures need an explicit Retry with backoff, and failures that remain need a Catch to a recovery path; nothing is retried by default.
V: AWS Step Functions, AWS Lambda

C=Tag immutability: it blocks pushes that reuse a tag, which would break this CI process, and it does not delete the existing untagged images.

@ DOP-C02 D1 T1.2 advanced use-case
S: A pipeline deploys to dev, staging, and production environments requiring different test depths: dev runs only unit tests; staging runs unit, integration, and load tests; production should proceed only if staging's tests and a security scan passed. How should the pipeline be structured to enforce this?
A: Run the unit, integration, and load tests once in the build stage and reuse that result for each environment.
B: Deploy to the three environments in parallel stages and roll back any environment whose tests fail later.
C: Use sequential per-environment stages with their own tests, and a security scan gating the production stage.
D: Use one shared environment for dev, staging, and production, separated by feature flags per release.
K: C
G: ## Progressive promotion
A release pipeline moves one artifact through environments in order, and each environment acts as a **gate** for the next:
- **Dev stage**: deploy, run unit tests.
- **Staging stage**: deploy, run unit, integration and load tests.
- **Security scan action**: run in or before the production stage entry.
- **Production stage**: starts only if everything earlier succeeded.
In CodePipeline, stages run in sequence; a failed action stops the stage and the artifact never reaches later stages. Actions inside a stage can run in parallel (same `runOrder`) or in order.
Example: `Source → Build → Dev (deploy, unit) → Staging (deploy, integration, load) → Security (scan) → Prod (deploy)`.
## Why sequence matters
Integration and load tests only mean something against the environment they ran in. Promoting the same tested artifact step by step keeps that evidence valid.
W: Sequential per-environment stages with a gated production stage: dev runs unit tests, staging runs unit, integration and load tests, and the security scan runs before production. CodePipeline stages run in order and a failed action stops the artifact, so production receives only what passed every earlier gate.
X: A=Tests once in the build stage: integration and load tests need a deployed environment, and a result from one context does not prove the others work, so the per-environment gates are meaningless.
B=Parallel deploy with later rollback: production gets the change before staging tests pass, so nothing gates production; rollback only limits damage after users are affected.
D=One environment split by feature flags: flags hide features but do not isolate data, capacity or configuration, so load and integration tests would run against production.
T: Different test depth per environment means sequential stages with gates, so production receives only an artifact that passed every earlier stage.

S: A company must prevent any account from creating resources without encryption at the organization level. Which preventive control fits?
A: SCPs that deny create actions lacking encryption condition keys

G: ## Preventive versus detective controls
A **preventive** control stops a noncompliant action before it happens; a **detective** control finds it afterwards. W: SCPs with encryption condition keys: a `Deny` statement on create actions when keys such as `ec2:Encrypted` or `rds:StorageEncrypted` are false, attached at the root or an OU, blocks unencrypted create requests in every member account before any resource exists.

D=Wiki page and checklist: guidance relies on each team remembering it and enforces nothing.

@ DOP-C02 D5 T5.1 advanced troubleshooting
S: A central security account has an EventBridge rule intended to receive GuardDuty findings forwarded from ten member accounts via a custom event bus. Findings from nine accounts arrive correctly, but events from the tenth account never appear, even though CloudTrail confirms GuardDuty is generating findings there. What should the engineer check first?
A: Whether AWS Config is recording the GuardDuty detector in the tenth account.
B: Whether GuardDuty is also enabled in the central security account itself.
C: The tenth account's rule target bus ARN and the bus policy for its PutEvents.
D: Whether the central account's operator IAM user has AdministratorAccess.
K: C
G: ## Cross-account event forwarding
To send GuardDuty findings from a member account to a central account with EventBridge, two pieces must line up:
- **In the member account**: a rule on the default bus matching `source: aws.guardduty` whose target is the central bus ARN, for example `arn:aws:events:us-east-1:111122223333:event-bus/security-bus`, and an IAM role that the rule uses to call `events:PutEvents` on that bus. The Region matters too: findings stay in the Region where GuardDuty produced them.
- **In the central account**: the custom bus's **resource-based policy** must allow the member account (or the whole organization via `aws:PrincipalOrgID`) to call `events:PutEvents`.
## Troubleshooting one missing account
If nine accounts work, the central rule is fine. Look at what is unique to the tenth: a typo in the bus ARN or wrong Region, a missing or wrong IAM role on its rule, or a bus policy statement that lists nine account IDs instead of ten. The member rule's `FailedInvocations` metric shows whether delivery is being attempted and failing.
W: Target bus ARN and bus policy: what is unique to the tenth account is its own forwarding rule and its entry in the central bus policy. A wrong bus ARN or Region on its rule, or a resource-based policy that does not allow that account to call `events:PutEvents`, stops only its events while the other nine arrive.
X: A=Config recording in the member account: Config is not involved in GuardDuty or EventBridge event delivery; findings are forwarded without it.
B=GuardDuty in the central account: findings are generated in the member account and forwarded by EventBridge; nine accounts already arrive, so the central GuardDuty setting is not the difference.
D=AdministratorAccess on an IAM user: cross-account event delivery is authorized by the bus policy and the sender's rule role, not by the permissions of a human IAM user in the central account.
T: When one account's cross-account events are missing, check that account's rule target ARN and role, and that the central bus policy allows it to PutEvents.
V: EventBridge, GuardDuty, IAM

S: A company wants to detect sensitive data such as PII in S3 buckets across all accounts. Which service fits?
A: Amazon Macie with a delegated administrator
B: AWS Config with S3 managed rules org-wide
C: AWS Shield Advanced with default protections
D: Amazon Inspector with EC2 and ECR scanning
K: A
G: ## What Amazon Macie does
Amazon Macie discovers sensitive data in Amazon S3.
- It keeps an inventory of buckets and evaluates their security, such as public access, encryption and sharing with other accounts.
- It inspects object contents with **managed data identifiers** (names, addresses, credit card numbers, passport numbers, credentials and more) and **custom data identifiers** based on regular expressions.
- **Automated sensitive data discovery** samples objects across your buckets continuously; **sensitive data discovery jobs** scan chosen buckets in depth.
- Findings go to the Macie console, EventBridge and Security Hub.
## Multi-account
With AWS Organizations, the management account designates a Macie **delegated administrator**, which enables Macie in member accounts and sees their buckets and findings centrally.
W: Macie with a delegated administrator: Macie inspects S3 object contents with managed and custom data identifiers, and a delegated administrator enables it in all member accounts and sees their buckets and findings centrally.
X: B=Config with S3 managed rules: Config evaluates bucket configuration, such as whether a bucket is encrypted or public. It never reads the objects, so it cannot find PII inside them.
C=Shield Advanced: Shield protects internet-facing resources against DDoS attacks and has no data classification features.
D=Inspector EC2 and ECR scanning: Inspector looks for software vulnerabilities and network exposure on instances, container images and Lambda functions. It does not classify data stored in S3.
T: Finding PII in S3 across accounts is Macie's job; Config checks settings, Inspector checks vulnerabilities.
V: Amazon Macie

@ DOP-C02 D5 T5.1 advanced use-case
S: Whenever an EC2 instance in production enters the 'stopped' state unexpectedly, the team wants to capture diagnostics, start the instance again, and notify the channel automatically. Which design fits BEST?
A: An EventBridge rule on the state-change event that starts an SSM Automation runbook.
B: An Auto Scaling group of one per instance, so a stopped instance gets replaced.
C: A CloudWatch dashboard of instance states reviewed by the on-call engineer each shift.
D: A cron job on a bastion host that polls describe-instances hourly and restarts them.
K: A
G: ## Event-driven remediation
EC2 publishes an `EC2 Instance State-change Notification` event to Amazon EventBridge whenever an instance changes state. A rule can match only the relevant ones, for example:
- `source`: `aws.ec2`, `detail-type`: `EC2 Instance State-change Notification`, `detail.state`: `stopped`
- optionally filtered further in the runbook by a tag such as `env=prod`.
## Systems Manager Automation as the target
An EventBridge rule can start an **SSM Automation runbook** directly, passing the instance ID from the event. A runbook is a sequence of steps such as:
- collect diagnostics (for example capture the console output or screenshot, or copy logs from the EBS volume),
- `aws:changeInstanceState` to start the instance again,
- `aws:executeAwsApi` to publish to an SNS topic that feeds the team's channel.
Runbooks run with an assumed IAM role, log each step and can be reused across accounts and Regions.
W: EventBridge rule starting an SSM Automation runbook: the `EC2 Instance State-change Notification` event with `state: stopped` triggers the runbook within seconds; its steps collect diagnostics, start the same instance again and publish to the team's SNS topic, the same way every time.
X: B=Auto Scaling group of one: Auto Scaling treats a stopped instance as unhealthy and replaces it with a new one. The original instance is terminated instead of started again, and no diagnostics are captured from it.
C=Dashboard reviewed each shift: a person must notice the change first, so nothing happens automatically and response time depends on when someone looks.
D=Hourly polling cron job on a bastion: it can miss a stop for up to an hour, depends on one self-managed host, and needs custom code for diagnostics and alerts.
T: React to EC2 state changes with an EventBridge rule that runs an SSM Automation runbook; polling and dashboards are slow and manual.
V: Amazon EventBridge, AWS Systems Manager Automation

@ DOP-C02 D1 T1.2 applied use-case
S: A team wants to run integration tests in an ephemeral environment created for each pipeline run and destroyed afterward. Which approach fits?
A: Deploy a temporary CloudFormation stack in a test stage and delete it after the tests
B: Run the integration tests against the production stack right after each deployment
C: Keep one long-lived shared test stack that each pipeline run deploys into and reuses
D: Skip integration tests in the pipeline and rely on production monitoring and alarms
K: A
G: ## Ephemeral test environments
An ephemeral environment is created for one pipeline run, used for tests, and deleted afterwards. With infrastructure as code this is cheap and repeatable:
- A test stage runs a CloudFormation deploy action that creates a stack with a unique name, for example one that includes the pipeline execution ID (`#{codepipeline.PipelineExecutionId}` in a V2 pipeline).
- A CodeBuild action runs the integration test suite against that stack's outputs (URL, queue name, table name).
- A final action deletes the stack (CloudFormation action mode `DELETE_ONLY`, or `aws cloudformation delete-stack` in a build step), plus a cleanup path for failed runs so nothing is left running.
## Why it helps
- **Isolation**: tests from one run cannot corrupt data or state used by another run.
- **Fidelity**: the environment is built from the same templates as production, so it also tests the infrastructure code.
- **Cost**: resources exist only for the duration of the tests.
W: Temporary CloudFormation stack: a test stage creates a uniquely named stack for the run, CodeBuild runs the integration tests against its outputs, and a final action deletes it, so each run gets a clean, isolated, production-like environment that stops costing money when the run ends.
X: B=Test against production: integration tests create and modify data and may fail in ways that affect real users; production is the environment the tests are meant to protect.
C=One shared long-lived stack: concurrent runs interfere with each other's data and deployments, leftover state makes results unreliable, and it is not created and destroyed per run as required.
D=Skip tests, rely on monitoring: monitoring detects defects only after users are affected; it does not replace catching them before release.
T: Build a fresh stack per pipeline run, test against it, and tear it down; shared or production environments cannot give isolated, repeatable integration tests.
V: AWS CloudFormation

@ DOP-C02 D4 T4.3 advanced use-case
S: A company wants to identify the top IP addresses causing the most 5XX errors in ALB logs over time. Which feature fits?
A: CloudWatch Contributor Insights rules
B: AWS Config conformance packs and rules
C: AWS Trusted Advisor security checks
D: CloudWatch composite alarms on 5XX counts
K: A
G: ## Top-N analysis on log data
Questions like "which clients cause the most errors" are top-N problems. **CloudWatch Contributor Insights** answers them continuously:
- A rule reads structured log events (JSON or common log format) in CloudWatch Logs, defines **keys** to group by, such as the client IP, and **filters**, such as status code 500 to 599.
- It reports the top contributors over time as a graph, and the results can be added to dashboards or used in alarms.
Contributor Insights reads only CloudWatch Logs, while ALB delivers access logs to S3 as space-delimited files. The logs must first be sent into a CloudWatch Logs log group, for example by a Lambda function that is triggered by new log objects and writes each entry as a JSON event. After that, a rule keyed on the client IP and filtered on 5XX codes shows which addresses cause the most errors hour by hour.
W: Contributor Insights rules: once the ALB entries are in CloudWatch Logs as structured events, a rule keyed on the client IP and filtered on status codes 500-599 ranks the addresses behind the most 5XX responses and graphs how those top contributors change over time.
X: B=Config conformance packs and rules: they bundle compliance rules for resource configuration and never analyze traffic or log fields.
C=Trusted Advisor security checks: they give account-level best-practice recommendations, not per-client error analysis of log data.
D=Composite alarms on 5XX counts: they combine alarm states into one signal, so they can say that errors are high but not which IP addresses cause them.
T: Top talkers or top error sources in log data point to Contributor Insights; alarms and compliance tools cannot rank contributors.
V: Amazon CloudWatch

@ DOP-C02 D3 T3.3 applied use-case
S: EC2 instances that fail system status checks must recover automatically with the same identity. Which feature fits?
A: A monthly AMI rebuild and relaunch of each instance
B: A CloudWatch alarm with the EC2 recover action
C: A cron job inside each instance rebooting it hourly
D: An SNS email alert to the on-call engineer's inbox
K: B
G: ## Two kinds of EC2 status checks
- **System status checks** detect problems with the underlying AWS host: loss of network connectivity or power, or host hardware and software issues. You cannot fix these from inside the instance.
- **Instance status checks** detect problems inside the guest, such as a failed boot or exhausted memory, which usually need a reboot or a configuration fix.
## The recover action
You can create a CloudWatch alarm on `StatusCheckFailed_System` with the EC2 **recover** action. When the alarm fires, EC2 moves the instance to healthy hardware and keeps its **identity**: the same instance ID, private IP addresses, Elastic IP addresses and instance metadata, and its EBS volumes stay attached. Many current instance types also support simplified automatic recovery, which is on by default; the CloudWatch alarm is the explicit, configurable option and can also notify an SNS topic.
Recovery applies to supported instance types with EBS-backed storage; instances using instance store volumes cannot be recovered this way.
W: CloudWatch alarm with the EC2 recover action: an alarm on `StatusCheckFailed_System` with the recover action moves the instance to healthy hardware automatically and keeps its identity: the same instance ID, private and Elastic IP addresses, metadata and attached EBS volumes.
X: A=Monthly AMI rebuild and relaunch: rebuilding images is a patching routine; it does not detect a host failure and produces new instances with new identities.
C=Hourly reboot cron job: a reboot runs on the same failed host and cannot fix a hardware problem, and a cron job inside an unreachable instance may not run at all.
D=SNS email alert: it only notifies a person, so recovery is manual and delayed rather than automatic.
T: A failed system status check is a host problem; the CloudWatch alarm recover action moves the instance to new hardware while preserving its ID, IPs and volumes.
V: Amazon CloudWatch, Amazon EC2
