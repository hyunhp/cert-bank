@ DOP-C02 D1 T1.4 advanced use-case
S: A team's V2 pipeline in CodePipeline deploys an ECS service and a CloudFormation stack in one Prod stage. Twice this quarter a release passed every action but pushed the checkout error alarm into ALARM about 20 minutes later, and an engineer had to rerun an older execution by hand. The team wants the Prod stage to return automatically to the last successful execution's artifacts if that alarm fires within 30 minutes after the stage succeeds, without writing or hosting any code. What should they configure?
A: An On Success condition on the Prod stage with a CloudWatchAlarm rule for the checkout alarm, a WaitTime of 30 minutes and the Rollback result
B: An Entry condition on the Prod stage with a CloudWatchAlarm rule for the checkout alarm and the Fail result, so a new release cannot enter while the alarm is active
C: An EventBridge rule on the checkout alarm's state change to ALARM that invokes a Lambda function calling RollbackStage with the last successful execution ID
D: The PARALLEL execution mode for the pipeline plus an On Failure condition with the Rollback result, so every execution can be rolled back on its own
K: A
G: ## Stage conditions in CodePipeline V2
A stage condition is a set of **rules** checked at a point in a stage's life, plus a **result** that engages when the rules fail.
- **Entry** conditions run before the stage starts; results are Fail or Skip.
- **On Failure** conditions run when the stage fails; the result is Rollback.
- **On Success** conditions run after all actions in the stage succeed; results are Rollback or Fail.
## The CloudWatchAlarm rule
The `CloudWatchAlarm` rule watches an existing alarm. Its optional `WaitTime` (minutes) keeps the rule watching for a state change before the result is applied, which is how a stage can "bake" after deployment.
## What Rollback does
A stage rollback starts a new execution of that stage with the source revisions and variables of the chosen earlier successful execution. It cannot target an execution from an older pipeline structure version, and it is not available in PARALLEL mode.
W: On Success with CloudWatchAlarm and Rollback: the condition is checked after every action in the stage has succeeded, keeps watching the checkout alarm for 30 minutes, and if the alarm goes to ALARM it rolls the stage back to the last successful execution. It is pure pipeline configuration, so there is no code to host.
X: B=Entry condition with Fail: an Entry condition only decides whether the next execution may enter the stage. It never rolls back the release that is already deployed and causing the alarm.
C=EventBridge plus Lambda: this would work, but it is exactly the custom code the team refuses to write, deploy and maintain.
D=PARALLEL mode: in PARALLEL mode stage rollback is not available and conditions with a Rollback result cannot be added, so this removes the very capability that is needed.
T: For post-deployment bake-and-rollback in CodePipeline V2, use an On Success condition with a CloudWatchAlarm rule, a WaitTime and the Rollback result.
V: AWS CodePipeline, Amazon CloudWatch

@ DOP-C02 D1 T1.1 advanced tradeoff
S: A pipeline deploys every merge to main into one shared staging environment, where a contract-test suite runs before release. Auditors now require evidence that every merged commit was deployed and tested in staging, but on busy days newer executions overtake waiting ones and some commits never reach staging. The Prod stage must keep its automatic stage rollback, and two executions must never deploy to staging at the same time. Which pipeline change meets all three requirements?
A: Change the execution mode to QUEUED, so waiting executions enter each locked stage in arrival order and none is superseded
B: Change the pipeline's execution mode to PARALLEL, so each merge gets its own independent execution that runs through staging without waiting
C: Keep SUPERSEDED mode but disable the transition into staging during business hours, and enable it each evening to release every waiting execution
D: Keep SUPERSEDED mode and add a manual approval action before staging, so an operator confirms each waiting execution before a newer one can pass
K: A
G: ## Three execution modes
- **SUPERSEDED** (default): a stage holds one execution at a time. An execution waiting between stages can be overtaken by a newer one, and the overtaken execution never continues.
- **QUEUED** (V2 only): stages are still locked one execution at a time, but waiting executions form a queue in arrival order and are never superseded.
- **PARALLEL** (V2 only): executions are independent and do not wait for each other. Stage rollback and conditions with a Rollback result are not available.
## Matching mode to requirement
"Every commit must be processed" rules out SUPERSEDED. "Never two deployments to the shared environment at once" rules out PARALLEL, which AWS recommends for feature branches with their own targets. QUEUED is the mode that keeps one-at-a-time stages and loses nothing.
W: QUEUED mode: every execution waits its turn at the staging stage and none is dropped, the stage lock keeps staging single-occupancy, and rollback stays available because the pipeline is not in PARALLEL mode.
X: B=PARALLEL mode: executions would deploy to the shared staging environment at the same time, and stage rollback for Prod is not available in PARALLEL mode.
C=Disabled transition: while a transition is disabled, the waiting execution can still be superseded by a newer one, and only the latest execution enters when it is re-enabled. Commits are still skipped.
D=Manual approval before staging: executions are superseded while they wait between stages, and an approval does not change that rule. It adds manual work without guaranteeing every commit is deployed.
T: Use QUEUED mode when every execution must run in order through shared stages; SUPERSEDED skips waiting executions and PARALLEL drops stage rollback.
V: AWS CodePipeline

@ DOP-C02 D1 T1.1 advanced use-case
S: A team keeps one GitHub repository connected to CodePipeline through AWS CodeConnections. A V2 release pipeline must start only when a release tag such as v2.4.0 is pushed, while ordinary pushes to main and to feature branches must not start it; a separate pipeline already builds every branch. The platform team rejects any solution that adds functions, webhooks or scripts that they would have to maintain. Which configuration meets these requirements?
A: A push trigger on the pipeline's source action with a Git tags filter that includes the glob pattern v* and with no branch or file path filters
B: A source action whose BranchName is set to refs/tags/v*, so the pipeline treats each matching tag as the branch it watches for new changes
C: A pull request trigger filtered on the destination branch main, combined with a CodeBuild step that stops the execution unless the commit is tagged
D: A GitHub webhook that calls a Lambda function, which checks whether the pushed ref is a tag starting with v and then calls StartPipelineExecution
K: A
G: ## Trigger filters in V2 pipelines
V2 pipelines with a CodeConnections source (GitHub, GitLab, Bitbucket) can use **triggers** instead of the single `BranchName` of the source action.
- A **push** trigger can filter on branches, file paths or **Git tags**, each with include and exclude glob patterns.
- A **pull request** trigger can filter on destination branches and file paths, for opened, updated or closed events.
When triggers are defined, the pipeline no longer starts from the action's default branch; `BranchName` only matters for manual starts.
## Example
A push trigger with tags include `v*` starts an execution for `v2.4.0` or `v3.0.0-rc1`, and ignores plain commits to `main`.
W: Tag filter on a push trigger: CodePipeline itself matches pushed tags against the glob and starts the release pipeline only for release tags, with nothing extra to host.
X: B=BranchName set to a tag ref: BranchName names one branch to watch; it is not a tag pattern, and it would not give tag-based starts.
C=Pull request trigger plus a CodeBuild check: the pipeline would still start for every pull request into main, and the "stop unless tagged" logic is a script the team has to maintain.
D=Webhook plus Lambda: this works, but it is precisely the function and webhook the platform team refuses to own.
T: In V2 pipelines, start release pipelines from Git tags with a push trigger's tag filter; no webhook or function is needed.
V: AWS CodePipeline, AWS CodeConnections

@ DOP-C02 D1 T1.4 advanced use-case
S: An order service runs on 45 EC2 instances spread evenly over three Availability Zones and is updated with CodeDeploy in-place deployments. After a bad release reached every zone at once, the team requires each release to reach one Availability Zone at a time, bake 30 minutes in the first zone and 10 minutes in each later zone, and never take more than two instances out of service in any zone, all without manual steps. Which deployment setup meets these requirements?
A: A custom deployment configuration with zonal configuration, a 600-second monitor duration, a 1,800-second first zone monitor duration and 13 healthy hosts per zone
B: CodeDeployDefault.OneAtATime with three deployment groups, one per Availability Zone, released by three pipeline stages that an on-call engineer approves after each bake period
C: A blue/green deployment with zonal configuration enabled and a 1,800-second first zone monitor duration, so each zone's replacement instances bake before traffic moves
D: The predefined CodeDeployDefault.HalfAtATime configuration with zonal configuration added in the deployment group and a 1,800-second monitor duration for every zone
K: A
G: ## Zonal deployments in CodeDeploy
A **zonal configuration** makes an EC2 in-place deployment go to one Availability Zone at a time instead of to random hosts across the Region.
- **Monitor duration**: seconds to wait after finishing a zone before starting the next one (bake time).
- **First zone monitor duration**: an optional, longer bake for the first zone only.
- **Minimum healthy hosts per zone**: a host count or fleet percentage that must stay healthy in each zone; it works together with the deployment-wide minimum healthy hosts.
## Limits worth knowing
- Only in-place deployments to EC2 support it; blue/green and on-premises instances do not.
- It is not available on predefined configurations; you must create a custom deployment configuration.
- A rollback runs on random hosts, not zone by zone.
## Working the numbers
45 instances over three zones is 15 per zone; 13 healthy hosts per zone means at most two are being updated in a zone at any time.
W: Custom zonal configuration: it deploys zone by zone, bakes 1,800 seconds after the first zone and 600 seconds after the others, and the 13-per-zone minimum keeps no more than two of a zone's 15 instances out of service. All of it runs automatically.
X: B=One deployment group per zone with approvals: it splits the fleet by hand and needs an engineer to approve each bake, which breaks the "no manual steps" rule; OneAtATime would also make each zone very slow.
C=Blue/green with zonal configuration: zonal configuration is supported only for in-place deployments to EC2 instances, not for blue/green deployments.
D=HalfAtATime with zonal settings: zonal configuration cannot be added to a predefined configuration, and half of the fleet at a time would far exceed two instances per zone.
T: CodeDeploy zone-by-zone rollouts need a custom in-place deployment configuration with zonal settings: monitor duration, first-zone monitor duration and minimum healthy hosts per zone.
V: AWS CodeDeploy, Amazon EC2

@ DOP-C02 D1 T1.4 advanced use-case
S: A payments API runs as an ECS service on Fargate behind an Application Load Balancer and is deployed today with CodeDeploy blue/green. The platform team is retiring CodeDeploy from all accounts to cut the number of deployment tools. Each release must still be checked with test traffic by an automated Lambda test before production traffic moves, and the old tasks must keep running for 20 minutes afterwards so that a rollback needs no new tasks. What should the team configure?
A: An ECS rolling update with the deployment circuit breaker and rollback turned on, plus a CloudWatch alarm that the service deployment monitors for 20 minutes
B: The ECS blue/green deployment strategy with a test traffic listener rule, a Lambda lifecycle hook at POST_TEST_TRAFFIC_SHIFT and a 20-minute bake time
C: The EXTERNAL deployment controller with a Lambda function that creates a new task set, shifts listener weights after its tests pass and deletes the old set later
D: A CodePipeline ECS standard deploy action followed by a CodeBuild test action, and an On Failure condition that rolls the stage back to the last success
K: B
G: ## Blue/green built into Amazon ECS
Amazon ECS now runs blue/green deployments itself, without CodeDeploy. The service keeps the current (blue) revision serving production while it starts the new (green) revision, then moves traffic.
- **Lifecycle stages** such as `POST_SCALE_UP`, `TEST_TRAFFIC_SHIFT`, `POST_TEST_TRAFFIC_SHIFT`, `PRODUCTION_TRAFFIC_SHIFT` and `POST_PRODUCTION_TRAFFIC_SHIFT` can carry **lifecycle hooks**: a Lambda function, or a pause hook that waits for `ContinueServiceDeployment`.
- **Test traffic**: listener rules (for example matching a test header) send test requests to green while production stays on blue.
- **Bake time**: after production traffic moves, blue and green both keep running for the configured time, so a rollback just moves traffic back to blue.
A Lambda hook must finish or return `IN_PROGRESS` within 15 minutes; each stage can last up to 24 hours.
W: ECS blue/green with a hook and bake time: the Lambda hook tests green with test traffic before production moves, and the 20-minute bake time keeps the blue tasks running so a rollback is instant, all without CodeDeploy.
X: A=Rolling update with circuit breaker: a rolling update replaces tasks in place, gives no isolated test traffic before production, and a rollback after completion needs new tasks to start.
C=EXTERNAL controller with custom code: it can reproduce blue/green, but the team would build and own its own deployment controller in Lambda, which is far more work than the built-in strategy.
D=Standard deploy action plus tests: tests run only after production already has the new version, and a stage rollback redeploys rather than switching back to tasks that are still running.
T: Amazon ECS has its own blue/green strategy with test traffic, Lambda or pause lifecycle hooks and a bake time, so CodeDeploy is no longer required for ECS blue/green.
V: Amazon ECS, AWS Lambda, Elastic Load Balancing

@ DOP-C02 D1 T1.3 advanced use-case
S: A company's CodeArtifact domain holds six repositories that all use a shared upstream repository with an external connection to npmjs. Internal packages use the @corp npm scope, and many were first published in 2021. A security review warns that if someone published a higher @corp version to the public registry, builds could pull it. The fix must cover every repository in the domain and every future @corp package without per-package changes. What should the team do?
A: Create a package group matching the @corp scope with EXTERNAL_UPSTREAM set to BLOCK, so no repository ingests those packages from public sources
B: Set Publish to ALLOW and Upstream to BLOCK on each existing @corp package in every repository, because new directly published packages get these settings by default
C: Remove the external connection from the shared upstream repository and add a second repository with the npmjs connection only for builds that need public packages
D: Reorder the upstream repositories so the internal repository is searched before the one with the external connection, letting internal versions always win resolution
K: A
G: ## Dependency substitution
If a repository can receive versions of the same package name both by direct publishing and from a public registry, an attacker can publish a higher version publicly and package managers may pick it. CodeArtifact prevents this with **package origin controls**.
## Two levels of control
- **Per package**: `Publish` and `Upstream` (ALLOW or BLOCK). The defaults follow the first version: a directly published package gets Publish ALLOW / Upstream BLOCK. Packages created before about May 2022 kept **ALLOW/ALLOW** and must be fixed by hand.
- **Per package group**: a group matches a namespace pattern across the **whole domain** and has `PUBLISH`, `EXTERNAL_UPSTREAM` and `INTERNAL_UPSTREAM` settings (ALLOW, BLOCK, ALLOW_SPECIFIC_REPOSITORIES or INHERIT).
## Which setting wins
When a package and its group disagree, **BLOCK always wins over ALLOW**. A package left at ALLOW/ALLOW therefore defers to its group.
W: Package group with EXTERNAL_UPSTREAM BLOCK: one setting covers every repository in the domain and every current or future package in the @corp namespace, and because BLOCK wins over the old ALLOW/ALLOW packages, public versions can no longer be ingested.
X: B=Per-package settings: this fixes only the packages it touches, needs work in every repository, and is exactly the per-package effort the team ruled out; the 2021 packages show defaults are not always safe.
C=Remove the external connection: public packages would no longer resolve through the normal repositories, which breaks most builds and pushes teams to a second, unprotected path.
D=Upstream order: search order decides where a version is looked up first, but package managers still choose the highest matching version, so a public higher version can still be ingested.
T: Stop dependency substitution domain-wide with a CodeArtifact package group whose EXTERNAL_UPSTREAM is BLOCK; BLOCK beats ALLOW at the package level.
V: AWS CodeArtifact

@ DOP-C02 D1 T1.2 advanced use-case
S: A library must pass unit and integration tests on three Node.js versions, each on both x86 and Arm build images, before a release is published. Today a CodePipeline stage holds six separate CodeBuild actions that duplicate configuration, and every new runtime version means editing the pipeline. The team wants one build action that runs all combinations in parallel, keeps their definitions in the buildspec and passes a single artifact to the next stage. Which approach meets these requirements?
A: A batch build whose buildspec defines a build matrix of runtime versions and images, run by a CodeBuild action with BatchEnabled and CombineArtifacts set to true
B: A batch build whose buildspec uses build fanout to split the test files over six parallel builds, run by a CodeBuild action with BatchEnabled set to true
C: A single CodeBuild project whose buildspec has six phases, one per combination, each switching the runtime with the runtime-versions setting before its tests
D: A Step Functions state machine with a Map state that starts six CodeBuild builds, called from the pipeline by a Step Functions invoke action that waits for the result
K: A
G: ## Batch builds in CodeBuild
A batch build runs several coordinated builds from one buildspec `batch` section:
- **Build graph**: builds with dependencies (`depend-on`).
- **Build list**: a list of builds that run in parallel.
- **Build matrix**: every combination of the listed environment settings (for example images and variables) as parallel builds.
- **Build fanout**: one build split into parallel shards to run a test suite faster.
## In CodePipeline
The CodeBuild action has `BatchEnabled` to run a batch from one action, and `CombineArtifacts` (only with `BatchEnabled`) to merge the batch's artifacts into one output artifact.
W: Build matrix with BatchEnabled and CombineArtifacts: the matrix generates all six runtime and image combinations in parallel from the buildspec, one pipeline action runs them, and the combined artifact feeds the next stage.
X: B=Build fanout: fanout splits one test suite across parallel shards in the same environment; it does not create different runtime and architecture combinations.
C=Six buildspec phases: a buildspec has fixed phases (install, pre_build, build, post_build), runs them in sequence on one image, and cannot switch between x86 and Arm.
D=Step Functions Map state: it can fan out builds, but it adds a state machine to build and maintain, and the build definitions leave the buildspec.
T: Use a CodeBuild batch build matrix with BatchEnabled (and CombineArtifacts) when one pipeline action must test many environment combinations in parallel.
V: AWS CodeBuild, AWS CodePipeline

@ DOP-C02 D1 T1.4 advanced use-case
S: A team builds images in a tooling account and wants a V2 pipeline there to deploy a Helm chart to a private EKS cluster in a production account. CodeDeploy already deploys the team's Lambda functions, and a manager suggests reusing it. The cluster API endpoint is private, cluster authentication uses EKS access entries, and the security team allows no long-lived credentials anywhere in the path. Which THREE steps are required? (Select THREE)
A: Add the EKS deploy action with Helm options, and set its actionRoleArn to a production account role that the pipeline can assume
B: Give the EKS action subnets and security groups in the cluster VPC, so its managed compute can reach the private API endpoint
C: Create an access entry on the cluster for the action role, with an access policy that lets it manage resources in the target namespace
D: Create a CodeDeploy application with the Amazon EKS compute platform and a deployment group that points at the cluster and the Helm release
E: Store an access key of an IAM user in the production account in Secrets Manager, and pass it to the EKS action as environment variables
F: Make the cluster API endpoint public for the CodePipeline IP ranges, because the EKS deploy action cannot run inside a customer VPC
K: A,B,C
G: ## Deploying to EKS from CodePipeline
CodeDeploy supports only three compute platforms: EC2/On-premises, AWS Lambda and Amazon ECS. There is no EKS platform. For EKS, V2 pipelines have the **EKS deploy action** (provider `EKS`).
- It deploys with **Helm** (release name, chart location, values files) or **kubectl** (manifest files), optionally into a namespace.
- It runs on CodePipeline-managed CodeBuild compute; for a private cluster you give it **subnets and security groups** in the cluster VPC.
- It supports cross-account deployments through `actionRoleArn`, a role in the target account.
## Kubernetes permissions
IAM permissions (for example `eks:DescribeCluster`) let the role find the cluster, but Kubernetes still has to authorize it. With access entries, you add the role that the action uses as an **access entry** with an access policy for the namespace.
W: A=EKS action with actionRoleArn: the pipeline assumes a temporary role in the production account, so no stored keys are needed.
B=Subnets and security groups: the managed compute is placed in the cluster VPC and can reach the private API endpoint.
C=Access entry for the action role: without it the role is authenticated by IAM but has no Kubernetes permissions, and Helm calls are rejected.
X: D=CodeDeploy with an EKS platform: no such compute platform exists; CodeDeploy deploys only to EC2/on-premises, Lambda and ECS.
E=IAM user key in Secrets Manager: a stored access key is a long-lived credential, which the security team forbids, and the action role already provides temporary credentials.
F=Public endpoint: the action can run in the cluster VPC when given subnets and security groups, so exposing the API endpoint is unnecessary and weakens security.
T: CodeDeploy has no EKS platform; use the CodePipeline EKS deploy action with a target-account action role, VPC settings for private clusters and an EKS access entry.
V: AWS CodePipeline, Amazon EKS, AWS CodeDeploy

@ DOP-C02 D1 T1.4 advanced tradeoff
S: A web application runs in an Elastic Beanstalk environment behind an Application Load Balancer. Product owners want each release to receive 10 percent of real client traffic for 15 minutes on a full set of new instances, with traffic moving back automatically if the new instances fail health checks. They do not want DNS changes or a second environment to manage. Which deployment policy should the team configure?
A: Immutable, so a full set of new instances is launched in a temporary Auto Scaling group and is terminated if health checks fail before it joins the environment
B: Traffic splitting with a 10 percent traffic split and a 15-minute evaluation time, so the new fleet serves part of the traffic before it takes all of it
C: Rolling with additional batch at a 10 percent batch size, so capacity stays full while each batch of instances is updated and health-checked in turn
D: Blue/green with a cloned environment and an environment URL swap after 15 minutes, using weighted Route 53 records to send 10 percent of users first
K: B
G: ## Elastic Beanstalk deployment policies
- **All at once / Rolling / Rolling with additional batch**: update existing or batched instances in place; old and new versions mix, and a failure leaves a partially updated environment.
- **Immutable**: launches a full set of new instances in a separate Auto Scaling group; if they fail health checks they are terminated and the old instances are untouched. All traffic moves at once.
- **Traffic splitting**: also launches a full new set, then sends a **traffic split** percentage of client traffic to it for an **evaluation time**. If the new instances stay healthy, all traffic moves and the old ones are terminated; if not, traffic moves back and the new ones are terminated.
- **Blue/green** is not a deployment policy: it is two environments and a CNAME swap.
W: Traffic splitting: it is the canary policy built into the environment, with the 10 percent split and 15-minute evaluation the product owners asked for, automatic fallback, and no DNS change or second environment.
X: A=Immutable: it gives a clean new fleet and safe failure, but it never sends a share of real traffic first; traffic moves all at once.
C=Rolling with additional batch: old and new versions serve traffic side by side on a share of instances, but the share is set by batches, there is no full new fleet and failed batches are not moved back automatically.
D=Blue/green with a URL swap: it needs a second environment and DNS changes, which are both ruled out, and DNS caching makes the traffic share imprecise.
T: Elastic Beanstalk's traffic-splitting policy gives a canary on a full new fleet with automatic fallback; immutable gives a new fleet without a traffic share.
V: AWS Elastic Beanstalk

@ DOP-C02 D2 T2.1 advanced use-case

@ DOP-C02 D6 T6.1 advanced tradeoff
S: An order service on 300 containers reads PostgreSQL credentials from Secrets Manager and caches them for 15 minutes. Compliance now requires rotation every 7 days. In a test with single-user rotation, some containers failed to authenticate until their cache expired, and the service cannot tolerate that. A: Alternating users rotation that uses the admin secret to clone the user once and then changes only the password that is not current
B: Single-user rotation every 7 days with a 4-hour rotation window at night, so password changes happen while fewer containers refresh their cache

K: A
G: ## Two Lambda rotation strategies for database secrets
- **Single user**: one user, one password. Rotation changes the password in the database and then in the secret. Between those moments, and while clients still cache the old value, connections with the old password fail. Fine for most cases and for interactive users.
- **Alternating users**: the secret covers two users (`user` and `user_clone`). The first rotation clones the user; each later rotation changes the password of the user that is **not** current. After rotation both credentials are valid, so a client with a cached value keeps working. Cloning needs a **superuser secret** supplied separately.
W: Alternating users: the password a container cached remains valid after rotation because rotation updates the other user, so no container fails during its 15-minute cache period.
X: B=Single user at night: the window between the database change and the cache refresh still exists; it is only moved to a quieter time.

D=Master user secret: running the application as the master user breaks least privilege, and managed master user rotation is still a single-user change.
T: When cached credentials must keep working through rotation, use Secrets Manager alternating-users rotation with a separate superuser secret.
V: AWS Secrets Manager, Amazon RDS

@ DOP-C02 D6 T6.1 advanced use-case
S: A platform team runs the same payments service in 14 EKS clusters in one account and adds a cluster almost every month. With IAM roles for service accounts, every new cluster needs another OIDC provider and another edit to the shared role's trust policy, which the IAM team must approve. G: ## Two ways to give pods IAM roles
- **IAM roles for service accounts (IRSA)**: each cluster has its own OIDC identity provider, and the role's trust policy names that provider. Every new cluster means a new provider and a trust policy change.
- **EKS Pod Identity**: the role trusts one service principal, `pods.eks.amazonaws.com`, once. Per cluster you install the **Pod Identity Agent** (a DaemonSet; built into EKS Auto Mode) and create an **association** between a namespace and service account and the role.

Each association is per cluster, and the role must be in the same account as the cluster (use role chaining for other accounts). Pod Identity works for pods on Linux EC2 nodes; pods on Fargate or Windows nodes still need IRSA.
W: Pod Identity: the trust policy never changes again; adding a cluster only needs the agent and an association, which the platform team controls in EKS.

C=Node instance role: every pod on those nodes would get the payments permissions, which breaks least privilege.
D=Shared association: associations are per cluster; one association does not apply to service accounts in other clusters.
T: EKS Pod Identity lets one role serve many clusters without trust policy edits; create an association per cluster, and use IRSA for Fargate pods.
V: Amazon EKS, AWS IAM
