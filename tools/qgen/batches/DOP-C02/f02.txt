@ DOP-C02 D5 T5.2 advanced definition
S: An operations engineer needs a cross-account view of patch compliance for thousands of instances and the ability to open a session or browse file systems on a noncompliant instance from the same console. Which capability fits?
A: AWS Config conformance packs and advanced queries
B: Change Manager requests and Change Calendar
C: Parameter Store hierarchies and AppConfig profiles
D: Patch Manager scan results and Fleet Manager
K: D
G: ## Two Systems Manager tools working together
- **Patch Manager** scans or installs patches on managed nodes against a patch baseline and reports each node as compliant or non-compliant, with missing patch details. Compliance data can be viewed across accounts and Regions, for example through Quick Setup patch policies and Systems Manager's multi-account views.
- **Fleet Manager** is the Systems Manager console for managing nodes. From it you can see node details, start a **Session Manager** session, browse and view files in the file system, view logs and performance counters, and manage users, all without SSH keys or open inbound ports.
## Why the combination fits
The engineer needs to find non-compliant instances among thousands, then act on one. Patch compliance answers "which ones"; Fleet Manager lets them open that node and investigate from the same console, with access controlled by IAM and logged.
W: Patch Manager scan results and Fleet Manager: Patch Manager reports patch compliance for the whole fleet, and Fleet Manager opens sessions and browses file systems on a chosen node directly in Systems Manager.
X: A=Config conformance packs and advanced queries: these bundle Config rules and query resource configuration, but they do not report OS patch state in depth or give shell or file-system access to an instance.
B=Change Manager requests and Change Calendar: Change Manager handles approval workflows for operational changes and Change Calendar blocks changes during set periods; neither reports patch compliance nor lets you browse an instance.
C=Parameter Store hierarchies and AppConfig profiles: both hold configuration values for applications; they have no patch compliance reporting and no session or file-system access to instances.
T: Use Patch Manager to find non-compliant nodes and Fleet Manager (with Session Manager) to open and inspect them from one console.

@ DOP-C02 D4 T4.3 advanced troubleshooting
S: On-call engineers receive five separate pages whenever a database slows down, because CPU, latency, error-rate, queue-depth, and 5xx alarms all fire together. The team wants a single page only when latency and error rate are both in ALARM. What should it implement?
A: Delete the four symptom alarms and page from the CPU alarm.
B: Replace the CPU alarm threshold with an anomaly detection band.
C: Raise the evaluation periods and datapoints on each metric alarm.
D: Page from a composite alarm with an AND rule over two alarms.
K: D
G: ## Alert storms and composite alarms
When one underlying problem triggers many metric alarms at once, each with its own notification, on-call engineers get a burst of pages for a single incident.
A **composite alarm** watches other alarms and evaluates a rule expression over their states, using `AND`, `OR` and `NOT`. For example:
- `ALARM("db-latency-high") AND ALARM("db-error-rate-high")`
The composite goes to `ALARM` only when the rule is true, and only the composite has the paging action.
## How the setup looks
- Keep the individual alarms (CPU, latency, errors, queue depth, 5xx) but remove their paging actions, or send them to a low-priority channel.
- Attach the pager notification only to the composite alarm.
- Optionally use the composite's actions suppressor feature to silence alarms during a known condition such as a maintenance window.
The team still sees every signal on dashboards, but gets one page when the customer-facing symptoms coincide.
W: Composite alarm with an AND rule: a rule such as `ALARM("db-latency-high") AND ALARM("db-error-rate-high")` pages once, only when both alarms are in `ALARM`, while the other alarms stay available for diagnosis without paging.
X: A=Page from the CPU alarm alone: this throws away the symptom signals that matter and pages on CPU, which is not the condition the team asked for.
B=Anomaly detection band on CPU: anomaly detection changes how one metric's threshold is set; it does not combine latency and error rate or reduce the other pages.
C=More evaluation periods: longer evaluation only delays each alarm; when the database slows down, all five alarms still fire and page separately.
T: Combine alarm states with a composite alarm to page on a meaningful combination; tuning individual alarms does not deduplicate them.
V: Amazon CloudWatch

@ DOP-C02 D4 T4.2 applied use-case
S: A company wants to query application logs by free-text keywords and visualize the results in dashboards at scale. Which service fits?
A: Amazon ElastiCache for Valkey
B: Amazon Neptune Analytics
C: Amazon OpenSearch Service
D: Amazon DocumentDB
K: C
G: ## Log analytics needs an inverted index
Searching free text across billions of log lines quickly requires a search engine that builds an **inverted index**: for each term, the list of documents that contain it. A query like `error AND payment-service` then touches only matching documents.
**Amazon OpenSearch Service** is a managed OpenSearch (and legacy Elasticsearch) cluster. It provides:
- Full-text search, filters and aggregations over JSON documents such as log events.
- **OpenSearch Dashboards** for visualizations and dashboards.
- Ingestion from sources such as Amazon Data Firehose, OpenSearch Ingestion pipelines or CloudWatch Logs subscriptions.
- An OpenSearch Serverless option when you do not want to manage cluster capacity.
## Example
Application logs flow through Firehose into an index per day; engineers search for a request ID and build a dashboard of 5xx counts by service.
W: Amazon OpenSearch Service: it is built for full-text search and aggregation of log data at scale, and ships with OpenSearch Dashboards for visualization.
X: A=Amazon ElastiCache for Valkey: an in-memory cache for key-based lookups; it does not index log text for keyword queries or provide log dashboards.
B=Amazon Neptune Analytics: a graph analytics engine for relationship queries and graph algorithms, not for keyword queries over log lines.
D=Amazon DocumentDB: a MongoDB-compatible document database for application data; it is not a log analytics platform with dashboards.
T: For keyword queries and dashboards over logs, pick a search engine (OpenSearch), not a cache, graph or document database.
V: Amazon OpenSearch Service

@ DOP-C02 D5 T5.1 applied use-case
S: A team needs to re-send last week's events to a fixed consumer after a bug. Which EventBridge feature fits?
A: Scheduled rules with a cron expression
B: Schema registry with schema discovery
C: An event bus archive with a replay
D: API destinations with a connection
K: C
G: ## EventBridge archive and replay
An **archive** stores events that arrive on an event bus. You can archive all events or only those matching an event pattern, and set a retention period (or keep them indefinitely).
A **replay** sends archived events from a chosen time window back to the same event bus. You pick which rules receive the replayed events, so only the fixed consumer processes them again. Replayed events carry a `replay-name` field, so consumers can recognize them.
## Example
A bug in the `invoice-generator` Lambda function mishandled orders from Monday to Friday. After deploying the fix, the team starts a replay of the `orders` archive for that time window, targeting only the `invoice-generator` rule, so other consumers do not see duplicates.
Replays are not instant: events are re-sent over time and the replay shows its progress and state until it completes.
W: Event bus archive with a replay: the archive keeps last week's events, and replay re-delivers that time window to selected rules, which is exactly reprocessing after a bug fix.
X: A=Scheduled rules with cron: they fire on a cron or rate schedule; they generate new trigger events and cannot resend past events.
B=Schema registry with discovery: it discovers and stores event structures for code generation; it holds no event data to re-send.
D=API destinations with a connection: they let a rule call an external HTTP endpoint with stored authorization; they are a target type, not a store of past events.
T: To reprocess past events, archive them in advance and replay a time window to chosen rules.
V: Amazon EventBridge

@ DOP-C02 D5 T5.2 applied use-case
S: A company wants automated response plans that page on-call engineers during outages, run runbooks, and record a timeline of each event. Which service fits?
A: Amazon Cognito user pools and Lambda triggers
B: AWS Storage Gateway volumes and snapshots
C: AWS Systems Manager Incident Manager
D: Amazon CloudFront distributions and functions
K: C
G: ## Response plans in Incident Manager
**AWS Systems Manager Incident Manager** manages an incident from detection to post-incident analysis. The central object is a **response plan**, which defines what happens when an incident starts:
- **Engagement**: which contacts, on-call schedules or escalation plans are paged (SMS, voice, email), with acknowledgement.
- **Runbook**: a Systems Manager Automation document that runs automatically to diagnose or mitigate.
- **Chat channel**: an Amazon Q Developer in chat applications (formerly AWS Chatbot) channel for the responders.
- **Timeline**: Incident Manager records events such as engagements, runbook steps and related alarms, and responders can add notes.
Incidents can be started by CloudWatch alarms, EventBridge events or manually. Afterwards, a **post-incident analysis** uses the timeline.
Availability note: Incident Manager stopped accepting new customers on November 7, 2025; accounts that already use it continue as before. For new accounts AWS points to Systems Manager OpsCenter and AWS Partner paging tools, but the exam still treats response plans as the detection-to-response answer.
## Example
An `API 5xx high` alarm starts the `checkout-outage` response plan: the on-call engineer is paged, a runbook collects diagnostics and restarts unhealthy tasks, and every step appears on the incident timeline.
W: Systems Manager Incident Manager: its response plans combine on-call engagement, automated runbooks and an incident timeline in one service.
X: A=Cognito user pools and Lambda triggers: they handle sign-up and sign-in for application users, with triggers that customize those flows; they do not page responders or track outages.
B=Storage Gateway volumes and snapshots: they give on-premises applications access to AWS storage and point-in-time backups; they have no incident features.
D=CloudFront distributions and functions: they deliver content from edge locations and run lightweight request code; they do not page responders or run runbooks.
T: Automated engagement, runbooks and incident timelines together describe Incident Manager response plans.
V: AWS Systems Manager
