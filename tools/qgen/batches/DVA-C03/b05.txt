@ DVA-C03 D1 T1.1 advanced troubleshooting
S: A nightly batch job running in one container loads 2 million records into a single DynamoDB table with BatchWriteItem from the AWS SDK for Python, and it already resends any UnprocessedItems. During the first minutes of each run the table throttles, and records are lost when retries give up. The table must stay in on-demand mode because other teams share it, the job touches no other AWS resource, and a longer run is acceptable. Which change needs the LEAST custom code?
A: Set the SDK client's retry mode to adaptive, so a client-side rate limiter slows requests to the table whenever throttling responses come back
B: Keep the standard retry mode and raise max attempts to 20, so each throttled BatchWriteItem call is retried many more times with backoff and jitter
C: Switch the table to provisioned capacity with auto scaling at a 70 percent target, so write capacity grows before the job reaches its peak rate
D: Wrap each BatchWriteItem call in a loop that sleeps for a random interval and doubles the sleep whenever a throttling exception is returned
K: A
G: ## SDK retry modes
The AWS SDKs offer three retry modes:
- **Standard** (the default): retries with exponential backoff and jitter, plus a **retry quota** (a token bucket). When the quota is used up, the SDK stops retrying and returns the error so the caller fails fast. It never slows the *first* attempt of a request.
- **Adaptive**: everything in standard **plus a client-side rate limiter**. It watches throttling responses and lowers the rate at which the client sends requests, and it can delay the initial request too.
- **Legacy**: older per-SDK behavior kept for backward compatibility.
## When adaptive fits
AWS recommends adaptive mode when a client targets **a single resource** (for example one DynamoDB table) and expects frequent throttling, as in batch processors, and when extra latency is acceptable. It is not a general default: a client that serves many resources would be slowed everywhere by throttling on one.
## Applying it here
One container, one table, throttling at the start, and a run that may take longer: a single configuration setting (`retry_mode = adaptive` in the config file, `AWS_RETRY_MODE`, or the client config) makes the SDK pace itself.
W: A=Adaptive retry mode: the job hits one table, throttling is expected and extra run time is fine, which is the exact case AWS documents for the client-side rate limiter, and it is a configuration setting, not code.
X: B=More standard retries: the job keeps sending new requests at full speed, retries only add load, and the standard retry quota can still run dry and fail requests fast.
C=Provisioned with auto scaling: the table must stay on demand for the other teams, and auto scaling reacts over minutes, so the first burst would still throttle.
D=Custom sleep loop: it could work, but it is hand-written backoff code that duplicates what the SDK already provides, so it is not the least custom code.
T: For one client hammering one resource with expected throttling, the SDK's adaptive retry mode adds client-side rate limiting with a config change.
V: Amazon DynamoDB, AWS SDKs

@ DVA-C03 D1 T1.1 advanced use-case
S: An order service sends events to an SQS FIFO queue that a Lambda function consumes. Events for the same order must be processed in the order sent, but orders are independent, and at peak 3,000 orders are active at once. Producers sometimes resend an event within a minute after a network timeout; each event has a unique eventId, and each resend carries a new sentAt timestamp in its body. Today every message uses MessageGroupId "orders" and throughput is far too low. Which TWO changes should the developer make? (Select TWO)
A: Set MessageGroupId to the order ID, so each order's events stay in sequence while different orders are processed by parallel Lambda invocations
B: Set MessageDeduplicationId to the eventId on every send, so a resend within the 5-minute deduplication interval is accepted but not delivered again
C: Set MessageGroupId to a new random UUID for each message, so the queue spreads every event across as many parallel invocations as it can
D: Turn on content-based deduplication on the queue, so SQS derives each message's deduplication ID from a SHA-256 hash of the message body
E: Convert the queue to a standard queue with a Lambda batch size of 10, so throughput is no longer capped and the event source mapping drops duplicates
K: A,B
G: ## Ordering and parallelism in FIFO queues
A FIFO queue keeps strict order **within a message group**. Lambda processes messages from one group in order and does not hand the next messages of that group to another invocation until the current ones are done. Different groups are processed in parallel: for FIFO event sources the number of concurrent invocations is capped by the **number of message group IDs** (or the maximum concurrency setting, whichever is lower).
With one group ID ("orders") the whole queue is a single ordered line, so only one batch is in flight at a time.
## Deduplication
FIFO queues drop a message whose **deduplication ID** matches one sent in the last **5 minutes**. The ID comes either from the producer (`MessageDeduplicationId`) or from **content-based deduplication**, which hashes the **message body** with SHA-256 (attributes are not included).
W: A=Group ID per order: ordering is only needed per order, so one group per order keeps each order's sequence and lets up to thousands of groups be processed in parallel.
B=Deduplication ID = eventId: the eventId is the same on every resend, so SQS recognizes the retry within the 5-minute window and does not deliver it twice.
X: C=Random group ID: every message becomes its own group, so events of the same order can be processed in parallel and out of sequence.
D=Content-based deduplication: each resend has a new sentAt value in the body, so its hash differs and SQS treats it as a new message.
E=Standard queue: standard queues give best-effort ordering and at-least-once delivery, and the event source mapping does not remove duplicates.
T: In FIFO queues, the message group ID sets the unit of ordering and parallelism; a stable producer-supplied deduplication ID stops resends.
V: Amazon SQS, AWS Lambda

@ DVA-C03 D1 T1.1 advanced tradeoff
S: A refund workflow calls a payment provider's non-idempotent API, then waits for a finance manager to approve refunds above $500, which can take up to three days, and then notifies the customer. The customer must be notified as soon as the manager approves. About 2,000 refunds run per day. The payment call must never run twice for one refund unless a retry is configured, and auditors want built-in execution history. Which design meets these requirements?
A: A Standard workflow that runs the payment task, then a Task state using the .waitForTaskToken pattern that resumes when the approval app returns the token
B: An asynchronous Express workflow that runs the payment task, then a Task state using .waitForTaskToken that resumes when the approval app returns the token
C: A Standard workflow that runs the payment task, then loops through a one-hour Wait state and a Choice state that checks a DynamoDB approval flag
D: A synchronous Express workflow that runs the payment task and stores a pending flag, plus a second Express workflow that the approval app starts
K: A
G: ## Standard vs Express workflows
- **Standard**: runs up to **1 year**, **exactly-once** (unless a `Retry` is defined), execution history retrievable for 90 days, supports `.sync` and `.waitForTaskToken`.
- **Express**: runs up to **5 minutes**, at-least-once when asynchronous and at-most-once when synchronous, history only through CloudWatch Logs, and **no** `.sync` or `.waitForTaskToken` integrations.
## Waiting for a person
The **callback pattern** (`.waitForTaskToken`) passes a task token to another system and pauses the execution, without polling, until that system calls `SendTaskSuccess` or `SendTaskFailure` with the token. The workflow continues the moment the approval arrives.
W: A=Standard with callback: Standard runs each task exactly once, lasts up to a year, keeps execution history, and the task token resumes the workflow the moment the manager approves.
X: B=Express with callback: Express workflows run for at most 5 minutes, use at-least-once semantics when asynchronous, and do not support the callback pattern at all.
C=Wait loop polling DynamoDB: it works, but an approval can sit up to an hour before the next check, so the customer is not notified as soon as the manager approves.
D=Two Express workflows: synchronous Express is at-most-once, but Express keeps no built-in execution history, so the audit requirement fails.
T: Long, non-idempotent, human-in-the-loop workflows belong in Standard workflows with the .waitForTaskToken callback pattern.

@ DVA-C03 D1 T1.1 advanced use-case
S: When an order item in DynamoDB changes to status SHIPPED, a company must start a Step Functions workflow with the full customer profile, which only an internal HTTPS API returns. Today a Lambda function reads the table's stream, discards about 95 percent of the records, calls the API, and starts the workflow. The team wants to remove this glue code, pay only for relevant events, and keep the profile enrichment. What should the developer build?
A: An EventBridge pipe with the table's stream as source, a filter on the new SHIPPED status, an API destination as enrichment, and the state machine as target
B: An EventBridge rule on the default event bus that matches DynamoDB item change events with status SHIPPED, with an input transformer and the state machine as target
C: A filter criteria on the Lambda event source mapping for the SHIPPED status, so the existing function runs only for shipped items before calling the API
D: An EventBridge pipe with the table's stream as source and an Express workflow as target that filters the records, calls the API, and starts the main workflow
K: A
G: ## EventBridge Pipes
A pipe connects **one source to one target** with optional steps in between:
1. **Source**: for example a DynamoDB stream, Kinesis stream, SQS queue or Amazon MQ broker.
2. **Filter** (optional): an event pattern; only matching events continue, and **you are charged only for events that match the filter**.
3. **Enrichment** (optional): a Lambda function, Step Functions Express workflow, API Gateway API or **API destination** adds data to each event.
4. **Target**: for example a Step Functions state machine, SQS, Lambda or an event bus.
## Why it replaces glue code
The stream polling, filtering, the HTTP call and the target invocation are configuration, so the custom function disappears.
W: A=Pipe with filter and API destination enrichment: the filter drops the 95 percent before billing, the API destination calls the profile API without code, and the pipe starts the state machine.
X: B=Default bus rule: DynamoDB does not publish item-level change events to the default event bus; item changes are only available through streams.
C=Event source mapping filter: it removes the irrelevant invocations, but the Lambda glue code that calls the API and starts the workflow stays, which the team wants to remove.
D=Pipe to a filtering Express workflow: every record reaches the target and is billed, and the filter and API logic move into another component instead of being removed.
T: EventBridge Pipes replaces stream-polling glue code with source, filter, enrichment and target, and bills only events that pass the filter.

@ DVA-C03 D1 T1.1 advanced use-case
S: An SNS topic fans out order events to six SQS queues. The publisher puts all data in a JSON message body and sets no message attributes, and the publisher team will not change its code. The fraud team's queue must receive only events whose body has amount greater than 10000 and country not equal to "US", without adding a Lambda function or changing the other five subscriptions. What should the developer configure?
A: On the fraud queue's subscription, set FilterPolicyScope to MessageBody with a filter policy of amount > 10000 and anything-but US for country
B: On the fraud queue's subscription, set a filter policy with the same numeric and anything-but conditions and leave FilterPolicyScope at its default value
C: On the topic, add a data protection policy that denies delivery to the fraud subscription when amount is 10000 or less or when country is US
D: Subscribe a Lambda function that parses each body and forwards matching events to the fraud queue, and remove that queue's direct subscription
K: A
G: ## Where SNS looks when it filters
Each subscription can have a **filter policy**. The subscription attribute `FilterPolicyScope` decides what the policy is matched against:
- `MessageAttributes` (the **default**): the message attributes set by the publisher.
- `MessageBody`: the JSON message body.
Filter policies support operators such as numeric ranges and `anything-but`, so business rules can be expressed without code.
## Applying it here
The publisher sends no attributes, so a policy evaluated against attributes never matches and the fraud queue would receive nothing. Setting the scope to `MessageBody` makes SNS evaluate the JSON fields `amount` and `country`. Only the fraud subscription changes; the other five keep receiving everything.
W: A=Body-scoped filter policy: SNS evaluates the conditions against the JSON body, which is where the publisher puts the data, so only matching events reach the fraud queue.
X: B=Default scope: the default scope is MessageAttributes, and the messages carry no attributes, so nothing would ever match and the queue would receive no events.
C=Data protection policy: these policies audit, mask or deny sensitive data such as PII; they are not a routing mechanism based on business values.
D=Forwarding Lambda function: it works, but the requirement forbids adding a Lambda function when a subscription filter can do the job.
T: SNS filter policies match message attributes by default; set FilterPolicyScope to MessageBody to filter on the JSON payload.

@ DVA-C03 D1 T1.2 advanced troubleshooting
S: A Lambda function consumes an SQS queue. When a downstream API is busy, the function sends the message back to the same queue with DelaySeconds=60 and an attempt counter in the body, giving up after 30 attempts. Lately such messages stop after about 16 attempts and land in the queue's dead-letter queue, and the RecursiveInvocationsDropped metric is above zero. The team wants to keep this design with the fewest changes. What should the developer do?
A: Run put-function-recursion-config with --recursive-loop Allow for the function, and keep the code's 30-attempt counter as the loop guard
B: Raise the source queue's maxReceiveCount to 40, so a message can be received enough times to reach 30 attempts before it moves to the dead-letter queue
C: Turn off X-Ray active tracing on the function, because Lambda counts loop iterations from the active tracing segments the function sends
D: Send the retries to a second SQS queue that also triggers the function, so each message alternates between two different event sources
K: A
G: ## Lambda recursive loop detection
Lambda adds tracking metadata (in the X-Ray trace header, **without needing active tracing**) to events from supported sources: **SQS, SNS, S3 and EventBridge custom buses**, plus direct Lambda-to-Lambda calls. Each time the function sends the event on with a supported SDK, the count rises.
- After about **16 invocations in one chain**, Lambda stops the next invocation and reports it (`RecursiveInvocationsDropped`, Health Dashboard, email).
- For an SQS source, the stopped invocation returns `RecursiveInvocationException` to the event source mapping, the message's receive count rises, and SQS finally moves it to the dead-letter queue.
- Loops through other services, such as DynamoDB, are not detected.
## Intentional recursion
If a design loops on purpose, set the function's recursive loop setting to `Allow` with `PutFunctionRecursionConfig` (`aws lambda put-function-recursion-config --recursive-loop Allow`). AWS advises keeping your own guard, like this attempt counter.
W: A=Allow recursive loops: the loop is intentional and bounded by the code's own counter, so allowing recursion for this function removes the 16-invocation stop without redesign.
X: B=maxReceiveCount 40: the receive count is not what stops the chain; Lambda keeps dropping each invocation after about 16, so the message just fails more times before reaching the dead-letter queue.
C=Turn off active tracing: detection uses tracing headers whether or not active tracing is on, so this changes nothing.
D=Second queue: the chain is still the same function invoked by the same original event through supported services, so Lambda still counts it and stops it.
T: Lambda stops SQS, SNS, S3 and EventBridge loops after about 16 invocations; intentional loops need --recursive-loop Allow.

@ DVA-C03 D1 T1.2 advanced use-case
S: A Java 21 Lambda function behind API Gateway spends 7 seconds initializing Spring, and p99 latency during traffic bursts breaks the SLO. The team will not pay for idle pre-initialized capacity. The init code seeds a java.util.Random once and creates a UUID used as an instance ID in log lines. The function uses 512 MB of ephemeral storage and no EFS. Which TWO actions should the developer take? (Select TWO)
A: Turn on SnapStart for published versions, and point the API Gateway integration at an alias of a published version instead of $LATEST
B: Create the seeded Random and the instance UUID in the handler or an afterRestore runtime hook instead of in init, so the values stay unique
C: Turn on SnapStart and add provisioned concurrency on the same alias, so restored snapshots are also kept warm through the burst periods
D: Turn on SnapStart for $LATEST, so every code change is snapshotted at once without publishing versions or updating the alias
E: Raise ephemeral storage to 4 GB and cache the serialized Spring context in /tmp, so later cold starts read the context from disk instead of rebuilding it
K: A,B
G: ## How SnapStart works
When you **publish a version**, Lambda runs the init phase, takes a Firecracker microVM snapshot of memory and disk, encrypts and caches it. New execution environments **resume from the snapshot** instead of initializing, often cutting cold starts to under a second. There is no idle capacity to pay for (for Java there is no extra SnapStart charge).
## Limits that matter
- Works only on **published versions** (and aliases that point to them), never on `$LATEST`.
- Not supported together with **provisioned concurrency**, EFS, or **ephemeral storage above 512 MB**.
## Uniqueness
Everything created in init is copied into every environment resumed from the same snapshot. Unique IDs, secrets and random seeds made in init are therefore **shared**. Generate them after restore: in the handler, or in an `afterRestore` runtime hook (Java uses the CRaC hooks).
W: A=SnapStart on a published version: SnapStart only applies to published versions, so API Gateway must call an alias of one; this removes most of the 7-second init with no idle capacity.
B=Unique values after restore: a seed and UUID made in init would be identical in every restored environment, so they must be generated in the handler or an afterRestore hook.
X: C=SnapStart plus provisioned concurrency: the two cannot be used on the same version, and provisioned concurrency is the idle capacity the team will not pay for.
D=SnapStart on $LATEST: SnapStart cannot be used on the unpublished $LATEST version.
E=4 GB ephemeral storage: SnapStart does not support ephemeral storage above 512 MB, and /tmp is per environment, so new environments would not have the cache anyway.
T: SnapStart needs published versions, cannot mix with provisioned concurrency or >512 MB /tmp, and requires unique values to be created after restore.
V: AWS Lambda, Amazon API Gateway

@ DVA-C03 D1 T1.2 advanced use-case
S: A Node.js Lambda function builds CSV exports of 20 to 60 MB on request, and users must start receiving bytes within one second. Today the function writes each file to S3 and returns a presigned URL, but security now forbids storing exports at rest anywhere. The function is not attached to a VPC, and clients can call any HTTPS endpoint with IAM-signed requests. What should the developer do?
A: Create a function URL with AWS_IAM auth and the RESPONSE_STREAM invoke mode, and write CSV rows to the response stream as they are generated
B: Create a function URL with AWS_IAM auth and the BUFFERED invoke mode, and gzip the CSV so that the full response fits inside the payload limit
C: Put a REST API in front of the function with a non-proxy Lambda integration and binary media types, so the CSV is returned within its 10 MB limit
D: Invoke the function asynchronously with an on-success destination in SQS, so clients read the finished CSV from the invocation record in the queue
K: A
G: ## Buffered vs streamed responses
- A **buffered** synchronous invocation returns the response only after the handler finishes, and it is capped at **6 MB**.
- **Response streaming** sends bytes as soon as the function writes them (better time to first byte) and allows up to **200 MB** per response. The first 6 MB stream uncapped; the rest at up to 2 MBps.
## How to stream
- A **function URL** with invoke mode `RESPONSE_STREAM`, or the `InvokeWithResponseStream` API.
- Node.js managed runtimes support it natively (other languages use a custom runtime or the Lambda Web Adapter).
- Function URLs do not stream inside a VPC; this function is not in one.
W: A=Streaming function URL: streaming allows up to 200 MB, delivers the first rows immediately, IAM auth matches the clients, and nothing is stored at rest.
X: B=Buffered with gzip: the client gets nothing until the whole file is built, and a 60 MB CSV is not guaranteed to compress under the 6 MB buffered limit.
C=REST API non-proxy integration: REST API payloads are capped at 10 MB, far below the 60 MB exports, and the response is still buffered.
D=Async with SQS destination: asynchronous invocations are limited to 1 MB, the record would sit at rest in a queue, and users would wait for the whole job.
T: For large or slow responses, Lambda response streaming (RESPONSE_STREAM function URL) returns up to 200 MB with a fast first byte.

@ DVA-C03 D1 T1.2 advanced troubleshooting
S: An S3 upload triggers an image-processing Lambda function asynchronously. On-call engineers need, for every event that finally fails, the original event plus the error type and message, delivered to an SQS standard queue within about 10 minutes of the upload. Today the function has a dead-letter queue with default retry settings; failed events sometimes arrive hours later and contain only the event. What should the developer configure?
A: Set MaximumRetryAttempts to 1 and MaximumEventAgeInSeconds to 600, and add an on-failure destination that targets the SQS queue
B: Set MaximumRetryAttempts to 1 and MaximumEventAgeInSeconds to 600, and keep the dead-letter queue as the place where failed events are collected
C: Keep the default retry settings, and add an on-failure destination that sends invocation records with the error details to the SQS queue
D: Set MaximumRetryAttempts to 0, and add an on-failure destination that is an SQS FIFO queue, so failed events are kept in upload order
K: A
G: ## Async invocation error handling
Lambda queues asynchronous events and retries them:
- **Function errors**: 2 retries by default (1 minute, then 2 minutes apart). `MaximumRetryAttempts` can be 0 to 2.
- **Throttles and system errors**: the event goes back to the queue and is retried for up to **6 hours** by default. `MaximumEventAgeInSeconds` (60 to 21,600) caps that age.
## Where failures go
- A **dead-letter queue** receives only the **event content**, without response details.
- An **on-failure destination** receives an **invocation record**: the request payload plus context and the **response payload**, which holds the error type and message. Destinations can be SQS, SNS, S3, Lambda or EventBridge, but **not FIFO** queues or topics.
W: A=Bounded retries plus on-failure destination: one retry and a 600-second age limit end processing within about 10 minutes, and the invocation record carries the event plus the error type and message.
X: B=Keep the dead-letter queue: the time limit is met, but a dead-letter queue gets only the event content, never the error details.
C=Default retry settings: throttled events can be retried for up to 6 hours, which explains the late arrivals and breaks the 10-minute target.
D=FIFO destination: SQS FIFO queues are not supported as destinations, so Lambda would report DestinationDeliveryFailures instead of delivering.
T: Use on-failure destinations (not DLQs) when you need error details, and bound async retries with MaximumRetryAttempts and MaximumEventAgeInSeconds.

X: C=orderId as a dimension: every order would become its own custom metric, a high-cardinality design that multiplies cost and is useless for alarms.
D=PutMetricData per order: these are synchronous API calls in the request path, which the requirement excludes, at 2,000 calls per second.
E=Metric filter with orderId dimension: an orderId dimension creates one metric per order, and parsing plain text lines is weaker than structured EMF.
T: Use EMF for custom metrics from Lambda; keep high-cardinality values like IDs as properties, never as dimensions.

@ DVA-C03 D4 T4.2 advanced use-case
S: A high-traffic API traced with X-Ray uses the default sampling rule. For a month-long investigation the team must trace every POST /checkout request (about 20 per second across 40 instances) and keep other paths near 1 percent, without redeploying the services, which already read sampling rules from the X-Ray service. Missing even a few checkout traces at peak seconds is not acceptable. What should the developer configure?
A: Add a sampling rule with priority 1 matching POST and /checkout at a fixed rate of 100 percent, and lower the default rule's rate to 1 percent
B: Add a local sampling rules JSON file to each service with a /checkout rule at rate 1.0, and set the file's default rule rate to 0.01
C: Add a sampling rule that matches POST and /checkout with a reservoir of 20 and a fixed rate of 0, and lower the default rule's rate to 1 percent
D: Add a sampling rule with priority 100 for POST /checkout at 100 percent, and a rule with priority 10 that matches every path at 1 percent
K: A
G: ## How X-Ray sampling rules work
Each rule has match criteria (service, HTTP method, URL path, ...) and:
- **Priority** (1 to 9999): rules are evaluated in **ascending** order; the first match decides. The **default rule** applies to requests that match no other rule.
- **Reservoir**: a fixed number of matching requests per second traced first, shared by all instances using the rule.
- **Rate**: the percentage of further matching requests traced after the reservoir is used.
## Central vs local rules
Rules defined in the X-Ray service are fetched by the SDKs, so changes need **no redeploy**, and the service splits reservoirs across instances. Local JSON rules require a redeploy and each instance samples on its own.
W: A=Priority 1 checkout rule at 100 percent: checkout requests match first and are always traced, and every other path falls to the default rule at 1 percent, all without redeploying.
X: B=Local rules file: changing local sampling rules requires redeploying every service.
C=Reservoir of 20 with rate 0: the reservoir is a per-second budget across all instances, so any second above 20 checkout requests leaves some untraced.
D=Catch-all at priority 10: the lower number is evaluated first, so checkout requests match the 1 percent catch-all and the 100 percent rule never applies.
T: X-Ray applies the first matching sampling rule in ascending priority; central rules change sampling without redeploying.
V: AWS X-Ray

@ DVA-C03 D4 T4.2 advanced troubleshooting
S: A CloudWatch alarm watches the Errors metric (Sum, 1-minute periods) of a Lambda function that runs only when a partner uploads files, a few times a day. The alarm must go to ALARM when errors occur in 2 of 3 consecutive minutes, but it spends most of the day in INSUFFICIENT_DATA, and on-call has started to ignore it. Which change makes the alarm state meaningful without missing real errors?
A: Treat missing data as notBreaching, so idle minutes count as good while 2 erroring minutes out of 3 still trigger ALARM
B: Treat missing data as breaching, so minutes without invocations count against the threshold and the alarm leaves INSUFFICIENT_DATA
C: Treat missing data as ignore, so the alarm keeps its current state through the minutes in which the function receives no invocations
D: Change the period to 1 day with 1 of 1 datapoints to alarm, so the alarm always has at least one data point from the daily uploads
K: A
G: ## Missing data in alarms
Lambda publishes `Errors` only for periods with invocations, so an idle function produces **no data points**. Each alarm chooses how to treat missing points:
- `missing` (**default**): if all points in the evaluation range are missing, the alarm goes to `INSUFFICIENT_DATA`.
- `notBreaching`: missing points count as **good**.
- `breaching`: missing points count as **bad**.
- `ignore`: the alarm keeps its **current state**.
AWS's guidance: for metrics that report only when something happens (like DynamoDB `ThrottledRequests` or sparse error counts), treat missing data as `notBreaching`.
W: A=notBreaching: idle minutes count as healthy so the alarm sits in OK, and two minutes with errors out of three still trigger ALARM.
X: B=breaching: every idle stretch would put the alarm into ALARM, creating constant false alarms.
C=ignore: the alarm keeps whatever state it had, so it can stay in INSUFFICIENT_DATA, or stay in ALARM long after an incident ends.
D=Daily period: errors are only evaluated once per day, so a burst of errors is noticed hours late, and the alarm no longer checks 2 of 3 minutes.
T: For sparse, event-driven metrics, treat missing alarm data as notBreaching to avoid INSUFFICIENT_DATA noise.

@ DVA-C03 D4 T4.3 advanced tradeoff
S: A Lambda function configured with 1,024 MB resizes images using a library that spreads work across all available CPU cores; each invocation takes about 8 seconds and memory use peaks at 400 MB. The function runs about 50,000 times a day with steady traffic and short init. The team wants clearly lower latency without paying noticeably more per invocation, and without code changes. Which approach is BEST?
A: Test the function at several memory sizes above 1,769 MB, because CPU grows with memory and shorter runs can keep cost per invocation flat
B: Lower memory to 512 MB, because the function peaks at 400 MB, which cuts the price per millisecond while the duration of each invocation stays the same
C: Keep 1,024 MB and add provisioned concurrency, because initialization accounts for most of the 8 seconds that each resize invocation takes
D: Keep 1,024 MB and raise ephemeral storage to 10 GB, so the library has more room for temporary files and each resize completes faster
K: A
G: ## Memory is also the CPU dial
Lambda allocates **CPU in proportion to memory**: at **1,769 MB** a function has the equivalent of **one vCPU**, and more memory brings more CPU power. A CPU-bound, multi-threaded workload therefore gets faster as memory grows.
## Cost math
Lambda bills **GB-seconds** (memory x duration). Doubling memory doubles the price per millisecond, but if the duration halves, the cost per invocation stays about the same while latency drops. Testing several sizes (for example with AWS Lambda Power Tuning) finds the point where cost and latency balance.
## Why not cut memory
At 1,024 MB the function already has less than one vCPU; 512 MB halves its CPU, so a CPU-bound job takes about twice as long.
W: A=Test larger memory sizes: more memory means more vCPUs for the multi-threaded library, so duration falls roughly as fast as the price per millisecond rises.
X: B=512 MB: CPU shrinks with memory, so the CPU-bound resize takes about twice as long and latency gets worse.
C=Provisioned concurrency: the 8 seconds are compute time in the handler, not initialization, and provisioned concurrency adds a standing cost.
D=More ephemeral storage: /tmp size does not add CPU, so a CPU-bound resize gets no faster.
T: Lambda CPU scales with memory (1 vCPU at 1,769 MB); CPU-bound functions often get faster at similar cost with more memory.
V: AWS Lambda

@ DVA-C03 D4 T4.3 advanced use-case
S: A REST API's GET /products method returns results that depend on the category and currency query string parameters and that change at most every 10 minutes. The team turned on stage caching to cut backend load, but users now receive products from the wrong category. Internal admin tools must be able to force a refresh of one entry, and public clients must not. Which THREE settings should the developer configure? (Select THREE)
A: Add the category and currency query string parameters as cache key parameters on the GET /products method
B: Set the cache TTL of the GET /products method to 600 seconds, so cached responses are reused for at most 10 minutes
C: Require authorization for cache invalidation, and grant execute-api:InvalidateCache only in the admin tools' IAM policies
D: Set the cache TTL of the GET /products method to 0 seconds, so that the cache can never return an outdated product list
E: Add the Authorization header as a cache key parameter, so that each user gets a separate cached product list from the stage
F: Leave cache invalidation authorization turned off, so admin tools can send Cache-Control: max-age=0 without signing requests
K: A,B,C
G: ## API Gateway response caching
- **Cache keys**: by default only the resource path is in the key. Add the method or integration **parameters that change the response** (query strings, headers, path parts); otherwise one cached response is returned for all values.
- **TTL**: 300 seconds by default, 0 to 3,600 allowed; **0 disables caching**.
- **Invalidating one entry**: a client sends `Cache-Control: max-age=0`. If **Require authorization** is on, only callers allowed `execute-api:InvalidateCache` may do it; others can be rejected with 403 or have the header ignored. If it is off, **any client** can flush entries, which can raise backend load.
W: A=Query strings as cache keys: category and currency now produce separate cache entries, so users get the right product list.
B=600-second TTL: the data changes at most every 10 minutes, so a 600-second TTL keeps responses within that window while cutting backend calls.
C=Authorized invalidation: only the admin tools hold execute-api:InvalidateCache, so they can refresh an entry and public clients cannot.
X: D=TTL 0: a TTL of zero turns caching off for the method, so backend load goes back up.
E=Authorization header as a key: the category and currency still are not in the key, and per-user entries destroy the hit rate.
F=Unauthorized invalidation: any public client could also send Cache-Control: max-age=0 and bypass the cache.
T: Put every response-changing parameter in the API Gateway cache key, set the TTL to the staleness budget, and require authorization for invalidation.
V: Amazon API Gateway

@ DVA-C03 D4 T4.3 advanced troubleshooting
S: A Lambda function behind API Gateway queries an RDS for MySQL instance and opens its connection outside the handler. During flash sales concurrency reaches 800, and the database rejects connections with "Too many connections" while its CPU stays near 30 percent. The DBA will not raise max_connections because connection memory is near the instance limit, Lambda concurrency must not be reduced, and credentials must come from Secrets Manager. What should the developer do?
A: Create an RDS Proxy for the instance that uses the Secrets Manager secret, and point the function's connection at the proxy endpoint
B: Raise max_connections to 1,000 in a custom DB parameter group, so the database accepts one connection from each concurrent environment
C: Set reserved concurrency on the function to 150, so no more than 150 environments ever hold open connections to the database at once
D: Open and close a database connection inside the handler on every invocation, so idle environments do not keep connections between requests
K: A
G: ## Why Lambda exhausts database connections
Each Lambda execution environment keeps its own connection. At 800 concurrent environments the database sees up to 800 connections, regardless of CPU load. Each connection also uses database memory.
## RDS Proxy
RDS Proxy keeps a **pool of database connections** and shares them among many client connections:
- It queues or throttles client connections that cannot be served right away instead of letting the database fail.
- It reads database credentials from **Secrets Manager** (or uses IAM database authentication), and clients can authenticate with IAM.
- It also speeds up failover by keeping client connections open.
W: A=RDS Proxy: hundreds of Lambda connections share a small pool of database connections, so the database stays under its limit without fewer environments, using the existing secret.
X: B=Raise max_connections: the DBA has ruled it out because connection memory is already near the instance's limit.
C=Reserved concurrency 150: it caps the function's concurrency, which the requirement forbids, and requests beyond it would be throttled.
D=Connect per invocation: opening and closing connections on each request adds latency and churn, and 800 concurrent invocations still need 800 connections at peak.
T: Use RDS Proxy to pool database connections for highly concurrent Lambda functions.
V: Amazon RDS, AWS Lambda, AWS Secrets Manager
