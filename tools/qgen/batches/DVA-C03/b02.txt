@ DVA-C03 D1 T1.1 applied use-case
S: A developer uses Kiro to build a new order-export feature for a serverless application. The team lead wants the AI agent's work to be traceable to agreed acceptance criteria, and wants the team to be able to review the plan before any code is written. Which approach meets these requirements?
A: Create a spec for the feature, review and edit its requirements and design documents, then have the agent work through the generated task list one task at a time
B: Describe the whole feature in a single chat prompt, let the agent generate every file at once, and then ask it to write the requirements from the finished code
C: Skip the agent, write the handler by hand with inline code completion, and accept each suggestion whenever it compiles without errors in the local build
D: Add the acceptance criteria as comments at the top of the handler file and let the agent edit the file freely until all of the comments are addressed
K: A
G: ## Spec-driven development in Kiro
Kiro is an AI-powered development environment from AWS built around **spec-driven development**: before the agent writes code, the feature is described in reviewable documents that live in the repository.
A spec for one feature has three parts, stored as markdown files under `.kiro/specs/<feature>/`:
- `requirements.md`: user stories with acceptance criteria, written in a structured form such as "WHEN a user exports orders THE SYSTEM SHALL ...".
- `design.md`: the technical design, for example components, data models, interfaces and error handling.
- `tasks.md`: a checklist of discrete implementation tasks, each linked back to the requirements it satisfies.
## Why this helps a team
The plan is visible and editable before any code exists, so a reviewer can correct a misunderstanding in two lines of text instead of in two hundred lines of code. Each task is small and points at specific requirements, so every change can be checked against the criteria it claims to meet.
W: Spec, review, then tasks: the requirements and design are reviewed and corrected before implementation starts, and each executed task traces back to specific acceptance criteria, which is exactly the traceability and up-front review the lead asked for.
X: B=Single prompt, requirements written afterward: requirements derived from finished code describe what was built, not what was agreed, so there is no review before coding and no real traceability.
C=Code completion only: inline completion helps type code faster, but it produces no plan to review and does not connect any line of code to an acceptance criterion.
D=Criteria as comments in one file: comments are not a reviewed design or a task plan, and an agent editing freely gives the team nothing to approve before code changes start.
T: Kiro specs (requirements, design, tasks) make the plan reviewable before coding and keep each implementation task traceable to acceptance criteria.
V: Kiro

@ DVA-C03 D1 T1.1 applied comparison
S: A team uses Kiro on a Node.js project. Every developer keeps retyping the same instructions into agent chats: use AWS SDK for JavaScript v3 clients, write structured JSON logs, and never hardcode Regions or account IDs. The team wants the agent to follow these rules in every session for every developer. What should the team do?
A: Create an agent hook that runs whenever a file is saved and asks the agent to rewrite the saved file so that it follows the team's SDK, logging and Region conventions
B: Write the conventions in markdown steering files in the project's .kiro/steering folder and commit them to the repository so that every developer's agent loads them
C: Add the conventions as an extra task at the end of every spec's tasks.md file so that the agent applies them after the rest of the feature has been implemented
D: Rely on the agent to infer the conventions from existing code, because AI coding agents learn each repository's standards permanently after the first session
K: B
G: ## Persistent project context: steering files
An AI coding agent starts each session knowing only what is in its context. Repeating standards in every prompt is error-prone, and different developers phrase them differently.
Kiro solves this with **steering files**: markdown documents in `.kiro/steering/` that describe the product, the technology stack, project structure and coding standards. The agent includes them as context, so the rules apply without being retyped.
- Because they are files in the repository, they are versioned and reviewed like code, and every developer who clones the repo gets the same guidance.
- Typical content: "Use `@aws-sdk/client-*` v3 clients", "Log JSON with a `requestId` field", "Read the Region from the environment".
## Steering versus hooks versus specs
- **Steering** = standing knowledge the agent always considers.
- **Agent hooks** = actions that run when an event happens, such as saving a file.
- **Specs** = the plan for one feature.
W: Steering files in .kiro/steering: they give the agent persistent, shared project knowledge in every session, and committing them means every developer's agent follows the same conventions without retyping them.
X: A=Hook that rewrites files on save: a hook triggers an action after an event; it does not give the agent the rules while it writes code, and rewriting every saved file adds churn and surprises instead of guiding generation up front.
C=Extra task in every spec: conventions would apply only to work done through that spec, only at the end, and they would have to be copied into each new spec by hand.
D=Agent infers conventions from code: inference from existing code is not a reliable or shared mechanism; nothing guarantees that every developer's agent picks up the same rules, while committed steering files supply them explicitly and are versioned with the code.
T: Put standing coding standards and project knowledge in committed Kiro steering files; use hooks for event-driven actions and specs for feature plans.
V: Kiro

@ DVA-C03 D1 T1.1 applied use-case
S: A developer wants an AI agent in Kiro to update the matching unit test file automatically whenever a TypeScript source file under src/handlers is saved, so that tests are not forgotten during fast iteration. Which Kiro feature should the developer configure?
A: A steering file that tells the agent unit tests are mandatory, so the agent writes tests whenever it next generates a new handler from a chat prompt
B: A spec whose tasks.md lists a test task for each handler, so the agent writes all of the tests together when the final implementation task is complete
C: An agent hook that triggers on file save events for files that match src/handlers and instructs the agent to update the corresponding unit tests
D: Inline code completion in the test files, so that suggestions propose updated test code whenever the developer opens the matching test file in the editor
K: C
G: ## Event-driven automation with agent hooks
Kiro **agent hooks** connect an IDE event to an agent action. A hook defines:
- **When**: an event such as a file being saved, created or deleted, optionally limited to a path pattern such as `src/handlers/**/*.ts`.
- **What**: the instructions the agent runs when the event fires, for example "update the unit tests that cover the changed handler".
Hooks automate repetitive follow-up work (tests, documentation, translation files, lint fixes) so it happens every time, not only when someone remembers.
## Compared with other Kiro features
- Steering files give the agent standing context, but they do not cause anything to run when a file is saved.
- Specs plan a feature as tasks; they run when you execute the tasks, not on every save.
W: Agent hook on file save: the hook fires on each save of a matching handler file and tells the agent to update the corresponding tests, which is the automatic, event-driven behavior the developer wants.
X: A=Steering file: steering adds guidance to the agent's context while it works on a request, but nothing is triggered when the developer saves a file they edited by hand.
B=Spec test tasks: tests would be written only when the spec's tasks are executed, not each time a handler is saved during fast iteration.
D=Code completion in test files: completion only suggests code while the developer types in a file; it does not react to saves of other files or update tests on its own.
T: Use Kiro agent hooks to run an agent action automatically on IDE events such as saving files that match a pattern.
V: Kiro

@ DVA-C03 D1 T1.1 advanced tradeoff
S: A team now generates most new Lambda function code with an AI coding agent. The generated pull requests usually pass unit tests, so some developers want to merge them without further checks. The security team is worried about injection flaws, leaked secrets and vulnerable dependencies. Which practices should the team adopt? (Select TWO)
A: Require a human reviewer to approve each AI-generated pull request against the same standards as hand-written code before it can be merged
B: Merge AI-generated pull requests automatically when unit tests pass, because the agent was configured with the team's coding standards
C: Ask the same AI agent to confirm that its own pull request is secure, and merge the pull request when the agent reports no security issues
D: Add static code analysis, secret detection and dependency vulnerability scanning to the CI pipeline as checks that must pass before merge
E: Exclude AI-generated files from code scanning so that the pipeline does not produce duplicate findings for code the agent already reviewed
K: A,D
G: ## Treat generated code as untrusted input
AI coding tools produce plausible code quickly, but plausible is not the same as correct or safe. Generated code can contain:
- injection flaws, such as SQL or shell commands built by string concatenation;
- hardcoded credentials or example secrets copied into source;
- outdated or vulnerable dependency versions, or package names that do not exist;
- IAM policies that are far broader than needed.
Passing unit tests only shows the code does what the tests check; tests written by the same agent often miss the cases a reviewer or attacker would try.
## Two layers that work together
- **Human review**: a developer who understands the system reads the diff and owns the decision to merge.
- **Automated gates**: static analysis (SAST), secret scanning and software composition analysis run on every pull request and block the merge on findings. They are consistent and do not get tired.
W: A=Human review before merge: a person accountable for the code checks logic, security and design with the same bar as any other change, which catches issues tests and the agent miss.
D=Required scanning in CI: static analysis, secret detection and dependency scanning find injection patterns, leaked keys and vulnerable libraries automatically on every pull request, and a required check stops the merge.
X: B=Auto-merge on green tests: tests do not measure security, and steering the agent with standards does not guarantee that each output follows them.
C=Agent verifies itself: asking the generator to grade its own work is not an independent check; it tends to repeat the same blind spots that produced the issue.
E=Exclude generated code from scanning: this removes scanning from exactly the code the security team is worried about; generated code needs the same or more scrutiny.
T: Never merge AI-generated code blindly: combine human review with required automated security scanning in the pipeline.
V: Kiro, AWS CodeBuild

@ DVA-C03 D1 T1.1 applied troubleshooting
S: An AI assistant generated a Python data-processing module that imports a package named boto3-s3-fastsync. The developer has never heard of it, the package is not in the company's AWS CodeArtifact repository, and a quick search finds a recently published package with that name on the public index. What should the developer do?
A: Install the package from the public index, because AI assistants are trained on real projects and only suggest packages that already have an established user community
B: Add the package to requirements.txt without pinning a version, so that the build always picks up the latest release with any security fixes that the publisher adds
C: Ask the assistant to regenerate the module until it suggests a different package, and accept the first suggestion whose import statement resolves without errors
D: Treat the import as unverified, confirm the dependency is really needed and trusted, or rewrite the code with boto3 and approved packages from CodeArtifact
K: D
G: ## Hallucinated and look-alike dependencies
AI code generators sometimes invent package names that sound right, such as a library that "obviously" should exist. Attackers watch for these names and publish packages under them, so that anyone who installs the suggestion runs the attacker's code. The same risk exists for misspellings of popular packages (typosquatting).
## Safe handling
- Check that the dependency is necessary: often the standard SDK already does the job (`boto3` has S3 transfer and multipart support).
- Verify the publisher, project history and source before adopting anything new.
- Pull packages through a controlled repository such as AWS CodeArtifact, with an upstream connection to the public index and package origin controls, so new external packages need a deliberate decision.
- Pin versions and scan dependencies in the pipeline.
W: Verify or replace the dependency: an unknown, newly published package suggested by an AI tool may be a hallucination that someone registered, so the developer confirms it is needed and trustworthy, or uses boto3 and approved packages from CodeArtifact instead.
X: A=Trust the assistant's suggestion: generators can produce package names that never existed in their training data, and a new public package with that name is a warning sign, not proof of a community.
B=Unpinned dependency: leaving the version open lets any future release, including a malicious one, flow into the build without review.
C=Regenerate until an import resolves: an import that resolves only proves a package with that name is installed; it says nothing about whether the package is safe or needed.
T: Verify every AI-suggested dependency before installing it; prefer the SDK and approved packages from a controlled repository such as CodeArtifact.
V: AWS CodeArtifact

@ DVA-C03 D1 T1.1 advanced use-case
S: An AI coding agent generated the IAM policy for a new Lambda function that calls one Amazon Bedrock model with the Converse API and writes results to a single DynamoDB table. The policy allows bedrock:* and dynamodb:* on Resource "*". The pull request is waiting for review. Which actions should the developer take before approving it? (Select TWO)
A: Accept the policy as generated, because the agent read the function code and therefore granted only the permissions that the function needs to run
B: Replace the wildcards with the specific Bedrock invoke action and DynamoDB write actions, scoped to the model ARN and the table ARN that the function uses
C: Run IAM Access Analyzer policy validation, or a custom policy check, on the policy in the pipeline so that overly broad permissions are flagged before deployment
D: Keep the wildcards but attach the policy to a separate role that is used only in production, so that developers cannot misuse the broad permissions in test
E: Move the policy into a service control policy for the account, because service control policies grant permissions to every Lambda function in the account
K: B,C
G: ## Least privilege for generated policies
AI tools often produce policies that "just work" by using wildcards. `bedrock:*` would let the function create and delete Bedrock resources, and `dynamodb:*` on `*` would let it drop any table in the account.
A least-privilege version for this function lists only what the code calls:
- `bedrock:InvokeModel` (the permission the Converse API requires) on the model or inference profile ARN, for example `arn:aws:bedrock:us-east-1::foundation-model/amazon.nova-lite-v1:0`;
- `dynamodb:PutItem` (and `UpdateItem` if used) on `arn:aws:dynamodb:us-east-1:111122223333:table/Results`.
## Checking policies automatically
IAM Access Analyzer can validate a policy and return security warnings, for example for overly permissive actions, and its custom policy checks (such as checking that a policy does not grant listed sensitive actions) can run in a CI/CD pipeline and fail the build.
W: B=Scope actions and resources: listing the exact invoke and write actions on the model ARN and table ARN removes everything the function does not use, so a bug or compromise cannot reach other resources.
C=Access Analyzer validation in the pipeline: automated validation and custom policy checks flag broad grants on this and every future generated policy before it is deployed.
X: A=Trust the agent's policy: reading the code did not stop it from using wildcards; generated IAM policies need the same least-privilege review as hand-written ones.
D=Broad policy only in production: production is where broad permissions do the most damage; moving the role does not reduce what the function can do.
E=Use an SCP instead: service control policies never grant permissions; they only set the maximum that identity policies in the account can allow.
T: Review AI-generated IAM policies for least privilege and validate them automatically with IAM Access Analyzer before deployment.
V: AWS IAM, IAM Access Analyzer, Amazon Bedrock, Amazon DynamoDB

S: An AI assistant suggests refactoring a 600-line Lambda handler into several smaller modules and replacing nested loops with a different algorithm. The handler has few tests and processes payments in production. How should the developer apply the suggestion?
A: Apply the whole refactoring in one commit, because the assistant guarantees that its refactorings preserve the observable behavior of the original handler
B: First add tests that capture the handler's current behavior, then apply the refactoring in small steps and run the tests after each step before deployment

C=Reject AI refactoring outright: there is no such rule; the suggestion can be valuable if it is verified the same way as any other change.

@ DVA-C03 D1 T1.1 applied troubleshooting
S: A developer accepts an AI code completion in a new Lambda function that runs on the Node.js 22.x runtime. The suggested code uses const AWS = require('aws-sdk') and new AWS.S3(). The function is deployed without bundling any dependencies, and every invocation fails with an error that the module aws-sdk cannot be found. What is the cause and fix?
A: The function's execution role is missing s3:GetObject; add the permission so that the runtime can load the SDK module from the S3 bucket that stores Lambda layers
B: The Node.js 22.x runtime loads modules only through ES module import syntax; rename the file to index.mjs and keep the same aws-sdk calls in the code
C: The suggestion uses the AWS SDK for JavaScript v2, which supported Node.js runtimes do not include; rewrite it with the v3 S3Client from @aws-sdk/client-s3
D: The aws-sdk package is installed only in the us-east-1 runtime image; deploy the function to that Region or attach the public SDK layer for your Region

G: ## Generated code can be outdated
Code completion models learn from large amounts of existing code, and much of it predates current SDK versions. A suggestion can be syntactically fine and still target an API that is deprecated or not available in your runtime.
## The AWS SDK for JavaScript on Lambda
- The v2 SDK (`require('aws-sdk')`, `new AWS.S3()`) has reached end of support.
- All supported Lambda Node.js runtimes include a version of the **AWS SDK for JavaScript v3**, which is modular: `import { S3Client, GetObjectCommand } from '@aws-sdk/client-s3'` and `await client.send(new GetObjectCommand({...}))`.

X: A=Missing S3 permission: IAM permissions affect API calls at run time; they have nothing to do with resolving a module at import time, and the SDK is not loaded from S3.
B=Switch to ES module syntax: module syntax does not create a package that is not installed; an import of aws-sdk would fail the same way.
D=Region-specific runtime image: the runtime contents do not differ in this way between Regions, and there is no public layer that makes this an expected fix.
T: Check AI code suggestions against current SDKs and runtimes; Lambda Node.js runtimes include the AWS SDK for JavaScript v3, not v2.

@ DVA-C03 D1 T1.1 applied use-case
S: A developer calls the Amazon Bedrock Runtime Converse API from a Python application. Responses must be at most 300 tokens and fairly deterministic, and the developer also needs to set the model's top_k parameter, which is specific to the chosen model. How should the developer pass these settings?
A: Put maxTokens and temperature in inferenceConfig, and pass top_k in additionalModelRequestFields because Converse has no common field for it
B: Put maxTokens, temperature and top_k together in inferenceConfig, because Converse translates every parameter name into each model's native format
C: Put all three settings in the system prompt as text instructions, because Converse does not accept inference parameters as API fields in a request
D: Switch to InvokeModel for every request, because Converse cannot pass any parameter that is specific to a model and rejects such requests outright
K: A
G: ## Inference parameters in the Converse API
The Converse API uses one request format for all models that support it. Inference parameters that most models share are fields of `inferenceConfig`:
- `maxTokens`: the maximum number of tokens to generate;
- `temperature`: randomness (lower values give more deterministic output);
- `topP` and `stopSequences`.
Parameters that only some models support, such as `top_k` for some models, go in `additionalModelRequestFields` as a JSON object, which Bedrock passes to the model.
```
client.converse(modelId=model_id, messages=msgs,
    inferenceConfig={"maxTokens": 300, "temperature": 0.2},
    additionalModelRequestFields={"top_k": 50})
```
Model-specific fields in the response come back in `additionalModelResponseFields`.
W: inferenceConfig plus additionalModelRequestFields: the common limits go in inferenceConfig, and the model-specific top_k goes in additionalModelRequestFields, so one Converse request carries all three settings.
X: B=Everything in inferenceConfig: inferenceConfig accepts only its defined fields (maxTokens, temperature, topP, stopSequences); top_k is not one of them, so it does not belong there.
C=Parameters as prompt text: instructions in a prompt do not set sampling or token limits; they are API fields, not wording the model reads.
D=Must switch to InvokeModel: Converse supports model-specific parameters through additionalModelRequestFields, so there is no need to give up the common format.
T: In Converse, set maxTokens and temperature in inferenceConfig and pass model-specific parameters in additionalModelRequestFields.
V: Amazon Bedrock

@ DVA-C03 D1 T1.1 advanced use-case
S: A web chat front end must show a model's answer word by word as it is generated, instead of waiting several seconds for the full response. The backend is a Lambda function on a Node.js runtime that calls Amazon Bedrock. Which implementation meets this requirement?
A: Call the Converse API in the function and return its output through an API Gateway HTTP API, which delivers each part of the response as soon as the function writes it
B: Call ConverseStream in the function and invoke the function asynchronously, so that Lambda forwards each contentBlockDelta event to the browser as it arrives
C: Call ConverseStream and write each contentBlockDelta to a streaming response through a function URL in RESPONSE_STREAM mode or a REST API set to stream
D: Call ConverseStream in the function and return all deltas through an API Gateway REST API with the default BUFFERED transfer mode for the Lambda proxy integration
K: C
G: ## Two places that must stream
Word-by-word display needs streaming end to end:
1. **Model to backend**: `ConverseStream` (or `InvokeModelWithResponseStream`) returns an event stream: `messageStart`, many `contentBlockDelta` events carrying text pieces, `messageStop` (with the `stopReason`) and `metadata` (token usage). `Converse` returns only when the whole answer is ready.
2. **Backend to client**: the Lambda function must stream its own response. Lambda supports response streaming natively on Node.js runtimes, through a **function URL** with invoke mode `RESPONSE_STREAM` or the `InvokeWithResponseStream` API. An API Gateway **REST API** proxy integration can stream too when its response transfer mode is set to `STREAM` (the default is `BUFFERED`).
## Example
The handler wrapped in `awslambda.streamifyResponse` loops over the ConverseStream events and writes each delta's text to the response stream, so the browser receives the first words in well under a second.
W: ConverseStream plus Lambda response streaming: the model streams deltas to the function, and the function URL in RESPONSE_STREAM mode or the REST API in STREAM mode passes each piece to the browser immediately.
X: A=Converse with an HTTP API: Converse waits for the full answer before returning, and HTTP APIs do not stream the response, so the user still waits for everything.
B=Asynchronous invocation: an asynchronous invoke returns to the caller immediately and sends nothing back, so the browser never receives the deltas.
D=REST API in BUFFERED mode: with the default transfer mode, API Gateway waits for the complete integration response before sending it, so streaming from Bedrock is lost at the last hop.
T: For token-by-token output, use ConverseStream and stream the Lambda response (function URL RESPONSE_STREAM or REST API STREAM transfer mode).
V: Amazon Bedrock, AWS Lambda, Amazon API Gateway

@ DVA-C03 D1 T1.1 applied troubleshooting
S: A Lambda function successfully calls the Amazon Bedrock Runtime Converse API. After a developer changes the code to ConverseStream for the same model, every call fails with AccessDeniedException. The execution role policy allows bedrock:InvokeModel on the model ARN. What should the developer change?
A: Add bedrock:Converse and bedrock:ConverseStream to the policy, because each Bedrock Runtime operation is authorized by an IAM action with the same name
B: Add bedrock:InvokeModelWithResponseStream on the same model ARN to the role, because ConverseStream is authorized by that action rather than InvokeModel
C: Request model access again for the streaming variant of the model, because Bedrock grants model access separately for streaming and non-streaming calls
D: Configure a VPC interface endpoint for bedrock-runtime, because streaming responses from Bedrock are available only to callers that run inside a VPC
K: B
G: ## Which IAM action authorizes which call
The Converse API is a common request format on top of the base inference actions, so its permissions reuse their IAM actions:
- `Converse` requires `bedrock:InvokeModel`.
- `ConverseStream` requires `bedrock:InvokeModelWithResponseStream`.
A role that only allows `bedrock:InvokeModel` can call `Converse` and `InvokeModel` but not the streaming operations.

G: ## What ThrottlingException means in Bedrock
`ThrottlingException` (HTTP 429) means the request exceeded an account quota for on-demand inference, such as requests or tokens per minute for that model in that Region. Short bursts can hit the per-minute limits even when average traffic is low.
## Two complementary fixes
- **Retry with backoff and jitter**: wait a little longer after each throttled attempt, with randomness so that many clients do not retry at the same moment. AWS SDKs do this for throttling errors; in boto3, for example, `Config(retries={"mode": "adaptive", "max_attempts": 8})`, where adaptive mode also rate-limits the client.
- **Cross-Region inference**: call an inference profile such as `us.<model-id>` as the `modelId`. Requests stay inside the profile's geography, and the IAM role needs access to the profile and to the model in each destination Region.
For predictable, sustained high volume, Provisioned Throughput or a quota increase are further options.
W: A=Backoff with jitter in the SDK: spreading retries over time lets bursty requests succeed once the per-minute window has room, without adding load while the quota is exhausted.
C=US cross-Region inference profile: routing across several US Regions gives the application more capacity during peaks, and the US profile respects the stated geography.
X: B=Immediate retry loop: retrying instantly adds even more requests while the quota is already exhausted, which makes throttling worse for every caller.
D=Streaming avoids quotas: streaming calls are subject to on-demand inference quotas just like non-streaming ones; the API style does not create capacity.
E=More Lambda memory: the 429 comes from Bedrock quotas, not from the caller's compute; function memory has no effect on it.
T: Handle Bedrock ThrottlingException with SDK backoff and jitter, and raise throughput with a cross-Region inference profile.
