@ DVA-C03 D3 T3.2 applied troubleshooting
S: A developer asks Kiro to generate unit tests for a Lambda function that calculates shipping fees. Kiro reads the handler and produces 25 tests that all pass, and line coverage rises to 92%. A week later a customer reports that orders over 20 kg are charged the lightweight rate, a defect that was already in the code when the tests were generated. Why did the tests miss the defect, and what should the developer change?
A: The tests were derived from the existing code, so they encode its current behavior, bug included; generate tests from the written requirements or a Kiro spec's acceptance criteria and review each assertion against them
B: Line coverage below 100% left the weight branch untested; ask Kiro to keep adding tests until every line is covered, because full line coverage proves that each branch of the fee calculation returns the correct result
C: Unit tests cannot detect calculation errors in Lambda code; replace the generated tests with tests that call the deployed function through API Gateway, since only end-to-end tests exercise the business rules
D: One generation run produces too little variety in its tests; regenerate the suite several times with different prompts and keep the union of all runs, so that the variation between runs eventually covers the faulty rule
K: A
G: ## Where a generated test gets its expected values
Every test has two parts: inputs that **exercise** the code and an assertion that says what the **correct** result is. The second part is called the test oracle.
When an AI tool such as Kiro writes tests by reading only the implementation, its best guide to "correct" is what the code does today. If the code charges the light rate for 21 kg, a test generated from that code will assert the light rate, pass, and lock the bug in.
## Coverage is not correctness
Line or branch coverage measures which code ran during the tests. A test that runs the heavy-parcel branch and asserts the wrong fee still counts as coverage. High coverage with code-derived assertions can therefore hide defects.
## Give the AI tool the requirement, then review
- Generate tests from an independent source of truth: the requirement, a ticket's acceptance criteria, or a Kiro **spec** (Kiro's spec-driven workflow writes requirements with acceptance criteria, a design and a task list before code).
- Example acceptance criterion: "orders over 20 kg use the heavy rate". The test for 21 kg then asserts the heavy rate and fails against the buggy code, which is exactly what should happen.
- A human reviews each generated assertion against the requirement before the tests are trusted as a regression suite.
W: Requirement-based tests with review: tests generated from the implementation inherit its mistakes, so the expected values must come from the requirements or spec acceptance criteria, and a reviewer checks that each assertion matches the rule rather than the current output.
X: B=Push line coverage to 100%: coverage only shows that a line ran, not that the assertion on it is right; the weight branch can be fully covered by a test that asserts the wrong fee taken from the code.
C=Only end-to-end tests: unit tests catch calculation errors well when their expected values are correct; calling the function through API Gateway would still pass if those tests also copy their expectations from the current behavior.
D=Regenerate and merge runs: every run reads the same buggy implementation, so more runs give more tests with the same wrong oracle rather than a test that expects the correct heavy rate.
T: AI-generated tests are only as good as their expected values: derive them from requirements or specs, not from the code under test, and have a human review the assertions.
V: Kiro, AWS Lambda

@ DVA-C03 D3 T3.2 applied use-case
S: A team uses Kiro to generate unit tests for a serverless application, and developers run the generated tests in their workspace before they commit. The team wants no generated test to join the regression suite unchecked, and no change to be deployed unless the whole suite passes. Which TWO actions meet these requirements? (Select TWO)
A: Commit the generated tests to the repository next to the code they cover, and have a reviewer check each assertion against the requirements in the pull request before merging
B: Add a CodeBuild action that runs the full test suite with a test report group and fails the build when any test fails, which stops the pipeline before the deploy stage
C: Tell the agent through a steering file to mark a failing test as skipped whenever it cannot make the test pass within three attempts, so that the pipeline is never blocked
D: Remove the test stage from the pipeline for commits written in Kiro, because the agent already ran the tests locally before the commit and running them again only adds build minutes
E: Send each commit diff to a Bedrock model and run only the tests that the model predicts are affected, treating every other test as passed when the pipeline decides whether to deploy
K: A,B
G: ## Two layers around AI-generated tests
AI tools write test code quickly, but a generated test protects production only when a person has checked what it asserts and a gate that nobody can skip runs it on every change.
- **Review in the pull request**: generated tests are committed next to the code they cover, so they are versioned and visible in the diff. The reviewer checks each assertion against the requirement (a test that asserts the current, possibly wrong, output protects nothing), and only merged tests become part of the regression suite.
- **Pipeline gate**: an AWS CodeBuild action runs the complete suite in a clean environment. A **report group** in the buildspec collects JUnit or similar result files (and coverage files such as JaCoCo or LCOV). The test command exits with a non-zero code when any test fails, which fails the build and stops AWS CodePipeline before the deploy stage.
## Why the pipeline gate stays deterministic
A local run can be skipped, can use different dependencies or can be edited. The pipeline result is the same for every commit, human-written or AI-written. Rules that let an agent skip or hide failing tests, or that trust a model's guess about which tests matter, turn the gate into an opinion.
W: A=Commit and review the generated tests: the tests become versioned code that a reviewer checks against the requirements before they join the suite, so no AI-written assertion is trusted unchecked.
B=CodeBuild test gate: running the whole suite in the pipeline and failing the build on any failure is the deterministic check that blocks deployment, regardless of who or what wrote the code and the tests.
X: C=Auto-skip failing tests: skipping a test the agent cannot fix hides exactly the regressions the suite exists to catch, and it lets the pipeline pass with known failures.
D=Trust the local run: a local run is not reproducible or enforced; dependencies, environment and test selection may differ, so the pipeline must run the suite itself.
E=Model-selected tests treated as passed: a prediction of which tests are affected can be wrong, and counting unrun tests as passed means a missed dependency ships a regression without any test having checked it.
T: Review AI-generated tests in the pull request like any other code, and keep a full, deterministic test run in the pipeline as the gate that blocks deployment.
V: Kiro, AWS CodeBuild, AWS CodePipeline

@ DVA-C03 D3 T3.2 advanced use-case
S: A nightly CodeBuild project runs 4,000 integration tests and publishes JUnit XML results to a CodeBuild report group. On a typical night 30-60 tests fail, and engineers spend the first hour of each day sorting failures into real regressions, environment problems and flaky tests. The team wants an AI-written triage summary each morning, but the AI must not change whether the build passed or failed. Which design meets these requirements?
A: An EventBridge rule on build completion invokes a Lambda function that reads the failed test cases from the report, sends their names, messages and recent pass history to a Bedrock model, and posts the summary to an SNS topic
B: A Lambda function sends the complete console log of every nightly build, including all passing tests, to a Bedrock model and sets the build result to succeeded when the model classifies every failure as a flaky test
C: The test report files are added to an Amazon Bedrock knowledge base every night, and engineers ask the knowledge base each morning which tests failed, because retrieval returns the failures already grouped by cause
D: A Bedrock model is fine-tuned each week on the past month of test reports so that it learns the suite, and the buildspec calls the custom model to decide which of the 4,000 tests should run on the following night
K: A
G: ## AI for test result analysis
Large suites produce more failures than people can read quickly. A model is good at reading failure messages and grouping them ("12 tests fail with the same connection timeout to the staging database"), but it needs the right input:
- **Only the failures**, with their test names, error messages and a short stack excerpt. CodeBuild report groups store each test case with its status and message, and the `DescribeTestCases` API can filter them by status.
- **History** for each failing test, such as how often it failed in recent reports, which separates flaky tests from new regressions.
## Keep the result separate from the summary
The build status comes from the tests themselves. The AI summary is advice for humans. An event-driven design keeps the two apart:
- Amazon EventBridge receives the CodeBuild build state change event when the nightly build finishes.
- A Lambda function gathers the failed cases, calls an Amazon Bedrock model with the Converse API and a prompt that asks for groups (regression, environment, flaky) with evidence.
- The function posts the text to an Amazon SNS topic (or a chat channel); it has no permission to change the build.
W: Event-driven triage summary: the Lambda function sends only the failed cases plus their history, which fits the model's context and gives it what it needs to separate regressions from flaky tests, and the build status stays exactly as the tests set it.
X: B=Full log and model-set status: thousands of passing-test lines waste tokens and may not fit the context window, and letting the model turn a failed build into a success breaks the requirement that the AI must not change the result.
C=Knowledge base of reports: retrieval returns the text chunks most similar to a question; it does not compute which tests failed last night or group failures by cause, so engineers still do the sorting.
D=Weekly fine-tuning and test selection: fine-tuning is costly and slow to refresh, does not produce a daily summary, and letting a model decide which tests run removes regression coverage from the nightly suite.
T: For AI test triage, send the model only the failures and their history, deliver the summary to people, and leave the pass or fail status to the tests.
V: AWS CodeBuild, Amazon EventBridge, AWS Lambda, Amazon Bedrock, Amazon SNS

@ DVA-C03 D3 T3.2 applied use-case
S: A coverage report (LCOV) shows that a refund module has 48% branch coverage. The uncovered branches handle partial refunds, currency rounding and a timeout from the payment provider. The team asks Kiro to improve coverage of this module. Which approach is most likely to produce useful tests?
A: Provide the coverage report and the refund requirements, name the uncovered branches, and ask for tests that assert the required outcome of each one, using the stubbing conventions from the project's steering file
B: Ask Kiro to raise total project coverage to 80% by any means and let the agent choose which files to test, since the overall coverage percentage is the figure that the pipeline gate checks before deployment
C: Ask Kiro to exclude the refund module from coverage measurement because payment code is hard to test, and to raise the threshold for the other modules so that the overall figure still reaches the target
D: Ask Kiro to simplify the refund module by deleting the rounding and timeout branches, since fewer branches mean that the existing tests cover a higher share of the module without any new tests
K: A
G: ## Using a coverage report as AI context
A coverage report (for example LCOV, Cobertura or JaCoCo, all accepted by CodeBuild coverage report groups) lists which lines and branches ran. It is useful input for an AI tool because it points at the exact gaps.
A good request to Kiro combines:
- **Where**: the uncovered branches from the report (partial refund, rounding, provider timeout).
- **What is correct**: the requirement for each case, for example "a partial refund never exceeds the captured amount" or "amounts round half-up to two decimals".
- **How the team writes tests**: Kiro **steering files** hold project guidance (test framework, how to stub the payment client, naming) that the agent applies to every task.
## Why the target number alone is a trap
If the only goal is a percentage, the cheapest path is tests for trivial code elsewhere, or excluding hard modules. The number rises while the risky refund paths stay untested. The goal is tested behavior in the risky branches; coverage is a way to find them.
W: Targeted, requirement-based request: the report shows the agent exactly which branches are missing, the requirements give it correct expected values, and the steering file keeps the tests in the team's style, so the new tests cover the risky refund paths with meaningful assertions.
X: B=Any means to 80%: the agent can reach the number with easy tests in unrelated files, so the refund module, where the gaps and the risk are, can stay at 48%.
C=Exclude the module: removing payment code from measurement hides the riskiest gaps from the report; the figure looks better while nothing in the refund paths is tested.
D=Delete branches: partial refunds, rounding and provider timeouts are real behavior; deleting the code that handles them creates defects to make a metric look better.
T: Give the AI tool the coverage gaps, the requirements and the team's test conventions, and aim at tested behavior in the risky branches, not at the percentage alone.
V: Kiro, AWS CodeBuild

@ DVA-C03 D3 T3.2 applied troubleshooting
S: Kiro generated unit tests for a Lambda function that reads orders from Amazon DynamoDB. The tests pass on the developer's laptop but fail intermittently in CodeBuild with `ResourceNotFoundException` and throttling errors. Review shows the tests call a shared development table through the AWS SDK. What should the developer do?
A: Stub the DynamoDB client in the unit tests with an SDK stubbing or mock library, record that rule in a steering file, and move checks against a real table to an integration suite that deploys its own stack
B: Give the CodeBuild service role AdministratorAccess and move the shared development table to provisioned capacity with high write capacity, so the generated tests have the access and throughput they need
C: Add a retry with a fixed five-second delay around every test case in the buildspec, so that intermittent errors from the shared table are absorbed and the generated tests report a pass on the second attempt
D: Ask Kiro to regenerate the tests each time they fail in CodeBuild and accept the new version without review, since the agent sees the latest error and can adjust the expected values until the tests pass
K: A
G: ## Unit tests should not depend on live resources
A unit test checks the function's own logic. If it calls a real DynamoDB table, its result also depends on things outside the code:
- whether that table exists in the account and Region where the test runs (CodeBuild may use a different account or Region than the laptop, hence `ResourceNotFoundException`),
- whether other people are writing to the shared table at the same time (throttling, changed data).
Such tests are **flaky**: they fail for reasons unrelated to the code change, and teams learn to ignore them.
## How to fix AI-generated tests that do this
- **Stub the SDK** in unit tests, for example with the AWS SDK for JavaScript client mock library, `botocore` Stubber, or moto in Python, so each test controls exactly what DynamoDB returns, including error cases.
- **Tell the AI tool the rule once**: put "unit tests never call AWS; stub the SDK clients" in a Kiro steering file so future generated tests follow it.
- **Keep integration tests separate**: tests that need a real table deploy their own short-lived stack (AWS SAM or CDK) with its own table, run, and tear it down.
W: Stub plus steering plus separate integration suite: stubbing removes the dependency on a shared table, the steering file stops the agent from generating the same pattern again, and real-table checks still exist in an isolated, repeatable integration suite.
X: B=Administrator role and more capacity: broader permissions do not create a missing table in the build's account or Region, and other users still change and throttle the shared table, so the tests stay flaky while the build gains far too much access.
C=Retry each test: retries hide the flakiness instead of removing it, slow the build, and a missing table fails on every attempt anyway.
D=Regenerate without review: letting the agent change expected values until tests pass rewrites the tests to match whatever the environment returned, which removes their value as checks of the code.
T: AI-generated unit tests must stub AWS calls; tell the tool that rule in a steering file and keep live-resource tests in a separate, self-contained integration suite.
V: Kiro, AWS CodeBuild, Amazon DynamoDB, AWS Lambda

@ DVA-C03 D3 T3.3 advanced tradeoff
S: A pipeline deploys CloudFormation change sets to production after a manual approval action. Approvers complain that most change sets only update Lambda code or environment variables, and waiting for them slows releases. The team wants a Lambda function that uses an Amazon Bedrock model to summarize each change set and wants routine changes approved automatically. Which design keeps the approval step safe?
A: The function applies fixed rules to the change set first: any IAM change, resource replacement or deletion waits for a human; only changes outside those rules are approved with PutApprovalResult, with the Bedrock summary attached
B: The function sends the change set to the Bedrock model and calls PutApprovalResult with Approved whenever the answer contains the words "low risk" and with Rejected in every other case, so that no human is involved
C: The function approves every change set at once and asks the Bedrock model to write a summary into the pipeline history afterwards, so that approvers can review the production changes later at their convenience
D: The approval action is removed and the deployment role is allowed to call Bedrock, so that CloudFormation asks the model whether to continue before it creates, updates or deletes each resource in the stack
K: A
G: ## Approvals in CodePipeline
A **manual approval action** pauses a pipeline until someone (or something with permission) calls `PutApprovalResult` with `Approved` or `Rejected` and the token of that approval. It can notify an Amazon SNS topic and include a custom message and a link for reviewers.
## Where AI fits
A CloudFormation **change set** lists every planned action: `Add`, `Modify` or `Remove`, and for modifications whether the resource will be **replaced**. These facts are machine-readable, so the decision about what is risky can be made by fixed rules:
- IAM roles or policies change, a resource is replaced, or a resource is deleted: a human must approve.
- Only a Lambda function's code or environment variables change: low risk.
An Amazon Bedrock model adds value on top of that by writing a readable summary ("updates the code of 3 functions; no data resources affected") for the approver or the audit trail.
## The safe pattern
Deterministic rules decide which changes may be approved automatically; the model explains, it does not decide. The function that calls `PutApprovalResult` has permission for that one pipeline only, and every automatic approval records the rule that allowed it.
W: Fixed rules decide, the model summarizes: risky change types are detected from the change set's structured data and always reach a human, routine changes skip the wait, and the Bedrock summary helps approvers without being the control.
X: B=Approve on the words "low risk": the decision depends on free text from a model, which can be phrased differently or be wrong, so a destructive change could be approved because of the wording of one answer.
C=Approve everything, review later: production changes are applied before anyone looks at them, so the approval step no longer prevents anything and a bad change is found only after the damage.
D=CloudFormation asks the model: CloudFormation has no step that consults a model before each resource action, and removing the approval leaves no human check for IAM changes, replacements or deletions.
T: For AI-assisted deployment approvals, let deterministic rules on the change set decide what may be auto-approved and use the model only to summarize for humans.
V: AWS CodePipeline, AWS CloudFormation, AWS Lambda, Amazon Bedrock

@ DVA-C03 D3 T3.3 applied use-case
S: A developer uses Kiro to write AWS CDK code for short-lived preview environments, one per feature branch, each with API Gateway, Lambda and a DynamoDB table. The security team requires that every environment change is reviewable and repeatable and that no developer workstation holds credentials that can change production. Which approach meets these requirements?
A: Commit the generated CDK code, review it with the `cdk diff` output in the pull request, and let the pipeline deploy each branch stack with a deployment role limited to the preview account
B: Let the Kiro agent run `cdk deploy` from the laptop with an administrator profile and without step approvals, since the agent can fix deployment errors immediately and simply retry
C: Store the natural-language prompt in the repository and have the pipeline ask a Bedrock model to generate fresh CDK code on each run, so environments always follow the latest model
D: Have a Lambda function ask a Bedrock model at runtime to create the resources through SDK calls whenever a branch is pushed, so that no CloudFormation stacks have to be managed
K: A
G: ## AI-generated infrastructure is still infrastructure as code
Kiro can write AWS CDK or CloudFormation code for an environment quickly. What makes that safe is the usual IaC discipline, applied to the generated code:
- **Reviewable**: the generated code is committed like any other code. `cdk diff` (or a CloudFormation change set) shows exactly which resources will be created, changed or replaced, and a reviewer approves the pull request.
- **Repeatable**: the same committed code produces the same stack on every run. Generating new code from a prompt on each run is not repeatable, because a model can produce different code for the same prompt.
- **Least privilege**: the pipeline deploys with a role that can change only the preview account (for example a CDK bootstrap deployment role there). Developers and their AI tools never need production credentials on a laptop.
## Example
A pull request for branch `feature/coupons` contains `lib/preview-stack.ts` written with Kiro's help. The pipeline runs `cdk synth`, posts the diff, and after merge deploys `Preview-feature-coupons` into the preview account; deleting the branch triggers `cdk destroy` for that stack.
W: Committed, reviewed CDK deployed by the pipeline: the code and its diff are reviewed before anything changes, the same code gives the same environment every time, and only the pipeline's scoped role can deploy, so no workstation credentials are involved.
X: B=Agent deploys with admin from the laptop: an administrator profile on a workstation is exactly the credential the security team forbids, and an agent retrying deployments without step approvals changes infrastructure that nobody reviewed.
C=Regenerate code on every run: a model can return different code for the same prompt, so environments drift between runs, and the code that is deployed was never reviewed.
D=Runtime resource creation by a model: resources created by SDK calls outside CloudFormation are not tracked as a stack, cannot be diffed or cleanly deleted, and the Lambda function would need broad create permissions.
T: Use AI tools to write IaC, then treat the output like any code: commit, review the diff, and let the pipeline deploy it with a scoped role.
V: Kiro, AWS CDK, AWS CloudFormation, AWS CodePipeline

@ DVA-C03 D3 T3.3 applied use-case
S: A team deploys a Lambda function with AWS SAM and CodeDeploy using a 10 percent canary for 10 minutes. They want AI help with analysis after a release goes wrong, but a bad release must still be rolled back within minutes even when no one is online. Which TWO actions meet these requirements? (Select TWO)
A: Attach CloudWatch alarms on the new version's errors and p99 duration to the deployment preference, so that CodeDeploy stops the deployment and shifts traffic back when an alarm fires
B: Configure CloudWatch investigations with an investigation group and add an investigation action to the same alarms, so that an investigation with hypotheses starts when an alarm fires
C: Turn off automatic rollback and let a Lambda function send the canary's logs to a Bedrock model every minute, rolling back only when the model concludes that the new release is faulty
D: Turn off automatic rollback during business hours so that engineers can keep the faulty version live while a Kiro agent analyzes the errors and writes a fix before the canary period ends
E: Replace the PostTraffic hook's test with a prompt that asks a Bedrock model whether the deployment looks healthy, and report success from the hook whenever the answer mentions no error
K: A,B
G: ## Post-deployment validation for Lambda with CodeDeploy
With AWS SAM, `AutoPublishAlias` and a `DeploymentPreference` (for example `Canary10Percent10Minutes`) make CodeDeploy shift 10% of the alias traffic to the new version, wait, then shift the rest. Two deterministic checks protect the release:
- **Alarms**: CloudWatch alarms listed in the deployment preference. If any goes into ALARM during the deployment, CodeDeploy stops it and moves traffic back to the old version automatically.
- **Hooks**: `PreTraffic` and `PostTraffic` Lambda functions run real checks and report `Succeeded` or `Failed` to CodeDeploy.
These work at 3 a.m. with nobody online and give the same answer for the same data.
## Where AI helps
After the rollback, someone still has to find out why. **CloudWatch investigations** is a generative AI feature that scans metrics, logs, traces, deployment events and CloudTrail changes and proposes root-cause hypotheses. Once an investigation group is configured, an alarm can have an action that starts an investigation, so the analysis is waiting when the engineer arrives.
The pattern: deterministic signals trigger the rollback; AI explains what happened.
W: A=Alarms on the deployment preference: CodeDeploy rolls back within the canary window based on metric thresholds, with no human or model in the loop, which meets the unattended rollback requirement.
B=Investigation action on the alarms: the same alarm that triggers rollback also starts a CloudWatch investigation, so AI-generated hypotheses and related telemetry are ready for the team after the event.
X: C=Model decides on rollback: rollback depends on a model's reading of log text, which can be wrong or slow, and with automatic rollback off a missed judgement leaves a bad release serving traffic.
D=Keep the faulty version live: disabling rollback exposes users to a known bad release so that an agent can debug in production; the analysis can run just as well after the old version is restored.
E=Model as the PostTraffic test: a hook should run deterministic checks against the new version; an answer that simply does not mention an error is not evidence that the release works.
T: Keep alarms and CodeDeploy rollback as the deterministic gate for releases, and use AI tools such as CloudWatch investigations to explain failures afterwards.
V: AWS CodeDeploy, AWS SAM, Amazon CloudWatch, AWS Lambda

@ DVA-C03 D3 T3.3 advanced use-case
S: A team builds a release assistant agent on Amazon Bedrock AgentCore Runtime. Release managers chat with it to check pipeline status, read recent deployment errors and, when they confirm, stop a failing CodeDeploy deployment. The agent's tools are exposed through an AgentCore Gateway. Security reviewers worry that a misread instruction could make the agent change production. What is the best control?
A: Limit the IAM roles behind the gateway's tools to read-only pipeline and log access plus `codedeploy:StopDeployment` for one application, and attach AgentCore Policy to the gateway to limit tool calls and inputs
B: Give the agent AdministratorAccess and attach an Amazon Bedrock guardrail with denied topics for destructive actions, because a guardrail blocks every tool call that could harm the production resources
C: Write in the agent's system prompt that it must never change production without approval, and give its role the same broad permissions as the release managers so that it can help with every task
D: Store a release manager's long-term access keys in AgentCore Memory so that every action is performed under a human identity, which makes the agent's actions show up correctly in AWS CloudTrail
K: A
G: ## An agent acts with the permissions you give it
An AI agent decides which tool to call from natural language. It can misunderstand a request or be manipulated by text it reads (for example, an error message that contains instructions). The question to ask is therefore: **what is the worst the agent can do with its permissions?**
## Layers that limit an agent
- **IAM on the roles that do the work**: the credentials the gateway's tools use to call AWS (for example the execution roles of Lambda function targets) and the agent's runtime role should allow only what the use case needs. Here that is reading pipeline state and logs, and `codedeploy:StopDeployment` on one application's deployment groups.
- **Policy in Amazon Bedrock AgentCore**: a policy engine associated with an AgentCore Gateway intercepts every tool call that goes through the gateway and evaluates it against deterministic policies written in Cedar before the tool runs, so you can say which tools an agent may call and with which parameters.
- **Human confirmation** for the one action that changes something, built into the application flow.
## What does not limit actions
- A **system prompt** is guidance the model may not follow.
- **Bedrock Guardrails** filter content in prompts and responses (harmful topics, PII, prompt attacks); they are not an authorization system for AWS API calls.
- Sharing a person's **long-term keys** makes the agent indistinguishable from that person and creates a secret to leak.
W: Least-privilege roles plus AgentCore Policy: even if the agent misreads an instruction, IAM allows only reads and stopping one application's deployments, and the gateway policy blocks tool calls outside the allowed set before they reach AWS.
X: B=Administrator plus guardrail: guardrails filter prompt and response content; they do not authorize or deny AWS API calls, so an administrator role leaves every production resource within the agent's reach.
C=System prompt instruction: a prompt is not an enforcement mechanism, and broad permissions mean that any misread or injected instruction can change production.
D=Human keys in memory: long-term keys stored with the agent can leak, cannot be scoped to the agent's task, and make CloudTrail show a person for actions that the agent took.
T: Limit an AI agent with least-privilege IAM and deterministic tool policies at the gateway, not with prompts or content guardrails.
V: Amazon Bedrock AgentCore, AWS CodeDeploy, AWS IAM

@ DVA-C03 D3 T3.3 applied troubleshooting
S: When a CodeBuild action fails, a pipeline invokes a Lambda function that sends the last 20 lines of the build log to an Amazon Bedrock model and posts the suggested fix on the pull request. Developers say the suggestions are generic ("check your dependencies") and often blame the wrong step. What change will most improve the suggestions?
A: Send the log of the failed build phase around the first error, the buildspec and the diff of the commit under test, and ask for the likely cause with the evidence lines quoted
B: Switch to the largest model available in Amazon Bedrock and raise the temperature, since a larger, more creative model can infer the full build context from twenty lines
C: Send the complete logs of the last 100 successful builds with each request, so that the model learns the project's normal output before it reads the log of the failed build
D: Ask the model to list a fix for every possible cause in one answer, so that developers can try each suggestion in turn until the build passes without reading the build logs
K: A
G: ## The model only knows what is in the prompt
A model asked "why did this build fail?" can reason only over the text it receives. The last lines of a CodeBuild log are often cleanup output or a generic `COMMAND_EXECUTION_ERROR`, while the real cause (a failing test, a missing environment variable, a dependency conflict) appears earlier.
## Context that makes CI failure analysis useful
- **The failing phase** of the build (`install`, `pre_build`, `build`, `post_build`) and the lines around the **first** error, not just the end of the log.
- **The buildspec**, so the model knows which commands ran in which phase.
- **The change under test**: the commit diff, which is usually where a new failure comes from.
- **An output format** that asks for one likely cause with the quoted evidence lines, so a developer can verify the claim quickly.
Keep the prompt focused: more text is not better if it is unrelated, and secrets must not appear in logs that are sent anywhere.
W: Relevant failure context: the first error in the failed phase, the commands from the buildspec and the diff together let the model connect the error to the change, and quoted evidence lets developers check the suggestion instead of trusting it.
X: B=Bigger model, higher temperature: no model can see lines it was never sent, and a higher temperature makes answers more varied, not more accurate.
C=Hundred successful logs: a large amount of unrelated output costs tokens, can exceed the context window, and buries the few lines of the failed build that actually matter.
D=Every possible fix: a long list of guesses moves the diagnostic work back to the developers and encourages random changes instead of a fix based on evidence.
T: AI troubleshooting in CI/CD depends on context: send the failing phase around the first error, the build definition and the change, and ask for evidence.
V: AWS CodeBuild, AWS CodePipeline, AWS Lambda, Amazon Bedrock

@ DVA-C03 D4 T4.1 applied use-case
S: An on-call team wants CloudWatch investigations to start automatically when the `checkout-api-5xx` alarm goes into ALARM, to take recent CloudTrail change events into account, and to let every on-call engineer view and continue the investigation. @ DVA-C03 D4 T4.3 advanced troubleshooting
S: Kiro flags that a Lambda function calls DynamoDB `GetItem` once per product ID in a loop, up to 100 IDs per request, and proposes a refactor that uses `BatchGetItem`. G: ## From N calls to one batch
Calling `GetItem` in a loop makes one network round trip per item. `BatchGetItem` fetches up to **100 items** (and up to 16 MB) from one or more tables in a single call, which an AI tool will often suggest as a code efficiency improvement.
## The partial-result rule
`BatchGetItem` is not all-or-nothing. If the request exceeds the response size limit, the table's throughput is exceeded, or an internal error occurs, DynamoDB returns the items it could read and lists the rest in **`UnprocessedKeys`**. The call still succeeds. Code that ignores this field silently drops items, which shows up only under load.
## Correct handling
- Loop while `UnprocessedKeys` is not empty, sending those keys again.
- Wait between retries with exponential backoff (and jitter) so the retry does not add to the throttling.
- Merge all returned items before building the response.
## Lesson for AI-suggested refactors
The suggestion was right about efficiency but incomplete about the API's contract. Reviewers should check the documented edge cases of any new API the tool introduces, and a test with a stubbed response that includes `UnprocessedKeys` keeps the handling in place.
W: UnprocessedKeys handling: under load DynamoDB returns part of the batch and lists the remaining keys, so the refactor must retry them with backoff and merge the results, otherwise products silently disappear from responses.
X: B=Only indexes: BatchGetItem reads items from tables by primary key; it does not require or use a global secondary index.
C=Ten items per call: the documented limit is 100 items (and 16 MB) per call, so a 100-ID request fits in one call; the missing items come from unprocessed keys, not from a ten-item cap.
D=Consistency and capacity mode: BatchGetItem supports eventually or strongly consistent reads on both capacity modes, and the consistency setting has nothing to do with keys being left unprocessed.
T: When an AI tool proposes BatchGetItem (or BatchWriteItem), check that the code retries the unprocessed keys or items with backoff; partial results are part of the API contract.
