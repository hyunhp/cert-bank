@ DVA-C03 D1 T1.2 expert troubleshooting
S: A Lambda function with a 60-second timeout and reserved concurrency of 10 consumes an SQS standard queue through an event source mapping with batch size 50 and a 20-second batching window. Each message takes about 1 second, so a full batch runs for about 50 seconds. The queue's visibility timeout is 60 seconds and its redrive policy uses maxReceiveCount 2. During bursts the function's Throttles metric rises, and healthy messages land in the dead-letter queue although the code never failed on them. The downstream API accepts at most 10 concurrent callers. Which THREE changes stop healthy messages from reaching the dead-letter queue while respecting the API limit? (Select THREE)
A: Set the mapping's maximum concurrency to 10 and keep reserved concurrency at 10, so pollers stop pulling batches the function cannot run
B: Raise the queue's visibility timeout to at least 380 seconds: six times the 60-second function timeout plus the 20-second batching window
C: Raise maxReceiveCount on the redrive policy to at least 5, so messages returned after a throttled or late receive still have attempts left
D: Remove the function's reserved concurrency so it can draw on the unreserved account pool, and let the event source mapping scale freely during bursts
E: Raise the function timeout to 900 seconds and keep the 60-second visibility timeout, so each batch of 50 messages has more time to finish
F: Lower the batch size to 10 and remove the batching window, so each invocation finishes sooner and messages go back to the queue more quickly
K: A,B,C
G: ## Why throttling sends healthy messages to the DLQ
Lambda pollers keep reading batches as the queue grows. A batch they read is **in flight** (invisible for the visibility timeout). If the function is throttled because reserved concurrency (10) is full, the batch cannot be processed and its messages become visible again when the timeout ends, each receive counting toward `maxReceiveCount`. With `maxReceiveCount = 2`, two throttled receives are enough to move a message that never failed into the DLQ.
## The three documented settings
- **Maximum concurrency** on the SQS event source mapping (2 to 1,000) caps how many invocations the mapping attempts, so pollers do not pull batches that would be throttled. Keep reserved concurrency greater than or equal to it.
- **Visibility timeout**: AWS recommends at least **6 x function timeout + MaximumBatchingWindowInSeconds**: 6 x 60 + 20 = **380 seconds**. Lambda also rejects a mapping whose function timeout exceeds the visibility timeout.
- **maxReceiveCount at least 5** gives Lambda several chances before the DLQ.
## Working the numbers
A 50-message batch takes about 50 seconds of a 60-second timeout, so a 60-second visibility timeout leaves no room for a retry after a throttle.
W: A=Maximum concurrency 10: the mapping only pulls as many batches as 10 invocations can run, which also matches the downstream API limit, so batches are not received and then throttled.
B=380-second visibility timeout: 6 x 60 seconds plus the 20-second window is the documented minimum, so a throttled batch is retried before its messages reappear.
C=maxReceiveCount 5 or more: a message that is received again after a throttle or late finish still has attempts left before the dead-letter queue.
X: D=No reserved concurrency: the function could scale far past 10 invocations and overload the API, which accepts only 10 callers.
E=900-second timeout with a 60-second visibility timeout: Lambda refuses a mapping whose function timeout is longer than the queue's visibility timeout, and messages would reappear mid-batch anyway.
F=Smaller batches without a window: invocations get shorter, but pollers still pull more batches than 10 invocations can run, so throttled receives keep counting toward the DLQ.
T: For SQS triggers, cap concurrency on the mapping, set visibility to 6 x timeout + batching window, and use maxReceiveCount of at least 5.
V: AWS Lambda, Amazon SQS

B: Raise the table's provisioned write capacity to 10,000 WCU, so there is headroom for the 2,400 WCU that the busy article's updates consume

G: ## How UpdateItem is charged
DynamoDB charges an `UpdateItem` for the **larger of the item's size before and after** the update, rounded up to 1 KB, **even if only one attribute changes**. A 7.5 KB article costs **8 WCU per update**.
## Working the numbers
- 300 updates/s x 8 WCU = **2,400 WCU** on one item.
- A single partition supports at most **1,000 WCU** (and 3,000 RCU). Adaptive capacity can isolate a hot item on its own partition, but not above that maximum.

W: A=Separate counter item: each increment then costs 1 WCU, so 300 per second needs about 300 WCU, under the 1,000 WCU per-partition maximum and far cheaper than 2,400 WCU.
X: B=More table capacity: the limit is the 1,000 WCU maximum of the single partition that holds the item, so 2,400 WCU on one item still throttles.
C=ReturnValues NONE: ReturnValues only changes what the response returns; the write is still charged for the full 8 KB item.
D=On-demand mode: on-demand tables have the same per-partition maximum, so one item still cannot absorb 2,400 write units per second.
T: UpdateItem costs the full item size, and one partition caps at 1,000 WCU; keep hot counters in small separate items.

C: Query on orderId with default eventually consistent reads: 24 KB is 3 RCU per page, so about 1,500 RCU in total
D: TransactGetItems for the 20 keys: transactional reads cost twice, so 40 RCU per page, about 20,000 RCU in total
K: A
G: ## Read capacity rules
- One **strongly consistent** read of up to 4 KB = **1 RCU**; eventually consistent = 0.5 RCU; transactional = 2 RCU.
- **GetItem / BatchGetItem**: **each item** is rounded up to 4 KB separately. A 1.2 KB item counts as 4 KB.
- **Query**: DynamoDB adds up the size of **all items returned** and rounds the **total** up to the next 4 KB once.
## Working the numbers for one page
- Query, strong: 20 x 1.2 = 24 KB -> 6 x 4 KB -> **6 RCU**; x 500 pages = **3,000 RCU**.

- Query, eventual: 3 RCU; x 500 = 1,500 RCU, but may return lines older than the reservation update.
- TransactGetItems: 20 x 2 = 40 RCU; x 500 = 20,000 RCU.
W: A=Strongly consistent Query: one Query rounds the combined 24 KB once, so it needs 6 RCU per page and 3,000 RCU in total while returning the latest data.
X: B=BatchGetItem: each 1.2 KB item is rounded to 4 KB on its own, so the same page costs more than three times as much.
C=Eventually consistent Query: it is the cheapest, but it can return lines from before the reservation update, which the page must not show.
D=TransactGetItems: transactional reads cost two units per item, and isolation across items is not required here.
T: Query rounds the total size of returned items once; batch and single-item reads round every item to 4 KB.

@ DVA-C03 D2 T2.1 expert troubleshooting

The authorizer validates a JWT and returns an Allow policy whose Resource is event.methodArn. G: ## How authorizer caching works
With caching on, API Gateway stores the **policy document** the authorizer returned, keyed by the identity source (for a TOKEN authorizer, the token header). - A REQUEST authorizer with method or path in the identity sources: correct but invokes once per token **and** method.

X: B=TTL 0: it works, but the authorizer then runs on every request, breaking the once-per-token-per-TTL requirement.

D=30-second TTL: users who act within 30 seconds still get 403, and the authorizer runs ten times more often.
T: With authorizer caching, return a policy covering every resource the token may reach, not just event.methodArn.
