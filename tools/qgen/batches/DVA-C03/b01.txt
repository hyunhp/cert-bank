# DVA-C03 batch 01: D2 T2.3 security risks of using and integrating AI services (2.3.1 access, 2.3.2 data privacy, 2.3.3 input/output filtering, 2.3.4 agent interactions, 2.3.5 sensitive content in logs)

@ DVA-C03 D2 T2.3 advanced use-case
S: A Lambda function in us-east-1 calls Anthropic Claude models on Amazon Bedrock, and its execution role allows inference through any inference profile. A new data residency rule says this role's requests may be processed only in US Regions: US geographic inference profiles stay allowed, but global cross-Region inference profiles must be blocked, even if someone later adds broader Bedrock permissions to the role. What should the developer do?
A: Add a Deny for bedrock:InvokeModel* on all resources with a StringEquals condition listing every commercial AWS Region outside the US as the value of aws:RequestedRegion
B: Add a Deny for bedrock:InvokeModel* on all resources with a StringEquals condition that matches the value unspecified in the aws:RequestedRegion condition key
C: Rewrite the role's Allow statement to list only the US geographic inference profile ARNs and their models, and remove every global inference profile ARN from the policy
D: Create an interface VPC endpoint for bedrock-runtime in us-east-1 with private DNS enabled, so that every inference request from the function is processed in that Region
K: B
G: ## How Bedrock authorizes a global cross-Region inference call
A **global** inference profile (ID prefix `global.`) can route a request to any supported commercial Region worldwide; a **geographic** profile such as `us.` stays inside one geography. For a global profile, Bedrock evaluates IAM for three resources:
- the inference profile in the source Region, `arn:aws:bedrock:us-east-1:<account>:inference-profile/global.<model>`;
- the foundation model in the source Region;
- the Region-agnostic global foundation model, `arn:aws:bedrock:::foundation-model/<model>` (no Region, no account).
For that last evaluation Bedrock sets the global condition key `aws:RequestedRegion` to the literal value `unspecified`, not to the Region that ends up serving the request.
## Blocking global routing
The Bedrock user guide documents two ways to disable global cross-Region inference for a role: leave out one of the three required Allow statements, or add an **explicit Deny** with `"StringEquals": {"aws:RequestedRegion": "unspecified"}`. Only the explicit Deny survives later changes, because a Deny always overrides an Allow.
It also warns that ordinary Region-deny conditions that list Region names (for example `us-west-2`) do not match the global foundation model evaluation, so they do not stop global routing. The same detail matters for SCPs that block unused Regions: they must allow `unspecified` (or exempt the inference profile) if global inference is wanted.
W: Deny on aws:RequestedRegion unspecified: every global profile call needs the Region-agnostic model evaluation that carries this value, so the explicit Deny blocks global routing permanently while geographic US profiles keep working.
X: A=Deny listing non-US Regions: the global model evaluation carries unspecified, not a Region name, so a list of Region names never matches it and global calls still succeed.
C=Allow only US profiles: it blocks global profiles today, but it is only an absence of Allow; anyone who later adds broader Bedrock permissions re-enables global routing.
D=Interface endpoint in us-east-1: the endpoint changes only the network path into the source Region; Bedrock still routes a global profile request to other Regions behind it.
T: Block global cross-Region inference with an explicit Deny on bedrock:InvokeModel* where aws:RequestedRegion equals unspecified; Region-name lists do not catch it.
V: Amazon Bedrock, AWS IAM, AWS Lambda

@ DVA-C03 D2 T2.3 applied use-case
S: A team runs a containerized service on Amazon ECS that calls Amazon Bedrock over HTTPS with a third-party HTTP client that accepts only a bearer token, not SigV4 signing. The security team forbids IAM users and long-lived credentials, wants every token to expire within 12 hours, and wants the token's permissions to match the ECS task role. What should the developer do?
A: Create a long-term Amazon Bedrock API key with a one-day expiration in the console, store it in AWS Secrets Manager, and rotate it daily with a Lambda rotation function
B: Generate short-term Amazon Bedrock API keys in the service with the Bedrock token generator library from the task role credentials, and call it before each request
C: Create an IAM user with the AmazonBedrockLimitedAccess policy, issue it an access key pair, and exchange the key pair for a bearer token at container startup
D: Call AWS STS AssumeRole for the task role at startup and send the returned session token in the Authorization header as the Bedrock bearer token
K: B
G: ## Two kinds of Amazon Bedrock API keys
Amazon Bedrock API keys let a client authenticate with `Authorization: Bearer <key>` (or the `AWS_BEARER_TOKEN_BEDROCK` environment variable) instead of SigV4.
- **Short-term key**: generated from the credentials of an existing IAM principal, for example with the `aws-bedrock-token-generator` library (`provide_token()` in Python). It lasts up to 12 hours or the remaining session duration, whichever is shorter, can be used only in the Region where it was generated, and **inherits the permissions of the principal** that generated it.
- **Long-term key**: an IAM service-specific credential for `bedrock.amazonaws.com`. Creating one **creates or uses an IAM user** with attached policies, and it lasts until its configured expiration. AWS recommends long-term keys only for exploration and tells you to switch to short-term credentials for applications with greater security requirements.
## Refreshing in a long-running process
A token generated once at startup stops working when it expires. The Bedrock documentation notes that generating a token is inexpensive and can be done for each API call, so the generator always builds the key from the role's current, automatically refreshed credentials.
W: Short-term keys from the token generator: they are derived from the task role, carry exactly its permissions, expire within 12 hours, and involve no IAM user, which meets every requirement.
X: A=Long-term key in Secrets Manager: a long-term key is tied to an IAM user and is the long-lived credential type the team forbids; storing and rotating it does not change what it is.
C=IAM user access keys: an IAM user with permanent access keys breaks both rules, and Bedrock bearer tokens are not produced by trading an access key pair at startup.
D=STS session token as bearer: a session token is one part of a SigV4 credential set, not a Bedrock API key. Bedrock rejects it in the Authorization header.
T: For production, use short-term Bedrock API keys generated from an IAM role (up to 12 hours, same permissions as the role); long-term keys create IAM users and are for exploration only.
V: Amazon Bedrock, Amazon ECS, AWS IAM

@ DVA-C03 D2 T2.3 advanced troubleshooting
S: A developer accidentally pushed two Amazon Bedrock API keys to a public repository: a long-term key created for a test IAM user and a short-term key generated from the developer's assumed-role session, which is still valid for several hours. Both keys must stop working immediately without disrupting other Bedrock users in the account. Which actions should the developer take? (Select TWO)
A: Deactivate or delete the long-term key's service-specific credential on the IAM user with UpdateServiceSpecificCredential or DeleteServiceSpecificCredential
B: Rotate the test IAM user's access key pair, because the long-term API key is derived from that user's active access key and stops working once it is replaced
C: Attach a policy to the role that made the short-term key that denies the bedrock and bedrock-mantle CallWithBearerToken actions, or revoke its sessions
D: Generate a new short-term key from the same role, because generating a fresh token invalidates every earlier token that was issued for that role session
E: Disable model invocation logging and delete the CloudTrail trail so that the leaked key values are no longer stored in any log destination
K: A,C
G: ## How each key type is revoked
A **long-term** Bedrock API key is an IAM service-specific credential attached to an IAM user. It is independent of that user's access keys and is managed with its own APIs:
- `UpdateServiceSpecificCredential` with `Status=Inactive` disables it at once (reversible).
- `ResetServiceSpecificCredential` issues a new value; `DeleteServiceSpecificCredential` removes it.
A **short-term** key is a pre-signed value that inherits the credentials and expiration of the session that generated it; it cannot be deactivated, reset or deleted on its own. The documented ways to stop it early are:
- invalidate the session that generated it, with a Deny on `*` conditioned on `aws:TokenIssueTime` earlier than now;
- attach a policy to that identity denying `bedrock:CallWithBearerToken` **and** `bedrock-mantle:CallWithBearerToken` (the actions that control API key use on the `bedrock` and `bedrock-mantle` endpoints; denying only the first leaves the Mantle endpoint open).
The same Deny attached to the IAM user of a long-term key also blocks that key. These controls affect the whole session or identity, not just one key.
## Limiting blast radius
`bedrock:CallWithBearerToken` can be scoped with the condition key `bedrock:bearerTokenType` (`SHORT_TERM` or `LONG_TERM`), and `iam:CreateServiceSpecificCredential` with `iam:ServiceSpecificCredentialAgeDays` caps how long new long-term keys can live.
W: A=Deactivate or delete the service-specific credential: this is the documented revocation path for a long-term key and affects only that one credential.
C=Deny the CallWithBearerToken actions or revoke the sessions: a short-term key cannot be deleted, so blocking API key use on both Bedrock endpoints for that role, or invalidating the session it came from, cuts it off before expiry.
X: B=Rotate the user's access keys: a long-term API key is a separate service-specific credential, not derived from the access key pair, so it keeps working after rotation.
D=Generate a new short-term key: issuing a new token does not invalidate earlier ones; each stays valid until its own expiry.
E=Disable logging and delete the trail: removing logs does not revoke anything, so both keys keep working, and deleting audit trails destroys the evidence of how the leaked keys were used.
T: Revoke a long-term Bedrock API key through its service-specific credential; stop a short-term key by denying the CallWithBearerToken actions or invalidating the session it came from.
V: Amazon Bedrock, AWS IAM, AWS CloudTrail

@ DVA-C03 D2 T2.3 applied troubleshooting
S: A developer deploys an application to a new AWS account and calls a third-party foundation model on Amazon Bedrock for the first time with InvokeModel. The execution role allows bedrock:InvokeModel on the model ARN, the account has a valid payment method, and the model is supported in the Region. A few early calls succeed, then every call returns AccessDeniedException. What is the most likely fix?
A: Open the Model access page in the Amazon Bedrock console, submit an access request for the model, and wait for AWS to approve the request before retrying
B: Enable cross-Region inference for the model and call it through a geographic inference profile so that capacity in another Region is used for the request
C: Grant the role aws-marketplace:Subscribe, aws-marketplace:Unsubscribe and aws-marketplace:ViewSubscriptions, then invoke the model again from that role
D: Create an interface VPC endpoint for bedrock-runtime, because first-time access to third-party models is only allowed from traffic that stays within a VPC
K: C
G: ## Automatic model access
Access to many serverless foundation models on Amazon Bedrock is enabled by default, given the right AWS Marketplace permissions; there is no per-model access request to submit for them. For a **third-party** model, the first invocation in an account starts an AWS Marketplace subscription in the background:
- During setup (up to about 15 minutes) calls may succeed temporarily.
- If a prerequisite is missing, the subscription fails and later calls return `AccessDeniedException`.
## Prerequisites
- The principal that makes the first call needs `aws-marketplace:Subscribe`, `aws-marketplace:Unsubscribe` and `aws-marketplace:ViewSubscriptions`.
- The account needs a valid payment method for Marketplace purchases.
- Anthropic models also need the one-time first-time-use form (`PutUseCaseForModelAccess`).
After the missing permission is granted, the subscription can take up to 2 minutes to complete.
## Controlling access the other way
Because access is on by default, an organization that wants to review a model's license first blocks it with an SCP or IAM deny and lifts the deny after approval.
W: Marketplace permissions for the calling role: the pattern of a few successes followed by AccessDeniedException is a failed background subscription, and these three actions are the documented prerequisite the role is missing.
X: A=Manual model access request: access is enabled by default once the Marketplace prerequisites are met, so there is no approval queue to wait in; the failure comes from the subscription that the first invocation started.
B=Cross-Region inference profile: routing to more Regions adds capacity, but the account still has no Marketplace subscription, so every Region denies the call the same way.
D=Interface VPC endpoint: PrivateLink changes the network path only. Model access does not depend on whether the request arrives through a VPC endpoint.
T: First use of a third-party Bedrock model subscribes the account through AWS Marketplace; without aws-marketplace Subscribe/Unsubscribe/ViewSubscriptions on the caller, calls fail with AccessDeniedException.
V: Amazon Bedrock, AWS Marketplace, AWS IAM

@ DVA-C03 D2 T2.3 applied use-case
S: An AWS Lambda function in private subnets with no NAT gateway or internet gateway must call the Amazon Bedrock Converse API. The compliance team requires that prompt traffic never uses a public network path, and the developer does not want to change the SDK client configuration in code. What should the developer configure?
A: A gateway VPC endpoint for Amazon Bedrock added to the private subnets' route tables, with an endpoint policy that allows the bedrock:InvokeModel action for the function role
B: A NAT gateway in a public subnet with a route from the private subnets, and a security group on the function that allows outbound HTTPS only to Bedrock IP ranges
C: An interface VPC endpoint for com.amazonaws.region.bedrock, because that one endpoint serves the control plane and the runtime inference APIs together
D: An interface VPC endpoint for com.amazonaws.region.bedrock-runtime with private DNS enabled, and a security group that allows HTTPS from the function
K: D
G: ## Amazon Bedrock has several API endpoints
Bedrock splits its APIs across separate service endpoints, and each needs its own interface endpoint (AWS PrivateLink):
- `bedrock`: control plane (create guardrails, logging configuration, custom models).
- `bedrock-runtime`: inference (`InvokeModel`, `Converse`, `ApplyGuardrail`).
- `bedrock-agent` and `bedrock-agent-runtime`: Agents and Knowledge Bases.
- `bedrock-mantle`: the OpenAI-compatible Mantle endpoint.
An interface endpoint places elastic network interfaces with private IPs in your subnets. Traffic from the function to Bedrock then stays on the AWS network, with no internet gateway, NAT device or public IP.
## Private DNS
With **private DNS enabled**, the standard name `bedrock-runtime.<region>.amazonaws.com` resolves to the endpoint's private IPs inside the VPC, so the SDK needs no `endpoint_url` change. Without it, code must point at the `vpce-...` DNS name.
The endpoint's security group must allow inbound TCP 443 from the function's security group.
W: bedrock-runtime interface endpoint with private DNS: Converse is a runtime API, so this endpoint carries it privately, and private DNS lets the unchanged SDK resolve the default hostname to the endpoint.
X: A=Gateway endpoint: gateway endpoints exist only for Amazon S3 and DynamoDB. Bedrock is reached through interface endpoints (PrivateLink).
B=NAT gateway: a NAT gateway sends traffic out through an internet gateway to the public service endpoint, which is the path the compliance team rules out, and it also contradicts the no-NAT design.
C=bedrock control plane endpoint: the bedrock endpoint serves control plane APIs only. Converse calls go to bedrock-runtime and would still fail without a route.
T: Private inference calls to Amazon Bedrock need an interface endpoint for bedrock-runtime (separate from bedrock); enable private DNS to keep SDK code unchanged.
V: Amazon Bedrock, AWS PrivateLink, Amazon VPC, AWS Lambda

@ DVA-C03 D2 T2.3 advanced use-case
S: An application VPC reaches Amazon Bedrock through an interface endpoint for bedrock-runtime. Security wants to prevent data exfiltration: from this VPC only the application role in the company's account may run inference, and only against one approved inference profile and its model ARNs, even if someone brings credentials from another AWS account. What should the developer change?
A: Attach a custom endpoint policy that allows bedrock:InvokeModel only for the application role as principal and only on the approved inference profile and model ARNs
B: Restrict the endpoint security group to the application instances' security group, and remove every other inbound rule on port 443 from the endpoint's network interfaces
C: Add a resource-based policy to the approved foundation model that allows only the application role, and attach it to every Region the profile can use
D: Attach an identity policy to the application role that denies bedrock:InvokeModel on all other resources, and keep the endpoint's default full-access policy
K: A
G: ## Three layers decide whether a call through an endpoint succeeds
1. **Network**: the endpoint security group decides which IPs can open a connection. It cannot see who signed the request or which API is called.
2. **Endpoint policy**: a resource-based policy on the interface endpoint. Every request through the endpoint must be allowed by it. The default policy allows full access to the service.
3. **Identity policy** of the caller (and SCPs).
## Why the endpoint policy stops exfiltration
Identity policies only constrain principals in your account. Credentials from another account, used on a host in your VPC, are governed by that other account's policies, so your identity policy never applies. The endpoint policy applies to **every** request through the endpoint, regardless of whose credentials sign it. Example:
`{"Effect":"Allow","Principal":{"AWS":"arn:aws:iam::111122223333:role/app"},"Action":["bedrock:InvokeModel","bedrock:InvokeModelWithResponseStream"],"Resource":[<profile ARN>,<model ARNs>]}`
Anything not allowed here is refused at the endpoint.
W: Custom endpoint policy: it applies to all traffic through the endpoint, so foreign credentials, other actions and unapproved models are all denied, while the approved role and resources keep working.
X: B=Security group only: a security group filters by network source and port; a host already allowed to connect can still sign requests with another account's credentials for any model.
C=Resource policy on a foundation model: foundation models are AWS-owned resources and you cannot attach your own resource-based policy to them, so this control does not exist.
D=Identity deny with default endpoint policy: the deny constrains only this role. Credentials from another account bypass it, and the default endpoint policy lets them through.
T: Use a VPC endpoint policy to limit which principals, actions and Bedrock resources are reachable through the endpoint; identity policies alone cannot stop foreign credentials.
V: Amazon Bedrock, AWS PrivateLink, AWS IAM

@ DVA-C03 D2 T2.3 applied definition
S: A legal team reviewing a new customer-support feature asks the developer whether the third-party company that built the foundation model, called through Amazon Bedrock's bedrock-runtime endpoint, can read the customers' prompts and the model's responses. Which statement is accurate according to the Amazon Bedrock documentation?
A: Model providers can read prompts and responses for their own models unless the account sets a customer managed KMS key on every request it sends to Bedrock
B: Model providers can read prompts only when a cross-Region inference profile is used, because the request then leaves the AWS Region where the call was made
C: Models run in Bedrock-owned model deployment accounts that providers cannot access, so providers have no access to Bedrock logs or to prompts and completions
D: Model providers receive prompts and responses through model invocation logging, so the developer must keep invocation logging disabled to protect customers
K: C
G: ## Where a Bedrock model actually runs
For each model provider, in each Region, Amazon Bedrock uses a **model deployment account** that the Bedrock service team owns and operates. After a provider delivers a model, Bedrock makes a deep copy of the provider's inference software into that account. The provider has **no access** to these accounts, so it cannot see Bedrock logs or customer prompts and completions.
## Related controls a developer still owns
- Encryption in transit: Bedrock requires TLS 1.2 (TLS 1.3 recommended).
- Network path: interface endpoints (PrivateLink) keep calls off the internet.
- Model invocation logging is off by default; when enabled it writes to **your** CloudWatch Logs group or S3 bucket in your own account and Region.
- Some models require AWS (not the provider) to retain traffic for abuse detection; the data retention settings and the abuse detection page document which ones. Retained data is not shared with model providers.
W: Model deployment accounts: providers have no access to the accounts where their models run, which is why they cannot see prompts, completions or Bedrock logs.
X: A=Customer managed key per request: Bedrock has no per-request KMS setting for inference, and provider isolation does not depend on one; it comes from the deployment account design.
B=Only with cross-Region inference: cross-Region routing sends the request to another AWS Region's Bedrock deployment, still inside AWS and still outside any provider's reach.
D=Providers read invocation logs: invocation logs are delivered only to destinations in your own account and Region; disabling them has nothing to do with provider access.
T: Bedrock runs each provider's model in a Bedrock-owned deployment account that the provider cannot access, so providers never see your prompts, completions or logs.

@ DVA-C03 D2 T2.3 applied use-case
S: A developer creates an Amazon Bedrock guardrail whose denied topics and blocked messages contain confidential product codenames. Security requires that the guardrail configuration be encrypted with a customer managed AWS KMS key that the security team controls and audits. The developer's role creates the guardrail, and an application role uses it on Converse calls. What should the developer do?
A: Keep the guardrail's default AWS-provided encryption, and let the security team audit guardrail use through the CloudTrail events for each Converse call
B: Set kmsKeyId on CreateGuardrail to the customer managed key, allow the creator role Decrypt, GenerateDataKey, DescribeKey and CreateGrant, and the app role Decrypt
C: Pass the customer managed key ARN in the guardrailConfig of every Converse request, so that Bedrock decrypts the guardrail definition with that key at inference time
D: Turn on SSE-KMS with the customer managed key on the S3 bucket that receives model invocation logs, since Bedrock stores guardrail definitions alongside those logs
K: B
G: ## Encrypting Amazon Bedrock resources with your own key
By default Bedrock encrypts a guardrail with a key that AWS provides and controls. To meet a "we control the key" requirement you supply a **customer managed key** when you create the resource, for example:
- Guardrails: `kmsKeyId` on `CreateGuardrail`.
- Model customization jobs and custom models: `customModelKmsKeyId`.
- Agents: `customerEncryptionKeyArn`.
- Knowledge base data source ingestion: `kmsKeyArn`.
## Key policy for a guardrail
The Bedrock documentation gives two sets of permissions:
- **Creators** (create or update the guardrail): `kms:Decrypt`, `kms:GenerateDataKey`, `kms:DescribeKey`, `kms:CreateGrant`.
- **Users** (call inference with the guardrail): `kms:Decrypt`.
Every use of the key appears in CloudTrail, and disabling the key cuts off use of the encrypted resource, which gives the security team both control and an audit trail.
W: kmsKeyId on CreateGuardrail with the documented grants: the guardrail is encrypted with the security team's key, the creator can write it, the application can decrypt it at inference, and every key use is logged.
X: A=Default encryption with CloudTrail auditing: the security team can see the calls but does not own the key, cannot change its policy and cannot disable it, so the customer-controlled key requirement is not met.
C=Key in guardrailConfig: guardrailConfig carries only the guardrail identifier, version and trace setting; encryption is fixed when the guardrail is created, not chosen per request.
D=SSE-KMS on the logging bucket: guardrail definitions are stored by Bedrock, not in your invocation log bucket, so encrypting that bucket leaves the guardrail on the default key.
T: Encrypt Bedrock resources with a customer managed key at creation time (kmsKeyId for guardrails) and grant creators Decrypt, GenerateDataKey, DescribeKey and CreateGrant, and users Decrypt.

@ DVA-C03 D2 T2.3 applied use-case
S: A developer has created and published version 2 of an Amazon Bedrock guardrail with content filters and denied topics, all set to block. A chat application calls the Converse API from AWS Lambda. The developer must apply the guardrail to both the user's message and the model's response and must show a friendly message whenever the guardrail intervenes. Which code change should the developer make?
A: Pass guardrailConfig with guardrailIdentifier, guardrailVersion 2 and trace enabled on each Converse call, and check whether stopReason is guardrail_intervened
B: Put the guardrail ARN and version in additionalModelRequestFields on each Converse call, and check whether the response body includes a guardrailAction key
C: Associate the guardrail with the Lambda execution role by tagging the role with the guardrail ID, so that every Bedrock call from the role is evaluated
D: Wrap the user message in amazon-bedrock-guardrails-guardContent XML tags inside the text block, and parse those tags out of the model response on return
K: A
G: ## Attaching a guardrail to an inference call
A guardrail is not attached to a model or an IAM role; the application names it on each request. (Central teams can also enforce a guardrail for a whole account or organization, which then applies in addition.)
- **Converse / ConverseStream**: the `guardrailConfig` parameter holds `guardrailIdentifier` (ID or ARN), `guardrailVersion` (a number or `DRAFT`) and optionally `trace` (`enabled`).
- **InvokeModel**: the same values go in request headers (`X-Amzn-Bedrock-GuardrailIdentifier`, `X-Amzn-Bedrock-GuardrailVersion`, `X-Amzn-Bedrock-Trace`).
The guardrail evaluates the input before the model runs and the output before it is returned.
## Reading the result
When the guardrail intervenes on a Converse call:
- `stopReason` is `guardrail_intervened`.
- The output message contains the blocked message configured in the guardrail.
- Careful: a sensitive information filter that masks (anonymizes) also sets `guardrail_intervened`, even though the masked answer is usable; with masking filters, read the trace to tell a block from a mask.
- With trace enabled, `trace.guardrail` shows which policy acted.
In Converse, `guardContent` content blocks can limit the evaluation to selected parts of a message; XML input tags are only for InvokeModel.
W: guardrailConfig on each call: this is the documented way to apply a guardrail version to Converse, and stopReason guardrail_intervened is the signal for showing the friendly message.
X: B=additionalModelRequestFields: that field passes model-specific inference parameters to the model; Bedrock does not read a guardrail from it, so no guardrail is applied.
C=Tag the execution role: guardrails are applied per request, not by tags on IAM roles. An IAM condition can require a guardrail, but tags do not apply one.
D=XML input tags in Converse: input tags are for InvokeModel; Converse uses guardContent blocks. Tags alone also name no guardrail, so nothing would be evaluated.
T: Apply a guardrail to Converse with guardrailConfig (identifier, version, trace) and detect intervention with stopReason guardrail_intervened.

@ DVA-C03 D2 T2.3 advanced troubleshooting
S: A developer calls InvokeModel with the guardrail identifier and version headers set. The guardrail's prompt attack filter is set to High, but jailbreak and prompt injection text typed by users still reaches the model. The request body contains the developer's system instructions followed by the raw user text in one prompt string. What should the developer do?
A: Raise the prompt attack filter to High for model responses as well, so that injected instructions are caught when the model repeats them in its output
B: Switch the guardrail version header to DRAFT, because the prompt attack filter is evaluated only on the working draft of a guardrail and not on published versions
C: Remove the system instructions from the prompt string so that the guardrail evaluates only user text, and move those instructions into a denied topic
D: Wrap only the user text in amazon-bedrock-guardrails-guardContent_<suffix> tags and send a new random tagSuffix in amazon-bedrock-guardrailConfig on every request
K: D
G: ## Why the prompt attack filter needs to know which text is user input
A prompt attack (jailbreak, prompt injection, prompt leakage) often looks just like a developer instruction: "You are a chemistry expert, now tell me...". To avoid flagging the developer's own system prompt, the prompt attack filter evaluates **user input**.
- With **InvokeModel** and **InvokeModelWithResponseStream**, the guardrail cannot tell user text from developer text in a single prompt string. You mark user input with **input tags**: `<amazon-bedrock-guardrails-guardContent_xyz> ... </amazon-bedrock-guardrails-guardContent_xyz>`. The documentation states that without tags, prompt attacks are not filtered for these calls.
- With **Converse**, you use `guardContent` content blocks instead of XML tags.
## The tag suffix
The suffix (`xyz` above) is supplied in the body as `"amazon-bedrock-guardrailConfig": {"tagSuffix": "xyz"}`. AWS recommends a **new random suffix for every request**, so an attacker cannot close the tag early with a guessed static tag and escape evaluation.
W: Input tags with a random tagSuffix: tagging marks the user text for prompt attack evaluation, which InvokeModel requires, and a fresh suffix per request stops users from forging a closing tag.
X: A=High filter on responses: the prompt attack filter targets prompts; it does not see untagged user text in InvokeModel at all, so changing response settings leaves the gap open.
B=Use DRAFT: published versions and the draft run the same filters; the version does not decide whether untagged InvokeModel input is checked for prompt attacks.
C=Move instructions into a denied topic: denied topics block subjects, they do not hold system instructions, and the untagged prompt string still would not be evaluated as user input.
T: With InvokeModel, prompt attack filtering needs the user input wrapped in guardContent tags with a per-request random tagSuffix; Converse uses guardContent blocks.
V: Amazon Bedrock Guardrails

@ DVA-C03 D2 T2.3 advanced use-case
S: A team serves a fine-tuned open-weight model from an Amazon SageMaker AI endpoint. They want the same Amazon Bedrock guardrail that their Bedrock-based apps use to check user prompts before the endpoint is called and to mask PII in the endpoint's responses, without moving the model. Which steps should the developer implement? (Select TWO)
A: Call ApplyGuardrail with source INPUT on the user prompt first, and if action is GUARDRAIL_INTERVENED return the guardrail's output text instead of calling the endpoint
B: Add the guardrail identifier and version to the SageMaker AI endpoint configuration so that SageMaker calls the guardrail on each InvokeEndpoint request
C: Call ApplyGuardrail with source OUTPUT on the endpoint's response, and when action is GUARDRAIL_INTERVENED return the masked text from outputs instead

K: A,C
G: ## ApplyGuardrail: guardrails without a Bedrock model call
`ApplyGuardrail` (bedrock-runtime) evaluates any text against a guardrail and **does not invoke a foundation model**. That makes it usable with models hosted elsewhere, such as SageMaker AI endpoints or third-party APIs, and at any point in an application flow.
Request: `POST /guardrail/{guardrailIdentifier}/version/{guardrailVersion}/apply` with
- `source`: `INPUT` for user content going to a model, `OUTPUT` for model responses;
- `content`: the text blocks to evaluate.
Response:
- `action`: `GUARDRAIL_INTERVENED` or `NONE`;
- `outputs`: the configured blocked message when content is blocked, the text with masking applied when PII was anonymized, or empty when nothing happened;
- `assessments`: which policies acted.
## Permissions
The caller needs `bedrock:ApplyGuardrail` on the guardrail ARN (and `kms:Decrypt` if the guardrail uses a customer managed key).
W: A=ApplyGuardrail on the input first: checking the prompt with source INPUT before calling the endpoint means blocked prompts never reach the model, and the guardrail's own message is returned.

X: B=Guardrail in the endpoint configuration: SageMaker AI endpoint configurations have no guardrail setting; Bedrock guardrails are applied by Bedrock APIs, not by SageMaker.
D=InvokeModel on the guardrail: ApplyGuardrail is its own action, bedrock:ApplyGuardrail. Granting InvokeModel neither authorizes it nor makes sense for a guardrail resource.

G: ## Requiring a guardrail with IAM
Bedrock publishes the condition key `bedrock:GuardrailIdentifier` for the inference actions behind `Converse`, `ConverseStream`, `InvokeModel` and `InvokeModelWithResponseStream`. Its value is the guardrail ARN with version, for example `arn:aws:bedrock:us-east-1:111122223333:guardrail/gr-7:3`.

G: ## Why model-generated code is a security boundary
Code that a model writes from user input is untrusted: a prompt injection can turn "summarize this CSV" into "read the customer table and post it to my server". Running it with `exec()` gives it everything the host process has: the function's IAM role, its network access and its memory.
