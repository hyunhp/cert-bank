@ DVA-C03 D3 T3.1 applied use-case
S: A Java service is packaged with a single-stage Dockerfile that starts FROM a Maven and JDK image, copies the whole repository, and runs mvn package. The image is 900 MB because it contains Maven, the JDK, the source code and the local dependency cache, and every source-only change downloads all dependencies again, taking 5 minutes. Which Dockerfile change makes the runtime image small and lets source-only changes reuse the downloaded dependencies?
A: Keep one stage, run mvn package, and then add a later RUN instruction that deletes the ~/.m2 cache, the source and the JDK tools to cut the size
B: Use a build stage that copies pom.xml and resolves dependencies before copying src, then a final JRE-only stage that copies just the built JAR
C: Keep one stage but copy the whole repository first and run dependency download and packaging in one RUN instruction with --no-cache set
D: Keep one stage but switch the base to a JRE-only image and install Maven with the OS package manager in a RUN instruction before packaging
K: B
G: ## Image layers and the build cache
Each Dockerfile instruction such as `RUN`, `COPY` or `ADD` creates a **layer**. Two rules follow from that:
- **Layers only add.** If one `RUN` writes 400 MB and a later `RUN rm -rf` deletes it, the image still carries the 400 MB in the earlier layer; the deletion only hides the files.
- **Cache reuse stops at the first change.** Docker reuses a cached layer only while the instruction and its inputs are unchanged. Once one layer is rebuilt (for example `COPY . .` after any source edit), every later instruction runs again.
So put slow, rarely changing steps first: copy only the dependency manifest (`pom.xml`, `package.json`, `requirements.txt`), download dependencies, and only then copy the source.
## Multi-stage builds
A Dockerfile can have several `FROM` lines. Each starts a new stage, and only the **last** stage becomes the image you push. Earlier stages are build scratch space:
- `FROM maven:3-eclipse-temurin-21 AS build` then `COPY pom.xml .`, `RUN mvn dependency:go-offline`, `COPY src ./src`, `RUN mvn package`
- `FROM eclipse-temurin:21-jre` then `COPY --from=build /app/target/app.jar /app/app.jar`
The final image holds a JRE and one JAR, often a few hundred MB smaller, and contains no compiler or source that an attacker could use.
W: Multi-stage build with dependencies resolved first: the dependency layer is reused whenever pom.xml is unchanged, so source edits rebuild only the compile step, and the final stage ships just a JRE and the JAR without Maven, the JDK, the source or the cache.
X: A=Delete in a later layer: the files removed by the later RUN still exist in the earlier layers, so the pushed image stays about the same size, and the dependency cache is still rebuilt on every source change.
C=Copy everything first with no cache: any source change invalidates the COPY layer and everything after it, and --no-cache disables reuse completely, so builds become slower, and the JDK and Maven remain in the image.
D=JRE base plus Maven in one stage: Maven, its downloaded dependencies and the source still end up in the shipped layers, and with no dependency-first COPY the 5-minute download still repeats on every edit.
T: Copy dependency manifests before source to keep the cache warm, and use a multi-stage build so the final image contains only the runtime and the built artifact.
V: Docker, Amazon ECR

@ DVA-C03 D3 T3.1 applied troubleshooting
S: An AWS CodeBuild project builds a container image successfully, but the post_build command docker push 123456789012.dkr.ecr.us-east-1.amazonaws.com/orders:$CODEBUILD_RESOLVED_SOURCE_VERSION fails with "no basic auth credentials". The project's service role has only the default CloudWatch Logs and S3 permissions that CodeBuild created. Which TWO changes allow the push without storing long-term credentials? (Select TWO)
A: Add a pre_build command that pipes aws ecr get-login-password into docker login with the username AWS and the registry URI of the account and Region
B: Add an ECR repository policy that allows the codebuild.amazonaws.com service principal to call ecr:BatchGetImage and ecr:GetDownloadUrlForLayer
C: Grant the service role ecr:GetAuthorizationToken plus the layer upload actions and ecr:PutImage on the orders repository in its IAM policy
D: Store an IAM user's access key ID and secret access key as plaintext environment variables of the project so Docker can sign the push
E: Enable the local Docker layer cache mode for the project so that the image layers are uploaded to ECR from the cache of the build host
K: A,C
G: ## How Docker authenticates to Amazon ECR
Docker does not understand IAM. It speaks the registry protocol and needs a username and password for the registry host (`<account>.dkr.ecr.<region>.amazonaws.com`). ECR bridges the two worlds:
- `aws ecr get-login-password --region us-east-1` calls **`ecr:GetAuthorizationToken`** with the caller's IAM credentials and returns a token that is valid for 12 hours.
- `docker login --username AWS --password-stdin <registry>` stores that token for the registry. Without this step Docker has no credentials at all, which is the "no basic auth credentials" error.
## What the role must allow for a push
After login, every request is still authorized against the IAM identity that obtained the token. A push needs:
- `ecr:GetAuthorizationToken` (resource `*`)
- on the repository: `ecr:BatchCheckLayerAvailability`, `ecr:InitiateLayerUpload`, `ecr:UploadLayerPart`, `ecr:CompleteLayerUpload`, `ecr:PutImage`
The AWS managed policy `AmazonEC2ContainerRegistryPowerUser` covers this, but a policy scoped to one repository is better practice.
## Typical buildspec
- `pre_build`: `aws ecr get-login-password ... | docker login --username AWS --password-stdin $REGISTRY`
- `build`: `docker build -t $REGISTRY/orders:$TAG .`
- `post_build`: `docker push $REGISTRY/orders:$TAG`
W: A=Log in with get-login-password: Docker needs a registry credential, and piping the ECR token into docker login provides one that is derived from the service role and expires after 12 hours.
C=Push permissions on the role: the token and every layer upload are authorized against the service role, so it needs GetAuthorizationToken plus the upload actions and PutImage on the repository, or the push fails with access denied after login.
X: B=Repository policy for the CodeBuild principal: that pattern lets CodeBuild itself pull a custom build environment image; it grants only pull actions and does nothing for docker commands that run inside the build with the service role.
D=Access keys in environment variables: this is exactly the long-term credential the requirement rules out, plaintext variables are visible in the project configuration, and Docker still needs a docker login step to use them.
E=Local Docker layer cache: the cache keeps layers on the build host to speed up later builds; it does not authenticate Docker to ECR or upload anything by itself.
T: To push to ECR from CodeBuild, log Docker in with aws ecr get-login-password and give the service role GetAuthorizationToken plus the repository's push actions.

@ DVA-C03 D3 T3.1 advanced troubleshooting
S: An Amazon ECR repository stores images tagged with the Git commit SHA. The pipeline also moves a staging tag to whichever image is currently deployed in the staging environment. After the security team set the repository's tag mutability to IMMUTABLE, the pipeline step that pushes the staging tag fails with ImageTagAlreadyExistsException. Commit SHA tags must never be overwritten, and the staging tag must keep moving. What is the simplest fix?
A: Keep IMMUTABLE and add a lifecycle policy rule for the staging tag with sinceImagePushed of 1 day, so the old tag is gone before the next push
B: Change the repository to IMMUTABLE_WITH_EXCLUSION with a wildcard exclusion filter for staging, so that only the staging tag stays mutable
C: Change the repository back to MUTABLE and rely on commit SHAs being unique, so no pipeline run ever pushes the same SHA tag a second time
D: Keep IMMUTABLE and push the staging tag with the docker push --force option, which overrides ECR tag immutability for that single tag
K: B
G: ## Tag mutability in Amazon ECR
A tag is a movable pointer to an image digest (`sha256:...`). With the default **MUTABLE** setting, pushing an existing tag simply repoints it. With **IMMUTABLE**, ECR rejects any push that would repoint an existing tag and returns `ImageTagAlreadyExistsException`. That protects release tags: once `orders:3f2a9c1` is deployed, nobody can silently replace what it means.
## Exclusion filters
Many pipelines need both kinds of tags: immutable version tags plus a few moving environment tags such as `latest`, `staging` or `prod`. ECR supports this with two extra settings:
- `IMMUTABLE_WITH_EXCLUSION`: all tags are immutable **except** those that match the exclusion filters (wildcards allowed).
- `MUTABLE_WITH_EXCLUSION`: all tags are mutable except the ones that match the filters.
Example: `aws ecr put-image-tag-mutability --repository-name orders --image-tag-mutability IMMUTABLE_WITH_EXCLUSION --image-tag-mutability-exclusion-filters filterType=WILDCARD,filter=staging`
The enforcement is server-side in ECR, so no client flag can bypass it.
W: Immutable with an exclusion for staging: ECR keeps every commit SHA tag immutable, while pushes of the staging tag are allowed to repoint it, so the pipeline works again without weakening the release guarantee.
X: A=Lifecycle rule to drop the tag: lifecycle rules run asynchronously within 24 hours rather than at push time, and an expire action deletes the whole image, including its commit SHA tag, not just the staging pointer.
C=Back to MUTABLE: uniqueness of SHAs prevents accidental reuse by the pipeline, but nothing stops a person or another job from overwriting a SHA tag, so the "must never be overwritten" control is lost.
D=docker push --force: Docker has no such option, and immutability is enforced by the registry on the server side, so a client flag could not override it anyway.
T: When most tags must be immutable but a few environment tags must move, use ECR IMMUTABLE_WITH_EXCLUSION with filters for the moving tags.

@ DVA-C03 D3 T3.1 applied use-case
S: An Amazon ECR repository receives about 50 images a day. Requirements: delete untagged images 3 days after they are pushed, keep only the 20 newest images whose tags start with dev-, and never delete images whose tags start with release-. Which lifecycle policy meets these requirements?
A: Rule 1: tagStatus any with imageCountMoreThan 20 and action expire. Rule 2: tagStatus tagged with tagPatternList release-* and action expire after 3 days
B: Rule 1: tagStatus tagged with tagPatternList release-* and a retain action. Rule 2: tagStatus any with sinceImagePushed 3 days and action expire
C: Rule 1: tagStatus untagged with sinceImagePushed 3 days and action expire. Rule 2: tagStatus tagged with tagPatternList dev-* and imageCountMoreThan 20, expire
D: Rule 1: tagStatus untagged with tagPatternList dev-* and imageCountMoreThan 20, expire. Rule 2: tagStatus tagged with release-* and sinceImagePushed 3 days
K: C
G: ## Anatomy of an ECR lifecycle rule
A lifecycle policy is a JSON list of rules. Each rule has:
- `rulePriority`: unique integer; lower numbers are applied first.
- `selection.tagStatus`: `untagged`, `tagged` (then `tagPatternList` or `tagPrefixList` is required) or `any`. A rule with `untagged` must not have a tag list. A rule with `any` must have the highest priority number, so it is evaluated last.
- `selection.countType`: `imageCountMoreThan` (keep the newest N, act on the rest) or `sinceImagePushed` with `countUnit: days` (act on images older than N days). Newer count types such as `sinceImagePulled` work with archiving.
- `action.type`: `expire` (delete) or `transition` (move to the archive storage class). There is no "retain" action.
## How rules combine
All rules are evaluated, then applied by priority; each image is acted on by at most one rule. Anything that no rule selects is **kept**. So the way to protect release images is simply not to select them: no `any` rule that could catch them, and no rule that names `release-*`.
Example for this case: priority 1 `untagged` + `sinceImagePushed` 3 days, priority 2 `tagged` + `tagPatternList: ["dev-*"]` + `imageCountMoreThan` 20, both `expire`. Use the lifecycle policy preview before applying; expirations happen within 24 hours of an image meeting the criteria.
W: Untagged by age, dev-* by count, release-* untouched: the first rule removes untagged images after 3 days, the second keeps only the 20 newest dev- images, and because no rule selects release- tags, those images are never expired.
X: A=An any rule keeping 20 images: tagStatus any selects every image, including release- images, so all but the newest 20 images of any kind would be deleted, and the second rule actively expires release images.
B=Retain action plus an any rule: ECR lifecycle rules support only expire and transition actions, and the any rule with 3 days would delete release- and dev- images older than 3 days as well.
D=Untagged rule with a tag list: a rule with tagStatus untagged must not include a tagPatternList, so this policy is invalid, and the second rule would delete release- images after 3 days.
T: ECR lifecycle rules only expire or archive what they select; protect images by never selecting them, and keep tagStatus any as the last rule if you use it at all.
V: Amazon ECR

@ DVA-C03 D3 T3.1 applied use-case
S: A team runs Python services from images in Amazon ECR and uses basic scanning with scan on push. Last week a critical CVE was published for a pip library that is baked into images pushed months ago that are still running. Nobody was alerted. The team wants automatic findings for both OS and programming language packages, re-evaluated when new CVEs appear, with a notification to an SNS topic. What should the developer configure?
A: Keep basic scanning and add a scheduled Lambda function that calls StartImageScan for every image each day, sending any findings to the SNS topic
B: Keep basic scanning and change the registry scan on push filter to a wildcard so every repository is scanned, then email the scan results to the team
C: Switch the registry to enhanced scanning with continuous scan, and add an EventBridge rule for Amazon Inspector findings that targets the SNS topic
D: Enable image signing with AWS Signer and an ECS policy that blocks unsigned images, which stops images with known CVEs from being deployed

G: ## Two scanning types in Amazon ECR
Scanning is configured at the **private registry** level, with repository filters.
- **Basic scanning** uses AWS native technology to find CVEs in **operating system packages**. Frequencies: scan on push or manual. Each image can be scanned once per 24 hours, and results are a point-in-time snapshot: an image scanned in March does not get a new finding when a CVE is published in June unless someone scans it again.
- **Enhanced scanning** integrates with **Amazon Inspector**. It finds vulnerabilities in OS packages **and programming language packages** (for example pip, npm, Maven). Frequencies: scan on push or **continuous scan**. With continuous scan, Inspector re-evaluates images in scope whenever new vulnerability information arrives and updates findings automatically.
## Getting alerts
Inspector publishes finding events to Amazon EventBridge. A rule such as source `aws.inspector2`, detail-type `Inspector2 Finding`, filtered by severity, can target an SNS topic, a Lambda function or a ticketing integration. ECR also sends `ECR Image Scan` events for basic scans.
W: Enhanced continuous scanning with an EventBridge rule: Amazon Inspector covers the pip library as a language package, re-scores existing images automatically when new CVEs are published, and its finding events can be routed to the SNS topic without custom code.
X: A=Daily manual scans: basic scanning examines operating system packages only, so the vulnerable pip library would still not be reported, and the team must build and maintain the scheduling and notification code.
B=Wildcard scan on push: this only widens which repositories are scanned at push time; images pushed months ago are not rescanned, and language packages are still out of scope for basic scanning.
D=Image signing with AWS Signer: signing proves who built an image and that it was not altered, but it says nothing about vulnerabilities inside a correctly signed image, so the CVE would still go unnoticed.
T: For language-package CVEs and alerts on images already in ECR, use enhanced scanning (Amazon Inspector) with continuous scan and route its findings through EventBridge.

@ DVA-C03 D3 T3.3 applied use-case
S: An Amazon ECS service on AWS Fargate has a desired count of 6 tasks and uses the rolling update deployment type. During deployments the service must never have fewer than 6 healthy tasks, and to stay within the account's vCPU quota it must never run more than 3 extra tasks at a time. Which deployment configuration meets these requirements?
A: minimumHealthyPercent 50 and maximumPercent 150
B: minimumHealthyPercent 100 and maximumPercent 100
C: minimumHealthyPercent 100 and maximumPercent 200
D: minimumHealthyPercent 100 and maximumPercent 150
K: D
G: ## Two numbers control an ECS rolling update
Both values are percentages of the service's **desired count**:
- `minimumHealthyPercent` is the floor: how many tasks must stay running and healthy. It is **rounded up**. With desired 4 and 50%, ECS may stop 2 old tasks before starting new ones.
- `maximumPercent` is the ceiling: how many tasks (old plus new) may run at once. It is **rounded down**. With desired 4 and 200%, ECS may start 4 new tasks before stopping any old ones.
The gap between the two is the room ECS has to work in. If floor and ceiling are both equal to the desired count, ECS can neither start an extra task nor stop an old one, and the deployment cannot make progress; ECS reports a service event saying it was unable to stop or start tasks because of the deployment configuration.
## Worked example for desired count 6
- 100 / 150: floor 6, ceiling 9. ECS starts up to 3 new tasks, waits until they are healthy, stops 3 old ones, and repeats.
- 50 / 150: floor 3. Capacity may drop by half.
- 100 / 200: ceiling 12, so up to 6 extra tasks run at once.
Defaults for a rolling update service are 100 and 200. Deployment failure detection (circuit breaker, CloudWatch alarms) is configured separately.
W: 100 and 150: the floor is 6 healthy tasks, so capacity never drops, and the ceiling is 9 tasks, so at most 3 new tasks run beside the old ones in each step.
X: A=50 and 150: the ceiling is right, but a 50 percent floor lets ECS stop 3 old tasks before replacements are healthy, which breaks the never fewer than 6 rule.
B=100 and 100: floor and ceiling both equal 6, so ECS can neither start an extra task nor stop an old one, and the deployment stalls with a service event about the deployment configuration.
C=100 and 200: capacity never drops, but the ceiling is 12 tasks, so ECS may launch 6 extra tasks at once and exceed the vCPU headroom the team has.
T: minimumHealthyPercent sets the rounded-up floor and maximumPercent the rounded-down ceiling of tasks during an ECS rolling update; the gap between them is the batch size.
V: Amazon ECS, AWS Fargate

@ DVA-C03 D3 T3.3 advanced troubleshooting
S: An Amazon ECS service on Fargate uses a task definition whose image is 123456789012.dkr.ecr.us-east-1.amazonaws.com/orders:stable. A developer pushed a fixed image and moved the stable tag to it. An hour later, tasks that service auto scaling launched in the meantime still run the old code. No one changed the service or the task definition. What explains this, and what is the fix?
A: Fargate keeps pulled images on its hosts for 24 hours; set ECS_IMAGE_PULL_BEHAVIOR to always in the task's environment to force fresh pulls
B: ECR serves the previous manifest of a moved tag for a while; wait for the tag change to propagate, or push the image again under the stable tag
C: ECS resolved stable to an image digest at the last deployment and uses that digest for all tasks; start a new deployment of the service
D: Auto scaling launches tasks from the first ACTIVE revision of the family; deregister the older revisions so that the service uses the newest one
K: C
G: ## Tags move, digests do not
An image tag such as `orders:stable` is a pointer that can be moved. The **digest** (`sha256:...`) identifies exact image content and never changes.
## Software version consistency in ECS
By default, when a service deployment starts, Amazon ECS **resolves each container's image tag to a digest**: the first task of the deployment establishes the digest, and ECS then uses that digest for every other task of the deployment and for later tasks such as scale-out or replacement of failed tasks. All tasks in a service therefore run identical images, even if someone moves the tag later.
Consequences:
- Moving a tag in ECR does **not** change what a running service starts.
- To pick up the new image under the same tag, start a new deployment (`aws ecs update-service --force-new-deployment`), which resolves the tag again.
- Better practice is a unique tag (or digest) per build and a new task definition revision per release, so every deployment is explicit and easy to roll back.
The behavior can be configured per container with the `versionConsistency` parameter in the container definition.
W: Digest pinned at deployment: ECS resolved stable to the old digest when the service was last deployed and keeps using it for new tasks, so a new deployment (force new deployment, or a new revision with a unique tag) is what makes the service resolve the moved tag.
X: A=Fargate image cache and pull behavior: ECS_IMAGE_PULL_BEHAVIOR is an ECS agent setting for EC2 container instances, not a task variable on Fargate, and no host cache explains new tasks getting the old image an hour later.
B=Tag propagation delay in ECR: a tag move is effective for new pulls right away, and pushing the same image again does not change what the service starts, because ECS is not resolving the tag for these tasks at all.
D=First ACTIVE revision: the service runs the exact revision it was last updated with, not the first or newest one of the family, and deregistering revisions does not change a running service.
T: ECS pins image tags to digests at each deployment, so moving a tag changes nothing until you start a new deployment; prefer unique tags per build.
V: Amazon ECS, AWS Fargate, Amazon ECR

@ DVA-C03 D3 T3.3 applied troubleshooting
S: A team moves an ECS service from the EC2 launch type to Fargate. The task definition uses the bridge network mode, sets cpu 256 and memory 512 only in the container definition, and maps containerPort 8080 to hostPort 0. It already has a task execution role for ECR pulls and logs. Registering it with requiresCompatibilities FARGATE fails validation. Which TWO changes are required? (Select TWO)
A: Set the network mode to awsvpc, and set hostPort to 8080 or remove it so that it matches the container port of the application
B: Keep the bridge network mode and add a placement constraint that restricts the tasks to Fargate capacity in the cluster's subnets
C: Add task-level cpu and memory values, such as 256 CPU units and 512 MiB, which form a valid Fargate task size combination
D: Set privileged to true on the container so that Fargate is allowed to map dynamic host ports on the shared host network
E: Switch the network mode to host so that the container binds port 8080 directly on the Fargate host without a port mapping
K: A,C
G: ## What Fargate requires in a task definition
On Fargate there is no container instance you manage, so several EC2-launch-type options do not apply:
- **Network mode must be `awsvpc`.** Each task gets its own elastic network interface and private IP in your subnets, with security groups on the task. In `awsvpc` mode `hostPort` must equal `containerPort` or be omitted; dynamic host ports (`hostPort: 0`) are a `bridge` mode feature.
- **Task-level CPU and memory are required**, and they must be one of the supported combinations (for example 256 CPU units with 512 MiB, 1 GB or 2 GB). Container-level values are optional limits within the task size.
- Parameters that are not valid on Fargate include `privileged`, `links`, `placementConstraints`, `dnsServers`, `extraHosts`, `ipcMode` and others.
- A **task execution role** lets the Fargate agent pull private ECR images, fetch secrets and send logs with the `awslogs` driver.
Example: `"networkMode": "awsvpc", "requiresCompatibilities": ["FARGATE"], "cpu": "256", "memory": "512"`, container `portMappings: [{"containerPort": 8080}]`.
W: A=awsvpc with matching ports: Fargate tasks only use the awsvpc network mode, where each task has its own IP address, so the port mapping must use 8080 for both values or omit hostPort.
C=Task-level CPU and memory: Fargate sizes and bills each task by its task-level CPU and memory, so the task definition must declare a supported combination such as 256 units and 512 MiB at the task level.
X: B=Bridge mode with a placement constraint: bridge mode is not supported on Fargate, and placementConstraints is one of the task definition parameters that Fargate rejects.
D=Privileged container: privileged is not a valid parameter on Fargate, and privilege has nothing to do with port mapping; dynamic host ports exist only in bridge mode on EC2 instances.
E=Host network mode: Fargate does not support host mode; there is no shared host network you can bind to, so awsvpc is the only valid choice.
T: A Fargate task definition needs the awsvpc network mode with hostPort equal to containerPort (or omitted) and a valid task-level CPU and memory combination.

@ DVA-C03 D3 T3.3 applied use-case
S: A Kubernetes Deployment on Amazon EKS runs 10 replicas of an API, and each pod has a readiness probe. A namespace ResourceQuota leaves room for only 2 additional pods. During every rollout, the service must keep at least 10 ready pods. Which update strategy in the Deployment manifest meets these requirements?
A: RollingUpdate with maxSurge 0 and maxUnavailable 2
B: RollingUpdate with maxSurge 2 and maxUnavailable 0
C: RollingUpdate with the default maxSurge and maxUnavailable
D: Recreate, with progressDeadlineSeconds set to 120
K: B
G: ## How a Deployment rolls out
A Deployment manages ReplicaSets. When you change the pod template (for example the image tag), Kubernetes creates a new ReplicaSet and shifts pods from the old one to the new one according to `spec.strategy`:
- `type: Recreate` deletes all old pods first, then creates new ones. There is a gap with no pods.
- `type: RollingUpdate` (default) replaces pods gradually within two limits:
  - `maxSurge`: how many pods may exist **above** `replicas` (number or percentage, percentages round **up**).
  - `maxUnavailable`: how many pods may be **missing** from `replicas` (percentages round **down**). Both cannot be 0.
A new pod counts as available only when its **readiness probe** succeeds, so the rollout waits for real readiness before it removes old pods.
## Example
`replicas: 10`, `maxSurge: 2`, `maxUnavailable: 0`: Kubernetes creates 2 new pods (12 total), waits until they are Ready, terminates 2 old ones, and repeats. Ready capacity never drops below 10.
The defaults are 25% and 25%: for 10 replicas that is up to 3 extra pods and up to 2 unavailable.
If new pods never become Ready, the rollout stops making progress and after `progressDeadlineSeconds` (default 600) the Deployment reports `ProgressDeadlineExceeded`. Kubernetes does not roll back by itself; use `kubectl rollout undo`.
W: maxSurge 2 and maxUnavailable 0: Kubernetes adds at most 2 new pods, which fits the quota, and removes an old pod only after a new one passes its readiness probe, so ready capacity never falls below 10.
X: A=maxSurge 0 and maxUnavailable 2: no extra pods are created, so Kubernetes must first take down 2 old pods, which drops ready capacity to 8 during each step.
C=Default 25 percent values: maxSurge rounds up to 3 pods, exceeding the 2-pod quota headroom, and maxUnavailable rounds down to 2, which allows ready capacity to fall to 8.
D=Recreate with a progress deadline: Recreate removes every old pod before creating the new ones, causing an outage, and the progress deadline only reports a stalled rollout; it does not keep capacity.
T: For zero capacity loss in a Kubernetes rollout, set maxUnavailable to 0 and size maxSurge to the spare room you have; readiness probes gate each step.

@ DVA-C03 D3 T3.3 advanced troubleshooting
S: A CodeBuild project on an x86_64 build environment pushes api:1.4.0 to Amazon ECR. The team sets cpuArchitecture to ARM64 in the runtimePlatform of the ECS Fargate task definition to move the service to Graviton, and new tasks stop at once with "exec format error". The same tag must keep working on x86_64 EKS nodes. What should the team do?
A: Set operatingSystemFamily to LINUX in runtimePlatform, so Fargate on Graviton translates the x86_64 instructions of the image through emulation
B: Add --platform linux/arm64 to the FROM line of the final stage only, so the one image that the build produces runs on both architectures
C: Add an ECR pull through cache rule for the repository, which converts each pulled image to the CPU architecture of the requesting host
D: Build and push an arm64 and an amd64 image, then create and push a manifest list for api:1.4.0 that references both architecture images
K: D
G: ## One tag, several architectures
Compiled binaries and native libraries in an image target one CPU architecture. An x86_64 image on an ARM64 (Graviton) host fails as soon as the entrypoint runs, typically with `exec format error`.
A **manifest list** (OCI image index) lets one tag cover several architectures. It is a small manifest that lists one image per platform, for example `linux/amd64` and `linux/arm64`. When a client pulls the tag, the container runtime picks the entry that matches its own platform.
## Building one in an AWS pipeline
- Build each architecture natively, for example one CodeBuild project with an x86_64 environment and one with an ARM environment, and push `api:1.4.0-amd64` and `api:1.4.0-arm64`.
- Create and push the list: `docker manifest create <repo>:1.4.0 <repo>:1.4.0-amd64 <repo>:1.4.0-arm64` then `docker manifest push <repo>:1.4.0`. (`docker buildx build --platform linux/amd64,linux/arm64 --push` is another way.)
- Amazon ECR stores manifest lists, and ECS task definitions and EKS pod specs can reference them like any other image.
- ECS on Fargate selects ARM64 through `runtimePlatform.cpuArchitecture: ARM64`.
Note: AWS Lambda does not support multi-architecture images; a Lambda function must point to an image built for its one architecture.
W: Per-architecture images plus a manifest list: the tag then resolves to the arm64 image on Graviton Fargate tasks and to the amd64 image on x86_64 EKS nodes, so one release tag works on both.
X: A=operatingSystemFamily and emulation: operatingSystemFamily only selects Linux or Windows; Fargate does not emulate another CPU architecture, so the x86_64 binaries still cannot run on Graviton.
