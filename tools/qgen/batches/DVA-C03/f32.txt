@ DVA-C03 D4 T4.1 applied use-case
S: An on-call team wants CloudWatch investigations to start automatically when the `checkout-api-5xx` alarm goes into ALARM, to take recent CloudTrail change events into account, and to let every on-call engineer view and continue the investigation. Today engineers start investigations by hand from the console with default settings. What should the developer configure?
A: Export CloudTrail logs to an S3 bucket in us-east-1, since investigations read change events from an organization trail bucket kept in that Region
B: A Lambda function run at five-minute intervals that generates a Logs Insights query from a plain-English prompt and emails results when 5XX errors rise
C: No change: investigations with default settings start on alarm state changes and are shared with users who have read access to CloudWatch in the account
D: Create an investigation group with an IAM role, deliver CloudTrail management events to CloudWatch Logs in the same Region, and add an alarm investigation action
K: D
G: ## CloudWatch investigations
CloudWatch investigations is a generative AI feature that, during an incident, scans telemetry (metrics, logs, traces, deployment events, AWS Health events and CloudTrail change events) and suggests observations and root-cause hypotheses that you accept or discard.
## Default versus configured
- **Without configuration**, an investigation is session-based and read-only: it uses the signed-in user's permissions, other users cannot view or continue it, and it is deleted after 24 hours.
- **After you configure** it, an **investigation group** (one per account) holds settings such as the IAM role the investigations use (trusted by `aiops.amazonaws.com`), retention (7 to 90 days) and encryption. Investigations are then available to every user who has the required permissions, can continue until resolved, and can be started from a **CloudWatch alarm action** (an action ARN such as `arn:aws:aiops:us-east-1:111122223333:investigation-group/ID`) or an Application Signals SLO.
## Change events need CloudTrail in CloudWatch Logs
To relate an issue to a recent change, AWS recommends configuring CloudTrail trails to send management events to CloudWatch Logs. Investigations analyze trail events only from trails that **send events to CloudWatch Logs in the same Region** where the investigation runs. (The investigation group can also be given access to change events in the CloudTrail Event history.)
W: Investigation group, CloudTrail to CloudWatch Logs, alarm action: the group makes investigations shared and allows alarm-triggered starts, the trail delivery lets investigations link the errors to recent changes, and the alarm action starts the investigation without a person.
X: A=Central S3 bucket in us-east-1: investigations analyze trail events delivered to CloudWatch Logs in the Region of the investigation (or the account's CloudTrail Event history), not log files in an S3 bucket in another Region.
B=Scheduled generated query: a natural-language query generator helps write Logs Insights queries; polling with it is not an investigation and produces no hypotheses or change correlation.
C=Default settings: default investigations are started by a user, are visible to that user alone and disappear after 24 hours, so they are neither alarm-started nor shared.
T: For alarm-started, shared CloudWatch investigations, configure an investigation group, send CloudTrail to CloudWatch Logs in the same Region, and add the investigation as an alarm action.

@ DVA-C03 D1 T1.1 applied use-case
S: A developer calls the Amazon Bedrock Runtime Converse API from a Python application. Responses must be at most 300 tokens and fairly deterministic, and the developer also needs to set the model's top_k parameter, which is specific to the chosen model. How should the developer pass these settings?
A: Put maxTokens and temperature in inferenceConfig, and pass top_k in additionalModelRequestFields because Converse has no common field for it
B: Put maxTokens, temperature and top_k together in inferenceConfig, because Converse translates parameter names into each model's native format
C: Put the three settings in the system prompt as text instructions, because Converse reads inference parameters from the prompt text of a request
D: Switch to InvokeModel for these requests, because Converse rejects any request that carries a parameter belonging to one model's native format
K: A
G: ## Inference parameters in the Converse API
The Converse API uses one request format for all models that support it. Inference parameters that most models share are fields of `inferenceConfig`:
- `maxTokens`: the maximum number of tokens to generate;
- `temperature`: randomness (lower values give more deterministic output);
- `topP` and `stopSequences`.
Parameters that only some models support, such as `top_k` for some models, go in `additionalModelRequestFields` as a JSON object, which Bedrock passes to the model.
```
client.converse(modelId=model_id, messages=msgs,
inferenceConfig={"maxTokens": 300, "temperature": 0.2},
additionalModelRequestFields={"top_k": 50})
```
Model-specific fields in the response come back in `additionalModelResponseFields`.
W: inferenceConfig plus additionalModelRequestFields: the common limits go in inferenceConfig, and the model-specific top_k goes in additionalModelRequestFields, so one Converse request carries all three settings.
X: B=Everything in inferenceConfig: inferenceConfig accepts its defined fields (maxTokens, temperature, topP, stopSequences); top_k is not one of them, so it does not belong there.
C=Parameters as prompt text: instructions in a prompt do not set sampling or token limits; they are API fields, not wording the model reads.
D=Switch to InvokeModel: Converse supports model-specific parameters through additionalModelRequestFields, so there is no need to give up the common format.
T: In Converse, set maxTokens and temperature in inferenceConfig and pass model-specific parameters in additionalModelRequestFields.
V: Amazon Bedrock

@ DVA-C03 D1 T1.1 applied use-case
S: Halfway through implementing a Kiro spec for a notification feature, the product owner adds a requirement: users must be able to mute notifications for 24 hours. Several tasks in the spec are already complete. How should the developer handle the change to keep the spec useful?
A: Delete the spec and generate a new one from scratch that includes the new requirement, then rerun the task list, including the tasks that are already complete
B: Add the new requirement as a code comment in the handler and mark the remaining tasks as complete, so that the task list no longer conflicts with the code
C: Update the requirements document with the new acceptance criteria, have the design and task list updated to match, review them, then implement the new tasks
D: Implement the mute logic directly in code through a chat prompt and leave the spec unchanged, because a spec serves to plan the first version of a feature
K: C
G: ## Specs are living documents
A Kiro spec is useful because it stays the single description of what the feature should do. When requirements change, the change flows through the same documents:
- `requirements.md` gets the new user story and acceptance criteria ("WHEN a user mutes notifications THE SYSTEM SHALL suppress them for 24 hours").
- `design.md` is updated, for example with a mute-until timestamp on the user record.
- `tasks.md` gains the tasks needed for the change; tasks that are already done are kept rather than redone.
The team reviews the updated documents, then the agent implements the new tasks.
## What goes wrong otherwise
If code changes bypass the spec, the documents stop matching the system, and the next person (or agent) working from the spec builds on wrong assumptions.
W: Update requirements, then design and tasks: the new criteria are recorded and reviewed, the plan reflects them, and just the new work is implemented, so the spec stays an accurate source of truth.
X: A=Regenerate the spec: throwing away a reviewed spec and redoing completed tasks wastes work and risks changing code that already met its criteria.
B=Comment and mark tasks complete: marking unfinished work as done hides it, and a code comment is not a reviewed requirement.
D=Chat prompt, spec left unchanged: the spec would no longer describe the feature, so traceability to acceptance criteria is lost for the new behavior.
T: When requirements change, update the Kiro spec (requirements, then design and tasks) and implement from it, so the spec remains the source of truth.
V: Kiro
