SC-900 (Microsoft Security, Compliance, and Identity Fundamentals) covers dozens of Microsoft product names, and most questions come down to one thing: which of them does the job described in the stem? The job is almost always carried by a verb. "Detect" risky sign-ins, "require" MFA, "classify" a document, "keep" email for seven years, "prove" that Microsoft is audited. This guide sorts the products by those verbs, so that a stem leads you straight to the right family before you read the options.

Study guide · Microsoft Security, Compliance, and Identity Fundamentals (SC-900)

The exam

45 minutes, passing score 700 on a scale of 1 to 1,000. Microsoft does not publish a fixed number of questions (this question bank's mock exam uses 45), so pace yourself by time. Skill areas: Describe the concepts of security, compliance, and identity (10–15%), Describe the capabilities of Microsoft Entra (25–30%), Describe the capabilities of Microsoft security solutions (35–40%), Describe the capabilities of Microsoft compliance solutions (20–25%). If the exam is not offered in your preferred language, you can request an additional 30 minutes.

The exam is wide rather than deep. The 225 SC-900 questions in this question bank split 84 security solutions, 62 Microsoft Entra, 51 compliance and 28 concepts, and the Entra and security questions alone name more than forty different products and features, none of them in more than 16 questions. One question in five is a straight definition, and another one in five compares two look-alikes. Use current names: Microsoft Entra ID, Microsoft Defender XDR, Microsoft Purview.

Beginner tip: when you practise, cover the options with your hand and write down the verb of the stem and the product you expect, then uncover. If your product is among the options, you are done. If it is not, the question is testing a look-alike pair, and you should add that pair to a list. After two or three practice sets the list is short, and it is exactly what you need to revise.

Concepts: learn the precise words

The smallest area, but it supplies the vocabulary for the rest. The shared responsibility model (what moves to Microsoft in IaaS, PaaS and SaaS, and what never does: your data, endpoints, accounts and access management), defense in depth, Zero Trust (verify explicitly, use least privilege, assume breach), encryption versus hashing, authentication versus authorisation, identity providers and federation. These are usually one-line definitions with distractors that swap two terms.

Microsoft Entra: who decides what

Two role systems cause most errors here. Microsoft Entra roles manage the directory: users, groups, passwords, app registrations. Azure RBAC manages Azure resources such as VMs and storage accounts. A Global Administrator is not automatically an Owner of every subscription. Also separate the three identity-protection tools: ID Protection scores Microsoft Entra sign-ins and users, Defender for Identity detects identity attacks from on-premises Active Directory signals (and now Microsoft Entra ID signals too), and Conditional Access is the engine that enforces a decision.

Going deeper: security defaults or Conditional Access, never both

Security defaults are a free, all-or-nothing package switched on for new tenants: every user registers for MFA, administrators always use MFA, and legacy authentication protocols, which cannot do MFA, are blocked. You cannot scope them to some users or apps. Conditional Access is the flexible replacement, needs Microsoft Entra ID P1 (P2 for risk-based conditions), and the two are not used together: a tenant turns security defaults off when it moves to Conditional Access. So "a small company on the Free edition wants basic protection with no configuration" points to security defaults, and "require MFA only from outside the office" points to Conditional Access. Note also that Conditional Access runs after the first authentication factor, which is why it is no answer to a network flood.

Security solutions: the largest area

Learn the Defender family by what each protects: Defender for Office 365 (email and collaboration), Defender for Endpoint (devices), Defender for Identity (identity attacks, starting from on-premises AD), Defender for Cloud Apps (SaaS apps, as a cloud access security broker), Defender for Cloud (Azure, other clouds, on-premises servers). Know the email timeline: Safe Attachments acts before delivery, Safe Links at the time of the click, zero-hour auto purge after delivery. In Sentinel, automation rules manage incidents centrally while playbooks, built on Logic Apps, act in other systems. Sentinel is moving into the Microsoft Defender portal: after March 31, 2027 it is no longer supported in the Azure portal.

Going deeper: why fixing one finding may not move the secure score

This is the classic secure score in the Azure portal. Defender for Cloud groups recommendations into security controls, each worth a maximum number of points, and a resource earns a control's points only when it passes every recommendation in that control. Fix one of two open findings on a VM and the score stays where it was. Only built-in Microsoft cloud security benchmark recommendations count and preview recommendations are left out: the score is built from recommendations, so it measures configuration, not attacks. The Defender portal now also shows a risk-based Cloud Secure Score for Defender for Cloud, a different model with different values, and Microsoft Secure Score there is another measure again.

Compliance solutions: three questions to ask

  1. Is it about Microsoft's compliance or yours? Service Trust Portal versus Compliance Manager.
  2. Is it about what the content is, or how long it lives? Sensitivity labels versus retention.
  3. Is it one action now, or a pattern over time? DLP versus insider risk management.
