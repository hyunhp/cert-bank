Four names show up as options in the same Databricks data engineering questions: declarative pipelines, Lakeflow Jobs running notebooks, Auto Loader and COPY INTO. They look like four competing ways to load data, which makes the questions feel like guesswork. They are not four of the same thing, though. Two of them load files, one declares tables and keeps them up to date, and one runs and schedules work. Once you see which layer each one sits in, the stem nearly always contains the detail that decides.

First, the names

Databricks renames products often, and exam material mixes old and new names. In the questions in this question bank:

  • Lakeflow Spark Declarative Pipelines, also called Lakeflow Declarative Pipelines or simply Lakeflow pipelines, were formerly Delta Live Tables. They are built on the open Spark Declarative Pipelines.
  • Lakeflow Jobs was formerly Workflows.
  • Auto Loader (the cloudFiles source) and COPY INTO kept their names.

If an option uses an older name, it is not wrong for that reason alone. Judge the mechanism.

They nest. A streaming table that ingests files reads them with Auto Loader underneath; in SQL that is CREATE OR REFRESH STREAMING TABLE bronze_orders AS SELECT * FROM STREAM read_files(...). A job can start that pipeline with a pipeline task, then run a notebook task after it. So "pipeline or job?" is often a false choice: many correct answers use both, and the question is which one owns which part.

COPY INTO versus Auto Loader

This pair belongs mostly to the DBX-DEA Data Ingestion and Loading section: 25 of the 27 DBX-DEA questions in this bank that name either tool sit there. Both are incremental and both avoid loading a file twice. The differences:

  • Scale. The Databricks documentation suggests COPY INTO for files in the order of thousands over time and Auto Loader for millions or more, because Auto Loader needs fewer operations to discover files and can split the work into batches. In file notification mode with file events, Auto Loader lists the directory once on the first run and then finds new files in the file events cache instead of listing again.
  • Interface. COPY INTO is one SQL statement you run, typically from a SQL task or a scheduled query. Auto Loader is a stream you start in Python or, through a streaming table, in SQL.
  • Schema. Auto Loader infers and evolves the schema (with cloudFiles.schemaLocation) and puts values that do not fit into _rescued_data. COPY INTO can evolve the target schema when you set mergeSchema, and its VALIDATE option checks files without writing.
  • Reloading a file. COPY INTO skips a file rewritten under the same name; force reloads it (and every other selected file). Auto Loader reloads everything if its checkpoint is deleted.
Going deeper: where each one remembers the files it has seen

COPY INTO records which files it has loaded for its target table, so the same statement against the same target skips what is already there. That is what makes it idempotent and safe to rerun after a timeout. Auto Loader keeps its record in the stream's checkpoint location, in a RocksDB store of discovered files, which gives exactly-once file processing and lets a failed stream resume where it stopped. The consequence decides several questions: for COPY INTO the history belongs to the table, for Auto Loader it belongs to the checkpoint. Point an Auto Loader stream at a new checkpoint and, because cloudFiles.includeExistingFiles defaults to true on the first start, every historic file loads again. Two streams sharing one checkpoint mix their offsets, so each stream needs its own.

Declarative pipeline versus a job running notebooks

When both could do the work, choose by what you want to own. A pipeline takes over ordering, checkpoints, retries and data quality, and in exchange restricts what you can write. The engine plans the whole graph before reading any data, so:

  • pivot() is rejected in a pipeline, because it must read the data to learn the columns; write conditional aggregation instead.
  • Each dataset can be defined only once. Two sources feeding one streaming table need append flows, not two pipelines.
  • Expectations (warn, drop, fail) decide which rows reach a table; they are not orchestration. In a triggered pipeline a failed expectation rolls back only that flow's update while the other flows keep updating, and a table that reads a validation table does not wait for it. To block downstream work, put validation and the downstream work in separate pipelines and chain them as pipeline tasks in a job.
  • Side effects such as calling a REST service or running a MERGE over JDBC are not a supported design inside dataset definitions. That is the moment to use Structured Streaming with foreachBatch as a job task, or, in a Python pipeline, a ForEachBatch sink as the target of an append flow.

Beginner tip: build the same tiny bronze-to-silver flow twice. First as two notebook tasks in a job: an Auto Loader stream with availableNow, then a cleaning query. Then as a pipeline with one streaming table and one materialized view plus an expectation. Look at what you had to write in the first version (checkpoint paths, task order, retry settings) that the pipeline did for you, and at the pipeline's graph and data quality tab. After that, "which one fits?" questions read like a checklist.

Who decides when it runs

A pipeline has a mode: triggered (process what is there, then stop) or continuous (keep running). When a job starts the pipeline, the job wins: a scheduled job runs one update and stops even if the pipeline is set to continuous. Databricks recommends leaving the pipeline triggered and using a continuous job when you want it always on. Plain streaming code follows a similar rule on serverless jobs, which accept only triggers that end on their own such as availableNow; an always-on stream with a short processingTime interval belongs in a continuous serverless pipeline instead.

Going deeper: why a full refresh can lose data a streaming table already had

A streaming table reads each input record once and keeps it, even if the source later deletes it. A full refresh clears the table and its checkpoints and reads again from whatever the source still holds. If a storage lifecycle rule deletes files after thirty days, or a Kafka topic keeps seven days, the rebuilt table holds only that window. This is why the narrower recovery options (refresh failed tables, reset one flow's checkpoint) are usually the right answers at professional level, and why the table property pipelines.reset.allowed = false exists to block full refreshes on tables whose history cannot be replayed.
