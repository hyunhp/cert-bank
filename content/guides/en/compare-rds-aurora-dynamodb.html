Amazon RDS, Amazon Aurora and Amazon DynamoDB appear in almost every AWS exam, from Cloud Practitioner to Solutions Architect – Professional. The questions rarely ask "which database is best"; they describe an application and hide two or three clues in the wording. This comparison shows how to read those clues, which exams go deepest into which service, and the features that settle the close calls.

Study guide · Comparison · Amazon RDS, Amazon Aurora and Amazon DynamoDB

Three questions, in this order

  1. How will the data be read? If every access is by a known key (get this customer's cart, this device's last readings), at very large or unpredictable scale, with millisecond latency and no servers to manage, the answer is DynamoDB. If the scenario mentions joins across tables, ad hoc reporting queries or an existing SQL schema, it is relational.
  2. Is there an engine to keep? A lift of an existing Oracle, SQL Server, Db2, MariaDB, MySQL or PostgreSQL database with minimal change points to RDS for that engine. Changing engines is a migration question (AWS DMS plus schema conversion), not a database choice.
  3. If it is MySQL or PostgreSQL, does it need what Aurora adds? Fast failover, up to 15 low-lag read replicas, storage that grows by itself, cross-Region replication with a promotable secondary (Aurora Global Database), or capacity that follows unpredictable load (Aurora Serverless v2). If the scenario stresses any of these, Aurora wins; otherwise standard RDS is a valid and cheaper answer.

One clue misleads people: "transactions". DynamoDB supports transactions across items and tables too, so transactions alone do not force a relational answer. Joins, flexible queries and referential structure do.

Going deeper: why Aurora fails over faster than standard RDS

In standard RDS with a Multi-AZ instance, the primary and the standby each have their own storage, kept in step by synchronous replication, and the standby serves no traffic. Aurora separates compute from storage. Every cluster has one shared storage volume, kept as six copies spread across three Availability Zones, and the writer and all replicas read from that same volume. A replica therefore holds no separate copy that must catch up: when the writer fails, a replica is promoted and points at storage that is already current. That is why Aurora replicas lag only slightly behind the writer, why they double as failover targets, and why "add Aurora replicas" answers both read scaling and availability in one step, while standard RDS needs read replicas for reads and Multi-AZ for failover.

Same words, different machinery

"Replica", "standby" and "global" mean different things in each service. Most wrong answers in this area come from mixing them up.

FeatureWhat it is for
RDS Multi-AZ DB instanceAutomatic failover inside a Region. The standby cannot be read.
RDS Multi-AZ DB clusterFaster failover plus two standbys that can serve reads (MySQL and PostgreSQL).
RDS read replicaRead scaling with asynchronous replication, so reads can be slightly stale; can be in another Region.
Aurora replicaRead scaling and failover target at once, behind a reader endpoint.
Point-in-time recoveryUndo a mistake by restoring to a second before it (RDS, Aurora and DynamoDB, up to 35 days). Replicas copy the mistake.

Two rules follow. Replicas and standbys never add write capacity: write limits are fixed with more IOPS, a bigger instance, sharding or a move to DynamoDB. And after a Multi-AZ failover, the endpoint name stays the same but its address changes, so applications must reconnect by name rather than caching the IP.

Beginner tip: create a DynamoDB table with partition key CustomerId and sort key OrderDate, add a dozen items for three customers, then fetch one customer's orders twice in the AWS CLI: once with query and a key condition, once with scan and a filter, both with --return-consumed-capacity TOTAL. The scan reads, and charges for, every item before the filter throws most of them away. That one comparison explains a large part of the DynamoDB questions in DVA-C03 and DEA-C01.

DynamoDB details that decide close calls

  • Capacity: on-demand for unknown or spiky traffic; provisioned with auto scaling for steady, predictable load.
  • Indexes: a global secondary index (GSI) adds a new partition key at any time but is eventually consistent; a local secondary index (LSI) keeps the partition key, must be created with the table and allows strongly consistent reads.
  • Changes and expiry: Streams for reacting to each item change; TTL for automatic deletion of old items without consuming write throughput; export to S3 for analytics without consuming table capacity.
Going deeper: why a table with spare capacity still throttles

DynamoDB stores a table's items in partitions chosen by hashing the partition key, and each partition can serve only a limited amount of reads and writes per second. The table's total capacity is spread across those partitions. If the key has few distinct values (a status field, today's date), most traffic hashes to the same partition and hits that partition's limit while the others sit idle, so the table throttles even though its overall metrics show spare capacity. Adaptive capacity raises throughput for busy partitions and can move hot items to partitions of their own, but no partition goes past its maximum of 3,000 reads or 1,000 writes per second. The fix the exams expect is a high-cardinality key, or adding a random or calculated suffix to spread writes (write sharding), not more capacity or another index.
