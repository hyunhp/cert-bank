AWS Certified CloudOps Engineer – Associate(SOA-C03)는 시스템을 설계하는 시험이 아니라 계속 돌아가게 하는 시험입니다. 문제는 계정에서 벌어지고 있는 일을 설명하고, 그것을 알아차리거나, 원인을 찾거나, 고치라고 요구합니다. 가능하면 다음번에는 저절로 고쳐지게 하라고 합니다. 이 세 동사는 세 가지 서비스 묶음에 대응합니다. 먼저 문제를 분류하고 나서 선택지를 읽으면 절반은 걸러집니다. 이 가이드는 그 순환을 바탕으로 합니다. 탐지, 분석, 조치, 그리고 예방입니다.

학습 가이드 · AWS Certified CloudOps Engineer – Associate (SOA-C03)

시험 개요

문제는 65개이며, 이 중 50개가 채점되고 15개는 채점되지 않습니다(어느 문제인지 표시되지 않습니다). 점수는 100~1,000점의 환산 점수로 나오고 합격 점수는 720점입니다. 모든 문제는 객관식(보기 4개 중 정답 1개) 또는 복수 응답(보기 5개 이상 중 정답 2개 이상)이며, SOA-C03 시험 가이드에는 다른 문제 유형이 없으므로 실습 문제(exam lab)도 없습니다. 다섯 도메인의 비중이 유난히 고릅니다. Monitoring, Logging, Analysis, Remediation, and Performance Optimization(22%), Reliability and Business Continuity(22%), Deployment, Provisioning, and Automation(22%), Networking and Content Delivery(18%), Security and Compliance(16%)입니다. 압도적인 도메인이 없으므로 건너뛰어도 안전한 영역도 없습니다.

이 문제은행의 SOA-C03 문제 395개 중 55개 지문(약 14%)이 무언가를 자동으로 처리하라고 명시적으로 요구하고, 81문제(21%)가 문제 해결 시나리오입니다. 가장 많이 태그된 서비스는 CloudWatch(38문제, 대략 열 문제 중 하나)이고, 그다음이 Systems Manager, S3, VPC(각 30문제), EC2(29문제), CloudFormation(28문제)입니다. "이 서비스는 무엇인가"보다 "가장 수작업이 적은 방법은 무엇인가"를 훨씬 많이 예상하십시오.

1단계: 신호 분류하기

모니터링 문제는 대부분 어떤 종류의 신호를 설명하는지로 귀결됩니다. 신호 유형마다 탐지 수단이 따로 있습니다.

지문에 나오는 것탐지 수단
임계값을 넘는 숫자(CPU, 지연 시간, 큐 깊이)CloudWatch 경보. 여러 경보를 묶어 잡음을 줄이려면 복합 경보(composite alarm)
로그에 특정 줄이 나타남지표 필터(metric filter, 경보를 걸 때) 또는 구독 필터(subscription filter, Lambda, Kinesis, Firehose로 스트리밍할 때)
개별 이벤트: 인스턴스 중지, 탐지 결과(finding), 상태 변경EventBridge 규칙

2단계: 분석하기

분석 문제는 어디를 봐야 하는지 묻습니다. CloudWatch Logs Insights는 내보내기 없이 로그 그룹 하나 또는 여러 개를 제자리에서 조회합니다. 누가 무엇을 바꿨는지는 CloudTrail이, 리소스가 변경 전후에 어떤 모습이었는지는 Config가 답합니다. 네트워크에서는 VPC Flow Logs가 트래픽에 실제로 일어난 일(ACCEPT 또는 REJECT)을 기록하고, Reachability Analyzer는 패킷을 보내지 않고 구성상 경로가 허용되는지 확인하며, Traffic Mirroring은 페이로드를 검사해야 할 때 실제 패킷을 복사합니다. 연결 문제는 계층별로 살펴보십시오. 보안 그룹, 네트워크 ACL, 라우팅 테이블 순서로 보고, Flow Logs로 확인합니다.

3단계: 조치하기

복구 도구는 수정 규모에 따라 달라집니다.

  • 인스턴스 하나에 작업 하나(중지, 재부팅, 복구): CloudWatch 경보 자체에 건 EC2 작업.
  • 플릿 전체에 명령 실행: Systems Manager Run Command.
  • 조건이나 승인이 있는 여러 단계: Systems Manager Automation 런북. 흔히 EventBridge 규칙이 시작합니다.
  • 구성 드리프트: 복구 작업(remediation action)을 연결한 Config 규칙.
  • 직접 고치기 위한 대화형 접근: Session Manager. SSH 포트를 열지 않고 배스천 호스트(bastion host)도 두지 않습니다.

초보자 팁: Systems Manager 문제는 관리형 인스턴스를 직접 보기 전에는 떠올리기 어렵습니다. AmazonSSMManagedInstanceCore 정책이 포함된 인스턴스 프로파일을 붙이고, Systems Manager 엔드포인트에 닿을 수 있는 서브넷에, 인바운드 규칙은 하나도 없이 작은 Amazon Linux 인스턴스 하나를 띄우십시오. Session Manager로 셸을 연 다음, 그 인스턴스에 Run Command를 실행합니다. 이어서 인스턴스 프로파일을 제거하고 Fleet Manager에서 노드 상태가 Connection lost로 바뀌는 것을 지켜보십시오(계정에 Default Host Management Configuration이 켜져 있지 않은 경우). 문제 해결 문제가 묻는 세 가지 전제 조건(에이전트, 역할, 네트워크 경로)을 모두 만나게 됩니다.

4단계: 다음번을 예방하기

Deployment, Provisioning, and Automation 도메인은 올바른 상태를 기본값으로 만드는 일을 다룹니다. 변경 세트를 쓰는 CloudFormation은 업데이트를 미리 보여 줍니다. 드리프트 탐지는 수동 변경을 찾아냅니다. StackSets는 같은 스택을 여러 계정과 리전에 배포합니다. State Manager는 일정에 따라 구성을 계속 다시 적용하며, 한 번만 실행하는 Run Command와는 다릅니다. Patch Manager는 유지 관리 기간(maintenance window) 안에 패치 기준선을 적용하고 규정 준수 상태를 보고합니다. EC2 Image Builder로 만든 골든 AMI와 시작 템플릿은 새 인스턴스를 일관되게 유지합니다.

신뢰성: 가용성은 복구 가능성이 아니다

두 질문을 구분하십시오. 계속 살아 있을 것인가? 이것은 Multi-AZ, 로드 밸런서 상태 확인, Auto Scaling 상태 확인과 조정 정책입니다. 되살릴 수 있는가? 이것은 백업, 특정 시점 복구, 그리고 RTO와 RPO에 맞춘 재해 복구 패턴입니다. RDS Multi-AZ는 자동으로 장애 조치합니다. 읽기 복제본은 읽기를 확장하고 리전 단위 복구에 도움이 되지만, 승격해야 합니다. 특정 시점 복원은 새 엔드포인트를 가진 새 인스턴스를 만들므로, 런북에 애플리케이션이 가리키는 곳을 바꾸는 단계가 있어야 합니다. AWS Backup은 여러 서비스에 걸친 백업 계획을 중앙에서 관리합니다.

더 깊이: 규정 준수 모드의 Vault Lock이 관리자조차 막는 이유

백업 삭제를 막는 일반적인 보호는 IAM의 판단이며, IAM을 바꿀 수 있는 사람은 그것을 되돌릴 수 있습니다. 관리자 권한을 가진 공격자나 부주의하게 넓게 쓴 정책이 있으면 뚫립니다. AWS Backup Vault Lock은 규칙을 볼트 자체로 옮깁니다. 거버넌스 모드에서는 특정 권한을 가진 사용자가 여전히 잠금을 바꾸거나 제거할 수 있으므로 테스트에 유용합니다. 규정 준수 모드에서는 잠근 뒤 유예 기간이 지나면 잠금이 변경 불가능해집니다. 루트 사용자를 포함한 어떤 사용자도 보존 기간이 끝나기 전에 복구 지점을 삭제하거나 보존 기간을 줄일 수 없습니다. 그래서 지문에 "관리자 계정이 탈취되어도 살아남아야 함"이나 "랜섬웨어"가 나오면 규정 준수 모드를, "먼저 정책을 테스트하고 싶다"가 나오면 거버넌스 모드를 가리킵니다.

네트워킹: 운영자의 관점

이 도메인은 네트워크를 설계하는 것이 아니라 운영하는 일을 다룹니다. 퍼블릭 서브넷과 프라이빗 서브넷, 아웃바운드 전용 접근을 위한 NAT 게이트웨이, AWS 트래픽이 NAT를 거치지 않게 하는 게이트웨이 엔드포인트와 인터페이스 엔드포인트, 하이브리드 DNS를 위한 Route 53 호스팅 영역과 Resolver 엔드포인트, 장애 조치 라우팅과 상태 확인, 그리고 Origin Access Control, 캐시 동작(cache behavior), 무효화(invalidation)를 갖춘 CloudFront입니다. DNS 응답은 레코드의 TTL 동안 캐시된다는 점을 기억하십시오. 그러므로 TTL은 계획된 변경 이후가 아니라 이전에 낮춰야 합니다.

더 깊이: 영역 apex에 별칭 레코드가 필요한 이유

DNS 표준은 CNAME 레코드가 같은 이름의 다른 레코드와 함께 있는 것을 허용하지 않습니다. 영역의 apex(example.com 자체)에는 항상 영역의 SOA 레코드와 NS 레코드가 있어야 하므로, 어떤 DNS 서비스에서도 그곳에 CNAME을 둘 수 없습니다. Route 53 별칭(alias) 레코드는 이 문제를 Route 53 안에서 해결합니다. 이름 서버가 대상(로드 밸런서, CloudFront 배포, S3 웹 사이트 엔드포인트)의 현재 주소를 조회해 일반 A 레코드나 AAAA 레코드로 응답합니다. 클라이언트는 별칭을 보지 못하고, 대상의 IP 주소가 바뀌어도 자동으로 따라가며, AWS 리소스에 대한 별칭 쿼리는 요금이 부과되지 않습니다. 그래서 "example.com이 로드 밸런서를 가리키게 하라"의 답은 하나뿐입니다. 별칭 레코드입니다.

운영자로서의 보안과 규정 준수

여기서도 예방, 탐지, 교정 패턴을 예상하십시오. 예방: 최소 권한 IAM, 위임된 관리자를 위한 권한 경계, 정책과 기본값으로 강제하는 암호화(S3 기본 암호화, EBS 기본 암호화). 탐지: 위협에는 GuardDuty, 보안 태세에는 Security Hub CSPM, 외부 접근에는 IAM Access Analyzer. 교정: Config 복구 작업과 EventBridge가 시작하는 런북. 기존의 암호화되지 않은 EBS 볼륨은 제자리에서 암호화할 수 없습니다. 스냅샷을 만들고, 암호화를 적용해 스냅샷을 복사한 뒤, 새 볼륨을 만드십시오.
