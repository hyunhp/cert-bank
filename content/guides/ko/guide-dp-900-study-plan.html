DP-900(Microsoft Azure Data Fundamentals)은 서비스 목록을 외우는 시험처럼 보입니다. 하지만 거의 모든 문제는 먼저 데이터를 설명하라고 요구합니다. 데이터는 어떤 형태인가? 어디에 쓰이는가? 누가 다루는가? 이 세 질문에 답하면 대개 알맞은 Azure 서비스가 따라 나오고, 선택지를 읽기 전에 답이 보이는 경우도 많습니다. 이 가이드는 세 질문을 먼저 설명하고, 각 답이 Azure의 어느 서비스로 이어지는지 보여 드립니다.

학습 가이드 · Microsoft Azure Data Fundamentals (DP-900)

시험 개요

시험 시간은 45분이고, 합격 점수는 1~1,000점 척도에서 700점입니다. Microsoft는 문항 수를 고정해 공개하지 않으므로(이 사이트의 모의고사는 45문항으로 가정합니다) 시간 기준으로 속도를 계획하세요. 평가 영역은 Describe core data concepts(25–30%), Identify considerations for relational data on Azure(20–25%), Describe considerations for working with non-relational data on Azure(15–20%), Describe an analytics workload(25–30%)입니다. 모든 평가 항목이 "설명하라(describe)" 또는 "식별하라(identify)"로 되어 있어, 무언가를 구축하기보다 알아보고 고르는 형태입니다. 다만 시험 페이지는 일부 문항이 대화형일 수 있다고 안내합니다.

이 문제은행의 DP-900 문제 225개 중 네 문제에 하나는 단순한 정의 문제입니다. 가장 자주 나오는 서비스는 Power BI, Azure Cosmos DB, Microsoft Fabric(각각 대략 열 문제에 하나)이고, 그다음이 Azure SQL Database입니다. 이 세 서비스 중 두 개가 분석 도구라는 점에 주목하세요. 분석 영역은 핵심 개념 영역만큼 비중이 큽니다.

선택지를 읽기 전에 세 질문에 차례로 답하세요. Azure 서비스는 대개 그 답에서 나옵니다.

질문 1: 데이터는 어떤 형태인가?

  • 정형(structured): 행과 열로 된 고정 스키마가 있고, 모든 레코드의 필드가 같습니다. 고객, 주문, 결제가 그 예입니다.
  • 반정형(semi-structured): 레코드마다 자기 필드 이름을 담고 있고, 레코드끼리 구성이 다를 수 있습니다. JSON 문서가 대표적입니다. 어떤 고객은 이메일 주소가 세 개이고, 다른 고객은 하나도 없을 수 있습니다.
  • 비정형(unstructured): 프로그램이 바로 읽을 수 있는 필드가 없습니다. 이미지, 동영상, 오디오, 스캔한 계약서가 그렇습니다.

파일 형식도 같은 논리를 따릅니다. CSV, JSON, XML은 사람이 읽을 수 있습니다. Parquet은 분석용으로 압축된 열 기반 형식이고, Avro는 행 기반입니다. Delta Lake는 Parquet 파일 위에 트랜잭션 로그를 더합니다. "몇 개 열만 대량으로 읽는 분석에 맞는 형식은?" 같은 문제(정답은 Parquet)가 나올 것으로 예상하세요.

질문 2: 어디에 쓰이는가?

지문 속 단서워크로드
작은 읽기와 쓰기가 많고, 하나하나가 정확해야 함트랜잭션(OLTP). ACID(원자성, 일관성, 격리성, 지속성)로 보호됩니다.
대량의 이력 데이터를 보고서와 추세 분석용으로 읽음분석(OLAP): 웨어하우스, 레이크 또는 레이크하우스.
결과가 내일 아침까지 필요함배치 처리.
이벤트가 도착하는 대로 몇 초 안에 하나씩 처리함스트림 처리.

질문 3: 누가 작업하는가?

데이터의 흐름을 따라가세요. 데이터베이스 관리자(DBA)는 운영 데이터베이스가 가용하고, 안전하고, 백업되고, 빠르게 유지되도록 합니다. 데이터 엔지니어는 데이터를 옮기고, 정제하고, 적재하며 파이프라인을 건강하게 유지합니다. 데이터 분석가는 준비된 데이터를 모델링하고 보고서를 만듭니다. 동사를 보세요. "삭제된 테이블 복원"은 DBA, "야간 적재 작업 수정"은 엔지니어, "매출 대시보드 작성"은 분석가입니다.

초보자 팁: SQL 문 종류가 헷갈린다면 노트북의 SQLite나 무료 온라인 SQL 실습 사이트에서 20분만 투자하세요. 외래 키로 연결된 Customer 테이블과 Order 테이블을 만들고(이것이 DDL입니다), 행 몇 개를 넣고 하나를 수정한 뒤(DML), SELECT로 두 테이블을 조인합니다. 각 문 위에 주석으로 "DDL" 또는 "DML"이라고 적으세요. 종류별로 한 번씩 직접 쳐 보면 시험 압박 속에서도 CREATE와 INSERT를 헷갈리지 않습니다.

답이 Azure의 어디로 이어지는가

정형 + 트랜잭션: 관계형 서비스

새 클라우드 앱에는 Azure SQL Database, SQL Server 인스턴스 기능과 거의 완전한 호환성이 필요하면 Azure SQL Managed Instance, 운영체제까지 완전히 제어해야 하면 SQL Server on Azure Virtual Machines를 씁니다. 오픈 소스 엔진에는 Azure Database for PostgreSQL 또는 MySQL이 있습니다. 이 중 IaaS는 VM 옵션뿐입니다. 세 가지 SQL 옵션 사이에서 무엇을 고를지 정하는 단서는 별도 비교 글에서 다룹니다. 이미 사용 중지되었거나 중지될 예정인 오답 선택지를 조심하세요. Azure Database for MariaDB는 사용 중지 절차가 진행 중이며(Microsoft는 Azure Database for MySQL로 마이그레이션하도록 권장합니다), Azure Cosmos DB for PostgreSQL도 사용 중지 절차에 들어가 신규 프로젝트에는 더 이상 권장되지 않습니다.

비정형 파일: Azure Storage

객체에는 Blob Storage(일반 파일은 블록 Blob, VM 디스크는 페이지 Blob, 로그는 추가 Blob)를 씁니다. 분석용으로 계층 구조 네임스페이스를 켜면 Azure Data Lake Storage가 됩니다. 클라이언트가 드라이브로 연결하는 공유에는 Azure Files, 한 리전 안의 단순한 키-속성 데이터에는 Table storage를 씁니다.

더 깊이: 보관(archive) 계층만 리하이드레이션이 필요한 이유

핫(hot), 쿨(cool), 콜드(cold)는 모두 온라인 계층입니다. 한 단계 내려갈수록 Blob 저장 비용은 낮아지고 읽기 비용은 올라가지만, Blob은 여전히 바로 열립니다. 보관(archive) 계층은 오프라인입니다. 저장 비용은 가장 낮지만 데이터가 바로 읽을 수 있는 형태로 보관되지 않습니다. 그래서 Blob을 먼저 온라인 계층으로 리하이드레이션(rehydration)해야 하고, 이 작업은 몇 시간이 걸릴 수 있습니다. "감사인이 요청하면 즉시 읽을 수 있어야 한다"는 조건이 붙으면, 거의 건드리지 않는 데이터라도 보관 계층이 제외되는 이유입니다. 더 차가운 계층마다 최소 보관 기간(쿨 30일, 콜드 90일, 보관 180일)도 있어서, 그 전에 Blob을 옮기거나 삭제하면 조기 삭제 요금이 부과됩니다.

전 세계 규모의 반정형 데이터: Azure Cosmos DB

지문에 낮은 지연 시간, 전 세계 사용자, 자주 바뀌는 스키마가 나오면 Cosmos DB를 고르세요. 계정 하나에 API 하나입니다. NoSQL(네이티브, JSON, 신규 앱의 기본값), MongoDB, Table, Apache Cassandra(열 패밀리), Apache Gremlin(그래프)이 있습니다. 다섯 가지 일관성 수준을 강한 것부터 약한 것 순서로 알아 두세요. Strong, Bounded staleness, Session, Consistent prefix, Eventual입니다. 은행 잔액에는 Strong이 필요하고, 사용자마다 자기가 담은 상품이 보여야 하는 장바구니에는 Session이 맞습니다.

분석: Fabric, Databricks, 스트리밍, Power BI

ETL은 적재 전에 변환하고, ELT는 먼저 적재한 뒤 대상 시스템에서 변환합니다. Microsoft Fabric은 모든 워크로드가 OneLake와 Delta 테이블을 공유하는 하나의 SaaS 플랫폼입니다. Fabric 레이크하우스는 Spark와 혼합 데이터에 맞고, 그 SQL 분석 엔드포인트는 읽기 전용입니다. Fabric 웨어하우스는 T-SQL 쓰기를 완전히 지원합니다. 바로 가기(shortcut)는 데이터를 있는 자리에서 참조하고, 미러링(mirroring)은 데이터베이스를 OneLake로 복제합니다. Azure Databricks는 Apache Spark와 Delta Lake를 기반으로 한 관리형 분석 플랫폼입니다. 스트림에서는 Event Hubs가 수집하고, Stream Analytics가 시간 창 단위로 쿼리합니다(연속 창(tumbling window)은 겹치지 않고, 호핑 창(hopping window)은 겹칩니다). Power BI에서 보고서는 모델 하나 위에 만든 하나 이상의 대화형 페이지이고, 대시보드는 고정된 타일로 이루어진 한 페이지입니다. 측정값(measure)은 쿼리 시점에 계산되고, 계산 열(calculated column)은 행마다 저장됩니다.

더 깊이: Delta Lake가 파일 폴더를 테이블로 바꾸는 방법

Parquet 파일은 그 자체로는 그냥 파일입니다. 작업이 중간에 실패하면 데이터셋이 절반만 남고, 열 구성이 틀린 파일이 다른 파일 옆에 들어와도 막을 방법이 없습니다. Delta 테이블은 Parquet 파일 옆에 트랜잭션 로그를 둡니다. 쓰기 작업은 그 항목이 로그에 커밋되어야 비로소 보이므로 ACID 트랜잭션이 됩니다. 로그가 스키마를 기록하므로 잘못된 행을 거부할 수 있습니다. 그리고 이전 항목이 남아 있으므로 테이블의 예전 버전을 조회할 수 있습니다. 덕분에 레이크하우스는 값싼 레이크 스토리지 위에서 웨어하우스 수준의 보장을 제공합니다. Fabric과 Databricks가 모두 Delta를 기본 테이블 형식으로 쓰는 이유이기도 합니다.

2주 학습 순서

  1. 1–4일차: 핵심 개념(데이터 형태, 파일 형식, 워크로드, 역할). 시험의 4분의 1을 차지하고, 나머지 공부를 모두 쉽게 해 줍니다.
  2. 5–7일차: 관계형 개념과 SQL, 이어서 Azure 관계형 서비스.
  3. 8–9일차: Azure Storage와 Cosmos DB.
  4. 10–13일차: 분석, Fabric, 스트리밍, Power BI.
  5. 14일차: 여러 영역이 섞인 연습 세트를 풀고, 헷갈린 개념 쌍 목록을 만듭니다.
