Terraform은 "워크스페이스(workspace)"라는 말을 서로 다른 두 가지에 쓰고, 상태(state)는 성격이 전혀 다른 두 종류의 장소에 저장합니다. 시험 문제는 이 겹침을 일부러 이용합니다. HCP Terraform 워크스페이스라면 정답인 보기가 CLI 워크스페이스에서는 오답이고, 원격 백엔드에서 통하는 해결책이 로컬 상태에는 아무 효과가 없습니다. 이 블로그를 위해 두 시험에 걸쳐 만든 Terraform 문제 518개 중 103개에 workspace라는 단어가 나옵니다. 이 비교 글은 네 가지 개념을 구분하고, 문제가 그중 무엇을 묻는지 알려 주는 단서를 정리합니다.

개념 비교 · TF-TA004 및 TF-IEP002

짧은 답

백엔드(backend)는 상태가 저장될 위치를 정합니다. 로컬은 작업 디렉터리의 파일이고, 원격은 S3 버킷이나 HCP Terraform 같은 공유 저장소로, 보통 잠금, 암호화, 접근 제어를 갖춥니다. CLI 워크스페이스는 같은 구성, 백엔드, 자격 증명 아래에 있는 또 하나의 상태 파일일 뿐입니다. HCP Terraform 워크스페이스는 작업 디렉터리를 완전히 대신하며, 자체 상태 버전, 변수, 자격 증명, 실행 기록, 권한을 가집니다. 격리, 접근 제어, 별도 자격 증명을 묻는 문제라면 CLI 워크스페이스가 정답인 경우는 거의 없습니다.

로컬 상태와 원격 상태

상태 속 시크릿노트북에 있는 일반 JSON암호화와 접근 제어를 쓸 수 있음. 그래도 상태는 비밀로 다뤄야 함

오답 보기로 자주 나오는 규칙이 두 가지 있습니다. Git은 상태 저장소가 아닙니다(잠금이 없고, 안에 든 시크릿을 누가 읽는지 통제할 수 없습니다). 그리고 backend 블록은 변수나 local보다 먼저 읽히므로 이들을 쓸 수 없습니다. 환경별 값은 부분 구성(partial configuration)으로 넣습니다. terraform init -backend-config=prod.s3.tfbackend처럼 씁니다. HCP Terraform에서는 backend 블록을 아예 쓰지 않고 cloud 블록을 씁니다. 한 구성에는 둘 중 하나만 있으며, 둘 다 있을 수는 없습니다.

잠금은 백업이 아닙니다

잠금은 두 실행이 같은 상태에 동시에 쓰지 못하게 막습니다. 두 번째 실행은 "Error acquiring the state lock"으로 실패합니다. 이를 조정하는 도구가 세 가지 있습니다. -lock-timeout=10m은 실행이 기다렸다가 다시 시도하게 합니다(기본값은 0s라서 즉시 실패합니다). -lock=false는 보호를 없애므로 맞는 경우가 드뭅니다. terraform force-unlock LOCK_ID는 강제 종료된 실행이 남긴 오래된 잠금을 지우며, 아무도 잠금을 쥐고 있지 않다고 확신할 때만 안전합니다.

s3 백엔드의 현재 답은 상태 객체 옆에 두는 잠금 파일(use_lockfile = true)입니다. DynamoDB 테이블을 쓰는 잠금은 지원 중단(deprecated)되었습니다. 역할(role)이 잠금 객체를 지울 수 없으면 잠금이 절대 풀리지 않으므로, "실행이 성공했는데 잠금이 남아 있다"는 권한 문제를 가리킵니다. 세 가지 보호 장치를 구분하십시오. 잠금은 쓰는 쪽을 직렬화하고, encrypt는 저장된 데이터를 보호하며, 누군가 덮어쓴 뒤 이전 상태를 복원할 수 있게 해 주는 것은 버킷 버전 관리뿐입니다.

더 깊이: -migrate-state와 -reconfigure, 그리고 빈 상태 사고

Terraform은 초기화된 백엔드를 .terraform 디렉터리에 기억합니다. backend 블록이 바뀌면 terraform init은 상태를 어떻게 할지 지정할 때까지 멈춥니다. -migrate-state는 기존 상태를 새 위치로 복사합니다. -reconfigure는 이전 구성을 무시하고 아무것도 복사하지 않습니다. 그래서 새 위치는 빈 상태로 시작하고, 다음 플랜은 이미 존재하는 리소스를 전부 생성하겠다고 제안합니다. 오류를 없애려고 누군가 -reconfigure를 고르는 것, 이것이 전형적인 프로덕션 사고입니다. s3 백엔드에서 HCP Terraform으로 옮길 때도 같은 길을 따릅니다. cloud 블록으로 바꾸고, init을 실행하고, 상태를 복사하겠느냐는 제안을 수락합니다. 어떤 경우든 먼저 상태 파일을 백업하십시오.

CLI 워크스페이스와 HCP Terraform 워크스페이스

둘이 만나는 곳이 한 군데 있습니다. cloud { workspaces { tags = [...] } }를 쓰면 CLI의 terraform workspace list와 select가 그 태그를 가진 HCP Terraform 워크스페이스를 대상으로 동작합니다. name과 tags는 함께 쓸 수 없고, 실행 하나는 여전히 정확히 워크스페이스 하나를 대상으로 합니다.

초보자 팁: 기본 로컬 백엔드를 쓰는 아무 로컬 테스트 폴더에서 terraform workspace new test를 실행하고, 작은 리소스 하나를 apply한 뒤 폴더 내용을 확인해 보십시오. 새 워크스페이스의 상태가 기본 terraform.tfstate 옆, terraform.tfstate.d/test/ 아래의 별도 파일에 있고, 코드와 자격 증명은 같다는 것을 볼 수 있습니다. CLI 워크스페이스가 두 번째 파일일 뿐이라는 것을 직접 보면 "이것이 격리 경계인가?" 문제가 쉬워집니다.

문제가 원하는 답은 무엇인가?

  • "dev 자격 증명으로 prod를 선택해 apply할 수 있다" 또는 "감사인이 환경별로 접근을 분리하라고 요구한다" → CLI 워크스페이스가 아닙니다. 환경마다 자체 백엔드를 가진 별도 루트 모듈을 쓰거나, 별도 HCP Terraform 워크스페이스를 쓰십시오.
  • "새 디렉터리나 백엔드 없이 변경을 시험할 버려도 되는 사본" → CLI 워크스페이스.
  • "환경별 변수, 자격 증명, 실행 기록과 팀 권한" → 프로젝트로 묶은 HCP Terraform 워크스페이스.
  • "엔지니어 두 명이 서로의 변경을 덮어썼다" → 잠금을 지원하는 원격 백엔드.
  • "잘못된 state push 이후 상태 복원" → 잠금이 아니라 버킷 버전 관리 또는 HCP Terraform 상태 버전.
  • "새로 클론한 저장소에서 플랜이 모든 것을 생성하려 하고 state list가 비어 있다" → terraform workspace show를 확인하십시오. 새 클론은 default에서 시작합니다. 그 플랜은 적용하지 마십시오.
더 깊이: prod 소비자가 dev 데이터를 조용히 읽게 되는 과정

CLI 워크스페이스를 지원하는 백엔드에서는 워크스페이스마다 별도의 키 아래에 상태를 둡니다. terraform_remote_state 데이터 소스는 생산자(producer)의 루트 모듈 출력만 읽으며, s3 백엔드에서는 workspace 인수의 기본값이 생산자의 default 워크스페이스입니다. 따라서 prod에서 실행되는 소비자는 workspace = terraform.workspace를 설정하거나 올바른 키를 가리키지 않는 한 default 워크스페이스의 출력을 받습니다. 오류는 나지 않습니다. 관련된 함정도 있습니다. terraform workspace select dev 다음에 -var-file=prod.tfvars를 쓰면, 변수 파일과 워크스페이스를 묶는 것이 없으므로 dev 상태에 대해 프로덕션 크기로 플랜을 세웁니다. 둘 다 강한 분리가 필요한 환경에는 별도 구성을 쓰라고 문서가 권하는 이유입니다.
