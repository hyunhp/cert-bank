AWS Certified Developer – Associate(DVA-C03)는 작은 서버리스 애플리케이션의 시험입니다. 사용자가 로그인하고, API를 호출하고, 함수가 실행되고, 데이터를 읽고 쓰고, 일부 작업은 큐로 넘어갑니다. 무언가 고장 나면 트레이스가 어디서 문제가 생겼는지 보여 줍니다. 거의 모든 문제가 이 경로의 한 지점에 놓여 있습니다. 그래서 이 가이드는 요청 하나를 브라우저에서 로그까지 따라가며, 구간마다 시험이 기대하는 지식과 사람들이 헷갈리는 설정을 정리합니다.

학습 가이드 · AWS Certified Developer – Associate (DVA-C03)

시험 개요

DVA-C03은 2026년 12월 1일부터 DVA-C02를 대체합니다(DVA-C02 마지막 응시일은 2026년 11월 30일). 65문제 중 50문제가 채점되고 15문제는 채점되지 않습니다. 점수는 100~1,000점 척도이며 최소 합격 점수는 720점입니다(시험 시간은 시험 가이드에 나와 있지 않습니다). 네 도메인은 그대로이고 비중이 바뀌었습니다. Development with AWS Services 30%, Security 26%, Testing and Deployment 22%, Troubleshooting and Optimization 22%입니다. 비중이 가장 많이 늘어난 것은 Troubleshooting입니다. 새로 추가된 내용은 AI 지원 개발(Kiro), 애플리케이션에서 Amazon Bedrock 같은 관리형 AI 서비스 호출, 그런 AI 서비스의 보안, 컨테이너 빌드와 배포입니다.

이 문제은행의 DVA-C03 문제 470개 중 AWS Lambda를 관련 서비스로 표시한 문제는 140개, 즉 30%입니다. 그다음이 DynamoDB 13%, API Gateway 10%입니다. Lambda는 이 시험의 뼈대입니다. 가장 먼저, 가장 깊이 공부하십시오.

구간 1: 사용자 로그인

Amazon Cognito에는 비슷해 보이는 두 부분이 있습니다. 사용자 풀(user pool)은 사용자 디렉터리입니다. 회원 가입, 비밀번호, MFA, 소셜 로그인, 그리고 API가 검사하는 JWT를 담당합니다. 자격 증명 풀(identity pool)은 토큰을 임시 AWS 자격 증명으로 교환합니다. 그래서 모바일 앱이 해당 사용자의 접두사(prefix)로 범위를 제한한 역할로 S3에 직접 업로드할 수 있습니다. "로그인과 내 API용 토큰"이면 사용자 풀, "앱이 AWS를 직접 호출해야 함"이면 자격 증명 풀이며, 보통 사용자 풀 뒤에 둡니다.

구간 2: 요청이 API Gateway에 도착

  • REST API는 더 풍부한 기능(요청 검증, 매핑 템플릿, 캐싱, 사용량 계획과 API 키)을 제공하고, HTTP API는 더 단순하고 저렴합니다.
  • 권한 부여: 사용자 풀 토큰에는 Cognito 권한 부여자, 사용자 지정 로직에는 Lambda 권한 부여자, AWS 호출자에는 IAM.
  • 모의(mock) 통합은 백엔드 없이 고정 응답을 돌려줍니다. 그래서 함수가 생기기 전에도 프런트엔드 팀이 작업을 시작할 수 있습니다.
  • 상태 코드를 읽으십시오. 429는 스로틀링, 504는 통합이 API 제한 시간(REST API 기본 29초)을 넘긴 경우, 502는 대개 프록시 통합에서 Lambda 함수가 잘못된 형태의 응답을 돌려준 경우입니다.

구간 3: 함수 실행

Lambda 설정과, 각 설정이 하지 않는 일을 알아 두십시오. 메모리는 CPU도 함께 정합니다. 제한 시간(timeout)은 호출 하나가 실행될 수 있는 시간만 제한합니다. SDK 클라이언트 생성과 참조 데이터 로드는 핸들러 바깥에 두어 웜(warm) 호출이 재사용하게 하십시오. 예약된 동시성(reserved concurrency)은 함수의 상한을 정하고 그만큼의 용량을 보장합니다. 프로비저닝된 동시성(provisioned concurrency)은 실행 환경을 초기화된 상태로 유지해 콜드 스타트를 없앱니다. VPC에 연결된 함수는 NAT 게이트웨이나 VPC 엔드포인트를 통해서만 인터넷과 퍼블릭 AWS 엔드포인트에 접근합니다.

더 깊이: 콜드 스타트의 실제 정체

Lambda는 코드를 실행 환경(execution environment)에서 실행합니다. 새 환경에 들어온 첫 요청은 환경 생성, 패키지나 이미지 다운로드, 런타임 시작, 핸들러 바깥 코드 실행(init 단계)의 비용을 치릅니다. 같은 환경에 들어오는 이후 요청은 이 모든 과정을 건너뛰고 핸들러만 실행합니다. 그래서 클라이언트 생성을 핸들러 밖으로 옮기면 도움이 되지만, 첫 요청에는 아무 효과가 없습니다. 웜 환경이 준비되는 속도보다 트래픽이 빨리 늘면 Lambda는 새 환경을 만들고, 그 요청들은 init 비용을 치릅니다. 프로비저닝된 동시성은 정해진 수의 환경에 대해 init 단계를 미리 실행하며, 위 설정 중 이 비용을 없애는 것은 이것뿐입니다. 예약된 동시성은 존재할 수 있는 환경의 수만 바꿀 뿐, 환경이 웜 상태인지는 바꾸지 않습니다.

구간 4: 데이터 읽기와 쓰기

DynamoDB 문제는 접근 패턴을 묻습니다. 실행할 쿼리에 맞춰 파티션 키(와 정렬 키)를 설계하고, Scan이 아니라 Query를 쓰십시오. 글로벌 보조 인덱스는 언제든 추가할 수 있지만 최종 일관성만 제공합니다. 로컬 보조 인덱스는 테이블을 만들 때 함께 만들어야 합니다. 쓰기 직후 읽기(read-after-write)가 필요하면 기본 테이블에 ConsistentRead를 쓰며, 읽기 비용은 두 배입니다. 스로틀링(ProvisionedThroughputExceededException)은 지수 백오프(exponential backoff)와 지터(jitter)로 처리하며, SDK가 이미 적용합니다. 캐싱은 DynamoDB에는 DAX, 그 밖에는 지연 로딩(lazy loading)이나 write-through 방식의 ElastiCache를 알아 두십시오.

구간 5: 느린 작업은 비동기로

호출자가 접수 확인만 필요하다면 작업을 큐에 넣고 작업 ID를 돌려주십시오. SQS는 받은 메시지를 가시성 제한 시간 동안 숨깁니다. 처리가 그보다 오래 걸리면 메시지가 다시 나타나 두 번 처리됩니다. 실패한 메시지는 maxReceiveCount를 넘으면 배달 못한 편지 큐(dead-letter queue)로 갑니다. SQS와 스트림 이벤트 소스에서는 ReportBatchItemFailures를 쓰면 Lambda가 실패한 레코드만 재시도합니다. SNS는 메시지 하나를 여러 구독자에게 팬아웃하고, EventBridge는 내용에 따라 이벤트를 라우팅합니다. 전달은 최소 한 번이므로 소비자는 멱등이어야 합니다.

구간 6: 비밀 값과 키

KMS Encrypt는 평문을 최대 4 KB까지만 받습니다. 그래서 파일에는 봉투 암호화(envelope encryption)를 씁니다. GenerateDataKey를 호출하고, 로컬에서 암호화한 다음, 암호화된 데이터 키를 파일과 함께 저장합니다. Secrets Manager는 비밀 값을 저장하고 교체(rotation)합니다. Parameter Store SecureString은 내장 교체 기능 없이 더 저렴하게 구성 값을 보관합니다. 사용자의 대용량 파일 업로드에는 S3 미리 서명된 URL(presigned URL)을 쓰며, 앱에 키를 넣어 배포하는 일은 절대 없어야 합니다.

초보자 팁: DynamoDB 테이블에 쓰는 AWS SAM "hello world" API를 하나 배포한 다음, 한 번에 하나씩 세 가지 방법으로 고장 내 보십시오. 제한 시간을 1초로 두고 2초 sleep을 넣기, 함수 역할에서 테이블 권한 빼기, NAT 게이트웨이가 없는 프라이빗 서브넷에 함수 연결하기입니다. 각 실패를 CloudWatch Logs에서 확인하십시오. 즉시 나오는 AccessDeniedException, Task timed out 한 줄, 제한 시간까지 멈춰 있는 상태는 매우 다르게 보입니다. 문제 해결 문제 상당수는 지금 보고 있는 것이 이 중 무엇인지 알아보라는 것입니다.

구간 7: 코드 배포

SAM 템플릿은 CloudFormation으로 확장됩니다. sam deploy는 CloudFormation 변경 세트(change set)로 배포하며, --confirm-changeset을 쓰면 적용하기 전에 승인을 기다립니다. Lambda 버전은 변경할 수 없고, 별칭(alias)이 버전을 가리키며, 가중치 별칭은 트래픽 일부를 새 버전으로 보냅니다. CodeDeploy는 그 트래픽을 canary(작은 비율 다음 나머지 전체) 또는 linear(같은 크기 단계) 방식으로 옮기고, CloudWatch 경보가 울리면 롤백합니다. 컨테이너는 ECR에서 태그 불변성(tag immutability)을 켜고 커밋 ID로 이미지에 태그를 다십시오. latest만 쓰는 일은 없어야 합니다. AWS AppConfig는 코드를 다시 배포하지 않고 기능 플래그를 점진적으로 바꿉니다.

구간 8: 무언가 고장 남

CloudWatch Logs와 Logs Insights는 함수 하나가 무엇을 했는지 보여 줍니다. AWS X-Ray 트레이스는 요청의 어느 구간이 실패하거나 느렸는지 보여 줍니다. Embedded Metric Format은 사용자 지정 지표를 로그 줄로 기록하므로, 함수가 PutMetricData를 호출하지 않습니다. 해결책을 고르기 전에 신호를 읽으십시오. 즉시 나타나는 오류는 대개 권한이나 검증 문제이고, 정확히 제한 시간만큼 걸리는 오류는 대개 네트워크나 느린 의존성 문제입니다.

그 위의 AI 계층

AI 문제는 네 도메인 전체에 퍼져 있으며, 대부분은 한 가지 규칙으로 풀립니다. AI는 생성하고 요약하고 설명하며, 결정은 결정론적 통제가 내립니다. 빌드 통과 여부는 테스트가, 에이전트가 무엇을 호출할 수 있는지는 IAM이, 롤백은 경보가 결정합니다. Bedrock Guardrails는 프롬프트와 응답의 내용을 필터링할 뿐 API 호출을 승인하지 않으며, 시스템 프롬프트는 아무것도 강제하지 않습니다. Kiro에서 스펙(spec)은 코드를 작성하기 전에 계획을 검토할 수 있게 하고, 스티어링 파일(steering file)은 팀 규칙을 모든 세션에 전달합니다.

학습 순서

  1. Lambda를 처음부터 끝까지, 그다음 API Gateway와 Cognito.
  2. DynamoDB와 캐싱, 그다음 SQS, SNS, EventBridge, Kinesis.
  3. IAM, KMS, Secrets Manager. 그다음 SAM, CloudFormation, CodeDeploy, 컨테이너.
  4. 로그, 지표, X-Ray. Bedrock과 Kiro. 그다음 시간을 재며 여러 주제를 섞은 세트 풀기.
