AWS Certified DevOps Engineer – Professional 시험(DOP-C02)이 특히 좋아하는 정답이 있습니다. 아무도 한밤중에 깨어날 필요가 없는 답입니다. 무언가가 문제를 감지하고, 무언가가 신호를 전달하고, 무언가가 문제를 고치거나 롤백하며, 기록이 남습니다. 사람이 이메일을 읽거나, 스크립트를 실행하거나, 서버에 로그인해야 하는 보기는 대개 오답입니다. 이 가이드는 그 루프를 따라 시험을 설명합니다. 릴리스 루프, 구성 루프, 운영 루프입니다.

학습 가이드 · AWS Certified DevOps Engineer – Professional (DOP-C02)

시험 개요

180분 동안 75문항(채점 65문항, 표시되지 않는 비채점 10문항)을 풀며, 문항은 객관식(multiple choice) 또는 복수 응답(multiple response)입니다. 결과는 100~1,000점의 환산 점수로 나오고 합격 점수는 750점입니다. 도메인은 여섯 개입니다. SDLC Automation(22%), Configuration Management and IaC(17%), Resilient Cloud Solutions(15%), Monitoring and Logging(15%), Incident and Event Response(14%), Security and Compliance(17%)입니다. 2026년 11월 현재 AWS는 DOP-C02의 후속 버전을 발표하지 않았지만, 이 시험의 한국어 버전은 2026년 12월 31일 이후 폐지됩니다.

이 문제은행을 위해 저희가 만든 DOP-C02 문제 395개에서는 특정 서비스 하나가 압도하지 않습니다. CloudWatch, Lambda, CloudFormation, AWS Config, Systems Manager가 각각 열 문제 중 하나꼴로 나오고, IAM, Organizations, CodePipeline, CodeBuild, S3, EventBridge가 바짝 뒤따릅니다. 이렇게 고르게 퍼져 있다는 점이 핵심입니다. 이 시험은 서비스 하나를 깊이 묻지 않고, 서비스들이 어떻게 연결되는지를 묻습니다. 또한 저희 AWS 문제은행의 SAP-C03이나 AIP-C01보다 복수 정답 문제가 적습니다(약 6%. SAP-C03은 9%, AIP-C01은 11%). 그래서 시간 대부분을 조합 고르기가 아니라 긴 시나리오를 읽는 데 씁니다.

각 시나리오를 세 칸으로 나눠 읽으세요. 상황을 감지하는 것, 신호를 전달하는 것, 그에 따라 조치하는 것입니다. 정답은 세 칸을 모두 관리형 구성 요소로 채웁니다.

릴리스 루프: 무엇을 되돌릴 수 있어야 하는지로 배포 방식을 고른다

SDLC Automation은 비중이 가장 큰 도메인이며, 문제는 요구사항의 단어 하나에 좌우되는 경우가 많습니다. "즉시", "점진적으로", "트래픽 전에 검증", "새 인스턴스 없이" 같은 단어입니다.

전략얻는 것
현재 위치(in-place, 롤링)추가 플릿이 필요 없고 같은 인스턴스와 볼륨을 재사용합니다. 롤백은 이전 버전을 다시 배포하는 것입니다. EC2와 온프레미스에서 CodeDeploy는 OneAtATime, HalfAtATime, AllAtOnce를 제공합니다.
블루/그린새 플릿이나 태스크 세트를 트래픽 전환 전에 테스트하고, 이전 것은 계속 실행해 즉시 되돌릴 수 있습니다. 이전 인스턴스에 저장된 것은 미리 옮겨 두지 않으면 사라집니다.
카나리트래픽의 작은 일부를 보내고 기다린 뒤 전체를 보냅니다(Lambda와 ECS).
선형(linear)100%가 될 때까지 일정 간격으로 같은 비율씩 옮깁니다(Lambda와 ECS).

두 버전이 동시에 실행될 때는 같은 데이터베이스를 공유합니다. 따라서 스키마 변경은 하위 호환이어야 합니다. 먼저 추가하고, 코드를 전환하고, 옛 열은 마지막에 제거합니다(흔히 expand and contract라고 부릅니다). 코드 변경과 같은 릴리스에서 열 이름을 바꾸는 보기는 아직 실행 중인 버전을 망가뜨립니다.

배포 주변 요소도 있습니다. 사람의 승인에는 CodePipeline의 수동 승인 작업을, 토큰을 저장하지 않는 GitHub 소스에는 CodeConnections를, 환경 변수의 시크릿 대신 buildspec의 Secrets Manager 참조를 씁니다. CodeDeploy는 EKS에는 아예 배포하지 않습니다(컴퓨팅 플랫폼은 EC2/온프레미스, Lambda, ECS). EKS의 카나리는 Argo Rollouts나 Flagger 같은 Kubernetes 컨트롤러가 맡습니다.

초보자 팁: AWS SAM으로 작은 Lambda 함수를 배포하면서 DeploymentPreference를 Canary10Percent5Minutes로 설정하고, 함수 오류에 대한 CloudWatch 경보를 Alarms에 넣어 보세요. 예외를 던지는 두 번째 버전을 게시하고, 5분 안에 몇 번 호출한 뒤 CodeDeploy가 스스로 트래픽을 되돌리는 모습을 지켜보세요. 실제로 한 번 롤백되는 것을 보면 어떤 표보다 경보-롤백 루프가 잘 이해됩니다. 스택 전체는 명령 하나로 지울 수 있습니다.

구성 루프: 코드형 인프라(IaC)가 대신 해 주지 않는 일

  • 드리프트는 감지될 뿐 일반 업데이트로는 복구되지 않습니다. CloudFormation은 요청을 받으면 스택과 실제 상태를 비교합니다. 스택 드리프트용 AWS Config 관리형 규칙을 쓰면 이 점검이 반복됩니다. 수동 변경을 유지하려면 템플릿에 반영하고 변경 세트(change set)를 검토하세요. (새로 나온 드리프트 인식 변경 세트(drift-aware change set, --deployment-mode REVERT_DRIFT)는 드리프트된 리소스를 템플릿대로 되돌릴 수도 있지만, 일반 업데이트는 그렇지 않습니다.)
  • 기능(capability)은 승인해야 합니다. 사용자 지정 이름을 가진 IAM 리소스에는 CAPABILITY_NAMED_IAM이, SAM과 기타 매크로에는 CAPABILITY_AUTO_EXPAND가 필요합니다.
  • 시크릿은 템플릿에 넣지 않습니다. Secrets Manager에 대한 동적 참조(dynamic reference)를 쓰세요. NoEcho는 값을 화면에서 숨길 뿐입니다. RDS는 서비스가 마스터 암호를 Secrets Manager에서 관리하게 하세요.
  • 시작 템플릿의 새 버전은 이후 시작되는 인스턴스에만 적용됩니다. 실행 중인 Auto Scaling 그룹에 반영하려면 인스턴스 새로 고침(instance refresh)을 쓰세요.
  • 여러 계정에 한꺼번에: Organizations를 통한 서비스 관리형 권한으로 StackSets를 위임된 관리자 계정에서 실행합니다. 개발자가 승인된 제품을 시작해야 한다면 Service Catalog를 씁니다. 개발자에게 없는 권한은 시작 역할(launch role)이 가집니다.
더 깊이: CloudFormation이 드리프트를 그대로 두는 이유

일반 스택 업데이트는 무엇을 바꿀지 정할 때 새 템플릿을 실제 리소스가 아니라 CloudFormation이 마지막으로 배포한 템플릿과 비교합니다. 누군가 콘솔에서 보안 그룹을 수정해도 저장된 템플릿은 그대로이므로, 다음 스택 업데이트는 그 리소스에 할 일이 없다고 보고 수동 수정은 살아남습니다. 드리프트 감지는 이와 별개로, 실제 리소스를 기대 속성과 비교하는 읽기 전용 작업입니다. 나중에 템플릿 변경이 그 리소스를 건드리면, 속성에 따라 CloudFormation이 수동 변경을 덮어쓰거나 업데이트가 실패하며, 일반 변경 세트는 이를 미리 알려 주지 않습니다(실제 상태와 비교하는 것은 드리프트 인식 변경 세트뿐입니다). 그래서 시험의 정답은 언제나 "업데이트를 실행해 드리프트를 고친다"가 아니라 변경을 템플릿으로 옮기는(또는 되돌리는) 것입니다.

운영 루프: 수동 단계 없는 복원력

Resilient Cloud Solutions 문제는 장애를 플랫폼이 처리하는 설계를 선호합니다. 로드 밸런서 상태 확인을 쓰는 다중 AZ Auto Scaling 그룹, 고정 세션(sticky session) 대신 ElastiCache나 DynamoDB에 둔 세션 상태, 콜드 스타트를 없애는 Lambda 프로비저닝된 동시성(reserved concurrency는 상한을 두고 예약할 뿐입니다), 리전 간 관계형 복구를 위한 Aurora Global Database, 모든 리전이 쓰기를 받아야 할 때의 DynamoDB 전역 테이블이 그 예입니다. Multi-AZ 데이터베이스 장애 조치 후 애플리케이션은 DNS 이름으로 다시 연결해야 합니다. 이름은 그대로이고 주소가 바뀌기 때문입니다.

학습 순서

  1. CodePipeline, CodeBuild, CodeDeploy를 처음부터 끝까지. 모든 배포 구성과 롤백 설정을 포함합니다.
  2. CloudFormation 심화(변경 세트, 드리프트, 스택 정책, StackSets, 동적 참조), 이어서 CDK와 SAM.
  3. CloudWatch 지표, 경보, Logs Insights, 지표 필터. EventBridge 패턴과 교차 계정 버스.
  4. Systems Manager(Automation, Run Command, Patch Manager, Parameter Store, OpsCenter)와 Config 수정 조치.
  5. Organizations, Identity Center, 멀티 계정 보안. 그다음 180분 시계를 맞춰 놓고 종합 세트.
