SC-900(Microsoft Security, Compliance, and Identity Fundamentals)에는 수십 개의 Microsoft 제품 이름이 나옵니다. 하지만 대부분의 문제는 한 가지로 귀결됩니다. 지문이 설명하는 일을 이 중 어느 제품이 하는가입니다. 그 일은 거의 항상 동사에 담겨 있습니다. 위험한 로그인을 "탐지한다", MFA를 "요구한다", 문서를 "분류한다", 이메일을 7년간 "보관한다", Microsoft가 감사받았음을 "증명한다" 같은 식입니다. 이 가이드는 제품을 이런 동사별로 정리했습니다. 그러면 선택지를 읽기 전에 지문만 보고도 올바른 제품군으로 바로 갈 수 있습니다.

학습 가이드 · Microsoft Security, Compliance, and Identity Fundamentals (SC-900)

시험 개요

시험 시간은 45분이고, 합격 점수는 1~1,000점 척도에서 700점입니다. Microsoft는 문항 수를 고정해 공개하지 않으므로(이 문제은행의 모의고사는 45문항을 씁니다) 시간 기준으로 속도를 조절하세요. 평가 영역은 Describe the concepts of security, compliance, and identity(10–15%), Describe the capabilities of Microsoft Entra(25–30%), Describe the capabilities of Microsoft security solutions(35–40%), Describe the capabilities of Microsoft compliance solutions(20–25%)입니다. 원하는 언어로 시험이 제공되지 않으면 30분 추가 시간을 신청할 수 있습니다.

이 시험은 깊이보다 범위가 넓습니다. 이 문제은행의 SC-900 문제 225개는 보안 솔루션 84개, Microsoft Entra 62개, 규정 준수 51개, 개념 28개로 나뉩니다. Entra와 보안 문제만 봐도 40개가 넘는 제품과 기능이 나오고, 그중 어느 것도 16문제를 넘지 않습니다. 다섯 문제에 하나는 단순한 정의 문제이고, 또 다섯 문제에 하나는 닮은꼴 두 개를 비교합니다. 현재 이름을 쓰세요. Microsoft Entra ID, Microsoft Defender XDR, Microsoft Purview입니다.

동사 지도

지문 속 동사제품 또는 기능
내가 누구인지 증명한다Microsoft Entra ID의 인증 방법: MFA, 암호 없는 인증(Windows Hello for Business, FIDO2 키, 패스키), 셀프 서비스 암호 재설정, 암호 보호.
들여보낼지 결정한다Conditional Access(조건부 액세스): 이런 신호(사용자, 위치, 장치, 앱, 위험)가 있으면 차단하거나, MFA나 규정을 준수하는 장치 같은 요구 사항을 붙여 허용합니다.
로그인이 얼마나 위험한지 점수를 매긴다Microsoft Entra ID Protection(로그인 위험과 사용자 위험). 계산은 ID Protection이 하고, 그 결과에 따라 행동하는 것은 Conditional Access입니다.
관리자 권한을 필요할 때만 준다Privileged Identity Management: 자격 있는(eligible) 역할을 필요한 시점에(just in time) 활성화하고, 자동으로 만료됩니다.
누가 아직 접근 권한이 필요한지 확인한다액세스 검토(access reviews). 접근 권한을 묶어 요청과 승인을 받게 하는 것은 권한 관리(entitlement management). 입사, 부서 이동, 퇴사 작업은 수명 주기 워크플로(lifecycle workflows).
네트워크 트래픽을 걸러내거나 흡수한다NSG(서브넷과 NIC에 거는 규칙), Azure Firewall(상태 저장, 네트워크 전체), Web Application Firewall(SQL 인젝션 같은 7계층 공격), DDoS Protection(트래픽 폭주).
취약한 구성을 찾는다Microsoft Defender for Cloud의 보안 태세 관리(CSPM)와 보안 점수(secure score).
전체 환경에서 탐지하고 대응한다Microsoft Sentinel(SIEM과 SOAR, 모든 소스). Microsoft 자체의 엔드포인트, ID, 이메일, 앱 신호를 연관 지어 인시던트로 묶는 것은 Microsoft Defender XDR.
파일이 어디로 가든 분류하고 보호한다민감도 레이블(sensitivity labels, Microsoft Purview Information Protection).
민감한 데이터에 대한 행동을 막는다데이터 손실 방지(DLP). 내부자의 장기적인 위험 행동은 내부자 위험 관리(insider risk management).
일정에 따라 보관하거나 삭제한다보존 정책(retention policies, 위치 전체)과 보존 레이블(retention labels, 개별 항목). 특정 소송 하나를 위해 보존하는 것은 eDiscovery 보존(hold).
누가 무엇을 했는지 기록한다감사(Audit). 기록만 하며, 차단하거나 암호화하거나 보존하지 않습니다.
Microsoft 자체의 규정 준수를 증명한다Service Trust Portal(ISO, SOC 같은 감사 보고서). 우리 회사의 통제 항목을 추적하는 것은 Compliance Manager와 규정 준수 점수(compliance score).

초보자 팁: 연습할 때 손으로 선택지를 가리고, 지문의 동사와 예상하는 제품을 적은 뒤 손을 떼세요. 예상한 제품이 선택지에 있으면 끝입니다. 없다면 그 문제는 닮은꼴 쌍을 묻는 것이니, 그 쌍을 목록에 추가하세요. 연습 세트를 두세 개 풀고 나면 목록은 짧아지고, 그것이 바로 복습할 내용입니다.

개념 영역은 아래 띠들의 용어를 제공합니다. 지문의 동사를 띠에 맞춘 다음, 제품에 맞추세요.

개념: 정확한 용어를 익히세요

가장 작은 영역이지만 나머지 영역에 쓰이는 용어를 제공합니다. 공동 책임 모델(IaaS, PaaS, SaaS에서 무엇이 Microsoft로 넘어가고, 무엇이 절대 넘어가지 않는지. 넘어가지 않는 것은 데이터, 엔드포인트, 계정, 액세스 관리입니다), 심층 방어(defense in depth), 제로 트러스트(명시적으로 확인, 최소 권한 사용, 침해를 가정), 암호화 대 해싱, 인증 대 인가, ID 공급자와 페더레이션이 여기에 속합니다. 대개 한 줄짜리 정의 문제이고, 오답 선택지는 두 용어를 뒤바꿔 놓습니다.

Microsoft Entra: 누가 무엇을 결정하는가

여기서는 두 역할 체계가 오답의 대부분을 만듭니다. Microsoft Entra 역할은 디렉터리를 관리합니다. 사용자, 그룹, 암호, 앱 등록이 그 대상입니다. Azure RBAC는 VM이나 스토리지 계정 같은 Azure 리소스를 관리합니다. Global Administrator라고 해서 자동으로 모든 구독의 Owner가 되지는 않습니다. ID 보호 도구 세 가지도 구분하세요. ID Protection은 Microsoft Entra 로그인과 사용자의 위험 점수를 매기고, Defender for Identity는 온프레미스 Active Directory 신호(이제는 Microsoft Entra ID 신호도)로 ID 공격을 탐지하며, Conditional Access는 결정을 실제로 집행하는 엔진입니다.

더 깊이: 보안 기본값과 Conditional Access는 함께 쓰지 않습니다

보안 기본값(security defaults)은 새 테넌트에서 켜져 있는 무료 일괄 패키지입니다. 모든 사용자가 MFA를 등록하고, 관리자는 항상 MFA를 쓰며, MFA를 지원하지 못하는 레거시 인증 프로토콜은 차단됩니다. 일부 사용자나 앱에만 적용하도록 범위를 정할 수는 없습니다. Conditional Access는 이를 대신하는 유연한 방식으로, Microsoft Entra ID P1이 필요하고(위험 기반 조건에는 P2) 두 가지를 함께 쓰지 않습니다. 테넌트가 Conditional Access로 옮겨 가면 보안 기본값을 끕니다. 그래서 "Free 버전을 쓰는 작은 회사가 설정 없이 기본 보호를 원한다"는 보안 기본값을 가리키고, "사무실 밖에서만 MFA를 요구한다"는 Conditional Access를 가리킵니다. 또한 Conditional Access는 첫 번째 인증 요소 이후에 실행됩니다. 그래서 네트워크 트래픽 폭주에 대한 답이 될 수 없습니다.

보안 솔루션: 가장 큰 영역

Defender 제품군은 각각 무엇을 보호하는지로 익히세요. Defender for Office 365(이메일과 협업), Defender for Endpoint(장치), Defender for Identity(ID 공격, 출발점은 온프레미스 AD), Defender for Cloud Apps(SaaS 앱, 클라우드 액세스 보안 브로커(CASB) 역할), Defender for Cloud(Azure, 다른 클라우드, 온프레미스 서버)입니다. 이메일 보호의 시간 순서도 알아 두세요. Safe Attachments는 배달 전에, Safe Links는 클릭하는 순간에, 제로아워 자동 제거(zero-hour auto purge)는 배달 후에 작동합니다. Sentinel에서 자동화 규칙(automation rules)은 인시던트를 중앙에서 관리하고, Logic Apps로 만든 플레이북(playbooks)은 다른 시스템에서 조치를 실행합니다. Sentinel은 Microsoft Defender 포털로 옮겨 가는 중이며, 2027년 3월 31일 이후에는 Azure 포털에서 더 이상 지원되지 않습니다.

더 깊이: 결과 하나를 고쳐도 보안 점수가 오르지 않을 수 있는 이유

Azure 포털의 기존(classic) 보안 점수 이야기입니다. Defender for Cloud는 권장 사항을 보안 제어(security controls)로 묶고, 각 제어에는 최대 점수가 정해져 있습니다. 리소스는 그 제어의 모든 권장 사항을 통과해야만 점수를 받습니다. VM에 열린 결과가 두 개 있는데 하나만 고치면 점수는 그대로입니다. 기본 제공 Microsoft cloud security benchmark 권장 사항만 점수에 반영되고, 미리 보기 권장 사항은 빠집니다. 점수가 권장 사항으로 만들어지므로 공격이 아니라 구성을 측정합니다. Defender 포털에는 이제 Defender for Cloud의 위험 기반 Cloud Secure Score도 있는데, 계산 방식과 값이 다른 별개의 모델입니다. 같은 포털의 Microsoft Secure Score는 또 다른 지표입니다.

규정 준수 솔루션: 던져야 할 세 가지 질문

  1. Microsoft의 규정 준수인가, 우리 회사의 규정 준수인가? Service Trust Portal 대 Compliance Manager.
  2. 콘텐츠가 무엇인지의 문제인가, 얼마나 오래 남는지의 문제인가? 민감도 레이블 대 보존.
  3. 지금 한 번의 행동인가, 시간에 걸친 패턴인가? DLP 대 내부자 위험 관리.
