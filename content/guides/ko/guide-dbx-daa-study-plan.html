영업 관리자가 묻습니다. "지난주 지역별 매출은 얼마였나요?" Databricks에서 분석가는 적어도 다섯 곳에서 이 질문에 답할 수 있습니다. SQL 편집기의 쿼리, 뷰, 구체화된 뷰(materialized view), AI/BI 대시보드, 그리고 관리자가 직접 묻는 Genie Agent입니다. Databricks Certified Data Analyst Associate 시험은 대부분 이 중에서 무엇을 고를지, 그리고 단계마다 달라지는 두 가지 세부 사항을 묻습니다. 어떤 컴퓨팅이 쿼리를 실행하는지, 누구의 데이터 권한이 적용되는지입니다. 이 가이드는 질문 하나를 다섯 곳 모두에서 따라갑니다.

장소 1: SQL 편집기의 쿼리

쿼리는 Databricks SQL용 컴퓨팅인 SQL 웨어하우스에서 실행됩니다. 데이터는 클라우드 스토리지에 있고, Unity Catalog가 이를 관리하며, 웨어하우스가 실제 작업을 합니다. sales.emea.orders를 읽으려면 분석가에게 USE CATALOG, USE SCHEMA, SELECT가 필요합니다. BROWSE는 Catalog Explorer에서 테이블 이름과 주석만 볼 수 있게 해 줍니다. 검색에서는 테이블이 보이는데 권한 오류가 나는 지문이 바로 이 경우입니다.

이 장소의 문제는 오류 없이 틀린 답을 내는 SQL을 묻습니다. 다음은 외워 두세요.

  • WHERE region = NULL은 아무것도 반환하지 않습니다. IS NULL을 쓰세요.
  • WHERE에 집계 함수를 쓰면 실패합니다. 그 조건은 HAVING에 들어가야 합니다.
  • LEFT JOIN 뒤에 오른쪽 테이블 열에 대한 WHERE 조건을 붙이면 조용히 내부 조인이 됩니다. 조건을 ON으로 옮기세요.
  • 조인 후 SUM이 너무 크게 나오면 팬아웃(fan-out)입니다. 먼저 다(多) 쪽을 키당 한 행으로 집계하세요.
  • count(col)은 NULL을 건너뛰고, count(*)는 건너뛰지 않습니다.

Genie Code(이전 이름 Databricks Assistant)가 편집기에서 SQL을 작성하고 고쳐 줄 수 있지만, 시험은 여전히 그 수정이 왜 맞는지 알기를 기대합니다.

초보자 팁: SQL 편집기에서 아주 작은 테이블 두 개를 만드세요. 행이 세 개인 customers와, 한 고객은 주문이 두 건이고 한 고객은 주문이 없는 orders입니다. LEFT JOIN을 작성한 뒤 WHERE o.amount > 0을 추가하면 주문 없는 고객이 사라지는 것을 볼 수 있습니다. 조건을 ON으로 옮기면 다시 나타납니다. 그다음 조인 후에 고객 열을 합산하면 값이 두 배가 되는 것을 확인할 수 있습니다. 이 두 실험이 "이 결과는 왜 틀렸을까?" 문제의 상당 부분을 해결해 줍니다.

장소 2와 3: 뷰 또는 구체화된 뷰

같은 쿼리를 다시 쓸 거라면 저장하세요. 선택의 기준은 비용을 언제 치르느냐입니다.

객체저장하는 것고를 때
표준 뷰쿼리만 저장. 읽을 때마다 전체를 실행합니다.가벼운 로직이고 항상 최신이어야 할 때.
동적 뷰쿼리만 저장. is_account_group_member()나 session_user()로 읽는 사람별로 행이나 열을 숨깁니다.그룹마다 다른 데이터를 봐야 할 때. 기억하세요: 기본 테이블에 SELECT 권한이 있는 사람은 이를 우회합니다.
구체화된 뷰미리 계산된 결과. 수동으로, 일정에 따라, 또는 작업(job)으로 새로 고칩니다.대시보드에 공급하는 무거운 집계. 읽기는 빠르고, 비용은 새로 고침 시점으로 옮겨 갑니다.

구체화된 뷰는 마지막 새로 고침 시점의 데이터를 보여 줍니다. 지문에서 대시보드 숫자가 "하루 늦다"고 하면 다른 무엇보다 먼저 새로 고침 일정을 보세요. 감사에는 Delta 이력이 도움이 됩니다. DESCRIBE HISTORY는 누가 언제 테이블을 바꿨는지 알려 주고, VERSION AS OF로는 지난달 보고서의 바탕이 된 상태를 조회할 수 있습니다.

장소 4: AI/BI 대시보드

대시보드에는 데이터셋이 있는 Data 탭과 위젯이 있는 Canvas가 있습니다. 데이터셋을 한 번 다듬고(필요한 열, 필요한 행), 위젯이 이를 잘라 보게 하세요. 대시보드 문제 대부분은 두 가지 설정으로 결정됩니다.

필터 대 매개 변수. 필드 필터는 열 기준으로 데이터셋 결과를 좁히며, SQL을 바꿀 필요가 없고, 작은 데이터셋에서는 브라우저에서 실행됩니다. :start_date 같은 매개 변수는 SQL 텍스트 자체를 바꾸므로 항상 웨어하우스에서 실행됩니다. 하위 쿼리 안의 날짜처럼 값이 쿼리 안쪽까지 들어가야 할 때 매개 변수를 쓰세요.

게시 설정. 공유 데이터 권한(shared data permissions)(기본값)에서는 모든 뷰어가 게시자가 볼 수 있는 것을 보므로, 뷰어에게 테이블 접근 권한이 필요 없습니다. 개별 데이터 권한(individual data permissions)에서는 쿼리가 각 뷰어로 실행되고, 뷰어 본인의 행 필터와 열 마스크가 적용됩니다. 어느 쪽이든 컴퓨팅은 게시자의 것을 씁니다. "지역 관리자는 자기 지역만 봐야 한다"는 지문은 대시보드를 따로 만드는 것이 아니라 개별 권한이나 행 필터를 원합니다.

더 깊이: 쿼리를 두 번째 실행하면 빠른 이유, 그리고 빠르지 않을 때

Databricks SQL에는 캐시가 여러 개 있습니다. 결과 캐시(result cache)는 바뀌지 않은 테이블에 대한 동일한 쿼리의 저장된 결과를 거의 즉시 돌려줍니다. 그중 로컬 부분은 웨어하우스 메모리에 있어서 웨어하우스가 멈추면 사라집니다. 서버리스 웨어하우스에서는 원격 결과 캐시가 정지 후에도 남습니다. 디스크 캐시는 스토리지에서 읽은 데이터 파일을 로컬 SSD에 보관하며, 역시 정지하면 지워집니다. 그래서 밤사이 자동 정지된 뒤 처음 실행하는 무거운 쿼리는 느리고 그다음은 빠릅니다. 쿼리를 고쳐 쓴 효과를 공정하게 측정하려면 SET use_cached_result = false가 필요한 이유도 여기에 있습니다. 대시보드에는 고유한 동작이 더 있습니다. 작은 데이터셋은 처음 로드한 뒤 브라우저에서 필터링되므로, 그런 상호 작용은 쿼리 기록에 아예 나타나지 않습니다.

장소 5: Genie Agent

Genie Agents(이전 이름 Genie spaces)는 관리자가 일상 언어로 질문하게 해 줍니다. 시험은 설정과, 여기서도 권한을 묻습니다.

  • 컴퓨팅과 데이터는 서로 다른 ID를 씁니다. 기본 웨어하우스를 저장하면 작성자의 컴퓨팅 자격 증명이 포함되므로, 사용자에게 웨어하우스 권한이 필요 없습니다. 데이터 접근은 항상 질문하는 사용자 본인의 Unity Catalog 권한으로 확인합니다. 에이전트를 공유해도 데이터 권한이 부여되지는 않습니다.
  • 컨텍스트는 신뢰도 순서로. 설명이 잘 달린 연결 테이블과 메트릭 뷰(metric view)가 먼저이고, 그다음은 예시 SQL 쿼리와 측정값과 필터를 위한 SQL 식이며, 일반 텍스트 지침이 마지막입니다. 작게 시작하세요. 목적은 좁게, 테이블은 적게.
  • 품질 측정. SQL Answer가 있는 벤치마크는 자동으로 채점됩니다. 사용자 피드백("Is this correct?")은 편집자에게 어디에 예시를 추가할지 알려 줄 뿐, 그 자체로 에이전트를 바꾸지는 않습니다.
더 깊이: "Florida"가 더는 일치하지 않게 되는 이유

Genie는 저장된 값을 기준으로 SQL을 씁니다. 사용자가 "Florida"를 입력했는데 열에 FL로 저장되어 있으면, 프롬프트 매칭(prompt matching, 형식 지원과 엔터티 매칭)이 그 열의 고유값을 저장한 목록으로 차이를 메웁니다. 이 목록은 스냅샷입니다. 데이터에 새 코드나 형식이 들어오면 스냅샷이 낡아서 Genie가 아무것도 일치하지 않는 필터를 만들기 시작합니다. 이런 문제가 가리키는 해결책은 새 지침이 아니라 그 열의 Refresh prompt matching입니다.

나머지 점수가 있는 곳

Importing Data: 아무것도 만들지 않고 파일을 탐색하는 read_files, 일회성 파일을 볼륨에 올리는 업로드 UI, 읽기 전용 카탈로그로 도착하는 공유 데이터를 위한 OpenSharing(이전 이름 Delta Sharing)과 Marketplace, 외부 데이터베이스를 그 자리에서 쿼리하는 Lakehouse Federation. Data Modeling: 스타 스키마의 팩트와 차원, 메달리온 계층. Analyzing Queries: Query History와 쿼리 프로필, Photon, 관리형 테이블의 Liquid Clustering과 예측 최적화(predictive optimization).

학습 순서

  1. SQL 정확성: 조인, 집계, NULL, 윈도 함수, 집합 연산자.

  3. 대시보드: 데이터셋, 필터, 매개 변수, 게시, 일정, 알림.
