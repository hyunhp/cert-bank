Professional Cloud Security Engineer 시험에는 제품이 많이 나오고, 그중 상당수가 비슷하게 들립니다. 정책, 경계(perimeter), 경계(boundary), 프록시, 보안 상태(posture)가 그렇습니다. 돌파구는 모든 통제가 정확히 한 가지 질문에 답한다는 점을 알아차리는 것입니다. IAM은 "누가 이 API를 호출할 수 있는가?"에 답합니다. VPC Service Controls는 "이 데이터가 이 선을 넘어도 되는가?"에 답합니다. Access Transparency는 "Google 직원이 무엇을 했는가?"에 답합니다. 이 시험의 오답은 거의 언제나 다른 질문에 답하는 실제 통제입니다. 이 가이드는 시험 내용을 그 질문별로 묶어 정리합니다.

학습 가이드 · Google Cloud Certified Professional Cloud Security Engineer (GCP-PSE)

시험 개요

2시간 동안 객관식 50~60문항을 풉니다. Google은 합격 점수를 공개하지 않으므로, 최신 세부 사항은 공식 시험 페이지에서 확인하세요. 섹션은 다섯 개이며, 시험 가이드에 나온 대략적인 비중은 Configuring access(약 25%), Securing communications and establishing boundary protection(약 22%), Ensuring data protection(약 23%), Managing operations(약 19%), Supporting compliance requirements(약 11%)입니다.

이 문제은행을 위해 저희가 만든 GCP-PSE 문제 275개 중 79개(29%)가 트러블슈팅 문제입니다. 동작해야 할 것이 막혔거나, 막혀야 할 것이 허용된 상황입니다. 문제 본문이나 보기에 서비스 계정이 나오는 문제는 45개, 조직 정책은 35개, Cloud KMS는 23개입니다. 요청이 왜 허용 또는 거부됐는지 계층별로 설명할 수 있다면, 이 시험의 상당 부분을 풀 수 있습니다.

"당신은 누구인가?": ID

Active Directory를 계속 쓰는 회사에는 별개의 흐름이 두 개 필요합니다. 프로비저닝은 Cloud Identity에 사용자와 그룹을 만드는 것으로, 보통 Google Cloud Directory Sync를 씁니다. 로그인은 사용자를 SAML로 ID 공급자에게 보내 비밀번호와 MFA를 확인하는 것입니다. 문제는 일부러 둘을 섞습니다. 동기화 문제는 SSO를 바꿔도 해결되지 않고, 어설션의 NameID가 사용자의 기본 이메일과 일치하지 않아 생긴 SSO 실패는 다시 동기화해도 해결되지 않습니다. 최고 관리자(super admin) 계정은 외부 ID 공급자를 거치지 않으므로, Google 자체의 2단계 인증으로 보호하세요.

소프트웨어에는 "다른 방법이 있다면 키는 쓰지 않는다"가 원칙입니다. Google Cloud 안에서는 연결된 서비스 계정을, 밖에서는 Workload Identity Federation을, 계정으로 행동해야 하는 사람에게는 가장(impersonation)을 씁니다. 조직 정책으로 새 키 생성을 막고, 아직 키 생성이 허용된 프로젝트에는 Editor 역할을 남겨 두지 마세요. Editor는 같은 프로젝트의 더 강력한 계정에 대한 키를 만들 수 있기 때문입니다.

"무엇을 할 수 있는가?": 승인

허용 정책은 권한을 부여하며 상속됩니다. 거부 정책은 먼저 검사되고, 상속되며, 중앙 가드레일 하나를 세우는 방법입니다(예: 지정된 그룹 외에는 누구도 production 태그가 붙은 프로젝트를 삭제할 수 없음). Privileged Access Manager는 상시 관리자 권한을, 사유 입력과 승인을 요구할 수 있는 기한부 권한 부여로 바꿉니다. 그리고 무언가가 예상대로 동작하지 않을 때는 알맞은 진단 도구를 쓰세요. Policy Analyzer는 "누가 무엇에 접근할 수 있는가", Policy Troubleshooter는 "이 주 구성원은 왜 이 권한을 가졌는가(또는 없는가)", Policy Simulator는 "이 정책을 적용하면 무엇이 바뀌는가"에 답합니다.

"이 선을 넘을 수 있는가?": 경계

통제를 계층에 맞추세요. 방화벽 정책은 IP 주소와 포트에 작용합니다. Cloud Armor는 백엔드에 닿기 전, 에지에서 HTTP(S) 트래픽을 걸러 냅니다. IAP는 ID와 컨텍스트로 웹 애플리케이션 접근을 통제합니다. VPC Service Controls는 Google API 수준에서 작동하며, 경계 안의 프로젝트와 경계 밖의 모든 것 사이에서 데이터가 이동하는 것을 막습니다.

더 깊이: 방화벽이 Google API를 통한 데이터 유출을 막지 못하는 이유

공격자가 소유한 버킷을 포함해, 세상의 모든 Cloud Storage 버킷은 같은 엔드포인트 storage.googleapis.com으로 접근합니다. 따라서 VM이 Cloud Storage와 통신하도록 허용하는 방화벽 규칙은 어느 버킷으로든 데이터를 복사할 수 있게 허용하는 셈이고, 엔드포인트를 막는 규칙은 정상적인 작업까지 망가뜨립니다. 호출자가 유효한 자격 증명을 가진 경우에는 IAM도 도움이 되지 않습니다. 탈취된 키나 내부자가 정확히 그런 경우입니다. VPC Service Controls는 요청 자체를 봅니다. 대상 리소스가 어느 프로젝트에 속하는지, 그 프로젝트가 경계 안에 있는지를 확인합니다. 네트워크 경로와 IAM 권한이 모두 문제없더라도, 경계 밖 버킷으로의 복사는 거부됩니다. 그래서 Google은 IAM과 경계를 함께 쓰라고 권장하며, 경계 변경은 먼저 테스트 실행(dry run) 모드로 시험해 보라고 합니다. 테스트 실행 모드는 실제로 막지 않고, 막혔을 요청을 기록합니다.

초보자 팁: 테스트 프로젝트 두 개를 준비해, 그중 하나에 테스트 실행 모드의 VPC Service Controls 경계를 만드세요. 보호된 프로젝트의 VM 서비스 계정에 다른 프로젝트 버킷의 쓰기 권한을 주고, 파일을 그곳으로 복사합니다. 복사는 성공하지만, 감사 로그에 경계 이름과 사유가 적힌 테스트 실행 위반 기록이 남습니다. 실제 위반 항목을 하나 읽어 보면 인그레스·이그레스 규칙 문제가 훨씬 쉬워집니다. 규칙이 일치시켜야 할 ID, 메서드, 프로젝트를 그 항목이 정확히 보여 주기 때문입니다.

"유출되면 무엇을 읽을 수 있는가?": 데이터 보호

Google Cloud는 저장 데이터를 이미 기본으로 암호화합니다. CMEK는 없던 암호화를 더하는 것이 아니라 통제권을 더합니다. 키를 어디에 두는지, 어떻게 순환하는지, 키 사용의 감사 기록, 그리고 키를 비활성화해 서비스가 데이터에 접근하지 못하게 하는 능력입니다. 승인된 사용자가 서비스를 통해 읽는 것은 막지 못합니다. 서비스가 호출자를 대신해 복호화하기 때문입니다. Cloud HSM은 키를 하드웨어에 보관하고, Cloud EKM은 키를 Google 밖에 보관합니다. 대신 외부 키 관리자의 가용성에 의존하게 됩니다.

Sensitive Data Protection은 민감한 데이터를 찾고, 검사하고, 익명화합니다. 어떤 변환을 되돌릴 수 있는지 알아 두세요. 삭제(redaction)와 마스킹은 되돌릴 수 없습니다. 결정적 암호화(AES-SIV)와 형식 보존 암호화는 같은 암호화 키(보통 Cloud KMS로 래핑)로 되돌릴 수 있습니다.

"어떻게 알아챌 것인가?": 운영과 증거

관리자 활동(Admin Activity) 감사 로그는 항상 켜져 있습니다. 데이터 액세스(Data Access) 로그는 BigQuery를 제외하면 꺼져 있습니다. 그래서 "아무것도 보이지 않는" 탐지기는 이 로그가 빠진 경우가 많습니다. 방화벽 규칙 로깅은 연결이 시작될 때의 판정을 기록하고, VPC 흐름 로그는 진행 중인 트래픽을 샘플링합니다. 둘 다 페이로드는 기록하지 않습니다. 페이로드는 Packet Mirroring이 기록합니다. 로그는 집계 싱크(aggregated sink)로 잠긴 중앙 프로젝트에 보내세요. 공급망 문제에서는 취약점 스캔이 문제를 찾고, Binary Authorization이 배포 시점에 증명(attestation)을 강제합니다.

"공급자는 무엇을 했는가?": 규정 준수

Access Transparency는 Google 직원이 내 데이터로 무엇을 했는지 기록합니다. Access Approval은 그들이 접근하기 전에 내 승인을 요구합니다(지원 서비스 한정, 문서화된 예외 있음). Assured Workloads는 규제 체계에 맞는 통제 패키지를 폴더에 적용합니다. 어떤 제품도 혼자서 규정을 충족하지는 못합니다. 그리고 새 조직 정책은 대개 소급 적용되지 않습니다. 예방 제약조건에, 기존 위반을 찾아내는 탐지 통제를 함께 짝지으세요.

학습 순서

  1. ID와 IAM(약 25%)을 진단 도구와 함께. 트러블슈팅 문제는 여기서 시작합니다.
  2. 경계: 방화벽 정책, Cloud Armor, IAP, 그다음 VPC Service Controls 심화.
  3. 데이터 보호: Cloud KMS, CMEK, Sensitive Data Protection, Secret Manager.
  4. 로깅, 탐지, 공급망, 이어서 규정 준수 통제, 그다음 종합 세트.
