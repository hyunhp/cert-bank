Application Developer – Associate 문제 상당수는 사실 한 가지 질문입니다. 이것은 어느 구성 요소가 맡아야 할까요? 검증 규칙, 계산된 점수, 후속 알림, 협력사 포털, 자유 텍스트 분류기는 각각 Foundry 안에 알맞은 자리가 있고, 오답 보기는 대개 그것을 다른 곳에 둡니다. 그 자리를 익히는 가장 좋은 방법은 머릿속으로 애플리케이션 하나를 만들면서 층마다 시험이 무엇을 물을지 생각해 보는 것입니다. 이 가이드는 간단한 설비 점검 앱으로 데이터 모델부터 모니터링까지 그 과정을 따라갑니다.

학습 가이드 · Palantir Application Developer – Associate (PLTR-APD)

시험 요약

3시간 동안 객관식 85문제를 풀며, 오픈북이고, 70% 이상 맞히면 합격이며, 도메인은 여덟 개입니다. 자격증은 2년 동안 유효하며, 불합격하면 14일을 기다린 뒤 재응시할 수 있습니다. Palantir는 도메인별 비중을 공개하지 않으므로, 이 문제은행은 여덟 도메인에 같은 비중을 둡니다. 최신 정보는 공식 시험 페이지를 확인하십시오.

이 문제은행의 PLTR-APD 문제 425개 중 거의 절반이 활용 사례 문제("팀에 X가 필요하다. 개발자는 무엇을 만들어야 하는가?")이고, 3분의 1 가까이가 문제 해결 시나리오입니다. 가장 자주 나오는 주제는 Action 유형이며, Automate, Workshop, Functions가 그 뒤를 잇습니다.

예제

점검자는 태블릿으로 펌프 점검 결과를 기록하고, 감독자는 불합격 건을 검토하고, 협력업체는 포털에서 배정된 작업을 확인하며, 불합격한 점검마다 후속 작업이 필요합니다. 이것을 층별로 만들어 보겠습니다.

1층: 화면보다 모델이 먼저

  • Pump는 기준 시스템(system of record)의 자산 번호를 키로 하는 객체 유형입니다. 이름과 위치는 키가 아닙니다. 키 값이 바뀌면 플랫폼은 새 객체로 인식하고, 사용자 편집과 링크가 사라진 것처럼 보입니다.
  • Inspection은 Pump의 목록 속성이 아니라 독립된 객체 유형입니다. 자체 데이터(날짜, 결과, 메모)를 가진 이벤트이며, Pump 및 Inspector와 다대일로 연결됩니다. 그러면 이력은 날짜순으로 정렬한 링크 탐색이 됩니다.
  • 펌프, 밸브, 압축기를 함께 나열해야 한다면, 빈 속성 수십 개를 가진 만능 유형 하나로 합치지 말고 인터페이스(interface)를 공유하게 하십시오.

대상이 존재하는데 링크가 비어 보인다면 먼저 키 형식(대소문자, 자릿수 채우기, 접두사)을 비교하고, 사용자가 대상을 볼 수 있는지 확인하십시오. 무엇이든 이름을 바꾸거나 지우기 전에, Workflow Lineage에서 그것에 의존하는 모듈, Function, Action, 자동화를 확인하십시오.

2층: 쓰기는 Action을 거친다

"Record Inspection"은 Action 유형입니다. 속성 몇 개를 직접 설정하는 것은 선언적(declarative) Action입니다. 실제 계산이나 연쇄 변경이 생길 때만 함수 기반(function-backed) Action이 됩니다. 예를 들어 불합격 결과가 나오면 그 펌프의 열린 작업 지시를 닫고 새 작업 지시를 만들어야 하며, 이 모두가 함께 성공하거나 함께 실패해야 하는 경우입니다.

좋은 Action 폼은 현재 선택에서 값을 미리 채우고, 유효한 목록을 제시하며, 중대한 변경에는 사유를 요구합니다. 하지만 객체의 현재 상태나 실행하는 사용자에 관한 규칙은 제출 조건(submission criteria)에도 두어야 하며, 어떤 규칙에 걸렸는지 알려 주는 메시지를 함께 두십시오.

더 깊이: 폼 제약만으로는 부족한 이유

폼은 열린 시점의 객체 모습을 기준으로 채워집니다. 사용자가 제출할 때쯤에는 다른 사용자나 자동화가 객체를 바꿨을 수 있습니다. 점검이 이미 승인되었거나, 마지막 예비 부품이 이미 예약되었을 수 있습니다. 제출 조건은 Action이 실제로 실행될 때 현재 상태와 실행하는 사용자를 기준으로 평가되므로, 이런 경쟁 상황에서도 유지됩니다. 같은 이유로 Workshop의 조건부 표시는 보안이 아니며, 외부 애플리케이션도 Action을 통해 써야 합니다. 규칙은 모든 경로가 거쳐 가는 곳에 있어야 합니다. 또 Action을 실행하려면 서로 독립적인 여러 층(Action 실행 권한, 객체 편집 권한, 객체의 마킹, 조건)을 모두 통과해야 하므로, 거부되었다면 층별로 진단하십시오.

3층: 로직은 Function에 둔다

고정된 규칙으로 계산하는 펌프의 위험 점수는 결정적이므로, TypeScript v2 또는 Python Function에 둡니다. 둘 중 무엇을 쓸지는 필요한 라이브러리와 유지 보수할 팀으로 정합니다. "이번 분기 고장이 가장 많은 펌프 상위 5개"는 서버 측 필터와 그룹 집계로 처리합니다. 모든 Inspection을 메모리에 올려 반복문을 돌리거나, 결과 한 페이지로 합계를 내서는 안 됩니다. Action 뒤에 있는 Function은 모든 편집을 한꺼번에 반환하고, Action이 한 번의 제출로 이를 적용합니다. 공유 Function에 호환성을 깨는 변경이 필요하면 새 버전을 게시하고, 새 매개변수는 기본값이 있는 선택 항목으로 추가하고, 소비자를 계획적으로 옮기십시오.

4층: Workshop으로 만드는 감독자 화면

검토 대기열은 불합격한 점검의 테이블입니다. 그 선택 변수가 상세 패널에 값을 넘기고, Approve와 Reject Action을 미리 채웁니다. 위젯마다 따로 쿼리를 두지 말고 변수 단위로 생각하십시오. 시험에 자주 나오는 내용은 다음과 같습니다.

  • 매일 바뀌면서 수천 개 행의 정렬에 쓰이는 값은 모듈에서 행마다 계산하지 말고, 파이프라인이 속성으로 저장해야 합니다.
  • 변수는 의존하는 것이 바뀌면 다시 계산됩니다. 불필요한 의존성을 없애고 숨겨진 탭은 지연 로드(lazy load)하십시오. 로딩 스피너는 느린 속도를 해결하지 못합니다.
  • Action 실행 후에는 고정된 지연 시간 대신 완료 이벤트로 의존 위젯을 새로 고치십시오.
  • 임베드된 모듈의 입력과 출력은 계약입니다. 호환되는 변경은 추가하는 변경입니다.

초보자 팁: 이 예제를 종이 한 장에 그려 보십시오. 키와 링크 카디널리티를 적은 객체 유형, Action, Function, 모듈, 포털, 자동화입니다. 그리고 틀린 연습 문제마다 그 해결책을 알맞은 칸에 적어 넣으십시오. 몇 번 하고 나면, 자꾸 헷갈리는 경계가 종이에 드러납니다. 그 도메인을 다시 공부하면 됩니다.

5층: 협력업체 포털, Workshop인가 OSDK인가

내부용 폼과 테이블에는 Workshop이 맞습니다. 맞춤 브랜딩, Foundry 계정이 없는 사용자, 기존 애플리케이션에 임베드하는 경우에는 OSDK가 필요합니다. 둘을 섞는 하이브리드 방식은 같은 Action과 Function을 공유합니다.

  • 애플리케이션을 등록할 때 사용하는 객체 유형과 Action을 정확히 나열한 스코프(scope)를 지정하십시오. 다른 Action이 필요한 새 기능에는 스코프 변경과 OSDK 재생성이 필요합니다.
  • 사람이 로그인한다면 사용자 기반 OAuth를 써서, 결과와 감사 기록에 개인이 반영되게 하십시오. 실제 접근 권한은 앱의 스코프와 사용자 권한의 교집합입니다. Workshop에서 Action을 실행할 수 있는 사용자라도, 스코프에 그 Action이 없는 앱으로는 실행할 수 없습니다.
  • 헤드리스 잡에는 서비스 기반 클라이언트 자격 증명을 쓰고, 시크릿은 서버에 둡니다. 프런트엔드 코드에 들어간 시크릿은 교체하고 옮겨야 합니다.
  • 페이지 토큰이 없어질 때까지 따라가십시오. 클라이언트에서 합산하지 말고 그룹 집계를 쓰십시오.
  • 액세스 토큰의 수명(expires_in)이 지난 뒤부터 호출이 실패한다면, 만료된 토큰을 갱신하지 않고 있는 것입니다.

6층: Automate로 만드는 후속 작업

"점검이 불합격하면 후속 작업을 만든다"는 새 상태에 조건을 건 이벤트 트리거입니다. 기한이 지난 작업을 매주 월요일에 요약하는 것처럼 주기적인 작업에는 스케줄을 쓰십시오. 임계값은 전이(transition)입니다. Automate의 임계값 조건은 기준을 넘나드는 순간(양방향 모두)에 실행되며, 측정값이 기준을 넘어 있는 동안 검사할 때마다 실행되지는 않습니다. 두 가지 사실에서 많은 점수가 나옵니다.

  • 조건과 Action 및 Logic 효과는 자동화 소유자의 권한으로 실행되고, 알림은 각 수신자의 권한을 씁니다. 소유권은 떠날 수 있는 개인이 아니라, 팀이 관리하는 최소 권한 서비스 사용자에게 두어야 합니다.
  • 실행은 최소 한 번(at least once)이므로 효과는 멱등이어야 합니다. 후속 작업을 만들기 전에 이미 있는지 확인하고, 외부 호출에는 멱등 키를 함께 보내십시오. 여러 Action 효과의 실행 순서는 보장되지 않습니다.

7층: AI가 도움이 되는 곳

점검자의 자유 텍스트 메모를 정해진 고장 유형 목록으로 분류하는 것은 AIP Logic에 잘 맞는 작업입니다. 출력은 그 정해진 목록 안의 값으로 제한하고, 신뢰도 값으로 불확실한 항목을 분류 담당(triage)에게 보냅니다. 고장 유형별 라우팅, 위험 점수, 권한 검사는 결정적으로 유지합니다. AI 제안 값과 사람이 확인한 값은 별도 속성에 저장하고, 확인 값은 Action으로 기록하십시오. AI FDE가 생성한 코드는 게시하기 전에 실제 스키마, 서버 측 쿼리, 거버넌스가 적용된 편집, 멱등한 부수 효과를 기준으로 검토합니다.

8층: 보안과 운영

앱을 열 수 있는지는 애플리케이션 리소스에 대한 접근 권한에 달려 있습니다. 앱 안의 데이터를 볼 수 있는지는 객체 유형과 그 바탕 데이터에 달려 있습니다. 지역별 가시성은 객체 보안 정책으로, 민감한 속성은 속성 수준 통제로 처리합니다. 필수 검토를 요구하는 브랜치 보호가 프로덕션의 Action과 Function을 지킵니다. 운영에서는 Action 실패, Function 지연 시간, 자동화 실패, 데이터 신선도, Ontology 인덱싱 지연을 모니터링하십시오. 빌드가 성공한 뒤에도 값이 한동안 예전 상태로 남아 있다면 인덱싱을 의심하십시오.

학습 순서

  1. Ontology 스키마 설계, 그다음 Action 유형. 다른 도메인 대부분이 이 위에 세워집니다.
  2. Function, 그다음 Workshop.
  3. OSDK와 외부 애플리케이션, 그다음 Automate.
  4. AI 기능, 그다음 애플리케이션 보안과 운영. 마지막으로 시간을 재며 여러 도메인을 섞은 세트.
