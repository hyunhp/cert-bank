Terraform Infrastructure Engineer Professional 시험은 이미 프로덕션에서 Terraform을 운영하는 사람을 위한 시험입니다. 명령이 무엇인지 묻는 문제는 드뭅니다. 이상하게 동작하는 구성, 플랜, 파이프라인을 보여 주고 그 이유나 결과를 묻습니다. 이 문제은행의 TF-IEP002 문제 252개 중 105개(42%)가 문제 해결 시나리오로, 이 문제은행의 Terraform Associate (004) 문제(266개 중 55개)보다 비율이 약 두 배입니다. 그래서 이 가이드는 네 가지 추적법을 알려 드립니다. 값 따라가기, 주소 따라가기, 시크릿 따라가기, 실행(run) 따라가기입니다. 거의 모든 시나리오는 이 중 하나로 풀립니다.

시험 요약

객관식이며, 온라인 감독 방식으로 영어로 90분 동안 치르고, Terraform 1.15를 기준으로 합니다. HashiCorp는 문제 수, 합격 점수, 도메인별 비중을 공개하지 않으니 공식 시험 페이지를 확인하십시오. 이 문제은행의 연습 세트는 내용을 일곱 영역으로 나눕니다. 구성(configuration), 상태 관리와 업그레이드, 워크플로와 수명 주기, CI/CD, 보안·시크릿·규정 준수, 모듈과 레지스트리, HCP Terraform 운영입니다. 이 이름은 이 문제은행의 분류일 뿐 공식 도메인 이름이 아닙니다. 이 문제은행 문제의 약 18%는 답을 두 개 이상 고르는 문제입니다. 문제에 개수가 적혀 있으면 정확히 그 개수만큼 고르십시오.

추적 1: 값 따라가기

리소스에 잘못된 값이 들어갔다면, 그 값이 거쳐 왔어야 할 사슬을 따라가 보십시오. tfvars 파일이나 -var가 루트 변수를 설정하고, 변수가 local로 흘러가고, local이 인수로 흘러갑니다. 모듈이라면 루트가 값을 명시적으로 넘겨야 합니다. 흔히 끊기는 곳은 다음과 같습니다.

  • 모듈 호출에서 값을 넘기지 않습니다. 루트는 instance_type을 설정했지만 module 블록이 넘기지 않아서, 하위 모듈이 자체 기본값을 씁니다. 모듈 사이에서는 이름만으로 공유되는 것이 없습니다.
  • null과 빈 문자열. var.name != null은 ""에 대해 참이므로 빈 문자열이 그대로 흘러갑니다. coalesce()는 null과 빈 문자열을 모두 건너뜁니다. 호출하는 쪽이 null을 넘기면, 변수를 nullable = false로 선언하지 않은 한 기본값을 덮어씁니다.
  • 템플릿이 값을 보지 못합니다. templatefile() 안에는 vars 객체의 키만 존재합니다. 넘기지 않은 모듈 변수를 쓰면 오류가 납니다.
  • 모듈은 닫힌 상자입니다. module.network.aws_subnet.private.id는 오류입니다. 모듈 밖으로 나가는 것은 선언된 출력(output)뿐입니다.
  • merge는 얕게 합칩니다. 두 번째 인수에 있는 중첩 tags 맵이 첫 번째 맵을 통째로 대체합니다.

초보자 팁: 이 도메인을 공부하는 동안 terraform console을 열어 두십시오. 연습 문제에 나오는 함수를 보기를 보기 전에 직접 입력해 봅니다. cidrsubnet("10.1.0.0/16", 4, 3), element(["a","b","c"], 4), try(...), merge(...), ...가 있을 때와 없을 때의 for 식 같은 것들입니다. 곧 Enter를 누르기 전에 결과를 예측하게 됩니다. 시험이 측정하는 능력이 바로 그것입니다.

더 깊이: 추측 없이 cidrsubnet 결과 예측하기

cidrsubnet(prefix, newbits, netnum)은 프리픽스를 newbits만큼 늘리고, 0부터 세어 netnum번째 서브넷을 고릅니다. ("10.1.0.0/16", 4, 3)이라면 /16에 4비트를 더해 /20이 됩니다. /20에는 주소가 4,096개 있고, 이는 셋째 옥텟에서 16씩 증가하는 크기입니다. 그래서 서브넷 N은 셋째 옥텟 N × 16에서 시작합니다. 따라서 서브넷 3은 10.1.48.0/20입니다. 흔한 실수는 새 비트 수를 곱하는 것입니다(3 × 4 = 12). 블록 크기를 먼저 구하고, 그다음 위치를 구하십시오. cidrhost도 네트워크 주소에서 같은 방식으로 계산하며, 블록 끝을 넘는 인덱스는 오류입니다.

추적 2: 주소 따라가기

Terraform은 모든 인스턴스를 전체 주소로 추적합니다. 아무도 건드릴 생각이 없던 것을 플랜이 삭제하려 한다면 주소가 바뀐 것입니다. 무엇이 이름을 바꿨는지 물어보십시오.

  • count 위치가 밀립니다. 리스트 가운데 요소를 지우면 그 뒤의 모든 인덱스가 다른 항목을 가리키게 되어, 수정되거나 교체됩니다. for_each는 키를 쓰므로 지운 키만 사라집니다.
  • for_each 규칙. 리스트가 아니라 맵이나 문자열 집합(set)을 받습니다. 키는 플랜 시점에 알려져 있어야 하므로, 같은 apply에서 만들어지는 ID는 키가 될 수 없습니다. 민감한(sensitive) 값도 키로 쓸 수 없습니다.
  • 리팩터링에는 moved가 필요합니다. 블록 이름 변경, for_each로 전환, 키 이름 변경에는 모두 moved 블록이 필요하며, 필요하면 인스턴스마다 하나씩 둡니다. 단일 리소스에 count를 추가하는 경우는 예외로, Terraform이 기존 객체를 인덱스 [0]으로 옮기도록 알아서 제안합니다. 그래도 moved 블록을 명시하는 것이 권장됩니다. 공유 모듈 안에 넣어 배포하면, 모든 사용자의 상태가 다음 플랜에서 고쳐집니다. state mv라면 상태마다 손으로 실행해야 합니다.
  • 삭제하지 않고 관리만 중단하기. lifecycle { destroy = false }를 넣은 removed 블록을 쓰십시오. 코드에 리소스 블록이 남아 있는 상태에서 state rm을 실행하면 다음 apply에서 중복 리소스가 생깁니다.
  • 상태 간 연결은 보이지 않습니다. 다른 구성이 terraform_remote_state로 읽는 출력의 이름을 바꾸면, 그 구성들은 다음 플랜에서 깨집니다. 기존 출력 옆에 새 출력을 추가하고, 사용하는 쪽을 옮긴 뒤, 기존 출력을 지우십시오.

추적 3: 시크릿 따라가기

보안 시나리오마다 값이 결국 어디에 남는지 물어보십시오. 화면, 상태, 플랜 파일, 로그, 버전 관리 중 어디입니까?

기법값이 여전히 남는 곳
sensitive = true화면에서는 숨겨짐. 상태와 저장된 플랜 파일에는 여전히 평문으로 남음. terraform output -json은 값을 출력함.
ephemeral 리소스나 변수영구적으로 남는 곳 없음. 프로바이더 블록, local, 쓰기 전용 인수처럼 저장되지 않는 곳에서만 쓸 수 있음.
쓰기 전용 인수(_wo)프로바이더로 보낸 뒤 버림. 프로바이더 지원이 필요함.
커밋된 tfvars 파일Git 기록, 클론, 포크. 먼저 시크릿을 교체하고, 그다음 파일을 지울 것.
동적 프로바이더 자격 증명실행마다 수명이 짧은 ID 토큰 하나. 저장된 키가 전혀 없음. 클라우드 신뢰 정책은 토큰의 audience와 subject에 맞춰야 함.
더 깊이: 쓰기 전용 비밀번호를 교체했는데 "No changes"가 나오는 이유

Terraform은 쓰기 전용 값의 사본을 보관하지 않습니다. 그래서 새 값과 이전 값을 비교할 수 없고, 비밀번호만 바뀌어서는 차이(diff)가 생기지 않습니다. 그래서 프로바이더는 이런 인수를 password_wo_version 같은 버전 인수와 짝지어 둡니다. 이 숫자는 Terraform이 저장합니다. 새 값과 같은 변경에서 이 숫자를 올리면 플랜이 비교할 대상이 생기고, 프로바이더는 업데이트로 인식해 새 쓰기 전용 값을 보냅니다. 파이프라인이 교체된 시크릿을 넘겼는데 데이터베이스가 이전 비밀번호를 유지하는 시나리오는 바로 이것을 시험합니다. 버전을 시크릿 저장소 자체의 버전 메타데이터에 연결해 두면, 교체가 곧 업데이트로 이어집니다.

추적 4: 실행 따라가기

많은 시나리오는 사실 실행이 어디에서 어떻게 이루어지는지에 관한 것입니다.

  • 검토했다고 적용된 것은 아닙니다. 플랜 하나를 승인한 뒤 플랜 파일 없이 apply -auto-approve를 실행하는 파이프라인은 새 플랜을 적용합니다. -out으로 저장하고 그 파일을 적용하십시오. 오래된 저장 플랜은 거부됩니다. 이 파일에는 민감한 값이 평문으로 들어 있고 프로바이더는 포함되지 않으므로, apply 잡은 같은 잠금 파일(lock file)로 init을 실행해야 합니다.
  • 종료 코드. -detailed-exitcode는 0(변경 없음), 1(오류), 2(변경 있음)를 반환합니다. 0이 아닌 코드에서 모두 실패하는 스크립트는 정상 플랜에서도 깨집니다.
  • 잠금. 기본 -lock-timeout은 0s이므로 두 번째 파이프라인은 즉시 실패합니다. 타임아웃을 추가하거나 잡을 직렬화하십시오. force-unlock은 잠금을 가진 쪽이 정말 죽었을 때만 쓰십시오.
  • 워크스페이스와 변수 파일이 어긋납니다. workspace select dev 다음에 -var-file=prod.tfvars를 써도 오류가 나지 않습니다. 둘을 연결하는 것이 없습니다.
  • HCP Terraform 실행 모드. local 모드에서는 아무것도 주입되지 않으므로, 변수 세트(variable set)에 둔 자격 증명은 노트북에 전달되지 않습니다. 에이전트는 아웃바운드 연결만 있으면 됩니다. 모드를 바꾸면 이미 플랜을 마친 실행이 깨집니다.
  • VCS 트리거. 경로 기반 트리거("Only trigger runs when files in specified paths change")를 쓰면, 공유 모듈 폴더처럼 지정한 경로 밖의 변경은 트리거 패턴이나 프리픽스에 포함하기 전까지 실행을 시작하지 않습니다. 새 워크스페이스는 첫 실행을 손으로 시작해야 합니다.
  • 정책. Sentinel에는 advisory, soft-mandatory, hard-mandatory 수준이 있고, OPA에는 advisory와 mandatory가 있습니다. 적용 범위는 정책 세트(policy set)에서 정합니다.

두 보기가 모두 맞아 보일 때의 판단 기준

권한이 가장 적고, 적용 전에 검토되며, Terraform 1.15의 문서화된 동작과 일치하는 보기를 고르십시오. 일상적인 -target, -lock=false, 백엔드 오류를 없애려는 -reconfigure(기존 상태를 마이그레이션하지 않습니다), 프로덕션 접근 경계로 쓰는 CLI 워크스페이스는 의심하십시오. 문제에 나오지 않은 조건에 기대는 보기는 오답일 가능성이 큽니다.

학습 순서

  1. 구성: 값 추적, 함수와 식, count와 for_each, 사용자 정의 조건.
  2. 상태: 백엔드, 잠금, 마이그레이션, 드리프트, moved와 removed, CLI와 프로바이더 업그레이드.
  3. 워크플로: 프로젝트 분리, 플랜 모드, 저장된 플랜, import, 환경, 실패한 실행.
  4. 파이프라인과 시크릿을 함께. 보안 문제 대부분이 파이프라인 안에서 일어나기 때문입니다.
  5. 모듈과 terraform test, 그다음 HCP Terraform 운영. 마지막으로 시간을 재며 여러 영역을 섞은 세트.
