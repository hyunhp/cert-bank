Associate Cloud Engineer는 Google Cloud 자격증 중 가장 실무에 가까운 시험 중 하나입니다. 다음에 무엇을 입력하고, 무엇을 클릭하고, 어떤 권한을 부여할지 묻습니다. 가장 쉬운 공부법은 프로젝트 하나의 일생을 직접 겪어 보는 것입니다. 프로젝트를 만들고, 비용을 연결하고, 워크로드를 올리고, 계속 돌아가게 하고, 누가 손댈 수 있는지 정합니다. 이 가이드는 그 순서를 따르며, 단계마다 권한 문제가 어디서 다시 등장하는지 짚어 줍니다. 이 시험에서는 권한이 언제나 다시 나오기 때문입니다.

학습 가이드 · Google Cloud Certified Associate Cloud Engineer (GCP-ACE)

시험 개요

2시간 동안 단일 선택과 복수 선택 문제 50–60문항을 풉니다. Google은 합격 점수를 공개하지 않고 합격 또는 불합격만 알려 줍니다. 최신 내용은 공식 시험 페이지에서 확인하고, 추측한 기준선보다 훨씬 높은 점수를 목표로 하십시오. 섹션은 네 개이며, 비중은 대략 다음과 같습니다. Setting up a cloud solution environment(클라우드 솔루션 환경 설정, 20%), Planning and implementing a cloud solution(클라우드 솔루션 계획 및 구현, 30%), Ensuring the successful operation of a cloud solution(클라우드 솔루션의 원활한 운영 보장, 30%), Configuring access and security(액세스 및 보안 구성, 20%).

이 문제은행의 GCP-ACE 문제 275개에서 나온 두 가지 수치가 이 가이드의 관점을 설명해 줍니다. 첫째, IAM이 단연 가장 자주 나오는 서비스입니다. 76문항에 등장하며, 그중 21문항은 액세스 및 보안 섹션 밖에 있습니다. 둘째, 78문항(28%)은 지문이나 보기에 gcloud, kubectl, bq가 나오며, 거의 모두 완전한 명령 형태입니다. 명령을 외워서 쓸 필요는 없지만, 명령을 읽고 무슨 일을 하는지 알아볼 수 있어야 합니다.

1단계: 빈 조직과 청구서

모든 것은 리소스 계층에서 시작합니다. 조직, 폴더, 프로젝트, 리소스입니다. 이 계층을 따라 두 종류의 규칙이 아래로 흐르며, 시험은 둘을 분명히 구분합니다.

  • IAM 허용 정책(allow policy)은 누가 작업할 수 있는지 정합니다. 부여한 권한은 트리를 따라 내려가며 쌓입니다. 폴더에 부여한 역할은 그 아래 모든 프로젝트에 미칩니다.
  • Organization Policy는 프로젝트 소유자를 포함한 모든 사람에게 어떤 구성이 허용되는지 정합니다. 허용 위치, 기본 네트워크 금지, 서비스 계정 키 금지 같은 것입니다.

새 조직 정책은 보통 이미 존재하는 리소스에는 영향을 주지 않습니다. "어제 제약 조건을 설정했는데 왜 지난달 만든 VM은 여전히 잘못된 리전에 있는가?"라는 문제라면 이것이 정답입니다. 해결책은 기존 리소스를 찾아(예: Cloud Asset Inventory) 직접 고치는 것입니다.

결제는 첫날 해야 할 일의 나머지 절반입니다. 결제 역할별로 무엇을 하는지 알아 두십시오. Billing Account User는 프로젝트를 결제 계정에 연결하는 것만 허용합니다. Billing Account Costs Manager는 연결을 통제하지 않고 예산과 비용 내보내기를 다룹니다. Billing Account Viewer는 재무 담당자가 비용을 조회할 때 씁니다. Project Billing Manager는 프로젝트 하나를 연결하거나 연결 해제합니다. 누구나 한 번은 걸리는 함정이 있습니다. 알림 전용 예산은 이메일을 보낼 뿐 지출을 절대 멈추지 않습니다. 자동으로 조치하려면 예산을 Pub/Sub 주제에 연결하고 코드가 응답하게 해야 합니다.

초보자 팁: 더 읽기 전에 무료 체험 프로젝트를 만들어 1단계를 직접 해 보십시오. 적은 금액과 기본 임계값 50/90/100%로 예산을 만들고, IAM을 열어 두 번째 Google 계정에 프로젝트의 Viewer 역할을 주십시오. 그 계정으로 로그인해 Cloud Storage 버킷을 만들어 보십시오. 이때 받는 오류 메시지에는 빠진 권한 이름이 나옵니다. 많은 문제 해결 문제가 바로 이 상황을 글로 설명하므로, 한 번 보고 나면 머릿속에 쉽게 그려집니다.

2단계: 워크로드 올리기

계획 섹션은 "어떤 제품이 맞는가"를 고르는 선택의 연속이며, 각 선택에는 결정적인 표현이 하나씩 있습니다.

지문에 나오는 표현떠올릴 것
특정 OS, 드라이버, 그대로 옮기는 레거시 앱Compute Engine. 확장과 자동 복구(autohealing)에는 인스턴스 템플릿 기반의 관리형 인스턴스 그룹
상태 비저장 컨테이너, 0까지 축소, 운영 부담이 적음Cloud Run
많은 컨테이너, Kubernetes 역량, 노드 제어GKE Standard. Google이 노드를 관리해야 한다면 GKE Autopilot
파일이 도착하거나 메시지가 들어오면 코드 실행Eventarc 또는 Pub/Sub과 함께 쓰는 Cloud Run functions
중단되어도 되는 배치 작업스팟 VM(Spot VMs)

예전 자료로 공부했다면 두 가지 이름 변경 때문에 점수를 잃을 수 있습니다. Container Registry는 서비스가 종료되었고(정답은 Artifact Registry), Cloud Deployment Manager는 지원이 종료되었습니다(정답은 Infrastructure Manager 또는 Terraform).

여기서도 권한이 다시 나옵니다. Cloud Run 서비스는 호출자 검사(invoker check)를 끄지 않는 한 모든 호출자에게 Cloud Run Invoker 역할을 요구합니다. 공개 웹사이트라면 이 검사를 끄는 것이 문서에 나온 방법입니다. 도메인 제한 공유(domain restricted sharing)를 쓰는 조직은 allUsers에 대한 권한 부여를 거부하기 때문입니다. VM은 연결한 서비스 계정으로 실행되며, 서비스 계정을 연결하려면 그 서비스 계정에 대한 역할이 필요합니다.

더 깊이: 연결과 가장(impersonate)의 차이, 그리고 역할을 서비스 계정에 부여하는 이유

서비스 계정은 ID인 동시에 자체 허용 정책을 가진 리소스입니다. 서비스 계정을 VM이나 Cloud Run 서비스에 연결하려면 Service Account User에 포함된 iam.serviceAccounts.actAs 권한이 필요합니다. 노트북이나 스크립트에서 직접 그 서비스 계정으로 행동하려면 단기 토큰을 요청해야 하며, 여기에는 Service Account Token Creator가 필요합니다. 두 역할 모두 프로젝트가 아니라 해당 서비스 계정 하나에 부여하십시오. 프로젝트 수준으로 부여하면 더 강력한 계정을 포함해 프로젝트의 모든 서비스 계정에 적용되므로, 작은 권한 부여가 권한 상승의 통로가 됩니다. 그래서 정답이 "프로젝트에"가 아니라 "서비스 계정에 역할을 부여한다"인 경우가 그토록 많습니다. 시험이 키를 다운로드하는 것보다 가장을 선호하는 이유도 가장으로 얻는 토큰이 단기 토큰이기 때문입니다. 키는 어디서든 동작하며, 정책으로 강제하지 않는 한 만료되지 않습니다.

3단계: 계속 돌아가게 하기

계획 섹션과 함께 비중이 가장 큰 섹션(30%)이며, 저희 문제 은행에서 문제 해결 문제가 가장 많은 섹션입니다(83문항 중 29문항). 운영 도구는 각 도구가 답하는 질문으로 익히십시오.

  • "누가 이것을 바꿨는가?" 항상 켜져 있는 관리자 활동(Admin Activity) 감사 로그. "누가 이 데이터를 읽었는가?" 데이터 액세스(Data Access) 감사 로그. 일부 BigQuery 서비스를 제외한 모든 서비스에서 기본적으로 꺼져 있습니다. 아무도 켜지 않았다면 해당 기록은 애초에 존재하지 않으며, 지금 켜도 지금부터만 기록됩니다.
  • "고장 나면 알려 달라." 메트릭 임계값(metric-threshold) 조건이 있는 알림 정책. "신호가 끊기면 알려 달라." 데이터가 더 이상 들어오지 않을 때 발생하는 메트릭 부재(metric-absence) 조건.
  • "이런 잡음은 그만 저장하라." _Default 싱크의 제외 필터. "로그를 다른 곳으로 보내라." BigQuery, Cloud Storage, Pub/Sub, 다른 프로젝트로 보내는 싱크. 싱크의 작성자 ID(writer identity)에는 대상에 대한 역할이 필요합니다.
  • "누군가 객체를 삭제했다." 일시 삭제(soft delete, 새 버킷은 기본으로 켜져 있으며 7일)로 복원합니다. 객체 버전 관리(Object Versioning)는 활성화한 시점부터만 이전 버전을 보관합니다.
  • "트래픽이 막혔다." 방화벽 규칙: 우선순위 숫자가 가장 낮은 규칙이 이기고, 거부가 허용을 이기는 것은 우선순위가 같을 때뿐이며, 경로(route)는 길을 고를 뿐 트래픽을 허용하지는 않습니다.

여기서는 명령이 나온다고 예상하십시오. 문제에 gcloud compute firewall-rules update RULE --disabled를 보여 주고 어떤 일이 일어나는지 물을 수 있습니다. 규칙은 설정을 유지하지만 적용되지 않습니다.

4단계: 누가 무엇을 할 수 있는지 정하기

액세스 섹션은 앞의 내용을 하나로 묶습니다. 카드에 적어 둘 만한 규칙은 다음과 같습니다.

  1. 최소 권한이란 가장 작은 리소스에 가장 좁은 역할을 주는 것입니다. 프로젝트의 Editor가 아니라 주제 하나의 Pub/Sub Publisher입니다.
  2. 실제 액세스 권한은 리소스의 정책과 모든 상위 리소스 정책의 합집합입니다. 같은 역할이 폴더에 부여되어 있는 한, 프로젝트의 권한 부여를 제거해도 아무것도 바뀌지 않습니다.
  3. Owner, Editor, Viewer는 이제 레거시 기본 역할이며 IAM Conditions를 붙일 수 없습니다. 현재 기본 역할은 Admin, Writer, Reader입니다. 운영 환경에서는 사전 정의 역할을 선호하십시오.
  4. 커스텀 역할은 조직 또는 프로젝트 수준에만 존재하며, 폴더에는 만들 수 없습니다.
  5. 거부 정책(deny policy)은 허용 정책보다 먼저 확인되며, 어떤 허용 역할도, 심지어 Owner도 이를 무시할 수 없습니다.
더 깊이: 상속된 권한을 하위 수준에서 제거할 수 없는 이유

IAM 허용 정책은 권한을 더하기만 합니다. Google Cloud는 요청을 확인할 때 리소스와 모든 상위 리소스의 허용 정책을 모아서, 그중 하나라도 해당 권한을 부여하는지 봅니다. 하위 수준에는 "여기만 제외"라고 말할 방법이 없으므로, 폴더 전체에 부여한 권한을 프로젝트 하나에서 취소할 수 없습니다. 실제 해결책은 두 가지입니다. 권한을 부여한 곳에서 바꾸거나, 먼저 평가되고 아래로 상속되는 거부 정책을 연결하는 것입니다. 문서에 나온 패턴은 "위에서 부여하고, 예외는 거부한다"입니다. 거부 조건은 리소스 태그만 인식하므로, 운영 프로젝트를 예외로 두려면 태그를 붙이고 그 태그로 조건을 작성합니다. 거부 정책을 관리하려면 별도의 역할(Deny Admin)이 필요하며, Owner에는 포함되어 있지 않습니다.

하나의 리소스 계층, 그 아래로 흐르는 두 종류의 규칙
조직
Organization Policy: 허용되는 구성을 정함 · 보통 기존 리소스에는 영향 없음 · 커스텀 역할을 둘 수 있음
폴더
여기에 부여한 역할은 아래 모든 프로젝트에 미침 · 커스텀 역할 불가
프로젝트
결제 계정에 연결됨 · 커스텀 역할을 둘 수 있음 · 폴더가 부여한 권한은 여기서 제거해도 소용없음
리소스
실제 액세스 권한: 자신과 모든 상위 리소스 허용 정책의 합집합 · 거부 정책은 Owner를 포함한 모든 허용보다 우선
허용 권한과 정책은 위에서 아래로 흐릅니다. 상위 수준이 부여한 것을 하위 수준에서 제거할 수 없습니다.

학습 순서

  1. 실제 프로젝트에서 계층, 조직 정책, 결제 역할과 예산(1단계).
  2. IAM과 서비스 계정을 일찍. 이후의 모든 주제가 이것에 기대기 때문입니다.
  3. Compute, GKE, Cloud Run, 스토리지 클래스와 데이터베이스.
  4. VPC 네트워크, 방화벽 규칙, Cloud NAT, Cloud DNS, 부하 분산기.
  5. 로깅, 모니터링, 백업, 그다음 시간을 재며 혼합 연습 세트.
